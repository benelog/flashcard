= AI 에이전트와 일하기: 지시하고, 계획을 다듬고, 검증한다

{ch-tech-choices}에서 기술 조합을 정했다.
이 장에서는 그 조합을 AI 코딩 에이전트에게 지시해 앱의 골격을 만들기까지의 흐름을 따라간다.
지시문에 무엇을 담는지, 코드보다 계획을 먼저 받아 요구사항과 아키텍처를 어떻게 다듬는지, 에이전트가 만든 코드를 어디까지 믿을지를 차례로 짚어 보겠다.
어느 에이전트를 쓰든 통하는 이야기만 다룬다.

이 장도 읽는 장이다.
대화 예시는 Flashcard를 시작하던 과정을 재구성한 것이고, 직접 설치해 띄우는 일은 {ch-first-run}에서 한다.

== 지시문: 시나리오, 기술 스택, 범위

에이전트는 모호한 지시를 받으면 그럴듯한 해석을 하나 골라 진행한다.
기술 스택을 못 박지 않으면 학습 데이터에서 가장 많이 본 조합으로 기운다.
"암기 카드 웹 앱을 만들어 줘"라고만 하면 React와 Node.js 기반의 골격이 돌아올 가능성이 크다.
그러면 {ch-tech-choices}에서 따져 내린 결론이 첫 응답에서 무의미해진다.

Flashcard의 시작 지시문을 재구성하면 다음과 같다.

[source,text]
----
암기 카드 웹 앱을 만들려고 한다. 코드를 만들기 전에 계획부터 세워 달라.

[기능]
- 사용자는 덱을 만들고 카드(원문 text, 뜻 meaning)를 담는다.
- 학습: 방향(원문→뜻, 뜻→원문)을 고르고, 카드를 뒤집어 스스로
  맞음/틀림을 판정한다. 덱을 한 바퀴 돌면 틀린 카드만 모아
  재도전 라운드를 반복한다.
- 복습: SM-2를 맞음/틀림 두 값으로 단순화한 간격 반복으로
  "오늘 복습" 큐를 만든다.

[기술: 바꾸지 말 것]
- 백엔드: Go + Gin. 화면도 서버에서 html/template으로 렌더링하고,
  부분 갱신은 htmx를 쓴다. React 같은 브라우저 렌더링 프레임워크 금지.
- 데이터베이스: SQLite 파일 하나. 단, 나중에 PostgreSQL로 바꿀 수 있게
  DB 접근을 인터페이스 뒤로 모은다.
- CSS는 프레임워크 없이 파일 하나. 브라우저 자바스크립트는 최소로.

[지금 만들지 않는 것]
- 로그인, 배포 설정, 통계 화면. 골격이 돈 다음에 붙인다.
----

SM-2는 1987년 SuperMemo가 만든 복습 일정 계산 방식으로, Anki를 비롯한 간격 반복 앱들이 이를 바탕으로 삼는다.footnote:[SM-2는 1987년 12월의 SuperMemo 1.0부터 쓰였고(https://super-memory.com/english/ol/sm2.htm[SuperMemo의 SM-2 알고리즘 설명]), Anki의 기본 알고리즘도 SM-2에 기반한다(https://faqs.ankiweb.net/what-spaced-repetition-algorithm.html[Anki FAQ]).]
원래는 답을 여섯 단계로 평가하지만, {ch-requirements}에서 정한 대로 맞음과 틀림 두 값만 쓰게 했다.

지시문의 세 부분은 맡은 일이 다르다.

첫째, 기능은 목록이 아니라 시나리오로 적었다.
동작의 순서와 규칙이 문장에 있어야 에이전트가 화면과 데이터의 모양을 스스로 도출한다.

둘째, 기술 스택에 "바꾸지 말 것"이라는 딱지를 붙였다.
이유까지 설명할 필요는 없지만, 협상할 수 없다는 사실은 분명히 한다.

셋째, 지금 만들지 않는 것을 적었다.
내버려 두면 첫 골격에 로그인과 통계 화면까지 딸려 온다.
범위를 좁히는 문장은 뒤에서 볼 "커밋 단위로 나눠 만들기"의 출발점이기도 하다.

== 코드보다 계획을 먼저 받는다

지시문 첫 줄에 "계획부터 세워 달라"고 적었다.
많은 에이전트가 파일을 고치지 못하게 잠근 채 계획만 내놓는 모드를 따로 두는데, 그런 모드가 있으면 켜는 쪽이 확실하다.
코드가 나온 뒤에 방향을 고치려면 만들어진 파일을 걷어내야 하지만, 계획은 문장 몇 줄이라 몇 분이면 고쳐 받는다.

계획에는 대체로 디렉터리 구조, 테이블 초안, 화면과 라우트(주소별 처리 경로) 목록, 구현 순서가 담겨 온다.
점검할 것은 세 가지다.

첫째, 요구사항 해석이 맞는가.
재도전 라운드가 "틀린 카드만 모아 반복"으로 잡혔는지, 카드가 원문/뜻의 대칭 구조인지 본다.

둘째, 기술 스택이 지시대로인가.
의존성 목록에 프런트엔드 빌드 도구나 ORM(SQL 대신 코드로 데이터베이스를 다루게 하는 라이브러리)이 슬쩍 들어와 있지 않은지 본다.

셋째, 범위가 부풀지 않았는가.
"지금 만들지 않는 것"이 계획에 들어와 있으면 빼 달라고 한다.

=== 계획을 사이에 둔 대화가 요구사항을 다듬는다

계획의 진짜 값어치는 그것을 사이에 둔 대화에서 나온다.
계획을 세우던 에이전트가 이렇게 되물었다.

"재도전 라운드에서 맞힌 답도 SRS 채점에 반영합니까?"

답은 반영하지 않는다는 것이다.
방금 본 카드를 다시 맞힌 것은 장기 기억의 성공이 아니기 때문이다.
그런데 요구사항을 처음 적을 때는 이 경우를 생각하지 못했다.
계획 단계의 질문이 스펙(요구사항 명세)의 빈틈을 드러냈고, 답을 정하면서 요구사항이 한 줄 늘었다.
앞의 지시문에 이 규칙이 없는 것도 그래서다.
요구사항은 구현 계획이라는 구체적인 그림 앞에 세워 봐야 빈틈이 드러난다.

아키텍처도 같은 방식으로 다듬어졌다.
초기안은 Go 서버를 무료 호스팅에 상주 서버로 올리는 흔한 구성이었다.
배포를 논의하던 중 "서버를 늘 켜 두지 않고 운영할 방법은 없나"라고 물었고, 에이전트가 Vercel이 Go를 서버리스 함수로 실행할 수 있다는 선택지를 트레이드오프 표와 함께 정리해 줬다.
상주 서버가 없어지면 관리할 인프라가 줄고 비용도 무료 티어 안에 들어오므로 그 안을 택했다.
다만 이렇게 얻은 정보는 틀릴 수 있어서, 실제로 Vercel에 올려 보고 확정했다.
그 첫 배포에서 Vercel의 Go 빌더가 `internal/` 아래 패키지를 가져오지 못해 앱 패키지를 `pkg/app`으로 옮긴 일이 저장소 이력에 남아 있다({ch-vercel}).

계획이 지시와 어긋나 있어도 실망할 일은 아니다.
어긋난 계획은 지시문의 어느 문장이 모호했는지 알려 주는 피드백이다.

구성 요소는 셋이다.
화면을 표시하는 브라우저, 화면 렌더링부터 JSON API까지 도맡는 Go 서버 하나, 데이터가 쌓이는 SQLite 파일이다.
앱을 공개할 때는 서버가 Vercel의 서버리스 함수로 옮겨 가고, 데이터베이스와 Google/GitHub 로그인은 Supabase가 맡는다.
어느 모드로 돌지는 서버를 실행할 때 환경 변수 `DATABASE_URL`이 있느냐로 정해진다.
값이 없으면 로컬 모드라, 계정 하나 만들지 않고도 3부까지의 실습을 내 컴퓨터만으로 따라갈 수 있다.

.[용어 풀이] 환경 변수(Environment Variable)
[NOTE]
====
프로그램이 실행될 때 운영체제에서 건네받는 이름표 붙은 값이다.
접속 주소나 비밀번호처럼 환경마다 달라지는 값을 코드에 적지 않고 바깥에서 주입하려고 쓴다.
같은 코드가 내 노트북에서는 로컬 데이터베이스를, 배포된 서버에서는 운영 데이터베이스를 바라보게 만드는 장치다.
값을 실제로 다루기 시작하는 곳은 {ch-supabase-db}부터다.
====

=== 화면: Go 서버가 렌더링하는 HTML

화면은 브라우저가 아니라 서버에서 만든다.
Go 서버가 표준 라이브러리의 템플릿 엔진(html/template)으로 완성된 HTML 문서를 만들어 보내고, 브라우저는 받은 문서를 그리기만 한다.
카드 한 장을 지우는 것 같은 부분 갱신은 htmx가 맡는다.
버튼에 적어 둔 속성대로 서버에 요청을 보내고, 돌아온 HTML 조각으로 화면의 해당 부분만 갈아 끼운다.
스타일은 프레임워크 없이 CSS 파일 하나(`internal/web/static/app.css`)이고, 어두운 테마도 이 파일 안에서 끝난다({ch-css-hello}).
직접 작성한 브라우저 자바스크립트는 음성 재생·클립보드 복사처럼 브라우저에서만 할 수 있는 일을 감싸는 파일 하나(`internal/web/static/app.js`, {n-app-js-lines}줄 남짓)뿐이다.
HTML과 CSS는 {ch-html-css}, 템플릿은 {ch-html-template}, htmx는 {ch-htmx}에서 다룬다.

=== 백엔드: Go와 Gin으로 만드는 서버 하나

백엔드는 Go와 웹 프레임워크 Gin으로 작성한 서버 하나다.
화면 렌더링, CSS 같은 정적 파일, 외부 프로그램이 쓸 JSON API(`/api/*`)를 이 서버가 전부 내보낸다.
정적 파일도 Go 바이너리 안에 내장(embed)하므로 배포 단위가 하나다.
화면과 API가 같은 주소에서 나오니, 주소가 다른 곳끼리 요청을 주고받을 때 따르는 제약(CORS) 문제도 생기지 않는다.
로컬에서는 `cmd/server`로 띄우는 평범한 HTTP 서버이고, 배포할 때는 같은 Gin 엔진을 Vercel 서버리스 함수 하나로 감싼다({ch-gin}, {ch-vercel}).

이 스택은 얼마나 적게 골랐는지가 특징이다.
Go 쪽의 직접 의존성은 Gin을 포함해 {n-direct-deps-ko-attr} 개가 전부다({ch-code-map}).
화면 쪽에는 패키지 매니저도 빌드 도구도 없고, 외부 라이브러리는 저장소에 파일째 넣어 둔 htmx 하나뿐이다.
개인 프로젝트에서 의존성 하나는 곧 업그레이드 부담 하나라, 표준 라이브러리와 프레임워크 기본 기능으로 되는 일에는 라이브러리를 더하지 않았다.

== 골격은 커밋 단위로 나눠 만든다

계획에 합의하면 구현으로 넘어가되, 전체를 한 번에 만들게 하지 않는다.
Flashcard의 첫 골격은 이런 순서였다.

첫째, 테이블 구조를 정의하는 스키마와 SQLite 연결.
둘째, SRS 채점 함수와 그 테스트.
값을 받아 값을 돌려주기만 하는 함수라 다른 것 없이도 옳은지 확인할 수 있다.
셋째, 덱과 카드의 Gin 라우트.
넷째, 화면 템플릿과 htmx 학습 흐름.

덩어리마다 `go build ./...`와 `go test ./...`가 통과하면 커밋한다.
대화가 길어지면 에이전트가 초반의 합의를 흐리게 기억하므로, 덩어리마다 대화를 새로 시작하는 쪽이 결과가 안정적이다.
사람도 검토 대상이 작아야 뒤에서 볼 검토 기준을 적용할 여유가 생긴다.

마지막 덩어리까지 끝나면 `go run ./cmd/server`로 서버를 띄우고 브라우저에서 `http://localhost:8080`을 연다.
덱을 만들고 카드를 뒤집어 보는 순간 {ch-requirements}의 요구사항이 처음으로 화면이 된다.
지금 따라 칠 필요는 없다.
{ch-first-run}에서 손에 넣는 것은 이 골격이 아니라 완성본이다.

== 합의는 AGENTS.md에 고정한다

계획을 다듬으며 내린 결정은 그 대화에만 남아 있고, 새 대화의 에이전트는 백지에서 시작한다.
그래서 결정을 프로젝트 지침 파일로 옮겨 둔다.

.[용어 풀이] 프로젝트 지침(`AGENTS.md`)
[NOTE]
====
프로젝트 폴더에 두면 에이전트가 작업을 시작할 때마다 읽어 들이는 안내 문서다.
자주 쓰는 명령, 폴더 구조, 이 프로젝트만의 규칙과 함정을 담아 두면 대화가 바뀌어도 같은 설명을 되풀이하지 않아도 된다.
새로 합류한 팀원에게 주는 온보딩 문서와 같다.
여러 에이전트가 이 이름을 읽으며, 도구에 따라 다른 파일 이름을 쓰기도 한다.
====

담을 것은 네 가지다.
첫째, 빌드·테스트·로컬 실행 같은 자주 쓰는 명령.
둘째, 디렉터리 구조와 계층 간 의존 방향의 요약.
셋째, 일반적인 관례와 다른 이 프로젝트만의 규약과 함정.
에이전트는 학습 데이터의 흔한 패턴을 기본값으로 삼으므로, 거기서 벗어난 곳을 알려 주지 않으면 그럴듯하지만 틀린 코드를 만든다.
넷째, 건드리면 안 되는 파일이나 실행하면 안 되는 명령 같은 금지 사항.

피할 것은 분량 욕심이다.
이 파일은 매번 에이전트의 기억에 실리므로, 길어질수록 중요한 지침이 묻히고 실제 작업에 쓸 몫이 줄어든다.

Flashcard 저장소에는 저장소 전체 규칙을 담은 루트의 `AGENTS.md`와 완성본 앱의 규칙을 담은 `flashcard-advanced/AGENTS.md`가 있고, 둘 다 백 줄이 안 된다.
다음은 두 파일에서 다섯 절을 골라 이어 붙인 발췌다.
맨 위 브랜치 정책은 루트 파일의 것이고({ch-git}에서 다룬다), 나머지 네 절은 앱 디렉터리 파일의 것이다.
낯선 이름은 뒤의 장에서 하나씩 다루니, 지금은 절 하나가 두어 줄로 끝난다는 것만 보면 된다.

# Flashcard 프로젝트 지침

## 브랜치 정책 (GitLab flow 단순화)

- `main`: 개발 브랜치. 모든 작업은 main에서 한다. main 푸시는 Vercel Preview 배포(개발 환경)로 이어진다.
- `release`: 운영 브랜치. 직접 커밋하지 않는다. 운영 배포는 main → release 병합으로만 한다.
- 두 브랜치 모두 push 전에 `./check.sh`가 통과해야 한다(CI도 같은 검사를 돌린다).

## 구조

- UI는 Go 서버가 렌더링한다: `internal/web` (html/template + htmx + 순수 CSS, 전부 바이너리에 embed).
- 브라우저 JS는 `internal/web/static/app.js` 하나뿐(TTS·클립보드·오프라인·서비스 워커). 프런트엔드 빌드 도구(npm 등)는 앱에 없다.
- JSON API(`/api/*`)는 `internal/handlers`에 있다. HTML과 API가 같은 Gin 엔진(`pkg/app`)에 물린다.

## 환경

| 환경 | 배포 | DB | 로그인 |
|---|---|---|---|
| local | `./run_local.sh` | SQLite (`local-db/flashcard.db`) | 없음(고정 사용자) |
| dev | main 푸시 → Vercel **Preview** | 개발용 Supabase 프로젝트 | GitHub/Google |
| production | release 병합 → Vercel **Production** | 운영 Supabase 프로젝트 | GitHub/Google |

- `./run_dev.sh`: local에서 **dev DB**에 붙어 서버를 띄운다. 값은 `.env.dev`에서 읽는다.
- 개발 환경 값의 단일 출처는 `.env.dev` 하나다. **운영 값은 로컬에 두지 않는다.**

## 스키마 관리

- Postgres 스키마의 단일 소스는 `internal/db/migrations/*.up.sql`. 새 변경은 항상 새 번호의 up/down 쌍을 추가한다.
- 적용은 `.github/workflows/migrate.yml`이 한다: main → dev DB, release → 운영 DB.
- local에서 dev DB에 미리 적용해 보려면 `./migrate_dev.sh`. 운영 DB에는 수동으로 적용하지 않는다.

## 검증

- 저장소 루트에서 `./check.sh` (gofmt, 세 모듈의 build·vet·test, Vercel 호환 검사)

"브라우저 JS는 `app.js` 하나뿐", "프런트엔드 빌드 도구는 앱에 없다" 같은 문장이 프로젝트 고유 규약의 예다.
화면 작업을 만나면 자바스크립트 라이브러리부터 더하려 드는 에이전트를 이 두 문장이 처음부터 막는다.

거꾸로 적혀 있지 않은 것도 있다.
`api/index.go`가 `internal/` 패키지를 import할 수 없다는 Vercel 배포 제약은 일반적인 Go 지식으로는 예측할 수 없는 함정인데, 이 파일에는 없다.
지침 문서는 지켜 달라고 부탁하는 방식이라, 기계로 검사할 수 있는 규약은 어기면 실패시키는 장치에 맡기는 쪽이 믿을 만하기 때문이다.
이 제약은 `./check.sh`가 검사하며, {ch-quality-gates}에서 다룬다.

== 에이전트가 만든 코드를 어디까지 믿을까

=== 승인과 되돌리기

파일을 고치고 명령을 실행하는 에이전트는 그만큼 위험하다.
잘못된 명령 하나가 파일을 지우거나 의도하지 않은 변경을 원격 저장소에 밀어 넣을 수 있다.
그래서 대부분의 에이전트는 읽기는 자유롭게 하고, 파일 수정이나 명령 실행처럼 상태를 바꾸는 행동은 실행 전에 승인을 받는다.

매번 승인하기 번거로운 행동을 자동 허용할지는 두 질문으로 정한다.
첫째, 되돌릴 수 있는가.
둘째, 잘못돼도 피해가 작업 디렉터리 안에 머무는가.
`go test` 같은 검증 명령은 둘 다 "예"라 자동 허용해도 되고, `git push`나 파일 삭제는 승인을 유지한다.

가장 강력한 안전망은 버전 관리다.
에이전트가 무엇을 바꾸든 `git diff`로 전체 변경을 보고, 마음에 들지 않으면 되돌릴 수 있다.
Flashcard도 검토를 통과한 변경만 커밋했다.
Git은 {ch-git}에서 다루고, 지금은 되돌릴 수 있는 안전망이 있다는 것만 알면 된다.

=== 검토 강도를 정하는 두 축

모든 줄을 정독하면 작성에서 아낀 시간을 검토에 도로 쓰고, 검토 없이 승인하면 그럴듯한 오류가 쌓인다.
그래서 코드의 성격에 따라 검토 강도를 달리한다.

첫째 축은 *오류를 발견하는 난이도*다.
CSS가 어긋나면 화면을 보는 순간 알지만, 복습 간격 계산이 미묘하게 틀리면 몇 주 뒤 복습 큐가 이상해질 때까지 아무도 모른다.

둘째 축은 *오류의 비용*이다.
버튼 위치가 틀린 것과 사용자 데이터를 지우는 마이그레이션(테이블 구조를 바꾸는 작업, {ch-migrations})이 틀린 것은 비용이 다르다.

|===
|  | 오류 발견이 쉬움 | 오류 발견이 어려움

| *오류 비용 낮음* | 빠르게 읽고 승인 | 테스트로 커버하고 승인
| *오류 비용 높음* | 실행 결과를 직접 확인 | 사람이 정독 + 테스트 + 단계적 적용
|===

Flashcard에서 화면 템플릿 수정은 왼쪽 위에 가까워 화면 확인 위주로 빠르게 승인했다.
`internal/db/migrations/`의 테이블 변경과 인증 코드(`internal/auth/`)는 오른쪽 아래라 코드를 정독하고 테스트 케이스를 함께 검토했다.

=== AI 코드의 품질은 검증 신호의 품질이다

오류 발견이 어려운 코드를 쉬운 쪽으로 옮기면 정독할 영역 자체가 줄어든다.
그 수단이 컴파일, 테스트(코드가 옳게 도는지 확인하는 코드를 기계가 대신 돌려 보는 것), 정적 분석(코드를 실행하지 않고 읽어 의심스러운 곳을 짚는 검사) 같은 자동 검증 신호다.

복습 간격 계산이 위험했던 것은 오류가 늦게 드러나기 때문이었다.
그런데 맞힐 때마다 간격이 1·6·16·45일로 늘어나는지, 틀리면 1일로 돌아오는지를 경계 조건까지 확인하는 테스트(`internal/srs/srs_test.go`, {ch-unit-tests})가 있으면 계산 오류는 커밋 전에 테스트 실패로 드러난다.
에이전트도 그 실패 메시지를 읽고 스스로 고친다.
같은 모델이라도 검증 신호가 풍부한 프로젝트에서는 오류를 잡아내며 수렴하고, 신호가 없는 프로젝트에서는 그럴듯한 오류를 남긴 채 끝난다.

*AI가 만든 코드의 품질은 그 코드를 검증해 주는 신호의 품질에 달려 있다.*
뒤의 기술 장들이 저마다 품질 검사 도구를 함께 다루는 이유이고, 이 신호들을 작업 흐름에 자동으로 거는 법은 {ch-quality-gates}에서 다룬다.

== 한계

아래는 Flashcard를 만들며 실제로 겪은 한계다.

첫째, 그럴듯하지만 틀린 코드다.
문법도 스타일도 멀쩡한데 논리가 틀린 코드는 겉모습이 매끄러운 만큼 경계심을 낮춘다.
요구사항 해석이 미묘하게 어긋난 오류는 자동 신호로도 잡히지 않는다.
재도전 라운드의 답까지 복습 일정에 반영하는 코드는, 그 동작을 기대하도록 짜인 테스트라면 테스트도 통과한다.

둘째, 학습 데이터에 없는 최신 API다.
모델은 지식의 기준 시점 이후에 바뀐 API를 모르고, 옛 버전의 API를 확신에 찬 어조로 쓰기도 한다.
공식 문서의 해당 부분을 대화에 붙여 주거나, 버전 확인이 필요하다고 밝혀 문서를 찾아보게 하는 것으로 대응했다.

셋째, 기억의 한계다.
대화가 길어지면 초반에 합의한 제약을 처음부터 없었던 것처럼 행동하기도 한다.
작업을 커밋 단위로 나누고, 대화를 넘어 지켜야 할 규칙은 `AGENTS.md`나 자동 검사에 담아 대응했다.

세 한계의 공통 대응책은 사람의 검증이고, 검증은 검증할 지식이 있어야 가능하다.
이 책이 2부부터 언어와 프레임워크의 기초를 다지는 이유다.

== 정리

* 지시문에는 기능을 시나리오로, 기술 스택을 협상 불가로, 범위를 "지금 만들지 않는 것"까지 담는다.
* 코드보다 계획을 먼저 받아 요구사항 해석, 기술 스택, 범위를 점검한다. 계획을 사이에 둔 질문이 요구사항과 아키텍처의 빈틈을 드러낸다.
* 앱은 로컬에서 브라우저·Go 서버·SQLite 셋으로 돌고, 공개할 때 서버는 Vercel, 데이터베이스와 인증은 Supabase로 옮긴다.
* 구현은 검증하고 커밋할 수 있는 덩어리로 나누고, 합의한 결정은 `AGENTS.md`에 짧게 고정한다. 기계로 검사할 수 있는 규약은 검사 장치에 맡긴다.
* 상태를 바꾸는 행동은 승인하고 버전 관리를 안전망으로 삼는다. 검토 강도는 오류 발견의 난이도와 오류의 비용으로 정하고, 자동 검증 신호를 늘려 정독할 영역을 줄인다.
* 최종 검증자는 기반 기술을 이해한 사람이다.

여기까지가 읽기만 하는 장이었다.
다음 {ch-first-run}에서 개발 도구를 설치하고, 완성본 저장소를 클론해 내 컴퓨터에서 띄운다.
