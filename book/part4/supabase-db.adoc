= Supabase 데이터베이스: 커넥션 풀러와 개발·운영 분리

{ch-supabase-auth}과 {ch-token-verification}에서 인증을 마쳤으니, 검증을 통과한 요청은 이제 데이터베이스로 내려간다.
3부까지 앱은 환경 변수 하나 없이 `go run ./cmd/server`로 떠서 SQLite 파일 하나에 덱과 학습 기록을 쌓았다({ch-first-run}).
이 장에서는 그 앱을 Supabase의 관리형 PostgreSQL로 옮긴다.

먼저 이 전환이 환경 변수 하나로 끝나는 구조와 PostgreSQL에서 더 풍부해지는 타입을 본다.
이어서 서버리스에서 커넥션이 폭증하는 문제와 그 해법인 트랜잭션 풀러, 함수와 DB를 같은 리전에 두는 콜로케이션, 직접 접근 통로를 잠그는 RLS 전략, 개발·운영 DB 분리를 다룬다.
운영 중인 스키마를 고치는 마이그레이션은 {ch-migrations}에서, 두 벌이 된 값의 관리는 {ch-env-secrets}에서 이어 간다.

== SQLite에서 PostgreSQL로

운영 환경에서는 SQLite 파일 하나짜리 구성이 성립하지 않는다.
{ch-vercel}에서 봤듯 서버리스 함수 인스턴스는 언제든 회수되고, 파일시스템도 인스턴스와 함께 사라지므로 거기에 쓴 SQLite 파일도 증발한다.
인스턴스가 여러 개 뜨면 각자 자기 파일시스템을 쓰므로 파일 하나를 함께 볼 방법도 없다.
데이터는 함수 바깥, 모든 인스턴스가 접속할 수 있는 별도의 데이터베이스 서버에 있어야 하고, 그 자리가 Supabase의 PostgreSQL이다({ch-tech-choices}).

=== DATABASE_URL이 모드를 정한다

이 전환에서 코드는 바뀌지 않는다.
연결 문자열을 담은 환경 변수 `DATABASE_URL` 하나를 주느냐 마느냐가 전부다.

.[용어 풀이] 연결 문자열(Connection String)
[NOTE]
====
데이터베이스에 접속하는 데 필요한 정보를 한 줄에 몰아 적은 문자열이다.
`방식://사용자:비밀번호@주소:포트/DB이름` 형식이라, 어느 서버의 어느 DB에 누구로 접속할지가 다 들어 있다.
집 주소와 현관 비밀번호를 함께 적은 쪽지와 같아서, 이 값이 새면 데이터베이스가 통째로 넘어간다.
포트 자리에 6543을 적으면 뒤에서 볼 트랜잭션 풀러를 거치고 5432를 적으면 DB에 직접 붙는다.
====

`internal/config/config.go`의 `Load`가 `DATABASE_URL`의 유무로 데이터베이스 드라이버와 인증 방식을 함께 결정한다.

[source,go]
----
	if cfg.DatabaseURL != "" {
		cfg.Driver = "postgres"
		cfg.AuthMode = "supabase"
		// ... (SUPABASE_URL·SUPABASE_ANON_KEY 필수 검사, JWKS URL 유도)
		return cfg, nil
	}

	// DATABASE_URL이 없으면 SQLite 파일로 1인 로컬 모드를 돈다. Vercel에서는
	// 함수의 일회용 파일시스템에 조용히 쓰게 되므로, 거기서 DATABASE_URL이
	// 없는 것은 언제나 설정 실수다.
	if os.Getenv("VERCEL") != "" {
		return nil, fmt.Errorf("DATABASE_URL is required on Vercel")
	}
	cfg.Driver = "sqlite"
	cfg.AuthMode = "local"
	// ...
----

`DATABASE_URL`이 있으면 PostgreSQL과 Supabase 인증, 없으면 SQLite와 고정 로컬 사용자다.
데이터베이스와 인증이 짝지어 바뀌는 것은 여러 사용자의 데이터가 한곳에 모이는 순간 "누구의 요청인가"를 가리는 진짜 인증이 필요해지기 때문이다.

가운데의 `VERCEL` 검사는 안전장치다.
Vercel은 자기 위에서 도는 프로세스에 `VERCEL` 환경 변수를 심어 주는데, 거기서 `DATABASE_URL`이 없으면 함수가 일회용 파일시스템에 SQLite 파일을 만들어 겉으로는 동작하면서 데이터를 조용히 잃는다.
이 검사가 그것을 명확한 기동 실패로 바꾼다.

=== 스토어 교체는 인터페이스 한 장 뒤에 숨는다

환경 변수 하나로 데이터베이스가 바뀌어도 핸들러 코드가 그대로인 것은 {ch-app-assembly}에서 본 handlers→store 계층 분리 덕분이다.
`internal/model/store.go`에는 핸들러가 저장소에 요구하는 계약이 Go 인터페이스(interface)로 선언되어 있다.
인터페이스는 메서드의 이름과 모양만 나열한 목록으로, 그 목록을 전부 갖춘 타입이면 무엇이든 이 자리에 들어올 수 있다.

[source,go]
----
type Store interface {
	GetOrCreateProfile(ctx context.Context, userID uuid.UUID, displayName string) (Profile, error)

	ListDecks(ctx context.Context, userID uuid.UUID) ([]Deck, error)
	CreateDeck(ctx context.Context, userID uuid.UUID, name string, description *string) (Deck, error)
	// ... (덱·카드·세션·공유·스마트 덱·통계에 걸쳐 모두 35개 메서드)

	DailyStats(ctx context.Context, userID uuid.UUID, tz string, days int) ([]DailyStat, error)
}
----

이 계약을 만족하는 구현이 pgx로 PostgreSQL에 붙는 `internal/pgstore`와 SQLite 구현 `internal/litestore` 둘이다.
두 구현은 SQL 문법(방언)만 다르고 행 타입과 `ErrNotFound` 같은 오류 값은 `internal/model`의 것을 함께 쓰므로, 어느 쪽이 꽂혀도 응답이 같다.
어느 구현을 꽂을지는 진입점이 정한다.
`cmd/server/main.go`의 다음 코드는 설정의 드라이버 값에 따라 SQLite 스토어 또는 PostgreSQL 엔진을 조립한다.

[source,go]
----
	var engine *gin.Engine
	if cfg.Driver == "sqlite" {
		s, err := litestore.Open(cfg.SQLitePath)
		// ...
		engine = app.New(cfg, s)
	} else {
		engine, err = app.Engine()
		// ...
	}
----

Vercel 함수의 진입점 `api/index.go`가 부르는 `pkg/app`의 `Engine()`은 PostgreSQL 전용이다.
`pkg/app`은 litestore를 import하지 않으므로, 서버리스에 올라가는 바이너리에는 SQLite 코드가 링크(컴파일 결과물에 포함되는 일)조차 되지 않는다.
3부까지 SQLite로 만들고 검증한 핸들러, 프런트엔드, 학습 로직은 한 줄도 바뀌지 않은 채 운영 데이터베이스 위에서 그대로 돈다.

== 같은 설계, 더 풍부한 타입

{ch-database-design}에서 한 설계(일곱 테이블, 외래 키와 cascade, 조회 패턴에서 역산한 인덱스)는 PostgreSQL에서도 그대로고, 바뀌는 것은 표현이다.
SQLite는 타입의 가짓수를 최소로 줄인 DB라 {ch-database-design}의 스키마는 많은 것을 `text` 열에 눌러 담았고, PostgreSQL은 그 자리마다 전용 타입을 내준다.
아래 표가 그 대응이고, 낯선 이름은 표 아래에서 하나씩 푼다.

|===
| {ch-database-design}의 SQLite 표현 | 운영 PostgreSQL

| `text` (Go가 만들어 넣는 UUID 문자열) | `uuid` 타입 + `gen_random_uuid()` 기본값
| `text` (고정 폭 UTC 문자열) | `timestamptz`
| `text` (JSON 문자열) | `jsonb`
| `text` (JSON 배열 문자열) | `text[]` 배열 + GIN 인덱스
| `text` + `check` 제약 | `enum` 타입
| `integer primary key autoincrement` | `bigint generated always as identity`
|===

운영 스키마의 출발점인 `internal/db/migrations/000001_init.up.sql`에서 사용자와 카드 테이블을 만드는 부분을 발췌한다.

[source,sql]
----
create type card_type as enum ('word', 'sentence', 'idiom');

create table profiles (
  id uuid primary key,
  display_name text,
  settings jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default now()
);

create table cards (
  id uuid primary key default gen_random_uuid(),
  -- ...
  front_text text not null,
  back_text text not null,
  card_type card_type not null default 'word',
  tags text[] not null default '{}',
  -- ...
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
----

카드의 두 열이 `text`·`meaning`이 아니라 `front_text`·`back_text`라는 첫 이름으로 등장하는데, 이름이 바뀐 사연은 {ch-migrations}에서 본다.

`settings`의 `jsonb`는 JSON을 파싱된 이진 형태로 저장하는 타입으로, 넣을 때 문법이 검증되고 내부 필드 조회와 인덱스도 가능하다.
`card_type`은 {ch-database-design}에서 `check` 제약으로 흉내 냈던 값 목록이 enum 타입이 된 모습이다.
타입 자체가 문서가 되고 저장 공간도 작지만, 값 목록을 바꾸는 일이 데이터 수정이 아니라 테이블의 틀을 고치는 명령(DDL, 데이터 정의어)이 된다.
특히 한 번 넣은 값을 목록에서 빼는 것은 불가능에 가깝고, 이 비용도 {ch-migrations}에서 실제 사례로 확인한다.

=== 기본 키: 데이터베이스가 UUID를 만든다

`profiles.id`에는 `default`가 없다.
DB가 만들지 않고 Supabase Auth가 발급한 사용자 UUID, 곧 {ch-token-verification}에서 본 JWT의 `sub` 클레임을 그대로 받아 쓰기 때문이다.
그래서 토큰에서 꺼낸 ID로 다른 테이블을 거치지 않고 곧장 조회할 수 있다.

나머지 테이블의 `id`는 `default gen_random_uuid()`로 DB가 직접 만든다.
SQLite에는 UUID 타입도 생성 함수도 없어 Go 코드가 만들어 넣었다.

순번 키는 `/cards/42` 같은 URL로 전체 카드 수를 드러내고 이웃 ID도 추측하게 하지만, UUID는 추측할 수 없고 전역에서 유일해 환경 사이에서 행을 옮겨도 충돌하지 않는다.
대신 16바이트로 bigint의 두 배 크기이고, 값이 무작위라 새 행이 정렬된 인덱스의 중간 아무 데나 끼어들어 대량으로 쌓이는 테이블에는 불리하다.
그래서 빠르게 쌓이고 외부에 노출되지 않는 `review_logs`에는 순번 키(`bigint generated always as identity`)를 써서 "노출되는 것은 UUID, 내부 대량 로그는 순번"으로 나눴다.

=== 시간대를 품은 타임스탬프

모든 시각 칼럼은 `timestamp`가 아니라 `timestamptz`(timestamp with time zone)다.
`timestamptz`는 값을 UTC 기준 절대 시각으로 저장하고, 조회하는 접속에 설정된 시간대에 따라 변환해 보여 준다.
반면 `timestamp`는 시간대 정보가 없는 벽시계 값이라, 서버·클라이언트·DB의 시간대가 어긋나면 읽는 쪽마다 다른 시각으로 해석된다.
{ch-database-design}의 SQLite에서는 고정 폭 UTC 문자열로 저장해 문자열 비교가 곧 시간 비교가 되게 맞췄는데, 여기서는 타입 하나로 끝난다.

`internal/pgstore/stats.go`의 일별 통계 쿼리는 UTC로 쌓은 복습 시각을 `reviewed_at at time zone $2`처럼 사용자의 IANA 시간대(예: `Asia/Seoul`)로 변환해 "그 사용자의 하루" 단위로 집계한다.
연속 학습일(streak) 계산도 같은 방식이다.

=== 배열과 GIN 인덱스

카드의 태그는 `text[]` 배열 칼럼이고, 스마트 덱의 태그 규칙은 `tags && $2`라는 배열 겹침(overlap) 연산으로 태그가 하나라도 겹치는 카드를 찾는다.
이 연산을 000001의 `create index cards_tags_gin on cards using gin (tags)` 인덱스가 받친다.
{ch-database-basics}에서 본 B-tree 인덱스는 한 칸에 값 하나가 든 경우를 정렬해 찾는 구조라 배열 안의 원소는 다루지 못하므로, 배열 칼럼에는 GIN 인덱스를 건다.

.[용어 풀이] GIN 인덱스(Generalized Inverted Index)
[NOTE]
====
한 칸에 값이 여러 개 들어 있는 열(배열, jsonb, 전문 검색용 문서)을 위한 PostgreSQL 인덱스다.
책 뒤 찾아보기가 낱말마다 쪽 번호를 모아 두듯 "값 → 그 값이 든 행"으로 뒤집어 둔 역색인이라, 특정 태그가 든 카드를 모든 행을 읽지 않고 찾아낸다.
대신 행 하나를 쓸 때 그 안의 값 개수만큼 색인을 손봐야 해서 갱신 비용이 B-tree보다 크다.
====

SQLite 구현(`internal/litestore/rules.go`)은 JSON 배열 문자열을 `json_each` 함수로 풀어 하나씩 대조하므로 조회 시간이 카드 수에 비례해 늘지만, GIN 인덱스는 태그에서 행으로 바로 간다.
혼자 쓰는 로컬에서는 체감되지 않던 차이가, 여러 사용자의 카드가 쌓이는 운영에서는 응답 시간으로 나타난다.

== 서버리스와 커넥션 풀

연결 문자열 하나를 넘기는 단순한 일처럼 보이지만, 서버리스에서는 이 장에서 함정이 가장 많은 주제다.

=== pgx를 고른 이유

Go에서 PostgreSQL에 접속하는 정석은 SQLite 때처럼 표준 `database/sql`에 드라이버를 꽂는 방식이고, 오랫동안 `lib/pq`가 그 자리를 지켰다.
그러나 `lib/pq`는 유지보수 모드에 들어갔고, 프로젝트 스스로 pgx(`github.com/jackc/pgx/v5`)로 갈아탈 것을 권한다.
pgx는 `database/sql`을 거치지 않는 PostgreSQL 전용 API를 제공하고, 커넥션 풀(`pgxpool`)이 내장되어 있으며, 쿼리를 DB에 어떤 방식으로 보낼지(실행 모드)를 고를 수 있다.
마지막 특성이 잠시 뒤 결정적으로 중요해진다.
DB 종류를 바꿀 가능성이 있다면 `database/sql`이 맞지만, Flashcard는 두 DB의 추상화를 Store 인터페이스 계층에서 해결했으므로 PostgreSQL 쪽은 pgx를 그대로 쓴다.

=== 서버리스에서 커넥션이 폭증하는 문제

데이터베이스 연결을 새로 여는 일은 비싸서, 서버는 연결 몇 개를 미리 열어 쥐고 요청마다 돌려쓴다({ch-app-assembly}에서 본 커넥션 풀이다).
상주 서버에서는 프로세스가 하나, 풀이 하나이므로 풀 크기가 곧 커넥션 상한이다.
서버리스에서는 동시 요청이 늘면 플랫폼이 함수 인스턴스를 여러 개 띄우고, 인스턴스마다 자기 풀을 만든다.
그래서 총 커넥션 수는 "인스턴스 수 × 풀 크기"가 되고, 인스턴스 수는 우리가 통제할 수 없다.
풀 크기가 4라도 인스턴스가 20개 뜨면 연결은 80개다.

PostgreSQL은 커넥션마다 서버 쪽 프로세스가 하나씩 붙어 메모리를 쓰므로 커넥션은 값비싼 자원이다.
무료 플랜의 Nano 인스턴스가 받는 직접 연결은 60개, 뒤에서 볼 풀러를 거치는 클라이언트는 200개가 상한이다footnote:[Supabase 문서 "Compute and Disk"의 컴퓨트 등급별 한도 표. https://supabase.com/docs/guides/platform/compute-and-disk[Compute and Disk]].
트래픽이 몰려 인스턴스가 불어나면 이 상한(`max_connections`)이 바닥나고, DB는 멀쩡한데 연결이 안 되는 장애가 난다.

=== 트랜잭션 풀러와 simple protocol

이 문제의 표준 해법이 커넥션 풀러(connection pooler)이고, Supabase는 Supavisor라는 풀러를 함께 제공한다.
우리 서버의 풀(pgxpool)이 DB 대신 풀러에 붙고, 풀러가 소수의 실제 Postgres 커넥션을 여러 클라이언트가 나눠 쓰게 한다.

이 절에서 말하는 세션은 DB에 접속해 있는 연결 하나를 뜻한다.
AI 에이전트와 나누는 대화 단위인 세션과는 다른 뜻이고, {ch-supabase-auth}의 로그인 세션이나 학습 세션(`study_sessions` 테이블)과도 다르다.

.[용어 풀이] 커넥션 풀러(트랜잭션 풀러와 세션 풀러)
[NOTE]
====
수많은 클라이언트가 저마다 DB에 직접 연결하는 대신, 소수의 실제 연결을 가운데서 빌려주고 돌려받게 하는 중개자다.
이름이 한 글자 차이인 커넥션 풀은 우리 서버가 자기 안에 쥐고 돌려쓰는 연결 묶음이고, 풀러는 DB 앞에 서서 중개하는 별도의 서버다.
트랜잭션 풀러는 트랜잭션 하나가 도는 동안만 연결을 빌려주고, 세션 풀러는 접속이 끝날 때까지 한 연결을 계속 쥐게 한다.
공용 회의실을 회의 한 건 단위로 빌려주느냐, 한 사람에게 하루 종일 배정하느냐의 차이다.
====

풀러의 트랜잭션 모드(포트 6543)는 함수 인스턴스가 아무리 늘어나도 실제 DB 커넥션을 소수로 유지하므로 서버리스와 궁합이 가장 좋다.
풀러가 있을 때와 없을 때를 그림 26에 견주었다.

<p class="fc-caption">그림 26 커넥션 풀과 커넥션 풀러. 풀러가 없으면 함수 인스턴스마다 자기 풀이 DB에 직접 붙어 총 커넥션이 "인스턴스 수 × 풀 크기"로 불어난다. 트랜잭션 풀러를 앞에 세우면 인스턴스가 아무리 늘어도 실제 DB 커넥션은 소수로 유지된다.</p>
++++

대가가 있다.
같은 클라이언트라도 트랜잭션마다 다른 실제 커넥션에 배정될 수 있으므로, 커넥션에 상태가 남는 기능은 쓸 수 없다.
대표적인 것이 프리페어드 스테이트먼트(prepared statement)다.
pgx는 기본적으로 확장 프로토콜(extended protocol)로 쿼리를 준비해 캐시하는데, 준비한 커넥션과 실행할 커넥션이 다르면 "prepared statement가 존재하지 않는다"는 오류가 난다.

.[용어 풀이] 프리페어드 스테이트먼트(Prepared Statement)
[NOTE]
====
같은 모양의 쿼리를 반복해서 쓸 때, DB에 미리 한 번 분석·준비시켜 두고 이후에는 값만 바꿔 빠르게 실행하는 방식이다.
자주 쓰는 서류 양식을 만들어 두고 빈칸만 채우는 것과 같다.
준비해 둔 연결과 실행하는 연결이 다르면 그 연결에는 양식이 없어서 이 방식을 쓸 수 없다.
====

이 사정이 `internal/db/db.go`에 압축되어 있다.
DB 커넥션 풀을 프로세스에서 단 하나만 만들어 돌려주는 함수다.

[source,go]
----
func Pool(ctx context.Context, databaseURL string) (*pgxpool.Pool, error) {
	poolOnce.Do(func() {
		cfg, err := pgxpool.ParseConfig(databaseURL)
		if err != nil {
			poolErr = fmt.Errorf("parse DATABASE_URL: %w", err)
			return
		}
		cfg.MaxConns = 4
		cfg.ConnConfig.DefaultQueryExecMode = pgx.QueryExecModeSimpleProtocol
		pool, poolErr = pgxpool.NewWithConfig(ctx, cfg)
	})
	return pool, poolErr
}
----

세 가지 결정이 담겨 있다.
첫째, `sync.Once`로 풀을 프로세스당 하나만 만들어 웜 인스턴스가 여러 호출에 걸쳐 재사용한다({ch-token-verification}의 JWKS 클라이언트와 같은 이유다).
둘째, `MaxConns = 4`로 풀을 작게 잡아 인스턴스가 늘어도 폭증의 기울기를 낮춘다.
셋째, `QueryExecModeSimpleProtocol`로 쿼리를 준비 단계 없이 한 번에 보내는 단순 프로토콜(simple protocol)을 강제해 트랜잭션 풀러에서도 안전하게 한다.

단순 프로토콜에서도 파라미터는 pgx가 안전하게 이스케이프한 텍스트로 인코딩하므로 SQL 인젝션({ch-database-basics}) 걱정은 없다.
확장 프로토콜의 바이너리 인코딩과 구문 재사용 이점은 포기하지만, 이 앱의 쿼리 규모에서는 측정조차 어려운 차이다.

== 리전 콜로케이션: 함수와 DB를 같은 곳에

{ch-vercel-config}에서 본 `vercel.json`은 함수 리전을 고정하고 있다.

[source,json]
----
{
  "regions": ["iad1"]
}
----

`iad1`은 Vercel의 미국 동부 버지니아 리전 이름이다.
그리고 `DEPLOY.md`의 첫 단계는 Supabase 프로젝트의 리전을 East US(North Virginia)로 고르라고 지시하며 "서울 리전을 고르면 안 됩니다"라고 못 박는다.
한국 사용자를 위한 앱인데 왜 서울이 아닐까.

핵심은 왕복 횟수의 비대칭이다.
사용자와 함수 사이는 요청당 한 번 왕복하지만, 함수와 DB 사이는 요청 하나에 여러 번 왕복한다.
홈 화면 하나만 해도 복습 큐 수, 통계 요약, 덱 목록 조회가 이어지고(`internal/web/home.go`), 인스턴스가 그 사용자를 처음 볼 때는 `EnsureProfile`의 프로필 확인까지 붙어 DB 왕복이 3~4번이다.

서울과 버지니아 사이의 왕복 지연(round-trip latency)은 약 180ms라, 함수가 iad1에 있고 DB가 서울이면 DB 왕복 4번에 지연만 700ms가 넘게 쌓인다.
같은 리전이면 왕복당 1ms 수준이라 쿼리 횟수가 체감 지연에 거의 영향을 주지 않는다.
Vercel의 Hobby 플랜도 함수 리전을 하나는 고를 수 있고 새 프로젝트의 기본값이 iad1이다footnote:[Vercel 문서 "Configuring regions for Vercel Functions"의 플랜별 리전 수 표와 기본 리전 설명. https://vercel.com/docs/functions/configuring-functions/region[Configuring regions for Vercel Functions]].
이 저장소는 그 기본값을 고정해 두었으므로 DB를 함수 곁인 버지니아에 만든다.
사용자→함수 구간의 180ms는 요청당 한 번뿐이고, 정적 자산은 CDN 엣지가 사용자 가까이에서 응답한다.
한국 사용자만 쓰는 앱이라면 함수 리전을 서울(`icn1`)로 바꾸고 Supabase 프로젝트도 서울에 만들어 둘을 함께 옮기면 된다.
어느 쪽이든 원칙은 콜로케이션(colocation)이다.

.[용어 풀이] 콜로케이션(Colocation)
[NOTE]
====
서로 자주 대화하는 두 시스템(여기서는 함수와 DB)을 같은 지역(리전)에 두어 물리적 거리를 좁히는 것이다.
하루에도 수십 번 오가는 두 부서를 같은 층에 두면 오갈 때마다 드는 시간이 쌓이지 않는 것과 같다.
====

== RLS 전략: 정책 0개로 잠근다

Supabase의 PostgreSQL에는 일반적인 DB 서버에 없는 문이 하나 더 있다.
PostgREST라는 관문 서버(게이트웨이)가 붙어 있어, 브라우저 같은 클라이언트가 API 서버 없이 웹 요청으로 테이블을 직접 읽고 쓸 수 있다.
이때 접속자는 `anon`(로그인 전)과 `authenticated`(로그인 후) 두 역할 중 하나로 취급되고, 문을 여는 열쇠는 {ch-supabase-auth}에서 본 anon key다.
anon key는 원래 브라우저 코드에 박아 배포하라고 만든 공개 값이라, Flashcard가 서버에서만 쓰더라도 누구든 손에 넣을 수 있다고 봐야 한다.
이 문을 그대로 두면 Go API의 인증·인가 로직을 우회하는 뒷문이 열린다.

Supabase의 표준 설계는 이 직접 접근을 열어 두고 테이블마다 RLS(Row Level Security, 행 수준 보안) 정책으로 "자기 행만 보인다"를 강제하는 것이다.

.[용어 풀이] 행 수준 보안(RLS, Row Level Security)
[NOTE]
====
"누가 어떤 행을 볼 수 있는가"를 테이블 안에서 행 단위로 통제하는 PostgreSQL 기능이다.
같은 테이블을 조회해도 사용자 A에게는 A의 행만, B에게는 B의 행만 보이도록 DB가 걸러 준다.
RLS를 켜면 기본값이 "거부"라서 허용 정책이 하나도 없으면 그 역할에는 아무 행도 보이지 않는다.
====

Flashcard는 다른 길을 택해, 모든 데이터 접근을 Go API로만 받고 PostgREST 경로는 원천 차단한다.
`internal/db/migrations/000001_init.up.sql`의 마지막 부분에서 모든 테이블에 RLS를 켜고, PostgREST가 쓰는 두 역할의 기본 접근 권한을 회수한다.

[source,sql]
----
-- The Go API is the only client of these tables. Enabling RLS with zero
-- policies blocks Supabase PostgREST access via the anon/authenticated roles,
-- while the table owner (the connection Go uses) bypasses RLS.
alter table profiles enable row level security;
alter table decks enable row level security;
-- ... (모든 테이블에 동일)

-- Belt and braces on Supabase: drop the default grants PostgREST roles get.
do $$
begin
  if exists (select 1 from pg_roles where rolname = 'anon') then
    revoke all on all tables in schema public from anon;
  end if;
  -- ... (authenticated 역할에도 동일)
end $$;
----

RLS를 켜고 정책을 하나도 두지 않으면, PostgREST 역할에는 모든 테이블이 빈 것처럼 보인다.
반면 Go API가 `DATABASE_URL`로 접속하는 postgres 역할은 테이블 소유자라서, PostgreSQL이 RLS 검사에서 빼 준다.
그 아래의 `revoke`는 RLS 설정이 실수로 풀리더라도 권한(grant) 자체가 없어 접근이 막히게 하는 이중 잠금(belt and braces)이다.
`do $$ ... $$` 블록으로 역할 존재를 확인하는 것은 `anon` 역할이 없는 순정 PostgreSQL에서도 같은 마이그레이션이 돌게 하려는 것이다.

스키마를 처음 만든 마이그레이션과 뒤에 카드 구조를 손보는 마이그레이션({ch-migrations})에 정의된 뷰의 `security_invoker = true` 옵션도 이 전략의 일부다.
PostgreSQL 뷰는 기본적으로 소유자 권한으로 실행되어 테이블의 RLS 잠금을 우회할 수 있는데, 이 옵션을 켜면 호출자 권한으로 실행되어 뷰가 뒷문이 되지 않는다.

RLS 정책 기반 설계는 CRUD 수준의 화면을 API 코드 없이 클라이언트에서 바로 만들 수 있고, 권한 규칙이 데이터 곁에 있어 어떤 클라이언트가 붙어도 일관된다.
클라이언트 종류가 여럿이고 API 서버를 얇게 두고 싶다면 이쪽이 낫다.
반면 인가(authorization) 로직이 테이블마다 SQL 정책으로 흩어지고, 정책 하나만 빠뜨려도 데이터가 노출된다.
Flashcard는 SRS 계산과 트랜잭션 때문에 어차피 Go API가 필수였으므로, 인가를 Go 쪽 한 곳에 모으고(store 계층의 모든 쿼리에 `user_id = $1` 조건이 붙는다) DB에 들어오는 길을 하나로 줄였다.
RLS를 접근 제어 규칙이 아니라 뒷문을 잠그는 자물쇠로 쓴 셈이다.

== 개발 DB와 운영 DB를 분리한다

이 장의 구성을 실제로 따라 하면 Supabase 프로젝트를 운영용과 개발용 둘 만들게 된다.
운영 DB는 사용자 데이터가 살아 있는 곳이므로 거기서 실험하지 않는다.
새 기능의 쿼리를 돌려 보고, 스키마 변경을 시험하고, 잘못된 `delete`를 저지르는 일은 지워도 되는 데이터 위에서 벌어져야 한다.
{ch-free-tier}에서 보겠지만 무료 플랜에는 자동 백업도 없어서, 운영 데이터 위의 실수는 돌아갈 시점이 없는 사고가 된다.
특히 {ch-migrations}의 마이그레이션은 개발 DB에 먼저 적용해 보면, 실패하든 어긋나든 사고의 반경이 개발 데이터 안에 갇힌다.

구성은 Supabase에서 프로젝트를 하나 더 만드는 것이 전부다(예: `flashcard`와 `flashcard-dev`).
리전은 운영과 같은 곳으로 맞추고, 프로젝트마다 자기만의 연결 문자열·anon key·JWKS URL이 나온다.
2026년 7월 기준 무료 조직은 활성 프로젝트를 2개까지 허용하므로 개발·운영 두 프로젝트가 그 한도를 채운다footnote:[Supabase 요금 페이지의 Free 플랜 항목. https://supabase.com/pricing[Pricing]].
일시정지된 프로젝트는 이 수에 들어가지 않으며, 이 한도의 의미는 {ch-free-tier}에서 다시 짚는다.

개발 환경을 다른 플랫폼에 차리는 안도 검토했지만, 2026년 7월 기준으로 카드 등록 없이 무료로 서버를 올릴 수 있는 플랫폼이 드물고({ch-vercel}) 그중 Render는 무료 PostgreSQL이 30일 뒤 만료된다.
플랫폼이 늘면 개발에서 통과한 것이 운영에서도 통과한다는 전제도 약해지므로, 이미 쓰는 Vercel의 Preview 스코프와 Supabase의 두 번째 무료 프로젝트로 꾸렸다.

이 두 프로젝트는 {ch-git}의 브랜치 정책, {ch-vercel-config}의 배포 구분과 나란히 정렬된다.

|===
| 층 | 코드 | 배포 | 데이터베이스

| 로컬 | 작업 중인 코드 | 없음 | SQLite 파일({ch-first-run})
| 개발 | `main` 브랜치 | Vercel 프리뷰 배포 | 개발 Supabase 프로젝트
| 운영 | `release` 브랜치 | Vercel 프로덕션 배포 | 운영 Supabase 프로젝트
|===

같은 대응을 그림 27에 그렸다.

배선은 {ch-vercel-config}에서 본 환경 변수 스코프가 맡는다.
`DATABASE_URL`이라는 같은 이름에 Production 스코프로는 운영 프로젝트의 값을, Preview 스코프로는 개발 프로젝트의 값을 등록해 두면, `main`에 push한 코드는 개발 DB를, `release`에 병합한 코드는 운영 DB를 바라본다.
`SUPABASE_URL`과 `SUPABASE_ANON_KEY`도 같은 방식으로 스코프를 나눈다.

일상 개발은 로컬 SQLite에서 하므로, 개발 프로젝트는 풀러, RLS, 마이그레이션, JWKS 인증처럼 Supabase에 붙어야만 확인되는 것을 시험할 때만 쓴다.
개발을 쉬어 개발 프로젝트가 일시정지되더라도({ch-free-tier}) 대시보드에서 깨우면 된다.

이 배선 위에서 스키마를 누가 언제 적용하는지는 {ch-migrations}에서, 로컬에서 개발 DB에 붙는 절차와 두 벌이 된 값의 관리는 {ch-env-secrets}에서 다룬다.

== 에이전트 활용 아이디어

운영 데이터베이스는 실수의 비용이 가장 큰 층이므로 지침도 가장 구체적으로 적는다.

* `AGENTS.md` 후보는 이 장의 결론들이다. "서버의 `DATABASE_URL`은 트랜잭션 풀러(6543)를 가리키고 pgx의 단순 프로토콜 설정을 걷어내지 않는다", "모든 테이블은 RLS를 켠 채 정책을 두지 않는다", "실험과 스키마 시험은 개발 Supabase 프로젝트에서만 한다."
* 풀러나 리전처럼 코드 밖 인프라가 얽힌 문제는 에이전트가 로그만으로 원인을 찾기 어렵다. "prepared statement 오류가 났다"는 증상과 함께 트랜잭션 풀러와 세션 상태라는 배경을 알려 주면 원인에 바로 다가간다.

== 정리

첫째, SQLite로 완성한 앱은 코드 수정 없이 운영 데이터베이스로 전환된다.
`DATABASE_URL`의 유무가 드라이버와 인증 방식을 함께 정하고, 핸들러는 Store 인터페이스만 바라보며, Vercel에서 이 값이 없으면 기동을 거부한다.

둘째, 설계는 같고 타입이 풍부해진다.
`text`로 눌러 담았던 자리에 uuid·timestamptz·jsonb·배열·enum·identity가 들어서고, 태그 검색은 GIN 인덱스가 받친다.

셋째, 서버리스에서는 커넥션이 폭증하므로 트랜잭션 풀러(6543)를 거치고, 프리페어드 스테이트먼트가 성립하지 않으므로 pgx에 단순 프로토콜을 설정한다.

넷째, 요청 하나가 DB를 여러 번 왕복하므로 함수와 데이터베이스를 같은 리전에 둔다.

다섯째, RLS는 "enable + 정책 0개 + revoke"로 PostgREST 경로를 막고, 인가를 Go API 한 곳에 모은다.

여섯째, 데이터베이스는 로컬 SQLite, 개발 Supabase(`main`), 운영 Supabase(`release`)의 세 층이 되고, 배선은 환경 변수 스코프가 맡는다.

다음 {ch-migrations}에서는 사용자 데이터가 살아 있는 채로 스키마를 바꾸는 마이그레이션과, 그 적용을 브랜치에 맡기는 워크플로를 다룬다.
