= Supabase 인증: OAuth 로그인과 쿠키 세션

{ch-vercel}에서 Go 서버를 Vercel 서버리스 함수로 배포했다.
남은 조각은 사용자 인증과 데이터베이스이고, 둘 다 Supabase가 맡는다.
이 장과 다음 {ch-token-verification}은 인증을, {ch-supabase-db}과 {ch-migrations}은 데이터베이스를 다룬다.

먼저 왜 Supabase였는지와 어떤 기능을 일부러 쓰지 않았는지를 정리하고, 로그인 버튼을 누른 순간부터 Go 서버가 사용자를 알아보기까지를 코드로 따라간다.
이 여정에는 브라우저 자바스크립트가 한 줄도 개입하지 않는다.

핵심 주장은 둘이다.
로그인 상태를 브라우저 스크립트가 닿을 수 없는 HttpOnly 쿠키에 두면, 공격이 파고들 수 있는 통로인 공격면(attack surface) 하나가 사라진다.
그리고 인스턴스가 언제든 사라지는 서버리스에서는, 세션 저장소를 두지 않는 무상태 구조라야 잃을 상태가 없다.
쿠키로 돌아온 토큰이 진짜인지 확인하는 원리는 {ch-token-verification}에서 다루지만, 로그인을 따라 만드는 데는 이 장만으로 충분하다.

== 로컬 인증에서 운영 인증으로

로컬 모드의 Go 서버는 모든 요청을 `internal/auth/local.go`의 미들웨어에 통과시키는데, 그 전문이 이만큼 짧다.

[source,go]
----
// LocalUserID는 로컬 모드의 모든 요청이 쓰는 고정 사용자다.
var LocalUserID = uuid.MustParse("00000000-0000-0000-0000-000000000001")

// LocalMiddleware는 로컬 단일 사용자 모드에서 토큰 검증을 대신한다. 모든 요청을
// LocalUserID로 로그인시키므로 Authorization 헤더도 Supabase도 필요 없다.
// required·optional 두 자리를 다 맡는다.
func LocalMiddleware() gin.HandlerFunc {
	return func(c *gin.Context) {
		c.Set(userIDKey, LocalUserID)
		c.Next()
	}
}
----

아무것도 검증하지 않고 모든 요청을 미리 정해 둔 사용자 하나로 취급한다.
앱을 공개하면 요청을 보내는 사람이 여럿이고, 서로의 덱과 학습 기록을 봐서는 안 되며, "나는 이 사용자다"라는 주장을 그대로 믿어 줄 수 없다.
그 주장을 위조할 수 없는 방식으로 확인하는 일이 인증이다.
검증 없는 로컬 인증이 운영에 새어 나가지 않도록, `internal/config/config.go`는 `DATABASE_URL`이 없을 때만 로컬 모드를 켜고, Vercel 환경에서 `DATABASE_URL`이 빠져 있으면 기동을 거부한다.

== 왜 Supabase인가

요구사항은 데이터베이스와 로그인까지 완전 무료로({ch-requirements}), 관리할 플랫폼을 늘리지 않고({ch-vercel}) 갖추는 것이었다.
Supabase는 관리형(managed) PostgreSQL과 OAuth 소셜 로그인을 포함한 인증(authentication) 서비스를 하나의 프로젝트, 하나의 무료 티어 안에 담고 있다.
2026년 7월 기준으로 무료 티어는 데이터베이스 500MB와 월간 활성 사용자 5만 명 수준을 제공하는데, 개인용 암기 카드 앱에는 차고 넘친다.
그래서 Flashcard가 계정을 관리하는 외부 플랫폼은 Vercel과 Supabase 둘뿐이다(무료 티어의 한도는 {ch-free-tier}).

.[용어 풀이] OAuth
[NOTE]
====
앱에 비밀번호를 직접 넘기지 않고, 이미 신뢰하는 구글이나 깃허브에 대신 로그인해 "이 사람이 맞다"는 확인만 받아 오는 방식이다.
앱은 당신의 구글 비밀번호를 끝내 보지 못하고, 구글이 발급한 확인 결과만 건네받는다.
그래서 비밀번호를 저장할 의무 자체가 앱에서 사라진다.
====

.[용어 풀이] 관리형 서비스(Managed Service)
[NOTE]
====
서버 설치, 백업, 보안 패치, 확장 같은 운영 작업을 제공업체가 맡고, 사용자는 기능만 가져다 쓰는 서비스다.
집을 직접 짓고 고치는 대신 관리사무소가 시설을 돌보는 아파트에 사는 것과 비슷하다.
====

=== 인증을 직접 만들면 무엇을 떠안는가

첫째, 비밀번호 저장이다.
비밀번호는 원문을 되짚을 수 없게 뭉갠 값으로 바꿔 저장해야 하고, 그 뭉개기에 bcrypt나 argon2 같은 검증된 해시 알고리즘을 올바른 파라미터로 적용해야 하며, 유출 사고가 나면 법적 책임까지 따라온다.

둘째, 소셜 로그인 연동이다.
Google과 GitHub 각각에 OAuth 앱을 등록하고, 인가 코드(authorization code)를 토큰으로 교환하는 절차를 구현하고, 프로바이더(provider)마다 다른 응답 형식과 오류 케이스를 처리해야 한다.
예를 들어 GitHub는 사용자가 이메일을 비공개로 두면 프로필 API의 `email` 필드를 `null`로 돌려주므로footnote:[GitHub REST API 문서 "Users"의 응답 설명. https://docs.github.com/en/rest/users/users[Users - GitHub Docs]], 이메일을 따로 조회하는 분기가 필요하다.
이 장의 인가 코드·인가 화면·인가 주소에서 "인가"는 사용자가 프로바이더 화면에서 우리 앱의 로그인 요청을 허가하는 OAuth 절차를 가리키고, {ch-database-basics}의 인가(그 사람이 이 일을 해도 되는지 앱 안에서 확인하는 권한 검사)와는 다른 뜻이다.

.[용어 풀이] 프로바이더(Provider)
[NOTE]
====
OAuth에서 사용자의 신원을 대신 확인해 주는 쪽, 곧 Google이나 GitHub처럼 이미 그 사람의 계정이 있는 서비스다.
신원 확인을 여권 발급 기관에 맡기고 우리는 여권을 확인만 하는 것과 같다.
Flashcard에서는 프로바이더마다 다른 응답 형식과 오류 처리를 Supabase가 흡수한다.
====

셋째, 토큰 수명 관리다.
액세스 토큰(access token)의 발급·만료·갱신, 리프레시 토큰(refresh token)의 회전과 폐기, 로그아웃 시 무효화까지 규칙 전체를 직접 운영해야 한다.

.[용어 풀이] 액세스 토큰(Access Token)과 리프레시 토큰(Refresh Token)
[NOTE]
====
액세스 토큰은 요청을 보낼 때마다 내미는 단기 출입증이고, 리프레시 토큰은 그 출입증이 만료됐을 때 새것을 받아 오는 장기 증서다.
매 요청에 실려 노출될 자리가 많은 액세스 토큰은 수명을 짧게 잡아 훔쳐도 오래 못 쓰게 하고, 갱신할 때만 꺼내는 리프레시 토큰은 길게 잡는다.
발급자가 리프레시 토큰을 폐기하면 갱신이 끊기므로, 로그아웃도 결국 이 토큰을 없애는 일이다.
AI 에이전트가 글을 세는 단위인 토큰과는 다른 뜻으로, 여기서는 로그인 상태를 증명하는 문자열이다.
====

넷째, 계정 부대 기능이다.
이메일 검증, 비밀번호 재설정, 계정 탈퇴는 핵심 도메인과 무관하지만 없으면 서비스가 성립하지 않는다.

기능 버그와 달리 인증 버그는 사고가 된다.
Flashcard는 이 목록 전체를 관리형 인증에 위임하고, Google/GitHub OAuth만 지원해 비밀번호를 아예 받지 않는다.
프로바이더와의 왕복 가운데 까다로운 부분(앱 등록, 동의 화면, 프로바이더별 응답 차이)은 Supabase가 흡수하고, 우리 서버는 Supabase와만 대화한다.
비밀번호를 받지 않는 이 앱에서 "Supabase Auth만 걷어내면 무엇이 남는가"를 따진 목록은 {ch-alternatives}에 있다.

=== 대안 비교: 언제 다른 선택이 나은가

|===
| 대안 | 제공 범위 | Flashcard 관점의 한계 | 이 대안이 더 나은 경우

| Neon | 서버리스 Postgres | 인증이 없어 별도 서비스 필요 | 인증 스택이 이미 있거나 DB 브랜칭이 필요할 때
| Firebase | 인증 + NoSQL DB + 호스팅 | Firestore는 관계형 스키마에 부적합, 벤더 종속 | 모바일 중심의 실시간 동기화 앱
| Auth0 / Clerk | 인증 전문 | DB가 없어 플랫폼이 하나 늘어남 | 엔터프라이즈 SSO·조직 관리가 필요할 때
| 자체 호스팅 | 전부 직접 구성 | 고정비와 운영 부담 | 데이터 주권·규제 요구, 서버 운영 역량이 있는 팀
|===

Neon은 훌륭한 서버리스 Postgres이고, 브랜치별로 DB 사본을 만드는 브랜칭은 Supabase에 없는 강점이다.
하지만 인증이 없어 Auth.js나 Clerk 같은 인증 스택을 따로 붙여야 하고, 그 순간 관리할 플랫폼이 늘어난다.

Firebase는 인증과 DB를 통합 제공한다는 점에서 가장 비슷한 대안이다.
그러나 Firestore는 NoSQL 문서 저장소라 {ch-database-design}의 관계형 스키마(외래 키 제약, JOIN, 집계 쿼리)를 그대로 옮길 수 없다.
더 큰 문제는 벤더 종속(vendor lock-in)이다.
Firestore 전용 API로 쓴 데이터 계층은 이식할 수 없지만, Supabase의 DB는 표준 PostgreSQL이라 `pg_dump` 한 번으로 어디로든 옮긴다.
반대로 모바일 SDK와 실시간 동기화가 핵심인 앱이라면 Firebase가 더 나은 답이다.

Auth0와 Clerk는 인증 기능이 더 깊어서 엔터프라이즈 SSO나 조직·팀 관리가 필요한 B2B 서비스에 낫다.
하지만 DB를 따로 마련해야 해 "플랫폼 최소화"와 어긋나고, 무료 티어의 월간 활성 사용자 한도를 넘기면 인증만으로 과금이 시작된다.

자체 호스팅은 VPS(Virtual Private Server, 매달 요금을 내고 빌려 쓰는 가상 서버)에 PostgreSQL과 인증 서버를 직접 올리는 방식이다.
Supabase 자체가 오픈소스라 통째로 직접 올릴 수도 있다.
데이터 주권이나 규제 요구가 있는 팀에는 정답이지만, 고정비와 백업·패치·모니터링 부담이 따라와 "완전 무료, 관리 최소화"와는 정반대다.

=== Supabase의 전부를 쓰지 않는다

Supabase는 테이블에서 REST API를 자동 생성하는 PostgREST, WebSocket 기반 실시간 구독인 Realtime, 파일 저장소인 Storage, Deno 기반 Edge Functions까지 제공한다.
Flashcard는 이 중 Postgres와 Auth만 쓴다.
PostgREST를 쓰지 않는 이유는 데이터 접근 규칙이 단순 CRUD가 아니기 때문이다.
간격 반복 계산이나 스마트 덱 조건 평가 같은 로직은 행 수준 보안(Row Level Security, RLS) 정책으로 표현하기에 복잡하고, Go 코드로 두는 편이 테스트하기도 쉽다.

Supabase의 공식 자바스크립트 라이브러리 supabase-js도 쓰지 않는다.
공식 퀵스타트는 supabase-js(와 서버 렌더링용 `@supabase/ssr`)를 프런트엔드 코드에서 불러 로그인하는 흐름을 안내한다footnote:[Next.js 퀵스타트가 `@supabase/supabase-js`와 `@supabase/ssr`이 설치된 템플릿에서 출발한다. https://supabase.com/docs/guides/getting-started/quickstarts/nextjs[Use Supabase with Next.js]].
그러나 Flashcard의 화면은 서버에서 렌더링되고({ch-html-template}, {ch-htmx}), 로그인 흐름에도 브라우저 자바스크립트가 필요 없다.
대신 Go 서버가 Supabase Auth의 REST API(GoTrue라는 오픈소스 인증 서버다)와 직접 대화하고, 그 클라이언트 전체가 `internal/web/gotrue.go`의 130줄 남짓이다.

이렇게 절제한 덕에 벤더 종속도 줄어든다.
데이터 계층은 표준 PostgreSQL 프로토콜로만, 인증은 표준에 가까운 조각(OAuth 인가 코드 흐름, JWT, JWKS)으로만 대화한다.
훗날 Supabase를 떠나더라도 DB는 `DATABASE_URL`만, 인증은 인가·토큰 엔드포인트 주소와 JWKS URL만 바꾸면 검증 코드가 그대로 동작한다.

== 서버 사이드 인증: 브라우저에는 토큰이 없다

로그인 버튼을 누른 순간부터 Go 핸들러가 사용자를 식별하기까지는, 브라우저가 세 곳을 차례로 다녀와 쿠키 하나를 받아 오는 여정이다.

프로바이더와 마주 보는 쪽은 GoTrue이고, 토큰이 오가는 ⑤는 서버와 GoTrue 사이의 통신이다.

.[용어 풀이] 리다이렉트(Redirect)와 콜백(Callback)
[NOTE]
====
서버가 브라우저에 "저 주소로 가라"고 응답하면 브라우저가 스스로 그 주소로 옮겨 가는 것이 리다이렉트다.
그렇게 다른 곳을 다녀온 브라우저가 우리 서버의 약속된 주소(`/auth/callback`)로 되돌아오는 것이 콜백이다.
로그인 도중 화면이 몇 번 바뀌는 것은 이 둘이 이어진 결과다.
====

출발점인 로그인 화면(`internal/web/templates/pages/login.html`)의 버튼은 서버의 시작 주소를 가리키는 평범한 링크다.

[source,html]
----
<a class="btn btn-big btn-google" href="/auth/login/google?next={{.Data.Next}}">
  <!-- ... -->
  Google로 계속하기
</a>
----

`?next=`는 로그인이 끝난 뒤 돌아갈 화면을 기억해 두는 파라미터인데, 그 안전 처리는 "만료와 리프레시" 절에서 다룬다.

=== OAuth 리다이렉트 여행

링크가 가리키는 `/auth/login/google`을 처리하는 핸들러가 그림의 ①~②, 방문자를 GoTrue의 인가 화면으로 떠나보내는 `internal/web/authpages.go`의 `startOAuth`다.

[source,go]
----
// startOAuth는 서버 측 PKCE 흐름을 시작한다. verifier와 돌아갈 주소를 짧은
// 수명의 쿠키에 남기고 방문자를 GoTrue로 보낸다.
func (w *Web) startOAuth(c *gin.Context) {
	provider := c.Param("provider")
	if provider != "google" && provider != "github" {
		w.renderError(c, http.StatusNotFound, "지원하지 않는 로그인 방식이에요.")
		return
	}
	// ...
	verifier := newPKCEVerifier()
	setCookie(c, pkceCookie, verifier, 300)
	setCookie(c, nextCookie, safeNext(c.Query("next")), 300)
	redirectTo := origin(c) + "/auth/callback"
	c.Redirect(http.StatusSeeOther, w.goTrue.authorizeURL(provider, redirectTo, pkceChallenge(verifier)))
}
----

핸들러는 "PKCE" 절에서 설명할 검증용 무작위 값(verifier)과 돌아갈 경로를 수명 5분짜리 쿠키에 적어 두고, 브라우저를 GoTrue의 인가 주소로 리다이렉트한다.

.[용어 풀이] 쿠키(Cookie)
[NOTE]
====
서버가 브라우저에 맡겨 두는 작은 기록으로, 브라우저는 같은 사이트에 요청을 보낼 때마다 이 기록을 자동으로 동봉한다.
가게가 손님 손목에 채워 준 입장 팔찌처럼, 한 번 채워 두면 매번 신원을 설명하지 않아도 된다.
이 책에서는 쿠키로 유지되는 로그인 상태를 로그인 세션이라 부르는데, AI 에이전트와 대화할 때 말하는 세션과는 다른 뜻이다.
====

인가 주소를 만드는 `internal/web/gotrue.go`의 `authorizeURL`은 GoTrue 주소 뒤에 값 네 개를 매단다.
어느 프로바이더로 갈지, 끝나면 어디로 돌아올지(`redirect_to`), 그리고 "PKCE" 절에서 볼 지문 값과 그 지문을 뜬 방식이다.

[source,go]
----
include::../../flashcard-advanced/internal/web/gotrue.go[tag=authorize-url]
----

이 주소로 이동한 브라우저는 GoTrue를 거쳐 Google이나 GitHub의 동의 화면으로 넘어간다(③).
방문자가 동의하면 프로바이더는 브라우저를 GoTrue로, GoTrue는 다시 `redirect_to`에 적힌 우리 앱의 `/auth/callback`으로 돌려보내고, 이때 URL에 `?code=`라는 인가 코드가 붙어 온다(④).
인가 코드는 토큰 그 자체가 아니라 "토큰으로 바꿔 갈 수 있는 교환권"이다.

교환권을 현물로 바꾸는 곳이 같은 파일의 `oauthCallback`, 그림의 ⑤~⑥이다.

[source,go]
----
// oauthCallback은 흐름을 마무리한다. code를 토큰으로 바꿔 HttpOnly 쿠키에
// 담으므로 브라우저는 access token을 보지 못한다.
func (w *Web) oauthCallback(c *gin.Context) {
	next := safeNext(cookieValue(c, nextCookie))
	verifier := cookieValue(c, pkceCookie)
	clearCookie(c, pkceCookie)
	clearCookie(c, nextCookie)

	// ... (GoTrue가 ?error=로 알린 자기 쪽 실패는 로그에 남기고 로그인 화면으로)
	code := c.Query("code")
	if w.goTrue == nil || code == "" {
		log.Printf("oauth callback: no code in callback")
		failLogin(c, "로그인에 실패했어요. 다시 시도해주세요.")
		return
	}
	// ... (verifier 쿠키가 만료됐으면 처음부터 다시 시도하라고 안내)
	tok, err := w.goTrue.exchangeCode(c.Request.Context(), code, verifier)
	if err != nil {
		log.Printf("oauth callback: code exchange failed: %v", err)
		failLogin(c, "로그인에 실패했어요. 다시 시도해주세요.")
		return
	}
	w.setAuthCookies(c, tok)
	c.Redirect(http.StatusSeeOther, next)
}
----

출발할 때 쿠키에 적어 둔 verifier를 꺼내 인가 코드와 함께 GoTrue에 보내고, 액세스 토큰과 리프레시 토큰을 받는다.
받은 토큰은 `setAuthCookies`로 쿠키에 넣고, 방문자를 원래 가려던 화면으로 돌려보낸다.
실패(GoTrue가 알린 오류, 코드 없음, verifier 쿠키 만료, 교환 실패)는 어느 분기든 오류 메시지를 플래시 쿠키에 담아 로그인 화면으로 되돌리고, 원인은 `log.Printf`로 서버 로그에 남긴다.

=== PKCE: 가로챈 교환권을 쓸모없게 만든다

인가 코드는 URL에 실려 오가므로 노출될 수 있고, 가로챈 공격자가 먼저 토큰으로 교환하면 남의 계정에 들어간다.
이 공격을 막는 장치가 PKCE다.

.[용어 풀이] PKCE(Proof Key for Code Exchange)
[NOTE]
====
OAuth에서 인가 코드를 가로채도 토큰으로 바꿀 수 없게 만드는 안전장치다.
로그인을 시작할 때 무작위 비밀값(verifier)을 만들어 그 지문(해시)만 먼저 보내 두고, 코드를 교환할 때 비밀값 원본을 제시해 지문과 맞는지 확인받는다.
코드만 훔친 공격자는 원본 비밀값이 없어 교환 창구에서 거절당한다.
====

`internal/web/gotrue.go`의 `newPKCEVerifier`가 만드는 verifier는 암호학적 난수 32바이트이고, `pkceChallenge`가 뜨는 challenge는 그 SHA-256 해시다.
`authorizeURL`의 `code_challenge_method=s256`이 "지문은 SHA-256으로 떴다"는 선언이다.
해시는 한 방향으로만 계산되므로 challenge가 노출돼도 verifier를 되짚어 낼 수 없다.
교환 요청(`exchangeCode`)은 인가 코드와 verifier 원본을 함께 실어 보내고, GoTrue는 처음 받은 challenge와 지금 받은 verifier의 해시가 일치할 때만 토큰을 내준다.
verifier는 방문자의 HttpOnly 쿠키에만 있었으므로, 코드만 가로챈 제3자는 이 관문을 통과하지 못한다.

=== HttpOnly 쿠키에 담는 로그인 세션

교환으로 얻은 토큰은 스크립트가 읽을 수 없는 HttpOnly 쿠키에 보관한다.
`internal/web/cookies.go`의 첫머리에 쿠키 이름들이 모여 있고, 주석이 이 절의 요지를 담고 있다.

[source,go]
----
// 쿠키 이름들. 세션 토큰은 HttpOnly라 페이지 스크립트(주입된 스크립트 포함)가
// 읽을 수 없다. localStorage 대신 쿠키를 쓰는 가장 큰 이유다.
const (
	accessCookie  = "fc_access"
	refreshCookie = "fc_refresh"
	pkceCookie    = "fc_pkce"
	nextCookie    = "fc_next"
	// ...
)
----

로그인 세션의 본체는 `fc_access`(액세스 토큰)와 `fc_refresh`(리프레시 토큰)다.
모든 쿠키는 한 함수를 거쳐 만들어지므로 보안 속성이 한곳에 모인다.

[source,go]
----
func setCookie(c *gin.Context, name, value string, maxAge int) {
	http.SetCookie(c.Writer, &http.Cookie{
		Name:     name,
		Value:    url.QueryEscape(value),
		Path:     "/",
		MaxAge:   maxAge,
		Secure:   isHTTPS(c),
		HttpOnly: true,
		SameSite: http.SameSiteLaxMode,
	})
}
----

속성 세 개가 각각 공격 하나씩을 맡는다.

첫째, `HttpOnly`는 스크립트를 통한 토큰 탈취를 막는다.
이 쿠키는 페이지의 어떤 자바스크립트도 읽을 수 없고, 브라우저가 HTTP 요청에 동봉할 때만 쓰인다.
공격자가 교차 사이트 스크립팅(XSS)으로 악성 스크립트를 심더라도 토큰을 복사해 나갈 길이 없다.

둘째, `Secure`는 평문 전송을 막는다.
이 쿠키는 HTTPS 연결에서만 전송되므로 통신을 엿보는 공격자에게 노출되지 않는다.
`isHTTPS`가 조건부인 것은 운영 구성을 로컬(`http://localhost:8080`)에서 확인할 때도 로그인이 돌아야 하기 때문이고, Vercel의 프록시(요청을 먼저 받아 함수에 전달하는 중계 서버) 뒤에서는 `X-Forwarded-Proto` 헤더로 원래 요청이 HTTPS였는지 판별한다.

셋째, `SameSite=Lax`는 교차 사이트 요청 위조(CSRF)를 막는다.
Lax는 다른 사이트에서 출발한 POST 요청에 쿠키를 싣지 않으므로, 데이터를 바꾸는 요청이 모두 POST인 이 앱에서는 이 한 줄이 CSRF 방어의 핵심이다.
악성 사이트에 숨겨 둔 폼이 `/decks/:slug/delete`로 POST를 보내도 쿠키 없이 도착하므로 익명 방문자의 요청일 뿐이다.
다른 사이트의 링크로 들어오는 평범한 이동(GET)에는 쿠키가 실린다.

.[용어 풀이] CSRF(교차 사이트 요청 위조, Cross-Site Request Forgery)
[NOTE]
====
로그인해 둔 방문자의 브라우저를 악성 사이트가 몰래 시켜, 우리 서버에 그 사람 이름으로 요청을 보내게 만드는 공격이다.
브라우저가 쿠키를 자동으로 동봉하는 성질을 거꾸로 이용하므로, 방문자는 남의 페이지에서 버튼 하나를 눌렀을 뿐인데 자기 덱이 지워질 수 있다.
악성 스크립트를 우리 페이지 안에 심는 XSS({ch-html-template})와 달리 공격자는 응답을 읽지 못하고 요청만 대신 보내게 할 뿐이라, 방어도 "남의 사이트에서 출발한 요청에는 쿠키를 붙이지 않는다"는 쪽이다.
====

토큰을 쿠키에 넣는 `setAuthCookies`는 액세스 쿠키의 수명을 토큰 만료(기본 1시간)보다 60초 짧게 잡는다.
서버 쪽에서 만료된 토큰이 쿠키에만 살아 있는 어중간한 상태를 피하기 위해서다.
리프레시 쿠키의 수명은 `refreshMaxAge` 상수로 정한 30일이다.
Supabase의 리프레시 토큰은 기본 설정에서 만료되지 않고 한 번 쓰면 교체될 뿐이며 세션 상한 설정은 Pro 플랜부터라서footnote:[Supabase 문서 "User sessions"의 리프레시 토큰과 세션 수명 설명. https://supabase.com/docs/guides/auth/sessions[User sessions]], 30일은 이 앱이 로그인 상태를 얼마나 오래 남겨 둘지 정한 값이다.

대안과 비교하면 차이는 안전의 기본값에 있다.
브라우저에서 인증을 처리하는 단일 페이지 앱(SPA)은 흔히 토큰을 localStorage(브라우저의 키-값 저장소)에 두는데, localStorage는 같은 사이트의 모든 스크립트가 읽을 수 있어 XSS에 성공한 공격자가 토큰을 들고 나간다.
SPA도 안전하게 만들 수 있지만 설계를 더 얹어야 하고, 쿠키 방식은 기본 속성 세 개만으로 방어선이 선다.
대신 쿠키는 CSRF라는 약점을 새로 들여오고, 그 대가를 `SameSite=Lax`로 치르는 것까지가 한 세트다.

=== 만료와 리프레시: 미들웨어가 조용히 처리한다

액세스 토큰의 수명은 1시간이다.
만료를 알아채고 리프레시 토큰으로 새 토큰을 받아 오는 일은 `internal/web/cookies.go`의 `withUser` 미들웨어가 페이지 핸들러 모르게 처리한다.

[source,go]
----
// withUser는 세션 쿠키에서 방문자를 알아내고, access token이 만료됐으면
// refresh token으로 페이지 핸들러 몰래 갱신한다. 익명 방문자는 통과시키며,
// 막는 일은 requireUser가 한다.
func (w *Web) withUser() gin.HandlerFunc {
	if w.cfg.AuthMode == "local" {
		return func(c *gin.Context) {
			auth.SetUserID(c, auth.LocalUserID)
			c.Next()
		}
	}
	return func(c *gin.Context) {
		if raw := cookieValue(c, accessCookie); raw != "" {
			if id, email, err := auth.ParseUser(raw, w.cfg.JWKSURL, w.cfg.JWTSecret); err == nil {
				auth.SetUserID(c, id)
				c.Set(emailKey, email)
				c.Next()
				return
			}
		}
		// access token이 없거나 만료됐다. refresh token을 한 번만 써 본다.
		if rt := cookieValue(c, refreshCookie); rt != "" {
			if tok, err := w.goTrue.refresh(c.Request.Context(), rt); err == nil {
				w.setAuthCookies(c, tok)
				if id, email, err := auth.ParseUser(tok.AccessToken, w.cfg.JWKSURL, w.cfg.JWTSecret); err == nil {
					auth.SetUserID(c, id)
					c.Set(emailKey, email)
					c.Next()
					return
				}
			}
			w.clearAuthCookies(c)
		}
		c.Next()
	}
}
----

경로는 셋이다.
첫째, 액세스 쿠키의 토큰이 유효하면 그대로 통과시킨다(가장 흔한 경로이고, 네트워크 왕복이 없다).
둘째, 만료됐거나 없으면 리프레시 쿠키로 GoTrue에 갱신을 한 번 요청해 새 토큰을 쿠키에 다시 심는다.
셋째, 그마저 실패하면 망가진 쿠키를 지우고 익명 방문자로 통과시킨다.
`auth.ParseUser`의 속(서명과 클레임 검증)은 {ch-token-verification}에서 다룬다.
맨 위의 로컬 모드 분기는 장 첫머리의 고정 사용자 규칙이 웹 계층에서도 똑같이 적용된다는 뜻이다.

익명 방문자를 통과시키는 것은 공개 화면(공유 덱 구경, 로그인 화면) 때문이고, 로그인이 필요한 화면 앞에는 `requireUser` 미들웨어가 문지기로 선다.
`requireUser`는 익명 방문자를 로그인 화면으로 보내면서, 로그인 뒤 되돌아갈 수 있게 가려던 주소를 `?next=`에 담는다.
그런데 이 `next` 값은 URL에 노출되는 사용자 입력이라 그대로 믿으면 안 되고, 이 값을 걸러 내는 함수가 `safeNext`다.

[source,go]
----
// safeNext는 앱 안의 경로만 받아들인다. 조작된 ?next= 링크가 로그인 뒤
// 방문자를 다른 출처로 튕겨 보내지 못하게 한다. 슬래시 하나로 시작해야 하고,
// "//host"는 다른 출처다. 역슬래시도 거절하는데, 브라우저가 "/\host"의
// 역슬래시를 슬래시로 읽어 "//host"로 가기 때문이다.
func safeNext(next string) string {
	if !strings.HasPrefix(next, "/") || strings.HasPrefix(next, "//") || strings.Contains(next, `\`) {
		return "/"
	}
	return next
}
----

`?next=`에 외부 주소를 심은 링크를 뿌리면, 로그인 직후 방문자를 피싱 사이트로 튕겨 보내는 열린 리다이렉트(open redirect) 공격이 가능하다.
`safeNext`는 `/`로 시작하는 앱 내부 경로만 허용한다.
`//evil.com`처럼 슬래시 두 개로 시작하는 값은 브라우저가 "지금과 같은 https로 evil.com에 가라"는 주소(프로토콜 상대 URL)로 읽으므로 걸러 낸다.
`/\evil.com`처럼 슬래시 뒤에 역슬래시를 붙인 값도 브라우저는 역슬래시를 슬래시로 읽어 `//evil.com`으로 가므로 거절한다footnote:[WHATWG URL Standard의 special scheme 처리 규칙. https://url.spec.whatwg.org/#special-authority-ignore-slashes-state[URL Standard §4.4]].

=== 로그아웃은 두 곳에서 끝난다

로그아웃은 방문자 브라우저의 쿠키와 GoTrue 서버에 살아 있는 리프레시 토큰, 두 곳을 지워야 한다.
`internal/web/authpages.go`의 로그아웃 핸들러가 둘을 순서대로 처리한다.

[source,go]
----
func (w *Web) logout(c *gin.Context) {
	if w.goTrue != nil {
		if at := cookieValue(c, accessCookie); at != "" {
			// 실패해도 무시한다. 쿠키만 지워도 브라우저는 로그아웃된다.
			_ = w.goTrue.logout(c.Request.Context(), at)
		}
	}
	w.clearAuthCookies(c)
	// signed_out은 app.js에 대한 신호다: 서비스 워커가 오프라인용으로 캐시해 둔
	// 이 사용자의 페이지 HTML을 지우게 한다.
	c.Redirect(http.StatusSeeOther, "/login?signed_out=1")
}
----

GoTrue의 로그아웃 엔드포인트로 서버 쪽 세션(리프레시 토큰)을 폐기하고, 이어서 쿠키를 지운다.
`?signed_out=1`은 서비스 워커가 이 사용자를 위해 캐시해 둔 화면을 지우라는 신호다({ch-caching}).
서버 폐기 호출의 오류를 `_`로 버린 것은 의도한 판단이다.
GoTrue 호출이 실패해도 쿠키 삭제만으로 이 브라우저는 로그아웃되고, 폐기되지 못한 리프레시 토큰은 GoTrue 안에 남더라도 그 값을 아는 곳이 어디에도 없어 쓰일 길이 없다.
서버 폐기 실패를 오류로 처리해 "로그아웃을 눌렀는데 로그인 상태인" 화면을 보이느니, 최선을 다하되(best-effort) 실패해도 진행하는 쪽이 정직하다.

=== 무상태: 쿠키를 쓰지만 세션 저장소는 없다

전통적인 쿠키 세션과 결정적으로 다른 점은, 서버 어디에도 세션 저장소가 없다는 것이다.

로그인한 사용자를 알아보는 방식은 크게 둘이다.
서버가 방문자 명부를 들고 손님에게는 번호표만 쥐여 주는 세션 저장소 방식과, 손님이 신분증을 직접 들고 다니는 JWT 방식이다.
세션 저장소 방식은 서버가 세션을 메모리나 Redis(값을 메모리에 두고 빠르게 꺼내 주는 별도의 저장 서버)에 두고 쿠키로는 세션 ID만 주고받는다.
상주 서버라면 좋은 선택이지만, 서버리스에서는 인스턴스 메모리에 세션을 둘 수 없고, Redis를 붙이면 관리 플랫폼이 하나 늘어난다.

Flashcard의 쿠키에는 번호표가 아니라 신분증 원본, 즉 서명된 JWT가 들어 있다.
서명은 발급자만 찍을 수 있지만 진짜인지 대조하는 일은 누구나 할 수 있고, 그 대조에만 쓰는 열쇠가 공개키(public key)다.
Supabase는 이 열쇠를 JWKS라는 공개 주소에 걸어 두므로, 어떤 인스턴스가 요청을 받아도 외부 저장소 조회 없이, 비밀 값 하나 없이 사용자를 식별한다({ch-token-verification}).
무상태(stateless)라서 인스턴스가 몇 개로 늘어나도(수평 확장) 걸리는 것이 없고, 콜드스타트 때 세션 저장소 연결을 기다릴 필요도 없다.

.[용어 풀이] 무상태(Stateless)
[NOTE]
====
서버가 이전 요청을 따로 기억해 두지 않고, 한 요청을 처리하는 데 필요한 정보가 그 요청 안에 모두 담겨 오는 구조다.
매번 신분증을 지참하고 오는 손님처럼, 창구 직원이 누구로 바뀌어도 바로 응대할 수 있다.
그래서 서버리스 인스턴스가 수시로 생기고 사라져도 아무 인스턴스나 요청을 처리할 수 있다.
====

대가는 발급된 토큰을 만료 전에 강제로 폐기하기 어렵다는 것이다.
Supabase는 액세스 토큰 수명을 1시간으로 짧게 잡고 리프레시 토큰 폐기로 갱신을 끊어 이 약점을 완화한다.
탈취 즉시 차단이 필요한 금융 서비스 수준이라면 세션 저장소나 토큰 블랙리스트를 검토해야 하지만, 이 앱에서는 1시간이면 감수할 만하다.

== 환경 변수와 OAuth 앱 등록

=== 환경 변수는 두 개면 된다

이 장의 구성 전체를 켜는 환경 변수는 `SUPABASE_URL`과 `SUPABASE_ANON_KEY` 둘이다.
아래는 `internal/config/config.go`에서 운영 모드로 판정한 뒤, 필수 값이 빠졌으면 기동을 거부하고 JWKS 주소는 직접 계산하는 부분이다.

[source,go]
----
if cfg.DatabaseURL != "" {
	cfg.Driver = "postgres"
	cfg.AuthMode = "supabase"
	if cfg.SupabaseURL == "" || cfg.SupabaseAnonKey == "" {
		return nil, fmt.Errorf("SUPABASE_URL and SUPABASE_ANON_KEY are required")
	}
	if cfg.JWKSURL == "" && cfg.JWTSecret == "" {
		cfg.JWKSURL = cfg.SupabaseURL + "/auth/v1/.well-known/jwks.json"
	}
	return cfg, nil
}
----

`SUPABASE_URL`은 프로젝트의 기본 주소(`https://<project-ref>.supabase.co`)로, GoTrue의 인가·토큰·로그아웃 엔드포인트와 JWKS URL이 모두 이 아래에 있다.

`SUPABASE_ANON_KEY`는 이름에 key가 들어 있지만 비밀이 아니다.
"이 요청이 어느 프로젝트의 익명(anonymous) 방문자 몫인가"를 GoTrue에 알리는 식별자로, supabase-js를 쓰는 앱에서는 브라우저 코드에 그대로 박아 배포하는 값이다.
노출되어도 할 수 있는 일은 익명 사용자에게 허용된 일뿐이다.
Supabase에는 브라우저가 테이블에 바로 요청을 보낼 수 있는 통로(PostgREST)도 딸려 오는데, Flashcard는 모든 테이블에 RLS를 켜 두고 정책을 하나도 만들지 않아 anon key로는 아무 행도 읽거나 쓸 수 없다({ch-supabase-db}).
데이터에 닿는 길은 Go 서버의 직접 연결 하나뿐이고, GoTrue 호출도 전부 서버에서 일어나므로 이 키가 브라우저에 내려갈 일도 없다.

=== OAuth 앱 등록과 Redirect URL

코드 밖에서 손으로 할 준비가 두 가지 있다(클릭 절차는 {ch-deploy}).

첫째는 프로바이더 쪽 등록이다.
Google Cloud Console과 GitHub Developer Settings에 OAuth 앱을 만들고, 발급받은 Client ID와 Secret을 Supabase 대시보드의 Providers 설정(어느 프로바이더로 로그인을 받을지 켜고 끄는 화면)에 입력한다.

.[용어 풀이] Client ID와 Client Secret
[NOTE]
====
프로바이더가 등록된 앱에 발급하는 아이디와 비밀번호 한 쌍으로, 앱이 "나는 그때 등록한 그 앱이다"라고 밝히는 데 쓴다.
Client ID는 로그인 주소에 실려 나가는 공개 값이지만, Secret이 밖으로 나가면 남이 우리 앱 행세를 할 수 있다.
그래서 Secret은 저장소에 커밋하지 않고 Supabase 대시보드에만 넣어 두며, 노출이 의심되면 새로 발급받아 다시 넣는다.
====

이때 프로바이더에 등록하는 콜백 주소는 우리 앱이 아니라 `https://<project-ref>.supabase.co/auth/v1/callback`이다.
프로바이더 입장에서 상대는 GoTrue이고, 우리 앱은 그 뒤에 있다.

둘째는 Supabase 쪽 허용 목록이다.
`startOAuth`가 보내는 `redirect_to`, 즉 로그인을 마친 브라우저가 돌아올 우리 앱의 주소는 대시보드의 URL Configuration에 미리 등록된 것만 유효하다.
Flashcard는 배포본의 `https://<앱>.vercel.app/auth/callback`과, 운영 구성을 로컬에서 확인할 때 쓰는 `http://localhost:8080/auth/callback`을 등록한다.
로컬 모드({ch-local-dev})는 로그인이 없으므로 이 등록과 무관하고, 로컬 주소는 환경 변수를 채워 운영 구성 그대로 띄웠을 때 실제 로그인 왕복을 배포 전에 확인하기 위한 것이다.
이 허용 목록이 없다면 공격자가 `redirect_to`에 자기 서버를 적어 인가 코드를 자기 쪽으로 배달시킬 수 있다.
로그인 후 다시 로그인 화면으로 돌아오는 증상을 만나면 이 목록에 배포 URL을 빠뜨리지 않았는지부터 확인한다.

== 에이전트 활용 아이디어

* 인증은 {ch-instructing}의 검토 강도 기준으로 보면 오류 발견이 어렵고 비용이 큰 영역이다. 고칠 파일을 `internal/auth`와 `internal/web/cookies.go`처럼 이름으로 못 박고, 결과 diff는 한 줄씩 정독한다.
* `AGENTS.md`에 "토큰은 HttpOnly 쿠키로만 다루고 브라우저 자바스크립트에 노출하지 않는다", "인증 검증 로직은 `internal/auth`에만 둔다", "리다이렉트 대상은 상대 경로만 허용한다"를 적어 둔다. 에이전트의 "더 깔끔한" 수정이 방어 장치를 걷어내는 사고를 막는다.
* 인증 코드를 고친 뒤에는 "이 변경에서 토큰 탈취, CSRF, 열린 리다이렉트 가능성을 점검해 달라"고 공격자 역할을 시킨다. 사람의 정독을 대체하지는 못하지만 빠뜨린 항목을 다시 확인하는 보완으로 쓸 만하고, 자주 쓰는 지시문으로 저장해 두고 불러 쓸 만하다.

== 정리

첫째, Supabase는 관리형 PostgreSQL과 OAuth 인증을 무료 티어 하나로 해결한다.
인증을 직접 만들 때 떠안는 비밀번호 저장, 계정 부대 기능, 토큰 수명 관리, OAuth 왕복 구현을 통째로 위임했다.

둘째, Supabase의 전부를 쓰지 않았다.
PostgREST·Realtime·Storage와 supabase-js 없이 Postgres와 GoTrue의 REST API만 골라 써서 벤더 종속을 줄였다.

셋째, 인증은 서버가 처리하고 브라우저에는 토큰이 없다.
Go 서버가 PKCE를 갖춘 OAuth 왕복과 코드 교환을 수행하고, 토큰은 HttpOnly·Secure·SameSite=Lax 쿠키에 담긴다.
XSS 토큰 탈취, 평문 전송, CSRF, 코드 가로채기, 열린 리다이렉트에 방어 장치가 하나씩 짝지어져 있다.

넷째, 쿠키를 쓰지만 서버는 무상태다.
쿠키에 든 서명된 JWT는 어느 인스턴스에서든 JWKS 공개키만으로 검증되고, 만료된 토큰은 `withUser`가 조용히 갱신한다.

다음 {ch-token-verification}에서는 JWT의 서명을 JWKS 공개키로 확인하는 원리와 클레임 검증, 페이지와 API의 두 인증 경로가 같은 검증 코드로 수렴하는 구조를 다룬다.
로그인은 이 장까지로 완성이므로, 진도가 급한 독자는 {ch-supabase-db}으로 바로 가도 된다.
