= 마이그레이션: 운영 중에 스키마를 고친다

스키마는 한 번 만들고 끝나지 않는다.
로컬 SQLite는 스키마가 어긋나면 파일을 지우고 새로 시작하면 그만이지만, 운영 DB는 사용자의 데이터가 살아 있는 채로 구조를 바꿔야 한다.
이 장에서는 golang-migrate로 변경 이력을 순서 있는 파일로 쌓는 방법과, 요구사항 변화가 스키마 변경으로 이어진 세 사례를 읽는다.
이어서 그 적용을 GitHub Actions와 브랜치에 맡기는 체계를 세우고, 배포와 마이그레이션이 서로를 기다리지 않는 상황에서 변경을 안전하게 나누는 확장 후 축소로 마무리한다.

== 로컬은 통째로, 운영은 순서대로

로컬 모드는 스키마를 관리한 적이 없다.
`internal/litestore`의 `Open`이 서버를 켤 때마다 바이너리에 임베드된 `schema.sql`을 통째로 적용하기 때문이다({ch-first-run}).
이 파일은 완성형 스키마 한 장이고, 모든 문장이 `create ... if not exists`라 몇 번을 실행해도 결과가 같다.
스키마가 크게 바뀌어 어긋나면 `flashcard.db`를 지우고 새로 시작해도 잃는 것은 내 학습 기록뿐이다.

운영 DB에서는 "지우고 새로 만들기"가 선택지에 없다.
지금 스키마가 어느 버전인지, 다음 버전으로 가려면 무엇을 실행해야 하는지가 명시적으로 남아 있어야 하고, 그 답이 순서 있는 마이그레이션이다.

.[용어 풀이] 마이그레이션(Migration)
[NOTE]
====
데이터베이스 구조를 바꾸는 절차를 순서 있는 변경 스크립트 파일로 남겨 관리하는 방식이다.
"이 테이블에 열을 추가한다" 같은 변경을 파일로 기록해 git에 쌓아 두면, 다른 환경에서도 같은 파일을 순서대로 실행해 똑같은 구조에 도달한다.
데이터베이스판 버전 관리다.
====

== golang-migrate와 버전 관리

`internal/db/migrations/` 디렉터리에는 `000001_init`부터 번호가 차례로 붙은 버전이 있고, 버전마다 적용(up)과 되돌리기(down) 스크립트가 쌍을 이룬다.
이 글을 쓰는 시점에 가장 최근 버전인 `000005_deck_story`는 덱에 이야기 글을 담는 `story` 칼럼을 더한 변경으로, {ch-html-template}에서 읽은 덱 스토리가 여기에 저장된다.
파일명의 앞자리 숫자가 버전이라, 어떤 환경이든 "현재 버전에서 최신 버전까지의 up을 순서대로 실행"하면 같은 스키마에 도달한다.

로컬 모드의 `schema.sql`은 이 다섯 마이그레이션을 모두 적용한 결과를 SQLite 문법으로 옮겨 한 파일로 합친 것이다.
그래서 PostgreSQL 마이그레이션을 추가하면 같은 커밋에서 `internal/litestore/schema.sql`도 고쳐야 로컬 모드와 운영이 같은 스키마 위에서 돈다.
이 일을 잊으면 `internal/litestore/schema_test.go`가 잡아 준다.
마이그레이션이 만든 테이블·뷰·열이 `schema.sql`에도 다 있는지, `schema.sql` 첫머리의 `Ported through:` 줄이 가장 최근 마이그레이션 이름을 적고 있는지를 대조하는 테스트다.

실행 도구는 golang-migrate 라이브러리다.
`internal/db/migrate.go`에서 아직 적용되지 않은 마이그레이션만 순서대로 실행하는 함수를 보자.

[source,go]
----
//go:embed migrations/*.sql
var migrationsFS embed.FS

// Migrate는 아직 적용되지 않은 마이그레이션을 모두 적용한다. golang-migrate가
// advisory lock을 잡으므로 트랜잭션 풀링이 아닌 직접 연결이 필요하다.
func Migrate(databaseURL string) error {
	src, err := iofs.New(migrationsFS, "migrations")
	// ...
	m, err := migrate.NewWithSourceInstance("iofs", src, "pgx5://"+trimScheme(databaseURL))
	// ...
	if err := m.Up(); err != nil && !errors.Is(err, migrate.ErrNoChange) {
		return err
	}
	// ...
}
----

`//go:embed`는 SQL 파일을 컴파일 시점에 바이너리 안에 넣는 Go 기능으로, litestore가 `schema.sql`을 품는 것과 같은 방식이다.
golang-migrate는 `schema_migrations` 테이블에 현재 버전을 기록해 두고 미적용분만 실행하며, 적용 중에는 PostgreSQL 권고 잠금(advisory lock)을 잡아 동시 실행을 막는다.

.[용어 풀이] 권고 잠금(Advisory Lock)
[NOTE]
====
특정 행이나 테이블이 아니라, 프로그램끼리 약속한 이름 하나를 잠그는 PostgreSQL 기능이다.
회의실 문에 거는 "사용 중" 팻말처럼, DB가 강제로 막는 것이 아니라 팻말을 확인하기로 약속한 프로그램들 사이에서만 지켜진다.
마이그레이션 도구는 이 팻말로 두 실행이 같은 마이그레이션을 동시에 돌리는 사고를 막는다.
====

=== schema_migrations: 버전 한 줄과 dirty 플래그

golang-migrate는 대상 DB에 `schema_migrations` 테이블을 스스로 만들고 행 하나만 유지한다.
열은 마지막으로 적용된 버전 번호(`version`)와, 그 적용이 끝까지 성공했는지를 나타내는 참·거짓 값(`dirty`) 둘이다.
개발 DB에 다섯 마이그레이션을 모두 적용한 뒤 조회하면 `version`은 5, `dirty`는 거짓이다.

`m.Up()`은 이 한 줄을 읽고 쓰는 절차다.
첫째, 권고 잠금을 잡고 현재 버전과 dirty를 읽는다(테이블이 없으면 빈 DB로 본다).
둘째, dirty가 참이면 아무것도 하지 않고 `Dirty database version 3. Fix and force version.` 같은 오류를 내며 멈춘다.
셋째, 현재 버전보다 번호가 큰 up 파일을 순서대로 실행하되, 파일마다 dirty=참으로 먼저 기록하고 성공하면 dirty=거짓으로 덮어쓴다.
넷째, 실행할 파일이 없으면 `ErrNoChange`를 돌려주는데, `internal/db/migrate.go`는 이를 오류로 취급하지 않으므로 이미 최신인 DB에 몇 번을 실행해도 결과가 같다.

파일 실행이 실패하면 dirty가 참인 채로 남고, 그 뒤의 모든 실행은 둘째 단계에서 거부된다.
반쯤 바뀐 DB 위에 다음 마이그레이션을 얹는 대신, 사람이 실제 상태를 확인하고 버전을 손으로 맞춘 뒤 다시 시작하라는 것이다.

도구는 파일 하나를 통째로 보내고, PostgreSQL은 한 번에 받은 여러 문장을 암묵적인 트랜잭션 하나 안에서 실행한다.
그래서 한 문장이 실패하면 그 파일의 변경은 전부 취소되고, 뒤에서 볼 000003처럼 뷰를 지우고 다시 만드는 파일이 뷰만 사라진 채 남는 일은 없다.
dirty가 남은 DB는 대개 변경 없이 표시만 더럽혀진 상태라, 스키마를 확인한 뒤 버전을 되돌리면 정상으로 돌아온다.
예외는 파일이 성공한 뒤 dirty를 끄기 전에 러너가 죽거나 연결이 끊긴 경우로, 변경이 적용됐는데도 dirty가 남으므로 확인 없이 버전을 되돌리면 안 된다.

=== 마이그레이션은 direct 연결로

함수 주석의 "직접 연결이 필요하다"는 이 잠금 때문에 생기는 제약이다.
권고 잠금의 팻말은 그것을 건 연결 하나에만 매달려 있는데, {ch-supabase-db}의 트랜잭션 풀러는 트랜잭션이 끝날 때마다 연결을 회수해 다른 클라이언트에 빌려준다.
그러면 팻말은 엉뚱한 클라이언트의 연결에 걸린 채 남고, 팻말을 떼려는 요청은 팻말을 건 적 없는 연결로 간다.
그래서 마이그레이션은 작업이 끝날 때까지 같은 연결을 붙드는 경로로 접속해야 하고, 진입점인 `cmd/migrate/main.go`는 별도의 연결 문자열을 우선 사용한다.

[source,go]
----
func main() {
	url := os.Getenv("MIGRATE_DATABASE_URL")
	if url == "" {
		url = os.Getenv("DATABASE_URL")
	}
	// ...
}
----

`MIGRATE_DATABASE_URL`에는 포트 5432의 연결 문자열을 넣고, `MIGRATE_DATABASE_URL='<direct 연결 문자열>' go run ./cmd/migrate`처럼 실행한다.
직접 연결과 Supabase의 세션 풀러가 둘 다 5432이고, 둘 다 접속이 끝날 때까지 한 연결을 쥐고 있다.
마이그레이션은 배포할 때 한 번, 커넥션 하나로 끝나므로 이 연결의 부담은 문제가 되지 않는다.
수시로 열리는 API 쿼리는 6543으로, 가끔 실행되고 세션 상태에 기대는 마이그레이션은 5432로 나뉜다.

어느 5432를 쓸지는 주소 체계가 정한다.
인터넷 주소에는 오래 쓰여 온 IPv4와 그 뒤를 잇는 IPv6가 있는데, 2026년 7월 기준으로 Supabase의 직접 연결 주소(`db.<project-ref>.supabase.co`)에는 IPv6 주소만 등록되어 있다.
그래서 IPv6로 나가지 못하는 네트워크에서는 접속이 안 되고, 뒤에서 마이그레이션을 실행할 GitHub Actions 러너가 그런 환경이다.
이 저장소는 IPv4로 접속되면서 세션이 유지되는 세션 풀러의 5432 주소(`aws-0-us-east-1.pooler.supabase.com:5432`)를 쓴다.
API용 풀러 문자열에서 포트 번호만 6543에서 5432로 바꾼 것이다.

== 사례로 보는 스키마 진화

Flashcard는 초기 스키마 이후 네 번의 변경을 겪었고 그 이력이 마이그레이션 파일로 남아 있다.
그 가운데 사례 셋을 골라 요구사항 변화가 마이그레이션으로 이어진 과정을 본다.

=== 사례 1: 덱 공유 기능 추가

"내 덱을 다른 사용자에게 공유하고 싶다"는 요구가 추가됐다.
`internal/db/migrations/000002_sharing.up.sql` 전체로, 덱 테이블에 공유용 열 두 개를 더하고 공유 슬러그의 중복을 막는 인덱스를 건다.

[source,sql]
----
alter table decks
  add column share_slug text,
  add column shared_at timestamptz;

create unique index decks_share_slug_idx on decks (share_slug)
  where share_slug is not null;
----

공유 상태를 별도 테이블이 아니라 `decks`의 nullable 칼럼 두 개로 표현했다.
`share_slug is null`이면 비공유, 값이 있으면 공유 중이다.
마지막의 인덱스는 조건에 맞는 행만 골라 중복을 검사하는 부분 유니크 인덱스(partial unique index)다.
`where share_slug is not null` 조건 덕분에 공유되지 않은 대다수의 덱(NULL)은 인덱스에 들어가지 않고, 값이 있는 slug끼리만 겹치지 않는지 검사한다.

=== 사례 2: 양방향 카드로의 전환

초기에는 카드가 앞면(front)/뒷면(back)이라는 방향 있는 이름을 달고 있었다.
그런데 "영어→뜻"뿐 아니라 "뜻→영어"로도 학습하는 요구가 들어오자 이름이 실체와 어긋나게 됐다.
`internal/db/migrations/000003_bidirectional_cards.up.sql`에서 발췌한 다음 코드는 카드 종류에 '개념(concept)' 값을 더하고, 카드의 두 열 이름을 바꾸고, 학습 방향을 담는 열을 세션 테이블에 추가한다.

[source,sql]
----
alter type card_type add value if not exists 'concept';

create type study_direction as enum ('text_to_meaning', 'meaning_to_text');

alter table study_sessions
  add column direction study_direction not null default 'text_to_meaning';

drop view cards_with_stats;

alter table cards rename column front_text to text;
alter table cards rename column back_text to meaning;

-- ... (cards_with_stats 뷰를 새 칼럼 이름으로 재생성)
----

칼럼 이름을 `text`(외우려는 표현)와 `meaning`(그 뜻)이라는 방향 중립적 이름으로 바꾸고, 방향은 세션의 속성(`direction`)으로 옮겼다.
"방향은 카드가 아니라 학습 세션의 것"이라는 모델링 교정이다.
뷰가 칼럼을 참조하므로 뷰를 지우고 이름을 바꾼 뒤 다시 만든다.

down 파일 첫머리에는 추가한 enum 값은 제거할 수 없어 그대로 남긴다는 주석이 있다(`internal/db/migrations/000003_bidirectional_cards.down.sql`).

[source,sql]
----
-- Note: the 'concept' value added to card_type cannot be removed from the
-- enum; it is left in place (rows using it would block a true rollback).
----

PostgreSQL enum은 값을 추가할 수는 있어도 제거할 수 없으므로 이 down은 완전한 역연산이 아니다.
되돌릴 수 없는 변경의 한계를 주석으로 명시해 두는 것이 실무적인 타협이고, {ch-supabase-db}에서 말한 "enum은 변경이 비싸다"의 실증이다.

=== 사례 3: 덱 슬러그용 시퀀스

덱 URL을 `/deck?id={uuid}`에서 `/decks/{slug}` 형태의 짧은 경로로 바꾸는 요구가 생겼다.
`internal/db/migrations/000004_deck_seq.up.sql`의 핵심 두 줄은 덱마다 자동으로 증가하는 순번을 붙이고, 그 값이 겹치지 않게 제약을 건다.

[source,sql]
----
alter table decks add column seq bigint generated always as identity;
alter table decks add constraint decks_seq_key unique (seq);
----

새 칼럼을 추가하는 마이그레이션에는 기존 데이터를 어떻게 채울지라는 질문이 늘 따라온다.
`generated always as identity` 칼럼은 기존 행에도 순번을 자동으로 채워(backfill) 그 답을 대신해 준다.
이 `seq`를 뒤섞어 4자 URL 코드로 바꾸는 슬러그 설계는 {ch-domain-model}에서 다뤘다.

세 사례 모두 사용자 데이터가 쌓인 뒤에 도착한 요구다.
데이터를 보존한 채 열을 더하고 이름을 바꾸고 기존 행을 채우는 일이 순서 있는 파일로 남아, 어떤 환경이든 같은 명령 하나로 같은 스키마에 도달한다.

== 스키마 적용을 누가, 언제 하는가

=== 스키마 적용을 브랜치에 맡긴다

사람이 직접 적용하면 적용을 잊은 채 코드만 배포하거나, 개발 DB를 건너뛰고 운영에 먼저 적용하거나, 셸에 올려 둔 운영 연결 문자열 위에서 다른 명령까지 실행하게 된다.
셋 다 사람의 주의력에 기대는 위험이라, {ch-quality-gates}의 원칙대로 기계에 넘긴다.

`.github/workflows/migrate.yml`이 그 일을 한다.
마이그레이션 SQL이 바뀐 커밋이 push될 때만 깨어나고, `main`이면 개발 DB에, `release`면 운영 DB에 적용한다.
두 연결 문자열은 저장소 시크릿 `DEV_MIGRATE_DATABASE_URL`과 `PROD_MIGRATE_DATABASE_URL`로 등록해 둔다.

.[용어 풀이] 저장소 시크릿(Repository Secret)
[NOTE]
====
비밀번호나 접속 키처럼 코드에 적어 둘 수 없는 값을 GitHub에 따로 맡겨 두고, 워크플로가 돌 때만 꺼내 쓰게 하는 보관함이다.
저장소 설정 화면에서 이름과 값을 등록하면 워크플로 파일에서는 `secrets.이름`으로 가리키기만 하므로, 값은 저장소의 어느 파일에도 남지 않는다.
한 번 등록한 값은 다시 열어 볼 수 없고 덮어쓰기만 되며, 실행 로그에 찍히더라도 GitHub가 별표로 가려 준다.
유출이 의심되면 새 값으로 덮어쓰면 된다.
====

배포 절차는 이렇다.
첫째, 마이그레이션 파일을 추가하고, 칼럼 이름 변경이나 기존 행 채우기처럼 기존 데이터를 건드리는 변경이면 `./migrate_dev.sh`로 개발 DB에 먼저 적용해 결과를 눈으로 확인한다.
둘째, `main`에 push하면 워크플로가 개발 DB에 적용하고, 프리뷰 배포가 그 스키마 위에서 도는지 확인한다.
셋째, `main`을 `release`에 병합하면 같은 워크플로가 운영 DB에 적용하고, 프로덕션 배포가 뒤따른다.
사람이 하는 일은 파일을 쓰고 브랜치를 옮기는 것뿐이다.

같은 브랜치에 커밋을 연달아 밀어 워크플로가 두 번 깨어나면, 뒤엣것은 권고 잠금 앞에서 기다렸다가 앞엣것이 끝난 뒤에 돈다.
그래서 이 워크플로는 {ch-quality-gates}의 CI와 달리 진행 중인 실행을 취소하지 않는다.
마이그레이션을 중간에 끊으면 dirty가 참인 채로 남아 사람 손이 필요해지기 때문이다.

=== migrate.yml: 검사가 아니라 바꾸는 워크플로

이 워크플로는 {ch-git}의 브랜치 정책과 {ch-supabase-db}의 개발·운영 DB 분리 위에 서 있고, 문법은 {ch-quality-gates}의 `ci.yml`에서 본 그대로다.
다만 CI가 저장소 안에서 끝나는 검사를 했다면, `migrate.yml`은 러너 바깥의 살아 있는 데이터베이스에 접속해 되돌리기 어려운 변경을 남긴다.

[source,yaml]
----
include::../../.github/workflows/migrate.yml[]
----

네 곳을 차례로 보자.

첫째, `paths` 필터가 여기서는 시간을 아끼는 장치가 아니라 안전장치다.
필터가 없으면 스키마와 무관한 커밋마다 아무 일도 하지 않으려고 운영 DB에 접속을 열게 된다.
마이그레이션 코드가 완성본 앱 디렉터리 아래에 있으므로 경로마다 `flashcard-advanced/` 접두사가 붙고, 실행 스텝도 `working-directory`로 그 디렉터리에서 돈다.
워크플로 파일 자신(`.github/workflows/migrate.yml`)도 목록에 넣어, 이 파일을 고친 커밋에서 실제로 도는지 확인한다.

둘째, `${{ github.ref_name == 'release' && ... || ... }}`가 브랜치를 보고 접속할 DB를 정한다.
`github.ref_name`은 실행을 깨운 브랜치 이름이라, `release`면 운영 DB의, 그 밖(곧 `main`)이면 개발 DB의 연결 문자열이 `MIGRATE_DATABASE_URL`에 담긴다.
잡의 `name`에도 같은 표현식을 써서 로그에서 어느 DB의 마이그레이션인지 먼저 드러나게 했다.

셋째, `cancel-in-progress`가 `false`다.
검사는 다시 돌리면 그만이지만, 마이그레이션을 중간에 끊으면 dirty가 남으므로 중단 자체가 사고다.

넷째, 시크릿이 비어 있으면 곧바로 실패시킨다.
등록되지 않은 시크릿을 참조하면 GitHub는 오류 대신 빈 문자열을 건네주므로, 이 검사가 없으면 뜻 모를 오류를 뱉거나 엉뚱한 곳에 접속을 시도한다.
{ch-supabase-db}에서 본 서버의 기동 시점 설정 검사와 같은 발상이고, 오류 문구가 시크릿을 등록할 화면과 이름까지 안내한다.

이 구성 덕분에 개발자의 노트북에는 운영 접속 정보가 없어도 되고, 값이 없는 곳에서는 그 값으로 저지르는 사고도 일어나지 않는다({ch-env-secrets}).

=== 왜 서버가 스스로 적용하지 않는가

서버가 뜰 때 마이그레이션을 실행하게 만들면 워크플로도 시크릿도 필요 없지 않을까.
실제로 이 앱의 로컬 모드는 `litestore.Open`이 서버를 켤 때마다 `schema.sql`을 통째로 적용한다.

프로세스가 하나뿐이고 배포할 때 한 번 뜨는 상주 서버라면 좋은 선택지다.
기동 첫머리에서 마이그레이션을 실행하고 실패하면 뜨지 않게 하면 코드와 스키마가 늘 같이 맞춰진다.

서버리스에서는 그 전제가 네 가지로 어긋난다.

첫째, 연결 문자열이 맞지 않는다.
함수의 `DATABASE_URL`은 트랜잭션 풀러(6543)를 가리키고, 5432 문자열을 함수에도 넣으면 스키마를 바꿀 자격을 늘 켜져 있는 함수에 쥐여 주게 된다.
지금은 그 자격이 저장소 시크릿 안에만 있어서, 함수는 데이터를 읽고 쓸 뿐 구조를 바꾸지 못한다.

둘째, 실행 시점을 사용자가 정하게 된다.
함수는 요청이 도착해야 뜨므로 첫 요청을 보낸 사용자가 인덱스가 만들어지는 시간을 대신 기다리고, 실행 시간 상한인 300초({ch-free-tier})를 넘기면 오류를 받는다.
중간에 끊긴 마이그레이션은 dirty를 남겨 그다음 요청들까지 기동에 실패한다.

셋째, 인스턴스마다 시도한다.
권고 잠금 덕분에 결과는 어긋나지 않지만, 바꿀 것이 없는 평상시에도 콜드스타트마다 5432 연결을 열고 잠금을 확인한다.

넷째, 새 코드가 기동하며 스키마를 바꾸는 순간에도 옛 코드의 인스턴스는 살아 있으므로, 다음 절의 확장 후 축소는 그대로 필요하다.

프로세스가 요청을 따라 생겼다 사라지고 연결이 트랜잭션 풀러를 거치는 이 앱에서는, 스키마 변경을 앱 바깥의 한 번뿐인 절차로 떼어 놓는 편이 맞다.
로컬 모드는 데이터가 나 하나의 것이고 프로세스가 하나이며 어긋나면 파일을 지우면 그만이라, 정반대로 해도 된다.

=== 배포와 마이그레이션은 서로를 기다리지 않는다

`main`에 push하는 순간 GitHub Actions의 마이그레이션과 Vercel의 배포가 동시에 출발하고, 둘 사이에는 순서가 정해져 있지 않다.
마이그레이션이 먼저 끝나 새 스키마 위에서 옛 코드가 도는 것은 대체로 무해하지만, 배포가 먼저 끝나 새 코드가 아직 없는 칼럼을 조회하면 그 요청은 오류로 끝난다.

해법은 스키마 변경을 파괴적이지 않은 단계로 나누는 확장 후 축소(expand and contract)다.

.[용어 풀이] 확장 후 축소(Expand and Contract)
[NOTE]
====
스키마를 고칠 때 "추가"와 "제거"를 한 배포에 함께 담지 않고 여러 배포로 나누는 방식이다.
먼저 새 칼럼을 더하고(확장), 옛 칼럼과 새 칼럼을 모두 채우는 코드를 배포한 뒤, 읽는 쪽을 새 칼럼으로 옮기고, 마지막 배포에서야 옛 칼럼을 지운다(축소).
새 방을 먼저 지어 짐을 옮긴 다음 옛 방을 허무는 순서라, 어느 시점에 멈춰도 코드와 스키마가 함께 성립한다.
====

칼럼 이름을 바꾼 000003을 이 잣대로 보면, `rename column front_text to text`는 옛 이름과 새 이름이 공존하는 순간이 없으므로 배포와 마이그레이션 사이의 시차 동안 한쪽은 반드시 어긋난다.
확장 후 축소로 풀자면 새 칼럼 추가, 양쪽에 함께 쓰는 코드 배포, 데이터 복사, 읽기 전환, 옛 칼럼 제거로 나눠야 한다.
크게 보면 추가, 코드 전환, 제거의 세 단계이고, 가운데 코드 전환이 배포 여러 번으로 쪼개진다.
시차의 두 경우와 이 다섯 단계를 그림 28에 그렸다.

Flashcard는 사용자가 적고, 시차도 GitHub Actions 잡 하나와 Vercel 빌드 하나가 끝나는 시간의 차이에 그친다.
그래서 그 복잡도를 감수하는 대신 짧은 오류 가능성을 받아들였다.
규모가 정해 준 선택이지 원칙이 아니므로, 사용자가 늘면 값비싼 변경부터 확장 후 축소로 옮겨 가는 것이 맞다.
`AGENTS.md`에 "칼럼 삭제·이름 변경은 추가, 코드 전환, 제거의 세 단계로 나눈다"를 적어 둔 이유다.

== 정리

첫째, 운영 스키마는 golang-migrate의 버전 있는 up/down 파일 쌍으로 고친다.
같은 파일을 같은 순서로 실행하면 어떤 환경이든 같은 스키마에 도달하고, 로컬의 `schema.sql`은 그 결과를 SQLite로 옮긴 한 장이다.

둘째, 지금 상태는 `schema_migrations`의 한 줄이 말해 준다.
적용이 실패하면 dirty 플래그가 다음 실행을 막아 사람의 확인을 요구하고, 권고 잠금 때문에 마이그레이션은 세션이 유지되는 5432 연결로 붙는다.

셋째, 적용의 주체는 사람이 아니라 브랜치다.
`main` 푸시는 개발 DB에, `release` 병합은 운영 DB에 `migrate.yml`이 적용하고, 운영 연결 문자열은 저장소 시크릿 안에만 있어 함수에는 스키마를 바꿀 자격이 없다.

넷째, 배포와 마이그레이션은 서로를 기다리지 않으므로, 칼럼 삭제와 이름 변경은 확장 후 축소로 나눠야 어느 시점에 멈춰도 코드와 스키마가 함께 성립한다.

4부에 남은 것은 하나다.
다음 {ch-env-secrets}에서는 같은 이름이 개발과 운영에서 서로 다른 내용을 담게 된 환경 변수와 시크릿을 어디에 두고 어떻게 관리하는지 다룬다.
그것까지 갖춰지면 {ch-deploy}를 펴고 배포를 완주할 준비가 끝난다.
