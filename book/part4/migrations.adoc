= 마이그레이션: 운영 중에 스키마를 고친다

{ch-supabase-db}에서 운영 데이터베이스에 연결을 마쳤다.
그런데 스키마는 한 번 만들고 끝나지 않는다.
요구사항이 바뀌면 운영 중인 DB의 틀을 고쳐야 하는데, 이것은 연결과는 성격이 다른 새 문제다.
로컬 SQLite는 스키마가 어긋나면 파일을 지우고 새로 시작하면 그만이지만, 운영 DB는 사용자의 데이터가 살아 있는 채로 틀을 바꿔야 한다.
이 장에서는 먼저 golang-migrate로 변경 이력을 순서 있는 파일로 쌓는 방법을 익히고, 실제 요구사항 변화가 스키마 변경으로 이어진 세 사례를 읽는다.
이어서 그 적용을 사람이 아니라 GitHub Actions와 브랜치에 맡기는 체계를 세우고, 배포와 마이그레이션이 서로를 기다리지 않는 상황에서 스키마 변경을 안전하게 나누는 확장 후 축소로 마무리한다.

== 로컬은 통째로, 운영은 순서대로

로컬 모드는 스키마를 관리한 적이 없다.
`internal/litestore`의 `Open`이 서버를 켤 때마다 바이너리에 임베드된 `schema.sql`을 통째로 적용하기 때문이다({ch-first-run}).
이 파일은 완성형 스키마 한 장이고, 모든 문장이 `create ... if not exists`라 몇 번을 실행해도 결과가 같다.
이 방식이 허용되는 것은 로컬 DB의 데이터가 나 하나의 것이기 때문이다.
스키마가 크게 바뀌어 파일과 어긋나면 `flashcard.db`를 지우고 새로 시작해도 잃는 것이 내 학습 기록뿐이다.

운영 DB는 사용자의 덱과 학습 기록이 살아 있는 채로 틀을 고쳐야 하므로, "지우고 새로 만들기"는 선택지에 없다.
지금 스키마가 어느 버전인지, 다음 버전으로 가려면 무엇을 실행해야 하는지가 명시적으로 남아 있어야 하고, 그 답이 순서 있는 마이그레이션이다.

.[용어 풀이] 마이그레이션(Migration)
[NOTE]
====
데이터베이스 구조를 바꾸는 절차를, 순서 있는 변경 스크립트 파일로 남겨 관리하는 방식이다.
"이 테이블에 열을 추가한다" 같은 변경을 코드처럼 파일로 기록해 git에 쌓아 두면, 다른 환경에서도 같은 파일을 순서대로 실행해 똑같은 구조에 도달한다.
스키마의 변경 이력을 손으로 기억하는 대신 파일로 남기는, 데이터베이스판 버전 관리다.
====

== golang-migrate와 버전 관리

`internal/db/migrations/` 디렉터리에는 `000001_init`부터 `000005_deck_story`까지 다섯 버전이 있고, 버전마다 적용(up)과 되돌리기(down) 스크립트가 쌍을 이뤄 모두 열 파일이다.
가장 최근의 `000005_deck_story`는 덱에 이야기 글을 담는 `story` 칼럼을 더한 변경으로, {ch-html-template}에서 읽은 덱 스토리가 여기에 저장된다.
파일명의 앞자리 숫자가 버전이라, 어떤 환경이든 "현재 버전에서 최신 버전까지의 up을 순서대로 실행"하는 것만으로 같은 스키마에 도달한다.
덕분에 스키마의 버전 관리를 코드와 같은 git 저장소에서 하게 된다.
로컬 모드의 `schema.sql`이 이 다섯 마이그레이션을 모두 적용한 결과를 SQLite 방언으로 눌러 담은 한 장이라는 사실도 이제 말할 수 있다.
그래서 PostgreSQL 마이그레이션을 추가하면 같은 커밋에서 `internal/litestore/schema.sql`도 함께 고쳐야, 로컬 모드와 운영이 같은 스키마 위에서 돈다.

실행 도구는 golang-migrate 라이브러리다.
`internal/db/migrate.go`의 핵심을 보자.
마이그레이션 파일 중 아직 적용되지 않은 것만 순서대로 실행하는 함수다.

[source,go]
----
//go:embed migrations/*.sql
var migrationsFS embed.FS

// Migrate는 아직 적용되지 않은 마이그레이션을 모두 적용한다. golang-migrate가
// advisory lock을 잡으므로 트랜잭션 풀링이 아닌 직접 연결이 필요하다.
func Migrate(databaseURL string) error {
	src, err := iofs.New(migrationsFS, "migrations")
	// ...
	m, err := migrate.NewWithSourceInstance("iofs", src, "pgx5://"+trimScheme(databaseURL))
	// ...
	if err := m.Up(); err != nil && !errors.Is(err, migrate.ErrNoChange) {
		return err
	}
	// ...
}
----

`//go:embed`는 SQL 파일을 컴파일 시점에 바이너리 안에 넣는 Go 기능으로, litestore가 `schema.sql`을 품는 것과 같은 방식이다.
golang-migrate는 `schema_migrations` 테이블에 현재 버전을 기록해 두고 미적용분만 실행하며, 적용 중에는 PostgreSQL 권고 잠금(advisory lock)을 잡아 동시 실행을 막는다.

.[용어 풀이] 권고 잠금(Advisory Lock)
[NOTE]
====
특정 행이나 테이블이 아니라, 프로그램끼리 약속한 이름 하나를 잠그는 PostgreSQL 기능이다.
회의실 문에 "사용 중" 팻말을 걸어 두는 것과 같아서, DB가 접근을 강제로 막는 것이 아니라 그 팻말을 확인하기로 약속한 프로그램들 사이에서만 지켜진다.
마이그레이션 도구는 이 팻말로 "지금 누군가 스키마를 고치는 중"임을 알려, 두 사람이 같은 마이그레이션을 동시에 실행하는 사고를 막는다.
====

=== schema_migrations: 버전 한 줄과 dirty 플래그

"지금 이 DB가 몇 번 버전인가"를 어디에 적어 두느냐가 이 방식의 심장이다.
golang-migrate는 대상 DB에 `schema_migrations`라는 테이블을 스스로 만들고, 거기에 행 하나만 유지한다.
열은 둘로, 마지막으로 적용된 버전 번호(`version`)와 그 적용이 끝까지 성공했는지를 나타내는 참·거짓 값(`dirty`)이다.
개발 DB에 다섯 마이그레이션을 모두 적용한 뒤 이 테이블을 조회하면 `version`은 5, `dirty`는 거짓이다.

이 한 줄을 읽고 쓰는 절차가 `m.Up()`의 전부다.
첫째, 권고 잠금을 잡는다.
둘째, `schema_migrations`에서 현재 버전과 dirty를 읽는다(테이블 자체가 없으면 아직 아무것도 적용되지 않은 빈 DB로 본다).
셋째, dirty가 참이면 아무것도 하지 않고 `Dirty database version 3. Fix and force version.` 같은 오류를 내며 멈춘다.
넷째, 현재 버전보다 번호가 큰 up 파일을 번호 순서대로 실행하는데, 파일 하나마다 그 버전을 dirty=참으로 먼저 기록하고, 파일을 실행하고, 성공하면 같은 버전을 dirty=거짓으로 덮어쓴다.
다섯째, 실행할 파일이 하나도 없으면 `ErrNoChange`를 돌려주는데 `internal/db/migrate.go`가 이 값을 오류로 취급하지 않으므로, 이미 최신인 DB에 몇 번을 실행해도 결과가 같다.

네 번째 단계의 "dirty를 먼저 켜고 나중에 끈다"는 순서에 이 도구의 성격이 드러난다.
파일을 실행하다 실패하면 dirty가 참인 채로 남고, 그 뒤의 모든 실행은 세 번째 단계에서 거부된다.
스키마가 반쯤 바뀐 DB 위에 다음 마이그레이션을 얹어 상태를 더 헝클어뜨리는 대신, 사람이 DB를 열어 실제 상태를 확인하고 버전을 손으로 맞춘 뒤 다시 시작하라고 요구하는 것이다.
자동으로 복구를 시도하지 않고 멈춰 서는 것은 되돌리기 어려운 대상을 다루는 도구가 갖춰야 할 기본자세다.

도구가 파일 하나를 통째로 DB에 보낸다는 점도 알아 두면 좋다.
PostgreSQL은 이렇게 한 번에 받은 여러 문장을 암묵적인 트랜잭션 하나 안에서 실행하므로, 파일 안의 어느 한 문장이 실패하면 그 파일이 만든 변경은 전부 취소된다.
뒤에서 볼 000003처럼 뷰를 지우고 칼럼 이름을 바꾸고 뷰를 다시 만드는 파일이 중간에서 끊겨 뷰만 사라진 채 남는 일은 없다는 뜻이다.
그래서 dirty가 남는 상황은 "DB에는 아무 변경도 없는데 표시만 더럽혀진" 경우이고, 실제 스키마를 확인한 뒤 버전을 되돌리면 정상으로 복귀한다.
예외는 파일이 성공한 뒤 dirty를 거짓으로 덮어쓰기 전에 러너가 죽거나 연결이 끊긴 경우로, 이때는 변경이 적용됐는데도 dirty가 남으므로 확인 없이 버전을 되돌리면 안 된다.

=== 마이그레이션은 direct 연결로

함수 주석의 "직접 연결이 필요하다"가 바로 이 잠금 때문에 생기는 제약이다.
{ch-supabase-db}에서 API 쿼리는 트랜잭션 풀러를 거치게 만들었다.
그런데 권고 잠금의 "사용 중" 팻말은 그 팻말을 건 연결 하나에만 매달려 있다.
트랜잭션 풀러는 트랜잭션이 끝날 때마다 연결을 회수해 다른 클라이언트에 빌려주므로, 팻말을 건 연결과 그다음 작업을 하는 연결이 서로 다른 것이 되어 잠금이 오동작한다.
그래서 마이그레이션만은 작업이 끝날 때까지 같은 연결을 붙들 수 있는 경로로 접속해야 한다.
진입점인 `cmd/migrate/main.go`는 별도의 연결 문자열을 우선 사용한다.

[source,go]
----
func main() {
	url := os.Getenv("MIGRATE_DATABASE_URL")
	if url == "" {
		url = os.Getenv("DATABASE_URL")
	}
	// ...
}
----

`MIGRATE_DATABASE_URL`에는 직접 연결(포트 5432) 문자열을 넣고, `MIGRATE_DATABASE_URL='<direct 연결 문자열>' go run ./cmd/migrate`처럼 실행한다.
Supabase가 직접 연결이 어려운 네트워크를 위해 제공하는 세션 풀러(포트 5432)도 접속이 끝날 때까지 한 연결을 쥐고 있다.
세션 상태가 유지되므로 같은 용도로 쓸 수 있다.
마이그레이션은 배포할 때 한 번, 커넥션 하나로 끝나는 작업이라 직접 연결의 커넥션 부담이 문제가 되지 않는다.
정리하면 수시로 열리는 API 쿼리는 트랜잭션 풀러(6543)로, 가끔 실행되고 세션 상태에 기대는 마이그레이션은 세션이 유지되는 5432 쪽으로 용도에 따라 포트가 나뉜다.

그런데 같은 5432라도 어느 주소의 5432인지가 한 번 더 문제가 된다.
인터넷 주소 체계에는 오래 쓰여 온 IPv4와 그 뒤를 잇는 IPv6 두 세대가 있는데, 아직 IPv6로 통신하지 못하는 네트워크가 적지 않다.
2026년 7월 기준으로 Supabase의 직접 연결 주소(`db.<project-ref>.supabase.co`)에는 IPv6 주소만 등록되어 있어서, IPv6로 나가는 길이 없는 네트워크에서는 이 이름으로 접속 자체가 되지 않는다.
뒤에서 마이그레이션을 대신 실행하게 될 GitHub Actions 러너가 바로 그런 환경이고, 인터넷 회선에 따라서는 개발자의 노트북도 그렇다.
그래서 이 저장소는 마이그레이션에도 세션 풀러의 5432 주소(`aws-0-us-east-1.pooler.supabase.com:5432`)를 쓴다.
IPv4로 접속되면서 세션도 유지되는 주소를 고르는 것이 요점이고, 포트 번호만 6543에서 5432로 바꾼 문자열이 그 답이다.

== 사례로 보는 스키마 진화

Flashcard는 초기 스키마 이후 네 번의 변경을 겪었고 그 이력이 그대로 마이그레이션 파일로 남아 있다.
그 가운데 사례 셋을 골라, 요구사항 변화가 마이그레이션으로 이어진 과정을 순서대로 보자.

=== 사례 1: 덱 공유 기능 추가

"내 덱을 다른 사용자에게 공유하고 싶다"는 요구가 추가됐다.
`internal/db/migrations/000002_sharing.up.sql` 전체다.
덱 테이블에 공유용 열 두 개를 더하고, 공유 슬러그의 중복을 막는 인덱스를 건다.

[source,sql]
----
alter table decks
  add column share_slug text,
  add column shared_at timestamptz;

create unique index decks_share_slug_idx on decks (share_slug)
  where share_slug is not null;
----

공유 상태를 별도 테이블이 아니라 `decks`의 nullable 칼럼 두 개로 표현했다.
`share_slug is null`이면 비공유, 값이 있으면 공유 중이다.
마지막의 인덱스는 부분 유니크 인덱스(partial unique index)로, 테이블 전체가 아니라 조건에 맞는 행만 골라 중복을 검사한다.
공유 slug는 공유된 덱에만 존재하므로, `where share_slug is not null` 조건 덕분에 공유되지 않은 다수의 덱(NULL)은 인덱스에 아예 들어가지 않고, 값이 있는 slug 사이에서만 유일성이 강제된다.

=== 사례 2: 양방향 카드로의 전환

초기에는 카드가 앞면(front)/뒷면(back)이라는 방향 있는 이름을 달고 있었는데, "영어→뜻"뿐 아니라 "뜻→영어"로도 학습하는 양방향 요구가 들어오자 이름이 실체와 어긋나게 됐다.
`internal/db/migrations/000003_bidirectional_cards.up.sql`에서 발췌한다.
카드 종류에 '개념(concept)' 값을 하나 더하고, 카드의 두 열 이름을 바꾸고, 학습 방향을 담는 열을 세션 테이블에 추가하는 내용이다.
맨 앞의 값 하나가 뒤에서 되돌리기 이야기의 주인공이 된다.

[source,sql]
----
alter type card_type add value if not exists 'concept';

create type study_direction as enum ('text_to_meaning', 'meaning_to_text');

alter table study_sessions
  add column direction study_direction not null default 'text_to_meaning';

drop view cards_with_stats;

alter table cards rename column front_text to text;
alter table cards rename column back_text to meaning;

-- ... (cards_with_stats 뷰를 새 칼럼 이름으로 재생성)
----

칼럼 이름을 `text`(외우려는 표현)와 `meaning`(그 뜻)이라는 방향 중립적 이름으로 바꾸고, 방향은 세션의 속성(`direction`)으로 옮겼다.
"방향은 카드가 아니라 학습 세션의 것"이라는 모델링 교정이 이 마이그레이션의 본질이다.
뷰가 칼럼을 참조하므로 drop 후 재생성하는 순서도 눈여겨보자.

down 파일에는 스키마 진화의 쓴맛이 기록되어 있다.
`internal/db/migrations/000003_bidirectional_cards.down.sql` 첫머리로, 추가한 enum 값은 제거할 수 없어 그대로 남긴다는 주석이다.

[source,sql]
----
-- Note: the 'concept' value added to card_type cannot be removed from the
-- enum; it is left in place (rows using it would block a true rollback).
----

PostgreSQL enum은 값을 추가할 수는 있어도 제거할 수 없으므로 이 down은 완전한 역연산이 아니다.
되돌릴 수 없는 변경의 한계를 주석으로 명시해 두는 것이 실무적인 타협이다.
{ch-supabase-db}에서 말한 "enum은 변경이 비싸다"는 트레이드오프의 실증이기도 하다.

=== 사례 3: 덱 슬러그용 시퀀스

덱 URL을 `/deck?id={uuid}`에서 `/decks/{slug}` 형태의 짧은 경로로 바꾸는 요구가 생겼다.
`internal/db/migrations/000004_deck_seq.up.sql`의 핵심 두 줄이다.
덱마다 자동으로 증가하는 순번을 붙이고, 그 값이 겹치지 않게 제약을 건다.

[source,sql]
----
alter table decks add column seq bigint generated always as identity;
alter table decks add constraint decks_seq_key unique (seq);
----

`generated always as identity` 칼럼을 추가하면 기존 행에도 순번이 자동으로 채워진다(backfill).
새 칼럼을 추가하는 마이그레이션에서 기존 데이터를 어떻게 채울지는 항상 따라오는 질문인데, identity의 기본 동작이 그 답을 대신해 준 경우다.
이 `seq`를 뒤섞어 4자 URL 코드로 바꾸는 슬러그 설계는 {ch-domain-model}에서 다뤘다.

세 사례의 공통점은 사용자 데이터가 쌓인 뒤에 도착한 요구라는 것이다.
데이터를 보존한 채 열을 더하고 이름을 바꾸고 기존 행을 채우는 일이 모두 순서 있는 파일로 남아, 어떤 환경이든 같은 명령 하나로 같은 스키마에 도달한다.

== 스키마 적용을 누가, 언제 하는가

남은 절반은 "그럼 운영 DB에는 누가 적용하는가"다.

=== 스키마 적용을 브랜치에 맡긴다

사람이 직접 하는 방식에는 세 가지 실패가 따라온다.
스키마를 바꿔 놓고 적용을 잊은 채 코드만 배포하거나, 개발 DB에 적용하는 것을 건너뛰고 운영에 먼저 적용하거나, 운영 연결 문자열을 셸에 올려 둔 김에 다른 명령까지 그 위에서 실행하는 것이다.
셋 다 사람의 주의력에 기대는 종류의 위험이라, {ch-github-actions}의 원칙대로 기계에 넘긴다.

`.github/workflows/migrate.yml`이 그 일을 한다.
마이그레이션 SQL이 바뀐 커밋이 push될 때만 깨어나고, 어느 DB에 적용할지는 브랜치가 정한다.
`main`이면 개발 DB에, `release`면 운영 DB에 적용하며, 두 연결 문자열은 저장소 시크릿 `DEV_MIGRATE_DATABASE_URL`과 `PROD_MIGRATE_DATABASE_URL`로 등록해 둔다.
저장소 시크릿은 코드에 적어 둘 수 없는 값을 GitHub에 따로 맡겨 두고 워크플로가 돌 때만 꺼내 쓰게 하는 보관함이다.
워크플로 파일의 문법과 브랜치로 시크릿을 고르는 표현식은 다음 절에서 뜯어본다.

배포 절차 전체는 이렇게 정리된다.
첫째, 마이그레이션 파일을 추가하고, 칼럼 이름 변경이나 기존 행 채우기처럼 기존 데이터를 건드리는 변경이면 `./migrate_dev.sh`로 개발 DB에 먼저 적용해 결과를 눈으로 확인한다.
둘째, `main`에 push하면 워크플로가 개발 DB에 적용하고, 프리뷰 배포가 그 스키마 위에서 도는지 확인한다.
셋째, `main`을 `release`에 병합하면 같은 워크플로가 이번에는 운영 DB에 적용하고, 프로덕션 배포가 뒤따른다.
사람이 하는 일은 파일을 쓰고 브랜치를 옮기는 것뿐이고, 어느 DB에 적용할지는 이미 브랜치가 답하고 있다.

권고 잠금이 여기서 한 번 더 제값을 한다.
같은 브랜치에 커밋을 연달아 밀면 워크플로가 두 번 깨어날 수 있는데, 뒤엣것이 잠금 앞에서 기다렸다가 앞엣것이 끝난 뒤에 돈다.
그래서 이 워크플로만은 {ch-github-actions}의 CI와 달리 진행 중인 실행을 취소하지 않는다.
마이그레이션을 중간에 끊으면 `schema_migrations`의 dirty가 참인 채로 남아 사람 손이 필요해지기 때문이다.

=== migrate.yml: 검사가 아니라 바꾸는 워크플로

이제 `migrate.yml`을 한 줄씩 뜯어보자.
이 워크플로는 {ch-git}의 브랜치 정책과 {ch-supabase-db}의 개발·운영 DB 분리 위에 서 있고, 문법은 {ch-github-actions}의 `ci.yml`에서 본 그대로다.
다만 성격이 다르다.
{ch-github-actions}의 두 워크플로가 저장소 안에서 끝나는 일(검사, 정적 사이트 빌드)을 했다면, `migrate.yml`은 러너 바깥의 살아 있는 데이터베이스에 접속해 되돌리기 어려운 변경을 남긴다.
그 차이가 파일의 모든 줄에 드러난다.

[source,yaml]
----
include::../../.github/workflows/migrate.yml[]
----

네 곳을 차례로 보자.

첫째, `paths` 필터가 여기서는 시간을 아끼는 장치가 아니라 안전장치다.
필터가 없으면 스키마와 무관한 커밋마다 운영 데이터베이스에 접속을 열게 된다.
바꿀 것이 없으니 결과는 같지만, 아무 일도 하지 않기 위해 운영 DB의 문을 하루에도 몇 번씩 여는 구성은 사고의 여지만 늘린다.
마이그레이션 코드가 완성본 앱 디렉터리 아래에 있으므로 `paths`의 경로마다 `flashcard-advanced/` 접두사가 붙고, 실행 스텝도 `working-directory`로 그 디렉터리에 들어가서 돈다.
목록에 워크플로 파일 자신(`.github/workflows/migrate.yml`)이 들어 있는 것도 눈여겨보자.
이 워크플로를 고친 커밋에서는 고친 결과가 실제로 도는지 확인할 수 있어야 한다.

둘째, `${{ github.ref_name == 'release' && ... || ... }}`가 브랜치를 보고 접속할 DB를 정한다.
`github.ref_name`에는 이 실행을 깨운 브랜치 이름이 들어 있으므로, `release`면 운영 DB의 연결 문자열이, 그 밖의 브랜치(곧 `main`)면 개발 DB의 연결 문자열이 `MIGRATE_DATABASE_URL`에 담긴다.
{ch-git}에서 정한 브랜치 정책이 여기서 데이터베이스 선택으로 이어진다.
잡의 `name`에도 같은 표현식을 써서, 실행 목록에 "운영 DB 마이그레이션"인지 "dev DB 마이그레이션"인지가 드러나게 했다.
사람이 나중에 로그를 볼 때 가장 먼저 확인하고 싶은 것이 그것이기 때문이다.

셋째, `cancel-in-progress`가 `false`다.
{ch-github-actions}의 `ci.yml`에서는 추월당한 검사를 취소하는 것이 이득이었지만, 마이그레이션을 중간에 끊으면 데이터베이스가 어중간한 상태로 남는다(앞에서 본 dirty 플래그다).
검사는 언제든 다시 돌리면 그만이지만, 바꾸는 작업은 중단 자체가 사고다.
같은 이름의 설정이라도 워크플로의 성격에 따라 값이 뒤집힌다.

넷째, 시크릿이 비어 있으면 곧바로 실패시킨다.
등록되지 않은 시크릿을 참조하면 GitHub는 오류 대신 빈 문자열을 건네주므로, 이 검사가 없으면 워크플로는 "연결 문자열이 없다"는 뜻 모를 오류를 뱉거나 엉뚱한 곳에 접속을 시도한다.
빈 값을 이른 단계에서 명시적인 실패로 바꾸는 이 검사는, {ch-supabase-db}에서 본 서버의 기동 시점 설정 검사와 같은 발상이다.
오류 문구가 시크릿을 등록할 화면과 이름까지 안내하므로, 처음 설정하는 사람이 로그만 보고도 다음에 할 일을 안다.

접속 정보 두 벌은 앞 절에서 말한 저장소 시크릿 `DEV_MIGRATE_DATABASE_URL`과 `PROD_MIGRATE_DATABASE_URL`이고, 값은 각각 개발·운영 Supabase 프로젝트의 연결 문자열이다.
이 문자열이 왜 평소 API가 쓰는 것과 다른 포트여야 하는지는 앞의 direct 연결 절에서 봤다.

.[용어 풀이] 저장소 시크릿(Repository Secret)
[NOTE]
====
비밀번호나 접속 키처럼 코드에 적어 둘 수 없는 값을 GitHub에 따로 맡겨 두고, 워크플로가 돌 때만 꺼내 쓰게 하는 보관함이다.
저장소 설정 화면에서 이름과 값을 등록해 두면 워크플로 파일에서는 `secrets.이름`으로만 가리키므로, 값 자체는 저장소의 어느 파일에도 남지 않는다.
한 번 등록한 값은 다시 열어 볼 수 없고 덮어쓰기만 되며, 실행 로그에 찍히더라도 GitHub가 별표로 가려 준다.
값을 읽을 수 없다는 성질이 오히려 안전장치다.
유출이 의심되면 확인할 방법을 찾는 대신 새 값으로 덮어쓰면 된다.
====

DB 비밀번호가 든 문자열을 저장소가 아니라 GitHub의 보관함에 두는 이 구성 덕분에, 개발자의 노트북에는 운영 접속 정보가 없어도 된다.
{ch-env-secrets}에서 다시 이야기하겠지만, 값이 없는 곳에서는 그 값으로 저지르는 사고도 일어나지 않는다.

=== 왜 서버가 스스로 적용하지 않는가

여기서 의문이 하나 생긴다.
서버가 뜰 때 마이그레이션을 한 번 실행하게 만들면 워크플로도 시크릿도 필요 없지 않은가.
실제로 이 앱의 로컬 모드가 그렇게 하고 있다.
`litestore.Open`이 서버를 켤 때마다 `schema.sql`을 통째로 적용하므로, 로컬에서는 스키마를 따로 챙길 일이 없다.

상주 서버라면 이 방식이 좋은 선택지다.
프로세스가 하나뿐이고 배포할 때 한 번 뜨므로, 기동 절차의 첫머리에서 마이그레이션을 실행하고 실패하면 아예 뜨지 않게 하면 코드와 스키마가 늘 같은 시점에 맞춰진다.
컨테이너 하나로 도는 앱에서 흔히 쓰는 구성이고, 관리할 파이프라인도 보관할 시크릿도 하나 줄어든다.

서버리스에서는 그 전제가 네 가지로 어긋난다.

첫째, 연결 문자열이 맞지 않는다.
함수에 주입된 `DATABASE_URL`은 트랜잭션 풀러(6543)인데 권고 잠금은 그것을 잡은 세션이 유지되는 동안만 유효하므로, 이 연결로는 마이그레이션을 실행할 수 없다.
자동 적용을 하려면 5432 문자열을 함수의 환경 변수에도 넣어야 하는데, 그것은 스키마를 바꿀 수 있는 자격을 늘 켜져 있는 함수에 쥐여 주는 일이다.
지금은 그 자격이 GitHub 저장소 시크릿 안에만 있어서, 함수는 데이터를 읽고 쓸 수 있을 뿐 틀을 바꾸지는 못한다.

둘째, 실행 시점을 사용자가 정하게 된다.
서버리스 함수는 요청이 도착해야 뜨므로, 배포가 끝나도 첫 요청이 올 때까지 마이그레이션은 실행되지 않는다.
그 첫 요청을 보낸 사용자가 인덱스가 만들어지는 시간을 대신 기다리고, 함수의 실행 시간 상한인 300초({ch-free-tier})를 넘기면 응답 대신 오류를 받는다.
게다가 중간에 끊긴 마이그레이션은 dirty를 남기므로 그다음 요청들은 기동 자체에 실패한다.
스키마 변경이라는 관리 작업을 사용자 요청 처리 경로 안으로 들여놓는 순간, 실패의 대가를 사용자가 치르게 된다.

셋째, 인스턴스마다 시도한다.
동시 요청으로 함수 인스턴스가 여럿 뜨면 저마다 기동 절차에서 마이그레이션을 실행하려 든다.
권고 잠금이 이들을 한 줄로 세워 주므로 결과가 어긋나지는 않지만, 콜드스타트마다 5432 연결을 열고 잠금을 확인하는 비용이 모든 인스턴스에 붙는다.
바꿀 것이 하나도 없는 평상시에도 이 절차는 계속 돈다.

넷째, 배포 순서 문제가 해결되지 않는다.
새로 뜬 코드가 기동하며 스키마를 바꾸더라도 옛 코드가 도는 인스턴스는 그 순간에도 살아 있다.
다음 절의 확장 후 축소는 그대로 필요하고, 얻은 것은 워크플로 하나를 줄인 것뿐이다.

정리하면 기동 시 마이그레이션은 프로세스가 하나이고 수명이 긴 서버에서 성립하는 방식이다.
프로세스가 요청을 따라 생겼다 사라지고 그 연결이 트랜잭션 풀러를 거치는 이 앱에서는, 스키마를 바꾸는 일을 앱 바깥의 한 번뿐인 절차로 떼어 놓는 편이 맞다.
로컬 모드가 정반대로 하는 것은 조건이 정반대이기 때문이다.
데이터가 나 하나의 것이고, 프로세스가 하나이며, 어긋나면 파일을 지우고 다시 시작하면 그만이다.

=== 배포와 마이그레이션은 서로를 기다리지 않는다

자동화하고 나면 새로 생기는 문제가 하나 있다.
`main`에 push하는 순간 GitHub Actions의 마이그레이션과 Vercel의 배포가 동시에 출발하고, 둘 사이에는 아무 순서도 정해져 있지 않다.
마이그레이션이 먼저 끝나면 새 스키마 위에 옛 코드가 잠시 도는 것이고, 배포가 먼저 끝나면 옛 스키마 위에 새 코드가 잠시 도는 것이다.

앞의 경우는 대체로 무해하다.
칼럼 하나가 늘어난 테이블을 옛 코드가 모른 척하고 지나갈 뿐이다.
문제는 뒤의 경우다.
새 코드가 아직 없는 칼럼을 조회하면 그 요청은 오류로 끝난다.

해법은 스키마 변경을 파괴적이지 않은 단계로 나누는 것이고, 이 방식을 확장 후 축소(expand and contract)라고 부른다.

.[용어 풀이] 확장 후 축소(Expand and Contract)
[NOTE]
====
스키마를 고칠 때 "추가"와 "제거"를 한 배포에 함께 담지 않고 여러 배포로 나누는 방식이다.
먼저 새 칼럼을 더하기만 하고(확장), 옛 칼럼과 새 칼럼을 모두 채우는 코드를 배포한 뒤, 읽는 쪽을 새 칼럼으로 옮기고, 마지막 배포에서야 옛 칼럼을 지운다(축소).
집을 고칠 때 새 방을 먼저 지어 짐을 옮긴 다음 옛 방을 허무는 순서와 같아서, 어느 시점에 멈춰도 코드와 스키마가 함께 성립한다.
코드와 스키마가 동시에 바뀌지 않는 모든 배포에서 필요하며, 무중단 배포의 기본 문법이기도 하다.
====

칼럼 이름을 바꾼 000003을 이 잣대로 다시 보자.
`rename column front_text to text`는 옛 이름과 새 이름이 공존하는 순간이 없으므로, 배포와 마이그레이션 사이의 짧은 시차 동안 한쪽은 반드시 어긋난다.
확장 후 축소로 풀자면 새 칼럼 추가, 양쪽에 함께 쓰는 코드 배포, 데이터 복사, 읽기 전환, 옛 칼럼 제거로 나눠야 한다.
크게 보면 추가, 코드 전환, 제거의 세 단계이고, 가운데 코드 전환이 배포 여러 번으로 쪼개진다.

Flashcard는 사용자가 적고 이 시차가 GitHub Actions 잡 하나와 Vercel 빌드 하나가 끝나는 시간의 차이에 그치므로, 그 복잡도를 감수하는 대신 짧은 오류 가능성을 받아들였다.
다만 이것은 규모가 정해 준 선택이지 원칙이 아니므로, 사용자가 늘면 값비싼 변경부터 확장 후 축소로 옮겨 가는 것이 맞다.
`CLAUDE.md`에 "칼럼 삭제·이름 변경은 추가, 코드 전환, 제거의 세 단계로 나눈다"를 적어 둔 이유이기도 하다.

== 정리

첫째, 운영 스키마는 순서 있는 마이그레이션으로 고친다.
로컬 SQLite는 서버를 켤 때마다 완성형 `schema.sql`을 통째로 적용하면 그만이지만, 운영 DB는 사용자 데이터가 살아 있는 채로 틀을 바꿔야 하므로 golang-migrate의 버전 있는 up/down 파일 쌍으로 변경 이력을 쌓는다.
같은 파일을 같은 순서로 실행하면 어떤 환경이든 같은 스키마에 도달한다.

둘째, 지금 상태는 `schema_migrations`의 한 줄이 말해 준다.
적용이 실패하면 dirty 플래그가 참으로 남아 다음 실행을 막아 세우고, 자동 복구 대신 사람의 확인을 요구한다.
권고 잠금은 그것을 잡은 세션이 끊기면 풀리므로, 마이그레이션만은 트랜잭션 풀러가 아니라 세션이 유지되는 5432 연결로 붙는다.

셋째, 적용의 주체는 사람이 아니라 브랜치다.
`main` 푸시는 개발 DB에, `release` 병합은 운영 DB에 `migrate.yml`이 적용하고, 운영 연결 문자열은 저장소 시크릿 안에만 있다.
서버가 기동하며 스스로 적용하는 방식은 프로세스가 하나뿐인 상주 서버의 것이다.
요청을 따라 떴다 사라지는 함수에는 스키마를 바꿀 자격을 아예 주지 않는다.

넷째, 배포와 마이그레이션은 서로를 기다리지 않는다.
그 시차를 견디는 문법이 확장 후 축소이고, 칼럼 삭제와 이름 변경은 추가·전환·제거의 단계로 나눠야 어느 시점에 멈춰도 코드와 스키마가 함께 성립한다.

저장소와 품질 게이트에서 시작해 배포, 인증, 운영 데이터베이스와 그 스키마를 고치는 절차까지 왔다.
4부에 남은 것은 하나다.
다음 {ch-env-secrets}에서는 이 장에서도 두 벌로 늘어난 값, 곧 환경 변수와 시크릿을 다룬다.
같은 이름의 값이 개발과 운영에서 서로 다른 내용을 담을 때, 그 값들을 어디에 두고 어떻게 관리하는지가 그 내용이고, 그것까지 갖춰지면 {ch-deploy}를 펴고 배포를 완주할 준비가 끝난다.
