= Vercel: 왜 이 플랫폼이고, 무엇이 배포되는가

{ch-quality-gates}까지 코드가 검사를 통과하게 만들었다.
이 장부터는 그 코드가 내 컴퓨터를 벗어나 누구나 접속할 수 있는 인터넷 주소에 올라간다.

이 장이 답할 질문은 둘이다.
왜 상주 서버가 아니라 서버리스(serverless)이고, 그중에서도 왜 Vercel인가.
그리고 화면(HTML 페이지)과 정적 자산, JSON API를 모두 내주는 Go 앱이 어떻게 함수 하나로 배포되는가.
그 함수를 세우는 설정과 플랫폼 제약은 다음 {ch-vercel-config}의 몫이다.

== 왜 Vercel인가

=== 요구사항에서 출발하기

배포 플랫폼을 고를 때 잣대로 삼은 것은 세 가지다.

첫째, 완전 무료여야 한다({ch-requirements}의 비기능 요구사항).
개인용 암기 앱의 트래픽은 거의 늘지 않는다.

둘째, 관리할 플랫폼이 최소여야 한다.
플랫폼이 두 개면 계정·환경 변수·배포 파이프라인을 챙길 곳도, 장애 때 확인할 곳도, 무료 정책 변경을 지켜볼 곳도 두 개다.

셋째, 콜드스타트(Cold Start)가 최소여야 한다.
암기 앱은 하루에 몇 번 짧게 쓰는 앱이라, 접속할 때마다 첫 응답이 수 초씩 걸리면 "잠깐 복습하려던" 사용자는 앱을 닫는다.

.[용어 풀이] 콜드스타트(Cold Start)
[NOTE]
====
잠들어 있던 서버리스 함수가 첫 요청에 깨어나 준비를 마칠 때까지 걸리는 지연이다.
한동안 덮어 둔 노트북을 열 때 뜸을 들이는 것과 비슷하다.
기동이 빠른 언어를 고르면 줄지만({ch-tech-choices}), 지연의 크기는 플랫폼이 함수를 얼마나 자주 재우느냐에 더 크게 좌우된다.
====

이 세 요구사항은 서로 긴장 관계에 있다.
무료이면서 콜드스타트가 없으려면 상주 서버가 좋은데, 무료 상주 서버에는 대개 관리 부담과 슬립(sleep, 한동안 요청이 없으면 서버를 재워 두는 정책) 문제가 따라붙는다.

=== 첫 번째 안: 무료 상주 서버에 Go를 올리기

처음 검토한 안은 Flashcard의 Go 서버를 Koyeb 같은 무료 상주 서버(always-on server) 플랫폼에 통째로 올리는 것이었다.
서버가 늘 떠 있으니 콜드스타트가 없고, `cmd/server`를 그대로 올리면 되니 로컬과 프로덕션의 실행 형태도 같다.
데이터베이스 커넥션 풀(데이터베이스로 가는 연결을 미리 열어 두고 돌려쓰는 묶음, {ch-supabase-db})과 인메모리 캐시도 프로세스 수명 내내 유지할 수 있다.

그런데 따져 볼수록 감점 요소가 쌓였다.

첫째, 무료 티어의 지속성이 불안하다.
무료 상주 서버 플랫폼들은 한동안 요청이 없는 무료 인스턴스(instance)를 재우는 슬립을 도입하거나 무료 범위를 축소하는 쪽으로 바뀌곤 했다.
슬립에 들어간 인스턴스는 깨우는 데 수 초에서 수십 초가 걸려, 상주 서버의 최대 장점인 "콜드스타트 없음"이 사라진다.

.[용어 풀이] 인스턴스(Instance)
[NOTE]
====
요청을 처리하려고 실제로 켜져서 돌아가는 앱 한 벌이다.
코드는 한 벌이어도 인스턴스는 여럿일 수 있고, 서버리스에서는 플랫폼이 트래픽을 보고 알아서 켜고 끄므로 앱이 그 수를 통제하지 못한다.
그래서 인스턴스 하나의 메모리에 담아 둔 것은 언제 사라져도 이상하지 않은 값으로 다뤄야 한다.
====

실제 이력도 그렇다.
2026년 7월에 다시 조사해 보니, Fly.io는 2024년에 무료 티어를 폐지해 신규 가입자에게는 짧은 체험 뒤 카드를 등록하는 종량제만 남았다.
Koyeb는 2026년 2월 Mistral AI에 인수된 뒤 신규 사용자가 무료 티어에 가입할 수 없게 되었고, 진입 플랜이 월 29달러부터다.
Render는 카드 등록 없이 배포할 수 있지만, 무료 웹 서비스는 15분 미사용 시 잠들고 무료 PostgreSQL은 생성 30일 뒤 만료된다(처음 90일이던 기한을 2024년에 30일로 줄였다).
"카드 등록 없이 계속 무료"라는 조건을 들이대면 후보가 이렇게 빠르게 사라진다.

둘째, 배포가 내 숙제가 된다.
상주 서버에 앱을 올리는 흔한 방식은 컨테이너(container)다.
Dockerfile을 쓰고, 베이스 이미지의 보안 업데이트를 따라가고, push할 때마다 이미지를 새로 빌드해 올리는 배포 파이프라인도 직접 꾸려야 한다.

.[용어 풀이] 컨테이너(Container)와 Dockerfile
[NOTE]
====
앱 코드와 그 앱을 실행할 환경(운영체제 라이브러리, 런타임, 설정)까지 상자 하나에 담아 통째로 옮기는 배포 방식이 컨테이너다.
그 상자에 무엇을 담을지 적은 설계도 파일이 Dockerfile이고, 상자의 바탕인 베이스 이미지는 보안 취약점이 발견되면 새 버전이 나온다.
서버리스 함수는 코드만 올리면 실행 환경을 플랫폼이 맞춰 주므로 이 상자가 필요 없다.
====

이 감점 요소들을 보다가 질문이 바뀌었다.
"어느 무료 상주 서버가 제일 나은가"가 아니라 "상시 떠 있는 프로세스 없이 이 앱을 돌릴 수는 없나"가 진짜 질문이었다.
요청이 올 때만 코드가 깨어나는 서버리스라면 슬립 정책과 숨바꼭질할 일이 없고, 빌드와 배포도 플랫폼이 대신한다.
Vercel의 서버리스 함수(Serverless Function)가 Go를 지원한다는 사실이 그 답이 됐다.

=== 상주 서버와 서버리스: 일반 트레이드오프

첫째, 콜드스타트.
상주 서버는 프로세스가 늘 떠 있으므로(슬립하지 않는다면) 콜드스타트가 없다.
서버리스는 요청이 뜸하면 인스턴스가 회수되고, 다음 요청은 런타임 기동부터 다시 시작한다.
Go처럼 단일 바이너리로 컴파일되는 언어는 기동이 수십 밀리초에 머물지만, JIT 컴파일러를 데워야 하는 JVM은 웹 프레임워크 하나만 얹어도 초 단위로 늘어난다.
{ch-tech-choices}에서 Go를 고른 이유 중 하나다.

둘째, 상태(state).
상주 서버는 프로세스 메모리에 캐시, 세션, 커넥션 풀을 안심하고 둘 수 있다.
서버리스에서는 인스턴스가 언제 사라질지 모르므로 메모리는 "있으면 좋은 캐시" 이상으로 신뢰할 수 없다.
방금 요청을 처리하고 아직 켜져 있는 따뜻한(warm) 인스턴스가 재사용되는 동안에는 전역 변수의 값이 살아 있지만, 그것은 최적화이지 보장이 아니다.

디스크도 마찬가지다.
함수에 딸린 디스크는 인스턴스와 함께 사라지고, 인스턴스가 여러 개 뜨면 각자 자기 디스크를 본다.
3부 내내 데이터를 담아 온 `flashcard.db` 파일 하나가 여기서 성립하지 않는 이유다.
그 파일을 함께 올려도 사용자가 만든 덱은 인스턴스가 꺼질 때 지워지고, 두 사람이 동시에 접속하면 서로 다른 데이터를 보게 된다.
그래서 배포된 앱의 데이터는 함수 바깥의 데이터베이스에 있어야 하고, 그 자리를 {ch-supabase-db}에서 PostgreSQL로 채운다.

셋째, 비용 모델.
상주 서버는 트래픽이 0이어도 인스턴스 비용이 나간다(무료 티어라면 무료 한도를 소모한다).
서버리스는 실행한 만큼만 과금되므로 트래픽이 적은 개인 앱에서는 0원에 수렴한다.
반대로 트래픽이 꾸준히 많다면 어느 수준을 넘어서면서 상주 서버 쪽이 더 싸진다.

넷째, 실행 시간 제한.
서버리스 함수에는 요청당 실행 시간 제한이 있다(Vercel의 무료 플랜은 요청당 300초다. {ch-free-tier}).
오래 걸리는 배치 작업, 웹소켓(WebSocket)처럼 연결을 오래 붙드는 통신, 요청과 상관없이 뒤에서 계속 도는 백그라운드 작업은 서버리스에 얹기 어렵다.

.[용어 풀이] 웹소켓(WebSocket)
[NOTE]
====
브라우저와 서버가 연결을 한 번 맺어 두고, 그 통로로 양쪽이 아무 때나 메시지를 주고받는 통신 방식이다.
요청 한 번에 응답 한 번으로 끝나는 보통의 HTTP와 달리 전화를 걸어 놓고 통화를 이어 가는 쪽에 가깝고, 채팅이나 실시간 협업에 쓴다.
연결을 오래 붙들고 있는 것이 전제라, 실행 시간에 제한이 걸린 함수 위에서는 성립하기 어렵다.
====

Flashcard는 이 네 가지 모두에서 서버리스 친화적이다.
요청은 전부 짧게 끝나고, 오래 붙드는 연결이 없고, 상태는 모두 PostgreSQL에 있고, 트래픽은 적다.
콜드스타트라는 약점은 Go의 빠른 기동으로 상쇄한다.
실시간 동기화(웹소켓)나 오래 걸리는 배치가 있었다면 결론은 달라졌을 것이다.

=== 대안 비교: 어디에 무엇을 올릴 수 있나

같은 "Go 앱 하나를 무료로" 구도에서 검토한 플랫폼들을 비교하기 전에, 표에 나오는 엣지(edge)라는 말부터 짚어 둔다.

.[용어 풀이] 엣지(Edge)
[NOTE]
====
사용자와 가까운 각지에 흩어 놓은 서버들을 엣지라 부른다.
파일의 복사본을 이 서버들에 미리 뿌려 두는 것이 CDN이고, 코드까지 그 자리에서 돌려 응답을 만들어 내는 것이 엣지 실행이다.
첫 응답이 빠른 대신, 엣지에서 돌릴 수 있는 코드의 언어와 실행 환경에는 제약이 따른다.
====

|===
| 플랫폼 | 실행 모델 | Go 지원 | 평가

| Vercel | 서버리스 함수 + 글로벌 CDN | 함수 런타임으로 공식 지원 | 함수 하나로 앱 전체 서빙, git push 배포까지 완결
| Netlify | 서버리스 함수 + CDN | Go 함수는 종료 예정인 옛 모드로만 작성 가능 | 정적 호스팅·DNS·프록시로는 최상, 서버 런타임으로는 부적합
| Cloudflare Pages/Workers | 엣지 실행 | 네이티브 Go 불가(Workers는 JS/WASM 실행 모델) | Go를 WASM으로 컴파일하는 우회는 제약이 많음
| GitHub Pages | 정적 전용 | 불가 | 서버 코드가 없는 순수 정적 사이트라면 가장 단순한 선택
| Koyeb/Fly.io 등 무료 상주 서버 | 상주 프로세스 | 컨테이너/바이너리로 자유롭게 실행 | 콜드스타트 없음, 대신 슬립·정책 변경·컨테이너 관리 부담
|===

Netlify는 정적 사이트에 작은 함수 몇 개를 곁들이는 구도라면 Vercel과 대등하다.
다만 Netlify Functions에서 Go는 AWS Lambda 호환 모드로만 작성할 수 있는데, 이 모드는 폐기 예정으로 표시되어 있고 2027년 7월 1일부터는 그 모드로 만든 함수가 포함된 배포가 거부된다.footnote:[https://docs.netlify.com/build/functions/overview/[Netlify Functions 문서]가 안내하는 이주 경로는 자바스크립트 전용 패키지라, Go에는 옮겨 갈 곳이 없다.]
대신 도메인과 TLS 인증서, 다른 곳에 올린 백엔드로 요청을 넘기는 프록시 용도로는 무료 플랜이 여전히 좋은 선택이다({ch-alternatives}).

Cloudflare Pages/Workers는 전 세계 엣지에서 실행되는 모델이 강점이라, 지연에 민감한 전 세계 대상 서비스라면 유력하다.
그러나 Workers는 V8(크롬의 자바스크립트 엔진) 기반 JavaScript/WASM(웹어셈블리) 실행 모델이라 Go를 네이티브로 돌릴 수 없다.
Go를 WASM으로 컴파일하면 표준 라이브러리의 `net` 패키지가 실제 TCP 연결을 열지 못하는 시험용 가짜 네트워크로 바뀐다footnote:[Go 저장소의 `src/net/net_fake.go` 머리 주석이 이 구현을 js/wasm과 wasip1/wasm을 위한 가짜 네트워크이며 다른 패키지의 테스트를 통과시키려는 용도라고 밝힌다. https://github.com/golang/go/blob/master/src/net/net_fake.go[net_fake.go]].
그래서 PostgreSQL에 TCP로 붙는 pgx 드라이버가 동작하지 않는다.
서버 코드를 TypeScript로 쓸 계획이라면 이야기가 다르다.

GitHub Pages는 서버 코드가 없는 순수 정적 사이트라면 가장 단순한 답이지만, 서버가 HTML을 렌더링하고 인증과 데이터베이스가 필요한 Flashcard는 처음부터 후보가 아니었다.

웹소켓·백그라운드 작업·긴 요청이 필요하거나 콜드스타트를 한 번도 용납할 수 없는 서비스라면 무료 상주 서버가 여전히 옳은 선택이다.
이 앱을 상주 서버로 옮기면 무엇이 번거로워지고 무엇이 편해지는지는 {ch-alternatives}에 정리해 두었다.
배포처를 바꾸면 {ch-supabase-auth}의 로그인 설정도 함께 고쳐야 하므로, 그 비교는 인증까지 읽은 뒤라야 온전해진다.

Vercel 선택의 결정타는 특정 기능이 아니라 구도다.
페이지·정적 자산·API를 서빙하는 Go 앱 하나를 한 저장소, 한 플랫폼, 한 번의 `git push`로 배포할 수 있고, 콜드스타트는 Go로 최소화한다.

== 무료 티어는 어디까지 버티는가

Vercel의 무료 요금제인 Hobby 플랜은 결제 수단을 등록하지 않아도 쓸 수 있다.
정적 호스팅과 글로벌 CDN, Go를 포함한 서버리스 함수 런타임, 자동 HTTPS, 커스텀 도메인(내가 산 주소를 앱에 붙이는 것), GitHub 연동 자동 배포가 모두 들어 있다.
이 가운데 Flashcard가 실제로 쓰는 것은 Go 함수 런타임, 자동 HTTPS, GitHub 연동 자동 배포 셋이다.
정적 호스팅을 쓰지 않는 이유는 아래 "배포의 단위" 절에서 밝힌다.

.[용어 풀이] HTTPS(HyperText Transfer Protocol Secure)
[NOTE]
====
브라우저와 서버가 주고받는 내용을 암호로 감싸서, 중간에서 누가 들여다보거나 바꿔치기하지 못하게 하는 통신 방식이다.
서버는 자신이 그 주소의 주인임을 증명하는 인증서(certificate)를 갖춰야 하고, 이 인증서는 만료 전에 다시 발급받아야 한다.
자동 HTTPS는 이 발급과 갱신을 플랫폼이 대신한다는 뜻이다.
====

구체적인 한도 수치와 초과 시 벌어지는 일, Hobby 플랜을 개인·비상업 용도로 제한하는 약관은 Supabase 쪽 한도와 함께 {ch-free-tier}에서 다룬다.
Flashcard의 실사용량은 Vercel의 어떤 한도 근처에도 가지 않는다.

== 배포의 단위: Go 함수 하나가 앱 전체다

Vercel의 출발점은 파일 묶음을 CDN에 올려 서빙하고 동적인 부분만 함수로 채우는 정적 호스팅이지만, Flashcard에는 미리 만들어 둘 HTML이 없다.
페이지는 요청마다 Go 서버가 렌더링하고({ch-html-template}), CSS와 아이콘 같은 정적 자산도 embed로 Go 바이너리 안에 들어 있다.
그래서 이 앱의 배포 단위는 서버리스 함수 하나이고, 그 함수가 HTML 페이지·정적 자산·JSON API를 전부 서빙한다.
코드가 배포되어 요청을 받기까지를 그리면 그림 22처럼 된다.

.[용어 풀이] CDN(Content Delivery Network)
[NOTE]
====
전 세계 곳곳의 서버에 같은 파일의 복사본을 미리 뿌려 두고, 방문자에게 가장 가까운 서버가 응답하게 하는 배달망이다.
서울에서 접속하면 서울 근처 서버가 같은 파일을 건네므로 어디서 열어도 빠르다.
====

배포 트리거는 GitHub 저장소 연동이다.
Vercel 프로젝트에 저장소를 연결해 두면 브랜치에 push할 때마다 자동으로 빌드와 배포가 실행되고, 끝나면 `<프로젝트 이름>.vercel.app` 형태의 주소가 생긴다.
{ch-first-run}의 `localhost`가 내 컴퓨터 안에서만 통하는 주소였다면, 이 주소는 누구나 열 수 있는 인터넷 주소다.
Vercel은 Next.js 같은 프런트엔드 프레임워크를 감지해 빌드 절차를 잡아 주는데, 이 저장소에는 감지할 프레임워크가 없다.
그래서 `vercel.json`에 프레임워크 없음을 명시해 두었고({ch-vercel-config}), 빌드랄 것은 Go 함수 컴파일뿐이다.
어느 브랜치에 push해야 운영에 반영되는지도 {ch-vercel-config}에서 정한다.

.[용어 풀이] 빌드와 배포
[NOTE]
====
빌드(build)는 사람이 쓴 소스 코드를 기계가 돌릴 수 있는 형태로 변환·조립하는 과정이고, 배포(deploy)는 그 결과물을 사용자가 접속하는 서버에 올려 서비스되게 하는 과정이다.
원고를 인쇄용 파일로 짜는 일이 빌드라면, 그 책을 서점 매대에 올리는 일이 배포다.
Vercel은 이 두 단계를 push 한 번에 이어서 실행한다.
====

=== Vercel Go 런타임의 동작 방식

Vercel의 함수 배포 규약은 파일 시스템 기반이다.
저장소의 `api/` 디렉터리에 놓인 파일이 각각 하나의 서버리스 함수가 되고, `.go` 파일은 Go 런타임으로 컴파일된다.
파일에 요구하는 것은 함수 하나의 모양뿐이다.
요청을 담은 자리(`r`)와 응답을 써 넣는 자리(`w`)를 인자로 받는 표준 `net/http` 모양의 함수를 대문자 이름으로 내보내면(export) 된다.

[source,go]
----
func Handler(w http.ResponseWriter, r *http.Request)
----

이 규약대로라면 `api/decks.go`, `api/cards.go`처럼 엔드포인트마다 함수를 쪼갤 수도 있다.
Flashcard는 반대로 함수를 딱 하나만 만들고, 그 안에서 Gin 라우터가 모든 경로를 처리하게 했다.
이유는 셋이다.

첫째, 코드 재사용이다.
{ch-app-assembly}에서 만든 Gin 라우터(`pkg/app`)를 그대로 쓰면 로컬 서버와 프로덕션이 같은 코드로 동작한다.
함수를 쪼개면 라우팅·미들웨어·인증을 Vercel의 파일 규약에 맞춰 다시 조립해야 한다.

둘째, 콜드스타트를 맞는 횟수다.
함수가 열 개면 사용자가 화면을 옮길 때마다 다른 함수의 콜드스타트를 맞을 수 있다.
함수가 하나면 첫 요청 한 번으로 앱 전체가 따뜻해진다.

셋째, 환경 변수, 로그, 리전 설정을 함수 하나에만 적용하면 된다.

대가도 있다.
모든 엔드포인트가 한 함수의 메모리·실행 시간 제한을 공유하고, 특정 엔드포인트만 따로 늘리거나 다른 리전에 둘 수 없다.
이미지 변환처럼 무거운 엔드포인트가 짧은 조회와 섞인 서비스라면 함수를 나누는 쪽이 낫다.
모든 엔드포인트가 짧은 CRUD뿐인 이 앱에서는 나눠서 얻는 것이 없다.

.[용어 풀이] CRUD(Create·Read·Update·Delete)
[NOTE]
====
데이터를 만들고(Create), 읽고(Read), 고치고(Update), 지우는(Delete) 네 가지 기본 조작의 머리글자다.
덱을 만들고, 카드 목록을 열어 보고, 뜻을 고치고, 카드를 지우는 일이 전부 여기에 든다.
"단순 CRUD"라고 하면 복잡한 계산이나 오래 걸리는 작업 없이 데이터를 넣고 빼는 수준이라는 뜻이다.
====

=== 캐치올 함수: api/index.go

.[용어 풀이] 캐치올(Catch-all)
[NOTE]
====
정해진 몇몇 주소만 따로 받는 대신, 특정 범위의 모든 주소를 하나가 통째로 받아 처리하게 만든 것이다.
대표번호 하나로 걸려 온 전화를 안에서 담당자에게 연결하는 것과 같다.
여기서는 모든 요청을 함수 하나가 받아, 그 안의 Gin 라우터가 경로별로 나눈다.
====

단일 함수의 실체는 들어온 요청을 Gin 라우터에 그대로 넘겨주는 짧은 연결 코드다(`api/index.go` 발췌).

[source,go]
----
// Vercel은 이 파일을 모듈 바깥에서 컴파일하므로 internal/ 패키지를 (직접)
// import할 수 없다. 필요한 공용 코드는 pkg/에 둔다.
package handler

import (
	"net/http"

	"github.com/benelog/flashcard/pkg/app"
)

func Handler(w http.ResponseWriter, r *http.Request) {
	engine, err := app.Engine()
	if err != nil {
		http.Error(w, "server misconfigured: "+err.Error(), http.StatusInternalServerError)
		return
	}
	engine.ServeHTTP(w, r)
}
----

핵심은 마지막 한 줄, `engine.ServeHTTP(w, r)`다.
Gin의 `*gin.Engine`은 표준 `http.Handler` 인터페이스를 구현하므로({ch-app-assembly}), Vercel이 요구하는 핸들러 안에서 요청을 그대로 넘기면 이후의 경로 매칭·미들웨어·핸들러 실행은 전부 Gin이 한다.
Vercel 함수는 Vercel의 호출 규약과 Gin 앱 사이를 잇는 얇은 어댑터(규격이 다른 두 쪽을 연결하는 변환 플러그 같은 코드)일 뿐이다.

`app.Engine()`이 반환하는 엔진은 `pkg/app/app.go`에서 조립된다.
아래 코드의 `sync.Once`는 엔진을 프로세스에서 딱 한 번만 조립하고, 그 뒤로는 만들어 둔 것을 재사용하게 하는 장치다.

`pkg/app/app.go` (조립 코드 일부):

[source,go]
----
var (
	engine     *gin.Engine
	engineOnce sync.Once
	engineErr  error
)

// Engine은 프로세스 전역 라우터를 돌려준다. 서버리스 인스턴스가 따뜻할 때는
// 재사용된다.
func Engine() (*gin.Engine, error) {
	engineOnce.Do(func() {
		engine, engineErr = build()
	})
	return engine, engineErr
}
----

`build()`는 환경 변수 읽기, 데이터베이스 커넥션 풀 생성, 라우터·미들웨어 조립을 수행한다.
셋 다 메모리 안에서 끝나고(풀 생성은 설정만 잡을 뿐 연결을 열지 않는다), 비용이 드는 첫 데이터베이스 연결과 토큰 검증용 열쇠 묶음(JWKS) 조회는 처음 쓰는 요청에서 일어난다({ch-vercel-config}의 "콜드스타트" 절).
따뜻한 인스턴스에서는 두 번째 요청부터 만들어 둔 엔진과 커넥션 풀을 그대로 쓴다.
인스턴스가 회수되면 다음 콜드스타트에서 다시 초기화될 뿐, 상태의 원본은 전부 PostgreSQL에 있으므로 데이터가 어긋나지 않는다.

로컬 개발 서버(`cmd/server/main.go`)도 PostgreSQL 모드에서는 같은 `app.Engine()`을 부른다({ch-app-assembly}).
로컬은 `engine.Run()`으로 포트를 열어 상주 서버처럼 돌고, Vercel은 `engine.ServeHTTP()`로 요청 단위로 실행한다.
실행 모델은 달라도 라우팅·인증·비즈니스 로직이 같으므로, "로컬에서 되는데 프로덕션에서 안 되는" 차이가 구조적으로 줄어든다.

=== rewrite로 모든 경로를 한 함수로

Vercel의 파일 규약대로라면 `api/index.go`는 `/api/index` 경로만 담당한다.
홈 화면 `/`도, 페이지 `/decks/ab3f`도, JSON API `/api/me`도 이 함수로 보내려면 `vercel.json`의 리라이트(rewrite) 규칙 하나가 필요하다.

.[용어 풀이] 리라이트(Rewrite)
[NOTE]
====
겉으로 보이는 주소와 실제로 그 요청을 처리하는 위치를 다르게 이어 주는 서버 속 안내판이다.
방문자는 `/decks/ab3f`로 문을 두드렸다고 여기지만, 서버는 뒤에서 `/api/index` 창구로 안내한다.
주소를 바꿔 다시 요청하게 만드는 리다이렉트와 달리, 브라우저 주소창은 그대로 두고 처리할 곳만 바꾼다.
====

[source,json]
----
{ "source": "/(.*)", "destination": "/api/index" }
----

`/(.*)`는 경로가 무엇이든 들어맞는 패턴이다.
rewrite는 요청 URL을 바꾸지 않으므로 함수에 도착한 `*http.Request`의 경로는 여전히 `/decks/ab3f`다.
그래서 Gin에 등록된 페이지 라우트(`internal/web`의 `GET /decks/:slug` 등)와 JSON 라우트(`api.GET("/decks/:slug", h.GetDeck)` 등)가 변환 없이 매칭된다.
어떤 라우트에도 걸리지 않는 경로는 Gin의 `NoRoute` 핸들러가 받아 404 페이지를 렌더링하므로, 존재하지 않는 페이지까지 앱이 책임진다.

== 정적 자산: CDN이 아니라 함수가 서빙한다

이 구조에는 정적 자산의 서빙 경로라는 트레이드오프가 있다.
통상 CSS·자바스크립트·아이콘 같은 정적 파일은 CDN에 올려, 콜드스타트도 함수 실행 비용도 없이 엣지에서 바로 내보낸다.
Flashcard는 모든 경로를 함수로 보내므로 `app.css` 한 장을 받는 데도 Go 함수가 실행된다.
그 대신 배포 단위가 함수 하나로 끝나고, 앱과 자산이 한 바이너리에 들어 있어 버전이 어긋날 일이 없으며, 어떤 파일을 어디에 올릴지 관리할 목록도 없다.
페이지마다 불러오는 정적 자산은 셋(`app.css`, `htmx.min.js`, `app.js`)이고, 아래의 캐시 헤더 덕에 한 번 받으면 브라우저가 계속 재사용한다.
트래픽이 많은 서비스라면 정적 자산만이라도 CDN에 두는 쪽이 맞다.

아래 코드는 embed된 정적 자산을 라우트로 등록하면서, 응답마다 캐시 지시를 붙이는 부분이다.

`internal/web/routes.go` (registerStatic 발췌):

[source,go]
----
// registerStatic은 embed된 자산을 내준다. 파일 이름에 해시가 없으므로 템플릿이
// ?v=<assetVersion>을 찍은 URL만 immutable로 두고, 맨 URL에는 짧은 TTL을 준다.
// 서비스 워커가 그 위에 stale-while-revalidate를 얹는다.
func (w *Web) registerStatic(r *gin.Engine) {
	static, err := fs.Sub(staticFS, "static")
	if err != nil {
		panic(err)
	}
	server := http.FileServer(http.FS(static))
	// ...
	r.GET("/static/*filepath", func(c *gin.Context) {
		if c.Query("v") == assetVersion() {
			c.Header("Cache-Control", "public, max-age=31536000, immutable")
		} else {
			c.Header("Cache-Control", "public, max-age=3600")
		}
		c.Request.URL.Path = "/" + strings.TrimPrefix(c.Param("filepath"), "/")
		server.ServeHTTP(c.Writer, c.Request)
	})
	// ...
}
----

`Cache-Control`의 `max-age`는 브라우저에 이 응답을 몇 초 동안 다시 묻지 말고 재사용하라는 지시다.
`3600`이면 한 시간, `31536000`이면 1년이고, `immutable`까지 붙으면 새로고침을 해도 다시 묻지 않는다.

어느 쪽을 줄지는 지문(fingerprint)이 있는지로 정한다.
지문은 파일 내용을 짧게 요약한 해시(hash)라서, 내용이 조금이라도 바뀌면 값도 바뀐다.
이 앱의 파일 이름은 `app.css`처럼 고정이라, 템플릿이 자산 주소 끝에 내용 해시를 `?v=`로 붙여 주고 그 지문이 맞는 요청에만 1년짜리 `immutable`을 준다.
배포로 내용이 바뀌면 지문도 바뀌어 주소가 달라지므로, 사용자 한 명당 그때 한 번만 함수까지 요청이 온다.
한 시간짜리 지시는 누군가 지문 없이 맨 주소(`/static/app.css`)를 직접 부를 때를 위한 안전망이다.
지문을 만드는 코드와 이 장치가 없을 때 나는 사고, 그 위에 캐시를 한 겹 더 얹는 서비스 워커는 {ch-caching}에서 다룬다.

== 에이전트 활용 아이디어

* `AGENTS.md`에 "`api/index.go`는 internal/을 import할 수 없다. 공유 코드는 `pkg/app`에 둔다"를 적는다. 같은 규칙을 `./check.sh`의 `go build api/index.go`가 기계적으로 검사하므로({ch-quality-gates}), 지침과 자동 검사가 이중으로 지킨다.
* 정적 자산을 늘릴 때는 "새 아이콘 파일을 추가하고 `{{asset}}` 헬퍼로 참조해 달라"처럼 저장소의 관례를 참조점으로 준다. 해시 없는 파일명이 캐시에 눌러앉는 사고를 피할 수 있다.

== 정리

무료·단일 플랫폼·최소 콜드스타트라는 세 요구사항에서 출발해, 무료 상주 서버 안을 "상시 떠 있는 프로세스 없이 돌릴 수 없나"라는 질문으로 뒤집고 Go 서버리스 함수를 공식 지원하는 Vercel로 수렴했다.
웹소켓이나 장시간 작업이 필요하거나 콜드스타트를 한 번도 허용할 수 없다면 결론은 달라진다.

배포되는 것은 함수 하나다.
`api/index.go`가 Gin 엔진 전체를 감싸는 캐치올 함수가 되어 HTML 페이지·정적 자산·JSON API를 전부 서빙하고, 정적 자산까지 함수가 내주는 대가는 `Cache-Control` 캐시 헤더로 줄였다.

다음 {ch-vercel-config}에서는 이 함수를 세우는 `vercel.json`의 각 항목, 개발 배포와 운영 배포의 구분, 콜드스타트의 비용이 어디서 생기는지를 다룬다.
