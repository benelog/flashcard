= Vercel 설정과 제약: vercel.json, 콜드스타트, 배포 절차

{ch-vercel}에서 Gin 엔진을 통째로 감싼 Go 함수 하나가 앱 전부라고 정했다.
남은 것은 그 함수를 실제로 세우는 일이다.
Vercel의 Go 런타임은 함수 파일을 모듈 바깥에서 단독으로 컴파일하고, 요청이 없으면 함수를 재워 두며, 어느 브랜치의 push를 운영에 반영할지도 미리 정해 두어야 한다.

이 장은 런타임의 제약이 저장소의 디렉터리 구조까지 바꾼 이야기에서 시작해 `vercel.json`의 각 항목을 읽는다.
이어서 {ch-git}의 main·release 정책이 개발 배포와 운영 배포로 나뉘는 방식, 콜드스타트의 비용, 배포 절차 전체를 구성 요소 관점에서 정리한다.

== Vercel Go 함수의 제약과 대응

=== internal 패키지를 import할 수 없다

{ch-vercel}에서 본 `api/index.go` 상단 주석은 우회해야 했던 제약의 흔적이다.

[source,go]
----
// Vercel은 이 파일을 모듈 바깥에서 컴파일하므로 internal/ 패키지를 (직접)
// import할 수 없다. 필요한 공용 코드는 pkg/에 둔다.
----

플랫폼의 컴파일 방식 탓에 이 진입점 파일이 앱 안쪽에 감춰 둔 코드를 직접 가져다 쓸 수 없다는 뜻이다.
{ch-code-map}에서 다뤘듯 Go에는 `internal` 디렉터리 관례가 있다.
`internal/` 아래의 패키지는 `internal`을 품은 바로 위 디렉터리와 그 하위의 코드에서만 import할 수 있고, 바깥에서 import하면 컴파일러가 거부한다.
이 저장소라면 `flashcard-advanced/` 안의 코드만 `internal/`을 쓸 수 있고, Flashcard는 설정(`internal/config`), 데이터 접근(`internal/pgstore`), 핸들러(`internal/handlers`)를 비롯한 내부 구현 전부를 `internal/`에 두었다.

문제는 Vercel이 `api/index.go`를 저장소 모듈의 일원이 아니라 모듈 외부에서 단독 컴파일한다는 점이다.
그래서 `api/index.go`가 `internal/` 패키지를 직접 import하면 Vercel 배포가 컴파일 에러로 실패한다.

대응은 엔진 조립 코드를 `internal/app`이 아니라 `pkg/app`에 두는 것이었다.
`pkg/`는 "외부에서 import해도 되는 공개 패키지"를 두는 관례적 위치라, 모듈 밖에서 컴파일되는 코드도 자유롭게 import할 수 있다.
누가 누구의 코드를 가져다 쓰는지 화살표로 그린 import 그래프는 그림 23처럼 된다.

`api/index.go`가 직접 만나는 패키지는 `pkg/app` 하나뿐이고, 모듈에 속한 `pkg/app`은 `internal/` 패키지들을 마음껏 import할 수 있다.
`internal`의 보호는 그대로 두고 모듈 바깥의 진입점에는 공개 창구 하나만 열어 준 것이고, 주석의 "(직접)"이라는 단서가 이 구도를 가리킨다.

=== 로컬 빌드로는 잡히지 않는 실패: 별도 검사의 필요

이 제약은 평소의 빌드 검사로는 위반이 잡히지 않는다.
`go build ./...`는 모든 패키지를 모듈의 일원으로 빌드하므로, `api/index.go`가 `internal/`을 직접 import해도 에러가 나지 않는다.
로컬에서는 초록불인데 push하면 Vercel 빌드가 빨간불이 되는, 가장 늦게 발견되는 종류의 실패다.

이 실패는 모듈 루트에서 파일 하나를 지목해 빌드하면 로컬에서 재현된다.

[source,bash]
----
go build api/index.go
----

Go는 파일 단위로 빌드를 지시받으면 그 파일을 모듈 소속으로 인정되지 않는 `command-line-arguments`라는 임시 패키지로 취급한다.
그래서 `internal/`을 직접 import했다면 `use of internal package ... not allowed` 에러가 나고, Vercel에서 벌어질 실패를 push 전에 볼 수 있다.

Flashcard는 이 명령을 상시 품질 게이트로 만들었다.
저장소 루트의 `./check.sh`가 gofmt·build·vet·test 다음 마지막 검사로 `flashcard-advanced/`에서 이 빌드를 돌린다({ch-quality-gates}).
에이전트가 `api/index.go`에 `internal/handlers`를 직접 import해도 `go build ./...`와 테스트는 모두 통과하므로, 이런 암묵적 제약은 명시적 검사로 박제해 두지 않으면 같은 함정을 다시 밟게 된다.

== vercel.json 해부

이 배포 구성의 설계도인 `vercel.json`은 일곱 줄이지만, 앞의 결정들이 전부 이 안에 들어 있다.

`vercel.json`:

[source,json]
----
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "framework": null,
  "regions": ["iad1"],
  "ignoreCommand": "git diff --quiet ${VERCEL_GIT_PREVIOUS_SHA:-HEAD^} HEAD -- . || exit 1",
  "rewrites": [{ "source": "/(.*)", "destination": "/api/index" }]
}
----

`$schema`는 편집기가 오타나 없는 항목을 알려 주게 하는 명세 주소일 뿐, 앱의 동작에는 영향을 주지 않는다.

`rewrites`의 유일한 규칙은 {ch-vercel}에서 다뤘다.
경로 해석이 전부 Gin 라우터의 몫이라, 새 페이지는 Go 코드에 라우트 한 줄을 더하는 것으로 끝나고 이 파일을 고칠 일이 없다.

`"framework": null`은 감지할 프레임워크가 없다는 결정을 파일에 적어 둔다.
Vercel은 저장소를 import하는 순간 감지한 프레임워크를 프로젝트 설정(Framework Preset)에 저장하는데, 이 값은 저장소가 바뀌어도 따라 바뀌지 않는다.
Flashcard가 이 함정을 실제로 밟았다.
이 앱의 초기 구현은 Next.js 프런트엔드였고({ch-git}의 커밋 로그), Go 서버 렌더링으로 전환하며 `package.json`까지 지웠지만 Framework Preset에는 Next.js가 남아 있었다.
그 상태로 운영 배포를 하자 Vercel이 `next build`를 실행했고, pages 디렉터리를 찾지 못해 빌드가 실패했다.
`"framework": null`은 대시보드에 무엇이 저장되어 있든 덮어쓰므로, 저장소만으로 빌드 방식이 정해진다.

`ignoreCommand`는 배포를 건너뛸 조건이다.
여기 적은 명령이 성공(종료 코드 0)하면 Vercel은 그 커밋의 빌드와 배포를 생략한다.
이 저장소에는 완성본 앱과 2부의 최소 앱, 책 원고가 함께 있어서, Vercel 프로젝트의 Root Directory에 `flashcard-advanced/`를 적어 배포할 앱의 폴더를 알려 두고, `ignoreCommand`도 그 폴더 안에서 실행된다.
그래서 이 `git diff` 명령은 앱 디렉터리에 변경이 없을 때 성공하고, 원고나 연습용 코드만 고친 커밋에서는 앱이 다시 배포되지 않는다.
{ch-quality-gates}에서 CI가 `paths-ignore`로 원고 커밋의 검사를 건너뛴 것과 같은 판단이다.

이 명령에서 중요한 것은 무엇과 견주느냐다.
``VERCEL_GIT_PREVIOUS_SHA``는 Vercel이 넣어 주는 환경 변수로, 그 브랜치에서 마지막으로 배포에 성공한 커밋의 SHA다.
처음에는 이 자리에 직전 커밋인 ``HEAD^``를 적어 두었다가 운영 배포를 한 달 동안 놓쳤다.
Vercel은 push에 담긴 커밋 가운데 마지막 하나만 검사한다.
앱을 고친 커밋과 원고만 고친 커밋을 함께 push했는데 마지막이 원고 커밋이면, `git diff HEAD^ HEAD`는 변경 없음으로 끝나고 앞선 앱 변경까지 배포되지 않는다.
운영 사이트는 오류 없이 새 기능만 빠진 채 돌아가므로 이 누락은 알아채기 어렵다.
마지막 성공 배포와 견주면 그 사이에 쌓인 커밋을 한 번에 보므로 이 문제가 없어진다.

`:-`는 환경 변수가 비어 있을 때 뒤의 값을 대신 쓰라는 셸 문법이라, 그 브랜치의 첫 배포에서는 ``HEAD^``와 견준다.

끝의 `|| exit 1`은 종료 코드를 0과 1 둘로만 맞춘다.
Vercel은 이 명령이 0(건너뛴다)이나 1(배포한다)을 낸다고 보지만, `git diff`는 오류 코드도 낸다.
Vercel은 빌드할 때 저장소를 최근 커밋 열 개까지만 얕게 복제(shallow clone)하므로footnote:[https://vercel.com/docs/builds/configure-a-build[Vercel 문서 "Configuring a Build"]가 빌드마다 `git clone --depth=10`으로 최근 커밋 열 개만 받아 온다고 밝힌다.] 마지막 성공 배포가 그보다 오래되면 견줄 커밋이 없어 `git diff`가 오류로 끝난다.
`|| exit 1`을 붙여 두면 확실히 변경이 없을 때만 0이 나가고, 나머지는 전부 "일단 배포한다"로 모인다.

=== regions: 함수를 iad1에 고정하는 이유

`"regions": ["iad1"]`은 서버리스 함수의 실행 리전(region)을 미국 동부(버지니아 북부)로 고정한다.

.[용어 풀이] 리전(Region)
[NOTE]
====
서버가 물리적으로 놓인 지역이다.
클라우드 업체가 세계 여러 곳에 둔 데이터 센터 가운데 어디에서 코드를 돌릴지 고르는 것이 리전 선택이고, `iad1`은 미국 동부를 가리킨다.
데이터가 오가는 거리가 멀수록 응답이 늦어진다.
====

한국에서 쓰는 앱인데 함수를 미국 동부에 두는 이유는, PostgreSQL이 Supabase 무료 티어의 미국 동부(East US, North Virginia) 리전에 있기 때문이다.
함수를 같은 지역에 두면 요청당 서너 번 일어나는 함수↔데이터베이스 왕복이 같은 지역 안에서 끝난다.
서울과 버지니아 사이의 왕복이 약 180ms, 같은 리전 안에서는 1ms 수준이라 그 차이가 왕복 횟수만큼 곱해진다.
이 콜로케이션(colocation) 전략의 셈법과 Supabase 쪽 설정은 {ch-supabase-db}에서 다룬다.

=== 같은 오리진의 덤: CORS가 등장하지 않는다

페이지와 API가 같은 서버, 같은 도메인에서 나오므로 브라우저의 요청은 전부 같은 오리진(same-origin) 요청이다.
오리진은 프로토콜·도메인·포트를 묶어 부르는 출처라서, 셋이 모두 같으면 같은 오리진이다.

.[용어 풀이] CORS(Cross-Origin Resource Sharing)
[NOTE]
====
웹페이지가 자신과 다른 출처(도메인·포트)의 API를 부를 때, 브라우저가 그 호출을 허용할지 검사하는 보안 규칙이다.
서버가 "이 출처는 허용한다"고 응답 헤더로 밝혀야 브라우저가 결과를 넘겨준다.
남의 사이트가 몰래 내 API를 호출해 사용자를 도용하는 일을 막는 장치다.
====

주소가 서로 다르면 브라우저는 본 요청에 앞서 보내도 되는지 묻는 CORS 프리플라이트(preflight) 요청을 보내지만, 같은 오리진에서는 이 절차가 없다.
그래서 이 앱에는 CORS 미들웨어도 허용 출처 설정도 없다.
한동안 넣어 두었던 CORS 미들웨어도 켜질 일이 없어 걷어냈고, 다른 도메인에서 이 API를 직접 호출하는 클라이언트가 생기면 그때 미들웨어를 더하고 허용 출처를 환경 변수로 받으면 된다.

== 개발 배포와 운영 배포를 구분한다

Vercel의 배포에는 두 종류가 있다.
프로덕션 배포(Production Deployment)는 프로젝트에 지정된 프로덕션 브랜치(Production Branch)에 push나 병합이 일어날 때 실행되어 대표 도메인에 반영된다.
프리뷰 배포(Preview Deployment)는 그 외 브랜치에 push할 때마다 만들어지며 배포마다 고유 URL을 받는다.

.[용어 풀이] 프리뷰 배포(Preview Deployment)
[NOTE]
====
운영에 반영하지 않고 확인용으로만 띄우는 배포다.
push한 시점의 코드가 운영과 같은 방식으로 빌드되어 고유 주소를 받으므로, 대표 도메인에 영향 없이 변경 사항을 눌러 볼 수 있다.
관객 없이 본 무대에서 하는 리허설이다.
====

프로덕션 브랜치의 기본값은 `main`이지만, {ch-git}의 정책은 `main`을 개발, `release`를 운영 브랜치로 쓰는 것이었다.
그래서 Vercel 대시보드의 프로젝트 설정에서 프로덕션 브랜치를 `release`로 바꾼다.
이 글을 쓰는 시점에는 프로젝트 설정의 환경(Environments) 화면에 있다.

이 설정 하나로 `main` push는 개발 환경을 확인하는 프리뷰 배포가 되고, `main`을 `release`에 병합하면 운영 배포가 된다.
프리뷰 URL은 두 종류다.
배포마다 새로 발급되는 고유 URL과 별개로, 브랜치의 최신 프리뷰를 늘 가리키는 고정 별칭(`<앱>-git-main-<계정>.vercel.app` 형식)이 생긴다.
{ch-supabase-auth}의 OAuth Redirect URL처럼 개발 환경의 주소를 어딘가에 등록해야 할 때는 이 별칭을 등록한다.
함수 리전, rewrite 규칙, 스코프별 환경 변수처럼 로컬 서버에는 없는 요소가 어긋났는지는 여기서 처음 드러난다.
Vercel 빌드가 "만들 수 있는가"를, CI가 "옳은가"를 묻는다면({ch-quality-gates}), 프리뷰 배포는 "실제 인프라 위에서 돌아가는가"를 확인한다.

환경 변수도 같은 기준으로 나뉜다.
Vercel의 환경 변수에는 Production, Preview, Development라는 스코프(scope), 곧 값이 어느 배포에 적용되는지를 나누는 범위가 있어서, 같은 이름에 스코프별로 다른 값을 등록할 수 있다.
`DATABASE_URL`에 Production 스코프로는 운영 데이터베이스를, Preview 스코프로는 개발 데이터베이스를 등록하면, 같은 코드가 서로 다른 데이터베이스를 바라본다({ch-supabase-db}).
Development 스코프는 `vercel dev` 명령으로 내 컴퓨터에서 앱을 띄울 때 읽히는 값의 자리다.
이 책의 로컬 실행은 {ch-local-dev}의 스크립트가 맡으므로 이 스코프는 쓰지 않고, 개발 환경의 값은 전부 Preview 스코프에 넣는다.

얻는 것은 운영과 같은 인프라에서 미리 확인하는 단계이고, 치르는 것은 운영 반영마다 `main`에서 `release`로의 병합 한 단계, 그리고 스코프별로 이중 관리하는 환경 변수다(한쪽을 빼먹으면 개발과 운영이 조용히 어긋난다).
하루에도 몇 번씩 운영 배포를 하는 팀이라면 거추장스럽겠지만, 혼자 운영하는 앱에서는 운영 반영을 일부러 챙겨서 하게 된다는 이점이 더 크다.

=== 잘못 나간 배포 되돌리기

배포가 앱을 깨뜨렸을 때 응급 처치는 Vercel 대시보드에서 한다.
배포 목록에는 지금까지의 프로덕션 배포가 남아 있고, 마지막으로 멀쩡했던 배포를 골라 다시 대표 도메인에 올릴 수 있다(이 글을 쓰는 시점에는 Instant Rollback이라는 기능이다).
이미 만들어 둔 결과물로 갈아 끼우므로 빌드를 기다리지 않는다.

정식 대응은 {ch-git}에서 본 revert다.
문제의 커밋을 revert한 새 커밋을 main에 만들고, 개발 환경에서 확인한 뒤 release로 병합한다.

대시보드 복귀만 하고 두면 저장소의 이력은 그대로라, 다음 release 병합에서 문제의 변경이 다시 나간다.
그래서 급한 불은 대시보드에서 끄고, 곧바로 revert로 이력을 운영과 같은 상태로 맞춘다.
데이터베이스 스키마까지 바뀐 배포라면 코드만 되돌려서는 끝나지 않을 수 있는데, 그 습관은 {ch-migrations}에서 다룬다.

== 콜드스타트: Go 바이너리라서 감당 가능한 비용

서버리스를 택한 이상 콜드스타트는 피할 수 없다.
그 비용은 대략 "런타임 기동 + 애플리케이션 초기화"로 나뉘고, Go는 둘 다에서 유리하다.

첫째, 런타임 기동.
스크립트 언어는 인터프리터를 띄운 뒤 수많은 모듈 파일을 읽어야 하고, JVM은 클래스 로딩과 JIT 워밍업을 거쳐야 한다.
Go 함수는 컴파일된 단일 바이너리라 그런 준비 없이 실행 즉시 코드가 돈다({ch-tech-choices}).

둘째, 애플리케이션 초기화.
`pkg/app`의 `build()`가 하는 일(환경 변수 읽기, 커넥션 풀 준비, 라우터 조립)은 전부 메모리 안에서 끝나고, `sync.Once` 덕분에 콜드스타트당 한 번만 치른다.
단, 첫 요청에는 비용이 두 가지 더해진다.
하나는 커넥션 풀이 데이터베이스와 첫 연결을 맺는 시간이다.
다른 하나는 로그인 토큰(JWT)을 검증할 열쇠 묶음인 JWKS(JSON Web Key Set)를 Supabase에서 처음 받아 오는 네트워크 왕복이다.
`DEPLOY.md`의 문제 해결 절도 "첫 요청이 느림"의 원인으로 이 둘을 적어 두었다.

무료 티어에서 감수하기로 한 것은 셋이다.

첫째, 한동안 요청이 없으면 다음 첫 요청이 느리다.
유료 요금제의 상시 워밍업 같은 옵션 없이 콜드스타트를 그대로 맞는다.
하루 몇 번 쓰는 암기 앱이라면 이 지연은 학습 한 번의 첫 화면에서만 생기고, 카드를 넘기는 요청들은 따뜻해진 인스턴스가 받는다.
Go 바이너리의 기동은 수십 밀리초라 지연의 대부분은 첫 데이터베이스 연결과 JWKS 조회이고, 이 둘도 인스턴스가 살아 있는 동안은 되풀이되지 않는다.

둘째, 요청당 실행 시간 제한이 있다(무료 플랜은 300초다. {ch-free-tier}).
엔드포인트가 전부 짧은 CRUD라 제한 근처에도 가지 않지만, 오래 걸리는 작업을 API에 넣을 수 없다는 설계 제약은 남는다.

셋째, 인스턴스 회수 시점을 제어할 수 없다.
그래서 프로세스 메모리에는 상태의 원본을 두지 않고 모든 상태를 데이터베이스에 둔다.

반대급부는 "서버 관리 0, 고정 비용 0"이다.

== 배포 절차 개요: 구성 요소로 읽는 DEPLOY.md

클릭 절차는 {ch-deploy}에 화면 캡처와 함께, `flashcard-advanced/DEPLOY.md`에는 짧은 체크리스트로 있다.
여기서는 "무엇이 무엇과 연결되는가"라는 구성 요소 관점으로 다섯 단계를 요약한다.

첫째, Supabase 프로젝트를 만든다.
리전은 Vercel 함수의 iad1과 맞도록 East US(North Virginia)로 고른다.
여기서 아래 표의 세 값, 곧 데이터베이스 연결 문자열과 프로젝트 URL, anon key가 나온다.
개발용 프로젝트도 하나 더 만드는데, 그 이유는 {ch-supabase-db}의 몫이다.

둘째, 데이터베이스 마이그레이션(migration)을 실행한다.
빈 데이터베이스에 {ch-database-design}에서 설계한 테이블을 만드는 작업으로, `go run ./cmd/migrate`가 스키마를 Supabase의 PostgreSQL에 적용한다.
손으로 실행하는 것은 처음 한 번뿐이고, 그다음부터는 스키마 파일이 바뀐 커밋마다 `migrate.yml`이 브랜치가 정한 DB에 적용한다({ch-migrations}).

셋째, OAuth 앱을 등록한다.
Google과 GitHub에 OAuth 애플리케이션을 만들고 자격 증명을 Supabase에 연결한다({ch-supabase-auth}).

넷째, GitHub 저장소를 만들어 push하고, 운영용 `release` 브랜치를 만들어 둔다({ch-git}).

다섯째, Vercel에서 저장소를 import하고, Root Directory를 `flashcard-advanced/`로 지정하고, 프로덕션 브랜치를 `release`로 바꾸고, 환경 변수를 등록한다.
빌드 설정은 `vercel.json`이 정하므로, 사람이 입력할 것은 Root Directory, 프로덕션 브랜치, 그리고 다음 표의 환경 변수 셋뿐이다.

|===
| 이름 | 값

| `DATABASE_URL` | Transaction pooler 문자열 (6543)
| `SUPABASE_URL` | `https://<ref>.supabase.co`
| `SUPABASE_ANON_KEY` | anon key
|===

세 값 모두 Go 함수가 런타임에 읽는다.
`DATABASE_URL`은 데이터베이스 연결에, `SUPABASE_URL`과 `SUPABASE_ANON_KEY`는 Supabase 인증 서버와의 통신과 토큰 검증에 쓰이고, JWKS 주소는 `SUPABASE_URL`에서 유도된다.
인증까지 서버가 수행하므로({ch-supabase-auth}) 브라우저에 새겨 넣는 값은 하나도 없다.
`DATABASE_URL`이 직접 연결(5432)이 아니라 트랜잭션 풀러(6543)여야 하는 이유는 서버리스의 연결 폭증 문제와 얽혀 있어 {ch-supabase-db}에서 다룬다.
Production에는 운영 Supabase 프로젝트의 값을, Preview에는 개발 프로젝트의 값을 넣는다.
값의 의미는 {ch-supabase-auth}와 {ch-supabase-db}를 읽으며 채워 가면 된다.

앞의 세 단계(Supabase 프로젝트, 마이그레이션, OAuth 등록) 없이 Vercel 연결만 먼저 하면, 배포는 성공해도 앱은 뜨지 않는다.
빌드는 코드가 컴파일되는지만 확인하고, 필요한 환경 변수가 비어 있으면 함수가 기동을 거부하도록 짜여 있어({ch-supabase-db}) 접속자에게는 500 오류만 보인다.
그래서 배포는 4부를 마친 뒤 {ch-deploy}의 순서를 따라 완주하는 편이 안전하다.

여기까지 마치면 이후의 배포는 전부 자동이다.
`git push origin main` 한 번에 Vercel이 Go 함수를 컴파일해 프리뷰 배포를 만들고, `main`을 `release`에 병합하면 같은 과정이 운영 배포로 실행된다(`origin`은 {ch-git}에서 등록한 원격 저장소의 기본 이름이다).
새 버전은 중간 상태 없이 한 번에(원자적으로) 서비스되고, 배포 스크립트도 서버 접속도 없다.

== 에이전트 활용 아이디어

* `AGENTS.md`에 "`vercel.json`의 rewrite와 함수 리전은 바꾸지 않는다"를 적어 둔다. 다만 지침은 부탁이라, 기계로 확인할 수 있는 규칙이라면 검사 쪽이 더 믿을 만하다.
* 배포가 실패하면 Vercel 대시보드의 빌드 로그를 대화에 붙여 넣는다. 빌드 환경 차이나 환경 변수 누락처럼 로컬에서 재현되지 않는 실패일수록 로그 해석을 맡기는 값어치가 크다.
* 플랫폼 제약을 새로 발견하면 그것을 커밋 전에 재현하는 명령을 찾아 `./check.sh`에 더하게 한다. `go build api/index.go`가 그렇게 들어간 검사다.

== 정리

Vercel Go 런타임이 `api/index.go`를 모듈 외부에서 단독 컴파일한다는 제약 때문에 조립 코드를 `pkg/app`에 두었다.
`go build ./...`로는 잡히지 않는 이 위반은 `./check.sh`의 `go build api/index.go`가 커밋 전에 잡는다.

`vercel.json`은 네 가지를 정한다.
모든 요청을 함수 하나로 모으는 rewrite, 프레임워크가 없다는 `"framework": null`, 데이터베이스와 같은 지역의 함수 리전, 앱 디렉터리가 바뀌지 않은 커밋의 배포를 건너뛰는 `ignoreCommand`다.

프로덕션 브랜치를 `release`로 바꿔 `main` push는 프리뷰 배포로, `release` 병합은 운영 배포로 나눴고, 환경 변수는 스코프로 운영·개발 값을 따로 둔다.
잘못 나간 배포는 대시보드에서 이전 배포로 복귀시키고 곧바로 revert로 이력을 맞춘다.

콜드스타트는 서버리스의 대가지만, 단일 바이너리인 Go라서 감당할 만한 수준에 머문다.

다음 {ch-supabase-auth}에서는 공개된 앱의 관문인 인증, 곧 OAuth 로그인과 쿠키 세션을 다룬다.
