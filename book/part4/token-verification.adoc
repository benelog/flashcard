= 토큰 검증의 원리: JWT와 JWKS

{ch-supabase-auth}에서 로그인을 마친 브라우저의 HttpOnly 쿠키에는 서명된 토큰이 담겨 돌아온다.
이 장에서는 서버가 그 토큰이 진짜인지 판별하는 원리를 해부한다.
앱을 따라 만드는 데에는 {ch-supabase-auth}까지로 충분하므로, 원리가 궁금할 때 읽으면 된다.
JWT의 구조, JWKS 공개키로 서명을 확인하는 절차, 클레임 검증, 그리고 두 인증 경로가 같은 검증 코드로 모이는 구조를 차례로 본다.

== Go에서의 JWT 검증

JWT(JSON Web Token)는 헤더·페이로드·서명 세 부분을 점으로 이은 문자열이고, 페이로드에는 사용자 ID(`sub`), 만료 시각(`exp`) 같은 클레임(claim)이 들어 있다.
앞의 두 토막은 암호가 아니라 JSON을 Base64URL이라는 규칙으로 글자만 바꿔 적은 것이라, 토큰을 주운 사람도 내용은 읽을 수 있다.
대신 한 글자라도 고치면 마지막 토막인 서명과 맞지 않게 되므로 고쳐 쓰지는 못한다.
검증의 핵심은 "이 토큰을 정말 Supabase가 발급했는가"를 서명으로 확인하는 것이다.

.[용어 풀이] JWT(JSON Web Token)
[NOTE]
====
로그인에 성공했다는 사실을 서버가 서명해서 발급하는 긴 문자열로, 소지자가 누구이고 언제까지 유효한지가 적힌 디지털 출입증이다.
놀이공원의 입장 밴드처럼 한 번 받으면 요청마다 신분증을 다시 보이지 않아도 되고, 위조하면 서명이 깨지므로 서버는 진짜인지 검사만 하면 된다.
====

.[용어 풀이] 클레임(Claim)
[NOTE]
====
토큰 안에 적힌 주장 하나하나를 클레임이라 한다.
"이 토큰의 주인은 이 사용자다"(`sub`), "이 시각에 만료된다"(`exp`), "로그인한 사용자용이다"(`aud`)처럼 발급자가 서명으로 보증하는 항목들이다.
어떤 클레임을 어디까지 믿을지 정하는 일이 곧 인증 규칙이 된다.
====

=== JWKS: 공개키를 내려받아 서명을 확인한다

Supabase는 비대칭 키(asymmetric key)로 토큰에 서명하고, 확인용 열쇠인 공개키(public key) 목록을 JWKS(JSON Web Key Set)라는 표준 형식으로 공개한다.
주소는 `https://<project-ref>.supabase.co/auth/v1/.well-known/jwks.json`이다.

.[용어 풀이] 대칭 키와 비대칭 키(Symmetric/Asymmetric Key)
[NOTE]
====
서명과 검증에 같은 열쇠 하나를 쓰는 방식이 대칭 키이고, 서명하는 개인키(private key)와 확인하는 공개키(public key)가 짝으로 나뉘는 방식이 비대칭 키다.
비대칭 키에서는 확인만 할 수 있는 열쇠를 따로 나눠 줄 수 있다.
JWT의 서명 방식 이름에서 HS256은 대칭 키(HMAC)를, RS256과 ES256은 비대칭 키를 뜻한다.
====

.[용어 풀이] JWKS와 서명 검증
[NOTE]
====
발급자가 개인키로 찍은 서명을 대조할 수 있도록 공개키를 모아 공개한 목록이 JWKS(JSON Web Key Set)다.
인감은 주인만 찍을 수 있지만, 인감증명서(공개키)를 가진 사람은 누구나 그 도장이 진짜인지 대조할 수 있는 것과 같다.
====

`internal/auth/jwt.go`에서 서명을 대조할 열쇠를 어디서 가져올지 정하는 부분이다.

[source,go]
----
func keyfuncFor(jwksURL, secret string) (jwt.Keyfunc, error) {
	if secret != "" {
		return func(t *jwt.Token) (any, error) {
			if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
				return nil, jwt.ErrTokenSignatureInvalid
			}
			return []byte(secret), nil
		}, nil
	}
	k, err := jwksFor(jwksURL)
	if err != nil {
		return nil, err
	}
	return k.Keyfunc, nil
}

func jwksFor(jwksURL string) (keyfunc.Keyfunc, error) {
	jwksMu.Lock()
	defer jwksMu.Unlock()
	if jwks == nil {
		failFirst := false
		k, err := keyfunc.NewDefaultOverrideCtx(context.Background(), []string{jwksURL},
			keyfunc.Override{NoErrorReturnFirstHTTPReq: &failFirst})
		if err != nil {
			return nil, err
		}
		jwks = k
	}
	return jwks, nil
}
----

기본 경로는 아래쪽 JWKS 분기다.
`github.com/MicahParks/keyfunc/v3` 라이브러리가 JWKS 문서를 내려받아 캐시하고 기본값인 1시간마다 다시 받으며(`jwkset`의 `RefreshInterval`), 검증할 때 토큰 헤더의 키 ID(`kid`)에 맞는 공개키를 골라 준다.
`jwks`를 프로세스당 한 번만 만드는 것(`jwksFor`)은 {ch-vercel-config}에서 본 서버리스 함수의 생명주기 때문이다.
웜 인스턴스는 여러 요청을 처리하므로 첫 요청 이후에는 네트워크 조회 없이 검증한다.
라이브러리 기본값은 첫 내려받기 실패를 삼키고 빈 키 묶음으로 출발한다(`NoErrorReturnFirstHTTPReq`).
그러면 콜드스타트 직후의 일시적 네트워크 오류로 멀쩡한 토큰이 몇 분 동안 401로 거절당한다.
그래서 이 코드는 첫 실패 때 클라이언트를 남기지 않고 오류(500)를 돌려주어, 다음 요청이 다시 받아 오게 한다.

위쪽 분기는 비대칭 키로 옮기기 전의 Supabase 프로젝트를 위한 공유 시크릿(HS256) 폴백(fallback)이라, 처음 읽을 때는 건너뛰어도 된다.
Supabase는 2025년 7월에 비대칭 서명 키 체계를 내놓았고, 2025년 10월 1일부터 새 프로젝트는 비대칭 키로 서명한다footnote:[Supabase 블로그 "Introducing JWT Signing Keys"(2025-07-14). https://supabase.com/blog/jwt-signing-keys[Introducing JWT Signing Keys]].
그 전에 만든 프로젝트는 대시보드의 JWT Signing Keys 화면에서 이관하기 전까지 공유 시크릿으로 서명하므로, `SUPABASE_JWT_SECRET`을 설정해 이 분기를 탄다.
이 분기의 HMAC 확인은 알고리즘 혼동(algorithm confusion) 공격을 막는다.
누구나 구할 수 있는 공개키를 비밀 열쇠인 척 쓰게 만들려고 토큰 머리의 서명 방식 표기(`alg`)를 바꿔치기하는 수법이다.

=== 왜 공유 시크릿이 아닌가

HS256은 서명과 검증에 같은 시크릿을 쓰므로, 검증하는 Go 함수에도 시크릿을 환경 변수로 배포해야 하고, 우리 쪽에서 그 시크릿이 새면 누구든 토큰을 위조할 수 있다.
JWKS 기반 비대칭 서명은 이 문제를 구조적으로 없앤다.
첫째, 개인키는 Supabase만 보유하므로 검증자 쪽에서 무엇이 유출되어도 위조할 수 없다.
둘째, JWKS URL은 공개 정보라 관리할 비밀이 하나 줄어든다.
셋째, 키 회전(key rotation)을 발급자 혼자 끝낸다.
JWKS 문서에 새 키를 추가하고 옛 키를 빼면 검증자는 캐시를 갱신하며 따라가므로, 발급자와 모든 검증자를 동시에 고칠 일이 없다.

발급자와 검증자가 같은 프로세스 안에 있거나 외부 네트워크 조회를 피해야 하는 폐쇄 환경이라면 시크릿 하나로 끝나는 대칭 키가 낫다.
발급자(Supabase)와 검증자(Go 서버)가 서로 다른 조직의 인프라에 있는 Flashcard에서는 JWKS가 유리하다.

=== 클레임 검증과 사용자 식별

서명이 유효해도 클레임 검증을 건너뛰면 안 된다.
다음은 `internal/auth/jwt.go`에서 토큰의 클레임을 검사한 뒤 그 내용을 돌려주는 함수다.

옵션 세 개가 각각 한 가지 공격 경로를 막는다.
`WithValidMethods`는 받아들일 서명 방식을 미리 정한 목록으로 고정한다.
토큰 머리의 서명 방식을 "서명 없음"(`alg: none`)으로 고쳐 놓고 검증하는 쪽이 믿어 주기를 노리는 수법이 있는데, 받아들일 방식을 먼저 정해 두면 소용이 없다.
`WithAudience("authenticated")`는 Supabase가 로그인 사용자에게 발급한 토큰만 받아, 익명 토큰이나 다른 용도의 토큰을 거른다.
`WithExpirationRequired`는 `exp` 클레임이 없는, 영원히 유효한 토큰을 거부한다.

검증을 통과하면 `sub` 클레임이 사용자 식별자다.
이 값은 Supabase `auth.users` 테이블의 UUID이고, {ch-database-design}에서 설계한 `profiles.id`가 이 값을 그대로 쓴다.
그래서 인증 시스템의 사용자와 우리 스키마의 사용자가 같은 키로 이어진다.

이 함수를 부르는 곳은 둘이다.
{ch-gin}에서 본 JSON API용 `parseUserID`는 `sub`만 꺼내고, {ch-supabase-auth}의 `withUser`가 쿠키의 토큰을 건네던 웹 계층용 `ParseUser`는 화면에 표시할 이메일까지 돌려준다.
`ParseUser`는 검사 규칙을 따로 두지 않고 `parseClaims`에 맡긴다.

=== 필수 인증과 선택 인증

이 파일은 JSON API용 미들웨어도 두 가지 내보낸다.
`Middleware`는 `Authorization: Bearer` 헤더의 토큰이 없거나 무효하면 401로 요청을 끊고, `OptionalMiddleware`는 유효한 토큰이 있을 때만 사용자 ID를 붙이되 없어도 통과시킨다.
둘을 라우터에 나눠 붙이는 이유는 {ch-gin}에서 다뤘다.

== 두 인증 경로의 공존

이 앱에는 인증 경로가 둘 있다.
HTML 페이지는 쿠키로, `/api/*`의 JSON API는 Bearer 헤더로 신원을 밝힌다.
JSON API는 저장소에 함께 있는 명령줄 도구(`flashcard-cli/`)나 외부 스크립트처럼 화면 없이 API만 부르는 호출자를 위해 남아 있다.

둘은 같은 Gin 엔진에 등록되고 같은 검증 코드를 쓴다.
`internal/web/routes.go`의 라우트 등록부에서 공개 페이지와 로그인 필수 페이지가 미들웨어 사슬로 나뉘는 곳을 발췌한다.

[source,go]
----
// 공개 페이지: 공유 덱 구경과 로그인 흐름.
pub := r.Group("/", w.withUser())
{
	pub.GET("/login", w.loginPage)
	pub.GET("/auth/login/:provider", w.startOAuth)
	pub.GET("/auth/callback", w.oauthCallback)
	pub.POST("/logout", w.logout)
	// ...
}

// 로그인해야 보는 페이지와 그 폼·htmx 끝점.
app := r.Group("/", w.withUser(), w.requireUser(), auth.EnsureProfile(w.store, w.failPage))
{
	app.GET("/", w.homePage)
	// ...
}
----

공개 그룹은 `withUser`만 지나서 익명도 통과하고, 로그인 그룹은 `requireUser`가 문을 지킨다.
끝의 `EnsureProfile`은 첫 요청에서 사용자의 프로필 행을 만들어 주는 미들웨어로, {ch-gin}의 JSON API와 함께 쓰되 실패 응답만 화면용 오류 화면(`failPage`)으로 끼워 만든다.
이 공유는 `internal/auth/jwt.go`의 작은 함수 하나 덕분에 성립한다.

[source,go]
----
// SetUserID는 인증된 사용자 ID를 요청 컨텍스트에 싣는다. API 미들웨어와 같은
// 키를 쓰므로, 쿠키로 인증한 웹 요청에서도 핸들러와 EnsureProfile이 똑같이
// 동작한다.
func SetUserID(c *gin.Context, id uuid.UUID) {
	c.Set(userIDKey, id)
}
----

쿠키에서 신원을 확인한 `withUser`도, 헤더에서 확인한 API 미들웨어도 사용자 ID를 컨텍스트의 같은 키에 넣는다.
그래서 그 아래의 코드(핸들러, `EnsureProfile`, store 계층)는 요청이 어느 문으로 들어왔는지 모른 채 `auth.UserID(c)` 하나로 동작한다.

== 정리

첫째, JWT 검증의 핵심은 서명 확인이다.
Supabase가 개인키로 서명한 토큰을 우리 서버는 JWKS로 공개된 공개키로 대조하고, 웜 인스턴스가 JWKS 클라이언트를 재사용해 첫 요청 이후에는 네트워크 조회가 없다.

둘째, 공유 시크릿(HS256)과의 차이는 유출의 결과에 있다.
JWKS 방식에서는 검증자에게 위조 능력이 없고, 배포할 비밀도 없으며, 키 회전도 발급자 혼자 끝낸다.

셋째, 서명이 유효해도 클레임을 검증한다.
허용 알고리즘 고정, `aud` 확인, 만료 필수라는 옵션 세 개가 `parseClaims` 한 곳에 모여 있고, 통과한 `sub`가 그대로 `profiles.id`가 된다.

넷째, 인증 경로는 둘이지만 둘 다 같은 컨텍스트 키에 사용자 ID를 남기므로 그 아래 코드는 구분하지 않는다.

다음 {ch-supabase-db}에서는 Supabase의 데이터베이스를 다룬다.
서버리스 환경에서 커넥션이 폭증하는 문제를 트랜잭션 풀러로 푸는 방법과 그 대가로 pgx에 붙여야 하는 설정이 그 내용이다.
