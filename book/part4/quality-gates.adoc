= 품질 게이트: 로컬 검사에서 GitHub Actions까지

{ch-unit-tests}에서 테스트와 gofmt·go vet으로 코드를 검증하는 신호를 만들었다.
그런데 그 신호는 누군가 기억해서 돌리는 동안만 작동한다.
이 장에서는 검사가 자동으로 걸리게 하는 장치를 세 겹으로 세운다.
파일을 고칠 때마다 도는 검사, 커밋 전에 한 번 돌리는 `check.sh`, 그리고 저장소에 코드가 도착하면 원격에서 도는 GitHub Actions의 CI다.

== 지시가 아니라 장치로

.[용어 풀이] 품질 게이트(Quality Gate)
[NOTE]
====
정해진 검사를 통과하지 못한 코드는 다음 단계로 넘어가지 못하게 막는 관문이다.
사람이 매번 신경 써서 지키는 규율이 아니라 시스템이 자동으로 세워 두는 장벽이라는 점이 핵심이다.
====

에이전트에게 "수정 후에는 반드시 gofmt와 go vet을 실행해"라고 적어 두는 것만으로는 부족하다.
첫째, 에이전트는 잊는다.
대화가 길어지거나 여러 파일을 연달아 고치는 중이면 검사 지시는 뒤로 밀리고, 배포를 깨뜨리는 것은 빠뜨린 한 번이다.
둘째, 실행이 들쭉날쭉하다.
같은 지시라도 어떤 날은 `go vet ./...`을, 어떤 날은 패키지 하나만 돌릴 수 있어서, "검사했다"는 보고가 무엇을 검사했다는 뜻인지 매번 확인할 수 없다.

통과 여부가 예/아니오로 갈리는 검사는 에이전트의 성실함에 맡기지 않고 장치로 강제한다.
이것이 이 장 전체의 원칙이다.
세 게이트를 시간 순으로 늘어놓으면 그림 21처럼 된다.

== 파일을 고칠 때마다: gofmt와 go vet

첫 번째 게이트는 파일을 고친 바로 그 순간에 도는 값싼 검사다.
사람이 에디터에서 저장하면 {ch-local-dev}에서 설정한 에디터가 gofmt를 돌린다.
에이전트에게도 같은 일을 시킬 수 있다.
대부분의 AI 코딩 에이전트는 파일을 고친 직후 정해 둔 셸 명령을 자동으로 실행하는 기능(흔히 훅이라 부른다)을 제공한다.
설정 방법은 도구마다 다르지만, 거기에 걸 검사의 설계는 같다.

.[용어 풀이] 셸(Shell)과 셸 스크립트(Shell Script)
[NOTE]
====
셸은 터미널({ch-first-run})에 친 명령을 받아 프로그램을 실행하고 결과를 돌려주는 프로그램이다.
리눅스와 macOS에서는 보통 bash나 zsh가 그 자리를 맡는다.
셸 스크립트는 한 줄씩 치던 명령들을 파일에 적어 한꺼번에 실행하게 만든 것으로, 변수와 조건 분기를 쓸 수 있어 작은 프로그램이 된다.
====

첫째, gofmt는 보고하지 않고 그냥 고친다(`gofmt -w`).
gofmt의 결과는 언제나 하나로 정해지므로, "포맷이 틀렸다"고 알려서 다시 고치게 하는 왕복은 시간만 버린다.

둘째, go vet은 방금 고친 파일이 속한 패키지에만 돌린다.
이 검사는 파일을 고칠 때마다 돌므로 느리면 모든 수정이 느려진다.
패키지 하나의 vet은 0.2초 안팎이지만, 다른 패키지로 번진 영향은 놓친다.
그 빈틈은 다음 게이트가 메운다.

셋째, 성공하면 조용하고 실패하면 시끄럽다.
통과하면 아무것도 출력하지 않고, 걸렸을 때만 오류 메시지를 에이전트에게 돌려준다.
대부분의 도구는 명령의 종료 코드로 성패를 판단해, 실패하면 그 출력을 에이전트에게 보여 준다.
에이전트는 자기가 방금 만든 vet 위반을 에러 메시지 그대로 보고 다음 차례에 스스로 고친다.

.[용어 풀이] 종료 코드(Exit Code)
[NOTE]
====
프로그램이 끝나면서 숫자 하나로 남기는 성적표다.
0이면 통과, 그 외의 숫자는 실패를 뜻한다.
셸 스크립트와 CI, 에이전트 도구가 모두 이 숫자를 보고 다음 단계로 넘어갈지 정한다.
====

사람의 에디터와 에이전트의 훅이 같은 gofmt를 돌린다는 점도 중요하다.
두 쪽의 포맷 규칙이 다르면, 번갈아 파일을 건드릴 때마다 공백과 줄바꿈만 바뀐 의미 없는 diff가 쌓인다.
설정 옵션이 없는 gofmt라 양쪽의 결과가 같은지 따로 맞춰 볼 필요도 없다.

== 커밋 전: check.sh

오래 걸리는 종합 검증은 파일마다 돌리지 않고 커밋 직전에 한 번 몰아서 건다.
커밋한 코드는 이력에 실려 원격 저장소와 배포로 흘러가기 때문이다.
이 저장소는 그 검증을 루트의 `check.sh` 하나에 모아 두었다.
사람이 터미널에서 돌리든 에이전트가 돌리든 같은 명령이다.

[source,bash]
----
include::../../check.sh[]
----

검사 순서는 싸고 빨리 실패하는 것부터다.

`gofmt -l .`은 포맷이 어긋난 파일 목록을 출력한다.
첫 번째 게이트가 gofmt를 자동 적용하므로 보통은 깨끗하지만, 그 게이트를 거치지 않고 들어온 수정(에디터 밖에서 고친 파일, `git merge`가 합친 파일)을 잡는다.

그다음 세 Go 모듈(`flashcard-advanced/`, `flashcard-basic/`, `flashcard-cli/`)마다 `go build`·`go vet`·`go test`를 돌린다.
첫 번째 게이트의 vet은 고친 패키지만 봤으므로, 다른 패키지로 번진 시그니처 변경은 여기서 처음 걸린다.
테스트가 가장 오래 걸린다.
{ch-app-tests}의 앱 기동 테스트가 SQLite 파일을 만들고 서버를 띄우기 때문이고, 그래서 파일을 고칠 때마다가 아니라 여기서 돈다.
2부의 연습용 Go 예제(`language-basic/go`)도 빌드와 vet을 돌려, 컴파일이 깨진 예제가 책에 실리지 않게 한다.

마지막 `go build api/index.go`는 이 저장소 고유의 검사다.
Vercel의 Go 런타임은 진입점인 `api/index.go`를 모듈 밖에서 단독으로 컴파일한다.
Go의 `internal/` 패키지는 같은 모듈 안에서만 import할 수 있으므로, 이 파일이 `internal/`을 import하면 로컬 빌드는 통과하는데 Vercel 배포만 실패한다.
내 컴퓨터는 이 파일을 앱 전체의 일부로 보고, Vercel은 이 파일 하나만 떼어 본다는 차이다.
파일을 단독으로 지정해 빌드하면 그 차이를 커밋 전에 재현할 수 있다.
배포가 깨진 뒤에 알면 수정→push→배포 대기를 왕복해야 하지만, 이 검사는 0.2초가 안 걸린다.
구조는 {ch-vercel-config}에서 다룬다.

에이전트가 이 스크립트를 빠뜨리지 않게 하는 방법은 둘이다.
`AGENTS.md`에 "push 전에 `./check.sh`가 통과해야 한다"고 적고, 에이전트 도구에서 이 명령을 승인 없이 실행하도록 허용해 둔다.
되돌릴 필요가 없는 검증 명령이라 자동 허용해도 안전하다({ch-instructing}).
그래도 이것은 부탁이라 빠질 수 있으므로, 같은 검사를 원격에서 한 번 더 돌린다.

== 원격: GitHub Actions

로컬의 게이트에는 공통된 약점이 있다.
통과하지 않고도 push할 수 있다는 것이다.
{ch-git}의 브랜치 정책에서 main으로 가는 코드는 개발 환경에, release로 가는 코드는 운영 환경에 닿는데, 검사를 건너뛴 코드가 그대로 도착할 수 있다.

로컬 게이트가 새는 경우는 셋이다.
첫째, 급한 수정을 바로 push할 때다.
둘째, 두 번째 사람이 합류할 때다.
풀 리퀘스트로 들어온 코드를 검사하려면 내 기계로 받아 직접 돌려야 한다.
셋째, 내 기계에만 있는 조건이 실패를 가릴 때다.
`go test`는 한 번 통과한 패키지의 결과를 저장해 두었다가 다시 보여 주는데, 결과에 영향을 주는 조건이 캐시가 알아채지 못하는 곳(환경 변수나 외부 파일)에 있으면 예전의 통과가 지금의 실패를 가린다.
CI는 아무것도 깔리지 않은 기계에서 저장소만으로 앱이 빌드되고 검증되는지 확인하는 장치다.

.[용어 풀이] 지속적 통합(CI, Continuous Integration)
[NOTE]
====
코드를 저장소에 합칠 때마다 빌드와 검사를 자동으로 돌려, 깨진 코드가 오래 섞여 있지 않게 하는 관행이다.
GitLab CI·CircleCI·Jenkins 같은 도구가 있고, 저장소가 GitHub에 있다면 별도 가입 없이 쓰는 GitHub Actions가 가장 손이 덜 간다.
====

=== 워크플로, 잡, 스텝, 러너

GitHub Actions는 저장소에서 어떤 일(이벤트)이 벌어지면 정해 둔 절차를 실행해 주는 도구다.
워크플로 하나가 잡을 여럿 담고, 잡 안에는 스텝이 순서대로 놓인다.

.[용어 풀이] 워크플로(Workflow)·잡(Job)·스텝(Step)
[NOTE]
====
워크플로는 `.github/workflows/` 아래의 설정 파일 하나로, 정해 둔 일이 벌어지면 깨어나 절차를 실행한다.
잡은 워크플로 안에서 컴퓨터 한 대를 차지하고 도는 작업 묶음이다.
스텝은 잡 안에서 위에서 아래로 하나씩 실행되는 단위로, 셸 명령이거나 남이 만들어 공개한 재사용 부품(액션, action) 하나다.
요리에 비유하면 워크플로는 조리법, 잡은 그것을 맡은 요리사, 스텝은 요리사가 밟는 단계다.
====

워크플로 파일의 형식은 YAML이다.

.[용어 풀이] YAML(YAML Ain't Markup Language)
[NOTE]
====
들여쓰기로 항목의 포함 관계를 나타내는 설정 파일 형식이다.
`이름: 값`으로 항목을 적고, 한 칸 더 들여쓴 줄은 바로 위 항목에 속한다.
{ch-gin-hello}의 JSON과 담는 내용은 같지만 중괄호와 따옴표가 없어 사람이 쓰기 편하다.
공백 한 칸이 어긋나면 다른 뜻이 되고, 탭 문자는 허용되지 않는다.
====

잡이 차지하는 컴퓨터가 러너다.

.[용어 풀이] 러너(Runner)
[NOTE]
====
GitHub가 검사를 돌릴 때마다 새로 빌려 주는, 아무것도 깔리지 않은 컴퓨터 한 대다.
코드를 내려받고 도구를 설치한 뒤에야 검사를 돌릴 수 있고, 끝나면 통째로 버려진다.
그래서 러너 안에서 파일을 고쳐도 저장소에는 아무것도 남지 않는다.
====

결과는 저장소 화면에서 본다.
push한 커밋 옆에 노란 점이 떴다가, 끝나면 통과는 초록 체크로, 실패는 빨간 가위표로 바뀐다.
Actions 탭에는 스텝마다의 출력이 남아 있고, 실패하면 메일로도 알려 준다.

잡끼리는 병렬로 돈다.
툴체인이 다른 검증 묶음이 여럿이면 잡을 나눠 시간을 줄일 수 있지만, Flashcard는 화면까지 Go 서버가 렌더링하므로 검증이 전부 Go 툴체인 위에서 돌고 잡도 하나면 된다.

=== ci.yml 읽기

저장소의 `.github/workflows/ci.yml` 전문이다.
`main`·`release`에 코드가 도착하거나 풀 리퀘스트가 갱신될 때 깨어나 gofmt·빌드·정적 분석·테스트·Vercel 호환 검사를 순서대로 돌린다.

[source,yaml]
----
include::../../.github/workflows/ci.yml[]
----

*`on`* 은 언제 도는지를 정한다.
`push`는 {ch-git}에서 정한 두 브랜치에 커밋이 도착할 때 깨어난다.
`release` push는 운영 배포({ch-vercel}) 직전의 마지막 관문이지만, 검사와 배포가 나란히 시작되므로 검사가 실패해도 배포는 진행된다.
진짜 관문으로 만들려면 뒤에서 볼 브랜치 보호 규칙으로 병합을 막아야 한다.
`pull_request`는 풀 리퀘스트가 열리거나 갱신될 때, `workflow_dispatch`는 GitHub 화면의 버튼으로 수동 실행할 때다.
`push`에만 `branches` 필터를 건 것은, 작업 브랜치를 push하고 풀 리퀘스트를 열 때 같은 커밋을 두 번 검사하지 않기 위해서다.

`paths-ignore`는 책 원고(`book/`)나 책 빌드 엔진(`book-template/`)만 고친 커밋에서 검사를 건너뛴다.
원고는 앱 바이너리에 들어가지 않으므로 검사 결과를 바꿀 수 없다.
이런 필터는 "이 경로가 바뀌지 않으면 결과가 절대 달라지지 않는다"가 참일 때만 건다.
깨진 코드를 통과시키는 대가가 1분 30초 안팎의 실행 한 번을 아끼는 이득보다 언제나 크다.

*`concurrency`* 는 같은 브랜치에서 아직 도는 검사가 있으면 취소하고 최신 실행만 남긴다.
연달아 push하면 앞선 커밋의 결과는 쓸모가 없기 때문이다.
`${{ github.ref }}`에는 브랜치 이름이 들어가므로 취소는 같은 브랜치 안에서만 일어난다.

*`setup-go`* 는 Go 버전을 워크플로에 적지 않고 `go.mod`에서 읽는다.
`go.mod`의 `go` 한 줄이 로컬과 CI가 함께 보는 단일 출처라 Go를 올릴 때 고칠 곳이 한 군데다.
`cache: true`는 모듈 다운로드 결과를 저장해 두 번째 실행부터 시간을 줄인다.
빌드·vet·테스트 스텝은 `working-directory`로 모듈을 정해 세 모듈을 각각 검사한다.

*gofmt 스텝* 은 `-w`가 아니라 `-l`을 쓴다.
러너의 파일을 고쳐 봐야 러너는 곧 사라지고 저장소에는 어긋난 파일이 남으므로, 어긋난 파일 이름을 찍고 `exit 1`로 실패한다.
같은 규칙인데 로컬에서는 고치고, 원격에서는 고발한다.

*Vercel 호환 스텝* 은 `api/` 아래에 `internal` 패키지를 가리키는 import가 있는지 `grep`(파일에서 특정 문자열이 든 줄을 찾는 명령)으로 확인한다.
`check.sh`의 `go build api/index.go`와 같은 제약을 지키는 더 가벼운 검사다.

== 같은 규칙을 세 곳에서

세 게이트가 무엇을 부르는지 한자리에 놓으면 다음과 같다.

|===
| 검사 | 파일 수정마다 | 커밋 전 `check.sh` | CI `ci.yml`

| 포맷 | `gofmt -w` (자동 수정) | `gofmt -l` (실패 처리) | `gofmt -l` (실패 처리)
| 정적 분석 | `go vet` (고친 패키지) | `go vet ./...` | `go vet ./...`
| 빌드 | 없음 | `go build ./...` | `go build ./...`
| 테스트 | 없음 | `go test ./...` | `go test ./...`
| Vercel 호환 | 없음 | `go build api/index.go` | `grep` 한 줄
|===

지킬 원칙은 하나, *세 곳의 명령이 서로 달라지게 두지 않는다.*
CI에서만 `-race` 플래그를 붙이거나 로컬에서만 특정 테스트를 건너뛰기 시작하면, "로컬에서는 통과하는데 CI에서만 깨진다"는 시간 낭비가 따라붙는다.
분담 기준은 빠르고 결정적인 검사는 앞쪽에, 느리고 포괄적인 검사는 뒤쪽에 두는 것이다.
앞쪽 게이트를 생략하면 vet 위반이 쌓인 채 한참 작업하다가 커밋 직전에 실패를 한꺼번에 마주한다.
오류는 발생 지점에 가까울수록 고치기 싸다.

== Vercel의 자동 배포와는 무엇이 다른가

{ch-vercel}에서 볼 Vercel은 `git push`마다 빌드하고 배포한다.
그래도 CI가 중복은 아니다.
Vercel의 빌드는 "이 코드로 앱을 만들 수 있는가"를 묻고, 컴파일만 되면 테스트가 실패하는 코드도 프로덕션으로 나간다.
CI는 "이 코드가 옳은가"를 묻고, 그 답이 나오기 전에는 코드가 브랜치에 들어가지 못하게 막을 수 있다.

.[용어 풀이] 브랜치 보호 규칙(Branch Protection Rule)
[NOTE]
====
특정 브랜치에 코드가 들어오는 조건을 GitHub 저장소 설정에 못 박아 두는 장치다.
CI 통과를 필수로 걸면 검사가 실패한 풀 리퀘스트는 병합 버튼이 잠기고, 직접 push를 막으면 풀 리퀘스트를 거치지 않은 코드는 들어오지 못한다.
{ch-git}의 브랜치 정책이 문서의 약속이라면, 이 규칙은 그 약속을 저장소가 강제하게 만든다.
====

혼자 개발하는 저장소에서도 스스로 만든 규칙에 스스로 걸리는 장치라 제값을 한다.

== 이 저장소의 다른 워크플로

`.github/workflows/`에는 파일이 둘 더 있다.
`book.yml`은 이 책을 GitHub Pages에 배포한다.
`ci.yml`과 반대로 `paths` 필터를 걸어 원고(`book/`)나 책 빌드 엔진(`book-template/`)이 바뀐 커밋에서만 깨어나므로, 커밋 하나는 대개 둘 중 하나만 깨운다.
`migrate.yml`은 저장소를 검사하는 대신 데이터베이스의 스키마를 실제로 바꾸는 워크플로라 {ch-migrations}에서 다룬다.
{ch-free-tier}에서는 Supabase 무료 프로젝트의 일시 정지를 막으려고 하루 두 번 깨어나는 스케줄 워크플로를 하나 더한다.
GitHub Actions는 검사 도구이면서 저장소에 딸린 작은 크론(cron, 정해 둔 시각마다 명령을 실행해 주는 예약 장치)이기도 하다.

== 무엇을 넣지 않았는가

`staticcheck`({ch-unit-tests})는 넣지 않았다.
표준 도구가 아니라 실행마다 설치해야 해서, 빈 캐시에서 재 보니 내려받아 컴파일하는 데 11초가 걸렸다.
vet이 보지 않는 문제가 눈에 띄기 시작하면 넣을 것이다.

브라우저를 띄워 사람의 조작을 재연하는 E2E 테스트도 없다({ch-whats-next}).
러너에 브라우저를 설치해야 하고, 실제 OAuth 로그인까지 검증하려면 테스트용 Supabase 프로젝트와 그 접속 정보가 따라온다.
지금 규모에서는 그 복잡도가 얻는 것보다 크다.
대신 {ch-app-tests}의 앱 기동 테스트가 브라우저 없이 화면과 API를 실제 요청으로 검사하고, 이미 `go test ./...` 한 줄에 들어 있다.

== 에이전트 활용 아이디어

* CI가 깨지면 실패한 스텝의 출력만 골라 에이전트에게 주고 원인을 찾게 한다. 로그를 통째로 붙이는 것보다 빠르다.
* 스케줄 워크플로(일시 정지 방지 핑, 정기 백업)는 요구사항만 또렷하면 에이전트가 한 번에 만들어 내는 일이다. 다만 시크릿 값이 로그에 찍히지 않는지는 사람이 정독한다.
* 검증 명령을 바꾸는 수정에서 `check.sh`와 `ci.yml` 중 한쪽을 빠뜨리지 않도록 `AGENTS.md`에 "두 파일은 같은 검사를 돌린다"고 적어 둔다.

== 정리

* 결과가 예/아니오로 갈리는 검사는 지시가 아니라 장치로 강제한다.
* 파일을 고칠 때마다 gofmt를 자동 적용하고 고친 패키지에 go vet을 돌린다. 에디터와 에이전트의 훅이 같은 규칙을 쓰고, 성공하면 조용하고 실패하면 오류를 돌려준다.
* 커밋 전에는 `check.sh` 하나로 세 모듈의 build·vet·test와 `go build api/index.go`(Vercel 호환)를 돌린다.
* CI는 깨끗한 러너에서 같은 검사를 다시 돌린다. gofmt는 고치는 대신 `-l`로 고발하고, 브랜치 보호 규칙으로 CI 통과를 병합 조건에 걸 수 있다.
* 세 곳의 명령이 서로 달라지지 않게 하고, 빠른 검사는 앞에, 느린 검사는 뒤에 둔다.

다음 {ch-vercel}에서는 `git push` 한 번으로 Go 서버리스 함수가 페이지·정적 자산·API를 서빙하는 구조로 배포되는 과정을 따라간다.
