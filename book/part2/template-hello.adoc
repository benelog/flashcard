= html/template 첫걸음: 데이터를 화면에 채우고 조각으로 나눈다

{ch-gin-hello}에서 `decks.html`에 섞여 있던 `{{range .Decks}}`와 `{{.Name}}`은 설명 없이 지나갔다.
이 장에서는 Go 표준 라이브러리 html/template의 문법을 익히고, 라우팅 표에 남겨 둔 세 줄(카드 추가, 카드 삭제, 학습 화면)까지 읽어 2부의 최소 앱 한 바퀴를 마친다.
완성본이 템플릿을 어떻게 조직하는지(레이아웃, 조각 묶음, 함수 등록, 자동 이스케이프)는 {ch-html-template}에서 해부한다.
`flashcard-basic` 폴더에서 `go run .`으로 서버를 띄워 두고 화면을 눌러 보며 읽기를 권한다.

== 화면은 누가 만드는가

서버가 브라우저에 보내는 것은 HTML 문서 한 장이다({ch-html-hello}).
그 문서를 Go 코드에서 만드는 가장 단순한 방법은 문자열을 이어 붙이는 것이다.

[source,go]
----
html := "<h1>" + deck.Name + "</h1>"
----

한 줄일 때는 멀쩡하지만, 태그 수십 개가 중첩된 화면을 따옴표와 덧셈 기호 사이에 흩어 놓으면 구조가 눈에 들어오지 않고, 화면을 고치는 일이 Go 코드를 고치는 일이 된다.
그래서 HTML은 HTML대로 파일에 두고 데이터가 들어갈 자리만 표시해 둔 뒤, 템플릿 엔진이 둘을 합쳐 완성된 문서를 만들게 한다.

.[용어 풀이] 템플릿 엔진(Template Engine)
[NOTE]
====
빈칸이 뚫린 문서 양식에 데이터를 채워 완성된 문서를 만들어 주는 도구다.
"○○ 님, 안녕하세요"라는 양식과 "김철수"라는 데이터를 주면 "김철수 님, 안녕하세요"를 돌려준다.
워드프로세서의 편지 병합과 같은 원리이며, 웹에서는 HTML 양식에 데이터를 채워 화면을 만든다.
====

Go에는 이 엔진이 html/template이라는 이름으로 표준 라이브러리에 들어 있어 따로 설치할 것이 없다.
{ch-gin-hello}의 `LoadHTMLGlob("templates/*.html")`이 `templates` 폴더의 파일을 전부 읽어 이 엔진에 등록했고, 핸들러의 `c.HTML(http.StatusOK, "decks.html", gin.H{...})`은 그중 하나를 골라 데이터를 채워 그렸다.

== 점 하나로 시작한다

템플릿을 실행할 때 서버는 데이터를 하나 건네준다.
템플릿 안에서 점(`.`)은 "지금 건네받아 보고 있는 데이터"를 가리키고, 점 뒤에 이름을 이으면 그 데이터의 필드를 꺼낸다.
이 "지금 보고 있는 데이터"를 컨텍스트(context)라고 부르는데, AI 에이전트에게 말하는 컨텍스트와는 다른 뜻이다.

`flashcard-basic/templates/cards.html`의 첫머리로, 핸들러가 `gin.H{"Deck": deck, "Cards": cards}`로 넘긴 데이터에서 덱 하나를 꺼내 쓰는 부분이다.

[source,html]
----
<h1 class="title">{{.Deck.Name}}</h1>
<p class="nav">
  <a class="navlink" href="/">덱 목록</a>
  <a class="navlink" href="/decks/{{.Deck.ID}}/study">학습 시작</a>
</p>
----

`{{.Deck.Name}}`은 "지금 보고 있는 데이터에서 `Deck`을 꺼내고, 거기서 다시 `Name`을 꺼내 이 자리에 찍으라"는 뜻이다.
`{{.Deck.ID}}`로는 덱 번호가 채워진 `/decks/3/study` 같은 주소가 만들어진다.

`Deck`과 `Cards`는 핸들러가 `gin.H`에 적어 준 키이고, `Name`과 `ID`는 {ch-go-sqlite}에서 본 `Deck` 구조체의 필드 이름이다.
템플릿에서 꺼내려면 필드가 대문자로 시작해야 한다({ch-go-hello}의 공개와 비공개 규칙).

== 조건과 반복

값을 찍는 것 말고 템플릿이 하는 일은 조건 분기와 반복이다.

=== if로 갈래 만들기

학습 화면 `templates/study.html`은 카드가 있을 때와 없을 때 다른 것을 그린다.

[source,html]
----
{{if .Card}}
<!-- ... 카드 한 장을 그린다 ... -->
{{else}}
<p class="item-empty">카드가 없다. 카드 목록에서 먼저 카드를 추가한다.</p>
{{end}}
----

`{{if}}`, `{{else}}`, `{{end}}`는 여느 언어의 조건 분기와 같다.
Go 템플릿은 비어 있는 값(false, 0, nil, 그리고 길이가 0인 문자열·슬라이스·맵)을 거짓으로 치므로footnote:[https://pkg.go.dev/text/template#hdr-Actions[text/template 패키지 문서의 Actions 절]], `{{if .Card}}`는 "카드가 담겨 있으면"이라고 읽힌다.

이 문법에는 `>`나 `==` 같은 기호 연산자가 없어서, 비교도 이름 붙은 함수로 적고 비교할 값 둘을 그 뒤에 놓는다.
`{{if gt .Total 0}}`은 "`Total`(카드 총수)이 0보다 크면"이다.
`gt`(greater than), `lt`(less than), `eq`(equal), `and`, `not`이 모두 "함수 이름 뒤에 인자" 꼴이다.

=== range로 목록 돌기

`{{range}}`는 목록을 돌며 안쪽 내용을 반복해 그린다.
{ch-gin-hello}에서 본 `decks.html`의 덱 목록을 다시 보자.

[source,html]
----
include::../../flashcard-basic/templates/decks.html[tag=deck-list]
----

`range` 블록 안에서는 점이 바뀐다.
바깥에서 점은 화면 전체의 데이터지만, 반복 안에서는 지금 순서의 덱 하나라서 `{{.Name}}`만 써도 그 덱의 이름이 나온다.
`range`에 붙은 `{{else}}`는 조건 분기가 아니라 "목록이 비어 있을 때"를 맡는다.

`{{with .Deck}}`도 점을 바꾼다.
블록 안에서 점은 `.Deck`이 되고, `.Deck`이 비어 있으면 블록 전체를 건너뛴다.
조건을 확인하면서 그 값으로 점을 옮겨 준다는 것이 `if`와 다르다.

=== 변수와 주석

점이 바뀐 안쪽에서 바깥 값을 꺼내야 할 때는 `$`로 시작하는 변수를 쓴다.
`{{$deck := .Deck}}`처럼 이름을 붙여 두면 `range` 안에서도 `{{$deck.Name}}`으로 꺼낼 수 있고, `$` 하나만 쓰면 언제나 처음 건네받은 뿌리 데이터를 가리킨다.

HTML 주석(`<!-- -->`)은 결과 HTML에 실려 브라우저 개발자 도구에서 누구나 볼 수 있지만, `{{/* ... */}}`로 쓰는 템플릿 주석은 결과에 나오지 않고 서버에만 남는다.
화면에 드러나면 곤란한 설명은 템플릿 주석으로 적는다.

== 조각에 이름 붙이기

`templates/cards.html`의 카드 목록 부분은 덱 목록과 조금 다르다.

[source,html]
----
include::../../flashcard-basic/templates/cards.html[tag=card-list]
----

`{{range .Cards}}` 안에 HTML 대신 `{{template "card-item" .}}` 한 줄만 있다.
카드 한 줄의 HTML을 `templates/card-item.html`에 정의해 두고 불러 쓰는 것이다.

[source,html]
----
include::../../flashcard-basic/templates/card-item.html[tag=card-item]
----

위 코드는 그 파일의 가운데 토막이고, 실제 파일은 `{{define "card-item"}}`으로 시작해 `{{end}}`로 닫힌다.
`{{define "이름"}}`은 템플릿 덩어리에 이름을 붙이고, `{{template "이름" 데이터}}`는 그 덩어리를 이 자리에 그려 넣으라는 호출이다.
함수를 정의하고 호출하는 관계와 같다.

호출할 때 넘기는 마지막 인자가 그 안에서 점이 된다.
`{{template "card-item" .}}`의 점은 `range`가 돌고 있는 카드 하나라서, `card-item` 안의 `{{.Text}}`는 그 카드의 앞면이 된다.
이 인자를 빠뜨리면 에러 없이 안쪽의 점이 비어, `<li>` 같은 틀만 그려지고 앞면·뒷면 자리는 빈칸으로 남는다.

조각을 떼어 두면 카드 줄의 생김새를 바꿀 때 고칠 곳이 한 파일이 된다.
완성본은 이 방식을 레이아웃·페이지·조각 파일로 넓혀 상단 바, 하단 메뉴 같은 공통 마크업까지 이름 붙은 조각으로 관리한다({ch-html-template}).

경로에서 덱 번호를 꺼내 정수로 바꾸고, 그 덱이 있는지 확인하고, 폼에서 앞면과 뒷면을 꺼내 빈칸을 막고, 저장한 뒤 카드 목록 화면으로 돌려보낸다.
저장 전에 `GetDeck`으로 덱부터 확인하는 것은, 그러지 않으면 없는 덱 번호로 온 요청이 저장 단계에서 외래 키 위반 에러를 내고 404가 아닌 500으로 답하게 되기 때문이다.
마지막 줄의 `c.Redirect`는 {ch-gin-hello}에서 본 관례로, 새로고침이 같은 카드를 한 장 더 만드는 일을 막는다.

삭제 버튼은 `card-item.html`에 있는, 버튼 하나를 폼으로 감싼 것이다.

[source,html]
----
<form method="post" action="/decks/{{.DeckID}}/cards/{{.ID}}/delete">
  <button class="delete">지우기</button>
</form>
----

"3번 덱의 7번 카드를 지운다"는 뜻이 `/decks/3/cards/7/delete`라는 경로에 그대로 담겨 있어, 삭제한 뒤 어느 화면으로 돌려보낼지도 경로만 보면 안다.

핸들러는 경로에서 덱 번호와 카드 번호를 꺼내 카드를 지우고 그 덱의 카드 목록으로 돌려보낸다.

[source,go]
----
include::../../flashcard-basic/handlers.go[tag=delete-card]
----

덱 번호는 지우는 조건과 돌아갈 주소 양쪽에 쓰이므로, 다른 덱에 속한 카드 번호로는 아무것도 지워지지 않는다.

"지워 달라"는 뜻의 HTTP 메서드 DELETE가 따로 있는데도 POST를 쓴 것은 브라우저의 폼이 GET과 POST만 보낼 수 있기 때문이다.
완성본도 같은 이유로 화면에서 부르는 삭제는 POST로 두었고({ch-htmx}), 브라우저의 제약이 없는 JSON API의 삭제는 DELETE 메서드로 받는다.

지우기 버튼을 누르면 확인 없이 바로 지워진다.
"정말 지울까요?" 같은 확인 대화상자는 자바스크립트로 띄우는 것이라 이 앱에는 넣지 않았고, 완성본이 그것을 속성 하나로 붙이는 방법은 {ch-htmx}에서 본다.

== 학습 화면: 카드를 뒤집는다

라우팅 표의 마지막 줄은 앞면을 보고 답을 떠올린 뒤 뒤집어 확인하는 학습 화면이다.
`handlers.go`의 `showStudy`는 덱의 카드를 전부 꺼낸 뒤, 주소에 실려 온 순번이 가리키는 카드 한 장만 골라 화면에 넘긴다.

[source,go]
----
include::../../flashcard-basic/handlers.go[tag=show-study]
----

새로 나온 `c.DefaultQuery("i", "0")`은 주소 끝에 `?i=2`처럼 붙는 값, 곧 쿼리 파라미터(query parameter)를 꺼낸다.
경로 파라미터가 "어느 덱인가"처럼 자원을 지목한다면, 쿼리 파라미터는 "몇 번째부터인가" 같은 부가 조건을 싣는다.
값이 없으면 "0"으로 치므로, `/decks/1/study`로 처음 들어오면 첫 카드가, `?i=2`면 세 번째 카드가 나온다(순번은 0부터 센다).
범위를 벗어난 값은 첫 카드로 되돌리므로 주소에 어떤 값을 붙여도 화면이 깨지지 않는다.
`Next`에 담는 `(i + 1) % len(cards)`는 나머지 연산으로 다음 순번을 만들어, 마지막 카드 다음에는 처음으로 돌아간다.

화면은 `templates/study.html`이다.
카드 앞면을 접힌 제목으로, 뒷면을 그 안에 숨긴 내용으로 그리고, 다음 카드로 가는 링크를 둔다.

[source,html]
----
include::../../flashcard-basic/templates/study.html[tag=study-card]
----

`{{.Pos}} / {{.Total}}`은 지금이 몇 번째 카드인지 보여 준다(핸들러가 순번에 1을 더한 `Pos`와 카드 총수 `Total`을 넘겼다).
`details`와 `summary`는 브라우저에 내장된 접기·펼치기 요소다.
`summary`(앞면)를 누르면 `details`가 열리며 안의 `p`(뒷면)가 나타나고, 다시 누르면 접힌다.
여닫는 동작은 브라우저가 맡고, `static/style.css`는 열린 상태를 뜻하는 `.study[open]` 선택자({ch-css-hello})로 "(눌러서 뒷면 보기)" 안내 문구를 지우는 정도의 모양만 보탠다.

완성본의 학습 화면에는 카드가 뒤집히는 3차원 CSS 애니메이션과 채점 버튼, 채점 결과로 다음 복습 시각을 정하는 간격 반복 알고리즘이 더해진다(화면 구조는 {ch-html-css}, 알고리즘은 {ch-core-logic}).
그래도 "앞면을 먼저 보여 주고, 사용자의 동작 한 번에 뒷면을 연다"는 방식은 이 템플릿과 같다.

== 최소 앱 한 바퀴를 돌아보며

여기까지로 2부의 최소 앱을 한 바퀴 다 읽었다.
SQLite 파일이 데이터를 저장하고(`store.go`), Gin 서버가 요청을 받아 처리하고(`handlers.go`), html/template이 그 데이터를 화면으로 그린다(`templates/`).
Go 파일 셋과 템플릿, 스키마를 다 합쳐도 600줄 남짓이고, `go run .` 한 번이면 앱이 뜬다.

이 앱에는 자바스크립트가 한 줄도 없다.
화면 이동은 링크가, 값을 보내는 일은 폼이, 카드 뒤집기는 `details`가 맡았고, 전부 브라우저에 처음부터 들어 있는 기능이다.

대가는 폼을 제출할 때마다 서버가 페이지 전체를 새로 그려 보낸다는 것이다.
카드 한 장을 추가해도 브라우저는 화면 전체를 다시 받으므로, 화면이 깜빡이고 스크롤은 맨 위로 돌아가고 입력 칸의 커서도 사라진다.
카드를 연달아 스무 장 입력하는 사람에게는 성가신 일이다.
이 아쉬움을 자바스크립트를 직접 쓰지 않고 메우는 도구가 htmx이고, {ch-htmx}에서 다룬다.

이 세 층의 짜임은 완성본에서도 같고, 다른 것은 각 층의 두께다.
최소 앱에는 로그인, 간격 반복, 인터넷 배포, 앱을 통째로 띄워 확인하는 테스트({ch-app-tests})가 없다.
완성본의 코드는 3부가, 배포와 로그인은 4부가 읽는데, 코드가 아무리 커져도 요청을 받아 저장소를 다녀와 HTML로 답하는 이 구도는 바뀌지 않는다.

== 직접 해 보기

템플릿은 컴파일러가 지켜 주지 않으므로, 고칠 때마다 그 화면을 브라우저로 열어 확인한다.
서버는 시작할 때 템플릿을 한 번만 읽으므로({ch-gin-hello}의 릴리스 모드), 템플릿을 고쳤으면 `go run .`을 껐다 켠 뒤 확인한다.

. 덱 목록의 각 줄에 그 덱의 카드 장수를 함께 보여 준다. 핸들러가 템플릿에 넘기는 데이터에 그 수까지 담아야 하므로, 화면만 고쳐서는 끝나지 않는다는 것을 확인하게 된다.
. `{{.Name}}`을 `{{.Naem}}`으로 일부러 잘못 적고 `go build`를 돌린다. 빌드는 통과하고 화면을 열어야 오류가 드러난다. 템플릿이 컴파일러의 보호 밖에 있다는 말의 뜻이다.
. 되풀이되는 조각을 `{{define}}`으로 빼내고 `{{template}}`으로 불러 쓴다. `card-item.html`이 이미 그렇게 되어 있으니, 다른 화면에서 같은 방식으로 한 번 더 해 보면 된다.
. 덱 이름을 `<b>단어</b>`처럼 태그가 섞인 문자열로 만들어 목록을 연다. 굵은 글씨 대신 태그가 그대로 보일 텐데, html/template이 값을 글자로만 취급해 화면을 지키기 때문이다. 그 원리는 {ch-html-template}에서 다룬다.

== 에이전트 활용 아이디어

템플릿의 오타는 빌드가 잡지 못하므로, 에이전트에게 화면을 고치게 했다면 "바꾼 뒤 어느 주소를 열어 확인해야 하는지"를 목록으로 받아 두고 사람이 브라우저로 눌러 본다.

"이 폴더의 템플릿에서 두 번 이상 되풀이되는 HTML 덩어리를 찾아 `{{define}}` 조각으로 뺄 후보를 제안해 달라"고 하면 눈에 잘 띄지 않는 중복이 목록으로 올라온다.
다만 조각을 너무 잘게 쪼개면 화면 하나를 읽으려고 파일 다섯 개를 오가게 되므로, 판단은 사람이 한다.

"화면은 `templates/` 아래 파일로만 만들고 Go 코드에서 HTML 문자열을 이어 붙이지 않는다", "새 화면도 자바스크립트 없이 폼과 링크로 만든다"를 지침 파일에 적어 둔다.
그냥 두면 에이전트는 익숙한 방식대로 삭제 버튼에 `confirm()` 확인 창을 붙이거나, 폼 대신 `fetch`로 서버를 불러 목록을 다시 그리는 자바스크립트를 끼워 넣기 쉽다.

== 정리

첫째, 템플릿은 HTML 파일에 데이터가 들어갈 자리만 표시해 두고 요청마다 채워 그리는 방식이다.
Gin에서는 표준 라이브러리 html/template을 `LoadHTMLGlob`으로 읽어 두고 `c.HTML`로 그린다.

둘째, 점은 지금 보고 있는 데이터이고, `{{.Deck.Name}}`처럼 필드를 이어 꺼낸다.
`{{if}}`로 갈래를, `{{range}}`로 반복을 만들고, 둘 다 `{{else}}`로 빈 경우를 맡긴다.
`range`와 `with` 안에서는 점이 그 항목으로 바뀌고, `$`는 언제나 뿌리 데이터를 가리킨다.

셋째, `{{define "이름"}}`으로 화면 조각에 이름을 붙이고 `{{template "이름" 데이터}}`로 불러 쓰면 고칠 곳이 한 파일로 모인다.

넷째, 카드 추가와 삭제는 POST로 받아 처리한 뒤 목록 화면으로 돌려보내고, 삭제 주소에 덱 번호를 함께 실어 돌아갈 곳을 경로에 담았다.

다섯째, 카드 뒤집기는 브라우저 내장 `details`와 `summary`가, 카드 넘기기는 링크와 쿼리 파라미터가 맡아 이 앱의 자바스크립트는 0줄이다.

이것으로 2부가 끝났다.
기능이 늘어난 완성본은 코드를 어디에 어떻게 나눠 둘 것인가라는 새 질문에 답해야 한다.
다음 {ch-design-principles}에서 그 답의 원칙부터 읽고, 데이터에서 화면 순으로 완성본의 코드를 따라간다.
