= Go로 데이터 다루기: 구조체에서 인터페이스까지

{ch-go-hello}에서 다룬 값은 글자 하나, 숫자 하나처럼 모두 낱개였다.
그런데 프로그램이 다루는 것은 대개 묶음이다.
덱 하나에는 번호와 이름이 함께 있고, 카드 한 장에는 앞면과 뒷면이 함께 있다.

이 장에서는 값 여러 개를 한 덩어리로 합치는 구조체, 거기 동작을 붙이는 메서드, 원본을 건네는 포인터, 여러 개를 담는 슬라이스와 맵, 서로 다른 타입을 같은 코드로 다루는 인터페이스, 타입 자리를 나중에 채우는 제네릭을 차례로 익힌다.
예제는 {ch-go-hello}처럼 파일 하나로 실행되는 연습용 코드다.
여기까지 익히면 {ch-go-sqlite}부터 펼칠 앱 코드에서 처음 보는 문법을 만날 일이 드물고, 새로 나오는 문법은 그 자리에서 짚는다.

== 구조체: 값 여러 개를 한 덩어리로

=== 타입을 선언한다

덱의 번호와 이름을 변수 두 개로 따로 두면, 덱이 두 개만 되어도 이름이 넷으로 늘고 함수에 넘길 때마다 인자 두 개를 나란히 적어야 한다.
이럴 때 쓰는 것이 구조체다.

[source,go]
----
type Deck struct {
	ID   int64
	Name string
}
----

`type 이름 struct { ... }`가 새 타입을 만드는 선언이다.
중괄호 안에 담을 값마다 이름과 타입을 한 줄씩 적는데, 이 각각을 필드라고 부른다.
이제 `Deck`은 `string`이나 `int`처럼 하나의 타입이 되어, 변수에 담고 함수에 넘기고 반환값으로 돌려받을 수 있다.

`int64`는 크기를 8바이트로 못 박은 정수다.
데이터베이스가 행마다 붙여 주는 번호를 받아 오는 표준 라이브러리 메서드 `LastInsertId()`가 `int64`를 돌려주기 때문에 이 타입을 쓴다({ch-go-sqlite}).
이 `Deck`은 최소 앱의 `store.go`에 그대로 들어 있는 구조체이고, 그 파일의 필드 옆에 붙은 백틱 표기는 {ch-go-sqlite}에서 짚는다.

.[용어 풀이] 구조체(struct)
[NOTE]
====
여러 값에 각각 이름표를 붙여 하나로 합친 데이터 꾸러미다.
덱 하나의 정보를 변수 두 개로 따로 넘기는 대신 `Deck`이라는 상자 하나에 담아 함께 다룬다.
서류 양식의 빈칸들처럼 각 칸(필드)마다 이름과 담을 값의 종류가 정해져 있다.
====

필드 이름이 대문자로 시작하는 것은 {ch-go-hello}에서 본 대로 패키지 밖으로 공개하기 위해서다.

=== 값을 만들고 필드를 읽고 쓴다

선언한 타입으로 실제 값을 만들어 보자.

[source,go]
----
d := Deck{Name: "토익 필수 단어"}
fmt.Println(d.ID, d.Name)

d.Name = "토익 필수 단어 2026"
fmt.Printf("%+v\n", d)
----

[source,text]
----
0 토익 필수 단어
{ID:0 Name:토익 필수 단어 2026}
----

`Deck{Name: "토익 필수 단어"}`처럼 필드 이름을 적고 콜론 뒤에 값을 주어 구조체 값을 만든다.
필드는 점을 찍어 읽고(`d.Name`), 같은 방식으로 고친다(`d.Name = ...`).
`%+v`는 구조체를 필드 이름까지 함께 찍는 자리 표시라 디버깅에서 자주 쓴다.

`ID`를 지정하지 않았는데 0이 들어간 것은 제로값이 구조체에도 그대로 적용되기 때문이다.
아무것도 지정하지 않아도 된다.

[source,go]
----
var empty Deck
fmt.Printf("%+v\n", empty)
----

[source,text]
----
{ID:0 Name:}
----

번호가 0인 것에는 뜻이 있다.
아직 저장하지 않은 덱에는 번호가 없고, 데이터베이스에 넣는 순간 번호가 붙는다({ch-go-sqlite}).
제로값이 곧 쓸 수 있는 초기 상태가 되도록 타입을 설계하는 것이 Go다운 방식이고, {ch-core-logic}에서 읽을 구조체가 이 성질을 이용한다.

== 메서드: 타입에 딸린 함수

구조체의 값을 가지고 무언가를 하는 함수는 그 타입에 붙여 둘 수 있다.

[source,go]
----
func (d Deck) Label() string {
	return fmt.Sprintf("%d번 덱: %s", d.ID, d.Name)
}
----

`func`와 함수 이름 사이의 괄호 `(d Deck)`을 리시버라고 한다.
"이 함수는 `Deck` 타입에 딸려 있으며 그 값을 `d`라는 이름으로 받는다"는 뜻이고, 이렇게 타입에 딸린 함수를 메서드라고 부른다.
`fmt.Sprintf`는 `Printf`와 같은 자리 표시를 쓰되, 화면에 찍는 대신 완성된 문자열을 돌려준다.

부를 때는 `fmt.Println`에서 봤던 것처럼 값 뒤에 점을 찍는다.

[source,go]
----
d := Deck{ID: 3, Name: "토익 필수 단어"}
fmt.Println(d.Label())
----

[source,text]
----
3번 덱: 토익 필수 단어
----

.[용어 풀이] 메서드와 리시버(Method·Receiver)
[NOTE]
====
특정 타입에 딸린 함수를 메서드라고 하고, 함수 이름 앞 괄호에 적어 그 타입의 값을 건네받는 변수를 리시버라고 한다.
`func (d Deck) Label() string`은 "`Deck` 값 하나를 `d`라는 이름으로 받아 일하는 `Label` 메서드"라고 읽는다.
물건에 직접 달린 버튼처럼, 값과 그 값을 다루는 동작을 한자리에 둔다.
{ch-gin}에서 HTTP 요청에 쓰는 "메서드"(GET, POST)는 이름만 같고 다른 것이다.
====

관련된 동작이 타입 옆에 모이므로, 코드가 늘어날수록 흩어진 함수 `label(d)`보다 `d.Label()`이 찾기 쉽다.

== 포인터: 원본을 건네는 방법

=== 복사본과 원본

Go에서 함수에 값을 넘기면 그 값이 복사되어 전달된다.
구조체도 마찬가지라, 함수 안에서 필드를 고쳐도 부른 쪽의 원본은 그대로다.

[source,go]
----
func renameCopy(d Deck) {
	d.Name = "바뀐 이름"
}

func main() {
	d := Deck{Name: "토익 필수 단어"}
	renameCopy(d)
	fmt.Println(d.Name)
}
----

[source,text]
----
토익 필수 단어
----

원본을 고치게 하려면 값이 아니라 그 값이 놓인 자리를 알려 줘야 하고, 그 자리를 담는 값이 포인터다.

.[용어 풀이] 포인터(Pointer)
[NOTE]
====
값 자체가 아니라 그 값이 저장된 위치(주소)를 담는 변수다.
집을 통째로 옮기는 대신 주소를 적은 쪽지를 건네는 것과 같아서, 쪽지를 받은 쪽은 그 주소로 찾아가 원본을 고칠 수 있다.
아무 곳도 가리키지 않는 빈 쪽지 상태는 `nil`로 표현한다.
====

`&x`는 변수 `x`의 주소를 얻고, 포인터 `p`가 있을 때 `*p`는 그 주소에 있는 값을 뜻한다.
타입 이름 앞에 붙은 `*`(예: `*Deck`)는 "그 타입의 값을 가리키는 포인터"라는 표기다.

[source,go]
----
func rename(d *Deck) {
	d.Name = "바뀐 이름"
}

func main() {
	d := Deck{Name: "토익 필수 단어"}
	rename(&d)
	fmt.Println(d.Name)
}
----

[source,text]
----
바뀐 이름
----

매개변수 타입이 `*Deck`으로 바뀌었고, 부를 때 `&d`로 주소를 넘겨 원본이 바뀌었다.
포인터로 필드에 접근할 때는 Go가 알아서 주소를 따라가 주므로 `d.Name`에 `*`를 붙이지 않는다.
최소 앱에서는 저장소 메서드들이 `(s *Store)`로 저장소를 포인터로 받는 데서 이 문법을 다시 만난다({ch-go-sqlite}).

기본 자료형으로 보면 동작이 더 분명하다.

[source,go]
----
n := 3
p := &n
fmt.Println(*p)
*p = 10
fmt.Println(n)
----

[source,text]
----
3
10
----

`p`는 `n`이 놓인 자리를 가리키고, `*p = 10`은 그 자리에 10을 넣으라는 뜻이라 `n`이 10으로 바뀐다.

=== 수정 의도를 드러내는 포인터 리시버

같은 이유로, 값을 고치는 메서드는 리시버를 포인터로 받는다.

[source,go]
----
func (d *Deck) Rename(name string) {
	d.Name = name
}

func main() {
	d := Deck{ID: 3, Name: "토익 필수 단어"}
	d.Rename("토익 필수 단어 2026")
	fmt.Println(d.Label())
}
----

[source,text]
----
3번 덱: 토익 필수 단어 2026
----

리시버가 `(d *Deck)`이므로 `d.Name = name`이 원본을 고친다.
`d`가 포인터가 아닌데도 `d.Rename(...)`이라고 쓸 수 있는 것은 Go가 필요한 주소를 알아서 넘겨주기 때문이다.

포인터 리시버는 "이 메서드는 값을 바꾼다"는 신호도 되어, 선언 한 줄만 봐도 원본을 건드리는지 읽기만 하는지 알 수 있다.
{ch-core-logic}에서 읽을 스마트 덱 규칙 검증 메서드 `(r *Rule) Validate()`는 검증하면서 빠진 값에 기본값을 채워 넣기 때문에 포인터 리시버를 쓴다.

=== 없음을 나타내는 nil

포인터는 "값이 없음"을 표현하는 데도 쓴다.

[source,go]
----
var missing *Deck
fmt.Println(missing == nil)
----

[source,text]
----
true
----

`Deck`의 제로값은 "모든 칸이 빈 덱"이지만 `*Deck`의 제로값은 아무 곳도 가리키지 않는 `nil`, 곧 "덱이 아예 없음"이라 둘은 다른 상태다.
이 구별은 {ch-database-basics}에서 배울 데이터베이스의 NULL을 받을 때 필요하다.
설명이 빈 문자열인 덱과 설명을 적지 않은 덱을 구별하려면 `string`이 아니라 `*string`으로 받는 식이고, Flashcard에서는 덱의 `Description`과 카드의 `Phonetic`·`Example`·`Notes`가 그렇게 선언되어 있다({ch-core-logic}).

`nil` 포인터에 담긴 값을 읽으려 하면 프로그램이 그 자리에서 멈추므로, 값이 없을 수 있는 포인터는 쓰기 전에 `if p != nil`로 확인한다.

== 슬라이스와 맵

같은 종류의 값을 여러 개 담는 방법은 순서대로 담는 슬라이스와 열쇠로 찾는 맵 두 가지다.

.[용어 풀이] 슬라이스와 맵(Slice·Map)
[NOTE]
====
슬라이스는 같은 종류의 값을 순서대로 담는 가변 길이 목록이고, 맵은 열쇠(키)로 값을 찾는 저장소다.
슬라이스가 번호 순서대로 꺼내는 물품 보관함이라면, 맵은 이름표를 보고 곧장 여는 사물함이다.
`[]string`이 문자열 슬라이스이고, `map[string]int`는 문자열 열쇠마다 정수를 붙여 둔 맵이다.
====

=== 슬라이스

[source,go]
----
words := []string{"apple", "banana"}
words = append(words, "cherry")
fmt.Println(len(words), words[0], words)
----

[source,text]
----
3 apple [apple banana cherry]
----

`[]string{...}`이 문자열 슬라이스를 만드는 표기다.
`len`으로 길이를 재고, `words[0]`처럼 대괄호에 순번을 적어 하나를 꺼내는데, 순번은 0부터 시작한다.

원소를 덧붙이는 `append`에서 초보자가 자주 걸려 넘어진다.
`append`는 슬라이스를 그 자리에서 늘리지 않고 덧붙인 결과를 새 슬라이스로 돌려주므로, `words = append(...)`처럼 결과를 반드시 다시 받아야 한다(받지 않으면 컴파일러가 거부한다).
슬라이스는 값을 직접 품은 통이 아니라, 값이 담긴 창고의 위치와 쓰는 칸 수(길이), 전체 칸 수(용량)를 적은 쪽지다.
`append`는 창고에 자리가 남으면 거기 덧붙이고 가득 찼으면 더 큰 창고로 옮겨 담는데, 어느 쪽이든 원래 쪽지 `words`에는 길이 2가 그대로 적혀 있다.

차례로 읽을 때는 {ch-go-hello}에서 본 `range`를 쓴다.

[source,go]
----
for i, w := range words {
	fmt.Println(i, w)
}
----

[source,text]
----
0 apple
1 banana
2 cherry
----

담을 개수를 미리 알면 자리를 예약해 둘 수 있다.

[source,go]
----
picked := make([]string, 0, len(words))
for _, w := range words {
	if len(w) <= 5 {
		picked = append(picked, w)
	}
}
fmt.Println(picked)
----

[source,text]
----
[apple]
----

`make`는 크기를 지정해 슬라이스나 맵을 만드는 내장 함수다.
`make([]string, 0, len(words))`는 길이 0, 용량 3, 즉 비었지만 세 개 들어갈 자리를 예약한 슬라이스를 만들어, 이어지는 `append`가 옮겨 담는 일 없이 예약된 자리를 채우게 한다.
{ch-core-logic}에서 볼 카드 정렬 함수 `SortCardsByIDOrder`가 `make([]Card, 0, len(cards))`로 이 패턴을 쓴다.

=== 맵

맵은 열쇠와 값의 짝을 담는다.

[source,go]
----
wrong := map[string]int{"apple": 3}
wrong["banana"] = 1
wrong["apple"]++
fmt.Println(wrong["apple"], len(wrong))
----

[source,text]
----
4 2
----

`map[string]int`는 "문자열을 열쇠로 정수를 찾는 맵"이라고 읽는다.
대괄호에 열쇠를 적어 값을 넣고 꺼내며, `len`은 담긴 짝의 개수를, `delete(wrong, "banana")`는 짝 하나를 지운다.

없는 열쇠를 읽으면 어떻게 될까.

[source,go]
----
n, ok := wrong["cherry"]
fmt.Println(n, ok)
----

[source,text]
----
0 false
----

에러 없이 제로값 0이 나온다.
그러면 "틀린 횟수가 0인 카드"와 "기록이 없는 카드"를 구별할 수 없으므로, 맵을 조회할 때는 열쇠가 실제로 있었는지를 두 번째 값으로 받을 수 있다.
그 값을 `ok`라는 이름으로 받는 관례가 있어 이 표기를 comma-ok(콤마 오케이) 관용구라고 부르고, `if n, ok := wrong["cherry"]; ok { ... }`처럼 초기화문 딸린 `if`와 함께 쓰는 것이 보통이다.

맵의 순회 순서는 정해져 있지 않아 `range`로 돌 때마다 다를 수 있으므로, 순서가 중요하면 슬라이스를 함께 쓴다.

== 인터페이스: 할 줄 아는 일로 분류한다

`Deck` 말고 카드 한 장을 나타내는 타입도 있다고 하자.
둘 다 "화면에 읽어 줄 문장"을 내놓을 수 있다면, 그 문장을 출력하는 코드는 상대가 덱인지 카드인지 몰라도 된다.
이 "할 줄 아는 일의 목록"을 타입으로 적어 둔 것이 인터페이스다.

[source,go]
----
type Labeler interface {
	Label() string
}
----

`Labeler`는 "`Label()`이라는 메서드가 있고 문자열을 돌려준다"는 조건 하나만 적어 둔 타입이고, `Deck`은 앞 절의 `Label` 메서드로 이 조건을 이미 만족한다.
카드 쪽도 만들어 보자.
앞뒷면 필드 이름은 최소 앱의 `Card` 구조체에서 가져왔다(실제 코드에는 카드 번호와 덱 번호 필드가 둘 더 있다).

[source,go]
----
type Card struct {
	Text    string
	Meaning string
}

func (c Card) Label() string {
	return c.Text + " / " + c.Meaning
}
----

`Deck`과 `Card` 어디에도 "나는 `Labeler`다"라고 적지 않았다.
자바의 `implements Labeler`나 C#의 `: Labeler`처럼 많은 언어는 타입 쪽에 그 선언을 요구하지만, Go에서는 메서드가 조건에 맞으면 그것으로 끝이다.
이를 암묵적 구현이라고 부른다.

.[용어 풀이] 인터페이스(interface)
[NOTE]
====
"이런 메서드들을 할 줄 아는 무엇"이라고 능력만 적어 둔 타입이다.
함수가 구체적인 타입 대신 인터페이스를 받으면, 그 조건을 만족하는 값은 무엇이든 넘길 수 있다.
콘센트 규격을 정해 두면 어느 회사 제품이든 꽂히는 것과 같아서, 쓰는 쪽과 만드는 쪽이 서로를 몰라도 된다.
====

인터페이스를 받는 함수는 이렇게 쓴다.

[source,go]
----
func announce(l Labeler) {
	fmt.Println("읽어 줍니다:", l.Label())
}

func main() {
	announce(Card{Text: "apple", Meaning: "사과"})
	announce(Deck{ID: 3, Name: "토익 필수 단어"})
}
----

[source,text]
----
읽어 줍니다: apple / 사과
읽어 줍니다: 3번 덱: 토익 필수 단어
----

`announce`는 오직 "`Label()`을 부를 수 있다"만 알므로, 세 번째 타입이 생겨도 고칠 것이 없다.

Flashcard는 내 컴퓨터에서는 SQLite 파일에, 배포된 환경에서는 PostgreSQL에 데이터를 담는다.
화면과 API 코드는 어느 쪽인지 모른 채 "저장소가 할 줄 아는 일"의 목록인 `model.Store` 인터페이스에만 의지하고, 프로그램이 시작할 때 SQLite 구현(`litestore`)과 PostgreSQL 구현(`pgstore`) 중 하나를 골라 끼운다.
테스트에서 가짜 저장소를 끼워 넣을 수 있는 것도 이 덕분이다({ch-app-assembly}).

== 제네릭: 타입을 나중에 정한다

인터페이스가 "할 줄 아는 일"로 서로 다른 타입을 같은 부류로 묶는다면, 제네릭(generics)은 타입 자리를 빈칸으로 비워 두는 문법이다.

=== 같은 코드가 두 번 나올 때

목록의 첫 원소를 돌려주되, 비어 있으면 제로값을 돌려주는 함수를 만든다고 하자.

[source,go]
----
func firstString(items []string) string {
	if len(items) == 0 {
		return ""
	}
	return items[0]
}

func firstInt(items []int) int {
	if len(items) == 0 {
		return 0
	}
	return items[0]
}
----

두 함수는 다루는 타입만 다르고 하는 일이 똑같아서, `[]float64`가 필요해지면 세 번째 함수를 또 쓰게 된다.
이렇게 담는 값의 종류만 다른 코드가 반복될 때 쓰는 문법이 제네릭이다.

=== 타입 매개변수

[source,go]
----
func first[T any](items []T) T {
	var zero T
	if len(items) == 0 {
		return zero
	}
	return items[0]
}
----

함수 이름 뒤의 대괄호 `[T any]`에서 `T`는 "부를 때 정할 타입"이라는 빈칸이고, `any`는 "어떤 타입이든 들어올 수 있다"는 조건이다.
빈칸에 이름을 붙여 두었으므로 매개변수 타입(`[]T`)과 반환 타입(`T`)에서 그 이름을 쓸 수 있다.
`var zero T`는 `T`가 무엇인지 모르는 채로 그 타입의 제로값을 얻는 표기로, `T`가 `string`이면 빈 문자열, `int`면 0이 된다.

부르는 쪽은 평범하다.

[source,go]
----
fmt.Println(first([]string{"apple", "banana"}))
fmt.Println(first([]int{}))
----

[source,text]
----
apple
0
----

`first[string](...)`처럼 타입을 적을 수도 있지만, 대개는 넘긴 값을 보고 컴파일러가 알아낸다({ch-go-hello}의 타입 추론).

=== 무엇이든 받으면 무엇도 할 수 없다

어떤 타입이든 받는다는 것은 그 값으로 할 수 있는 일이 없다는 뜻이기도 하다.
`T`가 무엇인지 모르니 더할 수도, 비교할 수도 없다.
그래서 값을 실제로 다루려면 빈칸에 조건을 걸어야 하는데, 그 조건도 인터페이스로 적는다.
이때의 인터페이스에는 메서드 대신 "이 빈칸에 올 수 있는 타입"을 나열한다.

[source,go]
----
type Number interface {
	int | float64
}

func sum[T Number](items []T) T {
	var total T
	for _, v := range items {
		total += v
	}
	return total
}
----

`int | float64`는 "정수이거나 실수인 타입"이라는 뜻이고, `T`가 둘 중 하나로 좁혀졌으므로 `total += v`처럼 더하기를 쓸 수 있다.
이렇게 타입 매개변수에 거는 조건을 제약(constraint)이라고 부른다.

[source,go]
----
fmt.Println(sum([]int{1, 2, 3}), sum([]float64{0.5, 2.5}))
----

[source,text]
----
6 3
----

.[용어 풀이] 제네릭(Generic)
[NOTE]
====
타입을 나중에 정하도록 비워 둔 채로 함수나 타입을 쓰는 문법이다.
`[T any]`의 `T`가 그 빈칸이고, `first([]string{...})`처럼 부르면 문자열로, `first([]int{...})`처럼 부르면 정수로 채워진다.
담는 값의 종류만 다른 함수를 종류마다 한 벌씩 쓰는 대신 하나로 끝내며, 더하거나 비교해야 하면 제약을 걸어 타입을 좁힌다.
====

=== 언제 쓰지 않는가

Go는 2009년에 공개됐는데 제네릭은 2022년 1.18 버전에서야 추가됐고, 그 13년 동안 제네릭 없이도 쓸 만한 프로그램이 얼마든지 만들어졌다.
그래서 통념은 "같은 코드가 두세 번 반복되는 것을 눈으로 확인하기 전에는 쓰지 않는다"이다.
타입 매개변수가 붙는 순간 함수 선언이 읽기 어려워지고 제약을 설계하는 일이 새로 생긴다.
실제로 나타난 반복을 걷어내는 데 쓰면 제값을 하지만, 나중에 필요할지 모른다는 이유로 미리 일반화하면 어려움만 남는다.

Flashcard의 제네릭 함수 `collect`는 두 저장소에서 쿼리 결과를 한 행씩 읽어 슬라이스에 담는 똑같은 코드를 걷어 낸 것으로, 스무 곳이 넘는 자리에서 부른다({ch-core-logic}).

== 직접 해 보기

이 장의 예제들을 파일 하나에 옮겨 담고 고쳐 보자.
`go run .` 한 번이면 결과를 확인할 수 있다.

. `Card`에 예문을 담을 필드를 더하고, `Label` 메서드가 그 값까지 보여 주도록 고친다. 필드를 더했는데 `Label`을 고치지 않아도 컴파일은 통과한다는 것도 확인해 두자. 컴파일러가 잡아 주는 실수와 잡아 주지 못하는 실수의 경계다.
. `Rename` 메서드의 리시버를 `*Deck`에서 `Deck`으로 바꾸고 실행한다. 이름이 바뀌지 않을 텐데, 왜 그런지를 이 장의 포인터 절에 비추어 설명할 수 있으면 된다.
. `Labeler`를 만족하는 새 타입을 하나 만들어 `announce`에 넘긴다. 인터페이스에 이름을 등록하는 절차 없이, `Label` 메서드를 갖추기만 하면 통과한다는 것이 Go 인터페이스의 성격이다.
. 덱 이름을 키로, 카드 장수를 값으로 담는 맵을 만들어 출력한다. 맵을 그냥 돌면 순서가 매번 달라지는 것도 확인해 보자.

== 에이전트 활용 아이디어

"필요할 때까지 일반화하지 말라"를 지시문에 적어 둔다.
그냥 두면 에이전트는 인터페이스를 미리 뽑고 제네릭까지 얹은 구조를 곧잘 제안한다.
"구현이 둘 이상 생기기 전에는 인터페이스를 만들지 말라"처럼 조건을 붙여 두면 결과가 달라진다.

리시버 선택은 기존 코드에 맞추게 한다.
값 리시버와 포인터 리시버가 한 타입 안에서 섞이면 읽는 사람이 매번 확인해야 하므로, "기존 메서드들이 어떤 리시버를 쓰는지 확인하고 맞춰 달라"고 덧붙인다.

헷갈리는 동작은 작은 프로그램으로 확인한다.
슬라이스를 함수에 넘겼을 때 원본이 바뀌는지, 맵의 순회 순서가 정말 매번 다른지 같은 질문은 20줄짜리 예제를 만들어 실행해 보게 하면 금방 끝난다.

== 정리

첫째, 구조체는 값 여러 개에 이름표를 붙여 한 덩어리로 합친 타입이고, 채우지 않은 필드는 제로값에서 출발한다.

둘째, 메서드는 리시버로 값을 받는 타입에 딸린 함수다.
값 리시버는 복사본을 받고, 포인터 리시버는 원본을 고친다.

셋째, 포인터는 값이 놓인 자리를 담아 원본을 고치게 하고(`&d`), 값의 부재를 표현한다(`nil`).

넷째, 여러 개를 담는 도구는 슬라이스와 맵이다.
`append`의 결과는 다시 받고, 맵에 열쇠가 있었는지는 comma-ok로 확인한다.

다섯째, 인터페이스는 "할 줄 아는 일"만 적어 둔 타입이고, Go에서는 메서드가 맞으면 선언 없이 만족한다.

여섯째, 제네릭은 타입 자리를 빈칸으로 두는 문법이고, 반복을 눈으로 확인한 뒤에 꺼내 드는 도구다.

다음 {ch-database-basics}에서는 2부의 마지막 언어인 SQL로 넘어가, 데이터가 결국 저장되는 데이터베이스와 대화하는 법을 작은 연습부터 익힌다.
