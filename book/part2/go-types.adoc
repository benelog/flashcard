= Go로 데이터 다루기: 구조체, 슬라이스와 맵

{ch-go-hello}에서 다룬 값은 모두 낱개였다.
글자 하나, 숫자 하나, 참거짓 하나다.
그런데 실제로 프로그램이 다루는 것은 대개 묶음이다.
카드 한 장에는 앞면과 뒷면과 틀린 횟수가 함께 있고, 덱 하나에는 카드가 여러 장 들어 있다.

이 장에서는 그 묶음을 다루는 문법을 익힌다.
값 여러 개에 이름표를 붙여 한 덩어리로 묶는 구조체, 그 덩어리에 동작을 붙이는 메서드, 원본을 건네는 포인터, 같은 것을 여러 개 담는 슬라이스와 맵, 서로 다른 타입을 같은 코드로 다루는 인터페이스, 그리고 타입 자리를 나중에 채우는 제네릭이 차례로 나온다.
{ch-go-hello}과 마찬가지로 예제는 모두 앱과 분리된 연습용 코드이고, 파일 하나로 실행된다.

이 여섯 가지가 Go 코드를 읽는 데 필요한 문법의 마지막 묶음이다.
여기까지 익히면 {ch-code-map}부터 펼칠 Flashcard의 실제 코드에서 처음 보는 문법을 만날 일이 거의 없다.

== 구조체: 값 여러 개를 한 덩어리로

=== 타입을 선언한다

카드 한 장을 프로그램에서 다룬다고 해 보자.
앞면, 뒷면, 틀린 횟수를 변수 세 개로 따로 두면 카드가 두 장만 되어도 이름이 여섯 개로 늘고, 함수에 넘길 때마다 셋을 함께 들고 다녀야 한다.
이럴 때 쓰는 것이 구조체다.

[source,go]
----
type Card struct {
	Front string
	Back  string
	Wrong int
}
----

`type 이름 struct { ... }`가 새 타입을 만드는 선언이다.
중괄호 안에 담을 값마다 이름과 타입을 한 줄씩 적는데, 이 각각을 필드라고 부른다.
이제 `Card`는 `string`이나 `int`처럼 하나의 타입이 되어, 변수에 담고, 함수에 넘기고, 반환값으로 돌려받을 수 있다.

.[용어 풀이] 구조체(struct)
[NOTE]
====
여러 값에 각각 이름표를 붙여 하나로 묶은 데이터 꾸러미다.
카드 한 장의 상태를 "앞면·뒷면·틀린 횟수"로 따로 들고 다니는 대신, `Card`라는 상자 하나에 담아 함께 다룬다.
서류 양식의 빈칸들처럼 각 칸(필드)마다 이름과 담을 값의 종류가 정해져 있다.
====

필드 이름이 대문자로 시작한 것에도 뜻이 있다.
{ch-go-hello}에서 본 대로 대문자로 시작하는 이름은 패키지 밖으로 공개된다.
`Front`를 소문자 `front`로 두면 이 패키지 안에서만 읽고 쓸 수 있다.

=== 값을 만들고 필드를 읽고 쓴다

선언한 타입으로 실제 값을 만들어 보자.

[source,go]
----
c := Card{Front: "apple", Back: "사과"}
fmt.Println(c.Front, c.Back, c.Wrong)

c.Wrong++
fmt.Printf("%+v\n", c)
----

[source,text]
----
apple 사과 0
{Front:apple Back:사과 Wrong:1}
----

`Card{Front: "apple", Back: "사과"}`가 구조체 값을 만드는 표기다.
필드 이름을 적고 콜론 뒤에 값을 준다.
만든 값의 필드는 점을 찍어 읽고(`c.Front`), 같은 방식으로 고친다(`c.Wrong++`).

`%+v`는 구조체를 통째로 찍을 때 쓰는 자리 표시로, 필드 이름까지 함께 보여 준다.
값이 어떻게 채워졌는지 확인하기 좋아서, 디버깅에서 자주 쓴다.

여기서 `Wrong`을 지정하지 않았는데 0이 들어간 것을 눈여겨보자.
{ch-go-hello}에서 본 제로값이 구조체에도 그대로 적용되어, 적지 않은 필드는 타입별 기본값으로 채워진다.
아예 아무것도 지정하지 않아도 된다.

[source,go]
----
var empty Card
fmt.Printf("%+v\n", empty)
----

[source,text]
----
{Front: Back: Wrong:0}
----

문자열 두 개는 빈 문자열이고 정수는 0이다.
{ch-go}에서 읽을 Flashcard의 학습 상태 구조체는 이 성질을 적극적으로 이용한다.
"아직 한 번도 복습하지 않은 카드"의 연속 정답 횟수와 복습 간격이 마침 0이어서, 값을 채우지 않은 상태가 그대로 올바른 초기 상태가 된다.
제로값이 곧 쓸 수 있는 초기 상태가 되도록 타입을 설계하는 것이 Go다운 방식이다.

== 메서드: 타입에 딸린 함수

구조체에 담긴 값을 가지고 무언가를 하는 함수는 그 타입에 붙여 둘 수 있다.

[source,go]
----
func (c Card) Label() string {
	return c.Front + " / " + c.Back
}
----

`func`와 함수 이름 사이에 괄호가 하나 더 있는 것이 보통 함수와 다르다.
이 괄호에 적은 `(c Card)`를 리시버라고 하고, "이 함수는 `Card` 타입에 딸려 있으며 그 값을 `c`라는 이름으로 받는다"는 뜻이다.
이렇게 타입에 딸린 함수를 메서드라고 부른다.

부를 때는 값 뒤에 점을 찍는다.
`fmt.Println`에서 봤던 그 점과 같은 표기다.

[source,go]
----
c := Card{Front: "apple", Back: "사과"}
fmt.Println(c.Label())
----

[source,text]
----
apple / 사과
----

.[용어 풀이] 메서드와 리시버(Method·Receiver)
[NOTE]
====
특정 타입에 딸린 함수를 메서드라고 하고, 함수 이름 앞 괄호에 적어 그 타입의 값을 건네받는 변수를 리시버라고 한다.
`func (c Card) Label() string`은 "`Card` 값 하나를 `c`라는 이름으로 받아 일하는 `Label` 메서드"라고 읽는다.
설명서에 적힌 사용법이 아니라 물건에 직접 달린 버튼처럼, 값과 그 값을 다루는 동작을 한자리에 묶어 두는 장치다.
{ch-gin}에서 HTTP 요청에 쓰는 "메서드"(GET, POST)는 이름만 같고 다른 것이다.
====

메서드로 두면 좋은 점은 관련된 동작이 타입 옆에 모인다는 것이다.
카드를 다루는 코드가 늘어날수록 `label(c)`, `isNew(c)`처럼 흩어진 함수보다 `c.Label()`, `c.IsNew()`가 찾기 쉽다.

== 포인터: 원본을 건네는 방법

=== 복사본과 원본

Go에서 함수에 값을 넘기면 그 값이 복사되어 전달된다.
이 규칙이 구조체에도 그대로 적용되므로, 함수 안에서 필드를 고쳐도 부른 쪽의 원본은 그대로다.

[source,go]
----
func renameCopy(c Card) {
	c.Front = "바뀐 앞면"
}

func main() {
	c := Card{Front: "apple", Back: "사과"}
	renameCopy(c)
	fmt.Println(c.Front)
}
----

[source,text]
----
apple
----

`renameCopy`가 고친 것은 복사본이라 원본은 `apple` 그대로다.
원본을 고치게 하려면 값이 아니라 그 값이 놓인 자리를 알려 줘야 한다.
그 자리를 담는 값이 포인터다.

.[용어 풀이] 포인터(Pointer)
[NOTE]
====
값 자체가 아니라 그 값이 저장된 위치(주소)를 담는 변수다.
집을 통째로 옮기는 대신 집 주소를 적은 쪽지를 건네는 것과 같아서, 쪽지를 받은 쪽은 그 주소로 찾아가 원본 집을 고칠 수 있다.
아무 곳도 가리키지 않는 빈 쪽지 상태는 `nil`로 표현한다.
====

문법은 기호 두 개가 전부다.
`&x`는 변수 `x`의 주소를 얻고, 포인터 `p`가 있을 때 `*p`는 그 주소에 있는 값을 뜻한다.
타입 이름 앞에 붙은 `*`(예: `*Card`)는 "그 타입의 값을 가리키는 포인터"라는 표기다.

[source,go]
----
func rename(c *Card) {
	c.Front = "바뀐 앞면"
}

func main() {
	c := Card{Front: "apple", Back: "사과"}
	rename(&c)
	fmt.Println(c.Front)
}
----

[source,text]
----
바뀐 앞면
----

매개변수 타입이 `*Card`로 바뀌었고, 부를 때 `&c`로 주소를 넘겼다.
이번에는 원본이 바뀌었다.
`c.Front`를 읽고 쓸 때 `*`를 따로 붙이지 않은 것도 눈여겨보자.
포인터를 통해 필드에 접근할 때는 Go가 알아서 주소를 따라가 주므로, 사람이 적어야 하는 곳은 주소를 얻는 `&` 쪽뿐이다.

기본 자료형으로 보면 동작이 더 분명하다.

[source,go]
----
n := 3
p := &n
fmt.Println(*p)
*p = 10
fmt.Println(n)
----

[source,text]
----
3
10
----

`p`는 `n`이 놓인 자리를 가리키고, `*p = 10`은 그 자리에 10을 넣으라는 뜻이다.
그래서 `n`이 10으로 바뀐다.

=== 수정 의도를 드러내는 포인터 리시버

메서드의 리시버도 포인터로 받을 수 있고, 이유는 같다.
값을 고치는 메서드는 포인터 리시버를 쓴다.

[source,go]
----
func (c *Card) MarkWrong() {
	c.Wrong++
}

func main() {
	c := Card{Front: "apple", Back: "사과"}
	c.MarkWrong()
	c.MarkWrong()
	fmt.Println(c.Wrong)
}
----

[source,text]
----
2
----

리시버가 `(c Card)`가 아니라 `(c *Card)`이므로 `c.Wrong++`가 원본을 고친다.
부르는 쪽 모양이 값 리시버일 때와 똑같다는 점도 눈여겨볼 만하다.
`c`가 포인터가 아닌데도 `c.MarkWrong()`이라고 쓸 수 있는 것은, Go가 필요한 주소를 알아서 넘겨 주기 때문이다.

여기서 얻는 것은 편리함만이 아니다.
포인터 리시버는 "이 메서드는 값을 바꾼다"는 신호가 되므로, 선언 한 줄만 봐도 그 메서드가 원본을 건드리는지 읽기만 하는지 알 수 있다.
{ch-go}에서 읽을 Flashcard의 규칙 검증 메서드가 정확히 이 경우로, 검증하면서 빠진 값에 기본값을 채워 넣기 때문에 포인터 리시버를 쓴다.

=== 없음을 나타내는 nil

포인터의 또 다른 쓰임은 "값이 없음"을 표현하는 것이다.

[source,go]
----
var missing *Card
fmt.Println(missing == nil)
----

[source,text]
----
true
----

포인터의 제로값은 `nil`, 즉 아무 곳도 가리키지 않는 상태다.
`Card` 값의 제로값은 "모든 칸이 빈 카드"이지만 `*Card`의 제로값은 "카드가 아예 없음"이라, 이 둘은 다른 상태를 표현한다.
{ch-database-basics}에서 배울 데이터베이스의 NULL을 Go 쪽에서 받을 때 이 구별이 필요해진다.
설명이 빈 문자열인 덱과 설명을 적지 않은 덱을 구별해야 하면 `string`이 아니라 `*string`으로 받는 식이고, {ch-go}에서 실제 코드로 확인한다.

`nil` 포인터에 담긴 값을 읽으려 하면 프로그램이 그 자리에서 멈춘다.
그래서 값이 없을 수 있는 포인터는 쓰기 전에 `if p != nil`로 확인하는 것이 관례다.

== 슬라이스와 맵

같은 종류의 값을 여러 개 담는 방법은 두 가지다.
순서대로 담는 슬라이스와, 열쇠로 찾는 맵이다.

.[용어 풀이] 슬라이스와 맵(Slice·Map)
[NOTE]
====
슬라이스는 같은 종류의 값을 순서대로 담는 가변 길이 목록이고, 맵은 열쇠(키)로 값을 찾는 저장소다.
슬라이스가 번호 순서대로 꺼내는 물품 보관함이라면, 맵은 이름표를 보고 곧장 여는 사물함이다.
`[]string`이 문자열 슬라이스이고, `map[string]int`는 문자열 열쇠마다 정수를 붙여 둔 맵이다.
처음부터 끝까지 훑어야 하는 목록에는 슬라이스를, 열쇠 하나로 곧장 찾아야 하는 조회에는 맵을 쓴다.
====

=== 슬라이스

[source,go]
----
words := []string{"apple", "banana"}
words = append(words, "cherry")
fmt.Println(len(words), words[0], words)
----

[source,text]
----
3 apple [apple banana cherry]
----

`[]string{...}`이 문자열 슬라이스를 만드는 표기다.
`len`으로 길이를 재고, `words[0]`처럼 대괄호에 순번을 적어 하나를 꺼낸다.
순번은 1이 아니라 0부터 시작한다.

원소를 덧붙이는 것은 `append`인데, 여기에 Go 초보자가 자주 걸려 넘어지는 부분이 있다.
`append(words, "cherry")`라고만 쓰면 안 되고 `words = append(...)`처럼 결과를 반드시 다시 받아야 한다.
슬라이스의 실체는 "값들이 실제로 담긴 저장 공간의 위치, 현재 길이, 최대 용량"을 담은 작은 값이기 때문이다.
`append`는 자리가 남으면 그 자리에 덧붙이지만, 가득 찼으면 더 큰 공간을 새로 마련해 기존 원소를 옮겨 담고 그 새 공간을 가리키는 슬라이스를 돌려준다.
어느 쪽이 일어날지는 부르는 쪽에서 알 수 없으므로, 반환값을 다시 받지 않으면 새 공간으로 옮겨 간 경우의 추가분을 잃어버린다.

훑는 것은 {ch-go-hello}에서 본 `range`다.

[source,go]
----
for i, w := range words {
	fmt.Println(i, w)
}
----

[source,text]
----
0 apple
1 banana
2 cherry
----

담을 개수를 미리 알면 자리를 예약해 둘 수 있다.

[source,go]
----
picked := make([]string, 0, len(words))
for _, w := range words {
	if len(w) <= 5 {
		picked = append(picked, w)
	}
}
fmt.Println(picked)
----

[source,text]
----
[apple]
----

`make`는 크기를 지정해 슬라이스나 맵을 만드는 내장 함수다.
`make([]string, 0, len(words))`는 길이 0, 용량 3인 슬라이스, 즉 아직 비었지만 세 개 들어갈 자리를 예약해 둔 슬라이스를 만든다.
이러면 이어지는 `append`가 예약된 자리를 채우기만 하므로, 더 큰 공간으로 옮겨 담는 일이 일어나지 않는다.
{ch-go}에서 볼 Flashcard의 카드 정렬 코드가 정확히 이 패턴을 쓴다.

=== 맵

맵은 열쇠와 값의 짝을 담는다.

[source,go]
----
wrong := map[string]int{"apple": 3}
wrong["banana"] = 1
wrong["apple"]++
fmt.Println(wrong["apple"], len(wrong))
----

[source,text]
----
4 2
----

`map[string]int`는 "문자열을 열쇠로 정수를 찾는 맵"이라고 읽는다.
대괄호에 열쇠를 적어 값을 넣고 꺼내며, `len`은 담긴 짝의 개수를 준다.
지우려면 `delete(wrong, "banana")`를 쓴다.

없는 열쇠를 읽으면 어떻게 될까.

[source,go]
----
n, ok := wrong["cherry"]
fmt.Println(n, ok)
----

[source,text]
----
0 false
----

에러가 나지 않고 제로값 0이 나온다.
그런데 이러면 "틀린 횟수가 0인 카드"와 "아예 기록이 없는 카드"를 구별할 수 없다.
그래서 맵 조회는 값과 함께 "그 열쇠가 실제로 있었는지"를 두 번째 값으로 받을 수 있고, 이 관용구를 comma-ok라고 부른다.
`if n, ok := wrong[key]; ok { ... }` 형태로 {ch-go-hello}에서 본 초기화문 딸린 `if`와 함께 쓰는 것이 보통이다.

맵의 순회 순서는 정해져 있지 않다는 것도 알아 두자.
같은 맵을 `range`로 두 번 훑으면 순서가 다를 수 있으므로, 순서가 중요하면 슬라이스를 함께 쓴다.

== 인터페이스: 할 줄 아는 일로 묶는다

지금까지 만든 `Card`와, 덱을 나타내는 다른 타입이 있다고 하자.
둘 다 "화면에 읽어 줄 문장"을 내놓을 수 있다면, 그 문장을 받아 출력하는 코드는 상대가 카드인지 덱인지 몰라도 된다.
이 "할 줄 아는 일의 목록"을 타입으로 적어 둔 것이 인터페이스다.

[source,go]
----
type Speaker interface {
	Text() string
}
----

`Speaker`는 "`Text()`라는 메서드가 있고 문자열을 돌려준다"는 조건 하나만 적어 둔 타입이다.
이제 그 조건을 만족하는 타입을 두 개 만들어 보자.

[source,go]
----
type Card struct {
	Front string
}

func (c Card) Text() string {
	return c.Front
}

type Deck struct {
	Name  string
	Count int
}

func (d Deck) Text() string {
	return fmt.Sprintf("%s 덱, 카드 %d장", d.Name, d.Count)
}
----

`fmt.Sprintf`는 `Printf`와 같은 자리 표시를 쓰되 화면에 찍는 대신 완성된 문자열을 돌려주는 함수다.

여기서 Go의 특징이 드러난다.
`Card`와 `Deck` 어디에도 "나는 `Speaker`다"라고 적지 않았다.
자바나 C#은 `implements Speaker`처럼 선언해야 하지만, Go는 메서드가 조건에 맞으면 그것으로 끝이다.
이렇게 선언 없이 자동으로 만족하는 방식을 암묵적 구현이라고 부른다.

.[용어 풀이] 인터페이스(interface)
[NOTE]
====
"이런 메서드들을 할 줄 아는 무엇"이라고 능력만 적어 둔 타입이다.
구체적인 타입 대신 인터페이스를 받도록 함수를 쓰면, 그 조건을 만족하는 값이면 무엇이든 넘길 수 있다.
콘센트 규격을 정해 두면 어느 회사 제품이든 꽂히는 것과 같아서, 쓰는 쪽과 만드는 쪽이 서로를 몰라도 된다.
Go에서는 "나는 이 인터페이스를 구현한다"고 선언할 필요가 없고, 메서드 이름과 모양이 맞으면 자동으로 만족한다.
====

인터페이스를 받는 함수는 이렇게 쓴다.

[source,go]
----
func announce(s Speaker) {
	fmt.Println("읽어 줍니다:", s.Text())
}

func main() {
	announce(Card{Front: "apple"})
	announce(Deck{Name: "토익 필수 단어", Count: 8})
}
----

[source,text]
----
읽어 줍니다: apple
읽어 줍니다: 토익 필수 단어 덱, 카드 8장
----

`announce`는 카드도 덱도 모르고, 오직 "`Text()`를 부를 수 있다"만 안다.
그래서 나중에 세 번째 타입이 생겨도 `announce`는 고칠 것이 없다.

이 문법이 이 앱의 구조를 지탱한다.
Flashcard는 데이터를 저장하는 방법이 두 가지다.
내 컴퓨터에서는 SQLite 파일에, 배포된 환경에서는 PostgreSQL에 담는다.
화면과 API를 만드는 코드는 둘 중 어느 쪽인지 모른 채 "저장소가 할 줄 아는 일"의 목록에만 의지하고, 프로그램이 시작할 때 실제 구현을 하나 골라 끼운다.
저장소를 통째로 바꿔도 화면 코드를 고치지 않아도 되는 이유이고, 테스트에서 가짜 저장소를 끼워 넣을 수 있는 이유이기도 하다.
그 실물은 {ch-gin}에서 다룬다.

== 제네릭: 타입을 나중에 정한다

인터페이스가 "할 줄 아는 일"로 서로 다른 타입을 묶는다면, 제네릭(generics)은 타입 자리를 아예 빈칸으로 비워 두는 문법이다.
이 장의 마지막 문법으로 이것을 익힌다.

=== 같은 코드가 두 번 나올 때

목록의 첫 원소를 돌려주는 함수를 만든다고 하자.
비어 있으면 제로값을 돌려주기로 한다.

[source,go]
----
func firstString(items []string) string {
	if len(items) == 0 {
		return ""
	}
	return items[0]
}

func firstInt(items []int) int {
	if len(items) == 0 {
		return 0
	}
	return items[0]
}
----

두 함수는 다루는 타입만 다르고 하는 일이 똑같다.
`[]float64`가 필요해지면 세 번째 함수를 또 쓰게 된다.
이렇게 "담는 값의 종류만 다르고 나머지가 같은" 코드가 반복될 때 쓰는 문법이 제네릭이다.

=== 타입 매개변수

[source,go]
----
func first[T any](items []T) T {
	var zero T
	if len(items) == 0 {
		return zero
	}
	return items[0]
}
----

함수 이름 뒤의 대괄호 `[T any]`가 새로 등장한 부분이다.
`T`는 "지금은 정하지 않고 부를 때 정할 타입"이라는 빈칸이고, `any`는 "어떤 타입이든 들어올 수 있다"는 조건이다.
빈칸에 이름을 붙여 두었으므로 매개변수 타입(`[]T`)과 반환 타입(`T`)에서 그 이름을 쓸 수 있다.

`var zero T`도 눈여겨보자.
`T`가 무엇인지 모르는 채로 그 타입의 제로값이 필요할 때 쓰는 표기다.
`T`가 `string`이면 빈 문자열, `int`면 0이 된다.

부르는 쪽은 평범하다.

[source,go]
----
fmt.Println(first([]string{"apple", "banana"}))
fmt.Println(first([]int{}))
----

[source,text]
----
apple
0
----

`first[string](...)`처럼 타입을 적을 수도 있지만, 대개는 넘긴 값을 보고 컴파일러가 알아낸다.
{ch-go-hello}에서 본 타입 추론이 여기서도 일한다.

=== 무엇이든 받으면 무엇도 할 수 없다

`any`에는 함정이 하나 있다.
어떤 타입이든 받는다는 것은 그 값으로 할 수 있는 일이 없다는 뜻이기도 하다.
`T`가 무엇인지 모르니 더할 수도, 비교할 수도 없다.
그래서 값을 실제로 다루려면 빈칸에 조건을 걸어야 하고, 그 조건을 적는 것도 인터페이스다.

[source,go]
----
type Number interface {
	int | float64
}

func sum[T Number](items []T) T {
	var total T
	for _, v := range items {
		total += v
	}
	return total
}
----

`int | float64`는 "정수이거나 실수인 타입"이라는 뜻이다.
`T`가 둘 중 하나로 좁혀졌으므로 `total += v`처럼 더하기를 쓸 수 있다.
이렇게 타입 매개변수에 걸어 두는 조건을 제약(constraint)이라고 부른다.

[source,go]
----
fmt.Println(sum([]int{1, 2, 3}), sum([]float64{0.5, 2.5}))
----

[source,text]
----
6 3
----

.[용어 풀이] 제네릭(Generic)
[NOTE]
====
타입을 나중에 정하도록 비워 둔 채로 함수나 타입을 쓰는 문법이다.
`[T any]`의 `T`가 그 빈칸이고, `first([]string{...})`처럼 부르면 문자열로, `first([]int{...})`처럼 부르면 정수로 채워진다.
담는 값의 종류만 다르고 나머지가 똑같은 함수가 여럿일 때, 같은 코드를 종류마다 한 벌씩 쓰는 대신 하나로 끝낼 수 있다.
빈칸을 `any`로 두면 그 값으로 할 수 있는 일도 없어지므로, 더하거나 비교해야 하면 제약을 걸어 타입을 좁힌다.
====

=== 언제 쓰지 않는가

제네릭은 Go에 늦게 들어온 문법이다.
언어가 2009년에 공개됐는데 제네릭은 2022년 1.18 버전에서야 추가됐다.
그 사이에 쓸 만한 코드가 없었느냐 하면 그렇지 않았고, 이 사실이 제네릭을 대하는 태도를 정한다.

통념은 "같은 코드가 두세 번 반복되는 것을 눈으로 확인하기 전에는 쓰지 않는다"이다.
타입 매개변수가 하나 붙는 순간 함수 선언이 읽기 어려워지고, 제약을 설계하는 일이 새 과제로 생긴다.
반복이 실제로 나타났을 때 그것을 걷어 내는 데 쓰면 제값을 하지만, 나중에 필요할지 모른다는 이유로 미리 일반화하면 얻는 것 없이 어려움만 남는다.

Flashcard에도 제네릭 함수가 하나 있는데, 여덟 곳에 똑같이 반복되던 코드를 확인한 뒤에 만든 것이다.
그 코드는 {ch-go}에서 읽는다.

== 에이전트 활용 아이디어

이 장의 문법은 에이전트가 특히 과하게 쓰기 쉬운 영역이라, 방향을 정해 두는 편이 낫다.

"필요할 때까지 일반화하지 말라"를 지시문에 적어 둘 만하다.
그냥 두면 에이전트는 인터페이스를 미리 뽑고 제네릭까지 얹은 구조를 곧잘 제안한다.
타입 하나뿐인 인터페이스와 한 번만 부르는 제네릭 함수는 읽는 사람에게 비용만 남기므로, "구현이 둘 이상 생기기 전에는 인터페이스를 만들지 말라"처럼 조건을 붙여 두면 결과가 달라진다.

값 리시버와 포인터 리시버의 선택은 물어보게 하는 편이 좋다.
"이 메서드가 원본을 고치는가"를 기준으로 정해야 하는데, 한 타입 안에서 둘이 섞이면 읽는 사람이 매번 확인해야 한다.
"기존 메서드들이 어떤 리시버를 쓰는지 확인하고 맞춰 달라"고 덧붙이면 저장소 안의 일관성이 유지된다.

문법이 헷갈릴 때는 {ch-go-hello}에서와 마찬가지로 작은 프로그램으로 확인한다.
슬라이스를 함수에 넘겼을 때 원본이 바뀌는지, 맵의 순회 순서가 정말 매번 다른지 같은 질문은 20줄짜리 예제를 만들어 실행해 보면 5초 만에 끝난다.

== 정리

첫째, 구조체는 값 여러 개에 이름표를 붙여 한 덩어리로 묶은 타입이다.
채우지 않은 필드는 제로값에서 출발하므로, 제로값이 곧 올바른 초기 상태가 되도록 설계하면 초기화 코드가 줄어든다.

둘째, 메서드는 타입에 딸린 함수이고 리시버로 값을 받는다.
값 리시버는 복사본을 받아 원본을 건드리지 않고, 포인터 리시버는 원본을 고친다.
선언 한 줄이 그 차이를 드러낸다.

셋째, 포인터는 값이 놓인 자리를 담는다.
원본을 고치게 하고(`&c`), 값의 부재를 표현한다(`nil`).

넷째, 여러 개를 담는 도구는 슬라이스와 맵이다.
`append`는 결과를 반드시 다시 받고, 개수를 미리 알면 `make`로 자리를 예약하며, 맵에 열쇠가 있었는지는 comma-ok로 확인한다.

다섯째, 인터페이스는 "할 줄 아는 일"만 적어 둔 타입이고, Go에서는 메서드가 맞으면 선언 없이 자동으로 만족한다.

여섯째, 제네릭은 타입 자리를 빈칸으로 두는 문법이다.
같은 코드가 타입만 바꿔 가며 반복되는 것을 눈으로 확인한 뒤에 꺼내 드는 도구다.

여기까지 낱개의 값부터 값의 묶음, 그리고 타입을 비워 두는 문법까지 Go의 기초를 익혔다.
다음 {ch-database-basics}에서는 2부의 마지막 언어인 SQL로 넘어간다.
화면이 보여 주고 서버가 다루는 데이터가 결국 저장되는 곳은 데이터베이스다.
그 데이터베이스와 대화하는 언어도 지금까지처럼 작은 연습부터 익혀 보자.
