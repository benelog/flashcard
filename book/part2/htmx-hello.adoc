= htmx 첫걸음: 새로고침 없이 화면 일부만 바꾼다

{ch-gin-hello}는 아쉬움 하나를 남기며 끝났다.
폼을 제출할 때마다 서버가 페이지 전체를 새로 그려 보낸다는 것이다.
카드 한 장을 추가하면 목록 끝에 한 줄이 늘어날 뿐인데, 브라우저는 리다이렉트를 따라가 화면 전체를 다시 받는다.
그 사이에 화면이 깜빡이고, 스크롤은 맨 위로 돌아가고, 입력 칸에 있던 커서도 사라진다.
카드를 연달아 스무 장 입력하는 사람에게는 성가신 일이다.

이번 장에서는 이 문제를 htmx(에이치티엠엑스)로 푼다.
카드 추가와 삭제를 새로고침 없이 만들고, {ch-gin-hello}에서 남겨 둔 마지막 라우팅인 학습 화면까지 얹어 2부의 최소 앱을 완성한다.

htmx에서 익힐 핵심은 하나다.
HTML 속성 몇 개로 "어디에 요청을 보내 어느 부분을 바꿀지"를 선언하면, 서버가 돌려준 HTML 조각으로 화면 일부만 바뀐다는 것이다.
완성본 앱이 htmx로 만드는 화면들(검색, 사전 자동 채우기, 학습 진행)은 {ch-htmx}에서 해부하고, 여기서는 이 개념 하나를 카드 추가와 삭제로 익힌다.
서버는 {ch-gin-hello}에서 했던 대로 `flashcard-basic` 폴더에서 `go run .`으로 띄워 두고, 직접 눌러 보며 읽기를 권한다.

== 화면 일부만 바꾸는 라이브러리

브라우저의 기본 동작에서 화면은 페이지 단위로 바뀐다.
링크를 누르거나 폼을 제출하면 새 페이지를 통째로 받아 처음부터 다시 그린다.
페이지를 떠나지 않고 서버와 주고받으려면 자바스크립트가 필요하다.
이렇게 화면 뒤에서 요청을 보내는 기법을 비동기 요청(AJAX)이라고 부른다.
직접 하려면 버튼에 자바스크립트로 반응을 걸고, 요청을 보내고, 응답을 받아 화면에서 바꿀 요소를 찾아 갈아 끼우는 코드를 짜야 한다.

htmx는 그 코드를 미리 다 써 둔 자바스크립트 라이브러리다.
우리가 자바스크립트를 쓰는 것이 아니라, `hx-`로 시작하는 HTML 속성으로 "어디에 요청을 보내고 응답을 어디에 넣을지"를 적어 두면 htmx가 그대로 수행한다.
서버가 돌려주는 것도 JSON이 아니라 HTML 조각(fragment)이다.
페이지 한 장을 그릴 줄 아는 서버라면 그 일부인 조각도 그릴 수 있으므로, {ch-gin-hello}까지 만든 서버에 더할 것이 거의 없다.
화면을 그리는 곳은 여전히 서버의 템플릿 한 곳이다.

새로고침 없는 화면을 만드는 다른 길로, React 같은 프레임워크로 화면 전체를 브라우저에서 그리는 SPA가 있다.
이 책이 그 길 대신 서버 렌더링과 htmx를 고른 이유는 {ch-tech-choices}에서 정리했다.
여기서 짚어 둘 것은 비용이다.
htmx는 파일 하나를 불러오면 준비가 끝나고, npm 같은 빌드 도구도, 새로 배울 언어도 필요 없다.

== 준비는 script 한 줄

htmx를 켜는 곳은 `flashcard-basic/templates/cards.html`의 head다.
다음 한 줄이 htmx 라이브러리 파일을 불러온다.

[source,html]
----
include::../../flashcard-basic/templates/cards.html[tag=htmx-script]
----

`defer`는 문서를 다 읽은 뒤에 스크립트를 실행하라는 속성이다.
`htmx.min.js`는 50KB 남짓한 파일 하나이고, CSS와 같은 자리인 `flashcard-basic/static/` 폴더에 들어 있다.
{ch-gin-hello}에서 본 `Static("/static", "./static")` 등록 덕분에 브라우저가 이 주소로 파일을 받아 간다.

htmx 공식 문서의 예제는 이 파일을 외부 배포 서버(CDN)의 주소로 불러온다.
이 앱은 그 대신 파일을 한 번 내려받아 저장소에 함께 두었다.
남의 서버가 멈추거나 주소가 바뀌어도 이 앱은 영향을 받지 않고, 인터넷이 끊긴 자리에서도 로컬 서버가 온전히 돈다.
파일 하나를 복사해 둔 것이 설치의 전부다.

== 카드 추가를 부분 갱신으로

응답이 들어갈 자리부터 확인하자.
`templates/cards.html`의 카드 목록이다.
덱에 든 카드를 하나씩 돌며 한 줄씩 그리는, {ch-gin-hello}의 덱 목록과 같은 구조다.

[source,html]
----
include::../../flashcard-basic/templates/cards.html[tag=card-list]
----

새 문법은 `{{template "card-item" .}}` 하나다.
카드 한 줄의 HTML을 `card-item`이라는 이름으로 딴 파일에 정의해 두고, 여기서 카드마다 한 번씩 불러 그린다(그 파일은 다음 절에서 본다).
지금 기억할 것은 목록에 `id="cards"`라는 이름표가 붙어 있다는 점이다.

그 아래에 카드 추가 폼이 있다.
{ch-gin-hello}의 덱 만들기 폼과 같은 모양인데, `hx-`로 시작하는 속성 세 개가 더 붙었다.

[source,html]
----
include::../../flashcard-basic/templates/cards.html[tag=card-form]
----

세 속성이 질문 하나씩을 맡는다.

`hx-post`는 "어디로 보내는가"다.
이 폼이 제출되면 페이지를 이동하는 대신 화면 뒤에서 이 주소로 POST 요청을 보낸다.
입력 칸의 값이 함께 실려 가는 것은 일반 폼 제출과 같다.

`hx-target`은 "응답을 어디에 넣는가"다.
`#cards`는 {ch-css-hello}에서 본 CSS 선택자 표기로, id가 `cards`인 요소, 즉 위의 카드 목록을 가리킨다.

`hx-swap`은 "어떻게 넣는가"다.
`beforeend`는 대상의 내용 끝에 덧붙이라는 뜻이다.
지정하지 않으면 대상의 내용을 통째로 갈아 끼우는데(`innerHTML`), 여기서는 목록을 다시 그리는 것이 아니라 끝에 한 줄 보태는 것이므로 `beforeend`를 골랐다.

`method`와 `action`이 지워지지 않고 그대로 남아 있는 것도 눈여겨보자.
htmx가 어떤 이유로든 없으면(파일을 아직 못 불러왔거나, 스크립트를 꺼 둔 브라우저이거나) 이 폼은 {ch-gin-hello}에서 본 일반 폼으로 제출되고, 앱은 전체 페이지 방식으로 여전히 동작한다.
기본 동작을 그대로 두고 그 위에 더 나은 경험을 얹는 이 접근을 점진적 향상(progressive enhancement)이라고 부른다.

== 서버는 페이지 대신 조각을 돌려준다

속성만으로는 절반이다.
htmx가 보낸 요청에 서버가 페이지 전체를 돌려주면, 목록 끝에 페이지 전체가 통째로 끼어드는 우스운 화면이 된다.
서버도 조각을 돌려줄 준비가 필요하다.
`flashcard-basic/handlers.go`의 카드 추가 핸들러다.
폼 값을 검사해 카드를 저장한 뒤, htmx 요청에는 새 카드 한 줄짜리 HTML 조각을, 일반 폼 제출에는 리다이렉트를 돌려준다.

[source,go]
----
include::../../flashcard-basic/handlers.go[tag=create-card]
----

덱 번호 확인과 빈칸 검사까지는 {ch-gin-hello}에서 읽은 핸들러들의 리듬 그대로다.
달라진 것은 응답을 만드는 마지막 부분이다.
htmx는 자신이 보내는 모든 요청에 `HX-Request: true`라는 HTTP 헤더를 붙인다.
헤더는 요청과 응답의 본문과는 별도로 딸려 가는 부가 정보 칸이다.
핸들러는 이 헤더가 있으면 `c.HTML`로 `card-item` 템플릿 하나만 그려 돌려주고, 없으면(일반 폼 제출이면) {ch-gin-hello}의 덱 만들기처럼 리다이렉트로 답한다.
주소 하나가 두 종류의 손님을 다 받는다.

그 `card-item` 템플릿이 `templates/card-item.html`이다.
카드 한 장을 목록의 한 줄로 그린다.

[source,html]
----
include::../../flashcard-basic/templates/card-item.html[tag=card-item]
----

`{{define "card-item"}}`이 이 HTML에 이름을 붙이는 문법이다.
이름 덕분에 이 템플릿은 두 자리에서 재사용된다.
카드 목록 화면을 처음 그릴 때도 카드마다 이것으로 그리고, htmx에 조각 하나를 돌려줄 때도 이것으로 그린다.
정의가 하나뿐이므로 새로 추가된 카드는 목록의 기존 줄과 똑같이 생기고, 카드 줄의 생김새를 바꿀 일이 생겨도 이 파일 하나만 고치면 두 자리가 함께 바뀐다.

이제 흐름이 이어졌다.
"카드 추가"를 누르면 htmx가 화면 뒤에서 POST를 보내고, 서버가 `<li>` 한 덩이를 돌려주고, htmx가 그것을 `#cards` 끝에 덧붙인다.
페이지 이동이 없으니 화면은 깜빡이지 않고, 스크롤과 커서는 제자리에 남는다.
서버를 띄워 두었다면 직접 카드를 넣어 보자.
목록 끝에 새 줄이 소리 없이 나타난다.

== 삭제도 속성으로 끝난다

{ch-gin-hello}의 라우팅 표에는 폼이 보낼 수 없다던 요청이 하나 있었다.
`DELETE /cards/:id`다.
그 발신인이 htmx다.
방금 인용한 `card-item.html`의 지우기 버튼에 그 속성들이 붙어 있다.

`hx-delete`는 `hx-post`의 형제로, DELETE 메서드로 요청을 보낸다.
폼은 GET과 POST만 알지만, htmx는 "지워 달라"는 뜻의 DELETE를 비롯한 다른 메서드도 보낼 수 있다.

`hx-target`의 값은 이번에는 선택자가 아니라 `closest li`다.
버튼에서 출발해 가장 가까운 바깥 `li`, 즉 버튼이 들어 있는 그 카드 줄을 가리키는 htmx 표기다.
카드가 몇 장이든 줄마다 id를 붙일 필요 없이, 눌린 버튼이 알아서 자기 줄을 찾는다.

`hx-swap="outerHTML"`은 대상의 내용이 아니라 대상 요소 자체를 응답으로 바꾸라는 뜻이다.
마지막의 `hx-confirm`은 요청을 보내기 전에 브라우저 확인 대화상자를 띄워 한 번 묻는다.
지운 카드를 되살릴 방법이 없는 앱이라, 묻는 단계 하나를 속성 하나로 세웠다.

받는 쪽은 `handlers.go`의 삭제 핸들러다.
카드를 지우고, 본문 없는 200 응답으로 답한다.

[source,go]
----
include::../../flashcard-basic/handlers.go[tag=delete-card]
----

이 응답이 마지막 조각이다.
성공 응답에 본문이 없으면 htmx는 대상을 빈 내용으로 바꾼다.
`outerHTML`이라 요소 자체가 빈 것으로 바뀌므로, 그 카드 줄이 화면에서 사라진다.
데이터베이스의 삭제와 화면의 삭제가 요청 한 번으로 함께 끝났다.

한 가지는 짚어 두어야 공평하다.
추가 폼과 달리 이 버튼에는 물러설 기본 동작이 없다.
폼이 아니어서, htmx가 없으면 눌러도 아무 일도 일어나지 않는다.
버튼마다 한 줄짜리 폼을 씌우면 점진적 향상을 지킬 수 있지만, 이 최소 앱은 코드를 줄이는 쪽을 골랐다.

== 학습 화면: 자바스크립트 없이 카드를 뒤집는다

이제 {ch-gin-hello}의 라우팅 표에서 남은 마지막 줄, 학습 화면이다.
암기 카드의 핵심 동작은 앞면을 보고 답을 떠올린 뒤, 뒤집어 확인하는 것이다.
이 뒤집기는 자바스크립트 없이, 이번에는 htmx조차 없이 만든다.

서버부터 보자.
`handlers.go`의 학습 화면 핸들러다.
덱의 카드를 전부 꺼낸 뒤, 주소에 실려 온 순번이 가리키는 카드 한 장만 골라 화면에 넘긴다.

[source,go]
----
include::../../flashcard-basic/handlers.go[tag=show-study]
----

새로 나온 것은 `c.DefaultQuery("i", "0")`이다.
주소 끝에 `?i=2`처럼 붙는 값을 쿼리 파라미터(query parameter)라고 한다.
{ch-gin-hello}에서 본 경로 파라미터가 "어느 덱인가"처럼 자원을 지목한다면, 쿼리 파라미터는 "몇 번째부터인가" 같은 부가 조건을 싣는 자리다.
`DefaultQuery`는 그 값을 꺼내되 없으면 "0"으로 친다.
그래서 `/decks/1/study`로 처음 들어오면 첫 카드가 나오고, `?i=2`면 세 번째 카드가 나온다(순번은 0부터 센다).
범위를 벗어난 값은 첫 카드로 되돌리므로 주소에 어떤 값을 붙여도 화면이 깨지지 않는다.

`Next`에 담는 `(i + 1) % len(cards)`는 나머지 연산으로 다음 순번을 만든다.
마지막 카드에서는 나머지가 0이 되어 처음으로 돌아가므로, 덱을 끝없이 도는 순환이 된다.

화면은 `templates/study.html`이다.
카드 앞면을 접힌 제목으로, 뒷면을 그 안에 숨긴 내용으로 그리고, 다음 카드로 가는 링크를 둔다.

[source,html]
----
include::../../flashcard-basic/templates/study.html[tag=study-card]
----

`details`와 `summary`는 브라우저에 내장된 접기·펼치기 요소다.
`summary`(앞면)를 누르면 `details`가 열리며 안에 있던 `p`(뒷면)가 나타나고, 다시 누르면 접힌다.
여닫는 동작은 브라우저가 처음부터 할 줄 아는 일이라, 우리는 요소를 배치만 했다.
`static/style.css`는 모양만 보탠다.
앞면 옆에 "(눌러서 뒷면 보기)"라는 안내 문구를 붙였다가, 열린 상태를 뜻하는 `.study[open]` 선택자로 열린 뒤에는 지우는 정도다.

"다음 카드"가 htmx가 아니라 일반 링크인 것에도 뜻이 있다.
학습 화면은 화면의 중심이 카드 하나뿐이라, 일부만 바꾸는 것과 전체를 새로 받는 것의 차이가 작다.
부분 갱신이 체감되는 자리(목록에 줄이 늘고 주는 곳)에만 htmx를 쓰고, 나머지는 브라우저 기본 동작에 맡기는 것이 이 도구를 쓰는 요령이다.

완성본 앱의 학습 화면은 여기서 몇 걸음 더 나아간다.
카드가 뒤집히는 3차원 CSS 애니메이션이 있고, 맞았는지 틀렸는지 채점하는 버튼이 있고, 채점 결과로 다음 복습 시각을 정하는 간격 반복 알고리즘이 뒤에 있다.
그 화면 구조는 {ch-html-css}에서, 알고리즘은 {ch-go}에서 읽는다.
그러나 "앞면을 먼저 보이고, 사용자의 동작 한 번에 뒷면을 연다"는 뼈대는 이 스무 줄과 같다.

== 최소 앱이 완성됐다

여기까지로 2부의 최소 앱이 완성됐다.
층을 세어 보자.
SQLite 파일이 데이터를 저장하고({ch-go-sqlite}의 `store.go`), Gin 서버가 요청을 받아 처리하고({ch-gin-hello}의 `handlers.go`), html/template이 화면을 그리고(`templates/`), htmx가 그 화면의 일부를 새로고침 없이 바꾼다(이 장).
Go 코드와 템플릿을 다 합쳐 몇백 줄, `go run .` 한 번으로 뜨는 앱이다.

이 네 층의 짜임은 완성본 앱에서도 같다.
완성본과의 차이는 층의 종류가 아니라 층마다의 두께다.
로그인이 없고, 틀린 카드를 더 자주 보여 주는 간격 반복이 없고, 인터넷에 공개하는 배포가 없고, 앱을 통째로 띄워 확인하는 테스트({ch-app-tests})가 없다.
간격 반복을 비롯한 완성본의 코드는 3부가, 배포와 로그인은 4부가 채운다.
그때 만나는 코드가 아무리 커져도, 요청을 받아 저장소를 다녀와 HTML로 답하는 이 구도 위에 있다는 사실은 바뀌지 않는다.

== 에이전트 활용 아이디어

부분 갱신 화면을 만지는 단계에서 에이전트를 쓰는 요령이다.

htmx의 동작은 화면 뒤에서 일어나므로, 먼저 그것을 보는 눈을 갖추자.
브라우저에서 F12로 개발자 도구를 열고 네트워크 탭을 켠 채 카드를 추가해 보면, 요청 한 건이 찍히고 응답 본문에 `<li>` 조각이 그대로 보인다.
htmx가 뜻대로 움직이지 않을 때도 이 화면부터 확인하고, 에이전트에게 물을 때 그 요청 주소와 응답 본문을 붙여 넣으면 화면을 말로 묘사하는 것보다 원인 찾기가 빠르다.

이 최소 앱은 기능 실험의 재료로 알맞다.
"덱 목록에도 htmx 지우기 버튼을 달아 달라", "카드를 추가한 뒤 입력 칸이 비워지게 고쳐 달라"처럼 이 장에서 본 패턴의 변주를 시켜 보자.
파일이 몇 개뿐이라 에이전트가 고친 곳을 전부 따라 읽을 수 있고, `go run .`으로 결과가 바로 확인된다.
지시문에 "일반 폼 제출로도 동작해야 한다"는 조건을 넣어 두면, 점진적 향상을 깨는 수정이 걸러진다.

htmx에는 이 장에서 본 것 말고도 속성이 많다.
남의 코드에서 처음 보는 `hx-` 속성을 만나면, 그 코드를 보여 주며 뜻을 묻는 것이 문서를 뒤지는 것보다 빠르다.
다만 설명을 받아 적는 데서 멈추지 말고, 속성 값을 바꿔 서버를 다시 띄우고 눌러 본 결과로 확인하자.
설명은 그럴듯하게 틀릴 수 있지만 화면에 실제로 일어난 일은 그렇지 않다.

== 정리

첫째, htmx는 HTML 속성으로 부분 갱신을 선언하는 자바스크립트 라이브러리다.
`htmx.min.js` 파일 하나를 script 한 줄로 불러오면 준비가 끝나고, 빌드 도구는 필요 없다.

둘째, 요청은 속성 세 개로 선언한다.
`hx-post`(어디로 보낼지), `hx-target`(응답을 어디에 넣을지), `hx-swap`(어떻게 넣을지)이고, `method`와 `action`을 남겨 두면 htmx가 없어도 일반 폼으로 동작한다(점진적 향상).

셋째, 서버는 페이지 대신 HTML 조각을 돌려준다.
`HX-Request` 헤더로 htmx 요청을 구별해 이름 붙은 템플릿 하나만 그려 보내고, 본문 없는 200 응답은 "대상을 비우라"는 답이 되어 삭제에 쓰인다.

넷째, 모든 상호작용에 htmx가 필요한 것은 아니다.
학습 화면의 뒤집기는 `details`/`summary`라는 브라우저 내장 요소로, 다음 카드 이동은 일반 링크와 쿼리 파라미터로 충분했다.

다섯째, 저장(SQLite), 서버(Gin), 화면(html/template), 부분 갱신(htmx)이 이어져 2부의 최소 앱이 완성됐다.
완성본 앱도 이 네 층의 구도 위에 서 있다.

이것으로 2부가 끝났다.
다음 {ch-design-principles}부터는 완성본 앱의 코드를 해부한다.
최소 앱은 파일 몇 개로 끝났지만, 기능이 늘어난 완성본은 코드를 어디에 어떻게 나눠 둘 것인가라는 새 질문에 답해야 한다.
그 답의 원칙부터 읽고, 데이터에서 화면 순으로 코드를 따라가 보자.
