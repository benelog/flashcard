= 데이터베이스 기초: 테이블, SQL, 인덱스

화면을 닫아도, 다른 기기에서 열어도 덱과 카드가 그대로인 것은 서버 건너편의 데이터베이스가 원본을 지키고 있기 때문이다.
화면과 서버의 언어에 이어, 이 장에서는 데이터를 다루는 기초 세 가지를 익힌다.
관계형 데이터베이스가 데이터를 담는 방식(테이블과 키), 그 데이터를 다루는 언어인 SQL, 조회 속도를 좌우하는 인덱스다.
재료는 2부의 남은 장들이 함께 쓸 최소 플래시카드 앱(`flashcard-basic/`)의 두 테이블과, 거기에 보내는 쿼리(query, 데이터베이스에 요청하는 문장)다.
Go의 구조체도, API가 주고받는 JSON도, 화면이 그리는 목록도 결국 테이블과 열을 옮겨 담은 것이라, 데이터의 모양을 먼저 알면 그 위의 코드가 빨리 읽힌다.

== 관계형 데이터베이스: 테이블에 담고 키로 잇는다

.[용어 풀이] 테이블·행·열(Table·Row·Column)
[NOTE]
====
관계형 데이터베이스가 데이터를 담는 격자로, 스프레드시트의 시트 한 장과 거의 같다.
표 하나가 테이블이고, 가로 한 줄인 행(Row)이 카드 한 장 같은 개별 기록이며, 세로 칸인 열(Column)이 이름·생성 시각처럼 기록마다 채우는 항목이다.
====

덱을 담는 `decks` 테이블을 스프레드시트처럼 그려 보면 이런 모양이다.

|===
| id | name

| 1 | 토익 필수 단어
| 2 | 회화 표현
|===

행 하나가 덱 하나다.
스프레드시트와 다른 점은 테이블의 구조와 규칙을 데이터베이스가 강제한다는 것이다.
어떤 열이 있고 각 칸에 어떤 종류의 값이 들어갈 수 있는지 미리 선언해 두면, 어긋나는 데이터는 아예 저장되지 않는다.

=== 왜 테이블을 나누는가

카드 테이블의 각 행에 소속 덱의 이름을 함께 적으면 어떨까.
당장은 편해 보이지만, 덱 이름을 바꾸는 순간 그 덱의 카드 수백 행을 전부 고쳐야 하고, 한 행이라도 빠뜨리면 같은 덱에 두 이름이 남는다.

관계형 모델의 답은 "같은 사실은 한 곳에만 적는다"이다.
덱 이름은 `decks` 테이블에 한 번만 적고, 카드 테이블에는 어느 덱에 속하는지 가리키는 식별자만 둔다.
이렇게 테이블을 주제별로 나누는 작업을 정규화(normalization)라 부른다.

.[용어 풀이] 정규화와 비정규화(Normalization·Denormalization)
[NOTE]
====
같은 사실이 두 곳에 적히지 않도록 데이터를 주제별 테이블로 나누는 설계 작업이 정규화다.
값을 고칠 때 한 곳만 고치면 되고 테이블 사이에 어긋난 값이 생기지 않는다.
반대로 비정규화(denormalization)는 조회를 쉽게 하려고 중복을 일부러 남겨 두는 선택이라, 읽기는 쉬워지는 대신 갱신할 때 함께 고칠 곳이 늘어난다.
{ch-database-design}에서 카드 테이블이 사용자 식별자까지 함께 들고 있는 이유가 이 비정규화다.
====

나뉜 테이블을 다시 잇는 수단은 키(key)다.

.[용어 풀이] 기본 키와 외래 키(Primary Key·Foreign Key)
[NOTE]
====
기본 키는 한 행을 유일하게 가리키는 식별 값으로, 테이블 안에서 같은 값이 두 번 나오지 않는다.
외래 키는 다른 테이블의 기본 키를 가리키는 열로, "이 카드는 저 덱에 속한다"처럼 테이블과 테이블을 잇는다.
스프레드시트로 치면 한 시트의 칸이 다른 시트의 특정 줄을 가리키도록 약속해 두고, DB가 그 약속이 깨지지 않게 지켜 주는 셈이다.
====

카드를 담는 `cards` 테이블도 그려 보자.

|===
| id | deck_id | text | meaning

| 1 | 1 | deadline | 마감 기한
| 2 | 1 | invoice | 청구서, 송장
|===

`id`가 이 테이블의 기본 키이고, `deck_id`가 `decks` 테이블의 `id`를 가리키는 외래 키다.
두 카드 모두 `deck_id`가 1이므로, 덱 이름을 중복해 적지 않고도 "토익 필수 단어" 덱에 속한다는 사실이 드러난다.

== 데이터베이스와 대화하는 언어, SQL

테이블을 만들고, 행을 넣고, 원하는 행을 찾아오는 모든 일은 SQL 문장으로 한다.

.[용어 풀이] SQL(Structured Query Language)
[NOTE]
====
관계형 데이터베이스에 일을 시킬 때 쓰는 표준 언어다.
원하는 결과를 문장으로 서술하면, 그 결과를 어떤 순서로 어떻게 찾을지는 데이터베이스가 정한다.
PostgreSQL, MySQL, SQLite 어느 것을 쓰든 기본 문법은 그대로 통하고 자리표시자 기호나 자료형 이름 같은 세부만 달라서, 한번 익히면 오래 쓰는 지식이다.
====

Go가 "이 순서로 이렇게 하라"라고 절차를 지시하는 언어라면, SQL은 "이 조건에 맞는 행"처럼 원하는 결과만 서술하는 선언형(declarative) 언어다.
{ch-go-sqlite}에서 볼 store 계층(데이터베이스 읽기와 쓰기를 도맡는 Go 코드 층)이 보내는 문장들이 전부 SQL이다.

SQL 문장은 역할에 따라 두 갈래로 나뉜다.

*DDL(Data Definition Language, 데이터 정의어)*: 테이블을 만들고 고치고 지우는, 데이터의 틀을 다루는 문장이다. `create table`, `alter table`, `drop table`이 대표다.

*DML(Data Manipulation Language, 데이터 조작어)*: 그 틀 안의 내용을 넣고 찾고 고치고 지우는 문장이다. `insert`, `select`, `update`, `delete`가 대표다.

=== 준비물은 sqlite3 하나다

SQLite는 서버 설치도 계정도 필요 없이 파일 하나로 돌아 실습 준비가 가장 간단하다.
명령줄 도구 sqlite3는 macOS에 기본으로 들어 있고, 리눅스는 `sudo apt install sqlite3` 한 줄, 윈도우는 sqlite.org에서 내려받으면 된다({ch-first-run}).
연습용 파일을 열고, 테이블을 만들어 행 하나를 넣고 다시 꺼내 보자.

[source,text]
----
$ sqlite3 practice.db
sqlite> create table decks (id integer primary key autoincrement, name text not null);
sqlite> insert into decks (name) values ('토익 필수 단어');
sqlite> select * from decks;
1|토익 필수 단어
----

sqlite3는 파일이 없으면 새로 만들고, 문장은 세미콜론(;)까지 쳐야 실행된다.
점으로 시작하는 `.tables`(테이블 목록)·`.quit`(종료)은 SQL이 아니라 sqlite3의 명령이다.
이 장의 연습 문장은 저장소의 `language-basic/sql/practice.sql`에 모아 두었으니, 처음부터 다시 하고 싶으면 `sqlite3 practice.db < practice.sql`로 한 번에 실행한다.
{ch-first-run}에서 앱 서버를 켰을 때 생긴 `flashcard.db`도 같은 도구로 열어 볼 수 있다.

== DDL: 데이터의 틀을 만든다

앞에서 그려 본 두 테이블의 실제 선언인 `flashcard-basic/schema.sql` 전문이다.
서버가 시작할 때 이 파일을 통째로 실행해 데이터베이스의 틀을 만든다({ch-go-sqlite}).

[NOTE]
====

집으로 치면 도면이고, 그 도면을 SQL로 적어 둔 파일이 `schema.sql`이다.
====

----
include::../../flashcard-basic/schema.sql[tag=schema]
----

한 줄이 열 하나이고, 각 줄은 "열 이름, 자료형, 규칙들" 순서로 읽는다.
테이블 이름 앞의 `if not exists`(이미 있으면 넘어가라) 덕분에 몇 번을 다시 실행해도 안전하다.
맨 끝의 `create index`는 이 장의 마지막 절에서 다룬다.

SQLite가 값을 담는 자료형은 NULL, 정수(integer), 실수(real), 문자열(text), 이진 데이터(blob) 다섯뿐이고footnote:[SQLite 공식 문서의 자료형 설명 https://www.sqlite.org/datatype3.html[Datatypes In SQLite]], 이 스키마는 integer와 text 둘로 끝난다.
`id`의 `integer primary key autoincrement`는 행을 넣을 때마다 데이터베이스가 1, 2, 3으로 번호를 매겨 주는 정수 순번이다.
카드 테이블의 `text text`는 앞이 열 이름이고 뒤가 자료형이다.

완성본은 이 정수 순번 대신 UUID라는 식별자를 문자열로 담는다.

.[용어 풀이] UUID(Universally Unique Identifier)
[NOTE]
====
어디서 만들어도 값이 겹치지 않도록 고안된 128비트 식별자로, `3f2a9c81-4b7e-…`처럼 16진수와 붙임표를 섞은 36자 문자열로 적는다.
대부분의 비트를 난수로 채워서, 여러 기기가 상의하지 않고 각자 만들어도 같은 값이 나올 확률은 무시할 만큼 낮다.
번호를 매겨 주는 중앙이 필요 없다는 것이 순번과 다른 점이고, 이 값을 기본 키로 삼은 이유와 대가는 {ch-database-design}에서 따진다.
====

자료형은 그 칸에 담길 값의 종류를 못 박는 장치로, Go의 타입이 컴파일 시점의 검증이라면 자료형은 저장 시점의 검증이다.
다만 SQLite는 이 검증이 느슨해서, 정수로 선언한 칸에 `'12'`를 넣으면 정수 12로 바꿔 담지만, `'abc'`는 거부하지 않고 글자 그대로 담는다(SQLite 문서가 타입 친화도(type affinity)라고 부르는 규칙이다).
그래서 값의 형식은 `check` 같은 제약과 앱 쪽 Go 코드가 함께 지킨다.
전용 자료형이 풍부한 운영 DB는 {ch-supabase-db}에서 다룬다.

나머지 규칙들이 제약이다.

.[용어 풀이] 제약(Constraint)
[NOTE]
====
데이터가 지켜야 할 규칙을 DB에 직접 새겨, 어긴 값은 아예 저장되지 않게 막는 장치다.
"이 칸은 비어 있으면 안 된다"(not null), "이 값은 중복되면 안 된다"(unique) 같은 규칙이다.
규칙을 데이터 곁에 두면 어떤 경로로 값이 들어와도 똑같이 적용된다.
====

`primary key`는 이 열이 행의 대표 식별자라는 선언이고, `not null`은 그 칸을 비워 둘 수 없다는 뜻이다.
비워 둔 칸에 데이터베이스가 남겨 두는 표시가 NULL이다.
이 스키마는 값을 담는 열마다 `not null`을 붙였지만, 제약이 없는 열(잠시 뒤 연습으로 추가할 `description` 같은 열)은 비워 둘 수 있다.

.[용어 풀이] NULL
[NOTE]
====
값이 채워지지 않은 칸에 남는 특별한 표시로, 0이나 빈 문자열이 아니라 "값 자체가 없음"을 뜻한다.
설문지의 빈칸이 "0이라고 답했다"가 아니라 "답하지 않았다"인 것과 같다.
비교도 남달라서 값이 없는 행은 `= NULL`이 아니라 `is null`로 물어야 찾는다.
"값이 없다"를 표현할 열에만 NULL을 허용하고 나머지는 `not null`로 막는 것이 스키마 설계의 기본이다.
====

카드 테이블의 `references decks (id)`는 외래 키 선언으로, `deck_id`에는 `decks`에 실제로 있는 덱의 id만 들어갈 수 있다.
코드에 버그가 있어도 존재하지 않는 덱의 카드나 이름 없는 덱은 저장 단계에서 거부된다.
코드는 고치면 되지만 오염된 데이터는 복구가 어려우므로, 마지막 방어선을 DB에 두는 것이다.
뒤에 붙은 `on delete cascade`는 부모 행(덱)이 지워질 때 그 행을 가리키는 자식 행(카드)도 함께 지우라는 옵션이다.
삭제 정책의 설계는 {ch-database-design}에서 다룬다.

제약은 이 밖에도 있다.
`unique`는 한 열에 같은 값이 두 번 나오지 못하게 막고, `default`는 값을 주지 않았을 때 대신 채울 기본값을 정하며, `check`는 괄호 안의 조건에 맞는 값만 받는다.
완성본의 카드 테이블은 `check`로 카드 종류를 넷으로 제한하고 `default`로 기본 종류를 정해 두었다({ch-database-design}).

=== alter table: 만든 틀을 고친다

이미 만든 테이블의 틀을 고치는 문장이 `alter table`이다.
Flashcard도 덱 공유 기능이 생기면서 `decks` 테이블에 `share_slug` 열이 뒤늦게 추가됐다.
연습용 테이블에서 `alter table decks add column description text;`를 실행해 보자.
기존 데이터는 그대로 두고 틀만 고치므로, 이미 있던 행들은 새 열이 빈 채로 남는다.

틀을 없애는 문장은 `drop`이다.
`drop table decks`는 테이블을 데이터까지 통째로 지우므로 가장 신중해야 할 문장이다.

데이터가 쌓인 테이블을 고치는 일은 처음 만드는 일과 다르다.
열을 더하는 문장을 이미 실행했는지 기억해야 하고, 실행 순서가 어긋나면 컴퓨터마다 테이블의 모양이 달라진다.
그래서 운영 데이터베이스에서는 구조 변경 문장들을 순서 있는 파일로 쌓아 관리한다(마이그레이션, {ch-migrations}).
로컬 모드의 `schema.sql`은 매번 통째로 다시 실행해도 되는 파일 하나라 이 문제를 비켜 간다.

== DML: 넣고, 찾고, 고치고, 지운다

DML의 네 동사 `insert`, `select`, `update`, `delete`는 API의 생성·조회·수정·삭제와 일대일로 대응한다.
요청을 받아 처리하는 코드인 핸들러(handler, {ch-gin}에서 다룬다)가 store 계층을 부르면, store 계층이 실행하는 것이 이 문장들이다.

=== insert: 행을 만든다

카드 한 장을 만들 때 최소 앱이 실행하는 문장이다.

[source,sql]
----
insert into cards (deck_id, text, meaning) values (?, ?, ?)
----

괄호 안의 열 목록과 `values`의 값 목록이 순서대로 짝을 이룬다.
`id`는 `autoincrement` 열이라 데이터베이스가 채우므로 목록에 없다.

`?`는 자리표시자(placeholder)다.
실제 값은 문장과 따로 전달되고, Go 코드에서는 `s.db.Exec(문장, 값1, 값2, …)`처럼 인자로 넘긴다({ch-go-sqlite}).
값을 문자열 이어 붙이기로 문장에 직접 끼워 넣으면 SQL 인젝션(SQL injection) 공격에 뚫리므로, "SQL은 반드시 자리표시자로"가 웹 개발의 철칙이다.

.[용어 풀이] SQL 인젝션(SQL Injection)
[NOTE]
====
사용자가 입력한 값에 SQL 조각을 섞어 넣어, 서버가 실행할 문장의 의미를 바꿔치기하는 공격이다.
검색어 칸에 `' or 1=1 --` 같은 문자열을 적어 조건을 "모든 행"으로 뒤집거나, 뒤에 삭제 문장을 덧붙이는 식이다.
자리표시자로 넘긴 값은 문장의 일부로 해석되지 않고 언제나 하나의 값으로만 취급되므로 이 공격이 성립하지 않는다.
지금도 흔한 공격이라 OWASP가 꼽는 웹 앱 10대 위험의 2021년판에서 3위(A03 Injection)에 올라 있다footnote:[OWASP Top 10:2021의 인젝션 항목 https://owasp.org/Top10/A03_2021-Injection/[A03:2021 Injection]].
====

자리표시자 기호는 드라이버마다 다르다.
SQLite는 `?`를, 완성본의 운영 모드가 쓰는 PostgreSQL 드라이버(pgx)는 `$1`, `$2`를 쓰지만, 값을 문장 밖에서 따로 전달한다는 원리는 같다.

.[용어 풀이] 드라이버(Driver)
[NOTE]
====
특정 데이터베이스와 대화하는 법을 아는 연결 부품이다.
프로그램이 보낸 SQL을 그 데이터베이스의 통신 규약으로 옮기고, 돌아온 결과를 프로그램이 다룰 값으로 되돌려 준다.
나라마다 다른 콘센트에 꽂는 여행용 어댑터처럼, 데이터베이스를 바꿀 때는 드라이버를 바꿔 끼우고 표준에서 벗어난 세부만 손본다.
Flashcard는 로컬 모드에서 SQLite 드라이버를, 운영에서 pgx를 쓴다({ch-supabase-db}).
====

=== select: 찾아 읽는다

가장 자주 쓰는 문장이다.
절을 하나씩 붙여 가며 결과를 좁혀 가는 구조라, 가장 단순한 형태부터 쌓아 보겠다.

[source,sql]
----
select * from decks
----

`*`는 모든 열이라는 뜻이고, 필요한 열만 적으면 그 열만 온다.

[source,sql]
----
select text, meaning from cards
----

`where`를 붙이면 가져올 행을 고른다.

[source,sql]
----
select text, meaning from cards where deck_id = ?
----

`order by`는 정렬 순서를, `limit`은 가져올 행 수의 상한을 정한다.
한 덱의 카드를 최근에 만든 순서로 다섯 장만 가져오는 문장이다.

[source,sql]
----
select text, meaning
from cards
where deck_id = ?
order by id desc
limit 5
----

`select`가 가져올 열, `from`이 대상 테이블, `where`가 행을 고르는 조건, `order by`가 정렬 순서(`desc`는 내림차순), `limit`이 행 수 상한이다.
조회의 기본 재료인 이 다섯 가지는 언제나 이 순서로 적는다.

"이 덱의 카드만"이라는 화면의 규칙은 `where deck_id = ?` 조건 하나로 구현된다.
여러 사용자를 받는 완성본에서는 같은 자리에 `where user_id = ?`가 빠짐없이 붙어 "내 데이터만"을 지킨다({ch-database-design}).

행을 세거나 더할 수도 있다.

[source,sql]
----
select count(*) from cards where deck_id = ?
----

`count(*)`는 조건에 맞는 행의 수를 숫자 하나로 돌려주는 집계 함수다.
집계 함수는 합계(`sum`), 평균(`avg`), 최솟값(`min`), 최댓값(`max`)까지 다섯이 기본이고, `group by`와 함께 쓰면 "덱별 카드 수" 같은 통계도 한 문장으로 나온다.

최소 앱의 `ListCards`가 실행하는 `select id, deck_id, text, meaning from cards where deck_id = ? order by id`도 방금 쌓은 구조 그대로다({ch-go-sqlite}).

=== 조인: 나눈 테이블을 다시 잇는다

덱의 이름은 `decks` 테이블에만 있으므로, 카드 내용과 소속 덱의 이름을 함께 보려면 두 테이블을 잇는다.

.[용어 풀이] 조인(JOIN)
[NOTE]
====
두 테이블을 공통 값으로 이어 붙여 하나의 테이블처럼 조회하는 연산이다.
주제별로 나눠 담은 데이터를 다시 합쳐 읽는 도구로, 카드 테이블과 덱 테이블을 덱 id로 이으면 카드 내용과 덱 이름을 한 줄에 놓고 볼 수 있다.
====

[source,sql]
----
select decks.name, cards.text, cards.meaning
from cards
join decks on cards.deck_id = decks.id
----

`on`이 잇는 규칙으로, "`cards`의 `deck_id`가 `decks`의 `id`와 같은 행끼리 한 줄로 붙여라"라고 읽는다.
외래 키로 이어 둔 관계를 조회 시점에 다시 합치므로, 테이블을 나눠도 조회가 불편해지지 않는다.
완성본은 자주 쓰는 조인을 뷰(view)라는 이름 붙은 조회로 저장해 두고 쓴다({ch-database-design}).

=== update와 delete: 고치고 지운다

최소 앱이 덱의 이름을 바꿀 때 실행하는 문장이다.

[source,sql]
----
update decks set name = ? where id = ?
----

`set`이 바꿀 열과 새 값, `where`가 바꿀 행을 정한다.
삭제도 구조는 같다.

[source,sql]
----
delete from decks where id = ?
----

`where`가 없는 `update`와 `delete`도 문법상 유효한 문장이고, 데이터베이스는 군말 없이 모든 행을 고치거나 지운다.
"조건을 빠뜨린 `delete`"는 데이터베이스 사고의 고전이므로, 고치고 지우는 문장은 `where`부터 확인한다.

로그인이 없는 최소 앱은 `id` 조건 하나로 충분하지만, 완성본의 같은 문장에는 `where user_id = ? and id = ?`처럼 사용자 조건이 함께 붙는다.
SQL 문장 안에 새겨 둔 인가(authorization) 검사다.
누군가 남의 카드 id를 알아내 지우는 요청을 보내도, `user_id`가 맞지 않아 아무것도 지워지지 않는다.

.[용어 풀이] 인증과 인가(Authentication·Authorization)
[NOTE]
====
인증은 "당신이 누구인가"를, 인가는 "그 사람이 이 일을 해도 되는가"를 확인하는 일이다.
건물 입구에서 신분증으로 본인임을 확인받는 것이 인증이고, 그 신분증으로 어느 층의 문까지 열리는지가 인가다.
로그인했다고 남의 카드를 지울 자격까지 생기지는 않으므로 둘은 따로 확인한다.
Flashcard에서 인증은 로그인 처리가(운영은 {ch-supabase-auth}의 Supabase 로그인), 인가는 모든 쿼리에 붙는 `user_id` 조건이 맡는다.
====

고치거나 지운 뒤에는 영향을 받은 행 수가 돌아온다.
이 숫자가 0이면 조건에 맞는 행이 없었다는 뜻이므로, store 계층은 이 값으로 "그런 덱이 없었다"를 판정한다({ch-go-sqlite}의 `DeleteDeck`).
그 판정이 웹에서 "찾는 대상이 없다"는 응답으로 이어지는 과정은 {ch-gin-hello}에서 다룬다.
여러 문장을 "전부 성공하거나 전부 취소"되는 한 단위로 묶는 트랜잭션(transaction)은 {ch-domain-model}에서 다룬다.

== 인덱스: 테이블이 커져도 빨리 찾는 법

`where deck_id = ?` 같은 조건으로 행을 찾을 때, 데이터베이스가 모든 행을 처음부터 끝까지 확인하는 것을 전체 스캔(full scan)이라 한다.
행이 백 개일 때는 문제가 없지만, 완성본은 카드 한 장을 채점할 때마다 복습 기록을 한 행씩 남기므로, 하루 100장씩 복습하면 한 해에 3만 6천 행, 열 해면 36만 행이 쌓인다.
전체 스캔은 읽는 양이 테이블 크기에 비례해 늘어난다.

.[용어 풀이] 인덱스(Index)
[NOTE]
====
특정 열의 값을 빠르게 찾도록 미리 정렬해 둔 보조 자료구조로, 책 뒤의 찾아보기(색인)와 같다.
찾아보기로 원하는 쪽에 바로 가듯, 인덱스가 있으면 DB가 모든 행을 읽지 않고 원하는 행으로 곧장 간다.
대신 데이터를 쓸 때마다 인덱스도 갱신하는 비용을 치른다.
====

인덱스를 만드는 문장도 DDL이다.
`schema.sql` 맨 끝에서 미뤄 두었던 한 줄로, `cards` 테이블의 `deck_id` 열에 인덱스를 건다.

[source,sql]
----
create index if not exists cards_deck_idx on cards (deck_id);
----

SQLite도 다른 관계형 데이터베이스처럼 인덱스의 기본형으로 B-tree를 쓴다.
B-tree는 값들을 정렬된 상태로 유지하는 트리 구조라, 이름순 전화번호부에서 이름을 찾듯 범위를 크게 좁혀 가며 내려간다.
마디 하나(SQLite의 기본 페이지 크기인 4KB 한 장)에 갈림길이 수백 개 들어가 한 번 고를 때마다 후보가 수백분의 일로 줄므로, 연습용 `cards` 테이블에 카드 50만 장을 넣어도 뿌리에서 잎까지 세 단계, 페이지 세 장만 읽고 원하는 값에 닿는다.
이 글을 쓰는 컴퓨터에서 같은 조회가 전체 스캔으로는 17ms, 인덱스로는 0.15ms였다.
등호 조건(`=`)과 범위 조건(`<`, `>=`), `order by` 정렬까지 인덱스의 정렬 순서로 해결된다.

=== 복합 인덱스와 열 순서

인덱스는 여러 열을 합쳐 만들 수도 있다.
완성본의 "오늘 복습할 카드" 조회는 사용자와 복습 시각 두 열을 합친 복합 인덱스가 뒷받침한다.
복합 인덱스는 성(姓)으로 먼저 정렬하고 같은 성 안에서 이름으로 정렬한 명부와 같아서, 성을 알면 그 구역으로 바로 가고 구역 안은 이름순이라 범위를 짚기도 쉽다.

그래서 열 순서가 중요하다.
"성이 김씨"처럼 값 하나로 정해지는 조건을 등치 조건, "이름이 ㄱ부터 ㄷ까지"처럼 구간을 묻는 조건을 범위 조건이라고 한다.
"오늘 복습할 카드"는 "`user_id`가 이 사용자인(등치 조건) 카드 가운데 `due_at`이 지금보다 이전인(범위 조건) 것"이다.
이런 질문에는 등치 조건의 열을 앞에, 범위 조건의 열을 뒤에 둔다.
사용자 구역으로 바로 들어가 `due_at` 순서로 늘어선 행을 앞에서부터 끊어 읽으면 되기 때문이다.
순서를 뒤집으면 시각이 지난 카드를 모든 사용자에 걸쳐 훑으며 이 사용자의 것을 골라내야 한다.

인덱스를 걸었다고 쿼리가 반드시 그 인덱스를 쓰지는 않는다.
조건에 맞는 행이 테이블의 대부분이라면 테이블을 통째로 읽는 편이 오히려 빠르고, 어느 경로로 갈지는 DB가 테이블의 크기와 값의 분포를 보고 정한다.
그러니 짐작하는 대신 쿼리 앞에 `explain query plan`을 붙여 실행 계획(execution plan)을 물어본다.

.[용어 풀이] 실행 계획(Execution Plan)
[NOTE]
====
DB가 이 쿼리를 어떤 경로로 처리하기로 정했는지 적은 계획표로, 어느 인덱스를 탈지, 테이블을 통째로 읽을지, 여러 테이블을 어느 순서로 읽을지가 나온다.
인덱스는 걸어 두는 것으로 끝나지 않고 쿼리가 실제로 쓰는지 확인해야 하는데, 그 확인 명령이 SQLite의 `explain query plan`(PostgreSQL은 `explain`)이다.
====

완성본의 실제 쿼리가 인덱스를 어떻게 쓰는지는 {ch-database-design}에서 실행 계획으로 확인한다.

=== 인덱스는 공짜가 아니다

그렇다면 모든 열에 인덱스를 걸면 될까.
행을 넣거나 고칠 때마다 그 테이블의 모든 인덱스도 갱신해야 하므로, 인덱스 하나하나가 쓰기 비용을 늘리고 저장 공간도 차지한다.
그래서 인덱스는 실제 조회 패턴에서 역산해 필요한 곳에만 건다.
앞서 본 `unique` 제약도 내부적으로는 유니크 인덱스로 구현된다.
중복을 검사하려면 같은 값을 빨리 찾아야 하기 때문이다.

== 직접 해 보기

`language-basic/sql/practice.sql`로 만든 연습용 데이터베이스에서 확인해 보자.
`sqlite3 practice.db < practice.sql`로 언제든 처음 상태로 되돌릴 수 있으니 마음 놓고 망가뜨려도 된다.

. 카드를 몇 장 더 넣고, 덱 이름과 카드 개수를 한 줄씩 보여 주는 문장을 쓴다. 조인과 `count(*)`, `group by`가 필요하다.
. 존재하지 않는 덱 번호로 카드를 넣어 본다. 외래 키가 막는지 확인하고, 막히지 않으면 `pragma foreign_keys = on;`을 먼저 실행한 뒤 다시 시도한다. 데이터를 지키는 규칙이 테이블 자체에 들어 있음을 확인하는 실험이다.
. `cards`에 카드를 넉넉히 넣은 뒤 `explain query plan select * from cards where deck_id = 1;`을 실행한다. 이어서 `drop index cards_deck_idx;`로 인덱스를 지우고 같은 문장을 다시 실행해 계획이 어떻게 달라지는지 견준다.
. 카드가 든 덱을 지워 본다. 카드가 함께 사라지는 것이 스키마에 적어 둔 `on delete cascade`의 효과다.

== 에이전트 활용 아이디어

`AGENTS.md`에 스키마의 위치(`flashcard-basic/schema.sql`)와 "쿼리를 새로 쓰면 어떤 인덱스를 타는지 함께 보고하라"를 적어 둘 만하다.
에이전트는 동작하는 쿼리는 잘 만들지만, 그 쿼리가 인덱스를 타는지는 시키지 않으면 확인하지 않는다.

원하는 결과는 우리말로 적고 검증 방법까지 한 지시에 넣는다.
"덱별 카드 수를 많은 순서로 뽑는 쿼리를 작성하고, explain query plan으로 전체 스캔이 없는지 확인해 달라"처럼 쓰면 된다.

카드가 쌓인 `flashcard.db` 사본을 놓고 "이 쿼리를 실행해 결과 10행을 보여 달라"고 시키면, 쿼리의 옳고 그름을 내 데이터로 곧장 확인할 수 있다.

== 정리

첫째, 관계형 데이터베이스는 데이터를 테이블에 담되, 같은 사실이 한 곳에만 적히도록 주제별로 나누고 기본 키와 외래 키로 잇는다.

둘째, SQL은 원하는 결과만 서술하는 선언형 언어다.
DDL로 틀과 제약을 만들고, DML로 내용을 넣고 찾고 고치고 지우며, 나눈 테이블은 조인으로 다시 합쳐 읽는다.
값은 자리표시자로 넘겨 SQL 인젝션을 막고, `update`와 `delete`에서는 `where`부터 확인한다.

셋째, 인덱스는 조회 비용이 테이블 크기에 비례해 늘지 않게 하는 찾아보기다.
복합 인덱스는 등치 조건 열을 앞에, 범위 조건 열을 뒤에 두고, 쓰기 비용이 있으므로 조회 패턴에서 역산해 건다.
