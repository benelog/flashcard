= 데이터베이스 기초: 테이블, SQL, 인덱스

{ch-requirements}에서 본 화면이 보여 주는 덱과 카드는 브라우저의 것이 아니다.
화면을 닫아도, 다른 기기에서 열어도 데이터가 그대로인 것은 서버 건너편의 데이터베이스가 원본을 지키고 있기 때문이다.
관계형 데이터베이스를 고르고 로컬 모드에서는 SQLite로 시작하기로 한 이유는 {ch-tech-choices}에서 정리했고, {ch-instructing}에서는 에이전트가 그 결정 위에 앱의 골격을 세우는 것까지 지켜봤다.
{ch-html-hello}부터 {ch-go-types}까지 화면의 언어와 서버의 언어를 익혔으니, 세 언어의 마지막 순서는 데이터의 언어다.
이 장에서는 관계형 데이터베이스가 데이터를 담는 방식(테이블과 키), 그 데이터를 다루는 언어인 SQL, 그리고 조회 속도를 좌우하는 인덱스를 익힌다.
재료는 {ch-go-sqlite}부터 2부의 남은 장들이 함께 쓸 최소 플래시카드 앱(`flashcard-basic/`)의 두 테이블과, 거기에 보내는 쿼리(query, 데이터베이스에 보내는 요청 문장)다.
{ch-database-design}에서 실제 테이블 설계를 해부하는 데 필요한 기초를 여기서 다진다.

3부에서 앱 코드를 읽기 전에 데이터의 모양부터 익혀 두는 데는 이유가 있다.
{ch-go-types}에서 익힌 Go의 구조체도, API가 주고받는 JSON도, 화면이 그리는 목록도 결국 여기 있는 표와 열을 옮겨 담은 것이다.
바닥의 모양을 알고 나면 그 위층의 코드가 왜 그렇게 생겼는지가 더 빨리 눈에 들어온다.

== 관계형 데이터베이스: 표에 담고 키로 잇는다

.[용어 풀이] 테이블·행·열(Table·Row·Column)
[NOTE]
====
관계형 데이터베이스가 데이터를 담는 격자로, 스프레드시트의 시트 한 장과 거의 같다.
표 하나가 테이블이고, 가로 한 줄인 행(Row)이 카드 한 장·사용자 한 명 같은 개별 기록이며, 세로 칸인 열(Column)이 이름·생성 시각처럼 기록마다 채우는 항목이다.
잠시 뒤 볼 `create table` 문이 이 시트의 이름과 열 목록을 미리 정해 두는 일에 해당한다.
====

덱을 담는 `decks` 테이블을 스프레드시트처럼 그려 보면 이런 모양이다.

|===
| id | name

| 1 | 토익 필수 단어
| 2 | 회화 표현
|===

행 하나가 덱 하나이고, 열은 모든 덱이 공통으로 갖는 항목이다.
스프레드시트와 다른 점은 이 표의 구조와 규칙을 데이터베이스가 강제한다는 것이다.
어떤 열이 있는지, 각 칸에 어떤 종류의 값만 들어갈 수 있는지를 미리 선언해 두면, 규칙에 어긋나는 데이터는 아예 저장되지 않는다.

=== 왜 표를 나누는가

카드도 담아야 하니 표가 하나 더 필요한데, 여기서 관계형 모델의 핵심 질문이 나온다.
카드 표의 각 행에 소속 덱의 이름을 함께 적으면 어떨까.
당장은 편해 보이지만, 덱 이름을 바꾸는 순간 그 덱에 속한 카드 수백 행을 전부 고쳐야 하고, 한 행이라도 빠뜨리면 같은 덱에 두 이름이 남는다.

관계형 모델의 답은 "같은 사실은 한 곳에만 적는다"이다.
덱의 이름은 `decks` 표에 한 번만 적고, 카드 표에는 어느 덱에 속하는지 가리키는 식별자만 둔다.
이렇게 표를 주제별로 나누는 작업을 정규화(normalization)라 부른다.

.[용어 풀이] 정규화와 비정규화(Normalization·Denormalization)
[NOTE]
====
같은 사실이 두 곳에 적히지 않도록 데이터를 주제별 표로 나누는 설계 작업이 정규화다.
주소를 서류마다 베껴 적는 대신 주소록 한 곳에만 적고 나머지 서류는 그 항목을 가리키게 하는 것과 같아서, 값을 고칠 때 한 곳만 고치면 되고 표 사이에 어긋난 값이 생기지 않는다.
반대로 비정규화(denormalization)는 조회를 쉽게 하려고 중복을 일부러 남겨 두는 선택이다.
읽을 때 여러 표를 뒤지지 않아도 되는 대신, 중복된 값을 갱신할 때 함께 고쳐야 할 곳이 늘어난다.
{ch-database-design}에서 카드 표가 소속 덱뿐 아니라 사용자 식별자까지 함께 들고 있는 이유가 이 비정규화다.
====

나뉜 표를 다시 잇는 수단은 키(key)다.
표 안에서 한 행을 콕 집어내는 열을 정해 두고, 다른 표는 그 값을 적어 두는 것으로 관계를 표현한다.

.[용어 풀이] 기본 키와 외래 키(Primary Key·Foreign Key)
[NOTE]
====
기본 키는 한 행을 유일하게 가리키는 식별 값으로, 표 안에서 같은 값이 두 번 나오지 않게 막는 대표 열이다.
외래 키는 다른 표의 기본 키를 가리키는 열로, "이 카드는 저 덱에 속한다"처럼 표와 표를 잇는 끈이다.
스프레드시트로 치면 한 시트의 칸이 다른 시트의 특정 줄을 가리키도록 약속해 두고, DB가 그 약속이 깨지지 않게 지켜 주는 셈이다.
====

카드를 담는 `cards` 표를 같은 방식으로 그려 보자.

|===
| id | deck_id | text | meaning

| 1 | 1 | trade-off | 맞바꿈, 절충
| 2 | 1 | pull request | 코드 반영 요청
|===

`id`가 이 표의 기본 키이고, `deck_id`가 `decks` 표의 `id`를 가리키는 외래 키다.
두 카드 모두 `deck_id`가 1이므로 "토익 필수 단어" 덱에 속한다는 사실이, 덱 이름을 한 글자도 중복해 적지 않고도 드러난다.
2부의 최소 앱은 이 두 표가 전부다.
완성본은 같은 방식으로 이어진 테이블 일곱 개로 이루어져 있는데, 전체 그림은 {ch-database-design}에서 요구사항을 따라 하나씩 도출한다.

== 데이터베이스와 대화하는 언어, SQL

표를 만들고, 행을 넣고, 원하는 행을 찾아오는 모든 일은 SQL 문장으로 이루어진다.

.[용어 풀이] SQL(Structured Query Language)
[NOTE]
====
관계형 데이터베이스에 일을 시킬 때 쓰는 표준 언어다.
"덱 표에서 이 사용자의 행을 만든 날짜 순으로 달라"처럼 원하는 결과를 문장으로 서술하면, 그 결과를 어떤 순서로 어떻게 찾을지는 데이터베이스가 스스로 정한다.
PostgreSQL, MySQL, SQLite 등 어느 관계형 데이터베이스를 쓰든 대부분의 문법이 통하므로, 한번 익히면 오래 쓰는 지식이다.
====

Go나 자바스크립트가 "이 순서로 이렇게 하라"라고 절차를 지시하는 언어라면, SQL은 원하는 결과의 조건만 서술하는 선언형(declarative) 언어다.
반복문을 돌며 행을 하나씩 확인하는 코드를 쓰는 대신 "이 조건에 맞는 행"이라고 말하면 끝이다.
{ch-go-sqlite}에서 볼 store 계층(데이터베이스 읽기와 쓰기를 도맡는 Go 코드 층)이 데이터베이스에 보내는 문장들이 전부 SQL이고, 이 장에서 그 문장들을 하나씩 읽는다.

SQL 문장은 역할에 따라 크게 두 갈래로 나뉜다.

*DDL(Data Definition Language, 데이터 정의어)*: 테이블을 만들고 고치고 지우는, 데이터의 틀을 다루는 문장이다. `create table`, `alter table`, `drop table`이 대표다.

*DML(Data Manipulation Language, 데이터 조작어)*: 그 틀 안의 내용을 넣고 찾고 고치고 지우는 문장이다. `insert`, `select`, `update`, `delete`가 대표다.

집에 비유하면 DDL은 설계와 시공이고 DML은 입주 후의 생활인 셈이다.

=== 준비물은 sqlite3 하나다

용어 상자에서 말했듯 SQL 문법은 어느 관계형 데이터베이스에서나 대부분 통하고, 그중 SQLite는 서버 설치도 계정도 필요 없이 파일 하나로 돌아 실습 준비가 가장 간단하다.
명령줄 도구 sqlite3는 macOS에 기본으로 들어 있고, 리눅스는 `sudo apt install sqlite3` 한 줄, 윈도우는 sqlite.org에서 내려받으면 된다(자세한 설치 방법은 {ch-first-run}에 있다).
연습용 파일을 열고, 표를 만들어 행 하나를 넣고 다시 꺼내 보는 세 문장을 실행해 보자.

[source,text]
----
$ sqlite3 practice.db
sqlite> create table decks (id integer primary key autoincrement, name text not null);
sqlite> insert into decks (name) values ('토익 필수 단어');
sqlite> select * from decks;
1|토익 필수 단어
----

sqlite3는 파일이 없으면 새로 만들고, 문장은 세미콜론(;)까지 쳐야 실행된다.
점으로 시작하는 `.tables`(표 목록)·`.quit`(종료)은 SQL이 아니라 sqlite3의 명령이다.
이 장의 연습 문장을 모아 둔 파일이 저장소의 `language-basic/sql/practice.sql`에 있으니, 처음부터 다시 시작하고 싶으면 `sqlite3 practice.db < practice.sql`로 한 번에 실행하면 된다.
{ch-first-run}에서 앱 서버를 켰을 때 생긴 로컬 데이터베이스 `flashcard.db`도 같은 도구로 열어 볼 수 있다.

== DDL: 데이터의 틀을 만든다

앞에서 스프레드시트처럼 그려 본 두 표의 실제 선언이다.
최소 앱의 `flashcard-basic/schema.sql` 전문인데, {ch-go-sqlite}에서 보겠지만 서버가 시작할 때 통째로 실행되어 데이터베이스의 틀을 만드는 파일이다.
파일 이름의 schema는 이 책에서 자주 쓰는 말이니 여기서 짚고 가자.

.[용어 풀이] 스키마(Schema)
[NOTE]
====
어떤 표가 있고 각 표에 어떤 열과 규칙이 있는지를 적어 둔 데이터베이스의 설계도다.
집으로 치면 도면이고, 그 도면을 SQL로 적어 둔 파일이 `schema.sql`이다.
데이터가 건물이라면 스키마는 건물의 골조라서, 나중에 고치려면 사는 사람을 내보내지 않고 벽을 옮기는 일에 가까워진다(그 작업을 마이그레이션이라 하고 {ch-migrations}에서 다룬다).
====

한 줄이 열 하나이고, 각 줄은 "열 이름, 자료형, 규칙들" 순서로 읽는다.
표 이름 앞의 `if not exists`(이미 있으면 넘어가라) 덕분에 몇 번을 다시 실행해도 안전하다.
맨 끝의 `create index` 한 줄은 이 장의 마지막 절에서 다룬다.

자료형부터 보자.
SQLite가 구분하는 자료형은 문자열(text), 정수(integer), 실수(real) 등 몇 가지뿐이고, 이 스키마는 그중 integer와 text 둘로 끝난다.
`id`의 `integer primary key autoincrement`는 행을 넣을 때마다 데이터베이스가 1, 2, 3으로 번호를 매겨 주는 정수 순번이라, 앞의 스프레드시트 그림에서 `id`가 1과 2였던 것이 여기서 나온 것이다.
카드 표의 `text` 열은 열 이름과 자료형이 같은 단어라 `text text`처럼 두 번 적혔는데, 앞이 이름이고 뒤가 자료형이다.

완성본은 이 정수 순번 대신 UUID라는 식별자를 문자열로 담는다.

.[용어 풀이] UUID(Universally Unique Identifier)
[NOTE]
====
전 세계 어디서 만들어도 값이 겹치지 않도록 고안된 128비트 식별자다.
`3f2a9c81-4b7e-…`처럼 16진수와 붙임표를 섞은 36자 문자열로 적으며, 대부분의 비트를 난수로 채운다.
난수의 범위가 워낙 넓어서 여러 기기가 서로 상의하지 않고 각자 값을 만들어도 같은 값이 나올 확률은 무시할 수 있을 만큼 낮다.
번호표를 나눠 주는 창구에 줄을 서는 대신 각자 도장을 파서 쓰는 방식이라, 번호를 매겨 주는 중앙이 필요 없다.
1, 2, 3으로 이어지는 순번 대신 이 값을 기본 키로 삼은 이유와 그 대가는 {ch-database-design}에서 따진다.
====

자료형은 그 칸에 담길 값의 종류를 못 박는 장치다.
{ch-go-hello}에서 본 Go의 타입이 컴파일 시점의 검증이라면 자료형은 저장 시점의 검증이다.
다만 SQLite는 이 검증이 느슨해서, 정수로 선언한 칸에 글자를 넣어도 대체로 그대로 받아 준다.
그래서 값의 형식은 `check` 같은 제약과, 값을 넣기 전에 확인하는 앱 쪽 Go 코드({ch-go-sqlite}에서 읽는다)가 함께 지킨다.
uuid, timestamptz(시간대를 품은 시각) 같은 전용 자료형이 풍부한 운영 DB는 {ch-supabase-db}에서 다룬다.

나머지 규칙들이 제약이다.

.[용어 풀이] 제약(Constraint)
[NOTE]
====
데이터가 지켜야 할 규칙을 DB에 직접 새겨, 어긴 값은 아예 저장되지 않게 막는 장치다.
"이 칸은 비어 있으면 안 된다"(not null), "이 값은 중복되면 안 된다"(unique)처럼 스프레드시트로는 강제하기 어려운 규칙을 DB가 대신 지켜 준다.
규칙을 애플리케이션 코드가 아니라 데이터 곁에 두면, 어떤 경로로 값이 들어와도 규칙이 똑같이 적용된다.
====

`primary key`는 이 열이 행의 대표 식별자라는 선언이고, `not null`은 그 칸을 비워 둘 수 없다는 뜻이다.
비워 둔 칸에 데이터베이스가 남겨 두는 표시가 NULL이고, `not null`은 그 NULL을 금지하는 제약이다.
이 스키마는 모든 열에 `not null`을 붙였지만, 제약을 붙이지 않은 열(잠시 뒤 연습으로 추가해 볼 `description` 같은 열)은 비워 둘 수 있다.

.[용어 풀이] NULL
[NOTE]
====
값이 채워지지 않은 칸에 데이터베이스가 남겨 두는 특별한 표시로, 숫자 0이나 빈 문자열이 아니라 "값 자체가 없음"을 뜻한다.
설문지의 빈칸이 "0이라고 답했다"가 아니라 "답하지 않았다"인 것과 같다.
설명 열을 만들어 두고 채우지 않은 덱의 `description`도 빈 글자가 들어간 것이 아니라 값이 없는 상태이고, 데이터베이스는 이 둘을 서로 다르게 취급한다.
비교 연산에서도 남달라서, 값이 없는 행은 `= NULL`이 아니라 `is null`로 물어야 찾을 수 있다.
"값이 없다"를 표현할 자리가 필요한 열에만 NULL을 허용하고 나머지는 `not null`로 막는 것이 스키마 설계의 기본이다.
{ch-database-design}은 "아직 공유하지 않은 덱"을 `share_slug`의 NULL로 표현하고, {ch-core-logic}은 그 NULL을 Go 코드에서 어떻게 받을지를 두고 포인터를 꺼내 든다.
====

카드 표의 `references decks (id)`는 외래 키 선언으로, `deck_id`에는 `decks` 표에 실제로 존재하는 덱의 id만 들어갈 수 있다.
존재하지 않는 덱의 카드, 이름 없는 덱 같은 데이터는 코드에 버그가 있어도 저장 단계에서 거부된다.
코드는 고치면 되지만 오염된 데이터는 복구가 어려우므로, 마지막 방어선을 DB에 두는 것이다.
뒤에 붙은 `on delete cascade`는 부모 행이 지워질 때의 동작을 정하는 옵션인데, 삭제 정책의 설계는 {ch-database-design}에서 다룬다.

제약에는 이 스키마에 나온 것 말고도 몇 가지가 더 있다.
`unique`는 한 열에 같은 값이 두 번 나오지 못하게 막고, `default`는 값을 주지 않았을 때 데이터베이스가 대신 채우는 기본값을 정하며, `check`는 괄호 안의 조건에 맞는 값만 받겠다는 선언이다.
완성본의 카드 표는 `check`로 카드 종류를 단어·문장·숙어·개념 넷으로 제한하고 `default`로 기본 종류를 정해 두는데, 그 실물은 {ch-database-design}에서 읽는다.

=== alter table: 만든 틀을 고친다

테이블은 한 번 만들면 끝이 아니다.
Flashcard도 덱 공유 기능이 생기면서 `decks` 표에 `share_slug` 열이 뒤늦게 추가됐다.
이미 만들어 둔 표의 틀을 고치는 문장이 `alter table`이다.
앞서 sqlite3로 만든 연습용 표에서 `alter table decks add column description text;`를 실행해 보자.
`alter table`은 기존 데이터를 유지한 채 틀만 고치므로, 이미 있던 행들은 새 열이 비어 있는 채로 남는다.

틀을 없애는 문장은 `drop`이다.
`drop table decks`는 표를 데이터까지 통째로 지우므로 DDL 중 가장 신중해야 할 문장이다.

데이터가 이미 쌓인 표의 틀을 고치는 일은 처음 만드는 일과 다르다.
열을 더하는 문장을 어제 이미 실행했는지 기억해야 하고, 실행 순서가 어긋나면 컴퓨터마다 표의 모양이 달라진다.
그래서 운영 중인 데이터베이스에서는 이런 구조 변경 문장들을 순서 있는 파일로 쌓아 관리하는데(마이그레이션, migration), 로컬 모드의 `schema.sql`은 매번 통째로 다시 실행해도 되는 한 파일이라 이 문제를 비켜 간다.
데이터가 쌓인 운영 데이터베이스의 틀을 고치는 이야기는 {ch-migrations}에서 본격적으로 다룬다.

== DML: 넣고, 찾고, 고치고, 지운다

이제 틀 안의 데이터 차례다.
DML의 네 동사 `insert`, `select`, `update`, `delete`는 {ch-gin}에서 볼 API의 생성·조회·수정·삭제와 일대일로 대응한다.
덱 API에서 요청을 받아 처리하는 코드인 핸들러(handler, {ch-gin}에서 다룬다)가 store 계층을 부르면, store 계층이 실행하는 것이 바로 이 문장들이다.

=== insert: 행을 만든다

카드 한 장을 만들 때 최소 앱이 실행하는 문장이다({ch-go-sqlite}에서 이 문장을 품은 Go 코드를 읽는다).

[source,sql]
----
insert into cards (deck_id, text, meaning) values (?, ?, ?)
----

괄호 안의 열 목록과 `values`의 값 목록이 순서대로 짝을 이룬다.
목록에 `id`가 없는 것을 눈여겨보자.
`autoincrement` 열이라 데이터베이스가 번호를 매겨 채우므로, 문장에는 사람이 정해 줄 값만 적는다.

`?`는 자리표시자(placeholder)다.
실제 값은 문장과 별도로 전달되고, Go 코드에서는 `s.db.Exec(문장, 값1, 값2, …)`처럼 인자로 넘긴다({ch-go-sqlite}).
값을 문자열 이어 붙이기로 문장 안에 직접 끼워 넣으면 SQL 인젝션(SQL injection) 공격에 뚫리므로, "SQL은 반드시 자리표시자로"가 웹 개발의 철칙이다.

.[용어 풀이] SQL 인젝션(SQL Injection)
[NOTE]
====
사용자가 입력한 값에 SQL 조각을 섞어 넣어, 서버가 실행할 문장의 의미를 공격자가 바꿔치기하는 공격이다.
검색어 칸에 단어 대신 `' or 1=1 --` 같은 문자열을 적어 조건을 "모든 행"으로 뒤집거나, 뒤에 삭제 문장을 덧붙이는 식이다.
빈칸을 채워 넣으라고 건넨 주문서에 주문 대신 새 명령을 적어 넣는 것과 같다.
자리표시자로 넘긴 값은 문장의 일부로 해석되지 않고 언제나 하나의 값으로만 취급되므로 이 공격이 성립하지 않는다.
웹 앱을 노리는 가장 오래된 공격이면서 지금도 흔하므로, 값을 문장에 이어 붙이는 코드는 그 자체로 결함으로 본다.
====

자리표시자 기호는 드라이버마다 다르다.
SQLite는 `?`를 쓰고 완성본의 운영 모드가 쓰는 PostgreSQL 드라이버(pgx, {ch-supabase-db})는 `$1`, `$2`처럼 번호를 붙이지만, 값을 문장 밖에서 따로 전달한다는 원리는 같다.

.[용어 풀이] 드라이버(Driver)
[NOTE]
====
특정 데이터베이스와 대화하는 법을 아는 연결 부품이다.
프로그램이 보낸 SQL을 그 데이터베이스가 알아듣는 통신 규약으로 옮기고, 돌아온 결과를 프로그램이 다룰 수 있는 값으로 되돌려 준다.
나라마다 다른 콘센트에 꽂는 여행용 어댑터와 같아서, 쓰던 기기는 그대로 두고 어댑터만 바꿔 낀다.
그래서 데이터베이스를 바꾸는 일은 드라이버를 바꿔 끼우고 자리표시자 기호처럼 표준에서 벗어난 세부만 손보는 일이 된다.
Flashcard는 로컬 모드에서 SQLite 드라이버를, 운영에서 PostgreSQL 드라이버 pgx를 쓴다({ch-supabase-db}).
====

=== select: 찾아 읽는다

가장 자주 쓰고 표현력도 가장 큰 문장이다.
절을 하나씩 붙여 가며 원하는 결과로 좁혀 가는 구조라, 가장 단순한 형태부터 쌓아 올려 보겠다.

시작은 "이 표에 있는 모든 것"이다.

[source,sql]
----
select * from decks
----

`*`는 모든 열이라는 뜻이다.
필요한 열만 적으면 그 열만 온다.

[source,sql]
----
select text, meaning from cards
----

`where`를 붙이면 가져올 행을 고른다.

[source,sql]
----
select text, meaning from cards where deck_id = ?
----

`order by`는 정렬 순서를, `limit`은 가져올 행 수의 상한을 정한다.
한 덱의 카드를 최근에 만든 순서로 다섯 장만 가져오는 문장이다.

[source,sql]
----
select text, meaning
from cards
where deck_id = ?
order by id desc
limit 5
----

절 단위로 끊어 읽으면 구조가 보인다.
`select`가 가져올 열, `from`이 대상 표, `where`가 행을 고르는 조건, `order by`가 정렬 순서(`desc`는 내림차순), `limit`이 행 수 상한이다.
이 다섯 가지가 조회의 기본 재료이고, 언제나 이 순서로 적는다.

`where deck_id = ?` 조건을 눈여겨보자.
"이 덱의 카드만"이라는 화면의 규칙이 SQL 조건 하나로 구현된 것이다.
여러 사용자를 받는 완성본에서는 같은 자리에 `where user_id = ?`가 빠짐없이 붙어 "내 데이터만"을 지키는데, 그 문장들은 {ch-database-design}에서 읽는다.

행을 그대로 가져오는 대신 세거나 더할 수도 있다.

[source,sql]
----
select count(*) from cards where deck_id = ?
----

`count(*)`는 조건에 맞는 행이 몇 개인지를 숫자 하나로 돌려주는 집계 함수다.
덱 목록에 "카드 12장" 같은 표시를 붙이고 싶다면 이 한 문장이면 된다.
집계에는 count 외에 합계(`sum`), 평균(`avg`) 등이 있고, `group by`와 묶으면 "덱별 카드 수"나 "날짜별 복습 수" 같은 통계도 SQL 한 문장으로 나온다.

최소 앱의 `ListCards`가 실행하는 문장도 방금 쌓아 올린 뼈대 그대로다({ch-go-sqlite}).
`select id, deck_id, text, meaning from cards where deck_id = ? order by id`, 즉 열 목록과 정렬만 다르다.
카드 수를 세어 붙이는 완성본의 실물 통계 쿼리는 {ch-database-design}에서 읽는다.

=== 조인: 나눈 표를 다시 잇는다

표를 나누라고 해 놓고 조회는 어떻게 하나 싶을 텐데, 그 답이 조인이다.

.[용어 풀이] 조인(JOIN)
[NOTE]
====
두 테이블을 공통 값으로 이어 붙여 하나의 표처럼 조회하는 연산이다.
카드 표와 덱 표를 덱 id로 이으면, 카드 내용과 소속 덱의 이름을 한 줄에 놓고 볼 수 있다.
데이터를 주제별 표로 나눠 담는 관계형 모델에서, 나눠 둔 것을 다시 합쳐 읽는 도구다.
====

앞서 봤듯 덱의 이름은 `cards`가 아니라 `decks` 표에만 있다.
카드 내용과 소속 덱의 이름을 함께 보려면 두 표를 잇는다.

[source,sql]
----
select decks.name, cards.text, cards.meaning
from cards
join decks on cards.deck_id = decks.id
----

`join ... on ...`의 `on`이 잇는 규칙이다.
"`cards`의 `deck_id`가 `decks`의 `id`와 같은 행끼리 한 줄로 붙여라"라고 읽으면 된다.
외래 키로 이어 둔 관계를 조회 시점에 다시 합치는 것이므로, 표를 나눠도 조회가 불편해지지 않는다.
완성본은 자주 쓰는 조인을 뷰(view)라는 이름 붙은 조회로 저장해 두고 쓰는데, 그 실물인 `cards_with_stats`는 {ch-database-design}에서 해부한다.

=== update와 delete: 고치고 지운다

최소 앱에서 덱의 이름을 바꿀 때 실행되는 문장이다.

[source,sql]
----
update decks set name = ? where id = ?
----

`set`이 바꿀 열과 새 값, `where`가 바꿀 행을 정한다.
삭제도 구조는 같다.

[source,sql]
----
delete from decks where id = ?
----

여기서 반드시 새겨 둘 것이 하나 있다.
`where`가 없는 `update`와 `delete`도 문법상 유효한 문장이고, 데이터베이스는 군말 없이 표의 모든 행을 고치거나 지운다.
"조건을 빠뜨린 `delete`"는 데이터베이스 사고의 고전이므로, 고치고 지우는 문장은 `where`부터 확인하는 습관이 필요하다.

로그인이 없는 최소 앱은 `id` 조건 하나로 충분하지만, 여러 사용자를 받는 완성본의 같은 문장에는 `where user_id = ? and id = ?`처럼 사용자 조건이 함께 붙는다.
그 조건이 SQL 문장 안에 새겨 둔 인가(authorization) 검사다.
남의 카드 id를 알아내 지우려는 요청이 와도 자기 행이 아니면 조건에 걸리지 않는 이중 안전장치다.

.[용어 풀이] 인증과 인가(Authentication·Authorization)
[NOTE]
====
인증은 "당신이 누구인가"를 확인하는 일이고, 인가는 "그 사람이 이 일을 해도 되는가"를 확인하는 일이다.
건물 입구에서 신분증으로 본인임을 확인받는 것이 인증이고, 그 신분증으로 어느 층의 문까지 열리는지가 인가다.
로그인에 성공했다고 해서 남의 카드를 지울 자격까지 생기는 것은 아니므로, 둘은 반드시 따로 확인해야 한다.
Flashcard에서 인증은 로그인 처리가 맡고(로컬 모드는 고정 사용자, 운영은 {ch-supabase-auth}의 Supabase 로그인), 인가는 모든 쿼리에 빠짐없이 붙는 `user_id` 조건이 맡는다.
====

고치거나 지운 뒤에는 몇 행이 영향을 받았는지가 돌아온다.
이 숫자가 0이면 조건에 맞는 행이 애초에 없었다는 뜻이므로, store 계층은 이 값으로 "그런 덱이 없었다"를 판정한다.
이 판정을 Go 코드로 옮긴 것이 {ch-go-sqlite}에서 읽을 `DeleteCard`이고, 그 결과가 웹에서 "찾는 대상이 없다"는 응답으로 이어지는 과정은 {ch-gin-hello}에서 다룬다.

한편 덱을 지우면 그 덱의 카드들은 어떻게 될까.
답은 앞서 DDL에서 본 `on delete cascade`에 있는데, 삭제 정책의 설계는 {ch-database-design}에서 정리한다.
그리고 여러 문장을 "전부 성공하거나 전부 취소"로 묶는 트랜잭션(transaction)도 복습 기록을 다루는 {ch-domain-model}에서 실제 코드와 함께 다룬다.

== 인덱스: 표가 커져도 빨리 찾는 법

마지막 기초는 조회 속도다.
`where deck_id = ?` 같은 조건으로 행을 찾을 때, 데이터베이스가 표의 모든 행을 처음부터 끝까지 확인하는 것을 전체 스캔(full scan)이라 한다.
행이 백 개일 때는 아무 문제가 없지만, 완성본의 복습 기록처럼 수십만 행씩 쌓이는 표에서는 조회마다 수십만 번의 확인이 일어난다.
훑는 양이 표 크기에 비례해서 늘어나는 것이 문제의 본질이다.

.[용어 풀이] 인덱스(Index)
[NOTE]
====
특정 열의 값을 빠르게 찾도록 미리 정렬해 둔 보조 자료구조로, 책 뒤의 찾아보기(색인)와 같은 역할이다.
찾아보기가 있으면 책장을 처음부터 넘기지 않고 원하는 쪽으로 바로 가듯, 인덱스가 있으면 DB가 모든 행을 훑지 않고 원하는 행으로 곧장 간다.
대신 찾아보기를 최신으로 유지하는 품이 들듯, 인덱스도 데이터를 쓸 때마다 갱신 비용을 치른다.
====

인덱스를 만드는 문장도 DDL이다.
장 앞머리의 `flashcard-basic/schema.sql` 맨 끝에서 미뤄 두었던 그 한 줄, `cards` 표의 `deck_id` 열에 인덱스를 거는 문장이다.

[source,sql]
----
create index if not exists cards_deck_idx on cards (deck_id);
----

SQLite도 다른 관계형 데이터베이스처럼 인덱스의 기본형이 B-tree인데, 값들을 정렬된 상태로 유지하는 트리 구조다.
트리는 값을 층층이 나눠 담아, 위층에서 아래층으로 갈림길을 한 번 고를 때마다 후보가 몇 분의 일로 줄어드는 구조다.
그래서 수십만 행이라도 몇 번만 내려가면 원하는 값에 닿는다.
정렬되어 있으므로 이름순 전화번호부에서 원하는 이름을 찾듯 범위를 크게 좁혀 가며 내려갈 수 있고, 등호 조건(`=`)과 범위 조건(`<`, `>=`), 그리고 `order by` 정렬까지 인덱스의 정렬 순서로 해결된다.
앞서 본 `ListCards`의 `where deck_id = ?`가 이 인덱스 덕분에 카드가 아무리 쌓여도 그 덱의 행으로 곧장 간다.

=== 복합 인덱스와 열 순서

인덱스는 여러 열을 묶어 하나로 만들 수도 있다.
완성본의 심장인 "오늘 복습할 카드" 조회는 사용자와 복습 시각 두 열을 묶은 복합 인덱스가 받친다(실물 SQL은 {ch-database-design}에서).

복합 인덱스는 성(姓)으로 먼저 정렬하고 같은 성 안에서 이름으로 정렬한 명부와 같다.
성을 아는 순간 그 구역으로 바로 가고, 구역 안은 이름순이라 범위를 짚기도 쉽다.

그래서 열 순서가 중요하다.
명부에 빗대면 성이 하나로 딱 정해지는 등치 조건, 이름이 구간을 묻는 범위 조건에 해당한다.
"이 사용자의(`user_id`가 정확히 하나로 정해지는 등치 조건) 복습 시각이 지난(`due_at`이 일정 시점 이전이라는 범위 조건) 카드"라는 질문에는, 등치 조건의 열을 앞에 두고 범위 조건의 열을 뒤에 두는 (등치, 범위) 순서가 들어맞는다.
사용자 구역으로 바로 들어가 `due_at` 순서로 늘어선 행을 앞에서부터 끊어 읽으면 되기 때문이다.

인덱스를 걸었다고 해서 쿼리가 반드시 그 인덱스를 쓰는 것은 아니다.
조건에 맞는 행이 표의 대부분이라면, 인덱스를 거쳐 한 행씩 찾아가는 것보다 표를 통째로 훑는 편이 오히려 빠르다.
어느 경로로 갈지는 표의 크기와 값의 분포를 본 DB가 스스로 정하므로, 짐작하는 대신 쿼리 앞에 `explain query plan`을 붙여 실행 계획(execution plan)을 직접 물어보면 된다.

.[용어 풀이] 실행 계획(Execution Plan)
[NOTE]
====
DB가 이 쿼리를 어떤 경로로 처리하기로 정했는지 적어 둔 계획표다.
어느 인덱스를 탈지, 아니면 표를 통째로 훑을지, 표를 여럿 이을 때는 어느 것부터 읽을지가 여기에 나온다.
같은 목적지라도 지도 앱이 그날의 도로 사정을 보고 경로를 고르듯, DB도 표의 크기와 인덱스를 보고 경로를 스스로 고른다.
그래서 인덱스는 걸어 두는 것으로 끝이 아니라 쿼리가 그 인덱스를 실제로 쓰는지 확인해야 하고, 그 확인 명령이 SQLite의 `explain query plan`(PostgreSQL은 `explain`)이다.
====

이 인덱스를 실제 쿼리가 어떻게 사용하는지는 {ch-database-design}에서 실행 계획으로 확인한다.

=== 인덱스는 공짜가 아니다

인덱스가 이렇게 좋다면 모든 열에 걸면 되지 않을까.
그렇지 않다.
행을 넣거나 고칠 때마다 그 표의 모든 인덱스도 함께 갱신해야 하므로, 인덱스 하나하나가 쓰기 작업의 비용을 늘린다.
저장 공간도 따로 차지한다.
그래서 인덱스는 "일단 다 걸어 두는" 것이 아니라 실제 조회 패턴에서 역산해 필요한 곳에만 건다.

참고로 앞서 본 `unique` 제약은 내부적으로 유니크 인덱스로 구현된다.
중복 검사를 하려면 어차피 같은 값을 빨리 찾아야 하니, 제약과 인덱스는 한 몸이다.

Flashcard가 어떤 조회를 위해 어떤 인덱스를 걸었고, 어떤 열에는 일부러 걸지 않았는지, 실제 인덱스 목록은 {ch-database-design}에서 해부한다.

== 직접 해 보기

`language-basic/sql/practice.sql`로 만든 연습용 데이터베이스에서 확인해 보자.
`sqlite3 practice.db < practice.sql`로 언제든 처음 상태로 되돌릴 수 있으니 마음 놓고 망가뜨려도 된다.

. 카드를 몇 장 더 넣고, 덱 이름과 카드 개수를 한 줄씩 보여 주는 문장을 쓴다. 조인과 `count(*)`, `group by`가 필요하다.
. 존재하지 않는 덱 번호로 카드를 넣어 본다. 외래 키가 이를 막는지 확인하고, 막히지 않는다면 `pragma foreign_keys = on;`을 먼저 실행한 뒤 다시 시도한다. 데이터를 지키는 규칙이 표 자체에 박혀 있다는 것이 이 실험의 요점이다.
. `cards`에 카드를 넉넉히 넣은 뒤 `explain query plan select * from cards where deck_id = 1;`을 실행한다. 이어서 `drop index cards_deck_idx;`로 인덱스를 지우고 같은 문장을 다시 실행해 계획이 어떻게 달라지는지 견준다.
. 카드를 지우지 않은 채로 덱을 지워 본다. 카드가 함께 사라지는 것이 스키마에 적어 둔 `on delete cascade`의 효과다.

== 에이전트 활용 아이디어

이 장에서 익힌 SQL 층을 에이전트와 함께 다룰 때 보태 둘 만한 것들이다.

`CLAUDE.md`에는 스키마의 위치(`flashcard-basic/schema.sql`)와 "쿼리를 새로 쓰면 어떤 인덱스를 타는지 함께 보고하라"는 지침을 적어 둘 만하다.
에이전트는 동작하는 쿼리를 만드는 데는 능하지만, 그 쿼리가 인덱스를 타는지는 지시하지 않으면 확인하지 않는다.

프롬프트에서는 원하는 결과를 SQL 대신 우리말로 적고, 실행 계획 확인까지 한 단계로 묶는 것이 요령이다.
"덱별 카드 수를 많은 순서로 뽑는 쿼리를 작성하고, explain query plan으로 전체 스캔이 없는지 확인해 달라"처럼 검증 방법을 지시문에 함께 넣는다.

자동화 이전의 값싼 검증 습관도 있다.
카드가 쌓인 `flashcard.db` 사본을 놓고 "이 쿼리를 실행해 결과 10행을 보여 달라"고 시키면, 쿼리의 옳고 그름이 내 데이터로 곧장 확인된다.

== 정리

이 장에서는 다음 장의 스키마 해부에 필요한 기초 세 가지를 다졌다.

첫째, 관계형 데이터베이스는 데이터를 테이블(행과 열)에 담되, 같은 사실이 한 곳에만 적히도록 표를 주제별로 나누고 기본 키와 외래 키로 잇는다.

둘째, SQL은 원하는 결과만 서술하는 선언형 언어다.
DDL(create·alter·drop)로 틀을 만들고 제약으로 규칙을 새기며, DML(insert·select·update·delete)로 내용을 다룬다.
값은 자리표시자로 전달해 SQL 인젝션을 막고, 나눈 표는 조인으로 다시 합쳐 읽으며, `update`와 `delete`에서는 `where` 조건이 안전벨트다.

셋째, 인덱스는 조회 비용이 표 크기에 비례해 늘지 않게 하는 찾아보기다.
등치 조건 열을 앞에, 범위 조건 열을 뒤에 두는 복합 인덱스 순서 원칙을 봤고, 쓰기 비용 때문에 조회 패턴에서 역산해 걸어야 한다는 것도 확인했다.

다음 {ch-go-sqlite}에서는 sqlite3 프롬프트에 치던 이 문장들을 Go 코드가 실행하게 만든다.
2부의 남은 세 장은 테이블 둘짜리 최소 플래시카드 앱(`flashcard-basic/`)을 재료로, 데이터 저장부터 웹 서버와 화면 템플릿까지 작은 앱 하나를 완성한다.
Flashcard 완성본의 실제 스키마 해부는 {ch-database-design}에서 이어 간다.
