= Gin 첫걸음: 저장한 데이터를 웹 화면으로

{ch-go-sqlite}에서 읽은 `store.go`의 함수들은 덱과 카드를 넣고 꺼내지만, 그 결과는 아직 테스트나 sqlite3로만 확인할 수 있다.
이 장에서는 그 위에 얹힌 웹 서버를 읽는다.
재료는 같은 앱의 `main.go`와 `handlers.go`, `templates/` 아래의 화면 파일이다.
웹 프레임워크 Gin(진)으로 서버를 띄우고, 주소와 처리 함수를 짝짓고, 폼으로 받은 값을 저장하고, 데이터를 화면과 JSON 두 모양으로 내보내는 최소 사용법을 익힌다.
완성본이 Gin을 어떻게 쓰는지(라우트 그룹, 바인딩, 미들웨어)는 {ch-gin}에서 해부한다.

== 웹 서버가 하는 일

브라우저 주소창에 `http://localhost:8080`을 치면, 브라우저는 그 주소가 가리키는 컴퓨터(여기서는 내 컴퓨터)의 8080번 포트에서 기다리는 프로그램에 "이 주소의 내용을 보여 달라"는 편지를 보낸다.
이 편지가 HTTP 요청(request)이고, 편지를 받는 프로그램이 웹 서버다.
서버는 요청을 읽고 필요한 데이터를 준비해 답장을 돌려보내는데, 이 답장이 HTTP 응답(response)이다.
답장의 내용은 브라우저가 그릴 HTML일 수도 있고, 프로그램이 읽을 JSON일 수도 있다.

들어온 요청의 주소를 보고 어느 함수에 맡길지 정하는 일이 라우팅(routing)이고, 요청 하나를 실제로 처리하는 함수가 핸들러(handler)다.

이 모든 것은 표준 라이브러리의 `net/http`만으로도 만들 수 있지만, 경로에서 값 꺼내기(`/decks/3`의 3), 폼 값 읽기, 템플릿과 JSON으로 응답하기처럼 되풀이되는 일을 직접 다 적어야 한다.
Gin은 이런 일을 한두 줄로 줄여 주는 웹 프레임워크다(고른 이유는 {ch-tech-choices}).

`OpenStore`는 {ch-go-sqlite}에서 읽은 그 함수이고, `defer store.Close()`는 프로그램이 끝날 때 연결을 닫는다.

`gin.SetMode(gin.ReleaseMode)`는 Gin을 릴리스 모드로 바꾼다.
기본인 디버그 모드는 응답마다 템플릿 파일을 다시 읽지만, 릴리스 모드는 시작할 때 한 번만 읽으므로 템플릿을 고치면 서버를 껐다 켜야 한다.

`gin.Default()`는 들어온 요청을 알맞은 처리 함수로 넘겨주는 Gin 엔진 하나를 만든다.
이름이 `Default`인 것은 미들웨어(middleware, 모든 요청이 핸들러 앞뒤로 거치는 공통 처리) 둘이 기본으로 끼워져 있기 때문이다.
요청마다 터미널에 기록을 남기는 Logger와, 처리 도중 사고가 나도 서버 전체가 멎지 않게 받아 내는 Recovery다.
`LoadHTMLGlob("templates/*.html")`은 `templates` 폴더의 HTML 템플릿을 전부 읽어 두어, 핸들러가 파일 이름만으로 화면을 그리게 한다.
`Static("/static", "./static")`은 `/static`으로 시작하는 주소로 오는 요청에 `static` 폴더의 파일(이 앱에는 `style.css` 하나뿐이다)을 그대로 돌려주라는 등록이다.
`registerRoutes`는 이 앱의 함수로, 나머지 주소와 핸들러를 짝짓는다.
마지막의 `r.Run(":8080")`이 요청을 기다리기 시작하는 줄이고, 서버를 끄기 전까지 `main`은 이 줄을 지나가지 않는다.

직접 띄워 보자.

[source,shell]
----
cd flashcard-basic
go run .
----

터미널에 `flashcard-basic listening on http://localhost:8080`이 찍히면 브라우저에서 그 주소를 연다.
처음에는 "아직 덱이 없다"는 빈 목록 화면이 나온다.

[source,go]
----
include::../../flashcard-basic/handlers.go[tag=routes]
----

`r.GET("/", ...)`은 "GET 요청이 `/` 주소로 오면 이 핸들러가 맡는다"는 등록이다.
GET과 POST는 요청의 종류를 나타내는 HTTP 메서드(method)로, GET은 "보여 달라", POST는 "새로 만들거나 처리해 달라"는 뜻이고, 같은 주소라도 메서드가 다르면 다른 요청이다.
브라우저의 폼이 보낼 수 있는 것은 이 둘뿐이라, 자바스크립트가 없는 이 앱에도 둘만 나온다.
{ch-go-types}의 메서드(구조체에 딸린 함수)와는 이름만 같은 다른 개념이다.

{n-basic-routes-ko-attr} 줄을 표로 정리하면 이 앱의 전부가 보인다.

|===
| 메서드 | 경로 | 하는 일

| GET | `/` | 덱 목록 화면
| POST | `/decks` | 덱 만들기
| GET | `/decks/:id` | 한 덱의 카드 목록 화면
| POST | `/decks/:id/rename` | 덱 이름 바꾸기
| POST | `/decks/:id/delete` | 덱 삭제(카드도 함께)
| POST | `/decks/:id/cards` | 카드 추가
| POST | `/decks/:id/cards/:cardID/delete` | 카드 삭제
| GET | `/decks/:id/study` | 학습 화면
| GET | `/api/decks` | 덱 목록을 JSON으로
|===

경로 중간의 `:id`는 그 자리에 오는 값을 이름 붙여 받아 두겠다는 표시다.
`/decks/3`으로 요청이 오면 `id` 자리에 3이 담기고, 핸들러가 꺼내 쓴다.
이렇게 경로에 실려 오는 값을 경로 파라미터(path parameter)라고 부른다.

이 장에서는 그중 넷(덱 목록 화면, 덱 만들기, 카드 목록 화면, JSON 응답)을 읽는다.
카드 추가와 삭제, 학습 화면은 {ch-template-hello}에서 읽고, 덱 이름 바꾸기(`renameDeck`)와 덱 삭제(`deleteDeck`)는 같은 패턴의 반복이라 지면에서는 생략한다.

[source,go]
----
include::../../flashcard-basic/handlers.go[tag=show-decks]
----

`showDecks` 자체는 핸들러가 아니라, `store`를 받아 핸들러를 만들어 돌려주는 함수다.
첫 줄 끝의 `gin.HandlerFunc`가 "핸들러 하나"를 뜻하는 타입이고, `return func(c *gin.Context) {`부터가 실제로 돌려주는 핸들러다.
돌려준 안쪽 함수는 바깥에서 받은 `store`를 기억해서 요청이 올 때마다 그 저장소로 데이터를 가지러 가고, 라우팅 코드에서 `showDecks(store)`처럼 괄호를 붙여 등록한 이유가 이것이다.
이 구조의 원리(팩토리 함수, 클로저)는 {ch-gin}에서 다루니, 지금은 "핸들러에 저장소를 쥐여 주는 포장"으로 읽으면 된다.

안쪽 함수의 매개변수 `c *gin.Context`는 요청 하나에 딸린 모든 것을 담은 값으로, 요청에서 값을 꺼내는 일도 응답을 만드는 일도 전부 `c`를 통한다.
몸통은 `store.ListDecks()`를 부르고 바로 에러부터 확인한다.
실패하면 `c.String`으로 에러 메시지를 보내는데, 첫 인자 `http.StatusInternalServerError`(500)는 "서버 쪽에서 사고가 났다"는 상태 코드(status code)다.
상태 코드는 응답마다 붙는 세 자리 숫자로, 요청이 잘 처리됐는지를 브라우저에 알린다.

성공하면 `c.HTML`이 상태 코드 200(`http.StatusOK`, "성공했다")과 함께 `decks.html`에 데이터를 끼워 그린 HTML을 돌려준다.
셋째 인자의 `gin.H`는 이름과 값의 쌍을 담는 맵({ch-go-types})으로, `gin.H{"Decks": decks}`는 "템플릿에 `Decks`라는 이름으로 덱 목록을 건넨다"고 읽는다.

== 템플릿이 데이터를 화면으로 그린다

핸들러가 건넨 데이터는 `flashcard-basic/templates/decks.html`이 받는다.
건네받은 덱들을 하나씩 돌며 목록의 한 줄로 찍는 부분이다.

[source,html]
----
include::../../flashcard-basic/templates/decks.html[tag=deck-list]
----

HTML 사이의 `{{...}}`가 데이터가 들어갈 자리다.
`{{range .Decks}}`는 `Decks` 목록을 하나씩 돌며 안쪽 HTML을 반복해 찍으라는 뜻이고, `{{.Name}}`은 지금 보고 있는 덱의 `Name` 값을 그 자리에 넣으라는 뜻이다.
`{{.ID}}`로는 덱마다 `/decks/3` 같은 링크가 만들어지고, `{{else}}`는 목록이 비었을 때 찍을 내용(처음 본 "아직 덱이 없다")이다.

이처럼 화면의 구조를 HTML로 적어 두고 데이터가 들어갈 자리만 비워 두었다가 요청마다 채워 그리는 파일을 템플릿(template)이라고 한다.
html/template의 문법은 {ch-template-hello}에서 익히므로, 이 장에서는 `{{range}}`와 `{{.필드}}` 두 가지면 충분하다.

----

`c.PostForm("name")`이 폼에서 `name` 칸의 값을 꺼낸다.
`strings.TrimSpace`로 앞뒤 공백을 걷어 낸 뒤, 빈 문자열이면 저장하지 않고 400(`http.StatusBadRequest`, "요청이 잘못됐다")으로 답한다.

폼에 `required`가 있는데도 서버가 또 검사하는 것은, 잠시 뒤에 쓸 curl 같은 도구로 폼을 거치지 않고도 빈 이름의 POST 요청을 보낼 수 있기 때문이다.
브라우저의 검증은 사용자를 위한 편의이고, 데이터를 지키는 최종 검증은 서버 몫이다.

저장에 성공하면 `c.Redirect(http.StatusSeeOther, "/")`로 "`/` 주소를 GET으로 다시 봐 달라"고 답하고, 브라우저는 덱 목록을 새로 요청해 그린다.
성공 화면을 곧바로 그리지 않는 데는 이유가 있다.
POST 응답으로 화면을 그리면 새로고침할 때마다 마지막 요청인 POST가 되풀이되어 같은 덱이 자꾸 만들어진다.
리다이렉트(redirect)를 끼우면 마지막 요청이 GET이라 새로고침이 안전하다(이 패턴의 이름과 사연은 {ch-html-template}에서 다룬다).

----

----

`c.Param("id")`가 라우팅의 `:id` 자리에 온 값을 꺼낸다.
주소는 글자의 나열이라 이 값도 숫자가 아닌 문자열 `"3"`이므로, `strconv.ParseInt`로 정수로 바꾸고 `/decks/abc`처럼 변환이 실패하면 400으로 답한다.

`store.GetDeck`은 찾는 덱이 없으면 `ErrNotFound`를 돌려준다.
저장소는 HTTP를 모르므로 "없다"는 사정을 에러 값으로만 알리고, 그것을 어떤 상태 코드로 전할지는 핸들러가 정한다.
`errors.Is`로 그 에러인지 확인해 404(`http.StatusNotFound`, "그런 자원이 없다")로 답하고, 그 밖의 에러는 서버 쪽 사고이므로 500으로 답한다.
잘못된 요청은 400, 없는 것은 404, 서버의 사고는 500이다.
두 관문을 통과하면 카드 목록을 꺼내 `cards.html`에 덱과 카드를 함께 넘긴다.

서버를 띄워 둔 채 다른 터미널에서 curl(브라우저 없이 터미널에서 HTTP 요청을 보내는 도구)로 확인해 보자.

[source,shell]
----
curl http://localhost:8080/api/decks
----

화면에서 덱을 하나 만들어 두었다면 결과는 이렇다.

[source,text]
----
[{"id":1,"name":"토익 필수 단어"}]
----

대괄호는 목록, 중괄호 하나가 덱 하나다.
키가 `ID`, `Name`이 아니라 소문자 `id`, `name`인 것은 {ch-go-sqlite}에서 본 `Deck` 구조체의 필드 옆에 붙은 `` `json:"id"` `` 표기 덕분이다.

이 주소는 화면 어디에도 연결되어 있지 않지만, 휴대폰 앱이든 다른 서버든 터미널의 curl이든 덱 목록이 필요한 프로그램은 같은 JSON을 받는다.
화면 없이 데이터만 주고받는 이런 창구가 API다.

== 직접 해 보기

`flashcard-basic`을 띄워 둔 채 고치고 확인해 보자.
서버를 껐다 켜야 새 코드가 반영되므로, 터미널 하나에는 `go run .`을, 다른 하나에는 curl을 두고 오가면 편하다.

. 덱 하나의 카드 목록을 JSON으로 돌려주는 `/api/decks/:id/cards` 라우팅을 더한다. `listDecksJSON`과 `showCards`를 절반씩 섞으면 나온다.
. 없는 덱 번호로 그 주소를 부르면 404가 나오는지 curl로 확인한다. `curl -i`로 부르면 응답의 상태 줄까지 보인다.
. 덱 이름에 1만 자짜리 문자열을 넣어 만들어 본다. 브라우저 폼으로도, 폼을 거치지 않는 curl(`curl -d "name=$(printf 'a%.0s' $(seq 1 10000))" http://localhost:8080/decks`)로도 시도한다. 지금의 `createDeck`은 빈 이름만 거르므로 둘 다 그대로 저장되는데, 길이를 제한하려면 어느 쪽에 검사를 두어야 하는지 생각해 본다.

== 에이전트 활용 아이디어

기능을 시키기 전에 라우팅부터 정하게 한다.
"카드를 고치는 기능을 넣어 달라" 대신 "필요한 메서드·경로·상태 코드를 표로 먼저 제안하라, 승인하면 구현하라"고 하면, 코드 수십 줄보다 빨리 검토할 수 있는 표 한 벌로 어긋난 설계를 구현 전에 바로잡을 수 있다.

핸들러를 만들었으면 "정상 요청, 잘못된 입력, 없는 번호 세 경우를 curl로 직접 호출해 상태 코드와 응답 본문까지 보여 달라"고 지시한다.
그럴듯한 핸들러도 에러 경로는 빠뜨리기 쉬운데, 400과 404가 실제로 찍힌 실행 결과는 얼버무릴 수 없다.
잘못될 수 있는 입력(음수 번호, 빈 문자열, 지나치게 긴 이름)을 먼저 나열하게 하면 이 검증의 목록이 된다.

== 정리

첫째, 웹 서버는 요청을 받아 응답을 돌려주는 왕복을 반복하고, Gin은 라우팅과 폼 읽기, HTML·JSON 응답을 몇 줄로 줄여 준다.

둘째, 서버는 `main` 함수 하나로 뜬다.
`gin.Default()`로 엔진을 만들고, `LoadHTMLGlob`으로 템플릿을, `Static`으로 정적 파일을 연결하고, 라우팅을 등록한 뒤 `Run(":8080")`으로 요청을 기다린다.

셋째, 핸들러는 `store`를 다녀와 `c.HTML`로 화면을, `c.JSON`으로 데이터를 돌려준다.

넷째, 폼 값은 `c.PostForm`으로 받아 서버가 다시 검증하고, 저장이 끝나면 리다이렉트로 답해 새로고침이 중복 제출로 이어지지 않게 한다.

다섯째, 잘못된 요청은 400, 없는 자원은 404, 서버의 사고는 500이고, `ErrNotFound` 같은 저장 계층의 에러를 몇 번으로 옮길지는 핸들러가 정한다.

다음 {ch-template-hello}에서는 뜻만 짚고 지나친 `{{range}}`와 `{{.필드}}`를 비롯한 html/template의 문법을 익히고, 라우팅 표에 남은 세 줄(카드 추가, 카드 삭제, 학습 화면)의 핸들러까지 읽어 최소 앱 한 바퀴를 마친다.
