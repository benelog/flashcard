= Gin 첫걸음: 저장한 데이터를 웹 화면으로

{ch-go-sqlite}에서 최소 플래시카드 앱 `flashcard-basic`의 저장 계층을 읽었다.
`store.go`의 함수들은 덱과 카드를 SQLite 파일에 넣고 꺼내지만, 그 결과를 확인할 길이 아직 코드 안에만 있다.
이번 장에서는 그 위에 웹 서버를 얹는다.
브라우저로 덱 목록을 보고, 폼으로 새 덱을 만들고, 같은 데이터를 JSON으로도 꺼내는 데까지 간다.

재료는 같은 앱의 `main.go`와 `handlers.go`, 그리고 `templates/` 아래의 화면 파일이다.
웹 프레임워크 Gin(진)으로 서버를 띄우고, 주소와 처리 함수를 짝짓고, 폼으로 받은 값을 저장하고, 저장소에서 꺼낸 데이터를 화면과 JSON 두 가지 모양으로 내보내는 최소 사용법을 익힌다.
완성본 앱이 Gin을 어떻게 쓰는지(라우트 그룹, 바인딩, 미들웨어)는 {ch-gin}에서 해부하므로, 이 장은 그 장을 읽기 위한 첫걸음이다.
여기서 일곱 개짜리 라우팅과 핸들러 한 줌으로 감을 잡아 두면, {ch-gin}에서 완성본의 라우팅 수십 개를 만나도 낯설지 않다.

== 웹 서버가 하는 일

코드로 들어가기 전에, 웹 서버가 무슨 일을 하는 물건인지부터 그려 보자.

브라우저 주소창에 `http://localhost:8080`을 치면 무슨 일이 벌어지는가.
브라우저는 그 주소가 가리키는 컴퓨터(여기서는 내 컴퓨터)의 8080번 포트에서 기다리고 있는 프로그램에 "이 주소의 내용을 보여 달라"는 편지를 보낸다.
이 편지가 HTTP 요청(request)이고, 편지를 받는 프로그램이 웹 서버다.
서버는 요청을 읽고, 필요한 데이터를 준비해, 답장을 만들어 돌려보낸다.
이 답장이 HTTP 응답(response)이다.
답장의 내용은 브라우저가 그릴 HTML일 수도 있고, 프로그램이 읽을 JSON일 수도 있다.
웹 서버가 하는 일은 이 왕복의 반복이 전부다.

서버 쪽에서 이 왕복을 처리하려면 두 가지가 필요하다.
들어온 요청의 주소를 보고 어느 함수에 맡길지 정하는 일이 라우팅(routing)이고, 그렇게 연결되어 요청 하나를 실제로 처리하는 함수가 핸들러(handler)다.
우편물 겉면의 주소를 보고 담당자를 정하는 일과, 그 담당자가 답장을 쓰는 일이라고 보면 된다.

이 모든 것은 {ch-go-hello}에서 소개한 표준 라이브러리의 `net/http`만으로도 만들 수 있다.
다만 경로에서 값 꺼내기(`/decks/3`의 3), 폼 값 읽기, 템플릿과 JSON으로 응답하기처럼 웹 서버마다 되풀이되는 일을 직접 다 적어야 한다.
Gin은 이런 일을 한두 줄로 줄여 주는 웹 프레임워크이고, 이 앱이 Gin을 고른 사연과 대안 비교는 {ch-tech-choices}에서 이미 다뤘다.
곧 보겠지만 핸들러 안에서 `c.PostForm`, `c.HTML`, `c.JSON` 한 줄씩이면 폼 읽기와 두 가지 응답이 끝난다.

----
include::../../flashcard-basic/main.go[tag=main]

첫 부분의 `OpenStore`는 {ch-go-sqlite}에서 읽은 그 함수다.
파일을 열고 스키마를 적용해 `Store`를 돌려주고, `defer store.Close()`는 프로그램이 끝날 때 연결을 닫는다.

그다음 네 줄이 이 장의 주인공이다.
`gin.Default()`는 요청 기록과 사고 수습 같은 기본 기능이 미리 붙은 Gin 엔진 하나를 만든다.
`LoadHTMLGlob("templates/*.html")`은 `templates` 폴더의 HTML 템플릿을 전부 읽어 두어, 핸들러가 파일 이름만으로 화면을 그릴 수 있게 준비한다.
`Static("/static", "./static")`은 `/static`으로 시작하는 주소로 오는 요청에 `static` 폴더의 파일(CSS, 자바스크립트)을 그대로 돌려주라는 등록이다.
`registerRoutes`는 우리가 만든 함수로, 나머지 주소와 핸들러를 짝짓는다(바로 다음 절에서 본다).

마지막의 `r.Run(":8080")`이 문을 여는 줄이다.
8080번 포트에서 요청을 기다리기 시작하고, 이 줄에서 프로그램은 끝나지 않고 계속 돌며 요청이 올 때마다 핸들러를 부른다.
서버를 끄기 전까지 `main`은 이 줄을 지나가지 않는다.

직접 띄워 보자.
Go는 {ch-first-run}에서 설치했으니, 저장소의 `flashcard-basic` 폴더로 가서 실행하면 된다.

[source,shell]
----
cd flashcard-basic
go run .
----

터미널에 서버가 8080번 포트를 듣기 시작했다는 로그가 찍히면, 브라우저에서 `http://localhost:8080`을 연다.
처음에는 "아직 덱이 없다"는 빈 목록 화면이 나온다.
이 화면이 어디서 오는지를 지금부터 따라가 보겠다.

== 주소와 핸들러를 짝짓는 라우팅

이 앱의 주소 지도는 `flashcard-basic/handlers.go`의 함수 하나에 모여 있다.
어떤 주소로 온 어떤 요청을 어느 핸들러가 맡는지를 한 줄에 하나씩 등록하는 코드다.

[source,go]
----
include::../../flashcard-basic/handlers.go[tag=routes]
----

`r.GET("/", ...)`은 "GET 요청이 `/` 주소로 오면 이 핸들러가 맡는다"는 등록이다.
GET, POST, DELETE는 요청의 종류를 나타내는 HTTP 메서드(method)다.
GET은 "보여 달라", POST는 "새로 만들어 달라", DELETE는 "지워 달라"는 뜻으로, 같은 주소라도 메서드가 다르면 다른 요청이다.
{ch-go-types}에서 본 Go의 메서드(구조체에 딸린 함수)와 이름만 같은 다른 개념이니 헷갈리지 말자.

일곱 줄을 표로 정리하면 이 앱의 전부가 보인다.

|===
| 메서드 | 경로 | 하는 일

| GET | `/` | 덱 목록 화면
| POST | `/decks` | 덱 만들기
| GET | `/decks/:id` | 한 덱의 카드 목록 화면
| POST | `/decks/:id/cards` | 카드 추가
| DELETE | `/cards/:id` | 카드 삭제
| GET | `/decks/:id/study` | 학습 화면
| GET | `/api/decks` | 덱 목록을 JSON으로
|===

경로 중간의 `:id`는 그 자리에 오는 값을 이름 붙여 받아 두겠다는 표시다.
`/decks/3`으로 요청이 오면 `id` 자리에 3이 담기고, 핸들러가 꺼내 쓴다.
이렇게 경로에 실려 오는 값을 경로 파라미터(path parameter)라고 부른다.

이 장에서는 표의 일곱 줄 중 넷을 읽는다.
덱 목록 화면, 덱 만들기, 카드 목록 화면, 그리고 JSON 응답이다.
카드 추가와 삭제, 학습 화면은 {ch-htmx-hello}의 재료로 남겨 둔다.
특히 DELETE는 브라우저의 폼이 보낼 수 없는 메서드라(폼은 GET과 POST만 안다), 그 요청을 누가 보내는지도 다음 장에서 밝혀진다.

저장소에서 덱 목록을 꺼내 `decks.html` 템플릿에 넘겨 화면을 그린다.

[source,go]
----
include::../../flashcard-basic/handlers.go[tag=show-decks]
----

모양이 조금 특이하다.
`showDecks` 자체는 핸들러가 아니라, `store`를 받아 핸들러를 만들어 돌려주는 함수다.
돌려준 안쪽 함수가 바깥에서 받은 `store`를 계속 기억하고 있어서, 요청이 올 때마다 그 저장소로 데이터를 가지러 갈 수 있다.
앞 절의 라우팅 코드에서 `showDecks(store)`처럼 괄호를 붙여 등록한 이유가 이것이다.
이 구조에 붙은 이름과 원리(팩토리 함수, 클로저)는 {ch-gin}에서 제대로 다루니, 지금은 "핸들러에 저장소를 쥐여 주는 포장"으로 읽으면 된다.

안쪽 함수의 매개변수 `c *gin.Context`는 요청 하나에 딸린 모든 것을 담은 값이다.
요청에서 값을 꺼내는 일도, 응답을 만드는 일도 전부 `c`를 통한다.

몸통은 {ch-go-hello}에서 익힌 리듬 그대로다.
`store.ListDecks()`를 부르고, 바로 다음 줄에서 에러부터 확인한다.
실패하면 `c.String`으로 에러 메시지를 담은 응답을 보내는데, 이때 첫 인자로 넘기는 `http.StatusInternalServerError`(500)는 "서버 쪽에서 사고가 났다"는 상태 코드(status code)다.
상태 코드는 응답마다 붙는 세 자리 숫자로, 요청이 잘 처리됐는지를 브라우저에 알린다.

성공하면 마지막 줄의 `c.HTML`이 응답을 만든다.
"성공했다"는 상태 코드 200(`http.StatusOK`)과 함께, 읽어 둔 템플릿 중 `decks.html`을 골라 데이터를 끼워 그린 HTML을 돌려준다.
셋째 인자의 `gin.H`는 이름과 값의 쌍을 담는 맵이다({ch-go-types}에서 본 그 맵이다).
`gin.H{"Decks": decks}`는 "템플릿에 `Decks`라는 이름으로 덱 목록을 건넨다"고 읽는다.

== 템플릿이 데이터를 화면으로 그린다

핸들러가 건넨 데이터는 화면 쪽 파일이 받는다.
`flashcard-basic/templates/decks.html`에서 덱 목록을 그리는 부분이다.
건네받은 덱들을 하나씩 돌며 목록의 한 줄로 찍는다.

[source,html]
----
include::../../flashcard-basic/templates/decks.html[tag=deck-list]
----

HTML 사이에 낀 `{{...}}`가 데이터가 들어갈 자리다.
`{{range .Decks}}`는 핸들러가 `Decks`라는 이름으로 넘긴 목록을 하나씩 돌며 안쪽 HTML을 반복해 찍으라는 뜻이고, `{{.Name}}`은 지금 보고 있는 덱의 `Name` 필드 값을 그 자리에 넣으라는 뜻이다.
`{{.ID}}`도 마찬가지여서, 덱마다 자기 번호가 담긴 `/decks/3` 같은 링크가 만들어진다.
`{{else}}`는 목록이 비었을 때 대신 찍을 내용이다.
서버를 처음 띄웠을 때 본 "아직 덱이 없다"가 여기서 나왔다.

이런 파일을 템플릿(template)이라고 한다.
화면의 뼈대는 HTML로 미리 적어 두고, 데이터가 들어갈 자리만 비워 두었다가 요청마다 채워 그리는 방식이다.
Go에 내장된 html/template의 문법과 안전장치는 {ch-go-templates}에서 본격적으로 다루므로, 이 장에서는 `{{range}}`와 `{{.필드}}` 두 가지면 충분하다.

[source,go]
----
include::../../flashcard-basic/handlers.go[tag=create-deck]
----

`c.PostForm("name")`이 폼에서 `name` 칸의 값을 꺼내는 한 줄이다.
`strings.TrimSpace`로 앞뒤 공백을 걷어 낸 뒤, 빈 문자열이면 저장하지 않고 400(`http.StatusBadRequest`, "요청이 잘못됐다")으로 답한다.

폼에 `required`를 붙였는데 서버가 또 검사하는 것이 이상해 보일 수 있다.
그런데 요청은 폼을 거치지 않고도 만들 수 있다.
잠시 뒤에 쓸 curl 같은 도구로 누구든 빈 이름의 POST 요청을 지어 보낼 수 있으므로, 브라우저의 검증은 사용자를 위한 편의일 뿐이고 데이터를 지키는 최종 검증은 언제나 서버 몫이다.

저장에 성공하면 `c.Redirect(http.StatusSeeOther, "/")`로 답한다.
"할 일은 끝났으니 `/` 주소를 GET으로 다시 봐 달라"는 응답이고, 브라우저는 이 답을 받으면 덱 목록 화면을 새로 요청해 그린다.
방금 만든 덱이 목록에 나타나는 이유다.
성공 화면을 곧바로 그려 주지 않고 한 번 돌려보내는 이 관례에는 이유가 있다.
POST 응답으로 화면을 그리면 사용자가 새로고침을 누를 때마다 마지막 요청인 POST가 되풀이되어 같은 덱이 자꾸 만들어지는데, 리다이렉트(redirect)를 사이에 끼우면 마지막 요청이 GET이라 새로고침이 안전하다.
이 패턴의 이름과 자세한 사연은 {ch-go-templates}에서 다룬다.

== 경로 파라미터와 404

[source,go]
----
include::../../flashcard-basic/handlers.go[tag=show-cards]
----

첫 줄의 `c.Param("id")`가 라우팅의 `:id` 자리에 온 값을 꺼낸다.
주소는 글자의 나열이므로 이 값도 숫자가 아니라 문자열 `"3"`이다.
그래서 `strconv.ParseInt`로 정수로 바꾸고, `/decks/abc`처럼 숫자가 아닌 것이 오면 변환이 실패하므로 400으로 답한다.

다음이 이 절의 눈여겨볼 대목이다.
`store.GetDeck`은 {ch-go-sqlite}에서 봤듯 찾는 덱이 없으면 `ErrNotFound`를 돌려준다.
저장소는 HTTP를 모르므로 "없다"는 사정을 에러 값으로만 알리고, 그것을 브라우저에 어떤 상태 코드로 전할지는 핸들러가 정한다.
`errors.Is`로 그 에러인지 확인해 404(`http.StatusNotFound`, "그런 자원이 없다")로 답하고, 그 밖의 에러는 서버 쪽 사고이므로 500으로 답한다.
잘못된 요청은 400, 없는 것은 404, 서버의 사고는 500.
저장 계층의 에러를 상태 코드로 번역하는 이 감각은 앞으로 어떤 핸들러를 읽든 되풀이해 나온다.

두 관문을 통과하면 카드 목록을 꺼내 `cards.html` 템플릿에 덱과 카드를 함께 넘긴다.
그 화면 안의 폼과 버튼이 어떻게 움직이는지는 {ch-htmx-hello}에서 이어 본다.

== 같은 데이터를 JSON으로도

마지막 라우팅 한 줄이 남았다.
`/api/decks`를 맡은 `flashcard-basic/handlers.go`의 `listDecksJSON`은 덱 목록 화면과 똑같은 데이터를 사람이 볼 화면 대신 프로그램이 읽을 JSON으로 내보낸다.

[source,go]
----
include::../../flashcard-basic/handlers.go[tag=list-decks-json]
----

`showDecks`와 나란히 놓고 보면 다른 곳은 응답을 만드는 마지막 줄뿐이다.
`c.HTML`이 있던 자리에 `c.JSON`이 왔다.
이 한 줄이 덱 목록을 JSON 문자열로 바꿔 응답에 담는다.
저장소에서 데이터를 꺼내는 일까지는 화면과 API가 완전히 같고, 그것을 어떤 옷을 입혀 내보내느냐만 다르다.
주소를 `/api` 아래에 모아 둔 것은 화면 주소와 데이터 주소를 구분하는 흔한 관례다.

서버를 띄워 둔 채 다른 터미널에서 확인해 보자.
curl은 브라우저 없이 터미널에서 HTTP 요청을 보내는 도구다.

[source,shell]
----
curl http://localhost:8080/api/decks
----

화면에서 덱을 하나 만들어 두었다면 결과는 이렇다.

[source,text]
----
[{"id":1,"name":"토익 필수 단어"}]
----

대괄호는 목록, 중괄호 하나가 덱 하나다.
키가 `ID`, `Name`이 아니라 소문자 `id`, `name`인 것은 {ch-go-sqlite}에서 본 `Deck` 구조체의 필드 옆에 붙은 `` `json:"id"` `` 표기 덕분이다.
JSON으로 내보낼 때 쓸 이름을 필드마다 적어 둔 것이라고만 알아 두자.

이 주소는 브라우저 화면 어디에도 연결되어 있지 않지만, 덱 목록이 필요한 프로그램이라면 무엇이든 쓸 수 있다.
휴대폰 앱이든, 다른 서버든, 방금처럼 터미널의 curl이든 같은 JSON을 받는다.
화면 없이 데이터만 주고받는 이런 창구가 API이고, 완성본 앱이 API를 어떻게 짜임새 있게 키우는지는 {ch-gin}에서 본다.

== 에이전트 활용 아이디어

웹 서버를 처음 만지는 단계에서 에이전트를 쓰는 요령이다.

기능을 시키기 전에 라우팅부터 정하게 하자.
"덱 이름 바꾸기 기능을 넣어 달라"고 곧장 시키는 것보다 "필요한 메서드·경로·상태 코드를 표로 먼저 제안하라, 승인하면 구현하라"가 낫다.
이 장의 라우팅 표에서 봤듯 표 한 벌이면 앱의 창구 전체가 드러나므로, 코드 수십 줄보다 표 한 줄을 검토하는 편이 빠르고, 어긋난 설계를 구현 전에 돌려세울 수 있다.

핸들러를 만들었으면 curl 호출 결과로 검증을 받자.
"정상 요청, 잘못된 입력, 없는 번호 세 경우를 curl로 직접 호출해 상태 코드와 응답 본문까지 보여 달라"고 지시한다.
겉보기에 그럴듯한 핸들러도 에러 경로는 빠뜨리기 쉬운데, 400과 404가 실제로 찍힌 실행 결과는 설명과 달리 얼버무릴 수 없다.

에러 경우의 목록을 뽑는 일도 시켜 볼 만하다.
"이 핸들러에서 잘못될 수 있는 입력을 모두 나열하고 각각 어떤 상태 코드로 답할지 정리하라"고 하면, 사람이 미처 떠올리지 못한 경우(음수 번호, 빈 문자열, 지나치게 긴 이름)가 목록에 올라온다.
에러를 상태 코드로 번역하는 이 장의 감각을 검토 기준으로 그대로 쓸 수 있다.

== 정리

첫째, 웹 서버는 요청을 받아 응답을 돌려주는 왕복을 반복하는 프로그램이다.
주소와 핸들러를 짝짓는 것이 라우팅이고, Gin은 이 배선과 폼 읽기, HTML·JSON 응답을 몇 줄로 줄여 주는 웹 프레임워크다.

둘째, 서버는 `main` 함수 하나로 뜬다.
`gin.Default()`로 엔진을 만들고, `LoadHTMLGlob`으로 템플릿을 읽어 두고, `Static`으로 정적 파일을 물리고, 라우팅을 등록한 뒤 `Run(":8080")`으로 문을 연다.

셋째, 핸들러는 `store`를 다녀와 `c.HTML`로 화면을, `c.JSON`으로 데이터를 돌려준다.
저장소에서 꺼내는 데이터는 같고 내보내는 옷만 다르다.
템플릿은 `{{range}}`로 목록을 돌고 `{{.필드}}`로 값을 채운다.

넷째, 폼 값은 `c.PostForm`으로 받고, 브라우저가 걸러 줘도 서버가 다시 검증하며, 저장이 끝나면 리다이렉트로 답해 새로고침이 중복 제출로 이어지지 않게 한다.

다섯째, 에러는 상태 코드로 번역한다.
잘못된 요청은 400, 없는 자원은 404, 서버의 사고는 500이고, `ErrNotFound` 같은 저장 계층의 에러 값을 몇 번으로 옮길지는 핸들러가 정한다.

한 가지 아쉬움을 남겨 두었다.
지금은 폼을 제출할 때마다 서버가 페이지 전체를 새로 그려 보낸다.
덱 하나를 만들어도, 카드 한 장을 더해도 화면 전체가 다시 온다.
다음 {ch-htmx-hello}에서는 htmx로 바뀐 조각만 받아 화면 일부만 갈아 끼우는 방법을 익힌다.
카드 추가와 삭제 라우팅을 남겨 둔 이유가 거기 있다.
