= 검토한 대안 기술: 언제 다른 선택이 더 나은가

{ch-tech-choices}에서는 데이터베이스, 백엔드 언어, 웹 프레임워크, 화면 렌더링의 네 계층에서 고른 쪽이 무엇을 해 주는지에 집중했다.
이 부록에는 저울의 반대편에 올라가 있던 후보를 모으고, 4부에서 정한 배포 플랫폼과 인증의 대안도 뒤쪽 두 절에 함께 두었다.
조건이 달라지면 답도 달라지므로 후보마다 "언제 그쪽이 더 나은가"를 적는다.
여기 나오는 이름들은 본문을 따라가는 데 필요하지 않으니, 낯설면 건너뛰었다가 자기 앱을 설계할 때 돌아와도 된다.

== 데이터베이스: 문서형 NoSQL

관계형 자체의 대안은 문서형 NoSQL(MongoDB, Firestore 등)이고, "덱 문서 안에 카드 배열을 통째로 저장하고 통째로 읽는" 구조라면 이쪽이 더 단순할 수 있다.

.[용어 풀이] NoSQL과 문서형 데이터베이스
[NOTE]
====
NoSQL은 데이터를 테이블과 테이블의 관계로 담지 않는 데이터베이스를 통칭하는 말이다.
그중 가장 널리 쓰이는 문서형은 데이터를 테이블의 한 줄이 아니라 그 자체로 완결된 한 덩어리(문서)로 저장한다.
덱 하나를 예로 들면, 카드 목록까지 통째로 품은 서류 한 장을 서랍에 넣어 두는 모습에 가깝다.
====

그러나 Flashcard는 카드를 덱 단위가 아니라 개별 단위로 다룬다.
"오늘 복습할 카드"는 덱의 경계를 넘어 복습 예정 시각으로 모으고, 스마트 덱은 오답률·태그 같은 조건으로 여러 덱의 카드를 가로질러 조회한다.
이런 조인과 인덱스 조회는 관계형 모델이 가장 잘하는 일이고({ch-database-basics}), 문서 DB에서는 데이터를 여러 문서에 복사해 두고 손으로 맞추는 일이 늘어난다.

문서형이 유리한 조건은 셋이다.
데이터의 모양이 자주 바뀌어 테이블을 미리 정의하기 어렵거나, 읽고 쓰는 단위가 늘 문서 하나로 떨어지거나, 여러 문서를 가로지르는 조회가 거의 없는 경우다.
Flashcard는 셋 다 아니었다.

== 데이터베이스: 처음부터 PostgreSQL 하나만 쓰기

Flashcard는 로컬 개발에 SQLite를, 운영에 PostgreSQL을 쓰는데, 하나로 통일하는 방향도 둘 있다.

처음부터 PostgreSQL 하나만 쓰면 방언 차이를 신경 쓸 일이 없고 저장소 구현도 한 벌이면 된다.
대신 독자가 첫 장부터 데이터베이스 서버를 설치하거나 계정을 만들어야 하고, 인터넷이 끊기면 실습이 멈춘다.
이 책은 3부까지를 내 컴퓨터 안에서 완결하려고 이 비용을 받아들이지 않았다.
이미 PostgreSQL을 로컬에 갖추고 있거나 팀이 함께 쓰는 개발 데이터베이스가 있다면 이쪽이 더 단순하다.

반대로 SQLite 하나로 운영까지 가는 길도 있다.
상주 서버 한 대에 배포하는 앱이라면 그 서버의 디스크에 놓인 파일 하나가 곧 데이터베이스가 되고, 백업이 파일 복사로 끝나 운영 부담이 가장 작다.
Flashcard가 이 길을 못 간 것은 배포처가 서버리스 함수이기 때문이다.
함수는 요청이 몰리면 여러 개로 복제되고 꺼질 때 자기 디스크를 함께 버리므로, 모두가 함께 보는 파일 하나를 둘 자리가 없다.

== 백엔드 언어: Node.js, Python, JVM

*Node.js/TypeScript*는 가장 강력한 대안이다.
Vercel의 1순위 런타임이고, 화면에 React 같은 프레임워크를 택한다면 백엔드까지 같은 언어로 통일할 수 있다.
Next.js 앱을 Vercel 무료 티어에 올리는 것은 가장 흔한 무료 운영 조합이라 월 0원 운영도 성립하고, 콜드스타트도 결격 사유가 아니다.
기동 시간을 늘리는 것은 런타임이 아니라 함수가 불러오는 의존성의 크기다footnote:[Vercel 지식 베이스는 "기동 시간은 함수 크기에 비례하고 그 크기의 대부분은 외부 의존성에서 온다. 큰 의존성은 파싱과 평가에 때로 몇 초 이상 걸린다"고 적는다. https://vercel.com/kb/guide/improve-function-cold-start-performance-on-vercel[How can I improve function cold start performance on Vercel?] 참고.].
Go는 기동이 수십 밀리초 수준이라 콜드스타트를 걱정 목록에서 지워 주고, Node.js는 의존성 크기를 작게 유지하는 일이 관리 항목으로 남는다.
이미 TypeScript에 능숙하거나 팀에 자바스크립트 경험이 쌓여 있다면 Node.js가 더 나은 선택이다.
대신 TypeScript의 타입은 컴파일 시점에 지워져 실행 중에는 값을 지켜 주지 못하고, 의존성이 깊게 쌓이기 쉬우며, 같은 작업 기준 메모리 사용량이 Go보다 크다.
이 책이 Go로 기운 결정타는 무료 티어가 아니라, 의존성을 표준 라이브러리 수준으로 줄인 관리 표면적, 언어 하나로 줄인 학습량, 컴파일이라는 빠르고 결정적인 검증 신호였다.

*Python*은 데이터 생태계가 강점이다.
형태소 분석, 발음 평가, 문장 난이도 채점 같은 자연어 처리(NLP) 기능을 붙일 계획이라면, 그런 라이브러리가 대부분 Python용으로 먼저 나오므로 Python이 더 나은 선택이다.
반면 인터프리터와 의존성까지 올려야 해서 배포할 묶음이 크고, 타입 힌트가 선택 사항이라 정적 검증 신호가 약하다.
Flashcard는 사전 조회를 외부 API에 맡기고 SRS 계산만 직접 하므로 이 강점을 쓸 일이 없었다.

*JVM*(Java/Kotlin)은 Spring 생태계의 축적된 패턴과 대규모 팀을 위한 규율이라는 성숙도가 강점이다.
상주 서버를 운영할 수 있고, 도메인이 복잡하며, 조직의 표준 기술 스택이 JVM이라면 굳이 벗어날 이유가 없다.
반면 서버리스에서는 초 단위 콜드스타트footnote:[AWS Lambda 문서는 의존성과 프레임워크를 불러오는 초기화가 "몇 초(several seconds)" 걸릴 수 있다고 적고, Java용 SnapStart의 목표를 그 지연을 1초 미만으로 줄이는 것으로 둔다. https://docs.aws.amazon.com/lambda/latest/dg/snapstart.html[Improving startup performance with Lambda SnapStart] 참고.]와 앱 코드보다 먼저 JVM이 차지하는 메모리가 무료 티어와 정면으로 충돌한다.
GraalVM 네이티브 이미지는 JVM 대신 곧바로 실행되는 파일 하나로 미리 빌드해 이 지연을 줄이지만, 빌드가 길어지고 리플렉션을 쓰는 라이브러리마다 설정을 더해야 하는 빌드 복잡도가 새로 생긴다.

=== 메모리 사용량의 배수는 언제 문제가 되는가

{ch-tech-choices}에서 Go 서버가 유휴 상태 기준 10~20MB로 돈다고 했다.
같은 서버를 Node.js나 Python으로 만들면 인터프리터와 프레임워크를 띄우는 것만으로 대략 50~100MB에서 시작하는 경우가 많다.
다만 이 배수는 여유분의 차이일 뿐, Vercel에서는 Node.js로 만들어도 메모리 한도에 닿기 어렵다({ch-free-tier}).
배수가 실질적인 차이를 만드는 곳은 Render처럼 메모리 512MB짜리 인스턴스를 내주는 컨테이너형 무료 호스팅이다(뒤의 배포 플랫폼 표 참고).
기본 점유가 큰 런타임은 앱을 얹기 전에 인스턴스의 절반을 쓰므로, 메모리를 적게 쓸수록 무료 티어가 바뀔 때 옮겨 갈 곳이 많아진다.

=== Go가 내주는 것

에러 처리가 장황하고, 고차 함수 중심의 표현력 높은 추상화는 다른 언어보다 불편하며, Rails나 Spring 같은 풀스택 프레임워크의 생산성을 기대하기 어렵다.
화면 템플릿이 {n-page-count}장이고 도메인이 단순한 Flashcard에서는 이 대가가 작지만, 규모가 커지면 계산이 달라진다.
관리자 화면 수십 장을 갖춘 사내 시스템을 빠르게 세워야 한다면, 모델 하나로 테이블 마이그레이션과 목록·상세·입력 화면, 라우팅까지 명령 한 번(scaffold)에 만들어 주는 Rails가 빠르다.

== 웹 프레임워크: net/http, chi, Echo

Go에서는 "프레임워크가 정말 필요한가"부터가 진지한 질문이다.
표준 라이브러리 `net/http`만으로도 실용적인 HTTP 서버를 만들 수 있고, Go 1.22부터는 표준 라우터 `http.ServeMux`가 HTTP 메서드 매칭과 경로 파라미터(path parameter)를 지원한다.
다음 코드는 "/api/decks/ 뒤에 덱 이름이 붙은 주소로 GET 요청이 오면 이 함수를 실행하라"고 등록하고, 주소에 담긴 덱 이름(slug)을 꺼내는 예다.

[source,go]
----
mux := http.NewServeMux()
mux.HandleFunc("GET /api/decks/{slug}", func(w http.ResponseWriter, r *http.Request) {
	slug := r.PathValue("slug")
	// ...
})
----

라우팅은 이 정도로 충분하고, 모자라는 것은 {ch-tech-choices}에서 Gin이 맡아 준다고 한 세 가지다.
라우트 그룹이 없으니 인증 검사를 핸들러마다 감싸야 하고, JSON은 `json.NewDecoder(r.Body).Decode(&body)` 한 줄로 읽히지만 형식과 값을 검사하는 잡무가 핸들러마다 반복되며, 미들웨어는 핸들러를 겹겹이 감싸(데코레이터 패턴) 손으로 조립해야 한다.
엔드포인트가 열 개 안팎이고 미들웨어도 한두 개뿐인 소형 서비스(Flashcard는 경로가 70여 개, 미들웨어가 복구·인증·프로필 보장 셋이다), 혹은 외부 의존성을 최소화해야 하는 라이브러리성 도구라면 이 반복이 감당할 만하다.
버전 업그레이드 부담도 학습 비용도 없다는 것이 이 길의 장점이다.

*chi*는 표준 `http.Handler` 인터페이스를 그대로 유지하는 얇은 라우터라, 표준 라이브러리 생태계의 미들웨어와 예제를 그대로 재사용할 수 있다.
"프레임워크에 종속되고 싶지 않다"는 요구가 강한 팀, 혹은 기존 net/http 코드에 라우팅만 보강하려는 프로젝트라면 chi가 더 나은 선택이다.
대신 JSON 바인딩과 응답 도우미는 직접 갖춰야 한다.

*Echo*는 기능 범위가 Gin과 가장 비슷하다.
가장 큰 차이는 핸들러가 `func(c echo.Context) error`처럼 에러를 반환하고, 중앙의 에러 핸들러가 이를 HTTP 응답으로 바꾼다는 점이다.
에러 처리를 한곳에 모으는 방식을 선호한다면 Echo가 더 맞을 수 있다.
Gin의 핸들러는 반환값이 없어서, Flashcard는 `fail` 같은 도우미 함수로 같은 효과를 낸다({ch-gin}).

네 후보 모두 이 규모의 트래픽을 감당하고도 남으므로 성능은 변별 요소가 아니고, Flashcard가 Gin을 고른 결정적 이유는 사용자층의 넓이였다({ch-tech-choices}).

== 화면 렌더링: SPA, Alpine.js, Stimulus

Flashcard는 서버가 완성된 HTML을 만들어 보내는 서버 렌더링을 택했다.
반대편 길인 SPA가 더 나은 경우는 넷이다.

첫째, 오프라인 우선(offline-first) 앱이다.
비행기 모드에서도 동작하려면 데이터와 화면을 조립하는 능력이 모두 브라우저에 있어야 하므로, 서버가 있어야 화면이 나오는 서버 렌더링으로는 성립하지 않는다.
둘째, 문서 편집기나 드로잉 도구, 스프레드시트처럼 키 입력 하나하나에 화면이 반응해야 해서 상태를 브라우저에 두는 편이 자연스러운 편집기다.
셋째, 팀에 프런트엔드 전문가가 있어 백엔드는 JSON API에, 화면은 프런트엔드 쪽이 전담하는 분업을 하는 경우다.
넷째, 구인 시장이다.
React 경험자는 어디서든 구할 수 있지만 htmx를 내건 채용 공고는 드물어서, 사람을 뽑아 팀을 키울 조직이라면 주류 기술을 따르는 편이 안전하다.

서버 렌더링을 택한 뒤 부분 갱신을 무엇으로 할지도 갈림길이다.
htmx 말고 Alpine.js와 Stimulus가 후보였는데, 둘 다 HTML에 동작을 붙인다는 지향은 같지만 동작 자체는 자바스크립트로 직접 쓰는 도구라서 두 번째 언어가 도로 살아난다.
드롭다운 열기, 입력값에 따라 버튼 활성화하기처럼 브라우저 안에서만 완결되는 상태 변화가 많다면 그 표현력이 필요하고, 그때는 Alpine.js가 htmx보다 잘 맞는다.
Flashcard의 상호작용은 "서버가 새로 그린 조각으로 바꿔치기"만으로 전부 표현할 수 있어서, 속성 선언으로 끝나는 htmx가 배우는 양이 가장 적었다.

== 배포 플랫폼: Vercel이 아닌 무료 PaaS

Supabase는 그대로 두고 Go 앱만 Vercel이 아닌 무료 PaaS로 옮기면 무엇이 번거로워지는지 따져 본다.

| Cloudflare Workers | 엣지 실행 | 불필요 | 하루 10만 요청, 호출당 CPU 10밀리초 | 정지가 없다
| Google Cloud Run | 컨테이너 서버리스 | 필요 | 월 200만 요청 | 인스턴스가 0으로 줄었다가 다시 뜬다
| Northflank | 상주 컨테이너 | 필요 | 프로젝트 1개, 서비스 2개 | 정지가 없다
| Fly.io·Railway·Koyeb·Heroku | 상주 서버 | 필요 | 상시 무료 없음 | 해당 없음
|===

조건은 Cloudflare Workers가 가장 넉넉하지만 여기에는 Go 바이너리를 올릴 수 없다({ch-vercel}).
나머지 후보로 로그인이 붙은 앱을 옮길 때 손이 가는 곳은 다섯이다.

첫째, 앱 주소가 바뀔 때마다 Supabase의 등록을 고쳐야 한다.
{ch-deploy}에서 본 대로 Google과 GitHub에 등록하는 주소는 Supabase의 콜백 주소라서, 호스팅을 옮겨도 고칠 곳은 Supabase의 Site URL과 Redirect URLs뿐이다.
문제는 고치는 횟수다.
무료 플랜에서 커스텀 도메인을 막아 둔 플랫폼의 임시 주소(`<앱이름>-<임의 문자열>.b4a.run` 같은)는 재배포할 때 접미사가 바뀌기도 한다footnote:[Back4app Containers의 무료 플랜이 그렇다. 커스텀 도메인은 유료 전용이고, 무료 임시 주소는 만료되면 배포까지 함께 사라진다. https://www.back4app.com/pricing/container-as-a-service[Back4app 가격 페이지] 참고.].
그때마다 Supabase에서 두 칸을 고치기 전에는 로그인이 되지 않는다.

앱 주소를 플랫폼에서 떼어 내면 이 번거로움이 사라진다.
내 도메인을 정적 호스팅에 두고 모든 경로를 백엔드로 넘기는 프록시 규칙을 놓는 것으로, Netlify라면 사이트 루트의 `_redirects` 파일에 이렇게 적는다.

[source,text]
----
/*  https://<백엔드 주소>/:splat  200
----

상태 코드 `200`은 리다이렉트가 아니라 프록시를 뜻해서 브라우저 주소창에는 내 도메인이 그대로 남는다.
백엔드 주소가 바뀌면 이 한 줄만 고치고 Supabase의 등록은 그대로 두면 되지만, 관리할 플랫폼이 하나 늘어난다.

둘째, 정지한 서버가 깨어나는 시간이 로그인 대기 시간에 더해진다.
Render의 무료 웹 서비스는 15분 동안 요청이 없으면 정지하고 복귀에 30초에서 1분이 걸린다.
로그인 왕복 사이에 서버가 잠들어 있으면 사용자는 빈 화면을 그만큼 더 본다.

셋째, 컨테이너 이미지와 배포 절차가 다시 내 몫이 된다.
Vercel에서는 `api/index.go` 하나를 두면 플랫폼이 빌드와 배포를 맡는다({ch-vercel-config}).
컨테이너 PaaS에서는 Dockerfile을 쓰고 베이스 이미지의 보안 업데이트를 따라가야 하며, push마다 이미지를 빌드해 올리는 단계를 {ch-quality-gates}의 워크플로에 더해야 한다.

넷째, 표의 아홉 플랫폼 중 여섯이 결제 수단 등록을 요구한다.
"카드 없이 시작한다"를 조건으로 걸면 후보는 Render 정도로 줄어든다.

다섯째, 리전을 Supabase 프로젝트와 맞춰야 한다.
앱과 데이터베이스가 멀면 쿼리마다 대륙을 왕복하는데({ch-supabase-db}), 무료 리전이 미국 중부와 유럽 서부뿐인 Northflank 같은 곳에서는 이 선택지 자체가 없다.

편해지는 것도 있다.
상주 서버에서는 `cmd/server`를 그대로 올리므로 `pkg/app`을 `internal/` 바깥에 두어야 했던 Vercel의 제약({ch-vercel-config})이 사라지고, 커넥션 풀을 프로세스 수명 내내 유지할 수 있어 커넥션 풀러를 거치며 받아들인 제약({ch-supabase-db})도 줄어든다.
요청당 300초라는 실행 시간 제한({ch-free-tier})도 콜드스타트도 없어서, 웹소켓이나 300초를 넘기는 작업이 필요해지면 이쪽만 답이 된다.
{ch-supabase-auth}의 GoTrue 클라이언트는 HTTP로만 대화하므로 인증 코드는 한 줄도 바뀌지 않는다.

이 대안이 더 나은 조건은 셋이다.
웹소켓이나 300초를 넘기는 작업이 필요하거나, 콜드스타트를 한 번도 받아들일 수 없거나, 주소가 고정된 도메인이 이미 있어 첫 번째 번거로움이 처음부터 없는 경우다.

== 인증: Supabase Auth 없이 OAuth를 직접 구현하기

Flashcard는 비밀번호를 받지 않으므로, {ch-supabase-auth}보다 질문을 좁혀 보자.
Google과 GitHub 로그인은 그대로 두고 Supabase Auth만 걷어 내면 무엇이 남는가.

없어지는 것은 `internal/web/gotrue.go`의 130줄 남짓과 환경 변수 두 개(`SUPABASE_URL`, `SUPABASE_ANON_KEY`)다.
대신 떠안는 것은 다섯 가지다.

첫째, 프로바이더 두 곳과 각각 직접 대화하게 된다.
지금은 GoTrue 하나에 프로바이더 이름만 바꿔 넘기면 되지만, 직접 구현하면 Google과 GitHub의 주소와 응답 형식을 따로 다뤄야 한다.
Google은 OAuth 위에 신원 확인 규격을 얹은 OpenID Connect(OIDC)를 따라 서명된 `id_token`에 사용자 정보를 담아 주지만, GitHub은 OIDC 프로바이더가 아니라 `id_token`이 없다.
그래서 GitHub은 액세스 토큰을 받은 뒤 `/user`를, 이메일을 비공개로 둔 계정이면 `/user/emails`까지 불러 신원을 읽어야 한다.
Supabase 대시보드에만 두던 Client ID와 Secret도 우리 앱의 환경 변수로 들어온다({ch-env-secrets}).

둘째, 가장 큰 변화로 토큰의 발급자가 우리가 된다.
{ch-supabase-auth}에서 우리 서버는 JWT를 JWKS 공개키로 대조하기만 했지만, 직접 구현하면 서명 키를 만들어 보관하고, 유출에 대비해 주기적으로 바꾸되 이전 키로 서명된 토큰이 만료될 때까지는 두 키를 모두 받아들여야 한다.
JWT 대신 세션 저장소를 두면 {ch-supabase-auth}가 서버리스에서 피했던 그 저장소가 도로 필요해지고, 함수 인스턴스의 메모리에는 둘 수 없으니 Redis 같은 외부 저장소를 붙이게 된다.
리프레시 토큰의 발급·회전·폐기도 우리 몫이라, GoTrue의 `/logout` 한 번이던 로그아웃이 폐기한 토큰 목록을 저장하고 갱신 때마다 대조하는 일로 바뀐다.

셋째, 같은 사람인지 판정하는 정책을 직접 정해야 한다.
같은 이메일로 어제는 Google, 오늘은 GitHub으로 들어온 사람은 한 사용자인가 두 사용자인가.
검증되지 않은 이메일을 믿고 합치면 남의 주소를 적어 둔 계정으로 그 사람의 덱에 들어가는 통로가 되므로, 프로바이더가 이메일을 검증했는지 먼저 확인해야 한다.
Supabase에는 이 정책과 계정을 매다는 테이블이 이미 있다.

넷째, 사용자 테이블이 스키마에 들어온다.
지금 `internal/db/migrations/000001_init.up.sql`의 `profiles`는 `id uuid primary key` 하나로 시작하고, Supabase의 사용자 테이블을 외래 키로 참조하지 않는다.
그래서 인증을 갈아 끼워도 스키마는 그대로지만({ch-supabase-auth}의 이식성), 직접 구현하면 이메일·프로바이더·검증 여부를 담을 사용자 테이블과 리프레시 토큰 테이블이 마이그레이션에 들어오고, {ch-migrations}에서 관리할 대상이 그만큼 늘어난다.

다섯째, 인증 코드는 방어 장치를 빠뜨려도 로그인이 정상으로 보인다.
PKCE를 붙이지 않아도, 돌아갈 주소를 앱 안의 경로로 제한하지 않아도, 이메일 검증 여부를 확인하지 않아도 화면은 똑같이 로그인된다.
{ch-supabase-auth}의 공격·방어 목록을 우리 코드에서 하나씩 확인하고 테스트로 옮겨야 한다.

직접 구현이 더 나은 조건도 있다.
프로바이더가 하나뿐이고 표준 OIDC를 따르면 첫째 항목의 분기가 사라져, `github.com/coreos/go-oidc` 같은 OIDC 클라이언트 라이브러리 하나로 인가 요청과 토큰 교환, `id_token` 검증까지 끝난다.
관리형 인증 서비스를 쓸 수 없는 규제나 망 조건이 있다면 선택의 여지가 없다.
이미 사용자 테이블과 세션 관리를 갖춘 앱에 소셜 로그인만 얹는 경우라면, 둘째 항목의 비용이 새로 생기지 않으므로 계산이 달라진다.

여섯 가지 선택의 대안을 한자리에 모으면 이렇다.

|===
| 계층 | 이 책의 선택 | 대안 | 대안이 더 나은 조건

| 데이터베이스 | SQLite(로컬)·PostgreSQL(운영) | 문서형 NoSQL | 테이블 구조가 유동적이고, 읽고 쓰는 단위가 문서 하나로 떨어질 때
| 데이터베이스 | 두 벌 구성 | PostgreSQL 하나 | 로컬에 이미 PostgreSQL이 있거나 팀 공용 개발 DB가 있을 때
| 데이터베이스 | 두 벌 구성 | SQLite 하나 | 서버리스가 아니라 상주 서버 한 대에 배포할 때
| 백엔드 언어 | Go | Node.js/TypeScript | 자바스크립트에 이미 능숙하거나 화면까지 같은 언어로 통일할 때

| 웹 프레임워크 | Gin | net/http | 엔드포인트가 적고 외부 의존성을 0으로 두고 싶을 때

| 인증 | Supabase Auth | OAuth 직접 구현 | 프로바이더가 하나뿐이고 표준 OIDC를 따르거나, 사용자 테이블과 세션 관리가 이미 있을 때

이 표는 오른쪽 끝 칸에 자기 프로젝트의 조건을 대입해 읽는다.
조건이 겹치는 줄이 있다면 그 줄의 대안이 독자에게는 더 나은 답이다.
