= 검토한 대안 기술: 언제 다른 선택이 더 나은가

{ch-tech-choices}에서는 데이터베이스, 백엔드 언어, 웹 프레임워크, 화면 렌더링이라는 네 계층을 정하면서 고른 쪽이 무엇을 해 주는지에 집중했다.
저울의 반대편에 무엇이 올라가 있었는지를 이 부록에 모았다.
4부에서 정한 배포 플랫폼과 인증도 뒤쪽 두 절에 함께 두었다.
기술 선택에 정답이 없다는 말은 조건이 달라지면 답도 달라진다는 뜻이므로, 후보마다 "언제 그쪽이 더 나은가"를 적어 둔다.
독자의 프로젝트는 Flashcard와 조건이 다를 것이니, 결론이 아니라 이 판단의 과정을 가져가면 좋겠다.

여기 나오는 이름들은 본문을 따라가는 데 필요하지 않다.
낯선 이름이 많다면 통째로 건너뛰었다가 자기 앱을 설계할 때 돌아와도 된다.

== 데이터베이스: 문서형 NoSQL

관계형이라는 방향 자체의 대안으로는 문서형 NoSQL(MongoDB, Firestore 등)이 있다.
테이블의 구조를 미리 정해 두기 어렵거나, 읽고 쓰는 단위가 늘 문서 하나로 떨어질 때 문서 DB의 강점이 산다.
카드 앱이라도 "덱 문서 안에 카드 배열을 통째로 저장하고 통째로 읽는" 구조라면 문서 DB가 더 단순할 수 있다.

.[용어 풀이] NoSQL과 문서형 데이터베이스
[NOTE]
====
NoSQL은 데이터를 테이블과 테이블의 관계로 담지 않는 데이터베이스를 통칭하는 말이다.
그중 가장 널리 쓰이는 문서형은 데이터를 테이블의 한 줄이 아니라 그 자체로 완결된 한 덩어리(문서)로 저장한다.
덱 하나를 예로 들면, 카드 목록까지 통째로 품은 서류 한 장을 서랍에 넣어 두는 모습에 가깝다.
MongoDB와 Firestore가 대표적인 문서형 데이터베이스다.
====

그러나 Flashcard는 카드를 덱 단위가 아니라 개별 단위로 다룬다.
"오늘 복습할 카드"는 덱의 경계를 넘어 복습 예정 시각으로 모으고, 스마트 덱은 오답률·태그 같은 조건으로 여러 덱의 카드를 가로질러 조회한다.
여러 테이블을 이어 붙이고(조인), 조건에 맞는 행을 빨리 찾아내는(인덱스) 이런 조회가 관계형 모델의 홈그라운드다.
조인과 인덱스, 그리고 테이블의 구조를 뜻하는 스키마는 모두 {ch-database-basics}에서 다루는 개념이다.
같은 조회를 문서 DB에서 구현하려면 데이터를 여러 문서에 복사해 두고 그 복사본들을 서로 맞추는 수동 동기화가 늘어난다.

정리하면 문서형이 유리한 조건은 셋이다.
저장하는 데이터의 모양이 자주 바뀌어 테이블을 미리 정의하기 어렵거나, 읽고 쓰는 단위가 늘 문서 하나로 떨어지거나, 여러 문서를 가로지르는 조회가 거의 없는 경우다.
Flashcard는 셋 다 아니었다.

== 데이터베이스: 처음부터 PostgreSQL 하나만 쓰기

Flashcard는 로컬 개발에 SQLite를, 운영에 PostgreSQL을 쓴다.
데이터베이스를 하나로 통일하는 길도 물론 있고, 방향은 둘이다.

처음부터 PostgreSQL 하나만 쓰는 쪽부터 보자.
개발과 운영이 같은 데이터베이스를 쓰니 방언 차이를 신경 쓸 일이 없고, 저장소 구현도 한 벌이면 된다.
대신 독자가 첫 장부터 데이터베이스 서버를 설치하거나 계정을 만들어야 하고, 인터넷이 끊기면 실습이 멈춘다.
이 책은 3부까지를 내 컴퓨터 안에서 완결시키는 것을 목표로 삼았기 때문에 이 비용을 받아들이지 않았다.
읽는 사람이 이미 PostgreSQL을 로컬에 갖추고 있거나 팀이 함께 쓰는 개발 데이터베이스가 있다면 이쪽이 더 단순하다.

반대로 SQLite 하나로 운영까지 가는 길도 성립한다.
서버리스가 아니라 상주 서버 한 대에 배포하는 앱이라면, 그 서버의 디스크에 놓인 파일 하나가 곧 데이터베이스가 된다.
쓰기가 한 프로세스에 몰려 있고 백업이 파일 복사로 끝나므로 운영 부담이 오히려 가장 작다.
Flashcard가 이 길을 못 간 이유는 배포처가 서버리스 함수여서다.
함수는 요청이 몰리면 여러 개로 복제되고 꺼질 때 자기 디스크를 함께 버리므로, 모두가 함께 보는 파일 하나를 둘 자리가 없다.

== 백엔드 언어: Node.js, Python, JVM

Go가 유일한 답은 아니다.
대안 세 가지를 놓고 언제 그쪽이 더 나은 선택인지 하나씩 따져 보자.

*Node.js/TypeScript*는 가장 강력한 대안이다.
Vercel의 1순위 런타임이고, 화면 렌더링에서 React 같은 브라우저 렌더링 프레임워크를 택한다면 브라우저 쪽 코드가 어차피 자바스크립트 계열이므로 백엔드까지 같은 언어로 통일할 수 있다.
공정하게 밝혀 두면, 이 대안으로도 이 책의 목표인 월 0원 운영은 성립한다.
Next.js 앱을 Vercel 무료 티어에 올리는 구성은 세상에서 가장 흔한 무료 운영 조합이라 해도 지나치지 않다.
Flashcard 규모의 트래픽이라면 Node.js 서버도 호출 수와 메모리 어느 한도에도 닿지 않는다.
콜드스타트도 결격 사유는 아니다.
Node.js 런타임 자체는 기동이 가벼워서, 기동 시간을 늘리는 것은 런타임이 아니라 함수가 불러오는 의존성의 크기다footnote:[Vercel 지식 베이스는 "기동 시간은 함수 크기에 비례하고 그 크기의 대부분은 외부 의존성에서 온다. 큰 의존성은 파싱과 평가에 때로 몇 초 이상 걸린다"고 적는다. https://vercel.com/kb/guide/improve-function-cold-start-performance-on-vercel[How can I improve function cold start performance on Vercel?] 참고.].
가상 머신을 통째로 띄우고 클래스를 읽어 들이느라 초 단위 지연을 각오해야 하는 JVM과는 부류가 다르다.
Go와의 차이는 성립이 아니라 정도의 문제다.
Go는 기동이 수십 밀리초 수준이라 콜드스타트를 걱정 목록에서 지워 주고, Node.js는 의존성이 늘어날수록 기동 시간이 함께 자라므로 의존성의 크기를 낮게 유지하는 일이 관리 항목으로 남는다.
이미 TypeScript에 능숙하거나 팀에 자바스크립트 경험이 쌓여 있다면 Node.js가 더 나은 선택이다.
반면 내주는 것도 있다.
TypeScript의 타입은 컴파일 시점에 지워져 코드가 실제로 도는 동안에는 값을 지켜 주지 못하고, 끌어 쓰는 의존성이 깊게 쌓이기 쉬우며, 같은 작업 기준 메모리 사용량이 Go보다 크다.
결국 이 책이 Go로 기운 결정타는 무료 티어의 성립 여부가 아니었다.
의존성을 표준 라이브러리 수준으로 줄여 관리할 표면적을 좁히는 것, 언어를 하나로 유지해 배우는 양을 줄이는 것, 그리고 컴파일이라는 빠르고 결정적인 검증 신호가 저울을 기울였다.

*Python*은 데이터 생태계가 강점이다.
영어 학습 앱이라는 도메인 특성상 형태소 분석, 발음 평가, 문장 난이도 채점 같은 자연어 처리(NLP) 기능을 붙일 계획이라면, 필요한 라이브러리가 대부분 Python 우선으로 나오므로 Python이 더 나은 선택이다.
반면 배포 아티팩트가 크고(인터프리터 + 의존성), 타입 힌트가 선택 사항이라 정적 검증 신호가 약하다.
Flashcard는 사전 조회를 외부 API에 위임하고 SRS 계산만 직접 하므로 이 강점을 쓸 일이 없었다.

*JVM*(Java/Kotlin)은 성숙도가 강점이다.
Spring 생태계의 축적된 패턴과 대규모 팀을 위한 규율은 다른 기술 스택이 따라오기 어렵다.
상주 서버를 운영할 수 있고, 도메인이 복잡하며, 조직의 표준 기술 스택이 JVM이라면 굳이 벗어날 이유가 없다.
반면 서버리스에서는 초 단위 콜드스타트footnote:[AWS Lambda 문서는 의존성과 프레임워크를 불러오는 초기화가 "몇 초(several seconds)" 걸릴 수 있다고 적고, Java용 SnapStart의 목표를 그 지연을 1초 미만으로 줄이는 것으로 둔다. https://docs.aws.amazon.com/lambda/latest/dg/snapstart.html[Improving startup performance with Lambda SnapStart] 참고.]와 앱 코드가 돌기 전에 JVM이 먼저 차지하는 메모리가 무료 티어와 정면으로 충돌한다.
JVM을 통째로 띄우는 대신 Go처럼 곧바로 실행되는 파일 하나로 미리 빌드해 주는 GraalVM 네이티브 이미지로, 클래스 로딩과 초기화를 실행 시점에서 빌드 시점으로 옮겨 이 지연을 줄일 수는 있다.
대신 빌드가 미리 컴파일하는 단계를 거쳐 길어지고 리플렉션을 쓰는 라이브러리마다 설정을 더해 주어야 해서, 콜드스타트를 덜어 낸 자리에 빌드 복잡도라는 새 비용이 들어온다.

=== 메모리 사용량의 배수는 언제 문제가 되는가

{ch-tech-choices}에서 Go 서버가 유휴 상태 기준 10~20MB로 돈다고 했다.
같은 일을 하는 서버를 Node.js나 Python으로 만들면 인터프리터와 프레임워크를 띄우는 것만으로 대략 50~100MB에서 시작하는 경우가 많아, 앱 코드가 한 줄 돌기 전에 Go가 다 쓰는 양의 몇 배를 런타임이 먼저 점유한다.
정확한 값은 앱과 측정 방식에 따라 다르니 절대값보다 "몇 배"라는 배수를 기억해 두면 된다.

다만 이 배수는 여유분의 차이이지, 무료 티어의 성립과 불성립을 나누는 차이는 아니다.
Flashcard가 배포되는 Vercel의 무료 한도는 넉넉해서, 이 규모의 앱이라면 Node.js로 만들어도 메모리 한도에 닿기 어렵다(실제 수치 계산은 {ch-free-tier}에서 한다).
배수가 실질적인 차이를 만드는 곳은 Render처럼 메모리 512MB짜리 인스턴스를 내주는 컨테이너형 무료 호스팅이다(뒤의 배포 플랫폼 표 참고).
이런 곳에서는 기본 점유가 큰 런타임이 앱을 얹기 전에 인스턴스의 절반을 쓰고 시작하므로, 메모리 사용량이 적을수록 무료로 갈 수 있는 플랫폼의 폭이 넓어진다.
{ch-free-tier}에서 다루듯 무료 티어는 정책에 따라 축소되거나 사라지기도 하는 만큼, 옮길 곳이 많다는 것은 그 자체로 보험이 된다.

=== Go가 내주는 것

단순함에는 대가가 따른다.
에러 처리가 장황하고, 고차 함수 중심의 표현력 높은 추상화는 다른 언어보다 불편하며, Rails나 Spring 같은 풀스택 프레임워크의 생산성을 기대하기 어렵다.
Flashcard처럼 화면 템플릿이 13장이고 도메인이 단순한 앱에서는 이 대가가 작지만, 규모가 커지면 계산이 달라진다.
예를 들어 회원 관리와 게시판, 관리자 화면 수십 장을 갖춘 사내 시스템을 빠르게 세워야 한다면 Rails 쪽이 빠르다.
모델 하나를 선언하면 테이블 마이그레이션과 목록·상세·입력 폼 화면, 라우팅까지 명령 한 번(scaffold)으로 생성해 주므로, 화면 수십 장을 손으로 짜는 일 자체가 사라지기 때문이다.

== 웹 프레임워크: net/http, chi, Echo

Go에서는 "프레임워크가 정말 필요한가"부터가 진지한 질문이다.
표준 라이브러리 `net/http`만으로도 실용적인 HTTP 서버를 만들 수 있기 때문이다.
특히 Go 1.22부터는 표준 라우터인 `http.ServeMux`가 크게 개선되어, HTTP 메서드 매칭과 경로 파라미터(path parameter)를 지원한다.
다음 코드는 "/api/decks/ 뒤에 덱 이름이 붙은 주소로 GET 요청이 오면 이 함수를 실행하라"고 라우터에 등록하고, 주소에 담긴 덱 이름(slug)을 꺼내는 예다.

[source,go]
----
mux := http.NewServeMux()
mux.HandleFunc("GET /api/decks/{slug}", func(w http.ResponseWriter, r *http.Request) {
	slug := r.PathValue("slug")
	// ...
})
----

라우팅만 놓고 보면 이 정도로 충분하고, 모자라는 것은 라우팅 바깥의 셋이다.
{ch-tech-choices}에서 Gin이 대신 맡아 준다고 한 그 세 가지, 곧 라우트 그룹과 JSON 바인딩과 미들웨어 체인을 표준 라이브러리로 하면 어떻게 되는지 짚어 보자.
라우트 그룹이 없으니 인증이 필요한 핸들러마다 검사를 감싸거나 래퍼 함수를 직접 만들어야 한다.
JSON도 `json.NewDecoder(r.Body).Decode(&body)` 한 줄로 읽히기는 하지만, 요청이 정말 JSON을 보냈는지 확인하고 값이 규칙에 맞는지 검사하는 잡무가 핸들러마다 반복된다.
모든 요청에 공통으로 걸 처리는 핸들러를 다른 핸들러로 겹겹이 감싸 만드는데(데코레이터 패턴), Gin이 미들웨어라는 이름으로 대신해 주던 그 조립을 손으로 해야 한다.
엔드포인트가 열 개 안팎이고 미들웨어도 한두 개뿐인 소형 서비스(Flashcard는 경로가 70여 개, 미들웨어가 복구·인증·프로필 보장 셋이다), 혹은 외부 의존성을 최소화해야 하는 라이브러리성 도구라면 이 반복이 감당할 만하다.
버전 업그레이드 부담도 학습 비용도 없다는 것이 표준 라이브러리만 쓰는 길의 최대 장점이다.

*chi*는 표준 `http.Handler` 인터페이스를 그대로 유지하는 얇은 라우터로, 표준 라이브러리 생태계의 미들웨어와 예제를 변환 없이 재사용할 수 있다.
"프레임워크에 종속되고 싶지 않다"는 요구가 강한 팀, 혹은 기존 net/http 코드에 라우팅만 보강하고 싶은 프로젝트라면 chi가 더 나은 선택이다.
대신 JSON 바인딩과 응답 도우미는 직접 갖춰야 한다.

*Echo*는 기능 범위가 Gin과 가장 비슷한 프레임워크다.
가장 큰 차이는 핸들러가 `func(c echo.Context) error`처럼 에러를 반환하고, 중앙의 에러 핸들러가 이를 HTTP 응답으로 변환한다는 점이다.
에러 처리를 한곳에 모으는 이 방식을 선호한다면 Echo가 더 맞을 수 있다.
Gin의 핸들러는 반환값이 없어서, {ch-gin}에서 다루듯 Flashcard는 `fail` 같은 도우미 함수로 같은 효과를 낸다.

성능은 이 규모의 앱에서 의미 있는 변별 요소가 아니며, 네 후보 모두 개인용 암기 카드 앱의 트래픽을 감당하고도 남는다.
Flashcard가 Gin을 고른 결정적 이유는 사용자층의 넓이였고, 그 이야기는 {ch-tech-choices}에 있다.

== 화면 렌더링: SPA, Alpine.js, Stimulus

Flashcard는 서버가 완성된 HTML을 만들어 보내는 서버 렌더링을 택했다.
반대편 길인 SPA가 더 나은 경우는 넷이다.

첫째, 오프라인 우선(offline-first) 앱이다.
비행기 모드에서도 동작해야 하는 앱은 데이터와 화면을 조립하는 능력이 모두 브라우저 쪽에 있어야 하므로, 서버가 있어야 화면이 나오는 서버 렌더링으로는 성립하지 않는다.
둘째, 고도로 상호작용적인 편집기다.
문서 편집기나 드로잉 도구, 스프레드시트처럼 키 입력 하나하나에 화면이 반응해야 하는 제품은 상태를 브라우저에 두는 SPA 모델이 자연스럽다.
셋째, 팀에 프런트엔드 전문가가 있는 경우다.
백엔드는 JSON API에 집중하고 화면은 프런트엔드 쪽이 전담하는 분업은 SPA가 만들어 주는 경계선 위에서 잘 돌아간다.
넷째, 구인 시장이다.
React 경험자는 어디서든 구할 수 있지만 htmx를 내건 채용 공고는 드물어서, 사람을 뽑아 팀을 키울 조직이라면 주류 기술을 따르는 편이 안전하다.

서버 렌더링을 택한 뒤 부분 갱신을 무엇으로 할지도 갈림길이다.
Flashcard가 고른 htmx 말고 Alpine.js와 Stimulus가 이 자리의 후보였다.
둘 다 HTML에 동작을 붙인다는 지향이 htmx와 같지만, 동작 자체는 자바스크립트로 직접 쓰는 도구라서 두 번째 언어가 도로 살아난다.
브라우저 안에서만 완결되는 상태 변화(드롭다운 열기, 입력값에 따라 버튼 활성화하기)가 많다면 그 표현력이 필요하고, 그때는 Alpine.js가 htmx보다 잘 맞는다.
Flashcard의 상호작용은 "서버가 새로 그린 조각으로 바꿔치기"만으로 전부 표현할 수 있었으므로, 속성 선언으로 끝나는 htmx가 배우는 양이 가장 적었다.

== 배포 플랫폼: Vercel이 아닌 무료 PaaS

{ch-vercel}에서는 상주 서버 대신 서버리스를 고른 과정을 다뤘다.
여기서는 그 결정을 되돌려 본다.
Supabase는 그대로 두고 Go 앱만 다른 무료 PaaS로 옮기면 무엇이 번거로워지는가.

먼저 2026년 8월 기준으로 후보들의 무료 조건을 정리하면 이렇다.

|===
| 플랫폼 | 실행 모델 | 결제 수단 등록 | 무료 조건 | 요청이 없을 때

| Vercel Hobby | 서버리스 함수 | 불필요 | 월 100만 요청, 전송량 100GB | 다음 요청에 함수가 다시 뜬다
| Render Free | 상주 컨테이너 | 불필요 | 메모리 512MB, 워크스페이스당 월 750시간 | 15분 뒤 정지, 복귀에 30초에서 1분
| Cloudflare Workers | 엣지 실행 | 불필요 | 하루 10만 요청, 호출당 CPU 10밀리초 | 정지가 없다
| Google Cloud Run | 컨테이너 서버리스 | 필요 | 월 200만 요청 | 인스턴스가 0으로 줄었다가 다시 뜬다
| Northflank | 상주 컨테이너 | 필요 | 프로젝트 1개, 서비스 2개 | 정지가 없다
| Fly.io·Railway·Koyeb·Heroku | 상주 서버 | 필요 | 상시 무료 없음 | 해당 없음
|===

표만 보면 Cloudflare Workers의 조건이 가장 넉넉하지만, 여기에는 Go 바이너리를 올릴 수 없다({ch-vercel}).
나머지 후보로 옮긴다고 가정하고, 로그인이 이미 붙어 있는 앱을 옮길 때 실제로 손이 가는 곳을 따라가 보자.

첫째, 앱 주소가 바뀔 때마다 Supabase의 등록을 고쳐야 한다.
{ch-deploy}에서 본 대로 Google과 GitHub에 등록하는 주소는 앱 주소가 아니라 Supabase의 콜백 주소다.
그래서 호스팅을 옮겨도 그 두 곳은 손대지 않아도 되고, 고칠 곳은 Supabase의 Site URL과 Redirect URLs 한 곳뿐이다.
문제는 고칠 곳의 개수가 아니라 고치는 횟수다.
무료 플랜에서 커스텀 도메인을 막아 둔 플랫폼에서는 `<앱이름>-<임의 문자열>.b4a.run` 같은 임시 주소만 받는데, 이런 주소는 재배포할 때 접미사가 바뀌기도 한다.footnote:[Back4app Containers의 무료 플랜이 그렇다. 커스텀 도메인은 유료 전용이고, 무료 임시 주소는 만료되면 배포까지 함께 사라진다. https://www.back4app.com/pricing/container-as-a-service[Back4app 가격 페이지] 참고.]
그때마다 Supabase 대시보드를 열어 두 칸을 고치기 전에는 로그인이 되지 않는다.
{ch-deploy}가 Site URL이 잘못돼 로그인이 엉뚱한 곳으로 새던 사고를 기록해 둔 것도 같은 종류의 문제다.

이 번거로움을 없애는 방법은 앱 주소를 플랫폼에서 떼어 내는 것이다.
내 도메인을 정적 호스팅에 두고, 모든 경로를 백엔드로 넘기는 프록시 규칙 한 줄을 놓으면 된다.
Netlify라면 사이트 루트의 `_redirects` 파일에 이렇게 적는다.

[source,text]
----
/*  https://<백엔드 주소>/:splat  200
----

상태 코드 `200`은 리다이렉트가 아니라 프록시를 뜻해서, 브라우저 주소창은 내 도메인 그대로 유지된다.
백엔드 주소가 바뀌면 이 한 줄만 고치면 되고, Supabase에 등록한 주소는 그대로 둔다.
대신 관리할 플랫폼이 하나 늘어난다.

둘째, 정지한 서버가 깨어나는 시간이 로그인 대기 시간에 더해진다.
Render의 무료 웹 서비스는 15분 동안 요청이 없으면 정지하고, 복귀에 30초에서 1분이 걸린다.
로그인은 브라우저가 프로바이더를 다녀와 `/auth/callback`으로 돌아오는 왕복이라, 그 사이에 서버가 잠들어 있으면 사용자는 빈 화면을 그만큼 더 본다.

셋째, 컨테이너 이미지와 배포 절차가 다시 내 몫이 된다.
Vercel에서는 `api/index.go` 하나를 두면 플랫폼이 빌드와 배포를 맡지만({ch-vercel-config}), 컨테이너 PaaS에서는 Dockerfile을 쓰고 베이스 이미지의 보안 업데이트를 따라가야 하며 push마다 이미지를 빌드해 올리는 워크플로도 직접 만들어야 한다.
{ch-github-actions}에서 만든 워크플로에 그 단계가 추가된다.

넷째, 표의 아홉 플랫폼 중 여섯이 결제 수단 등록을 요구한다.
Cloud Run은 무료 한도 안에서만 쓰더라도 열려 있는 결제 계정이 있어야 하고, Northflank는 무료 프로젝트를 만드는 데도 카드를 먼저 요구한다.
"카드 없이 시작한다"를 조건으로 걸면 후보는 Render 정도로 줄어든다.

다섯째, 리전을 Supabase 프로젝트와 맞춰야 한다.
앱과 데이터베이스가 멀면 쿼리 한 번마다 대륙을 왕복하게 되는데, 그 비용은 {ch-supabase-db}에서 다룬다.
무료 리전이 미국 중부와 유럽 서부뿐인 Northflank 같은 곳에서는 이 선택지 자체가 없다.

편해지는 것도 있으니 공정하게 적어 둔다.
상주 서버에서는 `cmd/server`를 그대로 올린다.
Vercel의 Go 빌더 때문에 `pkg/app`을 `internal/` 바깥에 두어야 했던 제약({ch-vercel-config})이 사라진다.
프로세스가 살아 있으므로 커넥션 풀을 프로세스 수명 내내 유지할 수 있고, {ch-supabase-db}에서 커넥션 풀러를 거치며 받아들였던 제약도 줄어든다.
{ch-free-tier}에서 본 요청당 300초라는 실행 시간 제한도 콜드스타트도 없어서, 나중에 웹소켓이나 300초를 넘기는 작업이 필요해지면 이쪽만 답이 된다.
그리고 인증 코드는 한 줄도 바뀌지 않는다.
{ch-supabase-auth}의 GoTrue 클라이언트는 HTTP로만 대화하므로 앱이 어디서 돌든 그대로 동작한다.

정리하면 이 대안이 더 나은 조건은 셋이다.
웹소켓이나 300초를 넘기는 작업이 필요하거나, 콜드스타트를 한 번도 받아들일 수 없거나, 주소가 고정된 도메인을 이미 갖고 있어 첫 번째 번거로움이 처음부터 없는 경우다.

== 인증: Supabase Auth 없이 OAuth를 직접 구현하기

{ch-supabase-auth}는 인증을 직접 만들 때 떠안는 것을 비밀번호 저장부터 셌다.
그런데 Flashcard는 비밀번호를 아예 받지 않으므로, 질문을 좁혀 볼 수 있다.
Google과 GitHub 로그인은 그대로 두고 Supabase Auth만 걷어 내면 무엇이 남는가.

없어지는 것부터 세면 간단하다.
`internal/web/gotrue.go`의 130줄 남짓과 환경 변수 두 개(`SUPABASE_URL`, `SUPABASE_ANON_KEY`)다.
대신 떠안는 것은 다섯 가지다.

첫째, 프로바이더 두 곳과 각각 직접 대화하게 된다.
지금은 인가 주소도 토큰 교환 주소도 GoTrue 하나뿐이라 프로바이더 이름만 바꿔 넘기면 된다.
직접 구현하면 Google과 GitHub의 주소와 응답 형식을 각각 다뤄야 하는데, 둘의 차이가 작지 않다.
Google은 OAuth 위에 신원 확인 규격을 얹은 OpenID Connect(OIDC)를 따라 서명된 `id_token`에 사용자 정보를 담아 주지만, GitHub은 OIDC 프로바이더가 아니라서 `id_token`이 없다.
GitHub 쪽은 액세스 토큰을 받은 뒤 `/user`를 한 번 더 불러 신원을 읽어야 하고, 이메일을 비공개로 설정한 계정이면 `/user/emails`를 또 불러 검증된 주소를 골라야 한다.
프로바이더를 하나 더 늘릴 때마다 이런 분기가 하나씩 늘어난다.
지금은 Supabase 대시보드에만 두면 됐던 Client ID와 Secret도 프로바이더마다 우리 앱의 환경 변수로 들어온다({ch-env-secrets}).

둘째, 토큰의 발급자가 우리가 된다.
이것이 가장 큰 변화다.
{ch-supabase-auth}에서 우리 서버는 쿠키에 든 JWT를 JWKS 공개키로 대조하기만 했고, 서명에 쓰는 비밀 값은 우리 쪽에 하나도 없었다.
직접 구현하면 그 서명을 우리가 찍는다.
서명 키를 만들어 보관하고, 유출에 대비해 주기적으로 바꾸되 이전 키로 서명된 토큰이 만료될 때까지는 두 키를 모두 받아들여야 한다.
JWT를 쓰지 않고 세션 저장소를 두는 길도 있지만, 그러면 {ch-supabase-auth}가 서버리스에서 피했던 그 저장소가 도로 필요해진다.
함수 인스턴스의 메모리에는 둘 수 없으므로 Redis 같은 외부 저장소를 붙이게 되고, 관리할 플랫폼이 하나 늘어난다.
리프레시 토큰의 발급·회전·폐기도 우리 몫이다.
지금은 로그아웃이 GoTrue의 `/logout` 호출 한 번이지만, 직접 구현하면 폐기한 토큰의 목록을 어딘가에 저장하고 갱신 때마다 대조해야 한다.

셋째, 같은 사람인지 판정하는 정책을 직접 정해야 한다.
같은 이메일 주소로 어제는 Google, 오늘은 GitHub으로 들어온 사람은 한 사용자인가 두 사용자인가.
한 사용자로 합치려면 프로바이더가 그 이메일을 검증했는지 먼저 확인해야 한다.
검증되지 않은 이메일을 믿고 합치면, 남의 주소를 적어 둔 계정으로 그 사람의 덱에 들어가는 통로가 된다.
사용자 하나에 프로바이더 계정 여럿을 매다는 테이블도 필요하다.
Supabase에는 이 정책과 테이블이 이미 있고, 합칠지 말지는 대시보드에서 정한다.

넷째, 사용자 테이블이 스키마에 들어온다.
지금 우리 스키마에는 사용자 테이블이 없다.
`internal/db/migrations/000001_init.up.sql`의 `profiles`는 `id uuid primary key` 하나로 시작하고, Supabase의 사용자 테이블을 외래 키로 참조하지 않는다.
이 설계 덕분에 인증을 갈아 끼워도 스키마는 그대로 두면 된다는 것이 {ch-supabase-auth}가 말한 이식성의 근거이기도 하다.
직접 구현하면 이메일·프로바이더·검증 여부를 담을 사용자 테이블과 리프레시 토큰 테이블을 만들어 마이그레이션에 넣게 되고, {ch-migrations}에서 관리할 대상이 그만큼 늘어난다.

다섯째, 검증의 성격이 다르다.
인증 코드는 방어 장치를 빠뜨려도 로그인이 정상으로 보인다.
PKCE를 붙이지 않아도, 돌아갈 주소를 앱 안의 경로로 제한하지 않아도, 이메일 검증 여부를 확인하지 않아도 화면은 똑같이 로그인된다.
{ch-supabase-auth}가 공격 하나에 방어 하나를 짝지어 확인한 목록을 이제 우리 코드에서 하나씩 확인해야 하고, 그 확인을 테스트로 옮기는 일까지 따라온다.

그래도 직접 구현이 더 나은 조건은 있다.
프로바이더가 하나뿐이고 그것이 표준 OIDC를 따르면 첫째 항목의 분기가 사라져서, `github.com/coreos/go-oidc` 같은 OIDC 클라이언트 라이브러리 하나로 인가 요청과 토큰 교환, `id_token` 검증까지 끝난다.
남는 것은 둘째부터 다섯째까지, 곧 우리가 발급하는 토큰과 사용자 판정, 사용자 테이블, 그리고 그 검증이다.
관리형 인증 서비스를 쓸 수 없는 규제나 망 조건이 있다면 선택의 여지가 없다.
그리고 이미 사용자 테이블과 세션 관리를 갖춘 앱에 소셜 로그인만 얹는 경우라면, 둘째 항목의 비용이 새로 생기지 않으므로 계산이 달라진다.

== 정리

여섯 가지 선택의 대안을 한자리에 모으면 이렇다.

|===
| 계층 | 이 책의 선택 | 대안 | 대안이 더 나은 조건

| 데이터베이스 | SQLite(로컬)·PostgreSQL(운영) | 문서형 NoSQL | 테이블 구조가 유동적이고, 읽고 쓰는 단위가 문서 하나로 떨어질 때
| 데이터베이스 | 두 벌 구성 | PostgreSQL 하나 | 로컬에 이미 PostgreSQL이 있거나 팀 공용 개발 DB가 있을 때
| 데이터베이스 | 두 벌 구성 | SQLite 하나 | 서버리스가 아니라 상주 서버 한 대에 배포할 때
| 백엔드 언어 | Go | Node.js/TypeScript | 자바스크립트에 이미 능숙하거나 화면까지 같은 언어로 통일할 때
| 백엔드 언어 | Go | Python | 자연어 처리처럼 Python 우선 라이브러리가 핵심일 때
| 백엔드 언어 | Go | JVM | 상주 서버를 쓰고 도메인이 복잡하며 조직 표준이 JVM일 때
| 웹 프레임워크 | Gin | net/http | 엔드포인트가 적고 외부 의존성을 0으로 두고 싶을 때
| 웹 프레임워크 | Gin | chi | 표준 인터페이스를 유지한 채 라우팅만 보강할 때
| 웹 프레임워크 | Gin | Echo | 에러 처리를 중앙 핸들러 한곳에 모으고 싶을 때
| 화면 렌더링 | 서버 렌더링 + htmx | SPA(React 등) | 오프라인 우선, 편집기급 상호작용, 프런트엔드 분업, 구인 시장
| 화면 렌더링 | htmx | Alpine.js·Stimulus | 서버를 거치지 않는 브라우저 안 상태 변화가 많을 때
| 배포 플랫폼 | Vercel 서버리스 함수 | Render·Cloud Run 등 컨테이너 PaaS | 웹소켓이나 오래 걸리는 작업이 필요하거나, 주소가 고정된 도메인을 이미 갖고 있을 때
| 인증 | Supabase Auth | OAuth 직접 구현 | 프로바이더가 하나뿐이고 표준 OIDC를 따르거나, 사용자 테이블과 세션 관리가 이미 있을 때
|===

이 표를 읽는 방법은 하나다.
왼쪽 두 칸이 아니라 오른쪽 끝 칸에 자기 프로젝트의 조건을 대입해 보는 것이다.
조건이 겹치는 줄이 있다면 그 줄의 대안이 독자에게는 더 나은 답이다.
