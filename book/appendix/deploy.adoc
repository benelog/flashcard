= 배포 준비: Supabase·Google·GitHub·Vercel 설정

이 책의 배포는 데이터베이스와 로그인을 맡는 Supabase, 소셜 로그인을 내주는 Google과 GitHub, 앱을 띄우는 Vercel의 웹 대시보드를 오간다.
코드를 올려 둘 GitHub 저장소를 만들고 처음 push하는 절차도 함께 다룬다.
{ch-vercel}부터 {ch-env-secrets}까지가 이 구성의 이유였다면, 이 부록은 어느 화면에서 무엇을 누르는지를 실제 대시보드 화면과 함께 따라간다.
`flashcard-advanced/DEPLOY.md`에는 같은 절차가 익숙해진 뒤 빠르게 확인하는 체크리스트로 정리되어 있다.

대시보드의 메뉴 이름과 위치는 자주 바뀐다(이 부록의 화면은 2026년 7월 기준이다).
화면이 책과 다르면 메뉴 이름보다 "무엇을 어디에 등록하는가"로 되짚는 편이 안전하므로, 관문을 다루는 절 끝에 그 목적을 한 줄로 남겨 두었다.

== 로그인은 세 관문을 지난다

로그인이 지나는 길을 먼저 그려 두면 막혔을 때 어느 화면을 열지 바로 안다.
사용자가 "Google로 계속하기"를 누르면 요청은 세 관문을 지나고, 관문마다 설정이 하나씩 필요하다.

첫째, 앱이 Supabase의 인증 서버(GoTrue)에 "이 사용자를 Google로 로그인시켜 달라"고 넘긴다.
Supabase에서 그 프로바이더(provider, 로그인을 대신 처리해 주는 Google·GitHub 같은 서비스. {ch-supabase-auth})가 켜져 있어야 지난다.
둘째, Supabase가 사용자를 Google 로그인 화면으로 보낸다.
Google 쪽에 "Supabase가 보낸 요청을 받아 준다"는 등록이 있어야 지난다.
셋째, Google이 인증을 마치면 Supabase를 거쳐 앱의 `/auth/callback`으로 돌려보낸다.
Supabase에 "이 앱 주소로 돌려보내도 된다"는 등록이 있어야 지난다.

하나라도 빠지면 로그인은 그 관문에서 멈추고, 관문마다 실패 증상이 달라 증상만으로 빠진 설정을 좁힐 수 있다(이 부록 끝의 "로그인이 안 될 때").

== 1. Supabase 프로젝트 만들기

https://supabase.com[supabase.com]에서 무료 계정을 만들고 New project를 누른다.
프로젝트 이름과 데이터베이스 비밀번호를 정하는데, 이 비밀번호는 나중에 연결 문자열에 들어가므로 비밀번호 관리자에 적어 둔다.
리전(region)은 Vercel 함수가 기본으로 뜨는 리전(iad1)과 같은 East US (North Virginia)를 고른다.
서울 리전이면 함수와 DB 사이 왕복이 180ms쯤으로 늘어, 그 왕복을 서너 번 하는 화면 하나마다 0.5~0.7초가 더 걸린다({ch-supabase-db}).

프로젝트가 만들어지면 두 종류의 값을 꺼내 둔다.
하나는 DB 연결 문자열이다.
대시보드 위쪽의 Connect 버튼을 누르면 Direct connection, Transaction pooler, Session pooler 세 문자열이 나온다.
서버가 쓸 Transaction pooler(포트 6543)와 마이그레이션이 쓸 Session pooler(포트 5432)를 각각 복사한다(둘의 차이는 {ch-supabase-db}).
남은 Direct connection은 {ch-free-tier}의 `pg_dump` 백업에 쓴다.
복사한 문자열의 비밀번호 자리에는 `[YOUR-PASSWORD]` 같은 자리표시자가 있으니, 대괄호까지 통째로 지우고 프로젝트를 만들 때 정한 비밀번호로 바꿔 둔다.
다른 하나는 API 값이다.
Settings → API에서 Project URL과 anon(public) key를 복사한다.
이 값들은 5절에서 Vercel 환경 변수로 넣으므로 비밀번호 관리자 항목에 함께 모아 두고, 저장소 안에 두려면 커밋되지 않는 `.env.dev`({ch-env-secrets})에만 둔다.

이 책은 개발용과 운영용 DB를 나눠 쓰므로({ch-supabase-db}) 같은 방식으로 프로젝트를 하나 더 만든다.
아래 로그인 설정도 두 프로젝트에 각각 해야 하고, 개발 프로젝트에 빠뜨리는 것이 로그인 실패의 흔한 원인이다.

== 2. OAuth 프로바이더 등록 (관문 1과 2)

로그인 버튼 하나를 살리려면 Google(또는 GitHub)에 이 앱을 위한 클라이언트를 만들고(둘째 관문), 그 값을 Supabase에 넣어 프로바이더를 켜야 한다(첫째 관문).

=== Google 클라이언트 만들기

https://console.cloud.google.com[console.cloud.google.com]에 들어간다.
OAuth 설정은 지금 *Google 인증 플랫폼(Google Auth Platform)* 한 곳에 모여 있다.
처음 들어가면 클라우드 프로젝트를 만들라는 안내가 먼저 나오므로, 화면 위쪽의 프로젝트 선택 칸에서 새 프로젝트를 만들고 이름을 정한다(Supabase 프로젝트와는 별개이고, 이름은 아무래도 좋다).
프로젝트가 선택된 상태에서 왼쪽 메뉴가 개요·브랜딩·대상·클라이언트로 되어 있으면 제대로 찾아온 것이다.

먼저 브랜딩(옛 OAuth consent screen)에서 사용자 유형을 External로 두고 앱 이름을 정한다.
External 클라이언트는 처음에 테스트 모드라 대상 화면의 테스트 사용자 목록에 올린 계정만 로그인할 수 있으므로, 내 계정을 그 목록에 넣어 둔다.
다른 사람에게 주소를 건넬 계획이라면 같은 화면에서 게시 상태를 프로덕션으로 올린다.
그다음 클라이언트 → 클라이언트 만들기로 가서 애플리케이션 유형을 웹 애플리케이션으로 고른다.
가장 중요한 칸이 승인된 리디렉션 URI(Authorized redirect URIs)이고, 여기에는 앱 주소가 아니라 Supabase 주소를 넣는다.

----
https://<project-ref>.supabase.co/auth/v1/callback
----

`<project-ref>`는 각 Supabase 프로젝트의 고유 식별자로, 1절에서 복사한 Project URL(`https://<project-ref>.supabase.co`)의 앞부분에 들어 있다.
Google이 인증을 마치고 처음 돌려보내는 곳은 Supabase이고, 앱의 `/auth/callback`은 그다음 홉(hop, 중계 구간)이다.
여기에 앱 주소를 넣으면 Google 화면에서 `redirect_uri_mismatch` 오류로 막힌다.

=== GitHub 클라이언트 만들기

GitHub도 구조는 같다.
https://github.com/settings/developers[github.com/settings/developers]에서 New OAuth App을 만들고, Authorization callback URL에 위와 똑같은 Supabase 콜백 주소를 넣는다.
필수 칸인 이름(Application name)과 홈페이지 주소(Homepage URL)에는 앱 이름과 배포 주소를 적으면 되고, 로그인 동작에는 영향이 없다.
발급된 Client ID와 Secret을 Supabase의 Sign In / Providers → GitHub에 넣고 사용 설정한다.

=== 개발용은 클라이언트를 따로

개발 프로젝트에도 같은 등록이 필요하다.
한 클라이언트에 개발 프로젝트의 콜백 주소까지 함께 등록해도 동작은 하지만, 그러면 개발과 운영이 같은 Client ID와 Secret을 나눠 쓴다.
프로젝트마다 클라이언트를 따로 만들면 개발용 값은 개발 Supabase 프로젝트에만 들어가 두 환경이 서로를 건드리지 않는다.
목적(관문 1·2): 로그인에 쓸 프로바이더는 Supabase에서 켜 두고, 그 프로바이더에는 Supabase 콜백 주소를 등록해 둔다.

== 3. 돌아올 주소 등록 (관문 3)

Supabase는 인증을 마친 사용자를 미리 허락한 주소로만 돌려보낸다.
Supabase 대시보드에서 Authentication → URL Configuration을 연다.

칸은 Site URL과 Redirect URLs(옛 이름은 Additional Redirect URLs) 둘이다.
Redirect URLs는 "돌아와도 되는 주소 목록"이고, 앱이 로그인 때 넘기는 돌아올 주소(`https://<앱 주소>/auth/callback`)가 이 목록에 있어야 그 주소로 돌아온다.

Site URL은 Redirect URLs에 맞는 주소가 없을 때 Supabase가 대신 보내는 기본 주소라, 잘못되어 있으면 로그인이 조용히 엉뚱한 곳으로 샌다.
이 책을 쓰는 동안에도 개발 프로젝트의 Site URL이 `http://localhost:8080`으로 남아 있어, 배포 사이트에서 로그인한 사용자가 오류 메시지 없이 `localhost:8080`으로 튕긴 일이 있었다(전말은 저장소의 `notes/2026-07-login-outage.md`).

두 칸은 이렇게 채운다.
운영 프로젝트는 Site URL을 배포 주소(커스텀 도메인이 있으면 그 주소)로 두고, Redirect URLs에 그 주소의 `/auth/callback`을 넣는다.
개발 프로젝트는 Site URL을 개발 배포의 고정 주소로 두고, Redirect URLs에 그 주소의 `/auth/callback`과 함께 `http://localhost:8080/auth/callback`을 넣는다.
뒤엣것은 로컬에서 개발 DB에 붙어 로그인을 시험할 때 쓴다(`run_dev.sh`, {ch-env-secrets}).

개발 배포 주소로는 배포마다 바뀌는 고유 URL이 아니라 고정된 대표 주소를 넣는다.
main 브랜치 프리뷰의 고정 별칭(`<앱>-git-main-<계정>.vercel.app`)이나 프리뷰에 지정해 둔 대표 도메인(이 책에서는 `flashcard-dev.vercel.app`)이 그것이다.
이 주소는 5절에서 Vercel 프로젝트를 만들어야 정해지므로, 아직 없다면 비워 두었다가 5절을 마친 뒤 돌아와 채운다.

Redirect URLs의 기존 항목을 편집할 때는 값 중간에 새 주소를 붙여 넣어 두 주소가 한 줄로 뭉개지지 않게, 한 항목에 완전한 주소 하나만 넣는다.
목적(관문 3): 앱이 돌려받을 `/auth/callback` 주소를 Redirect URLs에 등록하고, Site URL도 그 배포 주소로 맞춰 둔다.

== 4. GitHub에 저장소 만들고 올리기

Vercel은 GitHub 저장소에서 코드를 가져가므로, 그 전에 내 컴퓨터의 저장소를 GitHub에 올려 둔다.
{ch-git}의 안내대로 이미 계정을 만들어 push했다면, 운영용 release 브랜치까지 올라가 있는지만 확인하고 이 절을 건너뛴다.
아직이라면 여기서 첫 push를 한다.

https://github.com[github.com]에서 무료 계정을 만들고, New repository로 빈 저장소를 만든다.
저장소 이름만 정하고, README·`.gitignore`·라이선스를 추가하는 세 옵션(Add a README file, Add .gitignore, Choose a license)은 모두 끈 채 비워 둔다.
내 컴퓨터에 이미 코드와 이력이 있으므로 원격은 빈 그릇이어야 한다.
공개(Public)든 비공개(Private)든 {ch-env-secrets}의 규칙은 같아서, 비밀 값은 커밋하지 않는다.

{ch-first-run}에서 클론한 저장소의 원격은 저자의 저장소로 잡혀 있으므로, 할 일은 원격을 방금 만든 내 저장소 주소로 바꾸는 것이다.
"이 저장소의 원격을 GitHub의 <주소>로 바꾸고 main을 push해 줘" 정도로 에이전트에게 지시하면 된다.
첫 push에서는 SSH 키를 등록하거나 액세스 토큰을 만들어 비밀번호 대신 쓰는 인증을 거친다.
절차가 자주 바뀌므로 GitHub 공식 문서(SSH는 "Adding a new SSH key to your GitHub account", 토큰은 "Managing your personal access tokens")의 최신 안내를 따르고footnote:[두 문서 모두 https://docs.github.com/en/authentication[GitHub Authentication documentation] 아래에 있다.], 막히면 그 화면의 문구를 에이전트에게 보여 주며 물어본다.

push가 끝나면 {ch-git}의 브랜치 정책대로 운영용 release 브랜치를 만들어 함께 올려 둔다.
이것도 "main에서 release 브랜치를 만들어 push해 줘"라고 지시하면 된다.

=== 마이그레이션 시크릿 등록

{ch-migrations}의 워크플로가 스키마를 DB에 적용하려면 저장소가 연결 문자열을 알아야 한다.
GitHub 저장소의 Settings → Secrets and variables → Actions에서 New repository secret을 눌러 둘을 등록한다.
`DEV_MIGRATE_DATABASE_URL`에는 개발 프로젝트의 Session pooler 연결 문자열(포트 5432)을, `PROD_MIGRATE_DATABASE_URL`에는 운영 프로젝트의 같은 문자열을 넣는다.
그러면 마이그레이션 파일이 바뀐 커밋마다 워크플로가 브랜치를 보고 알맞은 DB에 스키마를 적용한다.
이 단계를 건너뛰면 5절의 배포는 성공해도 테이블이 하나도 없는 DB 위에 앱이 뜬다.
로그인 직후 프로필을 만드는 첫 쿼리가 실패해 500 오류 화면("일시적인 오류가 발생했어요")이 뜨고, Vercel Logs에는 `relation "profiles" does not exist`가 남는다.

== 5. Vercel에 올리고 환경을 나눈다

https://vercel.com[vercel.com]에서 Add New Project로 저장소를 가져온다(import).
Root Directory는 완성본 앱이 있는 `flashcard-advanced`로 지정한다.
루트에는 책 원고와 연습용 코드도 있어서 그대로 두면 Vercel이 앱을 찾지 못한다.
Framework Preset은 `vercel.json`의 `"framework": null`이 덮어쓰므로 무엇으로 감지되든 상관없다({ch-vercel-config}).

import 화면에서 Deploy를 누르면 첫 배포가 시작된다.
환경 변수가 없어 이 배포는 500 오류만 내지만, 필수 값이 없으면 함수가 일부러 기동을 거부하는 것이니({ch-vercel-config}) 아래에서 환경 변수를 채운 뒤 다시 배포하면 된다.
배포가 끝나면 프로젝트 화면 위쪽에 뜨는 `<앱 이름>.vercel.app` 형태의 주소가 3절의 Redirect URLs와 Site URL에 넣을 배포 주소다.

이 책의 브랜치 정책은 main을 개발용, release를 운영용으로 삼는데({ch-git}), Vercel은 처음에 main을 운영 브랜치로 잡아 둔다.
그대로 두면 main에 push할 때마다 운영 도메인에 배포되므로, Settings → Environments를 연다.
세 환경(Production, Preview, Development)이 각각 따르는 브랜치와 도메인이 여기 있다.

Production을 열어 Branch Tracking의 브랜치 값을 main에서 release로 바꾼다.
이제 release에 병합할 때만 운영에 배포되고, main에 push하면 프리뷰(개발 확인용) 배포가 된다.

다음은 환경 변수다.
1절에서 꺼내 둔 값을 스코프별로 나눠 등록한다.
`DATABASE_URL`에는 Transaction pooler 연결 문자열(포트 6543)을, `SUPABASE_URL`에는 Project URL을, `SUPABASE_ANON_KEY`에는 anon(public) key를 넣는다.
Production 스코프에는 운영 프로젝트 값을, Preview 스코프에는 개발 프로젝트 값을 넣어야 개발 배포는 개발 DB에, 운영 배포는 운영 DB에 붙는다({ch-env-secrets}).
세 번째 스코프인 Development 칸은 비워 둔다.
이름과 달리 `vercel dev`라는 로컬 실행 명령이 읽는 자리라 이 책의 구성에서는 쓰이지 않고({ch-vercel-config}), 개발 값이 들어갈 곳은 Preview다.
값은 각 환경 상세 화면의 Environment Variables 구역이나 왼쪽 메뉴 Environment Variables에서 넣는다.

환경 변수는 다음 배포부터 적용되므로, 값을 바꿨다면 다시 push하거나 대시보드에서 Redeploy한다.

마지막으로, Vercel은 프리뷰 배포에 기본으로 보호를 걸어 Vercel에 로그인한 팀 구성원만 열 수 있게 한다.
그러면 로그인 시도가 앱에 닿기도 전에 Vercel 로그인 화면이 가로채므로, Settings → Deployment Protection → Vercel Authentication의 Require Log In을 꺼 프리뷰를 공개로 연다(Hobby 플랜에서 가능).

== 로그인이 안 될 때

첫째, 로그인 버튼을 눌렀더니 Supabase 주소에서 `provider is not enabled`가 뜬다면 그 프로젝트에서 프로바이더가 꺼진 것이다(관문 1).
Sign In / Providers에서 켠다.

둘째, Google이나 GitHub 화면에서 `redirect_uri_mismatch`가 뜬다면 그 프로바이더에 Supabase 콜백이 등록되지 않은 것이다(관문 2).
앱 주소가 아니라 Supabase 주소(`https://<project-ref>.supabase.co/auth/v1/callback`)를 등록한다.

셋째, 로그인은 되는데 마지막에 엉뚱한 주소(예: `localhost:8080`)로 간다면, Redirect URLs에 그 배포의 `/auth/callback`이 없어 Supabase가 기본값인 Site URL로 보낸 것이다(관문 3).
Redirect URLs와 Site URL을 함께 확인한다.

이 밖에 세 가지가 더 있다.
나는 로그인이 되는데 다른 사람만 Google 화면에서 막힌다면 Google 클라이언트가 아직 테스트 모드다.
Google 인증 플랫폼의 대상 화면에서 그 계정을 테스트 사용자로 넣거나 게시 상태를 프로덕션으로 올린다.
로그인이 실패하고 Vercel Logs에 `net/http: invalid header field value`가 보이면 환경 변수 값에 줄바꿈이나 눈에 보이지 않는 제어 문자가 섞인 것이다(긴 키를 복사할 때 흔하다).
값을 다시 한 줄로 입력한다.
로그인 화면에서 5분 넘게 지체한 뒤 실패한다면 로그인 확인용 임시 쿠키(`fc_pkce`, 300초)가 만료된 것이니 처음부터 다시 시도한다.

== 정리

로그인의 세 관문은 Supabase에서 프로바이더 켜기, Google·GitHub에 Supabase 콜백 등록, Supabase의 Redirect URLs에 앱의 콜백 주소 등록이다.
여기에 Vercel의 환경 분리(브랜치와 스코프)를 더하면 개발과 운영이 각자의 DB와 도메인 위에서 따로 돈다.
메뉴 이름이 바뀌어도 이 구조는 오래가므로, 막히면 증상으로 관문을 짚고 그 관문의 설정 하나를 확인한다.
