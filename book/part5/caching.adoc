= 캐시와 서비스 워커: 낡은 화면이 남지 않게

{ch-pwa}에서 설치 자격의 두 조건을 갖췄다.
HTTPS는 Vercel이 주었고, manifest는 우리가 적었다.
남은 하나가 서비스 워커다.

서비스 워커는 브라우저가 앱과 네트워크 사이에 끼워 주는 작은 프로그램이다.
앱이 보내는 모든 요청이 이 프로그램을 먼저 지나므로, 어떤 요청은 네트워크에 보내고 어떤 요청은 저장해 둔 사본으로 답하도록 우리가 정할 수 있다.
설치되는 앱이 되려면 이 프로그램이 있어야 하고, 오프라인에서 무언가를 보여 주려면 사본을 남겨 두어야 한다.

문제는 그 사본이다.
서비스 워커를 붙이는 순간 앱에는 서버가 통제하지 못하는 저장소가 하나 생긴다.
서버가 "이 응답은 저장하지 말라"고 헤더에 적어 보내도 Cache Storage에는 그 지시가 통하지 않고, 서버 렌더링 앱이라 그 안에 들어가는 것은 사용자의 개인 화면 그 자체다.
무엇을 캐시할지보다 무엇을 캐시하면 안 되는지, 캐시한 것을 언제 어떻게 버릴지가 더 어려운 질문인 이유가 여기에 있다.

이 장에서는 `internal/web/static/sw.js`와 `offline.html`을 읽으며 그 질문들에 답한다.
자바스크립트를 거의 걷어 낸 이 앱에서 서비스 워커만은 왜 자바스크립트를 요구하는지도 함께 짚고, 마지막에는 SPA였다면 이 이야기가 어떻게 달라졌을지를 견주어 본다.

== 등록은 한 줄: 자바스크립트가 필요한 자리

서비스 워커는 저절로 켜지지 않는다.
{ch-htmx}에서 해부한 `app.js`, 곧 이 앱에 남은 유일한 자바스크립트 파일의 한 대목이 등록을 맡는다.

`internal/web/static/app.js` (발췌):

[source,js]
----
// PWA: 서비스 워커 등록 (localhost 포함, http에서는 브라우저가 거부한다).
if ("serviceWorker" in navigator) {
  navigator.serviceWorker.register("/sw.js").catch(() => {});
}
----

이 앱은 화면 갱신을 HTML과 htmx에 맡겨 자바스크립트를 거의 걷어 냈지만, 서비스 워커만은 자바스크립트 없이 켤 방법이 없다.
음성 합성이나 클립보드처럼 브라우저에서만 접근할 수 있는 Web API의 하나이기 때문이다.
{ch-htmx}에서 "그래도 남는 자바스크립트"의 목록에 서비스 워커 등록이 들어 있던 이유가 이것이다.

조건은 `"serviceWorker" in navigator` 하나로, 지원하지 않는 브라우저를 걸러 낸다.
개발 환경과 운영 환경을 구분하는 분기는 없다.
브라우저 자체가 HTTPS에서만 서비스 워커를 허용하고 예외는 localhost뿐이라, {ch-first-run}의 로컬 서버(`localhost:8080`)에서는 등록되고 그 밖의 평문 HTTP에서는 브라우저가 알아서 거부한다.
로컬에서도 켜 두는 것은 의도적이다.
페이지가 network-first라 코드를 고치고 새로고침하면 바로 반영되므로, 캐시가 개발을 방해하는 일이 크게 줄었다.
그래도 CSS 같은 정적 자원은 stale-while-revalidate 탓에 새로고침 한 번 늦게 보일 수 있다.
개발자 도구(DevTools)의 Application 탭에서 "Update on reload"를 켜 두면 이 어긋남도 사라진다.

.[용어 풀이] 개발자 도구(DevTools)
[NOTE]
====
브라우저에 내장된 점검 창이다.
지금 열려 있는 페이지의 HTML과 CSS, 오간 네트워크 요청, 브라우저에 저장된 캐시와 서비스 워커를 들여다보고 그 자리에서 바꿔 볼 수도 있다.
Chrome에서는 F12를 누르거나(macOS는 ⌥⌘I), 화면에서 오른쪽 클릭 후 "검사"를 고르면 열린다.
화면에 나온 결과만으로는 원인을 알 수 없을 때 자동차의 보닛을 열어 엔진을 확인하는 일에 해당하고, 설치와 캐시를 확인하는 절차도 전부 이 창에서 이루어진다.
====

`.catch(() => {})`로 실패를 삼키는 것도 의도적이다.
서비스 워커 등록에 실패해도 앱은 그냥 캐시 없이 동작할 뿐이므로, 사용자에게 보여 줄 오류가 아니다.

== sw.js: 무엇을 캐시하고 무엇을 캐시하지 않는가

`internal/web/static/sw.js`의 전문이다.
직접 쓴 일흔 줄 남짓한 파일이고, Workbox(서비스 워커 코드를 대신 만들어 주는 구글의 라이브러리) 같은 기성 도구를 쓰지 않았다.
어떤 요청을 캐시하고 어떤 요청은 캐시하지 않을지 정하는 규칙 전부가 이 안에 있다.
지금 이 전문을 다 읽을 필요는 없다.
아래에서 한 조각씩 다시 꺼내 볼 것이고, 지금은 "요청을 세 갈래로 나눠 다르게 처리하고, 저장소는 두 개를 쓴다"는 것만 보면 된다.

[source,js]
----
/* flashcard service worker.
   캐시는 둘로 나눈다. PAGES는 서버가 사용자별로 렌더링한 HTML이라 로그아웃할
   때 app.js가 지운다(서버는 이 응답에 no-store를 붙인다). STATIC은 사용자와
   무관한 자원이라 그대로 둔다. 페이지는 network-first(오프라인일 때만 마지막
   사본, 그것도 없으면 오프라인 안내 페이지), 정적 자원은
   stale-while-revalidate, API는 network only. */
const STATIC = "flashcard-static-v3";
const PAGES = "flashcard-pages-v3"; // 접두사 "flashcard-pages"는 app.js와 약속된 것
const KEEP = [STATIC, PAGES];
const OFFLINE = "/offline.html";

self.addEventListener("install", (event) => {
  event.waitUntil(
    caches
      .open(STATIC)
      .then((cache) => cache.add(OFFLINE))
      .catch(() => {}) // 첫 설치가 오프라인이어도 등록 자체는 실패시키지 않는다
      .then(() => self.skipWaiting()),
  );
});

self.addEventListener("activate", (event) => {
  event.waitUntil(
    caches
      .keys()
      .then((keys) =>
        Promise.all(
          keys.filter((k) => !KEEP.includes(k)).map((k) => caches.delete(k)),
        ),
      )
      .then(() => self.clients.claim()),
  );
});

self.addEventListener("fetch", (event) => {
  const url = new URL(event.request.url);
  const isData =
    url.pathname.startsWith("/api/") || url.origin !== self.location.origin;
  if (event.request.method !== "GET" || isData) return; // network only

  // 서버 렌더링 페이지: 항상 네트워크 우선, 오프라인이면 마지막 사본,
  // 그마저 없으면(한 번도 안 열어 본 주소) 오프라인 안내 페이지.
  if (event.request.mode === "navigate") {
    event.respondWith(
      (async () => {
        const pages = await caches.open(PAGES);
        try {
          const res = await fetch(event.request);
          if (res.ok) pages.put(event.request, res.clone());
          return res;
        } catch {
          const cached = await pages.match(event.request);
          if (cached) return cached;
          const offline = await caches.match(OFFLINE);
          return offline || Response.error();
        }
      })(),
    );
    return;
  }

  // 정적 자원: stale-while-revalidate. URL에 콘텐츠 해시(?v=)가 붙어 있어
  // 배포로 내용이 바뀌면 주소부터 달라진다. 낡은 사본이 새 HTML에 물리지 않는다.
  event.respondWith(
    caches.open(STATIC).then(async (cache) => {
      const cached = await cache.match(event.request);
      const network = fetch(event.request)
        .then((res) => {
          if (res.ok) cache.put(event.request, res.clone());
          return res;
        })
        .catch(() => cached);
      return cached || network;
    }),
  );
});
----

맨 위 주석이 이 파일의 요약이다.
요청을 데이터(API), 페이지 HTML, 정적 자원의 세 갈래로 나누고, 갈래마다 다른 캐시 전략을 쓴다.
그리고 저장한 것을 `PAGES`와 `STATIC` 두 저장소에 나눠 담는다.
왜 세 갈래이고 왜 저장소가 두 개인지가 이 절의 이야기다.

.[용어 풀이] 캐시 전략(Caching Strategy)
[NOTE]
====
같은 요청에 대해 캐시에 있는 사본과 네트워크의 최신 응답 중 무엇을 먼저 쓸지 미리 정해 둔 규칙이다.
network-first는 네트워크를 먼저 시도하고 실패했을 때만 사본을 꺼내는 방식, cache-first는 사본이 있으면 네트워크에 아예 묻지 않는 방식, stale-while-revalidate는 낡은(stale) 사본을 즉시 돌려주는 동안(while) 뒤에서 새 응답을 받아 캐시를 갱신(revalidate)하는 방식이다.
network only는 캐시를 건드리지 않고 언제나 네트워크로 나간다.
무엇을 고를지는 그 응답이 낡았을 때 사용자가 무엇을 손해 보는지에 달렸다.
빨리 보여 주는 이득과 정확하게 보여 주는 이득 중 어느 쪽이 큰지를 요청의 종류마다 따로 답한 것이 캐시 전략이다.
====

전략을 읽기 전에 이 응답들이 어디에 쌓이는지부터 알아 두어야 한다.
`caches.open("이름")`이 여는 저장소는 브라우저가 평소에 알아서 굴리는 캐시와는 다른 물건이다.

.[용어 풀이] Cache Storage(캐시 저장소)
[NOTE]
====
서비스 워커가 응답을 이름표 붙인 상자에 담아 두는 브라우저 안의 저장소다.
브라우저가 `Cache-Control` 헤더를 보고 알아서 굴리는 HTTP 캐시와는 다른 물건이라, 여기에 무엇을 넣고 언제 버릴지는 서비스 워커 코드가 전부 정한다.
상자는 이름으로 여러 개 만들 수 있고(`caches.open`), 이름째로 통째로 버릴 수 있다(`caches.delete`).
서버가 "저장하지 말라"고 붙인 헤더도 이 저장소에는 통하지 않는다는 점이 뒤에서 중요한 문제가 된다.
사용자가 브라우저 데이터를 지우거나 앱을 삭제하기 전까지 남는, 앱이 기기에 두고 온 짐이다.
====

서비스 워커는 세 가지 생애 사건, 곧 설치(`install`), 활성화(`activate`), 요청 가로채기(`fetch`)에 반응한다.

`install`에서는 오프라인 안내 페이지(`/offline.html`)를 미리 받아 `STATIC` 상자에 넣어 둔다.
네트워크가 끊긴 뒤에 오프라인 페이지를 받아 오려는 것은 앞뒤가 맞지 않으므로, 이것만은 미리 캐시(precache)해 두어야 한다.
`event.waitUntil(...)`은 그 저장이 끝날 때까지 설치를 완료로 치지 말라는 뜻이고, 저장이 끝나면 `skipWaiting()`을 부른다.
기본 동작대로라면 새 서비스 워커는 이전 버전을 쓰는 탭이 전부 닫힐 때까지 대기실에서 기다리는데, `skipWaiting()`은 그 대기를 건너뛰고 즉시 활성화한다.
여기서도 `.catch(() => {})`로 실패를 삼킨다.
첫 방문이 하필 네트워크가 불안한 순간이라 이 한 파일을 못 받아 왔다고 해서, 서비스 워커 등록 자체가 실패할 이유는 없다.

`activate`에서는 두 가지 일을 한다.
`KEEP` 목록에 없는 옛 캐시를 전부 지우고, `clients.claim()`으로 이미 열려 있는 탭까지 새 서비스 워커의 통제 아래로 데려온다.
`skipWaiting`과 `clients.claim`이 짝을 이루어야 배포 직후에 새 버전이 곧바로 적용된다.
이 앱의 캐시 이름이 v3인 것은 저장소를 하나에서 둘로 나누면서 버전을 올린 흔적이고, 그 덕에 예전 `flashcard-v2` 상자는 활성화 때 통째로 사라진다.

`fetch`가 핵심이다.
가장 먼저 하는 일이 캐시하지 않을 요청을 걸러 내는 것이다.

[source,js]
----
const isData =
  url.pathname.startsWith("/api/") || url.origin !== self.location.origin;
if (event.request.method !== "GET" || isData) return; // network only
----

`return`은 "내가 처리하지 않겠다"는 뜻이고, 그러면 요청은 평소대로 네트워크로 나간다.
GET이 아닌 요청, `/api/`로 시작하는 요청, 다른 오리진(이 앱이 아닌 다른 사이트)으로 나가는 요청이 여기에 걸린다.
htmx가 보내는 채점·저장 같은 POST 요청도 GET이 아니므로 전부 이 갈래다.

학습 앱에서는 반드시 이렇게 해야 한다.
`/api/` 응답을 캐시하면 "오늘 복습할 카드" 목록이 낡는다.
어제 다 외운 카드가 오늘도 큐에 남아 있거나, 방금 추가한 카드가 목록에 나타나지 않는다.
간격 반복은 서버가 계산한 최신 상태가 곧 앱의 가치인 기능이라, 여기서 낡은 데이터를 보여 주는 것은 앱이 조금 느린 것보다 나쁘다.
그래서 데이터는 무조건 네트워크다.

=== 페이지 HTML도 데이터다: navigate는 network-first

그런데 이 앱에서 걸러 내야 할 "데이터"는 `/api/` 경로가 전부가 아니다.
{ch-go-templates}에서 봤듯 페이지 HTML은 서버가 요청 시점에 렌더링하고, 홈 화면의 복습 큐도 통계 화면의 숫자도 HTML 안에 이미 들어 있다.
페이지가 곧 데이터다.
페이지 응답을 캐시에서 먼저 돌려주면 API를 캐시했을 때와 똑같은 문제가 생긴다.
방금 카드를 추가하고 홈으로 돌아왔는데 캐시된 어제의 목록이 보이는 식이다.

그래서 주소를 입력하거나 링크를 눌러 페이지를 여는 요청(`event.request.mode === "navigate"`)은 network-first로 처리한다.

[source,js]
----
if (event.request.mode === "navigate") {
  event.respondWith(
    (async () => {
      const pages = await caches.open(PAGES);
      try {
        const res = await fetch(event.request);
        if (res.ok) pages.put(event.request, res.clone());
        return res;
      } catch {
        const cached = await pages.match(event.request);
        if (cached) return cached;
        const offline = await caches.match(OFFLINE);
        return offline || Response.error();
      }
    })(),
  );
  return;
}
----

항상 네트워크를 먼저 시도하고, 성공한 응답은 사본을 `PAGES` 상자에 남긴다.
캐시를 읽는 것은 `fetch`가 예외를 던졌을 때, 즉 오프라인일 때뿐이다.
온라인일 때는 캐시가 화면에 아무 영향을 주지 않으므로 낡은 목록이 보일 일이 없고, 오프라인일 때만 "아무것도 안 뜨는 것보다는 어제의 화면"이라는 차선을 취한다.

오프라인일 때의 답이 두 단계인 것을 눈여겨보자.
먼저 그 주소의 마지막 사본을 찾고, 없으면 오프라인 안내 페이지를 내준다.

=== 사본이 없을 때 보여 줄 화면: offline.html

한 번도 열어 본 적 없는 주소를 오프라인에서 열면 캐시에 사본이 있을 리 없다.
이때 `Response.error()`만 돌려주면 브라우저의 네트워크 오류 화면이 뜬다.
브라우저 탭에서라면 익숙한 화면이지만, `display: "standalone"`으로 설치된 앱에서는 사정이 다르다.
주소창도 없는 창 안에 브라우저 오류 화면이 뜨면 사용자에게는 앱이 고장 난 것으로 보인다.

그래서 `internal/web/static/offline.html`을 두고, 서비스 워커가 설치 때 이 파일을 미리 캐시해 둔다.
이 파일에는 지켜야 할 조건이 하나 있다.
자기 힘만으로 떠야 한다는 것이다.

`internal/web/static/offline.html` (발췌):

[source,html]
----
  <!-- 스타일을 인라인으로 둔다: 이 페이지는 네트워크가 없을 때 뜨므로
       app.css가 캐시에 없어도 제대로 보여야 한다. -->
  <style>
    /* ... */
  </style>
----

`app.css`를 `<link>`로 불러오게 두면, 그 CSS가 캐시에 없는 상황에서는 스타일 없는 맨 HTML이 뜬다.
오프라인 안내 페이지가 오프라인일 때 깨져 보이는 것만큼 허무한 일도 없으므로, 스타일을 이 파일 안에 인라인으로 넣어 다른 캐시 항목에 기대지 않게 했다.
같은 이유로 이 페이지의 자바스크립트도 `online` 이벤트를 듣고 새로고침하는 두 줄뿐이다.
연결이 돌아오면 사용자가 원래 가려던 그 주소를 다시 여는 데까지 손이 한 번도 필요하지 않다.

=== 정적 자원: 일단 캐시로 보여 주고 뒤에서 갱신한다(stale-while-revalidate)

마지막 갈래는 두 필터를 다 통과한 요청, 즉 `app.css`와 `htmx.min.js`, 아이콘 같은 정적 파일이다.
여기에는 stale-while-revalidate를 쓴다.

[source,js]
----
const cached = await cache.match(event.request);
const network = fetch(event.request)
  .then((res) => {
    if (res.ok) cache.put(event.request, res.clone());
    return res;
  })
  .catch(() => cached);
return cached || network;
----

캐시에 있으면 그것을 즉시 돌려주고, 없으면 네트워크 응답을 기다린다.
어느 쪽이든 네트워크 요청은 함께 날아가서 성공하면 캐시를 갱신한다.
스타일과 스크립트는 어제의 사본을 써도 화면이 잘못되지 않으므로, 페이지와 달리 즉시성보다 속도를 택했다.
{ch-vercel}에서 본 것처럼 정적 자산은 함수까지 가야 나오는데, 이 캐시 덕에 재방문에서는 그 왕복 자체가 사라진다.

"어제의 사본을 써도 화면이 잘못되지 않는다"는 말에는 조건이 하나 붙는다.
어제의 CSS와 오늘의 HTML이 서로 아귀가 맞아야 한다는 것이다.
이 조건을 어떻게 지키는지는 아래의 "낡은 정적 자원이 새 화면에 물리는 문제" 절에서 따로 다룬다.

`cache.put`에 `res.clone()`을 넘기는 것도 그냥 지나칠 대목이 아니다.
응답 본문은 한 번만 읽을 수 있는 흐름이라, 캐시에 넣으면서 동시에 페이지에 돌려주려면 복제본이 필요하다.

=== 저장소를 둘로 나눈 이유: 개인 화면과 공용 자원

여기까지가 "무엇을 어떤 전략으로 캐시하는가"였다.
남은 질문은 "캐시한 것을 어디에 담고 언제 버리는가"이고, 이 앱은 그 답으로 상자를 두 개 쓴다.

`PAGES`에 담기는 것은 서버가 그 사용자를 위해 렌더링한 HTML이다.
덱 목록에는 사용자가 만든 덱 이름이, 학습 화면에는 카드의 앞뒷면이, 통계 화면에는 그 사람의 정답률이 들어 있다.
반면 `STATIC`에 담기는 `app.css`, `htmx.min.js`, 아이콘, `offline.html`은 누가 받아도 같은 파일이다.

성격이 다르니 버리는 시점도 달라야 한다.
로그아웃은 "이 기기에서 내 것을 치운다"는 뜻이므로 개인 화면의 사본은 그때 사라져야 하지만, 공용 자원까지 지우면 다음 로그인의 첫 화면이 느려질 뿐 얻는 것이 없다.
상자를 하나로 두면 이 둘을 따로 버릴 방법이 없다.
저장소를 이름으로 나눠 두었기 때문에 `caches.delete("flashcard-pages-v3")` 한 번으로 개인 화면만 통째로 버릴 수 있다.

=== 서버의 no-store는 캐시 저장소에 통하지 않는다

이 대목은 서버 렌더링 앱에 서비스 워커를 붙일 때 가장 놓치기 쉬운 함정이다.

이 앱의 페이지 응답에는 이미 "저장하지 말라"는 헤더가 붙어 있다.
{ch-go-templates}에서 본 `render` 함수의 한 줄이다.

`internal/web/render.go` (발췌):

[source,go]
----
c.Header("Cache-Control", "no-store") // 페이지는 사용자별이라 캐시에 공유하면 안 된다
----

그런데 이 헤더는 브라우저의 HTTP 캐시와 중간 프록시에 하는 말이지, 서비스 워커에 하는 말이 아니다.
`cache.put(request, response)`는 응답의 `Cache-Control`을 읽지 않는다.
개발자가 넣으라고 했으니 넣을 뿐이다.
그래서 서버가 no-store를 붙인 개인 화면을 우리가 직접 쓴 `sw.js` 코드가 사용자 기기의 Cache Storage에 그대로 저장한다.

이것은 버그가 아니라 우리가 택한 것이다.
오프라인에서 마지막 화면이라도 보여 주겠다고 했으니 개인 HTML을 기기에 남기는 것은 그 약속의 대가다.
다만 대가를 치르기로 했으면 뒷정리도 우리 몫이 된다.
사용자가 로그아웃했는데 방금 전까지 보던 카드 목록이 기기의 캐시에 남아 있고, 오프라인 상태에서 그 주소를 열면 다시 뜬다면, 그것은 로그아웃이라고 부르기 어렵다.

그래서 로그아웃 핸들러가 로그인 화면으로 돌려보낼 때 표시를 하나 달아 준다.

`internal/web/authpages.go` (발췌):

[source,go]
----
w.clearAuthCookies(c)
// signed_out은 app.js에 대한 신호다: 서비스 워커가 오프라인용으로 캐시해 둔
// 이 사용자의 페이지 HTML을 지우게 한다.
c.Redirect(http.StatusSeeOther, "/login?signed_out=1")
----

그 표시를 보고 캐시를 비우는 것은 브라우저 쪽 코드의 몫이다.

`internal/web/static/app.js` (발췌):

[source,js]
----
if (new URLSearchParams(location.search).has("signed_out")) {
  if ("caches" in window) {
    caches
      .keys()
      .then((keys) =>
        Promise.all(
          keys
            .filter((k) => k.startsWith("flashcard-pages"))
            .map((k) => caches.delete(k)),
        ),
      )
      .catch(() => {});
  }
  history.replaceState(null, "", location.pathname); // 주소창에서 흔적을 지운다
}
----

이름이 `flashcard-pages`로 시작하는 상자만 지우므로 정적 자원은 살아남는다.
쿼리 문자열은 `history.replaceState`로 곧바로 걷어 내, 사용자가 주소를 복사하거나 북마크할 때 `?signed_out=1`이 따라붙지 않게 한다.

쿠키를 지우는 것은 서버가, 캐시를 지우는 것은 브라우저가 한다는 이 분업을 기억해 두는 편이 좋다.
서버는 자기가 내려보낸 개인 화면이 사용자의 기기 어디에 몇 벌이나 남아 있는지 알지 못한다.
서비스 워커를 붙인 앱에서 "지웠다"는 말은 언제나 두 곳을 함께 지웠다는 뜻이어야 한다.

== 신경 써야 할 캐시는 한 층이 아니다

지금까지 서비스 워커의 캐시만 이야기했지만, 배포된 웹 앱에서 응답 하나가 사용자 화면에 닿기까지 거치는 캐시는 여러 층이다.
이 앱에는 세 층이 있고, 층마다 통제하는 주체와 비우는 방법이 다르다.

첫째, 브라우저의 HTTP 캐시다.
서버가 붙인 `Cache-Control` 헤더를 브라우저가 읽고 알아서 굴리는 층이다.
{ch-vercel}에서 본 `public, max-age=3600`이 여기에 하는 말이고, 앞에서 본 `no-store`도 이 층에 하는 말이다.
우리가 이 층을 통제하는 수단은 헤더뿐이고, 코드로 특정 항목을 골라 지울 수는 없다.

둘째, 서비스 워커의 Cache Storage다.
이 층은 정반대다.
헤더는 무시되고, 무엇을 넣고 언제 지울지를 우리 코드가 전부 정한다.
그래서 `no-store`가 통하지 않고, 대신 `caches.delete`로 골라 지울 수 있다.

셋째, Vercel의 CDN과 중간 프록시다.
이 앱은 페이지와 API에 `no-store`를 붙여 두었으므로 개인 응답이 공유 캐시에 남는 일은 없고, 정적 자산만 이 층의 도움을 받는다.

같은 파일 하나가 이 세 층에 각각 다른 나이의 사본으로 존재할 수 있어서 캐시를 다루기가 어렵다.
브라우저 HTTP 캐시에는 한 시간짜리 사본이, Cache Storage에는 지난 방문의 사본이 있는 식이다.
그래서 "고쳤는데 왜 안 바뀌지"라는 질문에는 언제나 "어느 층을 보고 있는가"라는 되물음이 따라온다.
개발자 도구의 Network 탭에서 응답이 어디서 왔는지(`(disk cache)`, `(ServiceWorker)`, 서버)를 확인하는 습관이 이 되물음에 답하는 가장 빠른 길이다.

== 낡은 정적 자원이 새 화면에 물리는 문제

정적 자원에 stale-while-revalidate를 쓰기로 한 순간, 배포 직후에 딱 한 번 나타나는 위험한 조합이 생긴다.
페이지 HTML은 network-first라 항상 최신인데, CSS와 자바스크립트는 캐시에 있는 어제 사본이 먼저 나온다.
새 HTML이 어제의 CSS를 만나는 것이다.
클래스 이름 하나를 바꾼 배포라면 그 화면은 스타일이 빠진 채로 뜬다.

원인은 파일 이름이 고정되어 있다는 데 있다.
`app.css`는 내용이 바뀌어도 이름이 `app.css`라, 캐시에는 같은 요청으로 보인다.
프런트엔드 빌드 도구가 `app.9f9fabf0.css`처럼 이름에 내용 해시를 붙여 주는 이유가 이것이다({ch-vercel}에서 지문이라는 말로 짚었다).

이 앱에는 빌드 도구가 없으니, 이름 대신 URL에 지문을 붙였다.
Go 서버가 시작할 때 embed된 CSS와 자바스크립트의 내용을 한 번 해시해 열두 자리 문자열을 만든다.

`internal/web/routes.go` (발췌):

[source,go]
----
// assetVersion은 embed된 CSS/JS의 내용 해시다. 템플릿이 모든 자산 URL에
// ?v=…로 붙이므로 배포하면 URL 자체가 바뀐다. 정적 파일을
// stale-while-revalidate로 내주는 서비스 워커가 새 페이지에 지난 버전의
// 스타일시트를 짝지을 수 없게 하기 위해서다. 파일 이름은 그대로라 저장소와
// devtools에서 읽기 좋다.
var assetVersion = sync.OnceValue(func() string {
	h := sha256.New()
	for _, name := range []string{"static/app.css", "static/app.js", "static/htmx.min.js"} {
		b, err := staticFS.ReadFile(name)
		if err != nil {
			panic(err)
		}
		h.Write(b)
	}
	return hex.EncodeToString(h.Sum(nil))[:12]
})

// asset은 템플릿 함수다: {{asset "/static/app.css"}}.
func asset(path string) string { return path + "?v=" + assetVersion() }
----

`sync.OnceValue`는 감싼 함수를 첫 호출 때 한 번만 실행하고 그 결과를 기억해 두는 표준 라이브러리 도구다.
페이지를 아무리 많이 렌더링해도 해시 계산은 프로세스마다 한 번이다.

`asset`은 {ch-go-templates}에서 본 템플릿 함수로 등록되어 있고, 공통 레이아웃이 자산 주소를 이 함수에 통과시킨다.

`internal/web/templates/layout.html` (발췌):

[source,html]
----
<link rel="stylesheet" href="{{asset "/static/app.css"}}">
<script src="{{asset "/static/htmx.min.js"}}" defer></script>
<script src="{{asset "/static/app.js"}}" defer></script>
----

브라우저가 받는 주소는 `/static/app.css?v=9f9fabf0d09a`가 된다.
CSS를 한 글자만 고쳐도 해시가 달라지고, 그러면 URL이 달라지고, 캐시에 없는 새 요청이 되어 네트워크로 나간다.
낡은 사본이 새 화면에 물릴 방법이 없어진다.

주소가 내용을 증명하게 되었으니 캐시 기간도 다르게 줄 수 있다.

`internal/web/routes.go` (registerStatic 발췌):

[source,go]
----
r.GET("/static/*filepath", func(c *gin.Context) {
	if c.Query("v") == assetVersion() {
		c.Header("Cache-Control", "public, max-age=31536000, immutable")
	} else {
		c.Header("Cache-Control", "public, max-age=3600")
	}
	// ...
})
----

지문이 맞는 요청의 응답은 영원히 변하지 않으므로 1년짜리 `immutable`을 붙인다.
지문이 없거나 틀린 주소로 들어온 요청에는 예전처럼 한 시간만 준다.
{ch-vercel}에서 한 시간이 상한이었던 이유가 "이름이 안 바뀌니 길게 잡을 수 없다"였는데, 그 전제가 사라지자 상한도 사라졌다.

== 손으로 올리는 캐시 이름

지문을 붙여도 사람이 잊으면 안 되는 수동 단계가 하나 남는다.
`sw.js`의 캐시 전략 자체를 바꿀 때다.

`STATIC`과 `PAGES`의 이름 끝에 붙은 `v3`이 그 수동 단계의 흔적이다.
전략을 바꿨다면 이 이름을 올려야 `activate` 훅이 옛 상자를 통째로 버리고 새 정책으로 다시 시작한다.
이름을 그대로 두고 전략만 바꾸면, 옛 정책으로 채워진 항목이 사용자 기기에 남아 새 코드와 섞인다.

Workbox 같은 라이브러리는 빌드 시점에 캐시 이름과 목록을 자동으로 생성해 이 문제를 없애 준다.
그러나 그 자동화에는 프런트엔드 빌드 파이프라인이 필요하다.
빌드 없이 정적 파일 몇 개로 완결되는 지금 구조에서, 캐시 전략을 거의 바꾸지 않는 앱을 위해 빌드 단계를 들여오는 것은 배보다 배꼽이 크다.
대신 `CLAUDE.md`에 "전략을 바꾸면 캐시 이름을 올린다"를 적어 두고 에이전트에게 지키게 한다.

== 캐시를 고쳤다면 확인할 것 네 가지

캐시는 고쳐도 화면이 즉시 달라지지 않아서, 고친 뒤에 확인하지 않으면 틀린 줄도 모른다.
{ch-pwa}에서 본 개발자 도구의 Application 탭이 확인 창구다.

첫째, Offline 체크박스를 켜고 이미 열어 본 페이지를 새로고침한다.
마지막으로 본 사본이 뜨고 상단에 오프라인 배너가 나타나야 한다(`app.js`가 `navigator.onLine`을 보고 띄운다).

둘째, Offline을 켠 채로 한 번도 열어 본 적 없는 주소를 연다.
브라우저의 네트워크 오류 화면이 아니라 `offline.html`이 떠야 한다.

셋째, 로그아웃한 뒤 Cache Storage를 다시 본다.
`flashcard-pages-v3` 상자가 사라지고 `flashcard-static-v3`만 남아 있어야 한다.

넷째, CSS를 한 글자 고쳐 배포한 뒤 페이지 소스에서 `?v=`의 값이 바뀌었는지 본다.
값이 그대로라면 지문이 계산되지 않은 것이고, 그러면 낡은 스타일이 새 화면에 물릴 수 있다.

== SPA였다면 무엇이 달랐을까

{ch-tech-choices}에서 SPA 대신 서버 렌더링과 htmx를 골랐다.
PWA는 그 선택과 무관하게 성립하지만, 캐시에 관해서는 두 구성이 서로 다른 문제를 떠안는다.
이 장의 캐시 이야기가 왜 이런 모양인지는 그 차이를 보면 분명해진다.

SPA의 PWA에서 캐시에 담기는 것은 앱 셸(shell), 곧 화면을 그리는 자바스크립트와 CSS다.
누가 받아도 같은 파일이라 캐시에 남겨 두기에 부담이 없고, 데이터는 API로 따로 받아 화면에 채운다.
그래서 오프라인에서도 앱의 껍데기는 즉시 뜨고, 데이터를 브라우저 안의 데이터 저장소(IndexedDB)에 미리 내려 두면 화면까지 그릴 수 있다.
사용자의 조작을 화면에 먼저 반영하고 나중에 서버와 맞추는 낙관적 갱신도 여기서 나온다.

서버 렌더링 앱의 PWA에서 캐시에 담기는 것은 완성된 화면 그 자체다.
데이터와 껍데기가 한 HTML 안에 붙어 있으므로 이득과 손해가 동시에 생긴다.

이득은 오프라인에서 내용까지 보인다는 것이다.
캐시된 덱 페이지에는 카드 이름이 이미 들어 있어서, 별도의 데이터 저장소 없이도 마지막으로 본 화면이 그대로 뜬다.
손해가 이 장에서 다룬 문제들이다.
캐시에 개인 정보가 들어가므로 로그아웃할 때 지워야 하고, HTML만 최신이고 CSS는 낡을 수 있으므로 지문을 붙여야 한다.
SPA였다면 캐시에 든 것이 사용자 중립적인 셸뿐이라 첫 번째 문제는 아예 생기지 않고, 빌드 도구가 파일 이름에 해시를 붙여 주니 두 번째 문제도 도구가 해결한다.

그리고 화면을 서버가 그리는 한, 오프라인에서 카드를 채점하는 일은 원리상 할 수 없다.
채점 결과로 바뀐 화면을 그려 줄 서버가 없기 때문이다.
이것을 흉내 내려면 채점 로직과 화면 템플릿을 자바스크립트로 한 벌 더 만들어 브라우저에 두어야 하는데, 그 순간 "로직은 Go 한 곳에만 둔다"는 이 구조의 이유가 사라진다.
오프라인 학습이 핵심 요구였다면 SPA가 정답이었을 것이다.
지하철에서 한두 번 못 여는 것을 감수하는 대신 코드를 한 벌만 유지하기로 한 것이 {ch-tech-choices}의 선택이고, 이 장의 캐시 설계는 그 선택을 따라간 결과다.


== 에이전트 활용 아이디어

서비스 워커는 코드가 일흔 줄뿐이어도, 실수하면 그 결과가 사용자 브라우저에 캐시로 남는다.
게다가 그 실수는 개발자 자신의 브라우저에서는 잘 드러나지 않는다.
개발자는 늘 최신 배포를 보고, 캐시가 문제를 일으키는 것은 옛 사본을 들고 있는 사용자 쪽이기 때문이다.

`CLAUDE.md`에는 세 가지를 적는다.
"`sw.js`의 캐시 전략을 바꾸면 캐시 이름의 버전을 올린다", "/api/ 응답과 GET이 아닌 요청은 캐시하지 않는다", "개인 화면 HTML은 PAGES 캐시에만 담고 로그아웃 때 지운다"이다.
셋 다 잊었을 때 사용자 기기에 흔적이 남는 종류의 실수라 지침으로 적어 둘 값어치가 크다.

캐시 전략을 바꾸는 작업은 확인 시나리오까지 지시문에 담는다.
"배포 후 첫 방문, 재방문, 오프라인, 로그아웃 직후 네 경우에 각 요청이 네트워크와 캐시 중 어디서 오는지, 어느 상자에 무엇이 남는지 표로 예측해 달라"고 하면, 코드보다 먼저 전략의 구멍이 드러난다.

캐시는 눈으로 확인해야 믿을 수 있는 대상이라, 검증까지 에이전트에게 맡기는 것이 좋다.
Claude Code에 브라우저를 붙이면(예: Chrome 확장 연동) 에이전트가 직접 페이지를 열고 `caches.keys()`를 실행해 상자와 그 내용을 읽어 올 수 있다.
서버를 잠시 내려 오프라인 상태를 만든 뒤 안내 페이지가 뜨는지 보게 하는 것도 같은 방법으로 시킬 수 있다.

== 정리

이 장에서는 서비스 워커가 요청을 가로채는 방식과, 그렇게 생긴 캐시를 어떻게 관리할지를 다뤘다.

첫째, `sw.js`는 요청을 세 갈래로 나눈다.
API와 폼 전송은 네트워크 전용이다.
간격 반복 앱에서 낡은 데이터는 느린 앱보다 나쁘기 때문이다.
서버가 렌더링하는 페이지 HTML은 그 자체가 데이터이므로 network-first로 두고 오프라인일 때만 마지막 사본을 꺼내며, 사본조차 없으면 `offline.html`을 보여 준다.
정적 자원만 stale-while-revalidate로 속도를 챙긴다.

둘째, 캐시에 무엇을 넣을지보다 언제 버릴지가 어렵다.
서버가 붙인 `Cache-Control: no-store`는 브라우저의 HTTP 캐시에만 통하고 서비스 워커의 Cache Storage에는 통하지 않으므로, 개인 화면 HTML을 담는 상자(`PAGES`)를 공용 자원 상자(`STATIC`)와 분리하고 로그아웃할 때 앞의 것만 지운다.
쿠키는 서버가, 캐시는 브라우저가 지운다.

셋째, 정적 자원의 URL에는 내용 해시로 만든 지문(`?v=`)을 붙인다.
페이지는 network-first라 늘 최신인데 CSS만 캐시의 옛 사본이 나오는 조합을 막기 위한 것이고, 지문이 맞는 주소는 1년짜리 `immutable`로 캐시할 수 있다는 이득도 따라온다.

넷째, 이 캐시 이야기의 모양은 서버 렌더링이라는 선택에서 나왔다.
SPA였다면 캐시에 담기는 것이 사용자 중립적인 셸이라 개인 정보 문제가 아예 없고, 빌드 도구가 파일 이름에 해시를 붙여 주니 지문 문제도 도구가 해결한다.
대신 오프라인에서 내용까지 보이는 이득은 서버 렌더링 쪽이 가져간다.

앱이 설치까지 됐으니 남은 것은 이 상태를 끊기지 않게 유지하는 일이다.
다음 {ch-free-tier}에서는 이 모든 것을 떠받치는 무료 티어의 한도를 정면으로 들여다본다.
무엇이 가장 먼저 터지는지 계산해 보면 뜻밖의 답이 나온다.
