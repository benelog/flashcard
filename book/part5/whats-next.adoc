= 다음 단계: 여기서 더 공부할 것들

책머리의 "이 책을 읽는 법"에서 각 언어의 완결된 입문, 시각 디자인, 네이티브 앱 개발, 대규모 트래픽을 전제한 확장 전략은 다루지 않는다고 적어 두었다.
그런데 책을 덮고 나면 "내 앱이 조금 자라면 무엇부터 필요해지는가"라는 더 구체적인 질문이 남는다.
이 장은 Flashcard가 일부러 갖추지 않은 것들을 꺼내, 왜 지금은 없어도 됐는지와 언제 필요해지는지를 짝으로 적는다.
모든 앱에 필요한 모범 사례의 목록이 아니라, 이 앱의 제약이 느슨해질 때 차례로 켜야 할 스위치의 목록이다.

== 없는 것을 세는 법

개인 앱에서 기능을 더하고 싶은 유혹을 따르면 대체로 손해다.
그래서 다음 세 질문을 통과하지 못한 것은 만들지 않았다.

첫째, 지금 아프지 않은가.
둘째, 없을 때 생기는 손해가 되돌릴 수 있는 것인가.
셋째, 나중에 넣기가 지금 넣기보다 크게 어려워지는가.

세 번째 질문이 핵심이다.
로그 수집은 나중에 붙여도 늦지 않지만, 데이터 모델의 정합성은 나중에 되돌리기 어렵다.
그래서 {ch-database-design}에서 제약과 외래 키에 공을 들였고 관측성은 뒤로 미뤘다.
아래 주제들도 이 기준으로 줄을 세웠다.

== 검증을 넓히기: E2E 테스트

{ch-quality-gates}에서 검사를 세 자리에 걸었다.
파일을 고칠 때마다 도는 gofmt·go vet, 커밋하기 전에 돌리는 `./check.sh`, GitHub에 push할 때마다 원격 러너에서 도는 CI다.
그 검사들이 부르는 테스트는 계산·파싱과 DB 흐름을 덮는 {ch-unit-tests}의 단위 테스트와, 앱을 통째로 띄워 화면과 API의 배선을 덮는 {ch-app-tests}의 통합 테스트다.
템플릿의 폼 이름이나 htmx 헤더가 잘못된 주소를 가리키는 오류는 이제 `go test` 한 번에 걸린다.

그래도 "화면에서 실제로 로그인이 되는가"에는 답하지 못한다.
{ch-app-tests}의 테스트는 서버의 응답까지만 본다.
htmx가 조각을 화면의 옳은 자리에 끼웠는지, CSS가 버튼을 화면 밖으로 밀어내지 않았는지, `app.js`의 음성 합성과 클립보드가 도는지는 확인하지 않고, 로컬 모드가 고정 사용자로 도니 실제 OAuth 로그인도 그 밖에 있다.
그래서 이 넷은 여전히 사람이 눌러 확인한다.
Playwright 같은 도구를 쓰면 "로그인하고, 덱을 만들고, 카드를 학습하고, 통계가 늘어난다"를 브라우저에서 자동으로 재연하는 E2E(End-to-End) 테스트를 만들 수 있다.

.[용어 풀이] E2E 테스트(End-to-End Test)
[NOTE]
====
사용자가 하듯 브라우저를 자동으로 조작해, 화면부터 서버와 데이터베이스까지 앱 전체를 한 번에 통과시켜 보는 테스트다.
{ch-app-tests}의 통합 테스트는 요청을 코드로 보내므로, 브라우저가 HTML과 CSS와 자바스크립트를 실제로 실행한 결과는 E2E 테스트에서만 드러난다.
대신 브라우저와 실제 데이터베이스를 띄워야 해서 느리고, 화면 구조가 조금만 바뀌어도 깨지기 쉽다.
====

E2E를 CI에 넣지 않은 것은 실제 데이터베이스를 붙이려면 테스트용 Supabase 프로젝트와 그 비밀이 따라오기 때문이다.
다만 로컬 모드가 그 부담의 절반을 덜어 두었다.
{ch-first-run}처럼 환경 변수 없이 서버를 띄우면 덱 생성부터 통계까지를 로그인 없이 브라우저로 재연할 수 있고, 확인할 흐름은 {ch-app-tests}의 테스트를 대본으로 삼으면 된다.

이 판단이 뒤집히는 조건은 두 번째 사람이 합류해 남의 코드를 리뷰해야 할 때, 그리고 브라우저가 있어야만 재연되는 증상을 같은 곳에서 두 번 겪었을 때다.
그때는 문제를 일으킨 흐름 하나부터 E2E 테스트로 옮긴다.

== 무엇이 잘못됐는지 알기: 로그, 에러, 관측성

Flashcard에는 에러 추적 도구가 없다.
사용자가 다섯 명일 때는 Vercel 대시보드의 함수 로그로 충분하지만, 쉰 명이 되면 누군가 오류를 만나도 아무도 말해 주지 않고 로그 속에서 문제를 찾기도 어려워진다.

이때 필요한 것은 세 가지다.
구조화된 로그(사람이 읽는 문장 대신 `user_id=…`, `status=500`처럼 기계가 거를 수 있는 필드), 에러 집계(같은 예외를 한 줄로 합쳐 발생 횟수와 첫 발생 시각을 보여 주는 것), 요청 추적(느린 요청 하나가 어느 쿼리에서 시간을 썼는지 따라가는 것)이다.
이 셋을 통틀어 관측성(Observability)이라 부른다.

.[용어 풀이] 관측성(Observability)
[NOTE]
====
밖으로 나오는 신호만 보고 시스템 안에서 무슨 일이 벌어지는지 알아낼 수 있는 성질이다.
서버를 뜯어보지 않고도 "왜 저 사용자에게만 오류가 났는가"에 답할 수 있으면 관측성이 있는 것이다.
미리 정해 둔 수치가 정상 범위에 있는지 지켜보는 모니터링과 달리, 관측성은 예상하지 못한 질문에 나중에도 답할 수 있는지를 묻는다.
====

구조화 로그는 Go 표준 라이브러리의 `log/slog`로 의존성 없이 시작할 수 있다.
에러 집계는 Sentry 같은 외부 서비스(무료 Developer 플랜은 월 5,000건의 오류와 30일 조회footnote:[https://sentry.io/pricing/[Sentry Pricing]의 Developer 플랜 기준.])를 붙이는 편이 빠르다.
다만 서비스가 하나 늘면 관리할 대시보드도 하나 늘므로, 관리 최소화라는 이 책의 기준으로 저울질해야 한다.

== 뚫리지 않게 하기: 보안과 비밀 관리

{ch-token-verification}에서 JWKS로 토큰을 검증하고 {ch-supabase-db}에서 RLS로 PostgREST 경로를 막았지만, 비밀 자체를 관리하는 규율은 거의 다루지 않았다.

{ch-env-secrets}의 `.env.dev`는 커밋되지 않지만, 비밀번호가 주기적으로 새 값으로 바뀌지(회전, rotation) 않고 노트북을 잃어버리면 그대로 노출된다.
`.gitignore`의 무시 목록을 강제로 뒤집는 옵션(`git add -f`)을 한 번 쓰면 비밀 값이 저장소 이력에 영원히 남는다.
그때의 대처는 이력 삭제가 아니라 {ch-env-secrets}에서 정리한 즉시 회전, 곧 값의 재발급이다.
`gitleaks` 같은 스캐너(커밋 이력에 비밀 값이 섞였는지 검사하는 도구)를 {ch-quality-gates}의 CI 워크플로에 스텝 하나로 걸어 두는 것이 값싼 보험이고, {ch-free-tier}에서 요금 페이지를 읽기로 한 반년 주기에 맞춰 비밀번호를 바꾸는 습관이 그다음이다.

`go.sum`이 고정한 의존성 버전에도 언젠가 취약점이 발견되므로, Dependabot처럼 업데이트 풀 리퀘스트를 자동으로 열어 주는 장치를 켜 두면 보안 업데이트를 놓치지 않는다.

== 느려지기 전에 알기: 성능

다음 걸음은 {ch-database-basics}에서 배운 인덱스를 실제로 검증하는 일이다.
`explain analyze`로 실행 계획을 읽으면 "이 쿼리가 내가 만든 인덱스를 정말 타는가"를 사실로 확인할 수 있다.
다만 테이블 전체가 PostgreSQL이 디스크를 읽는 단위인 8KB 페이지footnote:[https://www.postgresql.org/docs/current/storage-page-layout.html[PostgreSQL 문서 "Database Page Layout"]은 테이블과 인덱스가 보통 8kB 크기의 페이지 배열로 저장된다고 적는다.] 몇 장에 들어가는 규모일 때는 그 몇 장을 처음부터 끝까지 읽는 편이 빠르므로, 실행 계획은 데이터가 그 규모를 넘어 쌓인 뒤에 읽어야 의미가 있다.

{ch-supabase-db}에서 본 트랜잭션 풀러도 관측 대상이다.
동시 연결 수가 늘 때 풀러가 어디서 대기를 만들기 시작하는지는 대시보드의 연결 수 그래프에 먼저 나타난다.

== 언어와 프레임워크를 더 깊이

2부와 3부의 언어 장들은 이 저장소를 읽는 데 필요한 만큼만 다뤘다.

Go에서는 동시성이 남아 있다.
여러 작업을 동시에 진행하는 고루틴과 채널, 그리고 `context`를 통한 취소 전파는 요청 하나가 쿼리 서너 번으로 끝나는 이 앱에서는 쓸 일이 없었다({ch-supabase-db}에서 홈 화면 한 번을 3~4회로 세었다).
취소 전파는 사용자가 창을 닫는 것처럼 일이 더는 필요 없어졌을 때 그 일이 벌인 모든 갈래를 한 번에 멈추게 하는 것으로({ch-gin}), 외부 API를 여러 개 동시에 부르거나 배치 작업을 돌리면 곧바로 필요해진다.
인터페이스를 이용한 테스트 더블(test double, 진짜 구현 대신 시험용으로 꽂는 대역)도 함께 볼 만하다.
Flashcard의 핸들러는 `Store` 인터페이스에 의존하고 PostgreSQL 구현과 SQLite 구현이 이를 함께 만족하므로({ch-app-assembly}), 같은 자리에 모의 구현을 꽂으면 DB 없이 도는 핸들러 단위 테스트가 된다.
`internal/study/study_test.go`의 `stubStore`가 작은 인터페이스 하나를 이미 그렇게 대신하지만 `model.Store` 전체의 대역은 아직 없으니, 그 대역과 핸들러 테스트를 직접 써 보는 것이 좋은 연습이다.

화면 쪽에서는 {ch-html-css}에서 {ch-htmx}까지 다룬 HTML·CSS·자바스크립트를 더 깊이 파는 길이 있다.
표준 문서(MDN)가 가장 좋은 교과서이고, {n-app-js-lines}줄 남짓한 `static/app.js`를 늘려 가며 브라우저 Web API를 익히는 연습은 이 저장소에서 바로 시작할 수 있다.
한 화면 안에서 여러 상태가 얽히거나, 오프라인 편집이나 실시간 협업처럼 브라우저가 상태를 오래 들고 있어야 할 때는 React 같은 SPA 프레임워크로 가는 길도 있다.
접근성(accessibility, a11y)과 국제화(internationalization, i18n)도 이 책이 건드리지 않은 영역이다.
국제화는 화면의 글과 날짜 표기를 코드에서 떼어 내 언어를 더 얹기 쉽게 만드는 일이고, 접근성은 키보드만으로 카드를 뒤집을 수 있는가처럼 지금 구조에서도 답해 볼 만한 질문이다.

데이터베이스에서는 동시에 들어온 두 작업을 얼마나 떼어 놓고 처리할지 정하는 트랜잭션 격리 수준과 잠금이 다음 단계다.
{ch-domain-model}에서 트랜잭션을 소개했지만, 두 요청이 같은 행을 동시에 고칠 때 무슨 일이 벌어지는지는 사용자가 한 명이라 다루지 않았다.

== AI 에이전트와 더 멀리 가기

하나는 에이전트가 참고할 수 있는 정보를 넓히는 일이다.
데이터베이스 스키마를 에이전트가 직접 조회하게 하거나 이슈 트래커를 읽게 연결해 두면, 매번 내용을 복사해 붙여 넣지 않아도 된다.

다른 하나는 평가(evaluation)다.
"이 지시문을 고쳤더니 정말 나아졌는가"를 감이 아니라 재현 가능한 검사로 답하는 일이다.
같은 요청 여러 개를 옛 지시문과 고친 지시문에 각각 주고, 결과를 같은 기준으로 채점해 견준다.
테스트가 코드의 회귀를 막듯 평가는 지시문의 회귀를 막고, {ch-quality-gates}에서 결정적 검사를 지시가 아니라 장치로 강제한 이유가 여기서도 그대로 통한다.

== 앱이 이 그릇을 넘칠 때

첫째는 상주 서버가 필요해질 때다.
웹소켓으로 실시간 협업을 하거나, {ch-free-tier}에서 본 요청당 300초를 넘기는 배치 작업을 돌려야 한다면 서버리스 함수는 맞지 않는다.
이때 `pkg/app`에 앱 조립 코드를 모아 둔 결정이 제값을 한다.
{ch-app-assembly}에서 본 대로 `cmd/server`와 `api/index.go`가 같은 조립 함수로 같은 Gin 앱을 만들므로, 상주 서버로 옮기는 일은 배포 대상을 바꾸는 문제이지 코드를 다시 쓰는 문제가 아니다.

둘째는 관리형 데이터베이스를 벗어날 때다.
인증은 JWKS 검증이라는 표준 경로만 쓰고 데이터 접근은 Go API 한 곳으로 모았으며({ch-supabase-db}에서 PostgREST 경로를 막은 대가로 얻은 이동성이다), 핸들러 뒤에 PostgreSQL 구현과 로컬 모드의 SQLite 구현(`internal/litestore`)이 나란히 있다.
데이터베이스 교체는 이 저장소가 이미 한 번 해 본 일이다.

기술 선택이 좋았는지는 도입할 때가 아니라 떠날 때 드러난다.

== 마치며

{ch-requirements}의 암기 카드 앱이라는 작은 요구사항에서 출발했다.
AI 에이전트에게 지시해 구조를 계획하고, 세 언어의 최소 문법을 익혀 실제 코드를 해부했으며, Vercel과 Supabase로 앱을 공개한 뒤 사고 없이 운영하는 습관까지 세웠다.

"완전 무료, 관리 최소화"라는 빡빡한 제약 덕에 오히려 설계가 명확해졌다.
서버 렌더링, 서버리스 함수, 무상태 인증, 트랜잭션 풀러 같은 굵직한 결정은 전부 그 제약에서 따라 나왔다.
이 장에서 센 "없는 것들"도 제약이 아직 요구하지 않았을 뿐이다.

기술 선택이란 유행을 좇는 일이 아니라 자신의 제약을 정직하게 적고 트레이드오프를 따져 보는 일이다.
이제 이 저장소를 출발점 삼아, 여러분 자신의 제약과 요구사항으로 다음 앱을 만들어 보자.
