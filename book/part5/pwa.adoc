= PWA: 설치되는 앱으로 만들기

이제 주소만 있으면 누구나 브라우저로 Flashcard를 쓸 수 있다.
그런데 암기 앱은 하루에 몇 번씩 짧게 여는 앱이라, 그때마다 브라우저를 켜고 주소를 입력해야 한다면 잘 열리지 않는다.
{ch-requirements}에서 "설치해 쓰는 앱의 경험을 웹 하나로 낸다"는 요구사항을 세운 이유다.

이 장은 이미 쓰는 사람이 있는 앱에 기능 하나를 더하는 연습이기도 하다.
브라우저가 무엇을 보고 설치 자격을 판정하는지, `manifest.webmanifest`의 각 필드가 무엇을 정하는지, 설치를 어떻게 확인하는지, 이 앱이 PWA의 무엇을 쓰지 않기로 했는지를 차례로 본다.
서비스 워커와 캐시는 서버가 통제하지 못하는 저장소에 사용자의 개인 화면이 들어가는 문제라 {ch-caching}에서 따로 다룬다.

== 설치되는 앱의 조건

브라우저가 "이 사이트를 앱으로 설치하시겠습니까"라고 물어보게 하려면 흔히 세 가지가 필요하다고 말한다.

첫째, HTTPS로 서빙되어야 한다.
서빙(serving)은 서버가 요청을 받아 화면이나 파일을 내주는 일이고, HTTPS는 그 내용을 암호로 감싸 주고받는 통신 방식이다({ch-vercel}).
브라우저는 서비스 워커처럼 요청을 가로챌 수 있는 기능을 암호화되지 않은 연결에는 내주지 않는다.
Vercel이 인증서를 자동으로 발급하고 갱신하므로 이 조건은 저절로 충족된다.

둘째, 앱의 이름, 아이콘, 실행 방식을 브라우저에 알려 주는 웹 앱 매니페스트가 있어야 한다.

.[용어 풀이] 웹 앱 매니페스트(Web App Manifest)
[NOTE]
====
웹사이트가 "나를 앱으로 설치하면 이런 모습이 된다"고 브라우저에 알려 주는 JSON 문서다.
앱 이름, 아이콘, 시작 주소, 주소창을 숨길지 같은 설치 정보가 들어 있고, HTML의 `<link rel="manifest">`로 페이지에 연결한다.
가게 입구에 붙여 둔 간판과 영업 안내문에 해당한다.
====

셋째, 서비스 워커가 등록되어 있어야 한다.
이 조건은 브라우저마다 다르다.
Chrome은 오랫동안 `fetch` 핸들러가 있는 서비스 워커를 설치 조건으로 요구했지만, 모바일 108, 데스크톱 112 버전부터 그 요구를 없앴다footnote:[Chrome for Developers 블로그 "Revisiting Chrome's installability criteria". https://developer.chrome.com/blog/update-install-criteria[Revisiting Chrome's installability criteria]].
iOS의 Safari는 서비스 워커를 요구하지 않고, 매니페스트를 읽어 공유 메뉴의 "홈 화면에 추가"로 설치한다footnote:[MDN "Making PWAs installable"의 브라우저별 설치 지원 설명. https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable[Making PWAs installable]].
그러니 2026년 기준으로 서비스 워커는 설치의 필수 조건이라기보다 오프라인 안내와 캐시를 위한 장치다.
등록하는 한 줄은 {ch-caching}에서 읽는다.

.[용어 풀이] 서비스 워커(Service Worker)
[NOTE]
====
웹 페이지와 별개로 브라우저 뒤편에서 도는 작은 스크립트다.
페이지가 보내는 네트워크 요청 사이에 끼어, 캐시에 있는 응답을 대신 내주거나 네트워크로 흘려보낸다.
주문을 받아 창고에 있으면 바로 꺼내 주고 없으면 본사에 주문을 넣는 가게 안내원에 가깝다.
페이지를 닫아도 살아 있을 수 있어서 오프라인 동작과 푸시 알림의 토대가 된다.
====

Flashcard는 둘째 조건을 `manifest.webmanifest`로 채우고, 셋째 조건을 위해 `sw.js`를 둔다.
두 파일 모두 `internal/web/static/`에 있는 평범한 정적 파일이고, {ch-html-template}에서 본 embed로 Go 바이너리에 담겨 다른 정적 자산과 같은 경로로 서빙된다.

== manifest.webmanifest: 설치 화면을 결정하는 파일

`internal/web/static/manifest.webmanifest`의 전문이다.
앱 이름, 시작 주소, 표시 방식, 두 가지 색, 아이콘 목록을 JSON으로 적었다.

[source,json]
----
{
  "name": "Flashcard — 암기 카드",
  "short_name": "Flashcard",
  "description": "단어·문장·숙어·개념을 카드로 뒤집으며 외우는 학습 앱",
  "lang": "ko",
  "start_url": "/",
  "display": "standalone",
  "background_color": "#fafafa",
  "theme_color": "#2563eb",
  "icons": [
    { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png" },
    {
      "src": "/icons/icon-512-maskable.png",
      "sizes": "512x512",
      "type": "image/png",
      "purpose": "maskable"
    }
  ]
}
----

만들어 내는 코드도 빌드 단계도 없이, 손으로 쓴 JSON 파일 하나가 그대로 서빙된다.
브라우저가 이 파일을 찾을 수 있도록 모든 페이지의 공통 레이아웃(`internal/web/templates/layout.html`)이 `<head>`에서 연결한다.

[source,html]
----
<link rel="manifest" href="/manifest.webmanifest">
----

필드를 하나씩 보자.

`name`과 `short_name`은 쓰이는 자리가 다르다.
설치 대화상자에는 `name`이, 홈 화면 아이콘 아래의 좁은 자리에는 `short_name`이 나타난다.
아이콘 아래에서 잘리지 않게 `short_name`은 한 줄에 들어갈 만큼 짧게 두어야 하고, 이 앱의 `Flashcard`는 9자다.

`display: "standalone"`이 설치의 체감을 가장 크게 바꾼다.
앱을 열었을 때 주소창과 브라우저 탭이 사라져 네이티브 앱처럼 보인다.
`browser`로 두면 설치해 봐야 브라우저 창이 하나 더 열릴 뿐이다.

`start_url: "/"`는 아이콘을 눌렀을 때 열리는 주소라, 언제나 홈 화면의 "오늘 복습" 큐에서 시작한다.

`background_color`는 앱이 뜨는 동안 잠깐 보이는 시작 화면의 바탕색이고, `theme_color`는 상태 표시줄처럼 브라우저가 앱 주변을 칠할 때 쓰는 색이다.
`background_color`를 실제 앱 배경과 맞춰 두면 시작 화면에서 본 화면으로 넘어갈 때 깜빡임이 줄어든다.

=== 아이콘 세 개와 maskable

192px는 홈 화면의 아이콘 자리에, 512px는 시작 화면의 큰 아이콘 자리에 쓰이고, Chrome은 이 두 크기를 설치 조건으로 요구한다.
세 번째 아이콘만 `purpose: "maskable"`을 달고 있다.

Android는 제조사와 런처(launcher, 홈 화면의 모양과 아이콘 배치를 정하는 프로그램)에 따라 아이콘을 원형, 둥근 사각형, 물방울 모양 등으로 잘라 내고, 일반 아이콘은 가장자리의 글자나 그림이 함께 잘린다.
maskable 아이콘은 그 잘림을 예상해 가운데 80% 안에만 중요한 내용을 그린 그림이라, 어떤 모양으로 잘려도 살아남는다.
일반 아이콘과 maskable 아이콘을 둘 다 제공해 브라우저가 고르게 하는 것이 안전하므로, `internal/web/static/icons/` 아래에 `icon-192.png`, `icon-512.png`, `icon-512-maskable.png` 세 파일이 함께 있다.

== 설치를 확인하는 법

확인은 {ch-css-hello}에서 열어 본 개발자 도구(Chrome에서는 F12)의 Application 탭에서 한다.
Manifest 항목에서는 브라우저가 해석한 매니페스트가 필드별로 보이고, 아이콘을 실제로 불러오는지도 확인할 수 있다.
Service Workers 항목에서는 등록 상태와 활성화 여부를 보고, Offline 체크박스로 네트워크를 끊어 볼 수 있다.
Cache Storage 항목을 펼치면 {ch-caching}에서 다룰 두 캐시 상자(`flashcard-static-v3`, `flashcard-pages-v3`)가 보인다.

Android의 Chrome에서는 조건을 만족하면 주소창에 설치 아이콘이나 설치 안내가 뜨고, iOS의 Safari에서는 사용자가 공유 메뉴의 "홈 화면에 추가"를 직접 눌러야 한다.
`display: "standalone"`은 양쪽 모두에 적용되므로 설치 경로만 다르고 결과는 비슷하다.

== 이 PWA가 포기한 것

Flashcard는 PWA의 일부만 쓴다.

*오프라인 학습을 지원하지 않는다.*
지하철에서 앱을 열면 마지막으로 본 화면의 사본이나 오프라인 안내 페이지가 뜰 뿐, 카드를 뒤집으며 채점할 수는 없다.
지원하려면 카드 데이터를 브라우저 안의 데이터 저장소(IndexedDB)에 내려 두고, 오프라인에서 매긴 결과를 나중에 서버와 동기화해야 한다.
그러면 같은 카드를 두 기기에서 다르게 채점했을 때 `card_srs`의 난이도·간격·반복 횟수·다음 복습일을 하나로 합치는 충돌 해결이 따라오고, 경우의 수가 이 앱의 어느 코드보다 많아진다.
매일 쓰는 기기가 하나뿐인 개인 앱에서는 그 복잡도를 떠안을 이유가 없었다.

*푸시 알림이 없다.*
"오늘 복습할 카드 12장이 있습니다" 같은 알림은 암기 앱에 잘 어울리지만, 웹 푸시를 보내려면 사용자의 복습 시각에 맞춰 주기적으로 깨어나는 발송 서버가 필요하다.
{ch-free-tier}에서 볼 스케줄 워크플로로 흉내 낼 수는 있어도, 사용자별 시간대와 알림 시각을 관리하는 순간 이 앱은 다른 앱이 된다.

*백그라운드 동기화도 없다.*
오프라인 학습이 없으므로 나중에 보낼 것도 없다.

오프라인 학습에는 동기화가, 알림에는 상주하는 무언가가 필요하고, 어느 쪽도 "무료 인프라, 서버리스, 1인 운영"이라는 제약과 어울리지 않는다.
PWA를 고른 이유는 네이티브 앱의 배포 부담을 피하려는 것이었지, 그 모든 기능을 웹으로 재현하려는 것이 아니었다.

== 에이전트 활용 아이디어

설치 관련 파일은 값 하나가 틀려도 빌드가 깨지지 않고, 증상은 설치 화면에서야 드러난다.

* manifest 수정은 에이전트에게 맡기되, "`manifest.webmanifest`에 마스크 가능 아이콘을 추가해 달라"고 지시한 뒤 개발자 도구의 Application 탭에서 실제로 인식되는지 눈으로 확인하는 왕복이 가장 빠르다.
* `AGENTS.md`에는 "새 자산 파일을 추가하면 해시 대상 목록에도 넣는다"를 적어 둔다. 그 목록은 `internal/web/routes.go`의 `assetVersion`이 해시하는 `app.css`·`app.js`·`htmx.min.js` 세 파일이고, 잊으면 캐시가 이전 버전 파일을 붙잡는다({ch-caching}).

== 정리

설치 자격은 HTTPS와 manifest에서 생기고, HTTPS는 Vercel이 준다.
서비스 워커는 Chrome 108(모바일)·112(데스크톱) 이후 필수 조건에서 빠졌지만 오프라인 안내와 캐시를 위해 둔다.

`manifest.webmanifest`는 설치된 앱의 이름과 아이콘, 시작 주소, 표시 모드를 정하므로, 값을 채운 뒤에는 실제 기기에서 설치해 확인한다.

오프라인 학습, 푸시 알림, 백그라운드 동기화는 상주하는 무언가나 동기화 충돌 해결을 요구해서 쓰지 않기로 했다.

다음 {ch-caching}에서는 서비스 워커를 읽으며 무엇을 캐시하고, 캐시한 것을 언제 어떻게 버릴지를 다룬다.
