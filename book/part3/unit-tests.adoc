= 함수 하나씩 검증하기: 단위 테스트와 품질 검사 도구

{ch-core-logic}에서 읽은 SRS 알고리즘이나 스마트 덱 규칙이 설계대로 동작하는지 확인하는 일을 검사 코드로 적어 두고 기계가 반복 실행하게 하는 것이 테스트다.
이 장에서는 Go의 테스트 규칙과 명령을 익히고, 실제 테스트를 읽으며 테이블 주도 테스트(Table-driven Test), 전수 검사, 경계값 검사, 픽스처, 커버리지를 확인한 뒤 gofmt·go vet 같은 품질 검사 도구를 살펴본다.
이 테스트와 도구들은 AI 에이전트가 자기 작업을 스스로 검증하는 신호이기도 하다.

== go test의 세 가지 규칙

테스트를 찾아 실행하고 결과를 알려 주는 프로그램(테스트 러너)을 Go는 언어 도구에 내장해 두고, 무엇이 테스트인지를 세 가지 규칙으로 정한다.

첫째, 테스트 코드는 이름이 `_test.go`로 끝나는 파일에 담는다(`internal/srs/srs.go`의 테스트는 같은 디렉터리의 `srs_test.go`에 있다).
둘째, 테스트 함수의 이름은 `Test`로 시작한다.
셋째, 테스트 함수는 `*testing.T` 타입의 매개변수 하나를 받고, 실패 보고는 모두 이 `t`로 한다.

`go test` 명령이 이 규칙에 맞는 함수를 찾아 실행한다.
`_test.go` 파일은 `go build`가 만드는 실행 파일에서 빠지므로, 테스트가 많아도 배포되는 서버의 크기는 그대로다.

테스트 파일을 검증 대상과 같은 패키지로 선언하면 소문자로 시작하는 비공개 식별자까지 직접 부를 수 있다.
덱 번호를 슬러그로 바꾸는 계산을 검사하는 `internal/model/deckslug_test.go`의 앞부분에서 패키지 선언과 비공개 상수를 꺼내 쓰는 대목을 보자.

[source,go]
----
include::../../flashcard-advanced/internal/model/deckslug_test.go[tag=same-package]
		// ...
	}
}
----

첫 줄이 `package model`이므로 이 테스트 파일은 model 패키지의 일원이고, 패키지 밖에 공개되지 않은 `slugLen` 같은 상수를 그대로 읽는다.
첫 줄을 `package model_test`로 적으면 테스트가 별도 패키지가 되어 공개된 식별자만 쓸 수 있는 대신, 공개 API가 그대로면 내부 구현을 바꿔도 테스트가 깨지지 않는다.
이 저장소는 검증할 대상이 비공개인 경우가 많아 같은 패키지 방식을 골랐고, 라이브러리를 만들어 공개한다면 `_test` 패키지가 낫다.

`go test`는 속도를 반복 측정하는 `Benchmark` 함수와, 입력을 무작위로 바꿔 가며 프로그램을 깨뜨리는 값을 찾는 `Fuzz` 함수도 알아본다.
Flashcard는 둘 다 쓰지 않았지만, 뒤에 나올 슬러그 디코딩처럼 아무 문자열이나 들어오는 입구는 퍼징(fuzzing)이 잘 맞는 대상이다.

== 테스트 실행 명령

테스트 실행은 `go test` 명령 하나로 끝나고, 명령 뒤에 플래그(flag)를 덧붙여 동작을 바꾼다.

.[용어 풀이] 플래그(Flag, 명령행 옵션)
[NOTE]
====
명령의 동작을 바꾸려고 명령 이름 뒤에 덧붙이는 짧은 옵션이다.
`-`나 `--`로 시작하고(`go test -v`, `gofmt -w`), 값이 필요한 플래그는 뒤에 값을 함께 적는다(`go test -run TestEaseFloor`).
====

자주 쓰는 변형은 다음과 같다.

[source,bash]
----
go test ./...                              # 모듈 전체 테스트
go test ./internal/srs                     # 특정 패키지만
go test -run TestEaseFloor ./internal/srs  # 이름이 매칭되는 테스트만
go test -v ./internal/srs                  # 개별 테스트의 이름과 결과까지 상세 출력
go test -count=1 ./...                     # 캐시된 지난 결과를 무시하고 다시 실행
go test -race ./...                        # 동시 실행 오류까지 검사
----

`./...`은 현재 디렉터리 아래의 모든 패키지를 뜻하고, `-run`은 이름이 맞는 테스트만 골라 돌리며, `-v`(verbose)는 통과한 테스트의 이름까지 보여 준다.
나머지 두 플래그는 아래에서 따로 다룬다.

=== 성공과 실패의 출력

`flashcard-advanced/` 디렉터리에서 `go test ./...`를 실행하면 이런 출력이 나온다(일부만 옮겼다).

----
?   	github.com/benelog/flashcard/api	[no test files]
?   	github.com/benelog/flashcard/cmd/server	[no test files]
ok  	github.com/benelog/flashcard/internal/auth	0.007s
ok  	github.com/benelog/flashcard/internal/litestore	0.294s
ok  	github.com/benelog/flashcard/internal/srs	0.002s
ok  	github.com/benelog/flashcard/pkg/app	1.084s
----

패키지마다 한 줄이다.
`ok`는 그 패키지의 테스트가 모두 통과했다는 뜻이고 뒤의 숫자는 걸린 시간이며, `[no test files]`는 `_test.go` 파일이 없는 패키지라는 표시다.

다음은 `srs_test.go`의 기댓값을 일부러 틀리게 고치고 돌린 결과다.

----
--- FAIL: TestCorrectProgression (0.00s)
    srs_test.go:18: rep 3: interval = 16, want 15
FAIL
FAIL	github.com/benelog/flashcard/internal/srs	0.004s
FAIL
----

실패한 테스트 함수의 이름, 파일과 줄 번호, 코드에 적어 둔 메시지(뒤에서 볼 `t.Fatalf`의 서식 문자열이 실제 값으로 채워진 것)가 차례로 찍힌다.
어디서 무엇이 달랐는지가 한 화면에 담기므로 사람도 에이전트도 이 출력만 보고 고칠 곳을 찾아간다.
그래서 실패 메시지에는 기댓값과 실제값을 함께 넣는다.

=== 테스트 결과는 캐시된다

같은 명령을 한 번 더 돌리면 출력이 이렇게 바뀐다.

----
ok  	github.com/benelog/flashcard/internal/config	0.004s
ok  	github.com/benelog/flashcard/internal/litestore	(cached)
ok  	github.com/benelog/flashcard/internal/smartrules	(cached)
ok  	github.com/benelog/flashcard/internal/srs	(cached)
----

`(cached)`는 그 패키지의 코드도 테스트도 지난번과 같아서 저장해 둔 결과를 보여 줬다는 뜻이며, 정상 동작이다.
정말 다시 돌리려면 `-count=1`을 붙인다.
`-count`는 원래 반복 횟수를 정하는 플래그인데, 캐시가 횟수 1일 때만 쓰여서 캐시를 무시하는 관례적인 표기가 됐다.
{ch-local-dev}에서 에디터의 테스트 실행 설정에 이 플래그를 넣는 것도 그래서다.

=== -race: 동시 실행 오류 검사

`-race`는 여러 작업이 같은 데이터를 동시에 건드려 생기는 오류를 잡아내는 플래그다.

.[용어 풀이] 경쟁 상태(Race Condition)
[NOTE]
====
두 가지 일이 동시에 같은 데이터를 건드릴 때, 누가 먼저 닿느냐에 따라 결과가 달라지는 상태다.
같은 장부에 두 사람이 동시에 숫자를 고쳐 적으면 한쪽의 기록이 소리 없이 사라지는 것과 같다.
어쩌다 한 번씩만 재현되어 눈으로 찾아내기가 가장 어려운 종류의 버그다.
====

Go 서버는 요청 여러 개를 동시에 처리한다.
`-race`를 붙이면 테스트가 도는 동안 메모리 접근을 감시해 두 작업이 같은 값을 동시에 건드리는 대목을 알려 준다.
대신 Go 문서에 따르면 실행 시간이 2~20배, 메모리 사용량이 5~10배 늘어나므로 평소에 붙이는 플래그는 아니다.footnote:[Go 공식 문서의 경쟁 상태 검출기 소개 가운데 "Runtime Overhead" 절 https://go.dev/doc/articles/race_detector[Data Race Detector]]
Flashcard의 코드가 요청 사이에 공유하는 값은 다섯 곳뿐이고, 모두 `sync.Once`·`sync.Mutex`·`sync.Map` 같은 표준 라이브러리의 동기화 타입으로 감싸 두어 상시 검사 목록에는 넣지 않았다.
요청들이 함께 고치는 값을 보호 없이 들이게 되면 그때는 {ch-quality-gates}에서 볼 로컬 검사와 CI 양쪽에 `-race`를 함께 붙인다.

== SRS 알고리즘 테스트 읽기

`internal/srs/srs_test.go`에서 정답이 이어질 때의 간격 진행을 검증하는 테스트부터 읽어 보자.

[source,go]
----
include::../../flashcard-advanced/internal/srs/srs_test.go[tag=correct-progression]
	// ...
}
----

테이블 주도 테스트의 가장 단순한 형태다.
기댓값 목록 `wantIntervals`를 테이블로 놓고, `for ... range` 루프가 각 행에 같은 검증을 적용한다.

.[용어 풀이] 테이블 주도 테스트(단위 테스트 포함)
[NOTE]
====
단위 테스트는 함수 하나가 기대대로 동작하는지 자동으로 확인하는 작은 검사 코드다.
테이블 주도 테스트는 그 검사를 "입력과 기댓값의 목록(표)"으로 만들어, 한 번의 반복문으로 표의 모든 줄을 검사하는 방식이다.
검사할 경우를 늘리려면 표에 한 줄만 더하면 되므로, 비슷한 테스트 함수를 복사해 늘리는 것보다 관리가 쉽다.
====

파일 상단의 `var now = time.Date(...)`도 중요한 장치다.
{ch-core-logic}에서 `Grade`를 현재 시각을 인자로 받는 순수 함수로 설계한 덕분에, 테스트는 고정 시각을 넣어 언제 실행해도 같은 결과를 얻는다.

실패를 보고하는 방법은 두 가지다.

|===
| 메서드 | 하는 일 | 쓰는 상황

| `t.Fatalf` | 실패를 보고하고 그 테스트 함수를 즉시 중단 | 뒤 검증이 앞 결과에 의존할 때
| `t.Errorf` | 실패를 기록하고 다음 검증을 계속 진행 | 독립적인 검증의 실패를 한 번에 모두 보고할 때
|===

`TestCorrectProgression`은 두 번째 복습의 검증이 첫 번째 복습의 결과 위에서 이어지므로, 앞 단계가 틀리면 즉시 멈추는 `t.Fatalf`가 맞다.

오답이 거듭될 때 용이도가 어디까지 내려가는지 확인하는 테스트도 보자.

열 번 연속 틀려도 용이도가 하한 1.3 아래로 내려가지 않는지 확인한다.
`for range 10`은 Go 1.22부터 쓸 수 있는 정수 순회 문법이고, 필요 없는 반환값은 빈 식별자 `_`로 버린다.

== 규칙 파싱 테스트와 테이블 패턴

스마트 덱 규칙의 JSON을 읽어 빠진 값을 채우는 일은 `internal/smartrules`가, 그 규칙을 SQL 조회문으로 옮기는 일은 저장소가 맡는다.
DB마다 문법이 달라서 PostgreSQL은 `internal/pgstore/rules.go`가, SQLite는 `internal/litestore/rules.go`가 각자 옮긴다.

옮기는 쪽 테스트는 입력 자체를 테이블로 놓는다.
스마트 덱 규칙 네 종류가 모두 SQL 조회문으로 바뀌는지 확인하는 테스트다.

[source,go]
----
include::../../flashcard-advanced/internal/pgstore/rules_test.go[tag=queries-build]
		// ...
	}
}
----

네 규칙 타입의 JSON을 슬라이스 리터럴(literal, 값을 코드에 그대로 적어 넣는 표기)로 나열하고, 어느 타입도 빈 SQL을 만들지 않는지 한 루프로 검증한다.

`ruleQuery`는 문자열을 만들 뿐 DB에 접속하지 않으므로, 이 테스트는 PostgreSQL 전용 코드인데도 PostgreSQL 없이 돈다.
같은 파일은 이 점을 살려, 규칙의 값이 SQL 문자열에 이어 붙지 않고 자리표시자(`$1` 같은 빈칸)로 따로 넘어가는지(`TestRuleValuesAreBoundNotInterpolated`), 모든 규칙이 사용자 범위로 좁혀지는지(`TestEveryRuleScopesToTheUser`)도 검사한다.
{ch-database-basics}에서 본 SQL 인젝션 방지와 남의 데이터를 읽지 않는다는 약속을 규칙이 늘어나도 매번 자동으로 확인한다.
규칙을 해석하는 쪽(`internal/smartrules/rules_test.go`)에도 기본값 채움, 모르는 타입 거부, 상한 초과 시 되돌림처럼 `Validate`의 분기마다 테스트가 있다.

== DB를 붙인 테스트: 픽스처 헬퍼와 서브테스트

이 저장소에서 가장 큰 테스트 파일인 `internal/litestore/litestore_test.go`는 500줄이 넘고, 진짜 SQLite 파일을 열어 덱과 카드를 만들고 복습을 기록하고 통계를 읽는다.
PostgreSQL이었다면 테스트마다 DB 서버를 띄워 두어야 했겠지만, SQLite는 임시 파일 하나면 된다.

DB를 붙이면 테스트마다 깨끗한 DB가 필요하고, 끝나면 치워야 하고, 덱과 카드를 만드는 준비가 반복된다.
Go의 `testing` 패키지에 이 셋을 각각 맡는 도구가 있고, 파일 첫머리의 헬퍼 함수가 셋을 모두 쓴다.
테스트마다 새 임시 폴더에 SQLite DB를 열고, 끝나면 닫히도록 예약하고, 시험용 사용자까지 만들어 돌려주는 준비 코드다.

[source,go]
----
include::../../flashcard-advanced/internal/litestore/litestore_test.go[tag=fixture]
----

`t.TempDir()`은 이 테스트만 쓰는 임시 디렉터리를 만들고, 테스트가 끝나면 도중에 실패했더라도 내용까지 통째로 지운다.
테스트마다 새 디렉터리라 앞 테스트가 남긴 데이터가 뒤 테스트의 결과를 바꾸지 않는다.

`t.Cleanup()`은 테스트가 끝날 때 실행할 코드(여기서는 DB 연결 닫기)를 등록한다.
`defer`와 비슷하지만 등록한 함수가 반환될 때가 아니라 *테스트가* 끝날 때 실행되므로, 헬퍼 안에서 등록해도 정리는 헬퍼를 부른 테스트가 끝날 때 일어난다.

`t.Helper()`는 이 함수가 헬퍼임을 알린다.
이 한 줄이 있으면 헬퍼 안에서 실패했을 때 헬퍼 내부가 아니라 *헬퍼를 호출한 테스트의 줄 번호*가 보고되어, `testStore`를 부르는 여러 테스트 가운데 어느 것이 깨졌는지 알 수 있다.

이 헬퍼 덕분에 각 테스트의 첫 줄은 `s, userID := testStore(t)` 하나로 끝나고, 같은 파일의 `mustDeck`과 `mustCard`도 같은 구조로 덱과 카드를 만든다.
이렇게 테스트의 밑준비를 맡는 코드를 픽스처라고 부른다.

.[용어 풀이] 픽스처(Fixture)
[NOTE]
====
테스트를 돌리기 전에 갖춰 두는 고정된 환경과 데이터다.
빈 DB, 미리 만들어 둔 사용자와 덱처럼 "이 상태에서 시작한다"고 정해 두는 밑준비를 가리킨다.
모든 테스트가 같은 밑준비에서 출발해야 결과가 재현되므로, 준비하는 코드와 치우는 코드를 헬퍼 함수로 빼 두는 것이 관례다.
====

=== t.Run: 이름이 붙은 서브테스트

테이블의 케이스마다 조건이 달라지면 각 행에 이름을 붙이고 싶어지는데, `t.Run`이 그 일을 한다.
스마트 덱 규칙 네 가지가 각각 어떤 카드를 어떤 순서로 골라내는지 검증하는 `litestore_test.go`의 테스트다.

[source,go]
----
include::../../flashcard-advanced/internal/litestore/litestore_test.go[tag=subtest-table,indent=0]
	// ...
}
include::../../flashcard-advanced/internal/litestore/litestore_test.go[tag=subtest-run,indent=0]
		// ...
	})
}
----

테이블의 각 행은 이름(`name`), 입력(`rule`), 기댓값(`want`)을 담은 구조체이고, 루프 본문은 `t.Run(tt.name, func(t *testing.T) { ... })`으로 감쌌다.
`-v`를 붙인 출력을 보면 무엇이 좋아지는지 드러난다.

----
=== RUN   TestSmartRules
=== RUN   TestSmartRules/high_error
=== RUN   TestSmartRules/stale_nulls_first
=== RUN   TestSmartRules/tag_overlap
=== RUN   TestSmartRules/recent_newest_first
--- PASS: TestSmartRules (0.04s)
    --- PASS: TestSmartRules/high_error (0.00s)
    --- PASS: TestSmartRules/stale_nulls_first (0.00s)
    --- PASS: TestSmartRules/tag_overlap (0.00s)
    --- PASS: TestSmartRules/recent_newest_first (0.00s)
PASS
ok  	github.com/benelog/flashcard/internal/litestore	0.044s
----

각 케이스에 `부모테스트/케이스이름`이라는 이름이 붙는다(빈칸은 밑줄로 바뀐다).
실패하면 몇 번째 행인지가 아니라 어느 케이스인지가 나오고, 그 이름을 `-run`에 넘겨 한 케이스만 돌릴 수 있다.

[source,bash]
----
go test -run 'TestSmartRules/tag_overlap' ./internal/litestore
----

한 케이스에서 `t.Fatalf`로 멈춰도 멈추는 것은 그 서브테스트뿐이다.
`wantIntervals` 같은 단순한 기댓값 목록은 루프로 충분하고, 케이스마다 조건과 기대 결과가 다른 이 규칙 테스트에는 이름을 지어 주는 `t.Run`이 맞다.

== 커버리지: 숫자가 말하는 것과 말하지 않는 것

`-cover` 플래그는 테스트가 한 번이라도 실행한 코드가 전체의 몇 퍼센트인지 알려 준다.

[source,bash]
----
go test -cover ./internal/...
----

이 글을 쓸 때(2026년 9월)의 출력을 커버리지가 높은 순으로 늘어놓았다.

----
ok  	github.com/benelog/flashcard/internal/srs	0.005s	coverage: 100.0% of statements
ok  	github.com/benelog/flashcard/internal/study	0.004s	coverage: 100.0% of statements
ok  	github.com/benelog/flashcard/internal/model	0.014s	coverage: 97.4% of statements
ok  	github.com/benelog/flashcard/internal/smartrules	0.006s	coverage: 85.0% of statements
ok  	github.com/benelog/flashcard/internal/litestore	0.243s	coverage: 78.4% of statements
ok  	github.com/benelog/flashcard/internal/auth	0.012s	coverage: 73.6% of statements
ok  	github.com/benelog/flashcard/internal/cardcsv	0.006s	coverage: 69.6% of statements
ok  	github.com/benelog/flashcard/internal/config	0.005s	coverage: 55.0% of statements
ok  	github.com/benelog/flashcard/internal/web	0.008s	coverage: 19.8% of statements
ok  	github.com/benelog/flashcard/internal/handlers	0.005s	coverage: 3.2% of statements
ok  	github.com/benelog/flashcard/internal/pgstore	0.005s	coverage: 2.3% of statements
	github.com/benelog/flashcard/internal/db		coverage: 0.0% of statements
----

계산 규칙이 전부인 srs와 학습할 카드를 고르는 study가 100%이고, 도메인 타입(model), 규칙 파싱(smartrules), CSV 변환(cardcsv)이 뒤를 잇는다.
DB도 HTTP도 모르는 코드일수록 숫자가 높은데, 검증하기 쉬운 코드를 그런 자리에 모아 두었기 때문이다.

낮은 숫자는 조심해 읽어야 한다.
첫째, `internal/pgstore`의 2.3%는 대부분이 PostgreSQL에 SQL을 보내는 코드라 진짜 PostgreSQL 서버 없이는 검사할 수 없어서다.
그 비용을 치르는 대신 같은 동작을 SQLite 구현으로 검증했고(litestore 78.4%), 두 구현이 같은 인터페이스를 만족한다는 점({ch-app-assembly})이 그 근거다.
대가는 PostgreSQL 전용 SQL의 오류가 이 방식으로 잡히지 않는다는 것이다.

둘째, handlers의 3.2%와 web의 19.8%는 거의 검사되지 않는다는 뜻이 아니다.
이 앱의 화면과 API는 `pkg/app`에서 앱을 통째로 띄워 진짜 HTTP 요청을 보내는 테스트 {n-app-test-count-ko-attr} 개가 검사한다({ch-app-tests}에서 읽는다).
그런데 `go test -cover`는 각 패키지가 자기 테스트로 실행한 줄만 세므로, 다른 패키지의 테스트가 지나간 코드는 숫자에 잡히지 않는다(`-coverpkg` 옵션으로 범위를 넓히면 달라진다).

그래서 커버리지는 목표로 삼기에 나쁜 숫자다.
"90%를 채운다"는 규칙을 세우면 검증할 가치가 낮은 코드에도 형식적인 테스트가 붙어, 숫자는 올라가는데 잡히는 버그는 늘지 않는다.
커버리지는 *테스트가 없는 곳을 확인하는 지도*로 읽을 때 쓸모가 있다.
핸들러의 3%대도 핸들러를 얇게 유지한다는 {ch-app-assembly}의 설계와 함께 읽어야 하고, 그 계층에 로직이 쌓이기 시작하면 가장 먼저 테스트를 붙일 곳이라는 신호다.

== 품질 검사 도구

테스트가 동작이 맞는지 확인한다면, 코드가 형식과 상식에 맞는지는 Go 툴체인에 든 도구가 기계적으로 검사한다.

.[용어 풀이] 포매터와 정적 분석(gofmt·go vet)
[NOTE]
====
포매터는 줄 간격·들여쓰기 같은 코드의 겉모양을 정해진 하나의 형태로 자동 정리해 주는 도구다(gofmt).
정적 분석은 코드를 실행하지 않고 읽기만 해서 버그가 될 만한 대목을 찾아 주는 도구다(go vet).
사람의 판단 없이 늘 같은 결과를 내므로, 사람이든 AI든 코드를 고칠 때마다 자동으로 돌리기에 알맞다.
====

*gofmt*는 표준 포매터다.

[source,bash]
----
gofmt -l .   # 포맷이 어긋난 파일 나열
gofmt -w .   # 제자리 수정
----

들여쓰기, 정렬, 괄호 위치를 하나의 표준형으로 고정하며 설정 옵션이 아예 없다.
그래서 "탭이냐 스페이스냐" 같은 논쟁이 Go 커뮤니티에는 없고, 처음 보는 코드를 읽는 비용이 줄어든다.

*go vet*은 정적 분석기다.

[source,bash]
----
go vet ./...
----

컴파일은 통과하지만 십중팔구 버그인 코드(`Printf` 형식 문자열과 인자의 불일치, 도달 불가능한 코드, 잘못된 구조체 태그)를 잡아낸다.

*go build*도 가장 기본적인 검사다.
Go는 쓰지 않는 임포트와 지역 변수를 컴파일 에러로 처리하므로, `go build ./...` 통과는 타입이 어긋난 코드와 쓰지 않는 코드가 없다는 확인을 겸한다.

*staticcheck*은 Go 팀 바깥에서 만든 정적 분석기로, `go vet`보다 넓은 150여 가지 검사를 한다(`staticcheck ./...`).
`go install`로 따로 설치해야 하지만 Go 커뮤니티에서 사실상의 표준으로 통한다.

이 도구들은 빠르고(gofmt는 이 저장소 전체를 0.1초 안에 읽고, go vet도 빌드 캐시가 있으면 1초가 안 걸린다) 결정적이라 자동화의 재료로 알맞다.
이 프로젝트는 Go 파일을 고칠 때마다 gofmt와 go vet이 자동으로 돌게 해 두었고, 그 구성은 {ch-quality-gates}에서 다룬다.

== 세로 정렬은 취향이 아니라 규칙이다

gofmt가 고정하는 항목 중 처음 보면 낯선 것이 세로 정렬(vertical alignment)이다.
구조체 필드를 한 칸씩만 띄워 써도 gofmt가 칼럼을 맞춰 준다.

[source,go]
----
// 입력: 한 칸씩만 띄웠다
type User struct {
	ID int64 `json:"id"`
	Name string `json:"name"`
	EmailAddress string `json:"email"`
	OK bool // 활성 여부
}

// gofmt 출력: 칼럼이 맞춰졌다
type User struct {
	ID           int64  `json:"id"`
	Name         string `json:"name"`
	EmailAddress string `json:"email"`
	OK           bool   // 활성 여부
}
----

구조체의 필드명·타입·태그·줄 끝 주석, `const`·`var` 블록과 맵 리터럴의 값이 이렇게 정렬되고, 반대로 함수 본문의 문장에서는 손으로 맞춘 정렬을 gofmt가 도로 지운다.
어디를 정렬할지 도구가 정하므로 사람이 고를 자리가 없다.
Go 격언(Go Proverbs)의 한 문장이 이 태도를 요약한다.
"gofmt의 스타일은 누구의 취향도 아니지만, gofmt는 모두가 좋아한다."

대가도 있다.
칼럼을 맞추므로 한 줄이 길어지면 이웃한 줄의 공백도 바뀐다.
아래 구조체에 `MaxIdleConnections` 필드 하나를 더하면 손대지 않은 네 줄까지 함께 수정된 것으로 기록된다.

[source,diff]
----
 type Config struct {
-	Host  string
-	Port  int
-	Debug bool
-	TLS   bool
+	Host               string
+	Port               int
+	Debug              bool
+	TLS                bool
+	MaxIdleConnections int
 }
----

줄마다 마지막으로 고친 커밋(코드 변경 기록의 단위, {ch-git}에서 다룬다)을 보여 주는 `git blame` 명령은 나머지 네 줄의 책임 커밋도 이 커밋으로 옮긴다.

완화 장치는 gofmt 안에 있다.
첫째, 빈 줄이 정렬 그룹을 끊으므로, 논리 단위마다 빈 줄을 넣으면 긴 이름 하나가 구조체 전체의 공백을 바꾸지 않는다.
둘째, 한 항목이 유난히 길면 gofmt는 나머지를 늘리는 대신 그 블록의 정렬을 포기한다.

한글로 코드를 쓸 때의 함정도 하나 있다.
gofmt는 칼럼 너비를 화면 폭이 아니라 룬(rune, 글자 하나를 세는 Go의 단위) 개수로 센다.
한글 한 글자는 터미널에서 두 칸을 차지하지만 gofmt는 한 칸으로 세므로, 한글 문자열이 맵의 키처럼 앞 칼럼에 오면 gofmt를 방금 돌린 코드도 어긋나 보인다.
이때는 gofmt의 출력이 옳다고 받아들이면 된다.

== 테스트는 AI 에이전트의 검증 신호

테스트는 사람을 위한 안전망인 동시에 AI 에이전트를 위한 명세다.
기대 동작이 테스트로 고정되어 있을수록 에이전트에게 맡길 수 있는 작업이 넓어진다.
그래서 이 프로젝트는 암산으로 검산하기 어려운 계산(srs), 무엇이든 들어올 수 있는 입구(슬러그 디코딩, 규칙 파싱), 여러 테이블을 한꺼번에 고치는 DB 흐름(복습 기록, 공유 덱)처럼 틀려도 화면에 티가 나지 않는 곳부터 테스트로 덮었다.
핸들러와 화면은 앱을 통째로 띄워 요청을 보내는 편이 잘 맞아서 {ch-app-tests}에서 따로 읽는다.
{ch-quality-gates}에서 이 검사들을 에이전트의 작업 흐름과 CI에 자동으로 거는 법을 다룬다.

== 정리

첫째, Go의 테스트는 `_test.go` 파일, `Test` 접두사, `*testing.T` 매개변수 세 규칙만 지키면 `go test`가 찾아 실행한다.
캐시는 `-count=1`로 무시하고, 동시 실행 오류는 `-race`로 검사한다.

둘째, 입력과 기댓값을 표로 놓고 한 루프로 검사하는 테이블 주도 테스트가 기본 패턴이고, 케이스마다 조건이 다르면 `t.Run`으로 이름을 붙인다.

셋째, DB를 붙이는 테스트는 `t.TempDir`·`t.Cleanup`·`t.Helper`로 만든 픽스처 헬퍼가 준비와 정리를 맡는다.

넷째, 커버리지는 목표가 아니라 테스트가 없는 곳을 찾는 지도이고, 다른 패키지의 테스트가 실행한 코드는 숫자에 잡히지 않는다.

다섯째, gofmt·go vet·staticcheck는 빠르고 결정적이라 자동화에 알맞고, gofmt의 세로 정렬은 취향이 아니라 규칙이다.

다음 {ch-gin}에서는 이렇게 검증한 코드 조각들을 HTTP API로 엮는 웹 프레임워크 Gin을 다룬다.
