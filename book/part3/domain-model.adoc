= 이 앱만의 설계 둘: 간격 반복 상태와 덱 주소

{ch-database-design}에서 세운 테이블들은 대체로 어느 앱에나 있을 법한 것들이었다.
사용자가 있고, 그가 만든 덱이 있고, 덱에 카드가 담긴다.
외래 키로 관계를 맺고 인덱스로 조회를 받치는 방식도 관계형 데이터베이스를 쓰는 앱이라면 대개 같다.

이 장이 다루는 둘은 그렇지 않다.
간격 반복으로 복습 일정을 잡는 앱이라야 필요한 상태가 있고, 덱마다 짧은 주소를 붙이려는 앱이라야 풀어야 할 문제가 있다.
앞엣것은 "알고리즘이 기억해야 할 최소한이 무엇인가"라는 질문이고, 뒤엣것은 "순번을 그대로 주소에 쓰면 무엇이 새는가"라는 질문이다.

둘 다 요구사항에서 곧바로 칼럼이 나오지 않는다는 공통점이 있다.
도메인의 규칙을 먼저 정하고, 그 규칙이 데이터로 어떻게 남아야 하는지를 역산해야 칼럼이 정해진다.
설계가 요구사항의 받아쓰기가 아닌 대목이 여기다.

이 장부터는 스키마 파일만이 아니라 그것을 읽고 쓰는 store 계층의 Go 파일도 함께 연다.
그 파일들이 저장소 어디에 어떤 원칙으로 놓여 있는지는 {ch-code-map}에서 지도로 그렸으니, `internal/litestore/` 아래 경로가 나오면 그 지도의 저장소 구현 자리를 떠올리면 된다.

== SRS 데이터 모델

이 앱의 심장인 간격 반복 데이터 모델을 뜯어 보겠다.

=== 이진 SM-2 상태 저장

Flashcard의 SRS는 간격 반복 앱들이 널리 써 온 고전적 계산법인 SM-2 알고리즘의 이진(binary) 변형으로, 원래 SM-2의 0~5점 6단계 평가 대신 맞음/틀림 두 버튼을 품질 5와 2에 대응시킨다.
여기서 품질(quality)이란 복습한 사람이 "얼마나 또렷이 기억났는가"를 스스로 매기는 점수를 부르는 SM-2의 용어다.
알고리즘이 다음 상태를 계산하는 데 필요한 값이 곧 `card_srs`의 칼럼 구성이다.
`ease_factor`는 카드의 용이도로, 복습 간격을 늘려 가는 배율이다.
맞히면 0.1씩 커져서 다음 복습이 더 멀어지고, 틀리면 0.32씩 깎이며, 1.3 밑으로는 내려가지 않는다.
`interval_days`는 현재 복습 간격, `repetitions`는 연속 정답 횟수, `due_at`이 다음 복습 시각이다.
`correct_count`·`incorrect_count`는 알고리즘 입력은 아니지만 통계와 스마트 덱(오답률 규칙)의 재료이며, `lapses`(틀려서 간격이 처음으로 되돌아간 횟수)도 같은 성격의 기록이다.

상태 전이 로직은 `internal/srs/srs.go`에 순수 함수(입력을 바꾸지 않고 계산 결과만 돌려주는 함수로, {ch-core-logic}에서 자세히 다룬다)로 분리되어 있다.
맞음/틀림 판정 하나를 받아 위 칼럼들의 다음 값과 다음 복습 시각을 계산하는 `Grade`가 그것이고, 시그니처는 `func Grade(s State, correct bool, now time.Time) (State, time.Time)`이다.
다음 상태와 복습 시각, 값 두 개를 함께 돌려주는 데서 {ch-go-hello}에서 익힌 다중 반환이 실전에 쓰이는 모습도 보인다.
함수 본체를 한 줄씩 읽는 것은 {ch-core-logic}의 몫이다.

여기서 요지는 DB 상태와 계산 로직이 1:1로 대응한다는 점이다.
스키마를 설계할 때 "알고리즘이 다음 계산에 쓰는 최소 상태가 무엇인가"를 물으면 칼럼 목록이 저절로 나온다.

=== 복습 기록과 상태 갱신 트랜잭션

복습 한 번은 두 테이블을 건드린다.
`review_logs`에 판정을 남기고 `card_srs`의 상태를 전진시키는데, 이 둘은 반드시 함께 성공해야 한다.

.[용어 풀이] 트랜잭션(Transaction)
[NOTE]
====
여러 개의 데이터 변경을 하나의 작업으로 합쳐, 전부 반영되거나 전부 취소되게 하는 단위다.
계좌 이체에서 "보내는 쪽 잔액 차감"과 "받는 쪽 잔액 증가"가 반쪽만 성공하면 돈이 사라지듯, 함께 성공해야 하는 작업들을 한 묶음으로 만든다.
중간에 하나라도 실패하면 이미 마친 변경까지 되돌려(rollback), 데이터가 어정쩡한 상태로 남지 않게 한다.
====

`internal/litestore/sessions.go`의 `RecordReview`에서 핵심만 발췌한다.
트랜잭션 안에서 현재 SRS 상태를 읽고, 판정 로그를 남기고, 다음 상태를 써넣는 코드다.

[source,go]
----
tx, err := s.db.BeginTx(ctx, nil)
// ...
defer tx.Rollback()

// "for update"가 필요 없다: 트랜잭션이 SQLite의 단일 쓰기 주체를 이미 쥔다.
var state srs.State
err = tx.QueryRowContext(ctx,
	`select ease_factor, interval_days, repetitions from card_srs
	 where card_id = ? and user_id = ?`, cardID.String(), userID.String()).
	Scan(&state.EaseFactor, &state.IntervalDays, &state.Repetitions)
// ...

now := time.Now()
if _, err := tx.ExecContext(ctx,
	`insert into review_logs (user_id, card_id, session_id, result, is_retry, reviewed_at)
	 values (?, ?, ?, ?, ?, ?)`,
	userID.String(), cardID.String(), sessionID.String(), result, isRetry, fmtTime(now)); err != nil {
	return out, err
}

if isRetry {
	out.DueAt = now
	out.IntervalDays = state.IntervalDays
	return out, tx.Commit()
}

next, dueAt := srs.Grade(state, result, now)
correct, incorrect := 0, 1
if result {
	correct, incorrect = 1, 0
}
if _, err := tx.ExecContext(ctx,
	`update card_srs set
	   ease_factor = ?, interval_days = ?, repetitions = ?, due_at = ?,
	   last_reviewed_at = ?,
	   correct_count = correct_count + ?,
	   incorrect_count = incorrect_count + ?,
	   lapses = lapses + ?
	 where card_id = ? and user_id = ?`,
	next.EaseFactor, next.IntervalDays, next.Repetitions, fmtTime(dueAt),
	fmtTime(now), correct, incorrect, incorrect,
	cardID.String(), userID.String()); err != nil {
	return out, err
}
// ...
----

네 가지를 짚어 보자.

첫째, `defer tx.Rollback()`과 마지막의 `tx.Commit()`이 트랜잭션의 울타리다.
중간 어디서든 에러로 빠져나가면 rollback이 실행되어 로그 삽입까지 포함해 전부 되돌아가고, 끝까지 가야만 두 변경이 함께 확정된다.

둘째, 상태를 읽는 select에 잠금 문이 없다.
주석이 말하듯 SQLite는 한 시점에 쓰기 트랜잭션을 하나만 허용하고 이 스토어는 `SetMaxOpenConns(1)`로 아예 연결을 하나로 제한하므로(`internal/litestore/store.go`), 읽기-계산-쓰기 사이에 다른 갱신이 끼어들 수 없다.
여러 접속이 같은 행을 동시에 고칠 수 있는 운영 PostgreSQL에서는 사정이 달라서, 같은 함수의 운영 구현(`internal/pgstore/sessions.go`)은 `select ... for update`로 행 잠금을 건다.
잠금 없이 두 요청이 각자 읽은 값으로 계산해 덮어쓰면, 한쪽의 갱신이 소리 없이 사라지는 갱신 유실(lost update)이 생기기 때문이다.

셋째, `is_retry`면 로그만 남기고 커밋한다.
재도전 라운드는 방금 틀린 카드를 같은 세션에서 다시 넘겨 보는 기능인데, 이를 정답으로 SRS에 반영하면 "1분 전에 본 카드를 또 맞혔다"는 신호로 간격이 부풀어 알고리즘이 오염된다.
그래서 요구사항의 미묘한 규칙 하나가 분기 하나와 칼럼 하나로 구현됐다.

넷째, 정답/오답 카운터 갱신을 `correct_count = correct_count + ?` 형태로 SQL 안에서 처리했다.
값을 읽어 와 Go에서 더한 뒤 다시 쓰는 방식과 달리 DB가 한 번에 처리하므로, 중간에 다른 요청이 끼어들 틈이 없는 원자적(atomic) 갱신이다.
서버와 DB를 오가는 횟수도 한 번으로 준다.

.[용어 풀이] 원자적(Atomic)
[NOTE]
====
더 쪼갤 수 없는 하나의 동작처럼 처리되어, 중간 상태가 다른 작업에 보이지도 않고 끼어들 틈도 주지 않는 성질이다.
`correct_count = correct_count + 1`을 DB에 맡기면 읽기와 더하기와 쓰기가 한 동작으로 끝나지만, 값을 읽어 와 프로그램에서 더한 뒤 다시 쓰면 그 사이에 다른 요청이 같은 값을 읽어 가 한쪽의 증가가 사라질 수 있다.
엘리베이터 문이 반쯤 열린 채로 멈추지 않고 열리거나 닫히거나 둘 중 하나인 것과 같다.
방금 본 트랜잭션이 "전부 반영되거나 전부 취소"를 보장하는 것도 여러 변경을 하나의 원자적 동작으로 합치는 일이다.
====

=== "오늘 복습" 큐 쿼리

SRS의 출구는 "지금 복습할 카드를 달라"는 쿼리다.
`internal/litestore/cards.go`에서 발췌한, 복습 시각이 지난 카드를 가장 오래 밀린 순서로 가져오는 함수다.

[source,go]
----
const cardSelect = `
	select id, deck_id, text, meaning, card_type, tags, phonetic, example,
	       notes, created_at, attempts, error_rate, interval_days, due_at, last_reviewed_at
	from cards_with_stats`

func (s *Store) DueCards(ctx context.Context, userID uuid.UUID, dueBefore time.Time, limit int) ([]model.Card, error) {
	rows, err := s.db.QueryContext(ctx,
		cardSelect+` where user_id = ? and due_at <= ? order by due_at asc limit ?`,
		userID.String(), fmtTime(dueBefore), limit)
	// ...
}
----

`due_at <= ?`의 자리에는 `fmtTime`으로 포맷한 현재 시각 텍스트가 들어간다.
{ch-database-design}의 시각 절에서 본 고정 폭 표기 덕분에 이 문자열 비교가 정확히 시간 비교로 동작한다.
앞서 만든 `card_srs_user_due_idx (user_id, due_at)`를 (등치, 범위) 순서 그대로 쓰는 곳은 홈 화면 배지가 부르는 같은 파일의 `DueCount`다.
카드 본문이 필요 없으므로 뷰를 거치지 않고 `select count(*) from card_srs where user_id = ? and due_at <= ?`로 `card_srs`만 세는데, 조건이 인덱스 열과 정확히 겹쳐서 DB가 인덱스만 읽고 답을 낸다.
반면 `DueCards`의 실행 계획을 `explain query plan`으로 확인해 보면 이 인덱스를 타지 않는다.
같은 `user_id` 조건인데 결과가 다른 이유는 그 열이 어느 테이블의 것이냐에 있다.
`card_srs_user_due_idx`는 `card_srs`의 `user_id`에 걸린 인덱스인데, 뷰가 노출하는 `user_id`는 `cards` 쪽 칼럼이라 DB가 이 인덱스를 쓸 자리로 보지 않는다.
그래서 SQLite는 `cards_user_idx`로 그 사용자의 카드를 모은 뒤 카드마다 SRS 행을 기본 키(`card_id`)로 이어 붙이고 마지막에 `due_at`으로 정렬하는 경로를 고른다.
카드 5,000장(절반이 복습 대상)을 넣은 임시 SQLite 파일에서 재 보면 이 경로로 카드 20장을 가져오는 데 이 글을 쓰는 컴퓨터에서 3ms 안팎, 복습 대상 2,500장을 전부 가져와도 11ms 안팎이었고, 인덱스만 읽는 `DueCount`는 0.15ms 안팎이었다.
한 사람의 카드 수천 장 규모에서는 이 경로를 그대로 두고 뷰의 단순함을 유지했다.
같은 질문이라도 쿼리의 모양과 필요한 데이터 폭에 따라 실제 접근 경로가 달라진다는 것을 보여 주는 대비다.

== 덱 슬러그 설계: 시퀀스에서 URL로

URL 설계는 DB 설계와 맞닿아 있다.
`/decks/9f8c1c2e-...` 같은 UUID URL은 안전하지만 길고 흉하고, 순번을 그대로 노출한 `/decks/17`은 짧지만 순번이라는 사실 자체가 정보(전체 덱 수, 이웃 덱의 존재)를 흘린다.
덱을 가리키면서 주소창에 놓기 좋은 짧은 문자열, 즉 슬러그(slug)가 필요하다.

.[용어 풀이] 슬러그(slug)
[NOTE]
====
URL 안에서 자원 하나를 가리키는 짧고 읽기 쉬운 문자열이다.
블로그 글 주소 `/posts/hello-world`의 `hello-world`가 슬러그이고, Flashcard에서는 덱을 가리키는 `/decks/9x2k` 같은 네 글자 코드가 슬러그다.
내부 식별자를 그대로 내보이는 대신 사람이 주고받기 좋은 값을 앞에 세우는 장치라, 입으로 불러 주거나 손으로 옮겨 적기 좋아야 한다.
짧으면서도 값이 겹치지 않아야 하고 내부 순번을 짐작하게 해서도 안 된다는 요구가 여기서 나온다.
이어지는 절이 그 요구를 하나씩 푸는 과정이다.
====

Flashcard의 답은 "순번을 저장하되, 노출 전에 뒤섞는다"이다.

재료가 되는 순번이 `decks.seq`다.
스키마에서 `seq integer not null unique`로 선언되어 덱마다 겹치지 않는 번호가 하나씩 붙는다.
`internal/litestore/decks.go`에서 발췌한, 새 덱에 다음 번호를 붙이는 insert 문과 그것을 실행하는 `CreateDeck`의 핵심이다.

[source,go]
----
// insertDeckSQL은 CreateDeck과 ImportSharedDeck이 함께 쓴다. max(seq)+1이
// Postgres의 identity 열을 대신하며, 로컬은 쓰기 주체가 하나뿐이라 경쟁이 없다.
const insertDeckSQL = `insert into decks (id, user_id, name, description, seq, created_at, updated_at)
	 values (?, ?, ?, ?, (select coalesce(max(seq), 0) + 1 from decks), ?, ?)`

id := uuid.New()
now := fmtTime(time.Now())
_, err := s.db.ExecContext(ctx, insertDeckSQL,
	id.String(), userID.String(), name, description, now, now)
----

지금까지의 최대 순번에 1을 더하는 `max(seq) + 1` 채번(새 번호를 뽑아 배정하는 일)이다.
두 요청이 동시에 같은 최대값을 읽으면 같은 번호를 내줄 수 있는 방식이지만, 사용자가 하나이고 쓰기가 한 줄로 서는 로컬 모드에는 그런 경쟁이 없다.
여러 접속이 동시에 덱을 만드는 운영 PostgreSQL에서는 DB가 관리하는 시퀀스(identity 칼럼)가 채번을 맡아 이 경쟁을 원천 차단한다.
"덱마다 순번 하나"라는 같은 설계를 환경의 동시성 수준에 따라 다른 채번 장치로 구현한 대비다.
운영 쪽 장치는 {ch-supabase-db}에서 본다.

이제 이 순번이 URL이 되는 과정이다.
`internal/model/deckslug.go`에서 발췌한, 덱의 순번(`seq`)을 받아 뒤섞인 4자 코드로 바꾸는 함수다.

[source,go]
----
include::../../flashcard-advanced/internal/model/deckslug.go[tag=slug-constants]

include::../../flashcard-advanced/internal/model/deckslug.go[tag=encode]
----

이 파일은 SQL이 한 줄도 없는 순수 Go 코드라서, SQLite 스토어도 운영 스토어도 같은 함수를 그대로 쓴다.
설계 결정을 하나씩 풀어 보자.

첫째, 문자 집합은 Base36(0-9, a-z)이다.
Base62(대소문자 구분)보다 표현력은 낮지만 대소문자를 구분하지 않아 사용자가 슬러그를 입으로 전달하거나 손으로 입력할 때 혼동이 없다.
짧은 URL 코드에서는 표현력보다 오독 없는 전달이 더 중요하다는 판단이다.

둘째, 길이는 4자 고정으로, 36⁴ = 1,679,616이므로 전역에서 약 168만 개의 덱까지 표현할 수 있다.
`seq`는 사용자별이 아닌 전역 시퀀스라서 이 값이 서비스 전체 덱 수의 상한이 된다.
사용자 1,000명이 덱을 100개씩 만들어도 10만 개라 개인 학습 앱의 규모에서는 충분하다.
이 한계와, 모자라면 `slugLen`을 늘리면 된다는 확장 경로는 코드 주석에 적혀 있다.

셋째, 순번을 감추는 방법으로 곱셈 순열(multiplicative permutation)을 썼다.
아이디어 자체는 단순한데, 순번에 큰 상수를 곱한 뒤 일정한 크기로 나눈 나머지만 남기면 1·2·3처럼 이어지던 값이 서로 멀리 떨어진 코드로 흩어진다.
곱하는 상수를 잘 고르면 서로 다른 순번은 언제나 서로 다른 코드가 되고, 코드를 원래 순번으로 되돌리는 계산도 딱 하나로 정해진다.
그 "잘 고른 상수"의 조건은 전체 칸 수(`slugSpace`)와 1 말고는 공약수가 없다는 것이다(수학에서는 이를 서로소(coprime)라고 부른다).
이 조건이 지켜지면 서로 다른 순번은 서로 다른 코드로만 가고(전단사, bijection), 코드에서 순번으로 되돌릴 때 곱하는 값도 딱 하나 존재한다(역원).
그 되돌리는 값이 코드에 `slugMulInv`라는 이름으로 미리 구해져 있다.
암호학적으로 예측 불가능한 것은 아니므로 비밀 값에는 부적합하지만, 덱 슬러그는 어차피 소유자 인증 뒤에서만 조회되므로 "순번처럼 안 보이게 하기"면 충분하다.
조회 쪽은 `internal/litestore/decks.go`의 `GetDeckBySlug`가 `DecodeDeckSlug`로 슬러그를 `seq`로 되돌린 뒤 `where d.user_id = ? and d.seq = ?` 조건으로 찾는다.
슬러그 칼럼을 따로 저장하지 않고 `seq`에서 매번 계산하는 점도 특징인데, 전단사 변환이므로 저장할 필요가 없고 `seq`의 유니크 제약이 곧 슬러그의 유일성을 보장한다.

대조군으로 공유 슬러그(`share_slug`)를 보면 다른 선택을 했다.
`internal/model/sharing.go`의 `NewShareSlug`는 시퀀스 변환이 아니라 `crypto/rand`로 무작위 5자 Base36 토큰을 만들고, {ch-database-design}에서 본 부분 유니크 인덱스에 부딪히면 새 토큰으로 최대 다섯 번까지 재시도하고, 다섯 번 다 겹치면 에러를 돌려준다(`internal/litestore/sharing.go`의 `ShareDeck`).
개인 덱 슬러그는 행마다 이미 있는 `seq`에서 결정적으로 유도되니 충돌 자체가 없고, 공유 슬러그는 공유 시점에 새로 만드는 값이라 무작위 + 충돌 재시도가 단순하다.
같은 앱 안에서도 생성 시점과 유일성 보장 수단에 따라 슬러그 전략이 달라질 수 있음을 보여 주는 사례다.

== 운영 DB에 필요한 두 가지: 고치는 절차와 지키는 장치

로컬 SQLite의 스키마 관리는 이 장에서 본 것이 전부다.
서버가 시작할 때 `schema.sql`을 통째로 적용하고, 틀을 바꾸고 싶으면 파일을 고친 뒤 서버를 다시 시작하면 된다.
아직 소중한 데이터가 없는 개발용 파일이라면 지우고 새로 만들어도 그만이다.

운영 DB는 그럴 수 없다.
사용자의 학습 기록이 살아 있는 DB의 틀을 고치려면, 변경을 순서 있는 스크립트로 남겨 차례로 적용하는 절차(마이그레이션, migration)가 필요하다.
또 내 컴퓨터 안에서만 열리는 SQLite 파일과 달리 운영 PostgreSQL은 네트워크에 노출된 서버라, "누가 어떤 행에 손댈 수 있는가"를 DB 스스로 지키는 장치도 필요하다.
Flashcard는 PostgreSQL의 행 수준 보안(RLS, Row Level Security)을 그 장치로 쓴다.
지키는 장치는 {ch-supabase-db}에서, 고치는 절차는 운영 스키마(`internal/db/migrations/`)와 함께 {ch-migrations}에서 다룬다.

== 에이전트 활용 아이디어

도메인 규칙이 걸린 설계는 에이전트에게 넘기기 전에 규칙부터 말로 확정해야 한다.

"재도전 라운드의 답은 SRS 채점에 반영하지 않는다"처럼 요구사항 문장 하나가 칼럼 하나로 굳는 대목에서는, 그 문장을 지시문에 그대로 실어 준다.
규칙을 빼고 "복습 기록 테이블을 만들어 달라"고만 하면 에이전트는 흔한 설계를 골라 오고, 그 설계에는 `is_retry` 같은 칼럼이 없다.

자동화 아이디어로는 스키마 변경 리허설이 있다.
"바뀐 `schema.sql`을 빈 SQLite 파일에 적용하고 스키마 덤프를 보여 달라"는 지시를 스킬로 저장해 두면, 스키마를 만질 때마다 같은 검증을 명령 하나로 반복할 수 있다.

== 정리

이번 장에서는 Flashcard 고유의 두 설계를 데이터로 옮겼다.

SRS 상태는 알고리즘에 필요한 최소 상태로 칼럼을 구성했고, 복습 기록은 트랜잭션으로 로그 삽입과 상태 갱신을 원자적으로 처리한다.
재도전 라운드를 SRS에서 제외하는 도메인 규칙은 `is_retry` 칼럼 하나로 스키마에 남겼다.

덱 슬러그는 `max(seq)+1`로 채번한 순번을 곱셈 순열로 뒤섞은 Base36 4자 코드로, 짧은 URL과 순번 은닉을 저장 칼럼 추가 없이 얻었다.

그리고 로컬 SQLite는 시작할 때 스키마를 통째로 적용하면 그만이지만, 데이터가 살아 있는 운영 DB에는 고치는 절차(마이그레이션)와 지키는 장치(RLS)가 필요하다는 것까지 짚었다.
전용 타입과 RLS는 {ch-supabase-db}에서, 마이그레이션은 {ch-migrations}에서 이어진다.

여기까지가 데이터가 머무는 바닥층이다.
다음 {ch-core-logic}부터는 한 층 올라가, {ch-code-map}에서 그린 지도의 자리를 찾아가며 이 테이블들을 읽고 쓰는 핵심 로직을 Go 코드로 읽는다.
