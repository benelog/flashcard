= 로컬 개발 환경: 무설정 실행의 원리와 개발 도구

{ch-first-run}에서는 저장소를 클론해 명령 하나로 이 앱을 띄웠다.
데이터베이스 설치도, 계정 가입도, 설정 파일 작성도 없었고, {ch-app-tests}의 테스트도 같은 방식으로 앱을 띄웠다.
이 장에서는 그 무설정 실행을 성립시키는 코드의 분기를 따라간 뒤, 에디터 설정으로 사람 쪽 개발 환경을 갖추고, 환경 변수로 동작을 바꾸는 길까지 정리해 3부를 마무리한다.

== 무설정 실행은 어떻게 가능한가

배포된 Flashcard는 PostgreSQL과 Supabase 인증 위에서 돌지만, 로컬 서버는 코드 곳곳의 분기 덕분에 둘 다 없이 돈다.
출발점은 {ch-code-map}에서 읽은 `internal/config/config.go`다.
`DATABASE_URL`이 있으면 운영과 같은 PostgreSQL 구성을, 없으면 SQLite 파일과 로컬 인증이라는 기본값을 채운다.
`DATABASE_URL`은 실행할 때 바깥에서 건네주는 환경 변수이고, 코드의 `env("이름")`은 `os.Getenv`로 그 값을 읽어 앞뒤 공백을 걷어 내는 헬퍼다.
로컬에서는 아무도 이 값을 건네지 않으므로 아래 분기가 로컬 모드를 고른다.

[source,go]
----
	if cfg.DatabaseURL != "" {
		cfg.Driver = "postgres"
		cfg.AuthMode = "supabase"
		if cfg.SupabaseURL == "" || cfg.SupabaseAnonKey == "" {
			return nil, fmt.Errorf("SUPABASE_URL and SUPABASE_ANON_KEY are required")
		}
		// ...
		return cfg, nil
	}

	// DATABASE_URL이 없으면 SQLite 파일로 1인 로컬 모드를 돈다. Vercel에서는
	// 함수의 일회용 파일시스템에 조용히 쓰게 되므로, 거기서 DATABASE_URL이
	// 없는 것은 언제나 설정 실수다.
	if os.Getenv("VERCEL") != "" {
		return nil, fmt.Errorf("DATABASE_URL is required on Vercel")
	}
	cfg.Driver = "sqlite"
	cfg.AuthMode = "local"
	cfg.SQLitePath = env("SQLITE_PATH")
	if cfg.SQLitePath == "" {
		cfg.SQLitePath = "local-db/flashcard.db"
	}
	return cfg, nil
----

로컬 모드의 기본값은 SQLite 드라이버(파일은 `local-db/flashcard.db`)와 로컬 인증 모드다.
거꾸로 `DATABASE_URL`이 있는 운영 구성에서는 `SUPABASE_URL`과 `SUPABASE_ANON_KEY`까지 요구해, 값이 빠진 채 어중간하게 뜨는 일을 막는다({ch-supabase-auth}).

중간의 `VERCEL` 검사는 가드다.
배포 환경에서 `DATABASE_URL`을 빠뜨리면 서버리스 함수의 일회용 파일 시스템에 SQLite 파일을 만들었다가 데이터를 통째로 잃으므로, Vercel 위에서는 기동을 거부한다.

SQLite면 스키마 준비도 서버가 한다.
`internal/litestore/store.go`의 `Open`은 SQLite 파일을 열되 파일이나 폴더가 없으면 먼저 만들고, 임베드된 `schema.sql`을 곧바로 적용한다.

[source,go]
----
//go:embed schema.sql
var schemaSQL string

// ...
func Open(path string) (*Store, error) {
	if dir := filepath.Dir(path); dir != "." {
		if err := os.MkdirAll(dir, 0o755); err != nil {
			return nil, fmt.Errorf("create sqlite dir: %w", err)
		}
	}
	db, err := sql.Open("sqlite",
		path+"?_pragma=foreign_keys(1)&_pragma=busy_timeout(5000)&_pragma=journal_mode(wal)")
	// ...
	if _, err := db.Exec(schemaSQL); err != nil {
		db.Close()
		return nil, fmt.Errorf("apply schema: %w", err)
	}
	// ... 옛 파일 보정(ensureColumn)
	return &Store{db: db}, nil
}
----

경로의 물음표 뒤에 붙은 글자들은 파일을 열면서 거는 세 가지 설정이다.
외래 키 제약을 실제로 검사하고({ch-database-basics}), 파일이 잠겨 있으면 5초까지 기다리고, 쓰기 기록을 별도 파일에 먼저 남기는 방식(WAL)으로 읽기와 쓰기가 서로를 막지 않게 한다.
{ch-first-run}에서 본 `-wal` 파일이 그것이다.
스키마의 모든 문장이 `if not exists` 꼴이라 몇 번을 켜도 이미 있는 테이블은 건드리지 않는다.
다만 이미 있는 테이블에 새 열을 더해 주지는 않으므로, 생략한 `ensureColumn` 대목이 예전 파일에 빠진 열(지금은 `decks.story` 하나)을 보정한다.

인증 쪽 분기인 `internal/auth/local.go`는 토큰을 검사하는 대신 모든 요청을 고정된 한 명의 사용자로 로그인시킨다.

[source,go]
----
// LocalUserID는 로컬 모드의 모든 요청이 쓰는 고정 사용자다.
var LocalUserID = uuid.MustParse("00000000-0000-0000-0000-000000000001")

// ...
func LocalMiddleware() gin.HandlerFunc {
	return func(c *gin.Context) {
		c.Set(userIDKey, LocalUserID)
		c.Next()
	}
}
----

{ch-app-assembly}의 라우터 조립부(`pkg/app/app.go`)는 인증 모드가 로컬이면 JWT 검증 미들웨어 자리에 이 함수를 끼운다.
라우터도 핸들러도 store 계층도 그대로이고, 바뀌는 것은 문 앞의 문지기 하나뿐이다.

화면 쪽의 방문자 식별을 맡는 `internal/web/cookies.go`의 `withUser`도 인증 모드가 로컬이면 쿠키를 살피는 대신 모든 방문자를 고정 사용자로 세운다.

[source,go]
----
func (w *Web) withUser() gin.HandlerFunc {
	if w.cfg.AuthMode == "local" {
		return func(c *gin.Context) {
			auth.SetUserID(c, auth.LocalUserID)
			c.Next()
		}
	}
	// ... 쿠키 세션 검증과 갱신 (32장에서 다룬다)
}
----

로그인 화면으로 보내는 문지기는 방문자가 식별되지 않았을 때만 작동하므로, 로컬 모드에서는 로그인 화면이 나오지 않는다.

== .vscode: 에디터가 프로젝트의 규칙을 실어 나른다

코드를 고치는 사람의 환경으로는 코드 편집기 VS Code(Visual Studio Code)를 쓴다(설치는 {ch-first-run}).
다른 편집기를 쓰는 독자는 "프로젝트의 규칙을 어떻게 저장소에 실어 보내는가"라는 관점으로 읽으면 된다.

.[용어 풀이] 코드 편집기(Code Editor)와 확장(Extension)
[NOTE]
====
코드 편집기는 코드를 쓰고 고치는 일에 특화된 프로그램이고, VS Code는 마이크로소프트가 무료로 배포하는 코드 편집기다.
확장은 편집기에 기능을 하나씩 얹는 부가 프로그램으로, 언어마다 다른 자동 완성이나 디버깅 같은 기능을 채운다.
스마트폰에 필요한 앱을 골라 까는 것처럼, 같은 편집기라도 어떤 확장을 깔았느냐에 따라 다른 도구가 된다.
====

글꼴 크기나 색 테마는 개인의 영역이지만, "Go 파일은 저장할 때 gofmt를 돌린다", "검증은 이 명령들로 한다" 같은 규칙은 프로젝트의 성질이다.
VS Code는 작업 폴더 안의 `.vscode/`를 읽어 개인 설정 위에 덮어쓰므로, 이런 규칙만 담아 커밋하면 클론한 사람이 별도 안내 없이 같은 환경을 얻는다.
Flashcard의 `.vscode/`에는 `extensions.json`, `settings.json`, `tasks.json`, `launch.json` 네 파일이 있다.

=== extensions.json: 필요한 확장을 저장소가 알려 준다

`extensions.json`은 VS Code가 설치를 권하는 추천 확장 목록이다.
뒤에서 볼 포맷·검사·디버깅이 모두 얹히는 Go 공식 확장 `golang.go`와, 에디터에 붙는 AI 에이전트 확장 하나뿐이다.
화면도 서버 템플릿과 순수 CSS, {n-app-js-lines}줄 남짓의 JS라 별도 툴체인이 없고, 포맷은 gofmt가 독점하므로 포매터나 린터(코드의 흠을 찾아 주는 정적 분석 도구) 확장을 따로 들일 이유가 없다.

=== settings.json: 저장하는 순간 규칙이 적용된다

다음은 `settings.json`의 주요 부분으로, 저장할 때 적용되는 규칙과 테스트 실행 방식을 정한다.

[source,json]
----
{
  "editor.formatOnSave": true,

  "[go]": {
    "editor.defaultFormatter": "golang.go",
    "editor.codeActionsOnSave": {
      "source.organizeImports": "explicit"
    }
  },
  "go.useLanguageServer": true,
  "go.formatTool": "gofmt",
  "go.vetOnSave": "package",
  "go.testFlags": ["-count=1"],
  // ...
  "files.trimTrailingWhitespace": true
}
----

`editor.formatOnSave`와 `[go]` 블록 덕분에 Go 파일을 저장하는 순간 gofmt가 돌아 {ch-unit-tests}의 세로 정렬이 자동으로 맞춰진다.
`source.organizeImports`는 저장할 때 쓰지 않는 import를 지우고 정렬한다(Go는 쓰지 않는 import가 남으면 컴파일을 거부한다).
`go.vetOnSave`를 `package`로 두면 저장할 때마다 그 패키지에 `go vet`이 돌아, 정적 분석 결과가 편집 중에 밑줄로 나타난다.

.[용어 풀이] 언어 서버(Language Server)
[NOTE]
====
에디터와 따로 돌면서 코드를 읽고 이해해 주는 배후 프로그램이다.
자동 완성, 정의로 이동, 오류 표시를 에디터가 직접 구현하는 대신 이 서버에 물어보는 구조라, 언어 하나에 서버 하나만 있으면 여러 에디터가 함께 쓸 수 있다.
Go의 언어 서버는 gopls이고, `go.useLanguageServer`가 이를 켠다.
====

`go.testFlags`의 `-count=1`은 캐시된 지난 테스트 결과를 재사용하지 않게 하는 플래그라, 에디터에서 돌린 테스트 결과는 언제나 방금 실제로 실행된 결과다.

=== tasks.json: 검증 명령에 이름을 붙인다

`go build`·`go vet`·`go test`를 태스크(task, 자주 쓰는 명령에 이름을 붙여 VS Code 메뉴에서 실행하게 하는 기능)로 등록하면 명령을 외우지 않아도 되고, VS Code가 출력에서 파일과 줄 번호를 뽑아 문제 목록으로 만들어 준다.

[source,json]
----
{
  "version": "2.0.0",
  "tasks": [
    { "label": "go: build", "type": "shell", "command": "go build ./...",
      "options": { "cwd": "${workspaceFolder}/flashcard-advanced" },
      "group": "build", "problemMatcher": ["$go"] },
    { "label": "go: test", "type": "shell", "command": "go test ./...",
      "options": { "cwd": "${workspaceFolder}/flashcard-advanced" },
      "group": "test", "problemMatcher": ["$go"] },
    { "label": "go: vet", "type": "shell", "command": "go vet ./...",
      "options": { "cwd": "${workspaceFolder}/flashcard-advanced" },
      "problemMatcher": ["$go"] },
    {
      "label": "전체 검증",
      "dependsOn": ["go: build", "go: vet", "go: test"],
      "dependsOrder": "sequence",
      "group": { "kind": "test", "isDefault": true },
      "problemMatcher": []
    }
  ]
}
----

`options.cwd`는 명령을 실행할 위치로, 저장소 루트에 책 원고와 연습용 코드도 있어 `flashcard-advanced/`로 못 박아 둔다.
`problemMatcher`의 `$go`는 VS Code에 내장된 출력 해석 규칙으로, `internal/model/deckslug.go:42:5: ...` 같은 줄을 클릭 가능한 문제 항목으로 바꾼다.
`전체 검증` 태스크는 앞의 셋을 순서대로 실행하고, 하나라도 실패하면 거기서 멈춘다.

=== launch.json: F5 한 번으로 디버거를 붙인다

`launch.json`에는 서버 실행과 테스트 실행이라는 두 디버깅 구성이 있다.

.[용어 풀이] 디버거(Debugger)와 중단점(Breakpoint)
[NOTE]
====
디버거는 프로그램을 지정한 줄에서 잠시 멈춰 세우고, 그 순간의 변수 값을 들여다보는 도구다.
코드가 어떤 값으로 도는지를 짐작이 아니라 눈으로 확인할 수 있다.
어디서 멈출지 지정하는 표식이 중단점이고, 에디터에서 줄 번호 왼쪽을 클릭해 찍는다.
Go의 디버거는 델브(Delve, 실행 파일 `dlv`)다.
====

[source,json]
----
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "서버 (cmd/server)",
      "type": "go",
      "request": "launch",
      "mode": "debug",
      "program": "${workspaceFolder}/flashcard-advanced/cmd/server",
      "cwd": "${workspaceFolder}/flashcard-advanced"
    },
    {
      "name": "Go: 현재 파일의 패키지 테스트",
      "type": "go",
      "request": "launch",
      "mode": "test",
      "program": "${fileDirname}"
    }
  ]
}
----

첫 구성은 완성본 앱의 진입점을 앱 디렉터리에서 띄우므로, 디버거로 띄운 서버도 데이터 파일(`local-db/`)을 평소 자리에 만든다.
환경 변수 항목이 없어도 로컬 모드 덕분에 서버가 그냥 뜨므로, 클론 직후의 저장소에서 F5(VS Code의 디버깅 시작 단축키) 한 번으로 중단점까지 걸 수 있다.
{ch-core-logic}의 `srs.Grade`에 중단점을 걸고 카드 하나를 "맞음"으로 넘겨 보면, 글로만 따라가던 간격 계산이 값을 바꿔 가며 진행된다.

두 번째 구성은 열어 둔 파일이 속한 패키지의 테스트를 디버거 아래에서 돌려, 실패한 케이스의 입력값을 중단점에서 들여다보게 한다.
`dlv`가 없으면 Go 확장이 설치하겠느냐고 먼저 묻는다.

에디터의 저장 시 검사와, 파일을 고칠 때마다 도는 에이전트 쪽 gofmt·go vet이 같은 규칙을 지키는 두 곳이라는 이야기는 {ch-quality-gates}에서 잇는다.

== 환경 변수로 동작 바꾸기

환경 변수(Environment Variable)는 프로그램이 실행될 때 운영체제에서 건네받는 이름표 붙은 값으로, 코드를 고치지 않고 동작을 바깥에서 바꾸는 수단이다.
이 관점에서 로컬 모드는 환경 변수를 하나도 채우지 않았을 때의 기본 동작을 설계해 둔 결과다.

`config.go`가 읽는 환경 변수는 `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_JWKS_URL`, `SUPABASE_JWT_SECRET`, `PORT`, `SQLITE_PATH`, 그리고 배포 환경을 알리는 `VERCEL`이다.
그중 둘은 지금 바꿔 볼 수 있다.
셸에서 명령 앞에 `이름=값`을 붙이면 그 값을 환경 변수로 얹은 채 뒤의 명령을 실행한다(명령 둘이 아니라 한 줄짜리 명령 하나다).
`SQLITE_PATH=~/cards/my.db go run ./cmd/server`는 데이터 파일 위치를, `PORT=9090 go run ./cmd/server`는 접속 주소를 `http://localhost:9090`으로 바꾼다.

동작을 가장 크게 바꾸는 것은 `DATABASE_URL`이다.
이 값을 채우는 순간 서버는 SQLite를 접고 PostgreSQL에 연결하고, `SUPABASE_URL`과 `SUPABASE_ANON_KEY`를 함께 채우면 화면에 로그인이 생긴다.
그 값들을 어디서 얻고 어디에 적어 두는지는 {ch-env-secrets}에서 다룬다.

== 이 구성이 내주는 것

무설정 실행과 커밋된 에디터 설정에도 대가가 있다.

첫째, 로컬 모드는 운영과 다른 데이터베이스 엔진 위에서 돈다.
`internal/litestore`는 `internal/pgstore`와 같은 인터페이스를 SQLite로 다시 구현한 것이라 같은 기능을 두 벌 유지해야 하고, PostgreSQL에만 있는 기능(RLS, GIN 인덱스)은 로컬에 없다.
그 간극은 {ch-supabase-db}에서 개발용 PostgreSQL을 연결해 메운다.

둘째, `.vscode/`는 VS Code에 맞춘 설정이라 Neovim이나 GoLand를 쓰는 사람은 같은 규칙을 손으로 옮겨야 한다.
그래서 규칙의 원본은 에디터 바깥에 둔다.
포맷의 원본은 `gofmt`이고 검증의 원본은 `go vet`과 `go test`이며, `.vscode/`는 그 명령들을 편하게 부르는 껍데기일 뿐이다.

셋째, `settings.json`에 개인 취향을 섞으면 금세 다툼거리가 된다.
커밋되는 파일 내용을 바꾸지 않는 항목(글꼴, 색 테마)은 개인 설정에 두고, 내용을 바꾸는 규칙(`files.trimTrailingWhitespace` 같은)만 저장소에 남기는 것이 경계선이다.

== 에이전트 활용 아이디어

`AGENTS.md`에 "로컬 서버는 `go run ./cmd/server`, 환경 변수 없이 로컬 모드로 뜬다"와 "`local-db/`는 개발 데이터다"를 적어 둔다.
에이전트가 검증용 서버를 띄울 때와, 실험 뒤 무엇을 정리해도 되는지 판단할 때의 근거가 된다.

"서버를 띄우고 홈 화면과 `/api/healthz` 응답을 확인한 뒤 종료해 달라"는 스모크 테스트 지시는 자주 쓰는 지시문으로 저장해 두고 불러 쓸 만하다.
에이전트에게도 `tasks.json`과 같은 검증 명령을 쓰게 하면, 사람과 에이전트의 게이트가 어긋나지 않는다.

== 정리

* `config.go`는 `DATABASE_URL`이 없으면 SQLite 드라이버와 로컬 인증을 채우고, Vercel 위에서는 그 기본값으로 넘어가지 않는다.
* SQLite 저장소는 열 때 폴더와 스키마를 스스로 준비하고, API의 `LocalMiddleware`와 화면의 `withUser`가 고정 사용자를 세워 로그인 화면이 뜨지 않는다. 바뀌는 것은 문지기와 저장소뿐이고 나머지는 배포 환경과 같은 코드다.
* `.vscode/` 네 파일은 저장 시 포맷·검사, 검증 명령, 디버깅 구성을 저장소가 실어 나르게 한다. 규칙의 원본은 에디터 바깥의 `gofmt`·`go vet`·`go test`다.
* 환경 변수는 코드를 고치지 않고 동작을 바꾸는 통로로 남는다.

이 장으로 3부의 완성본 앱 해부가 끝났다.
설계 원칙과 코드 지도({ch-design-principles·code-map})에서 출발해 테이블, 핵심 로직과 테스트, 요청 처리와 조립, 화면을 읽었고, 앱을 통째로 띄워 배선까지 확인한 뒤 그 전부가 설정 없이 도는 원리를 봤다.
그런데 이 앱은 아직 내 컴퓨터에만 있다.
4부에서는 이 앱을 세상에 공개하고, 그 첫걸음은 코드의 이력을 관리하는 {ch-git}의 Git이다.
