= html/template 깊이 보기: 레이아웃 복제와 자동 이스케이프

{ch-gin}에서 만든 API는 JSON 데이터를 돌려준다.
덱 목록을 요청하면 중괄호와 따옴표로 감싼 텍스트가 올 뿐, 사람이 볼 화면은 아니다.
{ch-html-css}에서는 그 화면의 재료인 HTML과 CSS를 실제 파일로 읽었다.
이제 남은 질문은 하나다.
데이터베이스에서 꺼낸 덱 목록을 누가 HTML에 채워 넣는가.

Flashcard의 답은 서버다.
Go 표준 라이브러리 html/template이 HTML 양식에 데이터를 채워 완성된 화면을 만들고, 브라우저는 받은 그대로 그리기만 한다.
별도 프런트엔드 프레임워크 대신 서버가 화면을 그리는 구조를 택한 이유는 {ch-tech-choices}에서 정리했다.

문법은 다시 설명하지 않는다.
점 하나가 지금 보고 있는 데이터라는 것, `{{if}}`와 `{{range}}`가 갈래와 반복을 만든다는 것, `{{define}}`으로 조각에 이름을 붙여 `{{template}}`으로 불러 쓴다는 것까지 {ch-template-hello}에서 최소 앱으로 익혔다.
이 장은 그 문법 위에서, 화면 열세 장과 조각 넷을 거느린 앱이 템플릿을 어떻게 조직하는지를 읽는다.
페이지마다 같은 레이아웃을 씌우면서 이름 충돌을 피하는 Clone 패턴, 함수를 빌려주는 FuncMap, 사용자 입력을 안전하게 다루는 자동 이스케이프와 그 예외를 여는 덱 스토리의 마크다운, 템플릿을 실행 파일에 싣는 embed, 그리고 페이지 핸들러의 흐름과 템플릿 테스트까지 차례로 짚는다.

== 완성본의 템플릿 지도

먼저 파일 구성이다.
Flashcard의 템플릿은 `internal/web/templates/` 아래에 있고, 세 갈래로 나뉜다.
페이지 파일 13개(`pages/*.html`), 모든 페이지가 공유하는 공통 레이아웃 1개(`layout.html`), 여러 페이지가 나눠 쓰는 조각 4개(`partials/*.html`)가 전부다.
{ch-template-hello}의 최소 앱이 화면 파일 셋과 조각 하나였던 것과 비교하면 수가 늘었을 뿐 종류는 같다.
달라진 것은 이 파일들을 엮는 방식이고, 그 방식이 이 장의 내용이다.

엔진 선택도 짚어 두자.
Go 진영에도 선택지는 여럿 있다.
templ은 템플릿을 Go 코드로 컴파일해 필드 이름 오타를 컴파일 시점에 잡아 주고, quicktemplate은 속도를, pongo2는 Django풍 문법을 내세운다.
템플릿이 수십 장으로 늘고 여러 사람이 고치는 프로젝트라면 컴파일 검사를 해 주는 templ이 더 나을 수 있다.
Flashcard는 의존성이 늘지 않고 자동 이스케이프가 기본인 표준 라이브러리 html/template을 골랐다.
컴파일 검사가 없다는 약점은 이 장의 "템플릿도 테스트한다" 절에서 테스트로 메운다.

== 레이아웃과 조각: 공통 마크업은 한 번만 쓴다

홈, 덱 목록, 통계, 설정 어느 페이지를 열어도 상단 바와 하단 내비게이션은 같다.
이 마크업을 페이지 파일마다 복사해 두면 고칠 때마다 13곳을 손봐야 하므로, 공통 마크업은 `layout.html` 한 파일에만 쓰고 페이지는 저마다의 본문만 쓴다.

=== 액자와 그림: layout이 content를 불러들인다

쓰는 문법은 {ch-template-hello}에서 카드 한 줄을 조각으로 뗄 때 쓴 그 둘이다.
`{{define "이름"}} ... {{end}}`로 덩어리에 이름을 붙이고, `{{template "이름" 데이터}}`로 그 덩어리를 불러 그린다.
최소 앱은 이것으로 목록의 한 줄을 뗐지만, 완성본은 방향을 뒤집어 페이지 전체를 감싸는 데 쓴다.

`internal/web/templates/layout.html`이다.
HTML 문서의 기본 구조를 갖추고, 본문 자리에서 `content`라는 이름의 템플릿을 불러들인다.

[source,html]
----
{{define "layout"}}<!doctype html>
<html lang="ko">
<head>
  <meta charset="utf-8">
  <!-- ... -->
  <title>{{.Title}}</title>
  <link rel="stylesheet" href="{{asset "/static/app.css"}}">
  <script src="{{asset "/static/htmx.min.js"}}" defer></script>
</head>
<body>
<!-- ... -->
  <div class="frame">
    <!-- ... -->
    <main{{if .LoggedIn}} class="with-nav"{{end}}>
      {{template "content" .}}
    </main>
    {{if .LoggedIn}}
    <nav class="bottomnav">
      <div class="bottomnav-inner">
        <a class="navlink{{if eq .Path "/"}} active{{end}}" href="/">{{icon "home"}}홈</a>
        <a class="navlink{{if hasPrefix .Path "/decks"}} active{{end}}" href="/decks">{{icon "layers"}}덱</a>
        <!-- ... -->
      </div>
    </nav>
    {{end}}
  </div>
{{if .Flash}}
  <div class="toast"><div class="toast-msg {{.FlashKind}}">{{.Flash}}</div></div>
{{end}}
</body>
</html>{{end}}
----

`{{template "content" .}}`의 마지막 점은 "지금 내가 보고 있는 데이터를 그대로 넘겨준다"는 뜻이다.
그리고 `pages/` 아래의 페이지 파일 13개가 전부 `{{define "content"}}`로 시작한다.
레이아웃이 액자라면 각 페이지는 거기 끼우는 그림이고, `content`라는 이름이 끼우는 자리다.
최소 앱에서는 화면 파일마다 `<!doctype html>`부터 다시 적었는데, 화면이 열셋으로 늘면 그 반복이 상단 바 한 줄을 고치려고 파일 열세 개를 여는 일이 된다.

=== base를 복제하는 이유: Clone 패턴

여기서 문제가 하나 생긴다.
템플릿 집합 하나 안에서 같은 이름은 하나만 존재할 수 있는데, 페이지 파일 13개가 전부 `content`라는 이름을 쓴다.

여기서 파싱(parsing)이라는 말이 나온다.

.[용어 풀이] 파싱(parsing)
[NOTE]
====
텍스트를 읽어 그 구조를 프로그램이 다룰 수 있는 형태로 해석해 두는 일이다.
사람이 낯선 문장을 읽을 때 먼저 어디까지가 주어이고 어디부터가 서술어인지 가려내는 것과 같다.
템플릿 파싱은 `{{if}}`나 `{{range}}` 같은 표기가 어디서 시작해 어디서 끝나는지를 미리 해석해, 이제 데이터만 채우면 되는 상태로 준비해 두는 것이다.
컴파일러가 소스 코드를 읽을 때도, 브라우저가 HTML을 읽어 화면 구조를 만들 때도 가장 먼저 하는 일이 파싱이다.
====

Flashcard는 서버가 켜질 때 템플릿을 한 번만 파싱해 둔다.
요청이 올 때마다 파일을 다시 읽고 해석하는 일을 피하기 위해서다.
그런데 모든 파일을 한 집합에 파싱하면 마지막에 읽힌 `content`가 앞의 것들을 덮어써 버린다.
그래서 Flashcard는 레이아웃과 조각을 담은 공통 집합(base)을 두고, 페이지 수만큼 복제(Clone)한 뒤 복제본마다 페이지 파일 하나씩을 얹어 페이지마다 독립된 집합을 만든다.

`internal/web/render.go`의 파싱 코드다.
서버가 켜질 때 한 번 실행되어, 페이지 이름을 키로 하는 템플릿 맵을 만들어 둔다.

[source,go]
----
include::../../flashcard-advanced/internal/web/render.go[tag=parse-templates]
----

base 복제본에 `home.html`을 얹으면 그 안에서 `content`는 홈 화면 본문이 되고, `w.pages["home"]`은 "레이아웃 + 조각 + 홈 본문"을 갖춘 완성 집합이 된다.
`template.Must`는 파싱에 실패하면 그 자리에서 패닉을 일으킨다.
문법이 깨진 템플릿을 안고 조용히 기동하는 대신, 서버가 켜지는 순간 크게 실패하는 쪽을 택한 것이다.

=== render: 실행 시작점은 언제나 layout

파싱해 둔 템플릿을 실제로 그리는 함수는 `render`다.
핸들러가 페이지 이름을 건네면, 준비해 둔 맵에서 그 페이지의 템플릿 집합을 찾아 브라우저로 보낼 HTML 응답을 써 낸다.

`internal/web/render.go`:

[source,go]
----
include::../../flashcard-advanced/internal/web/render.go[tag=render]
----

`ExecuteTemplate`의 두 번째 인자가 `"layout"`이다.
어떤 페이지든 실행은 항상 레이아웃에서 시작하고, 레이아웃이 중간에 `content`를 불러들이는 구조다.
조각을 단독으로 그리는 `renderPartial`도 있는데, 페이지 일부만 갈아 끼우는 htmx 응답용이므로 {ch-htmx}에서 다룬다.

== FuncMap: 템플릿에 함수를 빌려준다

백분율을 구하거나, 날짜를 한국식으로 표기하거나, 카드 종류 코드 `word`를 "단어"로 바꾸는 일처럼 템플릿 안에서 계산이나 변환이 필요할 때가 있다.
이런 로직을 템플릿 문법으로 짜는 것은 무리이고, Go 함수를 등록해 템플릿에서 부르는 것이 정석이다.
그 등록부가 FuncMap이다.

`internal/web/funcs.go`의 등록부와 대표 함수 하나를 발췌했다.
앞의 블록은 템플릿에서 부를 이름과 실제 Go 함수를 짝지어 둔 목록이고, 뒤의 블록은 그중 하나인 `percent`로, 두 숫자를 받아 백분율을 계산해 돌려준다.

[source,go]
----
include::../../flashcard-advanced/internal/web/funcs.go[tag=func-map]

include::../../flashcard-advanced/internal/web/funcs.go[tag=percent]
----

방금 본 레이아웃의 `{{hasPrefix .Path "/decks"}}`가 등록된 함수 호출이었고, 통계 페이지의 `{{$p := percent .MatureCards .TotalCards}}`, 공유 갤러리의 `{{koDate .SharedAt}}`, 학습 카드의 `{{typeLabel .CardType}}`, 발음 기호 자리의 `{{orEmpty .Phonetic}}`도 마찬가지다.
왼쪽은 템플릿에서 부를 때 쓰는 이름이라 Go 함수 이름과 같을 필요가 없지만, 두 곳을 오가며 읽어야 하므로 같게 두었다.
`parseTemplates`에서 `Funcs(funcMap)`를 base에 걸어 두었기 때문에, base를 복제한 모든 페이지가 같은 함수들을 쓴다.

이 중 `icon`은 특별하다.
화면 곳곳의 아이콘 31개(집, 불꽃, 휴지통, 스피커 같은 것들)를 이미지 파일이나 아이콘 폰트(아이콘 그림들을 글꼴 파일 하나에 담아 배포하는 방식) 없이 인라인 SVG로 그리는 함수다.

.[용어 풀이] SVG와 인라인(Scalable Vector Graphics, inline)
[NOTE]
====
SVG는 그림을 픽셀의 색이 아니라 점과 선의 좌표로 적어 두는 형식이다.
좌표대로 그때그때 그리므로 아무리 확대해도 사진처럼 뭉개지지 않고, 내용이 결국 태그로 된 글자라서 HTML 문서 안에 그대로 써 넣을 수 있다.
이렇게 파일을 따로 두지 않고 문서 안에 직접 써 넣는 것을 인라인이라고 부른다.
인라인 SVG는 브라우저가 그림 파일을 따로 내려받지 않아도 되고, 색과 크기를 CSS로 바꿀 수 있다는 이점도 있다.
====

`internal/web/icons.go`:

[source,go]
----
func icon(name string) template.HTML {
	body, ok := icons[name]
	if !ok {
		return ""
	}
	return template.HTML(`<svg class="icon" viewBox="0 0 24 24" aria-hidden="true">` + body + `</svg>`)
}
----

반환 타입이 `string`이 아니라 `template.HTML`이라는 점이 핵심인데, 이 차이를 이해하려면 먼저 이스케이프 이야기를 해야 한다.

== 자동 이스케이프와 XSS: html/template이 기본인 이유

Go 표준 라이브러리에는 템플릿 패키지가 둘 있다.
text/template은 이름 그대로 일반 텍스트용이고, html/template은 같은 문법에 HTML을 위한 안전장치를 더한 것이다.
그 안전장치가 컨텍스트 자동 이스케이프(contextual auto-escaping)다.

왜 필요한지부터 보자.
Flashcard에서 카드의 원문과 뜻은 사용자가 입력하는 값이다.
누군가 카드 뜻에 `<script>...</script>`를 적어 넣고 덱을 공유하면, 이스케이프가 없는 세상에서는 그 공유 덱을 구경한 모든 사람의 브라우저에서 스크립트가 실행된다.
이것이 교차 사이트 스크립팅 공격이다.

.[용어 풀이] 이스케이프(Escape)와 XSS(교차 사이트 스크립팅)
[NOTE]
====
이스케이프는 특별한 의미를 지닌 문자를 의미 없는 표기로 바꿔 적는 일이다.
`<`를 `&lt;`로 바꿔 두면 브라우저는 태그의 시작이 아니라 그냥 부등호 글자로 읽는다.
XSS(Cross-Site Scripting)는 공격자가 입력란에 심어 둔 스크립트가 그 화면을 보는 다른 사용자의 브라우저에서 실행되는 공격이다.
사용자 입력을 화면에 되돌려 보여 주는 모든 웹 앱이 방어해야 하며, 이스케이프가 그 기본 방어다.
====

html/template은 `{{.Meaning}}` 같은 자리 표시의 값을 내보낼 때 위험한 문자를 자동으로 이스케이프한다.
카드 뜻에 `<b>중요</b>`를 입력해도 화면에 굵은 글씨가 나오지 않고 `<b>중요</b>`라는 글자 그대로 보이는 이유다.
개발자가 자리마다 기억해서 챙길 필요가 없으니, 잊어서 뚫릴 일도 없다.

"컨텍스트" 자동 이스케이프라는 이름에는 이유가 있다.
여기서 컨텍스트는 값이 놓인 자리, 즉 문맥을 뜻한다.
같은 값이라도 HTML의 어느 자리에 들어가느냐에 따라 위험한 문자가 다르기 때문에, html/template은 파싱하면서 각 자리 표시가 본문인지, 속성값인지, URL인지 파악해 두고 자리마다 맞는 이스케이프를 적용한다.
덱 목록 화면의 한 줄에는 그중 둘이 나온다.
`{{.Name}}`(본문)에는 태그 문자를 막는 HTML 이스케이프가, `href="/decks/{{.Slug}}"`(URL)에는 주소로 쓰기에 안전하게 만드는 URL 인코딩이 적용된다.
학습 화면 조각의 발음 듣기 버튼 `data-tts="{{$.TextTTS}}"`(속성값)에는 따옴표를 벗어나지 못하게 하는 속성 이스케이프가 적용된다.
템플릿을 쓰는 사람은 세 자리를 똑같이 `{{...}}`로 쓸 뿐이고, 구분은 엔진이 한다.

=== 이스케이프에 맡긴 결정: 스마트 덱 규칙 JSON

이 성질을 알고 나면 설계가 단순해지는 대목이 있다.
홈 화면의 추천 타일은 "오답률 높은 카드 복습하기" 같은 링크인데, 어떤 카드를 모을지 정하는 규칙을 JSON 문자열 그대로 쿼리 파라미터에 실어 보낸다.
예컨대 "오답률 높은 카드"라는 조건은 `minErrorRate` 같은 필드를 담은 JSON 한 줄이고, 링크는 `/study?rule=` 뒤에 그 글자들을 붙인 주소가 된다.
그런데 JSON에는 중괄호, 따옴표, 콜론처럼 URL에 그대로 둘 수 없는 문자가 가득해서, 누군가는 이 글자들을 주소용 표기로 바꿔야 한다.

핸들러에서 `url.QueryEscape`로 미리 인코딩해 두는 방법도 있지만, 그러면 인코딩 책임이 핸들러와 템플릿 두 곳에 흩어진다.
Flashcard는 값을 원문 그대로 넘기고 인코딩은 템플릿의 URL 문맥 이스케이프 한 곳에 맡긴 뒤, 그 결정을 구조체 주석으로 남겨 두었다.

`internal/web/home.go`:

[source,go]
----
type suggestionView struct {
	Title string
	Count int
	// Rule은 규칙 JSON 원문이다. 템플릿의 URL 컨텍스트가 /study?rule= 링크로
	// 이스케이프한다.
	Rule string
}
----

홈 템플릿(`home.html`)은 이 값을 `href="/study?mode=smart&rule={{.Rule}}"` 링크에 그대로 넣는다.
덱 목록 페이지의 저장된 스마트 덱도 같은 방식인데, 규칙이 데이터베이스에서 `json.RawMessage`(바이트 슬라이스) 타입으로 오는 점만 다르다.
바이트 슬라이스를 그대로 출력하면 숫자 나열이 되어 버리므로, 문자열로 바꿔 주기만 하는 한 줄짜리 함수 `ruleRaw`를 FuncMap에 등록했다(앞 절의 등록부에 있었다).
덱 목록 템플릿(`decks.html`)은 `href="/study?mode=smart&rule={{ruleRaw .Rule}}..."`처럼 쓴다.
인코딩은 여기서도 템플릿의 몫이다.

=== 이스케이프를 끄는 문: template.HTML

자동 이스케이프에도 뒷문이 하나 있다.
값의 타입이 `template.HTML`이면 엔진은 "이건 이미 안전한 HTML"이라 믿고 이스케이프 없이 내보낸다.
`icon` 함수의 반환 타입이 바로 이것이었다.
아이콘 SVG는 개발자가 소스 코드에 직접 적어 둔 문자열이라 사용자 입력이 섞일 여지가 없고, 이스케이프하면 그림이 아니라 태그 글자가 화면에 찍히므로 꺼야 한다.
규칙은 하나다.
`template.HTML`로 바꾸는 변환은 개발자가 통제하는 값에만 쓰고, 사용자 입력이 닿을 수 있는 값에는 절대 쓰지 않는다.

=== 사용자가 쓴 글을 HTML로 내보낼 때: 덱 스토리

방금 세운 규칙에 정면으로 걸리는 화면이 하나 있다.
덱 스토리, {ch-requirements}에서 기능만 소개한 그 글이다.
카드들이 나온 대화나 글 한 편을 덱마다 적어 둘 수 있게 한 것으로, 사용자는 그 글을 마크다운으로 쓴다.
소제목이나 대사 구분에 서식이 필요한데, 입력란에 서식 편집기를 붙이면 자바스크립트 라이브러리가 하나 늘기 때문이다.
사용자는 평범한 `<textarea>`에 기호로 서식을 적고, 서버가 그 원문을 HTML로 바꿔 덱 화면에 그린다.

문제는 그 마지막 단계다.
바꿔 놓은 HTML을 `{{.Data.StoryHTML}}`로 내보내려면 이스케이프를 꺼야 하고, 그러자면 값을 `template.HTML`로 감싸야 한다.
그런데 그 값의 출처는 사용자가 입력란에 적어 넣은 글이다.
"사용자 입력이 닿는 값에는 쓰지 않는다"를 그대로 어기는 모양이 된다.

해법은 변환기가 무엇까지 만들어 낼 수 있는지를 미리 좁혀 두는 것이다.
Flashcard가 쓰는 마크다운 변환기는 goldmark라는 라이브러리인데, 원문에 섞인 생 HTML을 결과에 그대로 통과시킬지 말지를 `html.WithUnsafe`라는 옵션 하나로 정한다.
이 옵션을 켜지 않으면 사용자가 `<script>`를 적어 넣어도 변환 과정에서 지워지고, 결과에 남는 것은 goldmark 자신이 만든 태그뿐이다.

다음은 그 변환기를 만들어 두는 `internal/web/markdown.go`다.
서버가 켜질 때 엔진 하나를 만들어 두고 모든 요청이 함께 쓴다.

[source,go]
----
include::../../flashcard-advanced/internal/web/markdown.go[tag=markdown-engine]
----

같은 파일의 `markdownHTML` 함수가 이 엔진으로 원문을 바꾼 뒤 결과를 `template.HTML(buf.String())`로 감싸 돌려준다.
`template.HTML`을 써도 되는 근거가 "이 값을 누가 적었는가"에서 "이 문자열을 만들어 낸 코드가 무엇까지 낼 수 있는가"로 옮겨 갔다.
그래서 앞 소절의 규칙은 이렇게 다시 적는 편이 정확하다.
`template.HTML`은 그 문자열을 만들어 낸 코드가 안전을 책임질 수 있을 때만 쓴다.
아이콘 SVG는 개발자가 소스에 직접 적어 두었고, 스토리 HTML은 변환기가 낼 수 있는 태그의 범위가 정해져 있어서 각각 그 조건을 만족한다.

이 화면을 만들며 정한 것이 둘 더 있다.
첫째, 변환을 브라우저가 아니라 서버에서 한다.
브라우저에서 바꾸려면 마크다운 라이브러리를 자바스크립트로 하나 들여야 하는데, 읽어야 할 언어를 늘리지 않기로 한 {ch-requirements}의 조건과 어긋난다.
Go 라이브러리를 쓰면 {ch-code-map}에서 본 go.mod에 의존성 한 줄이 느는 것으로 끝난다.
둘째, 데이터베이스에는 변환 결과가 아니라 마크다운 원문만 저장한다({ch-database-design}에서 본 `decks` 테이블의 `story` 칼럼이다).
바꿔 둔 HTML을 저장해 두면 화면을 그릴 때마다 변환하는 비용은 아끼지만, 변환 규칙을 바꾸는 날 예전 결과가 그대로 남는다.
마크다운 원문이 단일 출처이고, HTML은 그때그때 계산하는 값이다.

편집 화면에는 미리 보기 버튼도 있다.
저장하기 전에 서식이 어떻게 나오는지 확인하는 버튼인데, 누르면 입력란의 원문이 서버로 가고 방금 본 그 함수가 만든 HTML 조각이 화면에 끼워진다.
저장된 스토리를 그리는 코드와 미리 보기를 그리는 코드가 하나라 둘이 어긋날 수 없다.
화면 일부만 이렇게 갈아 끼우는 방식은 다음 {ch-htmx}에서 다룬다.

== embed: 템플릿을 실행 파일에 싣는다

`parseTemplates`가 읽는 `templateFS`는 디스크의 폴더가 아니다.
Go의 embed 기능으로 실행 파일 안에 넣어 둔 파일들이다.

`internal/web/web.go`의 선언부다.
주석 두 줄로 templates 폴더와 static 폴더 전체가 컴파일 결과물에 들어간다.

[source,go]
----
//go:embed templates
var templateFS embed.FS

//go:embed static
var staticFS embed.FS
----

.[용어 풀이] embed(Go)
[NOTE]
====
Go 컴파일러가 소스 코드 옆의 파일(HTML, CSS, 이미지 등)을 실행 파일 안에 통째로 넣어 주는 기능이다.
`//go:embed` 주석 한 줄로 켠다.
프로그램은 디스크가 아니라 자기 몸 안에서 그 파일을 읽는다.
서버를 옮길 때 실행 파일 하나만 복사하면 되고, 템플릿 파일을 빠뜨린 채 배포하는 사고가 원천적으로 사라진다.
====

대안은 실행 시점에 디스크에서 읽는 것이다.
템플릿만 고치면 서버 재시작 없이 반영되므로, 화면을 수시로 고치는 디자이너가 따로 있는 팀이라면 그쪽이 낫다.
대신 배포할 때 실행 파일과 템플릿 폴더의 짝이 맞는지를 사람이 챙겨야 한다.
Flashcard는 배포 산출물이 "실행 파일 하나"로 끝나는 단순함을 택해 embed를 골랐다.
로컬의 `go run ./cmd/server`와 4부에서 배포할 Vercel 함수가 완전히 같은 템플릿과 CSS를 보게 되므로, "내 컴퓨터에서는 되는데" 부류의 문제에서 자산 불일치가 빠진다.
이 구조가 배포에서 어떤 의미인지는 {ch-vercel}에서 다시 본다.

embed된 정적 자산을 브라우저에 내보내는 코드도 표준 라이브러리 조합이다.
`static/` 아래에는 파일 일곱 개(`app.css`, `app.js`, `htmx.min.js`, `sw.js`, `manifest.webmanifest`, `offline.html`, `favicon.ico`)와 앱 아이콘 PNG 세 장이 든 `icons/` 폴더가 있다.

`internal/web/routes.go`:

[source,go]
----
func (w *Web) registerStatic(r *gin.Engine) {
	static, err := fs.Sub(staticFS, "static")
	if err != nil {
		panic(err)
	}
	server := http.FileServer(http.FS(static))
	// ...
	r.GET("/static/*filepath", func(c *gin.Context) {
		// ... 캐시 헤더는 38장에서 본다 ...
		c.Request.URL.Path = "/" + strings.TrimPrefix(c.Param("filepath"), "/")
		server.ServeHTTP(c.Writer, c.Request)
	})
	// ...
}
----

`fs.Sub`로 embed 파일 시스템에서 static 폴더를 잘라 내고, 표준 라이브러리의 파일 서버를 Gin 라우트에 물리는 것이 전부다.

== 페이지 핸들러의 흐름

부품이 다 모였으니 요청 하나가 화면이 되기까지를 따라가 보자.
{ch-gin}의 API 핸들러가 "요청을 읽고, 스토어를 다녀와서, JSON으로 응답"이었다면, 페이지 핸들러는 마지막 단계만 "템플릿 렌더링"으로 바뀐다.

=== view 구조체: 모든 페이지의 공통 데이터

레이아웃은 어느 페이지에서든 제목, 현재 경로, 로그인 여부 같은 값이 필요하므로, 모든 템플릿 실행의 뿌리 데이터를 이 공통 필드를 갖춘 `view` 구조체 하나로 통일했다.

`internal/web/render.go`:

[source,go]
----
// view는 모든 템플릿이 실행 대상으로 받는 뿌리 객체다.
type view struct {
	Title     string
	Path      string // 요청 경로. 하단 내비의 활성 탭을 정한다
	LoggedIn  bool
	LocalMode bool
	Email     string
	Flash     string
	FlashKind string
	Data      any
}
----

앞쪽 필드들은 레이아웃이 쓰고, 페이지 본문마다 다른 데이터는 전부 `Data`에 담는다.
타입이 `any`이므로 무엇이든 담을 수 있고, `internal/web/home.go`의 홈 핸들러는 여기에 `gin.H`(문자열 키 맵)를 담는다.

[source,go]
----
w.render(c, http.StatusOK, "home", "Flashcard", gin.H{
	"Due":         due,
	"Streak":      summary.Streak,
	"Decks":       decks,
	"Suggestions": suggestions,
})
----

홈 화면 템플릿이 `{{.Data.Due}}`라고 적어 둔 값이 여기서 끝까지 연결된다.
핸들러가 스토어에서 계산해 맵에 담은 `Due`가, `view.Data`를 거쳐, 홈 화면의 "오늘 복습할 카드 N장"이 된다.
`Data` 한 칸을 두고 페이지마다 다른 것을 담는 이 방식은, 화면이 늘어도 뿌리 데이터의 타입을 하나로 유지하려는 선택이다.

=== 폼 처리와 PRG 패턴

화면에서 무언가를 만드는 것은 폼 제출, 즉 POST다.
`internal/web/decks.go`의 덱 생성 핸들러를 보자.
폼 필드를 읽고, 검증하고, 저장한 뒤, 완성된 화면을 그리는 대신 다른 주소로 이동시킨다.

[source,go]
----
func (w *Web) createDeck(c *gin.Context) {
	name := strings.TrimSpace(c.PostForm("name"))
	if name == "" {
		redirectWithFlash(c, flashError, "덱 이름을 입력해주세요", "/decks")
		return
	}
	deck, err := w.store.CreateDeck(c.Request.Context(), auth.UserID(c), name, nil)
	if err != nil {
		w.failPage(c, err)
		return
	}
	c.Redirect(http.StatusSeeOther, "/decks/"+deck.Slug)
}
----

`c.PostForm("name")`은 폼의 `<input name="name">` 값을 꺼낸다.
{ch-gin}의 JSON 바인딩과 하는 일은 같고, 데이터가 JSON 본문 대신 폼 인코딩으로 온다는 점만 다르다.
검증에 실패한 경로가 부르는 `redirectWithFlash`는 안내 문구를 남기고 목록으로 이동시키는 헬퍼인데, 그 속은 다음 소절에서 연다.

주목할 부분은 성공했을 때 `render`가 아니라 `c.Redirect`를 부른다는 것이다.
{ch-gin-hello·template-hello}에서 최소 앱의 폼들이 저장을 마치고 303으로 답하던 그 모양이고, 이름과 사연을 여기서 붙인다.
리다이렉트(redirect)는 결과 화면을 그리는 대신 "이 주소로 다시 가 보라"고 답해 브라우저를 다른 주소로 보내는 응답이다.
POST로 처리만 하고 곧장 GET 주소로 이동시키는 오래된 관례, 즉 Post/Redirect/Get(줄여서 PRG) 패턴을 따른 것이다.
상태 코드도 "다음 요청은 GET으로 하라"는 뜻의 303 See Other(`http.StatusSeeOther`)를 쓴다.

.[용어 풀이] PRG 패턴(Post/Redirect/Get)
[NOTE]
====
폼을 받은 POST 핸들러가 결과 화면을 직접 그리지 않고, 처리만 마친 뒤 GET 주소로 브라우저를 이동시키는 관례다.
POST 응답으로 그린 화면에서 사용자가 새로고침을 누르면 브라우저는 "양식을 다시 제출하시겠습니까?"라고 묻고, 수락하는 순간 같은 덱이 하나 더 만들어진다.
이동한 뒤의 화면은 평범한 GET 결과라 몇 번을 새로 고쳐도 조회만 반복된다.
글 등록이나 결제처럼 두 번 실행되면 곤란한 처리에는 거의 예외 없이 쓴다.
====

=== 플래시 메시지: 리다이렉트를 건너가는 한 줄

PRG에는 부작용이 하나 있다.
안내를 그려야 할 화면은 리다이렉트 다음의 GET 요청이 만든다.
그런데 HTTP는 무상태라 그 요청은 직전 POST에서 무슨 일이 있었는지 모르므로, "덱을 삭제했어요" 같은 안내를 전할 길이 끊긴다.
Flashcard는 수명이 60초인 쿠키로 이 틈을 잇는다.
쿠키(cookie)는 서버가 브라우저에 맡겨 두는 작은 쪽지다.
브라우저가 이 쪽지를 다음 요청부터 자동으로 함께 보내 주므로, 리다이렉트 뒤의 GET 요청에도 직전 POST가 남긴 안내가 딸려 온다.
이렇게 전달하는 한 줄짜리 안내를 플래시 메시지(flash message)라고 부른다.

.[용어 풀이] 플래시 메시지(flash message)
[NOTE]
====
다음 화면에 딱 한 번만 보여 주고 사라지는 안내 문구다.
"저장했어요"나 "덱을 삭제했어요"처럼 방금 끝난 처리의 결과를 알리는 데 쓴다.
남긴 쪽이 아니라 그다음 요청을 처리하는 쪽이 꺼내 쓰고 곧바로 지우기 때문에, 한 번 번쩍이고 만다는 뜻의 이름이 붙었다.
PRG 패턴에서 POST가 남긴 말을 리다이렉트 건너편 화면까지 전하는 통로여서, 웹 프레임워크 대부분에 같은 이름의 기능이 있다.
====

다음 코드는 안내 문구를 쿠키에 적어 두는 `setFlash`, 그것을 남긴 뒤 곧장 303으로 보내는 `redirectWithFlash`, 다음 요청에서 그 문구를 꺼내 읽고 곧바로 지우는 `takeFlash`다.
`createDeck`의 검증 실패 경로가 불렀던 것이 이 `redirectWithFlash`이고, 종류를 날 문자열 대신 `flashInfo`·`flashError` 상수로 받아 오타를 막는다.

`internal/web/cookies.go`:

[source,go]
----
// 플래시 메시지는 짧은 수명의 쿠키로 리다이렉트 한 번을 살아남는다.

// 플래시 종류. 템플릿이 이 값을 그대로 CSS 클래스로 쓴다.
const (
	flashInfo  = "info"
	flashError = "error"
)

func setFlash(c *gin.Context, kind, message string) {
	setCookie(c, flashCookie, kind+"|"+message, 60)
}

// redirectWithFlash는 모든 폼 핸들러가 공유하는 PRG(Post/Redirect/Get)
// 마무리다. 한 번짜리 메시지를 남기고 303으로 보내므로 새로고침해도 폼이
// 다시 제출되지 않는다.
func redirectWithFlash(c *gin.Context, kind, message, path string) {
	setFlash(c, kind, message)
	c.Redirect(http.StatusSeeOther, path)
}

// takeFlash는 대기 중인 플래시 메시지를 읽고 지운다.
func takeFlash(c *gin.Context) (kind, message string) {
	raw := cookieValue(c, flashCookie)
	if raw == "" {
		return "", ""
	}
	clearCookie(c, flashCookie)
	kind, message, ok := strings.Cut(raw, "|")
	if !ok {
		return flashInfo, raw
	}
	return kind, message
}
----

`takeFlash`가 꺼낸 메시지는 `view.Flash`에 담기고, 레이아웃 발췌의 마지막에 있던 `{{if .Flash}}` 블록이 화면 위에 토스트로 띄운다.
토스트(toast)는 화면 한쪽에 잠깐 떴다가 스스로 사라지는 알림 상자를 부르는 이름으로, 빵이 토스터에서 튀어 오르는 모습에서 왔다.
레이아웃은 모든 페이지의 공통이므로 어디로 리다이렉트하든 플래시는 보인다.
쿠키라는 저장소 자체와 로그인 유지에 쓰는 방법은 4부의 {ch-supabase-auth}에서 자세히 다룬다.

== 템플릿도 테스트한다

이 장 첫머리에서 html/template의 약점으로 미룬 것이 있다.
템플릿 안의 오타는 컴파일러가 잡아 주지 않아서, `{{.Naem}}`이라고 잘못 써도 `go build`는 통과한다.
문법이 깨진 것은 파싱 때, 없는 필드를 참조한 것은 그 페이지를 렌더링할 때에야 드러난다.

그래서 템플릿에도 테스트를 둔다.
파싱은 `New`가 내부(`parseTemplates`)에서 `template.Must`로 검증하므로, `New`를 호출하는 것만으로 전체 템플릿의 문법 검사가 된다.
렌더링은 대표 데이터를 넣어 실제로 그려 본다.
`template.Must`는 파싱이 실패하면 그 자리에서 패닉을 일으키고, 테스트 안에서 난 패닉은 그 테스트의 실패로 기록되기 때문이다.
`internal/web/templates_test.go`는 페이지 파일 13개가 모두 파싱됐는지 확인하고, 가장 복잡한 학습 화면 조각을 국면(phase)마다 실제로 렌더링해 본다.

[source,go]
----
func TestTemplatesParse(t *testing.T) {
	w := New(&config.Config{AuthMode: "local"}, nil)

	expected := []string{
		"home", "decks", "deck", "card_form", "study", "study_direction",
		// ...
	}
	for _, name := range expected {
		if _, ok := w.pages[name]; !ok {
			t.Errorf("page template %q missing", name)
		}
	}
	// ...
	for _, v := range []studyBodyView{
		{Phase: "studying", State: state, Card: card, TextTTS: "test", BackTTS: "test"},
		{Phase: "break", State: state},
		{Phase: "finished", State: state},
		{Phase: "empty", State: state},
	} {
		var sb strings.Builder
		if err := w.partials.ExecuteTemplate(&sb, "study_body", v); err != nil {
			t.Errorf("study_body phase %s: %v", v.Phase, err)
		}
		// ...
	}
	// ...
}
----

화면이 의도대로 예쁜지까지 검사하지는 않고, "깨지지 않고 그려진다"만 확인하는 이른바 스모크 테스트(smoke test)다.
그 정도만으로도 필드 이름 오타나 조각 이름 변경 같은 흔한 실수는 배포 전에 걸러지고, {ch-unit-tests}에서 만든 `go test ./...` 한 번에 같이 돈다.
컴파일형 엔진이 잡아 주는 것 가운데 문법 오류는 이 테스트가 파일 13개 전부에서 잡고, 없는 필드 참조는 실제로 그려 본 화면(학습 화면 조각의 네 국면)에서만 잡는다.
그려 보지 않은 화면의 필드 오타는 {ch-app-tests}에서 앱을 띄워 화면들을 실제로 요청해 보는 통합 테스트가 이어받는다.

== 에이전트 활용 아이디어

템플릿 층을 에이전트와 함께 다룰 때의 요령이다.

`CLAUDE.md`에는 템플릿 구조 규약을 적는다.
"페이지는 pages/, 여러 페이지가 쓰는 조각은 partials/에 두고 `layout.html`은 최소로만 고친다", "새 정적 파일은 embed 대상 디렉터리 안에 둔다"가 후보다.
모든 페이지가 `content`라는 같은 블록 이름을 쓰는 구조처럼 이 저장소 특유의 규칙은 일반 지식으로 예측할 수 없으므로, 명시할 가치가 크다.

템플릿은 컴파일 검사가 약한 영역이라는 점을 지시로 보완한다.
필드 이름을 잘못 참조해도 실행 전에는 드러나지 않을 수 있으므로, "수정 후 `go test ./internal/web`으로 템플릿 파싱 테스트를 돌려 확인하라"를 지시문의 마지막 줄로 굳혀 둔다.
{ch-quality-gates}에서 보겠지만, 이런 반복 지시는 결국 훅이나 스킬로 옮기는 것이 정답이다.

새 화면을 붙일 때는 "덱 상세 페이지와 같은 구조로"처럼 기존 페이지를 본보기로 지목하면, 레이아웃 연결과 조각 분리 관례가 함께 복제된다.

== 정리

이번 장에서는 {ch-template-hello}에서 익힌 템플릿 문법 위에서, 화면 열세 장짜리 앱이 템플릿을 조직하는 방법을 살펴봤다.

구조는 액자와 그림이다.
`layout.html`이 페이지 본문(`content`)을 감싼다.
페이지 파일 13개가 같은 이름을 쓰는 데서 오는 충돌은 base를 페이지마다 복제하는 Clone 패턴으로 풀었고, 템플릿에 부족한 계산력은 FuncMap으로 메웠다.
컨텍스트 자동 이스케이프는 사용자 입력의 XSS를 기본값으로 막고 본문·속성·URL 문맥을 스스로 구분한다.
스마트 덱 규칙 JSON의 인코딩을 템플릿에 맡긴 결정과 `template.HTML`이라는 예외의 문은 그 문자열을 만든 코드가 안전을 책임질 수 있을 때만 연다는 규칙도 짚었다.
사용자가 쓴 마크다운을 서버에서 HTML로 바꿔 내보내는 덱 스토리가 그 조건을 어떻게 지키는지도 함께 봤다.
템플릿과 정적 자산은 embed로 실행 파일에 실려, 로컬과 배포 환경이 같은 자산을 본다.

페이지 핸들러의 기본 구조는 {ch-gin}의 API 핸들러와 같았다.
`view` 구조체에 페이지 데이터를 담아 렌더링하고, 폼 POST는 PRG 패턴으로 중복 제출을 막았다.
안내 문구는 플래시 쿠키로 리다이렉트를 건너 전달하고, 컴파일러가 못 잡는 템플릿 오타는 스모크 테스트로 걸렀다.

한 가지 눈치챘을지 모르겠다.
이 장의 화면 전환은 전부 링크 이동과 폼 제출, 즉 전체 페이지 새로고침이다.
2부의 최소 앱이 남긴 아쉬움이 규모만 커진 채 그대로 있다.
카드 한 장을 삭제할 때 페이지 전체를 다시 그리는 대신 그 타일 하나만 사라지게 할 수는 없을까.
레이아웃 발췌가 읽어 들이던 `htmx.min.js`에 그 답이 들어 있다.
다음 {ch-htmx}에서는 자바스크립트를 직접 쓰지 않고도 화면 일부만 갈아 끼우는 htmx를 살펴보겠다.
