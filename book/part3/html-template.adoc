= html/template 깊이 보기: 레이아웃 복제와 자동 이스케이프

데이터베이스에서 꺼낸 덱 목록을 HTML에 채워 넣는 것은 서버다.
Go 표준 라이브러리 html/template이 HTML 양식에 데이터를 채워 완성된 화면을 만들고, 브라우저는 받은 그대로 그린다(그 이유는 {ch-tech-choices}).
문법은 {ch-template-hello}에서 익혔으므로, 이 장은 화면 {n-page-count-ko-attr} 장과 조각 넷을 거느린 앱이 템플릿을 어떻게 조직하는지를 읽는다.
레이아웃을 씌우는 Clone 패턴과 FuncMap, 자동 이스케이프와 그 예외인 덱 스토리, 그리고 embed와 페이지 핸들러, 템플릿 테스트 순서로 짚는다.

== 완성본의 템플릿 지도

Flashcard의 템플릿은 `internal/web/templates/` 아래에 세 갈래로 나뉜다.
페이지 파일 {n-page-count}개(`pages/*.html`), 모든 페이지가 공유하는 레이아웃 1개(`layout.html`), 여러 페이지가 나눠 쓰는 조각 4개(`partials/*.html`)다.

Go 진영에도 템플릿 엔진은 여럿 있다.
templ은 템플릿을 Go 코드로 컴파일해 필드 이름 오타를 컴파일 시점에 잡아 주고, quicktemplate은 속도를, pongo2는 Django풍 문법을 내세운다.
템플릿이 수십 장으로 늘고 여러 사람이 고치는 프로젝트라면 templ이 더 나을 수 있다.
Flashcard는 의존성이 늘지 않고 자동 이스케이프가 기본인 html/template을 골랐다.
컴파일 검사가 없다는 약점은 "템플릿도 테스트한다" 절에서 테스트로 메운다.

== 레이아웃과 조각: 공통 마크업은 한 번만 쓴다

어느 페이지를 열어도 상단 바와 하단 내비게이션은 같다.
페이지마다 복사해 두면 고칠 때마다 모든 페이지를 손봐야 하므로, 공통 마크업은 `layout.html`에만 쓰고 페이지 파일에는 본문만 쓴다.

=== 액자와 그림: layout이 content를 불러들인다

최소 앱이 목록의 한 줄을 떼는 데 쓴 `{{define}}`과 `{{template}}`을, 완성본은 방향을 뒤집어 페이지 전체를 감싸는 데 쓴다.

`internal/web/templates/layout.html`은 HTML 문서의 기본 구조를 갖추고, 본문 자리에서 `content`라는 이름의 템플릿을 불러들인다.

[source,html]
----
{{define "layout"}}<!doctype html>
<html lang="ko">
<head>
  <meta charset="utf-8">
  <!-- ... -->
  <title>{{.Title}}</title>
  <link rel="stylesheet" href="{{asset "/static/app.css"}}">
  <script src="{{asset "/static/htmx.min.js"}}" defer></script>
</head>
<body>
<!-- ... -->
  <div class="frame">
    <!-- ... -->
    <main{{if .LoggedIn}} class="with-nav"{{end}}>
      {{template "content" .}}
    </main>
    {{if .LoggedIn}}
    <nav class="bottomnav">
      <div class="bottomnav-inner">
        <a class="navlink{{if eq .Path "/"}} active{{end}}" href="/">{{icon "home"}}홈</a>
        <a class="navlink{{if hasPrefix .Path "/decks"}} active{{end}}" href="/decks">{{icon "layers"}}덱</a>
        <!-- ... -->
      </div>
    </nav>
    {{end}}
  </div>
{{if .Flash}}
  <div class="toast"><div class="toast-msg {{.FlashKind}}">{{.Flash}}</div></div>
{{end}}
</body>
</html>{{end}}
----

`{{template "content" .}}`의 마지막 점은 지금 보고 있는 데이터를 그대로 넘겨준다는 뜻이다.
`pages/` 아래의 페이지 파일은 전부 `{{define "content"}}`로 시작한다.
레이아웃이 액자라면 각 페이지는 거기 끼우는 그림이고, `content`라는 이름이 끼우는 자리다.

=== base를 복제하는 이유: Clone 패턴

html/template은 서로 불러 쓰는 템플릿들을 템플릿 집합이라는 한 묶음으로 관리한다.
한 집합 안에서는 같은 이름을 하나만 쓸 수 있는데, 페이지 파일 {n-page-count}개가 전부 `content`라는 이름을 쓴다.
Flashcard는 요청마다 파일을 다시 해석하지 않도록 서버가 켜질 때 템플릿을 한 번만 파싱해 두는데, 모든 파일을 한 집합에 파싱하면 마지막에 읽힌 `content`가 앞의 것들을 덮어쓴다.

.[용어 풀이] 파싱(parsing)
[NOTE]
====
텍스트를 읽어 그 구조를 프로그램이 다룰 수 있는 형태로 해석해 두는 일이다.
템플릿 파싱은 `{{if}}`나 `{{range}}` 같은 표기가 어디서 시작해 어디서 끝나는지를 미리 해석해, 데이터만 채우면 되는 상태로 준비해 두는 것이다.
컴파일러가 소스 코드를 읽을 때도, 브라우저가 HTML을 읽을 때도 가장 먼저 하는 일이 파싱이다.
====

그래서 레이아웃과 조각을 담은 공통 집합(base)을 두고 페이지 수만큼 복제(Clone)한 뒤, 복제본마다 페이지 파일을 하나씩 얹는다.

다음은 서버가 켜질 때 한 번 실행되어 페이지 이름을 키로 하는 템플릿 맵을 만드는 `internal/web/render.go`의 파싱 코드다.

[source,go]
----
include::../../flashcard-advanced/internal/web/render.go[tag=parse-templates]
----

base 복제본에 `home.html`을 얹으면 `w.pages["home"]`은 "레이아웃 + 조각 + 홈 본문"을 갖춘 완성 집합이 된다.
`template.Must`는 파싱에 실패하면 그 자리에서 패닉을 일으킨다.
문법이 깨진 템플릿을 안고 조용히 기동하는 대신, 서버가 켜지는 순간 크게 실패하는 쪽을 택한 것이다.

조각만 단독으로 그리는 `renderPartial`은 htmx 응답용이라 {ch-htmx}에서 다룬다.

== FuncMap: 템플릿에 함수를 빌려준다

백분율 계산, 날짜의 한국식 표기, 카드 종류 코드 `word`를 "단어"로 바꾸는 일처럼 템플릿 안에서 계산이나 변환이 필요할 때가 있다.
이런 로직은 템플릿 문법으로 짜지 않고 Go 함수를 등록해 부르는 것이 정석이고, 그 등록부가 FuncMap이다.

`internal/web/funcs.go`에서 발췌한 앞의 블록은 템플릿에서 부를 이름과 Go 함수를 짝지은 목록이고, 뒤의 블록은 두 숫자로 백분율을 계산하는 `percent`다.

----

include::../../flashcard-advanced/internal/web/funcs.go[tag=percent]
----

레이아웃의 `{{hasPrefix .Path "/decks"}}`가 등록된 함수 호출이었고, 통계 페이지의 `{{$p := percent .MatureCards .TotalCards}}`, 공유 갤러리의 `{{koDate .SharedAt}}`, 학습 카드의 `{{typeLabel .CardType}}`도 마찬가지다.
`parseTemplates`가 base에 `Funcs(funcMap)`를 걸어 두었으므로, base를 복제한 모든 페이지가 같은 함수를 쓴다.

이 중 `icon`은 화면 곳곳의 아이콘 31개(집, 불꽃, 휴지통 같은 것들)를 이미지 파일이나 아이콘 폰트(아이콘 그림들을 글꼴 파일 하나에 담는 방식) 없이 인라인 SVG로 그리는 함수다.

.[용어 풀이] SVG와 인라인(Scalable Vector Graphics, inline)
[NOTE]
====
SVG는 그림을 픽셀의 색이 아니라 점과 선의 좌표로 적어 두는 형식이라, 아무리 확대해도 뭉개지지 않는다.
내용이 태그로 된 글자여서 HTML 문서 안에 직접 써 넣을 수 있고, 이렇게 파일을 따로 두지 않는 것을 인라인이라고 부른다.
인라인 SVG는 따로 내려받을 파일이 없고 색과 크기를 CSS로 바꿀 수 있다.
====

`internal/web/icons.go`:

[source,go]
----
func icon(name string) template.HTML {
	body, ok := icons[name]
	if !ok {
		return ""
	}
	return template.HTML(`<svg class="icon" viewBox="0 0 24 24" aria-hidden="true">` + body + `</svg>`)
}
----

반환 타입이 `string`이 아니라 `template.HTML`이라는 점은 이스케이프를 본 뒤에 다시 다룬다.

== 자동 이스케이프와 XSS: html/template이 기본인 이유

Go 표준 라이브러리의 템플릿 패키지는 둘이다.
text/template은 일반 텍스트용이고, html/template은 같은 문법에 HTML을 위한 안전장치인 컨텍스트 자동 이스케이프(contextual auto-escaping)를 더한 것이다.

카드의 원문과 뜻은 사용자가 입력하는 값이다.
누군가 카드 뜻에 `<script>...</script>`를 적어 넣고 덱을 공유했는데 이스케이프가 없다면, 그 덱을 구경한 모든 사람의 브라우저에서 스크립트가 실행된다(교차 사이트 스크립팅 공격).

.[용어 풀이] 이스케이프(Escape)와 XSS(교차 사이트 스크립팅)
[NOTE]
====
이스케이프는 특별한 의미를 지닌 문자를 의미 없는 표기로 바꿔 적는 일이다.
`<`를 `&lt;`로 바꿔 두면 브라우저는 태그의 시작이 아니라 부등호 글자로 읽는다.
XSS(Cross-Site Scripting)는 공격자가 입력란에 심어 둔 스크립트가 다른 사용자의 브라우저에서 실행되는 공격이고, 이스케이프가 그 기본 방어다.
====

html/template은 `{{.Meaning}}` 같은 자리의 값을 내보낼 때 위험한 문자를 자동으로 이스케이프한다.
카드 뜻에 `<b>중요</b>`를 입력해도 굵은 글씨가 아니라 글자 그대로 보이고, 개발자가 자리마다 챙길 필요가 없으니 잊어서 뚫릴 일도 없다.

여기서 컨텍스트는 값이 놓인 자리를 뜻한다.
같은 값이라도 HTML의 어느 자리에 들어가느냐에 따라 위험한 문자가 다르므로, html/template은 파싱하면서 각 자리가 본문인지, 속성값인지, URL인지 파악해 자리마다 맞는 이스케이프를 적용한다.
덱 목록 한 줄의 `{{.Name}}`(본문)에는 HTML 이스케이프가, `href="/decks/{{.Slug}}"`(URL)에는 URL 인코딩이 적용된다.
학습 화면의 발음 듣기 버튼 `data-tts="{{$.TextTTS}}"`(속성값)에는 따옴표를 벗어나지 못하게 하는 속성 이스케이프가 적용된다.

=== 이스케이프에 맡긴 결정: 스마트 덱 규칙 JSON

이 성질 덕분에 단순해진 설계가 있다.
홈 화면의 추천 타일은 "오답률 높은 카드 복습하기" 같은 링크인데, 어떤 카드를 모을지 정하는 규칙을 JSON 문자열 그대로 `/study?rule=` 뒤에 실어 보낸다.
JSON에는 중괄호, 따옴표, 콜론처럼 URL에 그대로 둘 수 없는 문자가 가득해서, 누군가는 이 글자들을 주소용 표기로 바꿔야 한다.

핸들러에서 `url.QueryEscape`로 미리 인코딩할 수도 있지만, 그러면 인코딩 책임이 핸들러와 템플릿 두 곳에 흩어진다.
Flashcard는 값을 원문 그대로 넘기고 인코딩은 템플릿의 URL 문맥 이스케이프에 맡긴 뒤, 그 결정을 `internal/web/home.go`의 `suggestionView` 구조체 주석으로 남겼다.
홈 템플릿(`home.html`)은 이 값을 `href="/study?mode=smart&rule={{.Rule}}"`에 그대로 넣는다.
덱 목록의 저장된 스마트 덱도 같은 방식인데, 규칙이 데이터베이스에서 `json.RawMessage`(바이트 슬라이스)로 온다.
그대로 출력하면 숫자 나열이 되므로 문자열로 바꿔 주기만 하는 `ruleRaw`를 FuncMap에 등록해 `{{ruleRaw .Rule}}`처럼 쓰고, 인코딩은 여기서도 템플릿의 몫이다.

=== 이스케이프를 끄는 문: template.HTML

값의 타입이 `template.HTML`이면 엔진은 이미 안전한 HTML이라 믿고 이스케이프 없이 내보낸다.
`icon` 함수의 반환 타입이 이것이었다.
아이콘 SVG는 개발자가 소스에 직접 적은 문자열이라 사용자 입력이 섞일 여지가 없고, 이스케이프하면 그림 대신 태그 글자가 찍히므로 꺼야 한다.
그래서 `template.HTML` 변환은 개발자가 통제하는 값에만 쓰고, 사용자 입력이 닿을 수 있는 값에는 쓰지 않는다.

=== 사용자가 쓴 글을 HTML로 내보낼 때: 덱 스토리

이 규칙에 정면으로 걸리는 화면이 덱 스토리다.
{ch-requirements}에서 소개한, 카드들이 나온 대화나 글 한 편을 덱마다 적어 두는 기능이고, 사용자는 그 글을 마크다운으로 쓴다.
서식 편집기를 붙이면 자바스크립트 라이브러리가 하나 늘므로, 사용자는 평범한 `<textarea>`에 기호로 서식을 적고 서버가 그 원문을 HTML로 바꿔 그린다.
바꾼 HTML을 `{{.Data.StoryHTML}}`로 내보내려면 `template.HTML`로 감싸야 하는데, 그 값의 출처는 사용자가 적은 글이라 방금 세운 규칙을 어긴다.

해법은 변환기가 만들어 낼 수 있는 것을 미리 좁혀 두는 것이다.
Flashcard가 쓰는 마크다운 변환기 goldmark는 원문에 섞인 생 HTML을 통과시킬지를 `html.WithUnsafe` 옵션 하나로 정한다.
이 옵션을 켜지 않으면 사용자가 적은 `<script>`는 변환 과정에서 지워지고, 결과에는 goldmark 자신이 만든 태그만 남는다.

다음 `internal/web/markdown.go`는 서버가 켜질 때 변환 엔진 하나를 만들어 모든 요청이 함께 쓰게 한다.

[source,go]
----
include::../../flashcard-advanced/internal/web/markdown.go[tag=markdown-engine]
----

같은 파일의 `markdownHTML`이 이 엔진으로 원문을 바꾼 뒤 결과를 `template.HTML(buf.String())`로 감싸 돌려준다.
`template.HTML`을 써도 되는 근거가 "이 값을 누가 적었는가"에서 "이 문자열을 만든 코드가 무엇까지 낼 수 있는가"로 옮겨 갔다.
그래서 규칙을 다시 적으면, `template.HTML`은 그 문자열을 만든 코드가 안전을 책임질 수 있을 때만 쓴다.

이 화면을 만들며 정한 것이 둘 더 있다.
첫째, 변환은 서버에서 한다.
브라우저에서 바꾸려면 마크다운 라이브러리를 자바스크립트로 들여야 해서, 읽어야 할 언어를 늘리지 않기로 한 {ch-requirements}의 조건과 어긋난다.
둘째, 데이터베이스에는 마크다운 원문만 저장한다({ch-database-design}의 `decks` 테이블 `story` 칼럼).
변환한 HTML을 저장하면 변환 비용은 아끼지만, 변환 규칙을 바꾸는 날 예전 결과가 그대로 남는다.
원문이 단일 출처이고 HTML은 그때그때 계산하는 값이다.

편집 화면의 미리 보기 버튼을 누르면 입력란의 원문이 서버로 가고, 같은 함수가 만든 HTML 조각이 화면에 끼워진다.
저장된 스토리와 미리 보기를 그리는 코드가 하나라 둘이 어긋날 수 없다(화면 일부를 갈아 끼우는 방식은 {ch-htmx}).

== embed: 템플릿을 실행 파일에 싣는다

`parseTemplates`가 읽는 `templateFS`는 디스크의 폴더가 아니라, Go의 embed 기능으로 실행 파일 안에 넣어 둔 파일들이다.
`internal/web/web.go`의 선언부에서 주석 두 줄이 templates 폴더와 static 폴더 전체를 컴파일 결과물에 넣는다.

[source,go]
----
//go:embed templates
var templateFS embed.FS

//go:embed static
var staticFS embed.FS
----

.[용어 풀이] embed(Go)
[NOTE]
====
Go 컴파일러가 소스 코드 옆의 파일(HTML, CSS, 이미지 등)을 실행 파일 안에 통째로 넣어 주는 기능이고, `//go:embed` 주석 한 줄로 켠다.
프로그램은 디스크가 아니라 실행 파일 안에서 그 파일을 읽는다.
서버를 옮길 때 실행 파일 하나만 복사하면 되므로, 템플릿 파일을 빠뜨린 채 배포하는 사고가 사라진다.
====

대안은 실행 시점에 디스크에서 읽는 것이다.
템플릿만 고치면 서버 재시작 없이 반영되므로, 화면을 수시로 고치는 디자이너가 따로 있는 팀이라면 그쪽이 낫다.
대신 배포할 때 실행 파일과 템플릿 폴더의 짝을 사람이 맞춰야 한다.
Flashcard는 배포 산출물이 실행 파일 하나로 끝나는 단순함을 택해, 로컬의 `go run ./cmd/server`와 Vercel 함수({ch-vercel})가 완전히 같은 템플릿과 CSS를 본다.

`static/` 아래에는 파일 {n-static-files-ko-attr} 개(`app.css`, `app.js`, `htmx.min.js`, `sw.js`, `manifest.webmanifest`, `offline.html`, `favicon.ico`)와 앱 아이콘 PNG {n-icon-count-ko-attr} 장이 든 `icons/` 폴더가 있다.
`/static/`으로 시작하는 주소를 요청받으면 실행 파일 안의 그 파일을 돌려주는 코드(`internal/web/routes.go`의 `registerStatic`)도, `fs.Sub`로 static 폴더를 잘라 내 표준 라이브러리의 파일 서버를 Gin 라우트에 물리는 것이 전부다.

== 페이지 핸들러의 흐름

{ch-gin}의 API 핸들러가 "요청을 읽고, 스토어를 다녀와서, JSON으로 응답"이었다면, 페이지 핸들러는 마지막 단계만 템플릿 렌더링으로 바뀐다.

=== view 구조체: 모든 페이지의 공통 데이터

레이아웃은 어느 페이지에서든 제목, 현재 경로, 로그인 여부가 필요하므로, 템플릿에 건네는 맨 바깥 데이터(뿌리 데이터)를 이 공통 필드를 갖춘 `view` 구조체(`internal/web/render.go`)로 통일했다.

[source,go]
----
// view는 모든 템플릿이 실행 대상으로 받는 뿌리 객체다.
type view struct {
	Title     string
	Path      string // 요청 경로. 하단 내비의 활성 탭을 정한다
	LoggedIn  bool
	LocalMode bool
	Email     string
	Flash     string
	FlashKind string
	Data      any
}
----

앞쪽 필드는 레이아웃이 쓰고, 페이지마다 다른 데이터는 전부 `Data`에 담는다.
타입이 `any`라 무엇이든 담을 수 있고, `internal/web/home.go`의 홈 핸들러는 `gin.H`(문자열 키 맵)를 담는다.

[source,go]
----
w.render(c, http.StatusOK, "home", "Flashcard", gin.H{
	"Due":         due,
	"Streak":      summary.Streak,
	"Decks":       decks,
	"Suggestions": suggestions,
})
----

맵에 담은 `Due`가 `view.Data`를 거쳐 홈 템플릿의 `{{.Data.Due}}`, 곧 "오늘 복습할 카드 N장"이 된다.
`Data` 한 칸에 페이지마다 다른 것을 담으면, 화면이 늘어도 뿌리 데이터의 타입은 하나로 유지된다.

=== 폼 처리와 PRG 패턴

화면에서 무언가를 만드는 것은 폼 제출, 즉 POST다.
`internal/web/decks.go`의 덱 생성 핸들러는 폼 필드를 읽고, 검증하고, 저장한 뒤, 화면을 그리는 대신 다른 주소로 이동시킨다.

[source,go]
----
func (w *Web) createDeck(c *gin.Context) {
	name := strings.TrimSpace(c.PostForm("name"))
	if name == "" {
		redirectWithFlash(c, flashError, "덱 이름을 입력해주세요", "/decks")
		return
	}
	deck, err := w.store.CreateDeck(c.Request.Context(), auth.UserID(c), name, nil)
	if err != nil {
		w.failPage(c, err)
		return
	}
	c.Redirect(http.StatusSeeOther, "/decks/"+deck.Slug)
}
----

`c.PostForm("name")`은 폼의 `<input name="name">` 값을 꺼낸다({ch-gin}의 JSON 바인딩과 같은 일을 폼 인코딩으로 한다).
성공했을 때는 `render`가 아니라 `c.Redirect`를 부르는데, {ch-gin-hello·template-hello}의 최소 앱이 303으로 답하던 그 방식이다.
리다이렉트(redirect)는 결과 화면을 그리는 대신 "이 주소로 다시 가 보라"고 답해 브라우저를 다른 주소로 보내는 응답이다.
POST로 처리만 하고 곧장 GET 주소로 보내는 이 관례를 Post/Redirect/Get(PRG) 패턴이라 부른다.
상태 코드는 "다음 요청은 GET으로 하라"는 뜻의 303 See Other(`http.StatusSeeOther`)다.

.[용어 풀이] PRG 패턴(Post/Redirect/Get)
[NOTE]
====
폼을 받은 POST 핸들러가 결과 화면을 직접 그리지 않고, 처리만 마친 뒤 GET 주소로 브라우저를 이동시키는 관례다.
POST 응답 화면에서 새로고침을 누르면 브라우저가 양식을 다시 제출할지 묻고, 수락하면 같은 덱이 하나 더 만들어진다.
이동한 뒤의 화면은 평범한 GET 결과라 몇 번을 새로 고쳐도 조회만 반복되므로, 두 번 실행되면 곤란한 처리에는 거의 예외 없이 쓴다.
====

=== 플래시 메시지: 리다이렉트를 건너가는 한 줄

PRG에는 부작용이 하나 있다.
안내를 그릴 화면은 리다이렉트 다음의 GET 요청이 만드는데, HTTP는 요청 하나하나를 별개로 다루므로 그 요청은 직전 POST의 결과를 모른다.
Flashcard는 "덱을 삭제했어요" 같은 안내를 수명이 60초인 쿠키로 건넨다.
쿠키(cookie)는 서버가 브라우저에 맡겨 두는 작은 쪽지로, 브라우저가 다음 요청부터 자동으로 함께 보내 준다.
이렇게 전달하는 한 줄짜리 안내를 플래시 메시지(flash message)라고 부른다.

.[용어 풀이] 플래시 메시지(flash message)
[NOTE]
====
다음 화면에 딱 한 번만 보여 주고 사라지는 안내 문구로, "저장했어요"처럼 방금 끝난 처리의 결과를 알린다.
그다음 요청을 처리하는 쪽이 꺼내 쓰고 곧바로 지우기 때문에, 한 번 번쩍이고 만다는 뜻의 이름이 붙었다.
PRG 패턴에서 POST가 남긴 말을 리다이렉트 건너편까지 전하는 통로라, 웹 프레임워크 대부분에 같은 이름의 기능이 있다.
====

다음 코드는 안내 문구를 쿠키에 적는 `setFlash`, 그것을 남기고 곧장 303으로 보내는 `redirectWithFlash`(`createDeck`의 검증 실패 경로가 부른 것), 다음 요청에서 문구를 꺼내 읽고 지우는 `takeFlash`다.

`internal/web/cookies.go`:

[source,go]
----
// 플래시 메시지는 짧은 수명의 쿠키로 리다이렉트 한 번을 살아남는다.

// 플래시 종류. 템플릿이 이 값을 그대로 CSS 클래스로 쓴다.
const (
	flashInfo  = "info"
	flashError = "error"
)

func setFlash(c *gin.Context, kind, message string) {
	setCookie(c, flashCookie, kind+"|"+message, 60)
}

// redirectWithFlash는 모든 폼 핸들러가 공유하는 PRG(Post/Redirect/Get)
// 마무리다. 한 번짜리 메시지를 남기고 303으로 보내므로 새로고침해도 폼이
// 다시 제출되지 않는다.
func redirectWithFlash(c *gin.Context, kind, message, path string) {
	setFlash(c, kind, message)
	c.Redirect(http.StatusSeeOther, path)
}

// takeFlash는 대기 중인 플래시 메시지를 읽고 지운다.
func takeFlash(c *gin.Context) (kind, message string) {
	raw := cookieValue(c, flashCookie)
	if raw == "" {
		return "", ""
	}
	clearCookie(c, flashCookie)
	kind, message, ok := strings.Cut(raw, "|")
	if !ok {
		return flashInfo, raw
	}
	return kind, message
}
----

`takeFlash`가 꺼낸 메시지는 `view.Flash`에 담기고, 레이아웃 끝의 `{{if .Flash}}` 블록이 토스트로 띄운다.
토스트(toast)는 화면 한쪽에 잠깐 떴다가 스스로 사라지는 알림 상자다.
레이아웃은 모든 페이지의 공통이므로 어디로 리다이렉트하든 플래시가 보인다(쿠키 자체는 {ch-supabase-auth}).

== 템플릿도 테스트한다

템플릿 안의 오타는 컴파일러가 잡지 않아서, `{{.Naem}}`이라고 잘못 써도 `go build`는 통과한다.
문법 오류는 파싱 때, 없는 필드 참조는 그 페이지를 렌더링할 때에야 드러난다.

`New`가 내부에서 `template.Must`로 파싱하고 테스트 안의 패닉은 실패로 기록되므로, `New`를 호출하는 것만으로 전체 템플릿의 문법 검사가 된다.
렌더링 검사는 대표 데이터로 실제로 그려 본다.
`internal/web/templates_test.go`는 페이지 파일이 모두 파싱됐는지 확인하고, 가장 복잡한 학습 화면 조각을 국면(phase)마다 렌더링해 본다.

[source,go]
----
func TestTemplatesParse(t *testing.T) {
	w := New(&config.Config{AuthMode: "local"}, nil)

	expected := []string{
		"home", "decks", "deck", "card_form", "study", "study_direction",
		// ...
	}
	for _, name := range expected {
		if _, ok := w.pages[name]; !ok {
			t.Errorf("page template %q missing", name)
		}
	}
	// ...
	for _, v := range []studyBodyView{
		{Phase: "studying", State: state, Card: card, TextTTS: "test", BackTTS: "test"},
		{Phase: "break", State: state},
		{Phase: "finished", State: state},
		{Phase: "empty", State: state},
	} {
		var sb strings.Builder
		if err := w.partials.ExecuteTemplate(&sb, "study_body", v); err != nil {
			t.Errorf("study_body phase %s: %v", v.Phase, err)
		}
		// ...
	}
	// ...
}
----

화면이 의도대로 보이는지가 아니라 "깨지지 않고 그려진다"만 확인하는 스모크 테스트(smoke test)다.
그래도 흔한 실수는 배포 전에 걸러지고, `go test ./...` 한 번에 같이 돈다.
문법 오류는 페이지 파일 전부에서 잡지만 없는 필드 참조는 그려 본 학습 화면 조각에서만 잡으므로, 나머지 화면은 {ch-app-tests}의 통합 테스트가 이어받는다.

== 에이전트 활용 아이디어

`AGENTS.md`에는 템플릿 구조 규약을 적는다.
"페이지는 pages/, 공용 조각은 partials/에 두고 `layout.html`은 최소로만 고친다", "모든 페이지는 `content` 블록을 정의한다"처럼 이 저장소 특유의 규칙은 일반 지식으로 예측할 수 없어 적어 둘 가치가 크다.

템플릿은 컴파일 검사가 약하므로, 지시문 끝에 "수정 후 `go test ./internal/web`으로 확인하라"를 붙인다.
이런 반복 지시는 {ch-quality-gates}에서 보듯 커밋 전 `./check.sh` 같은 장치로 옮기는 편이 확실하다.

새 화면을 붙일 때는 "덱 상세 페이지와 같은 구조로"처럼 기존 페이지를 본보기로 지목하면, 레이아웃 연결과 조각 분리 관례가 함께 따라온다.

== 정리

* 구조는 액자와 그림이다. `layout.html`이 페이지 본문(`content`)을 감싸고, 같은 이름의 충돌은 base를 페이지마다 복제하는 Clone 패턴으로 푼다.
* FuncMap은 템플릿에 부족한 계산을 Go 함수로 메운다.
* 컨텍스트 자동 이스케이프는 본문·속성·URL 문맥을 구분해 XSS를 기본으로 막는다. `template.HTML`은 그 문자열을 만든 코드가 안전을 책임질 수 있을 때만 쓰고, 덱 스토리는 goldmark의 출력 범위로 그 조건을 지킨다.
* 템플릿과 정적 자산은 embed로 실행 파일에 실려, 로컬과 배포 환경이 같은 자산을 본다.
* 페이지 핸들러는 `view` 구조체로 렌더링하고, 폼 POST는 PRG 패턴과 플래시 쿠키로 마무리한다.
* 컴파일러가 못 잡는 템플릿 오타는 스모크 테스트로 거른다.

이 장의 화면 전환은 전부 링크 이동과 폼 제출, 즉 전체 페이지 새로고침이다.
카드 한 장을 삭제할 때 그 타일 하나만 사라지게 할 수는 없을까.
레이아웃이 읽어 들이던 `htmx.min.js`가 그 답이고, 다음 {ch-htmx}에서 살펴보겠다.
