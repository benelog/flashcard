= htmx: 부분 갱신과 무상태 학습 화면

{ch-html-css·html-template}의 화면은 전부 페이지 단위로 바뀐다.
링크를 누르거나 폼을 제출하면 서버가 페이지 한 장을 통째로 그려 보내고, 브라우저는 화면을 처음부터 다시 그린다.
카드 한 장을 추가해도 화면이 깜빡이고 스크롤이 맨 위로 돌아간다.
채점하면 곧바로 다음 카드가 나오는 리듬이 핵심인 학습 화면에서는 손실이 더 크다.

htmx(에이치티엠엑스)를 쓰면 HTML 속성 몇 개로 "어디에 요청을 보내 어느 부분을 바꿀지"를 선언하는 것만으로, 서버가 돌려준 HTML 조각으로 화면 일부만 바꿀 수 있다.
이 장은 그 기본기를 카드 삭제 버튼으로 익힌 뒤, 진행 상태를 hidden 필드에 실어 왕복시키는 무상태 학습 화면, `hx-swap-oob`와 `HX-Redirect`, 그리고 끝내 남는 자바스크립트(`app.js`)를 차례로 읽는다.

== 동적 화면의 두 갈래

새로고침 없는 동적 화면은 어떤 방법을 쓰든, 자바스크립트가 화면 뒤에서 요청을 보내고 응답이 오면 화면 일부만 바꾸는 기법을 바탕으로 한다.

.[용어 풀이] AJAX(비동기 요청)
[NOTE]
====
페이지 전체를 새로 받지 않고, 자바스크립트가 화면 뒤에서 서버와 데이터를 주고받는 기법이다(Asynchronous JavaScript and XML).
이름과 달리 요즘은 XML 대신 JSON이나 HTML 조각을 주고받는다.
"비동기"는 응답을 기다리는 동안에도 화면이 멈추지 않고 반응한다는 뜻이다.
====

이 기법 위에서 동적 화면을 만드는 길은 두 갈래다.

첫째, 화면 전체를 브라우저에서 그리는 자바스크립트 프레임워크다.
React, Vue, Svelte가 이 계열이고, 이렇게 만든 앱이 {ch-tech-choices}에서 본 SPA다.
서버는 JSON만 내려 주고, 화면을 그리는 일은 브라우저의 자바스크립트가 맡는다.
문서 편집기나 지도처럼 키 입력과 드래그 하나하나에 반응해야 하는 앱이라면 이쪽이 낫다.
대가는 언어와 빌드 도구가 한 벌 더 필요하고, 카드 하나를 지우면 서버의 데이터베이스와 브라우저가 기억하는 목록을 함께 맞추는 코드까지 짜야 한다는 것이다.

둘째, 서버가 계속 HTML을 그리고, 브라우저는 받은 HTML 조각을 제자리에 갈아 끼우기만 하는 방식이고 htmx가 그 대표다.
htmx는 비동기 요청 코드를 미리 다 써 둔 자바스크립트 라이브러리로, `hx-`로 시작하는 HTML 속성에 요청할 곳과 응답을 넣을 곳을 적어 두면 그대로 수행한다.
서버가 돌려주는 것은 HTML 조각이므로, 화면을 그리는 로직은 여전히 Go 한 곳에 있다.

Flashcard의 화면은 두 번째 길로 충분하다.
템플릿에서 `hx-post`가 붙은 자리는 {n-hx-post-count}곳으로, 카드 채점, 말한 답 채점, 따라 말하기, 다음 라운드 시작, 카드·덱·스마트 덱 삭제, 스마트 덱 저장, 사전 조회, 스토리 미리 보기가 전부다.
모두 "요청 한 번에 화면 조각 하나"로 표현되고, 키 입력 단위로 반응해야 하는 화면은 없다(그런 화면이 중심이 되는 경계는 {ch-alternatives}).
htmx는 파일 하나를 불러오면 준비가 끝나고, 빌드 도구도 새 언어도 필요 없다.

== 준비는 script 한 줄

모든 페이지의 공통 레이아웃 `internal/web/templates/layout.html`의 head에서 스타일시트와 함께 htmx와 `app.js`를 불러온다.

[source,html]
----
  <link rel="stylesheet" href="{{asset "/static/app.css"}}">
  <script src="{{asset "/static/htmx.min.js"}}" defer></script>
  <script src="{{asset "/static/app.js"}}" defer></script>
----

주소를 감싼 `asset`은 파일 내용의 해시를 주소 끝에 `?v=`로 붙이는 템플릿 함수로, 이전 버전 사본이 새 화면에 쓰이지 않게 한다({ch-caching}).
`defer`는 문서를 다 읽은 뒤에 스크립트를 실행하라는 속성이다.

50KB 남짓한 `htmx.min.js`는 외부 배포 서버(CDN)에서 불러오지 않고 저장소에 함께 두었다(벤더링, vendoring).
남의 서버가 멈춰도 영향이 없고, embed로 바이너리 안에 들어가므로 인터넷이 끊긴 자리에서도 로컬 서버가 온전히 돈다.
이 파일은 문서에서 `hx-` 속성이 붙은 요소를 찾아, 선언된 대로 요청을 보내고 응답을 DOM에 끼워 넣는다.

.[용어 풀이] DOM(문서 객체 모델)
[NOTE]
====
브라우저가 HTML 문서를 읽어 메모리에 만들어 두는 나무(tree) 구조다(Document Object Model).
화면의 모든 요소가 이 나무의 가지이고, 자바스크립트가 가지를 바꾸면 화면이 즉시 따라 바뀐다.
"페이지 일부를 갈아 끼운다"는 정확히는 가지 하나를 새 가지로 바꾼다는 뜻이다.
====

== 속성 세 개로 요청을 선언한다

가장 단순한 상호작용은 덱 상세 화면에서 카드 한 장을 지우는 버튼이다.
최소 앱에서는 누르면 화면 전체가 새로 떴지만, 여기서는 그 줄만 사라진다.
다음 `internal/web/templates/pages/deck.html`의 카드 목록에서 삭제 버튼에 요청을 선언하는 핵심 속성 세 개와 삭제 전 확인을 묻는 속성 하나가 붙어 있다.

[source,html]
----
  {{range .Data.Cards}}
  <li class="tile row">
    <!-- ... 카드 원문과 뜻 ... -->
    <a class="btn btn-icon" href="/cards/{{.ID}}" aria-label="카드 수정">{{icon "pencil"}}</a>
    <button class="btn btn-icon" aria-label="카드 삭제"
      hx-post="/cards/{{.ID}}/delete" hx-target="closest li" hx-swap="outerHTML"
      hx-confirm="이 카드를 삭제할까요?">{{icon "trash"}}</button>
  </li>
  {{else}}
  <!-- ... 카드가 없을 때의 안내 ... -->
  {{end}}
----

`hx-post`는 "어디로 보내는가"다.
버튼을 누르면 페이지를 이동하는 대신 화면 뒤에서 이 주소로 POST 요청을 보낸다.
htmx에는 `hx-delete`도 있지만, 이 앱은 htmx가 없어도 일반 폼 제출로 쓸 수 있게 화면 쪽 삭제 주소를 전부 `/cards/{{.ID}}/delete` 같은 POST 주소로 받는다.

`hx-target`은 "응답을 어디에 넣는가"다.
`closest li`는 버튼에서 가장 가까운 바깥 `li`, 즉 버튼이 든 카드 줄을 가리키므로 줄마다 id를 붙일 필요가 없다.
`#study-body`처럼 CSS 선택자를 쓸 수도 있다.

`hx-swap`은 "어떻게 넣는가"다.
`outerHTML`은 대상의 내용이 아니라 대상 요소 자체를 응답으로 바꾸라는 뜻이다.
지정하지 않으면 내용만 갈아 끼우고(`innerHTML`), 목록 끝에 한 줄 보탤 때는 `beforeend`를 쓴다.

`hx-confirm`은 요청 전에 브라우저 확인 대화상자를 띄운다.
지운 카드를 되살릴 방법이 없어서 둔 단계이고, 자바스크립트가 없는 최소 앱에는 넣을 수 없던 것이다.

다음은 `internal/web/cards.go`의 `deleteCard`로, 같은 주소가 htmx 요청과 일반 폼 제출을 모두 처리한다.

[source,go]
----
func (w *Web) deleteCard(c *gin.Context) {
	// ... 카드 ID를 읽어 삭제하고, 실패하면 에러 화면을 낸다 ...
	// htmx가 목록의 해당 <li>를 지우도록 빈 본문을 돌려준다.
	if isHTMX(c) {
		c.Status(http.StatusOK)
		return
	}
	setFlash(c, flashInfo, "카드를 삭제했어요")
	redirectBack(c, "/decks")
}
----

`isHTMX`는 요청에 `HX-Request` 헤더가 있는지 확인하는 한 줄짜리 헬퍼(`internal/web/web.go`)다.
헤더는 요청과 응답에 본문과 따로 딸려 가는 부가 정보 칸이고, htmx는 자신이 보내는 모든 요청에 이 헤더를 붙인다.
htmx 요청이면 본문 없는 200 응답을 돌려주고, htmx는 `outerHTML`에 따라 카드 줄 자체를 빈 내용으로 바꿔 지운다.
일반 폼 제출이면 플래시 메시지({ch-html-template})를 남기고 이전 화면으로 돌려보낸다.
기본 동작을 그대로 두고 그 위에 더 나은 경험을 얹는 이 접근을 점진적 향상(progressive enhancement)이라고 부른다.

== 페이지와 조각이 같은 템플릿을 공유한다

htmx 요청의 응답은 완성된 페이지가 아니라 HTML 조각(fragment)이고, 조각을 응답하는 함수는 `render`의 짝인 `renderPartial`이다.

.[용어 풀이] HTML 조각(fragment)
[NOTE]
====
`<html>`이나 `<head>` 없이 문서의 일부만 담은 HTML 토막으로, `<li>` 한 줄이나 카드 한 장 같은 화면의 한 부분이다.
그것만 열면 반쪽짜리 문서지만, 이미 열린 페이지의 한 자리에 끼워 넣기에는 충분하고 주고받는 양도 적다.
서버 렌더링과 htmx를 함께 쓰는 앱에서 화면 갱신의 단위는 이 조각이다.
====

`internal/web/render.go`의 `renderPartial`은 조각 전용 템플릿 묶음(`partials` 필드, `templates/partials/` 아래 파일들)에서 이름 붙은 템플릿 하나만 실행해 써 보낸다.

[source,go]
----
// renderPartial은 htmx 요청에 응답할 조각 하나만 써 낸다.
func (w *Web) renderPartial(c *gin.Context, name string, data any) {
	c.Header("Content-Type", "text/html; charset=utf-8")
	if err := w.partials.ExecuteTemplate(c.Writer, name, data); err != nil {
		_ = c.Error(err)
	}
}
----

중요한 것은 처음 로딩될 때의 화면과 htmx가 갈아 끼울 조각이 같은 템플릿 정의를 공유한다는 점이다.
`internal/web/templates/pages/study.html`은 `study_body`라는 조각 템플릿을 불러 그리는 것이 전부다.

[source,html]
----
{{define "content"}}
<!-- ... 스마트 덱 저장 버튼 ... -->
<div id="study-body">
  {{template "study_body" .Data.Body}}
</div>
{{end}}
----

학습을 시작하는 `GET /study`는 `render`로 페이지 전체를 받고, 그 뒤의 채점 요청은 `renderPartial`로 `study_body` 조각만 받아 `<div id="study-body">` 안을 갈아 끼운다.
첫 화면과 이후 화면이 한 템플릿에서 나오므로 둘이 어긋날 일이 없다.

== 무상태 학습 화면

학습은 요청 한 번으로 끝나지 않는다.
틀린 카드는 라운드가 끝난 뒤 다시 나오고, 전부 맞히면 완료 화면이 나온다.
채점 요청을 받은 서버가 다음 카드를 내놓으려면 남은 카드, 현재 라운드, 점수 같은 진행 상태를 알아야 한다.

카드 한 벌을 처음부터 끝까지 도는 이 한 번의 학습을 학습 세션이라고 부른다.
AI 에이전트와 대화할 때 말하는 세션이나 {ch-supabase-auth}의 로그인 세션과는 다른 뜻이다.
아래 "세션 저장 공간"의 세션은 또 다른 뜻으로, 서버가 사용자마다 마련해 두는 기억 자리다.

이 상태를 어디에 둘 것인가.

첫째, 서버 메모리의 사용자별 세션 저장 공간이다.
그러나 Vercel 서버리스 함수({ch-vercel})는 요청이 뜸하면 잠들었다 새로 깨어나고(콜드스타트) 그때 메모리는 백지가 되며, 인스턴스가 여럿이면 다음 요청이 같은 인스턴스에 온다는 보장도 없다.

둘째, 데이터베이스다.
상태는 살아남지만 채점마다 왕복이 늘고, 중간에 떠난 학습의 상태를 청소하는 일도 생긴다.
중단 후 재개가 꼭 필요한 앱이라면 치를 만한 비용이다.

셋째, 브라우저의 자바스크립트 변수다.
SPA의 방식이라 학습 흐름 전체가 브라우저 쪽으로 옮겨 가야 한다.

Flashcard는 넷째 길을 골랐다.
상태를 HTML 폼의 hidden 필드에 실어 요청과 응답 사이를 계속 왕복시킨다.
서버는 채점 요청에 담겨 온 상태로 다음 상태를 계산하고, 다음 카드 조각에 새 상태를 다시 hidden 필드로 실어 보낸다.
요청 하나하나가 독립인 HTTP의 무상태 성질을 그대로 따르는 설계다(무상태는 {ch-supabase-auth}에서 정리한다).

.[용어 풀이] hidden 필드(hidden field)
[NOTE]
====
`<input type="hidden">`, 즉 화면에 나타나지 않는 폼 입력 칸이다.
사용자가 보지도 입력하지도 않지만, 폼을 제출하면 보이는 입력 칸과 똑같이 값이 서버로 실려 간다.
가방에 붙인 짐표처럼, 화면이 눈에 띄지 않게 달고 있다가 요청할 때 서버에 건넨다.
====

다음 `internal/web/study.go`의 상태 구조체에는 아직 풀지 않은 카드 목록, 이번 라운드에서 틀린 카드 목록, 몇 번째 라운드인지가 있고, 나머지는 방향·점수·읽기 속도 같은 부가 값이다.

[source,go]
----
include::../../flashcard-advanced/internal/web/study.go[tag=study-state]
----

이 구조체가 HTML로 바뀐 모습이 `internal/web/templates/partials/study.html`의 `study_state_fields`로, 필드 하나가 hidden input 하나에 대응한다.

[source,html]
----
{{/* 학습 진행 상태를 hidden 필드로 실어 나른다. 서버는 아무것도 기억하지
     않고, 채점 요청에 담긴 이 상태로 다음 화면을 계산한다. */}}
{{define "study_state_fields"}}
<input type="hidden" name="session" value="{{.State.SessionID}}">
<input type="hidden" name="direction" value="{{.State.Direction}}">
<!-- ... title·return_url ... -->
<input type="hidden" name="queue" value="{{.QueueJoined}}">
<input type="hidden" name="missed" value="{{.MissedJoined}}">
<input type="hidden" name="round" value="{{.State.Round}}">
<!-- ... round_len·fp_total·fp_correct·tts_rate·voice ... -->
{{end}}
----

채점 버튼 둘은 이 필드들을 품은 폼 안에 있다.

[source,html]
----
      <form class="grade-grid" hx-post="/study/grade" hx-target="#study-body">
        {{template "study_state_fields" $}}
        <button class="btn btn-red btn-big" name="correct" value="false">{{icon "x"}} 틀렸어요</button>
        <button class="btn btn-green btn-big" name="correct" value="true">{{icon "check"}} 맞았어요</button>
      </form>
----

두 버튼은 `name="correct"`가 같고 value가 다르다.
HTML 폼은 실제로 눌린 제출 버튼의 name과 value만 보내므로, 정답과 오답을 구분하는 데도 자바스크립트가 필요 없다.

다음은 이 폼을 받는 `internal/web/study.go`의 `gradeCard`로, 채점 한 번에 벌어지는 모든 일이다.

[source,go]
----

함수가 새로 깨어나도, 다음 요청이 어느 인스턴스에 떨어져도 필요한 상태는 항상 요청 안에 있다.
대가는 셋이다.

첫째, 상태가 HTML에 노출된다.
개발자 도구로 hidden 필드를 보고 고칠 수도 있지만, 담긴 것은 카드 ID와 진행 숫자뿐이고 서버도 폼 값을 그대로 믿지 않는다.
`stateFromForm`은 라운드 번호가 1 미만이면 1로, 읽기 속도가 0 이하면 기본값 0.9로 보정하고, 돌아갈 주소(`return_url`)는 `safeNext`가 검사해 다른 사이트로 보내지 못하게 한다.
채점 기록은 로그인한 사용자 자신의 카드에만 미치므로, 값을 조작해 봐야 자기 통계를 망칠 뿐이다.
결제 금액이나 권한처럼 신뢰가 필요한 상태라면 이 방식을 쓰면 안 된다.

둘째, 새로고침에 약하다.
새로 고치면 학습이 처음부터 시작되는데, 몇 분이면 끝나는 이 앱에서는 받아들일 만하지만 긴 흐름이라면 데이터베이스가 낫다.

셋째, 요청마다 상태 전체가 왕복한다.
카드 ID는 36자짜리 UUID를 쉼표로 이어 붙이므로 카드 100장이면 큐 필드 하나가 3.7KB다.
이 앱의 학습 단위는 기본 50장, 최대 200장이라 큐 필드가 각각 1.8KB와 7.4KB에 그친다.

얻는 것은 세션 저장소도, 상태 테이블도, 청소 작업도 없는 구조다.
코드는 "폼을 읽고, 계산하고, 조각을 그린다"는 왕복 하나로 단순해진다.

== hx-swap-oob: 응답 하나로 여러 자리 채우기

카드 입력 화면에서 원문 칸에 영어 단어를 넣고 "사전에서 채우기"를 누르면, 뜻·발음 기호·예문 칸이 사전 조회 결과로 채워진다.
다음은 `internal/web/templates/pages/card_form.html`의 원문 입력 칸이다.

[source,html]
----
    <span class="field-label row-between">원문 (영어 · 용어)
      <span class="row">
        <!-- ... 발음 듣기 버튼 ... -->
        <button type="button" class="btn pill pill-blue"
          hx-post="/cards/lookup" hx-include="closest form"
          hx-target="#lookup-status" hx-swap="innerHTML">{{icon "book"}} 사전에서 채우기</button>
        <span id="lookup-status" class="tiny muted"></span>
      </span>
    </span>
----

`hx-include="closest form"`은 버튼이 속한 폼 전체의 값을 요청에 실으라는 뜻이라, 서버는 이미 입력된 칸이 무엇인지 안다.
그런데 직접 갈아 끼울 자리(`#lookup-status`)는 상태 메시지 한 곳뿐이고 채울 입력 칸은 셋이어서, `hx-swap-oob`를 쓴다.

서버의 `internal/web/dictionary.go`는 무료 사전 API(Free Dictionary API, `api.dictionaryapi.dev`)를 조회해 폼 값과 합친다.
사용자가 이미 입력한 칸은 받은 값 그대로 두고 빈 칸만 사전 결과로 채운 뒤, `lookup_result` 조각을 `renderPartial`로 그린다.
외부 서비스가 늦어져도 화면이 붙들리지 않도록, 조회는 8초가 지나면 포기한다.

다음은 응답 조각 `internal/web/templates/partials/lookup.html` 전문이다.

[source,html]
----
{{/* 사전 조회 응답: 상태 메시지(직접 타깃) + 비어 있던 폼 필드를
     hx-swap-oob로 바꿔치기한다. id는 card_form.html의 필드와 맞춘다. */}}
{{define "lookup_result"}}
<span>{{.Status}}</span>
<textarea id="f-meaning" name="meaning" rows="3" placeholder="우연한 행운, 뜻밖의 발견" hx-swap-oob="true">{{.Meaning}}</textarea>
<input id="f-phonetic" name="phonetic" placeholder="/ˌserənˈdipəti/" value="{{.Phonetic}}" hx-swap-oob="true">
<textarea id="f-example" name="example" rows="2" hx-swap-oob="true">{{.Example}}</textarea>
{{end}}
----

응답의 최상위 요소 가운데 `hx-swap-oob="true"`가 붙은 요소는 타깃과 무관하게, 문서에서 id가 같은 요소를 찾아 그 자리를 대신한다.
oob는 out of band, 즉 "지정된 통로 밖"이라는 뜻이다.
첫 `<span>`만 원래 타깃에 들어가 상태 메시지가 되고, 나머지 셋은 id가 같은 입력 칸(`f-meaning`, `f-phonetic`, `f-example`)을 찾아가 바꿔치기한다.

사전 조회를 서버가 하므로 브라우저 자바스크립트가 필요 없고, 응답을 두 줄 요약으로 다듬는 로직(`summarizeEntries`)은 {ch-unit-tests}의 방식대로 Go 테스트로 검증할 수 있다.

== HX-Redirect: 조각이 아니라 페이지 이동이 필요할 때

덱 상세 화면 상단의 덱 삭제 버튼(`hx-post="/decks/{{$deck.Slug}}/delete"`)은 카드 삭제와 사정이 다르다.
덱을 지우면 지금 화면이 통째로 무의미해지므로, 갈아 끼울 조각이 아니라 덱 목록으로의 이동이 필요하다.

서버가 평소처럼 303 리다이렉트를 보내면 htmx 요청도 그것을 따라가 덱 목록 페이지를 받아 온다.
htmx는 그것을 조각으로 여겨 버튼 자리에 끼워 넣으므로, 페이지 속에 페이지가 든 화면이 된다.
그래서 htmx는 `HX-Redirect`라는 전용 응답 헤더를 정해 두었고, 이 헤더를 받으면 htmx가 조각 교체를 멈추고 브라우저 전체를 그 주소로 이동시킨다.
다음은 `internal/web/decks.go`의 `deleteDeck`으로, 요청이 어디서 왔는지에 따라 이동 방식을 고른다.

[source,go]
----
func (w *Web) deleteDeck(c *gin.Context) {
	// ... 덱 삭제와 에러 처리 ...
	setFlash(c, flashInfo, "덱을 삭제했어요")
	// 삭제한 덱의 화면에 머물 수 없으므로 목록으로 보낸다. htmx 요청은 조각만
	// 갈아 끼우므로 이동을 HX-Redirect 헤더로 지시해야 한다.
	if isHTMX(c) {
		c.Header("HX-Redirect", "/decks")
		c.Status(http.StatusOK)
		return
	}
	c.Redirect(http.StatusSeeOther, "/decks")
}
----

htmx와 서버는 요청 헤더(`HX-Request`)와 응답 헤더(`HX-Redirect`)라는 평범한 HTTP 헤더 두 개로 대화한다.

== 그래도 남는 자바스크립트

여기까지 화면 갱신에 자바스크립트를 직접 쓰지 않았고, 카드 뒤집기조차 숨긴 체크박스와 CSS로 동작한다({ch-html-css}).
그래도 서버는 사용자의 스피커를 울리거나, 클립보드에 쓰거나, 인터넷이 끊겼는지 알 수 없다.
이런 일은 브라우저가 자바스크립트에만 열어 주는 통로로 해야 한다.

.[용어 풀이] Web API(브라우저)
[NOTE]
====
브라우저가 페이지의 자바스크립트에 열어 주는 기능 묶음이다.
음성 합성과 음성 인식(Web Speech), 클립보드, 온라인/오프라인 감지, 서비스 워커 등록처럼 사용자의 기기와 브라우저 자체를 다루는 창구다.
기기 안에서만 실행할 수 있으므로, 서버 렌더링 앱이라도 이 몫의 자바스크립트는 남는다.
====

완성품인 `htmx.min.js`를 빼면, 이 앱에서 직접 쓴 자바스크립트는 `internal/web/static/app.js`({n-app-js-lines}줄 남짓)와 {ch-caching}의 서비스 워커 `sw.js` 둘뿐이다.
2부에서 자바스크립트 문법은 익히지 않았으므로, 두 파일을 읽는 데 필요한 만큼만 먼저 짚는다.

=== 자바스크립트 읽는 법: Go와 견주어 다섯 가지

두 파일(합쳐 240줄 남짓)을 읽어 내는 데 필요한 다섯 가지만 Go와 견주어 짚는다.
문법이 눈에 익은 독자는 건너뛰어도 좋다.

첫째, 값에 이름을 붙일 때 `const`나 `let`을 앞에 쓴다.
Go의 `:=`와 같은 일을 하고, `const`는 그 이름에 다른 값을 다시 담지 않겠다는 표시다.
타입은 적지 않고, 문장 끝의 세미콜론은 있어도 없어도 된다.

[source,js]
----
const STATIC = "flashcard-static-v3";
let count = 0;
----

둘째, 함수를 이름 없이 값처럼 그 자리에서 적을 수 있다.
`(매개변수) => 결과` 모양이라 화살표 함수라 부른다.
두 파일에 화살표가 자주 나오는 것은 "이 일이 끝나면 할 일"을 그 자리에 적어 넘기기 때문이다.

[source,js]
----
const double = (n) => n * 2; // 중괄호와 return 없이 값 하나를 돌려준다
const log = (msg) => {
  console.log(msg); // 여러 줄이면 중괄호를 쓰고 return을 적는다
};
----

Go로 옮기면 아래와 같다.
이름 없는 함수를 값으로 다루는 것은 Go에도 있지만({ch-gin}의 클로저), 자바스크립트에서는 이쪽이 기본형이다.

[source,go]
----
double := func(n int) int { return n * 2 }
----

셋째, 나중에 도착하는 값은 프로미스(Promise)라는 그릇에 담아 다룬다.
네트워크 요청처럼 시간이 걸리는 일은 결과를 곧바로 돌려주지 못하므로, "다 되면 값이 들어올 그릇"을 먼저 돌려주고 프로그램은 다음 줄로 넘어간다.
값이 도착했을 때 할 일은 `.then(할 일)`에, 실패했을 때 할 일은 `.catch(할 일)`에 적는다.

.[용어 풀이] 프로미스(Promise)
[NOTE]
====
자바스크립트에서 아직 끝나지 않은 일의 결과를 미리 대신하는 값이다.
음식점의 진동 벨처럼, 음식 대신 벨을 먼저 받아 다른 일을 하다가 벨이 울리면 음식을 받는다.
Go는 시간이 걸리는 일을 고루틴에 맡기고 결과를 채널로 받지만, 브라우저의 자바스크립트는 흐름이 하나뿐이라 이 그릇을 주고받는 방식을 쓴다.
====

여러 프로미스는 `Promise.all(목록)`으로 합친다.
목록의 일이 전부 끝나야 값이 도착하는 프로미스 하나가 된다.
그 목록을 만들 때 자주 쓰는 `.filter(조건)`는 조건에 맞는 것만 골라 내고, `.map(할 일)`은 하나하나에 같은 일을 시켜 새 목록을 만든다.

넷째, `await`는 그릇에 값이 도착하기를 기다렸다가 꺼내 준다.
`.then`을 이어 붙여 깊어지는 코드를 위에서 아래로 읽히게 펴 주는 문법이라, 하는 일은 같고 모양만 다르다.
`await`를 쓰는 함수 앞에는 `async`를 붙인다.

[source,js]
----
// 아래 둘은 같은 일을 한다.
fetch("/decks").then((res) => console.log(res.status));

async function show() {
  const res = await fetch("/decks");
  console.log(res.status);
}
----

다섯째, 브라우저에서 일어나는 사건에는 미리 함수를 걸어 둔다.
`addEventListener("사건 이름", 할 일)`은 그 사건이 일어날 때마다 등록한 함수를 부르라는 뜻이다.
`app.js`는 클릭과 온라인·오프라인 전환에, {ch-caching}의 서비스 워커는 설치·활성화·요청 가로채기에 할 일을 걸어 두고, 두 파일의 코드는 대부분 이 일이다.
Go 서버의 라우팅이 주소와 핸들러를 미리 짝지어 두는 것과 같은 구조다.

`navigator`(브라우저 자신)나 `document`(지금 열린 문서)처럼 코드에 나올 낯선 이름은 문법이 아니라 브라우저가 열어 주는 창구이므로, 쓰이는 자리에서 설명한다.

=== app.js를 덩어리별로 읽는다

파일 머리의 주석이 이 절의 논지를 요약하고, 이어지는 코드는 시간대 쿠키, 서비스 워커 등록, 오프라인 배너의 세 덩어리다.
문법이 낯설면 주석과 아래 설명만 따라 읽어도 된다.

[source,js]
----
/* Flashcard에 남은 유일한 자바스크립트.
   앱 로직은 전부 Go 서버에 있고, 이 파일은 브라우저에서만 접근할 수 있는
   API(음성 합성, 클립보드, 온라인 상태, 서비스 워커, 시간대)만 감싼다. */

// 시간대: 서버가 "오늘"의 경계와 통계 날짜를 사용자 기준으로 계산하도록 알린다.
document.cookie =
  "tz=" +
  encodeURIComponent(Intl.DateTimeFormat().resolvedOptions().timeZone || "UTC") +
  ";path=/;max-age=31536000;samesite=lax";

// PWA: 서비스 워커 등록 (localhost 포함, http에서는 브라우저가 거부한다).
if ("serviceWorker" in navigator) {
  navigator.serviceWorker.register("/sw.js").catch(() => {});
}

// ... 로그아웃 뒤 서비스 워커의 페이지 캐시를 비우는 덩어리는 38장에서 본다 ...

// 오프라인 배너.
const banner = document.getElementById("offline-banner");
if (banner) {
  const update = () => banner.classList.toggle("show", !navigator.onLine);
  addEventListener("online", update);
  addEventListener("offline", update);
  update();
}
----

"오늘 복습할 카드"의 오늘이 어느 시간대의 오늘인지는 브라우저만 안다.
브라우저가 시간대 이름을 쿠키에 적어 두면 이후 모든 요청에 실려 가고, 서버의 `clientTZ` 함수가 그것으로 날짜 경계를 계산한다.
서비스 워커 등록은 앱을 설치하고 오프라인에서도 열리게 하는 준비로, {ch-caching}에서 다룬다.
오프라인 배너는 online/offline 이벤트를 듣기만 한다.

다음은 카드의 스피커 버튼을 누르면 영어를 읽어 주는 `speak`로, 음성 합성 Web API를 감싼 함수다.

[source,js]
----
function speak(text, rate) {
  if (!("speechSynthesis" in window) || !text) return;
  speechSynthesis.cancel(); // Chrome은 취소하지 않으면 큐에 쌓인다
  const u = new SpeechSynthesisUtterance(text);
  u.lang = "en-US";
  u.rate = rate || 0.9;
  // ... 브라우저가 가진 목소리 중 영어 목소리 고르기 ...
  speechSynthesis.speak(u);
}
----

읽을 글과 속도를 브라우저의 음성 기능에 넘기는 것이 전부다.

`speak`를 버튼에 연결하는 방식에 이 파일에서 가장 중요한 패턴이 있다.
`data-tts`는 "이 버튼이 눌리면 이 글을 읽어 달라"는 뜻으로, `data-copy`는 "이 링크를 복사하라"는 뜻으로 이 앱이 지어낸 속성 이름이다.

.[용어 풀이] data-* 속성(data attribute)
[NOTE]
====
`data-` 뒤의 이름은 개발자가 지어 쓰라고 HTML이 비워 둔 자유 칸이다.
`data-tts="apple"`처럼 적어 두면 브라우저는 그 값을 그리지 않고, 자바스크립트가 꺼내 쓸 데이터로만 요소에 보관한다.
표준 속성 이름과 겹칠 걱정 없이 요소에 값을 실어 둘 수 있는 것이 이 접두사를 두는 이유다.
====

다음 클릭 처리 부분은 화면 어디를 누르든 불리고, 눌린 자리에 `data-tts`나 `data-copy`가 있으면 그에 맞는 일을 한다.

[source,js]
----
// data-* 속성으로만 연결: 서버가 렌더링한(htmx로 갈아끼운) HTML에도 그대로 동작한다.
document.addEventListener("click", (e) => {
  const tts = e.target.closest("[data-tts], [data-tts-from]");
  if (tts) {
    e.preventDefault(); // 카드 뒤집기(label) 등 부모 동작을 막는다
    e.stopPropagation();
    const from = tts.dataset.ttsFrom && document.getElementById(tts.dataset.ttsFrom);
    speak(from ? from.value : tts.dataset.tts, parseFloat(tts.dataset.ttsRate));
    return;
  }

  const copy = e.target.closest("[data-copy]");
  if (copy) {
    e.preventDefault();
    navigator.clipboard
      .writeText(copy.dataset.copy)
      .then(() => (copy.dataset.done = "true"))
      .catch(() => prompt("아래 링크를 복사하세요", copy.dataset.copy));
  }
});
----

HTML의 `data-tts`는 자바스크립트에서 `dataset.tts`로 부르고, 붙임표가 든 `data-tts-from`은 붙임표를 떼고 다음 글자를 대문자로 올려 `dataset.ttsFrom`으로 부른다.
클립보드 쓰기는 곧바로 끝나지 않는 일이라, 성공과 실패 때 할 일을 프로미스의 `.then`과 `.catch`에 적었다.

버튼마다 처리기를 붙이는 대신 문서 전체에 처리기 하나를 붙이고 클릭된 요소의 속성을 그때 확인하는 이 패턴을 이벤트 위임이라고 부른다.

.[용어 풀이] 이벤트 위임(Event Delegation)
[NOTE]
====
요소마다 처리기를 붙이는 대신, 문서 꼭대기에 처리기 하나를 두고 방금 클릭된 것이 누구인지 그때그때 확인하는 패턴이다.
클릭 같은 이벤트가 자식에서 부모로 타고 올라오는 브라우저의 성질을 이용한다.
나중에 생긴 요소에도 처리기를 다시 붙일 필요가 없다는 것이 핵심 장점이다.
====

htmx는 채점할 때마다 스피커 버튼도 새 요소로 갈아 끼우므로, 버튼마다 처리기를 붙였다면 교체될 때마다 다시 붙여야 한다.
이벤트 위임에서는 요소가 속성만 지니면 되므로, 서버 템플릿이 `data-tts="{{$.TextTTS}}"`처럼 데이터만 실어 두면 무엇을 언제 갈아 끼우든 그대로 동작한다.

나머지 덩어리도 같은 패턴이다.
덱 스토리를 읽어 주는 `speakStory`(`data-tts-story`)는 Chrome이 긴 발화를 중간에 끊으므로 글을 문장 단위로 잘라 큐에 넣고, 한글이 든 조각만 한국어 목소리로 읽는다.
음성 인식을 감싼 `listen`(`data-listen`)은 들은 말의 후보를 폼의 `heard` 칸에 넣고 폼을 제출하며, 제출은 htmx가 가로채 채점과 같은 조각 왕복이 된다.
말한 답이 정답과 맞는지는 `app.js`가 아니라 서버의 `internal/study/speech.go`가 판정한다.

이 앱의 자바스크립트는 음성, 클립보드, 네트워크 상태, 서비스 워커, 시간대처럼 브라우저 밖에서는 할 수 없는 일뿐이고, 무엇을 보여 주고 어떻게 계산할지 정하는 앱 로직은 한 줄도 없다.

== 에이전트 활용 아이디어

`AGENTS.md`에 htmx 사용 원칙을 적는다.
"화면 갱신은 hx- 속성으로 해결한다", "htmx 응답은 조각 템플릿을 렌더링한다", "브라우저 JS는 `app.js`에만 추가한다"가 후보다.
지침이 없으면 에이전트는 `fetch`(자바스크립트에서 서버로 직접 요청을 보내는 함수)와 DOM 조작 코드를 기본으로 쓰므로, `app.js`가 조용히 자라난다.

동적 화면을 시킬 때는 "삭제 버튼을 누르면 그 행만 사라지고, 실패하면 행이 남은 채 오류 표시가 뜬다"처럼 성공과 실패의 화면 변화까지 적으면, 에이전트가 hx-target과 hx-swap을 바르게 고른다.
검증할 때는 개발자 도구의 네트워크 탭에서 응답이 조각 HTML인지 확인하게 하거나, 계획 단계에서 요청과 응답 예시를 먼저 보여 달라고 한다.

== 정리

* Flashcard는 동적 화면의 두 갈래 중 서버가 계속 HTML을 그리는 길을 골랐다. 기본기는 `hx-post`·`hx-target`·`hx-swap`과 `HX-Request` 헤더가 전부다.
* 삭제는 폼도 보낼 수 있는 POST 주소로 받아, htmx가 없어도 동작한다(점진적 향상).
* `renderPartial`로 조각을 응답하되, 페이지와 조각이 `study_body` 같은 템플릿을 공유해 화면이 한 벌로 유지된다.
* 학습 화면은 진행 상태를 hidden 필드에 실어 왕복시키는 무상태 설계다. 서버리스에서도 세션 저장소 없이 동작하는 대신, 상태가 노출되고 새로고침하면 처음부터 시작한다.
* 여러 자리를 채울 때는 `hx-swap-oob`, 페이지 이동이 필요할 때는 `HX-Redirect`를 쓴다.
* 브라우저만 할 수 있는 일은 `app.js` {n-app-js-lines}줄 남짓으로 남았고, 이벤트 위임과 data-* 속성 덕분에 htmx가 화면을 갈아 끼워도 그대로 동작한다.

다음 {ch-app-tests}에서는 이 층들이 이어 붙었을 때에도 옳은지 확인하며, hidden 필드 왕복과 `HX-Request` 헤더가 검증의 대상이 된다.
