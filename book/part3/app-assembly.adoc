= 앱을 조립하기: 계층 분리와 두 진입점

{ch-gin}에서 본 핸들러는 데이터를 스스로 꺼내지 않았다.
`store`라는 이름의 무언가에 물어보고 그 답을 JSON으로 옮겼을 뿐이다.

이 장은 그 뒤편의 저장소 계층이 왜 따로 있는지 보고, 나뉜 조각들이 한 벌의 앱으로 조립되어 내 컴퓨터의 서버와 Vercel 함수 양쪽에서 같은 모습으로 도는 과정을 따라간다.
로컬에서 검증한 동작이 배포 환경에서도 그대로라는 보장은 조립 코드를 어디에 두고 무엇을 공유하게 만드느냐에서 나온다.

== 계층 분리: handlers와 store

=== 두 계층의 골격

Flashcard 백엔드는 HTTP 요청을 다루는 일과 데이터베이스를 읽고 쓰는 일을 다른 패키지로 나눈다.
`internal/handlers`는 요청 파싱·검증·상태 코드를, `internal/pgstore`는 SQL을 맡는다.

두 계층 사이를 오가는 카드와 덱 같은 행 타입과 "없음"을 알리는 에러 값은 세 번째 패키지 `internal/model`에 둔다.
저장소 구현이 PostgreSQL용과 SQLite용(`internal/litestore`) 둘이라, 행 타입을 `pgstore`에 두면 SQLite 구현이 PostgreSQL용 패키지를 가져와야 하기 때문이다.

세 패키지의 선언부를 차례로 발췌한다.
첫째는 `internal/model`이 적어 둔 계약으로, 저장소가 할 줄 알아야 하는 메서드 목록과 행이 없을 때 쓰는 에러 값 하나다.

[source,go]
----
include::../../flashcard-advanced/internal/model/store.go[tag=store-head]
	// ... 덱 스토리·카드·세션·공유·스마트 덱·통계 메서드 생략 (모두 합해 35개)
}

// internal/model/model.go
var ErrNotFound = errors.New("not found")
----

둘째는 그 계약을 필드로 지닌 `Handlers`다.
어떤 데이터베이스가 들어올지는 모르고 계약만 안다.

[source,go]
----
// internal/handlers/handlers.go
type Handlers struct {
	Store model.Store
}

func New(s model.Store) *Handlers {
	return &Handlers{Store: s}
}
----

셋째는 그 계약을 실제로 이행하는 PostgreSQL 구현으로, 안에 든 것은 DB 연결 묶음 하나뿐이다.

[source,go]
----
// internal/pgstore/store.go
type Store struct {
	pool *pgxpool.Pool
}

func New(pool *pgxpool.Pool) *Store {
	return &Store{pool: pool}
}
----

`Handlers`는 `model.Store` 인터페이스를 품고, 그 인터페이스를 만족하는 `pgstore.Store`가 pgx 커넥션 풀(connection pool, DB 연결을 미리 여러 개 열어 두고 돌려쓰는 묶음)을 품는다.
조립은 `pkg/app/app.go`가 `pgstore.New(pool)`로 만든 스토어를 `handlers.New`에 건네는 한 줄이 전부다.
프레임워크 없이 생성자 함수로 엮는 수동 의존성 주입(dependency injection)이고, 부품이 넷(커넥션 풀, 스토어, JSON API 핸들러, 화면 핸들러)인 이 규모에서는 그것으로 충분하다.
핸들러가 인터페이스에 기대므로 로컬 모드에서는 SQLite 구현이 그 자리에 그대로 꽂힌다(운영의 PostgreSQL로 바뀌는 장면은 {ch-supabase-db}에서 본다).

.[용어 풀이] 의존성 주입(Dependency Injection)
[NOTE]
====
어떤 부품이 필요한 쪽이 그 부품을 스스로 만들지 않고, 밖에서 완성된 것을 건네받아 쓰는 조립 방식이다.
핸들러가 자기 안에서 PostgreSQL 스토어를 직접 만들면 영영 PostgreSQL 전용이 되지만, 밖에서 넣어 주면 무엇을 넣느냐에 따라 상대가 바뀐다.
전동 드릴이 날을 몸에 붙박지 않고 밖에서 끼우게 만든 것과 같다.
====

`ErrNotFound`는 {ch-core-logic}에서 본 센티널 에러(sentinel error)다.
스토어의 모든 조회 함수가 "행 없음"을 이 에러로 반환하고 {ch-gin}의 `fail`이 이를 404로 바꾸므로, pgx의 `ErrNoRows` 같은 드라이버 세부가 핸들러까지 새어 나오지 않는다.

`internal/pgstore/decks.go`에서 주소의 짧은 슬러그를 받아 그 사용자의 덱 ID를 찾아 주는 스토어 함수다.

스토어는 `context.Context`, `uuid.UUID`, `string` 같은 일반 타입만 받아 SQL을 실행하고 실패를 `model.ErrNotFound` 같은 앱 공용 에러로 번역하며, 핸들러는 `gin.Context`에서 값을 꺼내 스토어에 넘기고 결과를 상태 코드와 JSON으로 번역한다.
스토어는 HTTP를 모르고, 핸들러는 SQL을 모른다.

이 분리의 이점은 세 가지다.

첫째, 변경 범위를 예측할 수 있다.
응답 형식을 바꾸는 일은 handlers만, 쿼리를 최적화하는 일은 store만 건드리고, 잘못된 슬러그와 남의 덱을 모두 404로 처리하는 정책처럼 두 계층에 걸치는 결정은 `ErrNotFound`라는 계약 하나로 표현된다.

둘째, 테스트가 쉬워진다.
스토어 함수는 `gin.Context`를 요구하지 않으므로 HTTP 없이 DB만 있으면 검증할 수 있고, 슬러그 인코딩 같은 순수 로직은 `internal/model/deckslug_test.go`처럼 DB조차 없이 검사한다.

셋째, AI 에이전트에게 일을 맡기는 단위가 명확해진다.
"덱 목록 응답에 카드 수를 추가해 줘" 같은 요청이 어느 계층의 어느 파일을 고치는 일인지 구조에서 드러나므로, 에이전트의 변경을 검토할 범위도 좁아진다.

다만 이 앱의 분리는 실용적인 절충이다.
`internal/model/deck.go`의 `Deck` 구조체에는 `` `json:"id"` `` 같은 태그가 붙어 있어, 스토어의 도메인 타입이 API 응답 타입을 겸한다.
교과서대로라면 DB의 행 모양과 API 응답 모양이 따로 바뀔 수 있게 전달 전용 구조체인 DTO(Data Transfer Object)를 응답용으로 따로 둔다.
하지만 이 앱의 `Deck`은 필드가 모두 응답에 그대로 나가고 감추는 필드(`` `json:"-"` ``)가 없어서, 따로 두면 변환 코드만 늘어난다.
`Store` 인터페이스도 처음에는 없었고, 로컬 모드용 SQLite 스토어라는 두 번째 구현이 필요해졌을 때 `*pgstore.Store`에서 추출했다.
그 덕에 스토어를 모의 객체(mock)로 바꿔 끼우는 핸들러 테스트의 길도 열렸다.
작은 프로젝트에서는 처음부터 계층을 쌓기보다 이렇게 필요가 증명될 때 나누는 편이 맞다.

.[용어 풀이] 모의 객체(Mock)
[NOTE]
====
테스트할 때 진짜 부품 대신 끼워 넣는 가짜 부품이다.
진짜 데이터베이스에 다녀오는 대신 미리 정해 둔 답만 내놓으므로, DB를 띄우지 않고도 핸들러의 동작만 따로 시험할 수 있다.
평소에 재현하기 어려운 상황(DB 장애, 특정 에러)을 마음대로 만들어 낼 수 있다는 것도 이점이다.
====

== 하나의 엔진, 두 개의 진입점

이 부품들을 하나로 조립하는 곳은 앞의 발췌들이 거듭 가리킨 `pkg/app/app.go`다.

=== pkg/app: Gin 엔진을 만드는 조립 지점

다음은 핸들러 조립과 라우트 등록을 마친 `*gin.Engine`을 만드는 부분으로, 엔진을 프로세스에 하나만 만들어 돌려주는 `Engine`과 설정과 저장소를 받아 라우터를 조립하는 `New`가 등장한다.

[source,go]
----
var (
	engine     *gin.Engine
	engineOnce sync.Once
	engineErr  error
)

// Engine은 프로세스 전역 라우터를 돌려준다. 서버리스 인스턴스가 따뜻할 때는
// 재사용된다.
func Engine() (*gin.Engine, error) {
	engineOnce.Do(func() {
		engine, engineErr = build()
	})
	return engine, engineErr
}

func build() (*gin.Engine, error) {
	cfg, err := config.Load()
	if err != nil {
		return nil, err
	}
	if cfg.Driver != "postgres" {
		return nil, fmt.Errorf("app.Engine requires postgres, got driver %q", cfg.Driver)
	}
	pool, err := db.Pool(context.Background(), cfg.DatabaseURL)
	// ... 에러 처리 생략
	return New(cfg, pgstore.New(pool)), nil
}

// New는 아무 Store 구현 위에 라우터를 조립한다. 미들웨어는 cfg.AuthMode가
// 고른다. 운영은 Supabase 토큰 검증, 로컬 모드는 고정 사용자다.
func New(cfg *config.Config, s model.Store) *gin.Engine {
	h := handlers.New(s)

	gin.SetMode(gin.ReleaseMode)
	r := gin.New()
	r.Use(gin.Recovery())
	// ... 미들웨어와 API 라우트 등록 (뒤 절에서 발췌)

	// HTML 화면: 서버 렌더링 템플릿 + htmx, 쿠키 세션. 위의 API는 프로그램
	// 호출자를 위해 토큰 기반으로 남는다.
	web.New(cfg, s).Register(r)

	return r
}
----

첫째, 조립과 준비가 두 함수로 나뉘어 있다.
`New`는 설정과 스토어를 받아 라우터를 만드는 순수한 조립 함수이고, `Engine`은 설정 로드와 DB 커넥션 풀 생성까지 마친 완성품을 돌려주는 포장이다.
`New`가 `model.Store` 인터페이스({ch-go-types})를 받으므로 어떤 저장소 구현이든 꽂을 수 있다.

둘째, `Engine`은 `sync.Once`로 엔진을 프로세스(process)당 한 번만 만든다.
서버리스 함수는 요청이 뜸하면 꺼졌다가 새 요청이 오면 다시 켜지고, 켜진 동안에는 뒤이은 요청들을 같은 프로세스에서 처리한다.
그렇게 살아 있는 실행 환경을 웜 인스턴스(warm instance), 다시 깨어나며 처리하는 첫 요청을 콜드스타트(cold start)라고 부른다({ch-vercel}).
엔진을 한 번 만들어 계속 돌려쓰는 싱글턴(singleton)으로 두면, 설정 읽기와 라우트 등록과 DB 연결을 요청마다 되풀이하지 않고 콜드스타트의 첫 요청에서만 치른다.

.[용어 풀이] 프로세스(Process)
[NOTE]
====
운영체제가 프로그램 하나를 실행하려고 띄운 실행 단위다.
같은 프로그램이라도 두 번 실행하면 프로세스는 둘이고, 둘은 각자 자기만의 메모리를 쓴다.
서버가 켜져 있는 동안 메모리에 만들어 둔 것(라우터, 커넥션 풀, 캐시)은 요청이 바뀌어도 남아 재사용되고, 프로세스가 꺼지면 전부 사라진다.
====

셋째, `gin.Default()` 대신 `gin.New()`에 `gin.Recovery()`만 붙였다.
`gin.Default()`가 함께 등록하는 요청 로거는 Vercel이 요청 로그를 남겨 주므로 중복이고, 패닉(panic)을 요청 하나의 실패(500 응답)로 가둬 프로세스 전체가 멈추지 않게 하는 복구 미들웨어만 남겼다.

.[용어 풀이] 패닉(Panic)
[NOTE]
====
Go 프로그램이 더 진행할 수 없는 오류를 만나 그 자리에서 실행을 중단하는 것이다.
없는 배열 칸을 읽거나 nil 포인터를 따라가는 것처럼 코드가 당연하게 여기던 전제가 깨졌을 때 일어나고, 아무도 손을 쓰지 않으면 프로세스 전체가 종료된다.
Go는 `recover`로 이 중단을 가로챌 길을 열어 두었고, Gin의 `gin.Recovery()`가 요청마다 그 일을 대신한다.
====

넷째, 마지막의 `web.New(cfg, s).Register(r)`는 브라우저에 보일 HTML 화면의 라우트를 같은 엔진에 등록한다.
화면은 {ch-html-template}에서 다룰 서버 렌더링 템플릿이 맡으므로, `/api/*` 경로는 터미널에서 웹 요청을 직접 보내는 도구인 curl, 자동화 스크립트, 나중에 생길지 모를 모바일 앱 같은 프로그램을 위한 창구로 남는다.
두 세계는 인증 방식이 다르지만(화면은 쿠키, API는 Authorization 헤더의 토큰) 같은 스토어 `s`를 공유하므로, 어느 쪽으로 만든 카드든 다른 쪽에서도 보인다.

다섯째, `build()` 안에서 실패할 수 있는 일(설정 누락, 잘못된 드라이버, DB 연결 실패)은 모두 에러로 반환하고, 처리는 진입점에 맡긴다.

=== 로컬 서버와 Vercel 함수가 같은 앱을 공유한다

이 앱의 진입점(entrypoint)은 로컬 개발용 상주 서버와 Vercel에 배포되는 서버리스 함수(serverless function) 둘이다.
둘 다 방금 본 `New`가 조립한 엔진 위에서 돈다.

로컬 서버 `cmd/server/main.go`는 설정을 읽고, 저장 방식에 맞는 스토어를 갖춘 엔진을 얻고, 지정한 포트에서 서버를 띄운다.

[source,go]
----
func main() {
	cfg, err := config.Load()
	if err != nil {
		log.Fatal(err)
	}

	var engine *gin.Engine
	if cfg.Driver == "sqlite" {
		s, err := litestore.Open(cfg.SQLitePath)
		if err != nil {
			log.Fatal(err)
		}
		engine = app.New(cfg, s)
	} else {
		engine, err = app.Engine()
		if err != nil {
			log.Fatal(err)
		}
	}
	// ... 기동 로그 생략
	if err := engine.Run(":" + cfg.Port); err != nil {
		log.Fatal(err)
	}
}
----

분기의 기준은 설정의 드라이버다.
`DATABASE_URL` 없이 도는 로컬 모드(sqlite)에서는 SQLite 스토어를 직접 열어 `app.New`에 꽂고, PostgreSQL 설정이 있으면 그 조립까지 대신하는 `app.Engine()`을 부른다.
어느 쪽이든 라우터를 만드는 것은 같은 `New`다(로컬 모드의 전체 그림은 {ch-local-dev}에서 다룬다).
`engine.Run`은 `http.ListenAndServe`를 부르는 얇은 포장이라, `go run ./cmd/server` 하나로 8080 포트(`PORT` 환경 변수가 없을 때의 기본값)에 서버가 뜨고 이 한 프로세스가 화면 요청과 API 요청에 모두 응답한다.

Vercel 쪽 진입점 `api/index.go`도 하는 일은 같아서, `app.Engine()`으로 엔진을 얻어 들어온 요청을 그대로 넘겨줄 뿐이다.

[source,go]
----
// Package handler는 Vercel 서버리스 진입점이다.
// ...
// Vercel은 이 파일을 모듈 바깥에서 컴파일하므로 internal/ 패키지를 (직접)
// import할 수 없다. 필요한 공용 코드는 pkg/에 둔다.
package handler

func Handler(w http.ResponseWriter, r *http.Request) {
	engine, err := app.Engine()
	if err != nil {
		http.Error(w, "server misconfigured: "+err.Error(), http.StatusInternalServerError)
		return
	}
	engine.ServeHTTP(w, r)
}
----

이 코드가 성립하는 것은 `*gin.Engine`이 표준 `http.Handler` 인터페이스, 곧 Go 표준 라이브러리가 정해 둔 "요청을 받아 응답을 쓰는 물건"의 규격을 따르기 때문이다.
그래서 Vercel이 요구하는 시그니처 `func(http.ResponseWriter, *http.Request)` 안에서 `engine.ServeHTTP`를 부르면 Gin 라우터가 경로를 보고 핸들러를 찾아 실행한다.
`vercel.json`의 리라이트(rewrite, 어떤 주소로 들어온 요청이든 지정한 한곳으로 보내는 플랫폼 설정, {ch-vercel}) 규칙이 모든 경로의 요청을 이 함수 하나로 모아 주므로, 함수는 하나지만 앱 전체가 동작한다.

조립 코드를 `internal`이 아닌 `pkg/app`에 둔 것은 위 주석대로 Vercel의 Go 빌더가 이 파일을 모듈 바깥에서 컴파일해 `internal/` 패키지를 가져올 수 없기 때문이다({ch-code-map}, 배포 구성은 {ch-vercel-config}).

진입점은 둘이어도 조립은 `New` 하나라서 로컬과 운영의 요청이 같은 라우팅·핸들러·미들웨어 순서를 지나고, "로컬에서는 됐는데 배포하니 다르다" 같은 문제가 그만큼 줄어든다.
실행 환경이 바뀌어도(예: Vercel에서 일반 컨테이너로 이전) 진입점 파일 하나만 새로 쓰면 된다.

== 에이전트 활용 아이디어

`AGENTS.md`에는 계층 규약을 적는다.
"핸들러는 바인딩과 응답만 하고 로직은 store로 내린다", "새 라우트는 `pkg/app`의 조립부에 등록한다", "DB 접근은 Store 인터페이스를 통해서만 한다"가 이 저장소의 후보다.
"덱 목록에 카드 수를 더해 달라"는 요청에 에이전트는 스토어 메서드를 고치는 대신 핸들러 안에서 `count(*)` 질의를 바로 보내는 쪽으로 기울기 쉬우므로, 계층 경계일수록 지침이 필요하다.

조립 코드의 위치 제약은 지침보다 검사에 맡긴다.
`api/index.go`가 `internal/`을 가져올 수 없다는 규칙은 어겨도 로컬 빌드가 통과하므로, 이 저장소는 커밋 전에 도는 `./check.sh`가 `api/index.go`를 단독으로 빌드해 어기면 실패하게 했다({ch-quality-gates}).

== 정리

handlers(HTTP 관심사)와 store(DB 접근)로 계층을 나누면 변경 범위를 예측할 수 있고 테스트도 쉬워진다.
핸들러가 구현이 아니라 `Store` 인터페이스에 기대므로 같은 핸들러가 PostgreSQL과 SQLite 어느 쪽과도 짝을 이룬다.

`pkg/app/app.go`의 `New`가 조립한 `*gin.Engine`을 로컬 서버(`cmd/server`)와 Vercel 함수(`api/index.go`)가 공유하고, Vercel 쪽 완성품은 `Engine`이 `sync.Once` 싱글턴으로 제공한다.
이 공유는 `*gin.Engine`이 표준 `http.Handler`라서 성립하고, 조립 코드를 `pkg/`에 둔 것은 Vercel 빌더가 `internal` 패키지를 가져올 수 없기 때문이다.
같은 엔진에 HTML 화면 라우트도 등록되므로 `/api/*`는 curl·자동화 스크립트 같은 프로그램을 위한 창구로 남는다.

다음 장에서는 시선을 브라우저 쪽으로 돌려, {ch-html-hello}과 {ch-css-hello}에서 익힌 HTML과 CSS를 이 앱의 실제 화면 파일에서 다시 읽어 보겠다.
