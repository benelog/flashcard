= 코드는 어디에 있는가: 패키지 지도와 의존 방향

{ch-go-hello·go-types}에서 Go 문법을 파일 하나짜리 예제로 익혔고, {ch-design-principles}에서 이 앱의 구조 원칙을 읽었다.
저장소를 열기 전에 지도가 한 장 필요하다.
파일이 늘면 "이 문법이 무슨 뜻인가"보다 "이 코드가 왜 여기 있는가"가 어려워지기 때문이다.
Flashcard의 Go 코드는 파일 일흔 남짓, 패키지 {n-packages-no-cmd-ko}이고, 이 정도 규모에서도 디렉터리마다 맡은 일이 정해져 있고 의존이 한 방향으로 흘러야 길을 잃지 않는다.

이 장은 모듈과 디렉터리 배치, 패키지 사이의 의존 규칙, 앱이 켜질 때 무엇이 정해지는지를 차례로 본다.
배치가 주제이므로 코드는 구조를 드러내는 대목만 발췌한다.

이 장부터는 저장소를 직접 열어 두고 읽기를 권한다.
{ch-first-run}에서 클론해 둔 폴더를 편집기로 열면 되고, 함수 이름을 눌러 정의로 건너뛰는 기능이 있으면 한결 수월하다.
편집기가 없다면 {ch-first-run}의 선택 도구 절에서 VS Code를 깔아 두자(편집기 설정은 {ch-local-dev}에서 다룬다).

== 모듈 하나와 패키지 배치

Go의 코드 단위는 패키지(Package)이고, 패키지들을 버전 관리하는 단위가 모듈(Module)이다.
Flashcard는 모듈 하나에 패키지 {n-packages-no-cmd-ko}이 들어 있는 단일 저장소다(실행 파일을 만드는 `cmd/` 아래의 `main` 패키지 둘은 뺀 수다).

.[용어 풀이] 모듈과 패키지
[NOTE]
====
패키지는 관련된 코드 파일을 한 폴더에 모은 꾸러미이고, 모듈은 그 꾸러미들을 모아 버전과 배포를 관리하는 단위다.
책에 비유하면 패키지는 한 편의 장(章)이고, 모듈은 그 장들을 엮어 펴낸 책 한 권이다.
남이 만든 코드를 가져다 쓸 때도 모듈 단위로 버전을 지정해 받는다.
====

=== go.mod: 모듈 이름이 곧 임포트 주소

모듈의 정의는 앱 디렉터리(`flashcard-advanced/`) 맨 위의 `go.mod` 파일 하나로 끝난다.

[source,go]
----
module github.com/benelog/flashcard

go 1.26.4

require (
	github.com/MicahParks/keyfunc/v3 v3.8.0
	github.com/gin-gonic/gin v1.12.0
	github.com/golang-jwt/jwt/v5 v5.3.1
	github.com/golang-migrate/migrate/v4 v4.19.1
	github.com/google/uuid v1.6.0
	github.com/jackc/pgx/v5 v5.10.0
	github.com/yuin/goldmark v1.8.5
	modernc.org/sqlite v1.53.0
)
// ... 간접(indirect) 의존성 생략
----

첫 줄의 `module` 선언은 다른 코드가 이 안의 패키지를 임포트(import)할 때 적는 주소의 접두어다.
`internal/srs` 패키지를 쓰려면 `import "github.com/benelog/flashcard/internal/srs"`라고 쓴다.
경로가 GitHub 주소와 같은 것은 Go가 중앙 패키지 저장소 없이 소스 저장소 URL을 그대로 패키지 좌표로 쓰기 때문이다.

`require` 블록의 직접 의존성은 {n-direct-deps-ko-attr} 개뿐이다.
JWT 검증(keyfunc, golang-jwt), 웹 프레임워크(gin), 마이그레이션 실행기(migrate, {ch-migrations}), UUID 생성(uuid), DB 드라이버(pgx, sqlite), 덱 스토리의 마크다운을 HTML로 바꾸는 변환기(goldmark, {ch-html-template})다.
{ch-go-hello}에서 말한 두꺼운 표준 라이브러리와 {ch-tech-choices}의 "관리할 것이 적은가"라는 기준이 이 짧은 목록으로 나타난다.

=== 디렉터리마다 맡은 일이 있다

Go 커뮤니티에는 강제는 아니지만 널리 통용되는 디렉터리 관례가 있고, 이 저장소도 따른다.

[source,text]
----
flashcard/
├── api/            # Vercel 서버리스 함수 진입점
├── cmd/
│   ├── migrate/    # DB 마이그레이션 실행기
│   └── server/     # 로컬 개발 서버
├── internal/
│   ├── auth/       # JWT 검증·로컬 인증
│   ├── cardcsv/    # 카드 CSV 읽기·쓰기
│   ├── config/     # 환경 변수 로딩
│   ├── db/         # 마이그레이션 SQL
│   ├── handlers/   # JSON API 핸들러
│   ├── litestore/  # SQLite 스토어 (로컬 모드)
│   ├── model/      # 앱의 공용어: 행 타입과 저장소 계약
│   ├── pgstore/    # PostgreSQL 스토어 (배포)
│   ├── smartrules/ # 스마트 덱 규칙
│   ├── srs/        # 간격 반복 알고리즘
│   ├── study/      # 학습할 카드 고르기
│   └── web/        # 서버 렌더링 화면 (템플릿·정적 자산)
└── pkg/
    └── app/        # Gin 엔진 조립
----

이 지도에서 읽을 것이 세 가지 있다.

첫째, 최상위 세 디렉터리의 역할이 다르다.
`cmd/`는 실행 진입점(`main` 패키지)을 두는 곳으로 디렉터리 하나가 실행 파일 하나에 대응한다.
`internal/`에는 앱의 코드가 거의 전부 들어 있어서, 테스트 파일을 뺀 Go 코드 {n-go-lines}줄 가운데 {n-go-lines-internal}줄이 여기 있다.
`pkg/`에는 패키지가 하나뿐인데, 그 사연은 이 절 끝에서 밝힌다.

둘째, `internal/` 아래 패키지 이름이 곧 그 패키지가 아는 것의 범위다.
`srs`는 간격 반복 계산만 알고 데이터베이스를 모른다.
`smartrules`는 규칙의 생김새와 유효성만 알고, 그것을 SQL로 옮기는 방법은 모른다.
`cardcsv`는 카드와 CSV 사이의 변환만 안다.
아는 것이 좁은 패키지는 테스트가 쉽고, 다른 곳을 고칠 때 함께 열어 볼 일도 적다.

셋째, 같은 일을 하는 패키지 `pgstore`와 `litestore`가 나란히 있다.

=== internal이 막고 Vercel이 밀어낸 pkg

`internal/`은 Go 컴파일러가 특별 취급하는 디렉터리 이름이다.
그 아래의 패키지는 같은 모듈 안에서만 임포트할 수 있고, 외부 모듈이 임포트하면 컴파일 에러가 난다.
바깥에 내보이는 부분을 줄여 두면 안쪽 코드를 마음껏 고쳐도 남의 코드가 깨질 걱정이 없고, 그 경계를 컴파일러가 대신 지킨다.

`pkg/`는 반대로 외부에 공개해도 되는 패키지를 두는 관례적 위치다.
그런데 이 저장소의 `pkg/app`은 관례가 아니라 실제 제약 때문에 존재한다.
`api/index.go` 상단의 주석이 그 사정을 설명한다.

[source,go]
----
// Vercel은 이 파일을 모듈 바깥에서 컴파일하므로 internal/ 패키지를 (직접)
// import할 수 없다. 필요한 공용 코드는 pkg/에 둔다.
package handler
----

Vercel의 Go 런타임은 `api/` 아래 파일을 따로 떼어 내, 이 모듈에 속하지 않은 남의 코드처럼 컴파일한다.
그래서 이 파일에서는 `internal/` 패키지를 직접 임포트할 수 없고, Gin 엔진을 조립하는 코드를 `pkg/app`에 두어 로컬 서버와 Vercel 함수가 함께 쓴다.

지도에서 가장 설명이 필요한 자리가 여기다.
`pkg/app`을 `internal/app`으로 옮겨도 로컬 빌드와 테스트는 전부 통과하고, 깨지는 것은 배포뿐이다.
이렇게 플랫폼에만 있는 제약은 주석과 프로젝트 지침 파일에 적어 두지 않으면 같은 함정을 다시 밟는다.

== 의존은 한 방향으로만 흐른다

서로가 서로를 아는 관계가 되면 패키지를 나눈 의미가 없으므로, 어느 패키지가 어느 패키지를 알아도 되는지를 정해 두어야 한다.
그 규칙이 {ch-design-principles}의 첫째 원칙, 곧 모두가 `internal/model`을 알고 `model`은 아무도 모른다는 한 문장이다.

`internal/model`에는 카드와 덱 같은 행 타입, "없음"을 뜻하는 에러 값, 카드 종류와 학습 방향처럼 열이 받는 값과 그 판정, 데이터베이스를 모르는 순수한 계산 함수, 그리고 저장소 계약인 `Store` 인터페이스가 있다.

그래서 화면을 그리는 `web`, JSON API인 `handlers`, CSV를 다루는 `cardcsv`, 학습할 카드를 고르는 `study`는 `model`만 보면 되고, `pgstore`도 `litestore`도 임포트하지 않는다.
이들만 컴파일한 결과물에는 PostgreSQL 드라이버인 pgx가 아예 들어가지 않는다.
컴파일된 조각들을 실행 파일 하나로 이어 붙이는 마지막 단계를 링크(link)라고 하는데(웹 페이지의 링크와는 다른 말이다), 아무도 임포트하지 않은 부품은 이 단계에서 결과물에 실리지 않기 때문이다.

방향은 임포트 목록으로 확인한다.
`internal/web` 아래 어느 파일에도 `pgstore`나 `litestore`라는 이름이 없고, 반대로 `pgstore`의 파일에는 `web`이나 `handlers`가 없다.
구현 패키지를 화면이나 핸들러에서 직접 임포트하지 않는 것이 이 저장소의 규약이다.

`web`과 `handlers`도 서로를 임포트하지 않는다.
둘 다 필요한 요청 미들웨어(로그인한 사용자의 프로필 행을 보장하는 `EnsureProfile`)는 `internal/auth`에 두고, 실패했을 때 오류 화면을 그릴지 JSON으로 답할지만 각자 정한다.

== 앱이 켜질 때 정해지는 것

Flashcard는 켜질 때 데이터를 어디에 저장할지, 사용자가 누구인지를 어떻게 확인할지를 정한다.
그 결정을 내리는 곳이 `internal/config`이고, 결정에 따라 부품을 끼우는 곳이 진입점이다.

=== 설정 한 덩어리가 모드를 정한다

서버가 일을 하려면 데이터베이스 주소나 로그인을 맡긴 Supabase의 주소 같은 값이 필요하다.
이런 값은 코드에 적지 않고 실행 환경에 맡겨 두었다가 시작할 때 읽어 온다.
`internal/config/config.go`는 환경 변수(`DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_JWKS_URL`, `SUPABASE_JWT_SECRET`, `PORT`, `VERCEL`, `SQLITE_PATH`)를 읽어 설정 꾸러미 하나를 채우는 일만 하는 60여 줄짜리 파일이다.
파일 앞부분은 그 값들을 담을 그릇이다.

[source,go]
----
type Config struct {
	Driver          string // "postgres"(배포) 또는 "sqlite"(로컬 모드)
	DatabaseURL     string
	SQLitePath      string
	AuthMode        string // "supabase"(JWT 검증) 또는 "local"(고정 사용자)
	SupabaseURL     string // 웹 로그인(GoTrue) 기본 URL
	SupabaseAnonKey string // 서버 쪽 OAuth 흐름에 쓰는 GoTrue apikey
	JWKSURL         string
	JWTSecret       string // 옛 HS256 대비책. 값이 있으면 쓴다
	Port            string
}
----

지금 필요한 것은 앞의 넷이다.
`Driver`와 `DatabaseURL`·`SQLitePath`가 데이터를 어디에 둘지를, `AuthMode`가 사용자를 어떻게 확인할지를 나른다.
Supabase와 JWT 관련 값들은 {ch-supabase-auth}에서 다룬다.
이 그릇을 채우는 것이 같은 파일의 `Load` 함수다.

[source,go]
----
func Load() (*Config, error) {
	cfg := &Config{
		DatabaseURL: os.Getenv("DATABASE_URL"),
		// ... Supabase 값과 포트 읽기 생략
	}
	// ... 포트 기본값 처리 생략

	if cfg.DatabaseURL != "" {
		cfg.Driver = "postgres"
		cfg.AuthMode = "supabase"
		if cfg.SupabaseURL == "" || cfg.SupabaseAnonKey == "" {
			return nil, fmt.Errorf("SUPABASE_URL and SUPABASE_ANON_KEY are required")
		}
		// ... JWKS 주소 기본값 채우기 생략
		return cfg, nil
	}

	// DATABASE_URL이 없으면 SQLite 파일로 1인 로컬 모드를 돈다. Vercel에서는
	// 함수의 일회용 파일시스템에 조용히 쓰게 되므로, 거기서 DATABASE_URL이
	// 없는 것은 언제나 설정 실수다.
	if os.Getenv("VERCEL") != "" {
		return nil, fmt.Errorf("DATABASE_URL is required on Vercel")
	}
	cfg.Driver = "sqlite"
	cfg.AuthMode = "local"
	// ... SQLite 경로의 기본값 채우기 생략
	return cfg, nil
}
----

이 함수의 설계에는 세 가지 판단이 있다.

첫째, 모드를 정하는 것은 환경 변수 하나다.
`DATABASE_URL`이 있으면 PostgreSQL과 Supabase 인증, 없으면 SQLite와 고정 사용자다.
`MODE=local` 같은 스위치를 따로 두었다면 로컬 모드라고 적어 놓고 `DATABASE_URL`도 채워 둔 앞뒤가 안 맞는 설정이 생길 수 있다.
"쓸 데이터베이스 주소가 주어졌는가"로 갈음했으므로 그럴 일이 없다.
로컬 실행 스크립트가 `env -u DATABASE_URL`로 그 변수를 지우고 서버를 띄우는 것도 이 판정 때문이다({ch-local-dev}).

둘째, 어긋난 설정으로는 아예 켜지지 않는다.
PostgreSQL 모드인데 Supabase 값이 비어 있거나, Vercel 위에서 `DATABASE_URL`이 없으면 에러다.
후자를 그냥 두면 서버리스 함수의 일회용 파일시스템에 SQLite 파일을 만들어 정상인 척 돌다가, 함수가 꺼질 때 사용자 데이터를 통째로 잃는다.
조용히 잘못 도는 것보다 시끄럽게 죽는 편이 낫다는 판단이다.

셋째, 판정 결과가 문자열 두 개(`Driver`, `AuthMode`)로 남는다.
진입점과 조립 코드는 환경 변수를 다시 들여다보지 않고 이 두 값만 본다.

쓰인 문법은 모두 {ch-go-hello}에서 익힌 것이다.
`(*Config, error)`라는 반환값의 짝은 성공하면 채워진 설정과 `nil`(에러 없음)을, 실패하면 `nil`(설정 없음)과 에러를 돌려준다는 뜻이고, 부르는 쪽은 언제나 에러부터 확인한다.

=== 진입점은 얇다

이 앱의 진입점은 로컬 개발 서버 `cmd/server/main.go`와 Vercel 함수 `api/index.go` 둘이다.
로컬 쪽을 보자.

[source,go]
----
func main() {
	cfg, err := config.Load()
	if err != nil {
		log.Fatal(err)
	}

	var engine *gin.Engine
	if cfg.Driver == "sqlite" {
		s, err := litestore.Open(cfg.SQLitePath)
		if err != nil {
			log.Fatal(err)
		}
		engine = app.New(cfg, s)
	} else {
		engine, err = app.Engine()
		if err != nil {
			log.Fatal(err)
		}
	}
	// ... 기동 로그 생략
	if err := engine.Run(":" + cfg.Port); err != nil {
		log.Fatal(err)
	}
}
----

프로그램의 시작점인 `main` 함수는 설정을 읽고, `Driver` 값에 따라 저장소를 열고, 조립을 `pkg/app`에 맡긴 뒤 서버를 띄운다.
SQLite 쪽만 저장소를 여기서 열어 넘기고 PostgreSQL 쪽은 여는 일까지 `app.Engine()`이 대신하는데, 그 사연은 {ch-app-assembly}에서 푼다.

진입점을 얇게 두고 로직은 임포트할 수 있는 패키지에 두는 것이 Go의 관례다.
이 저장소에서는 `api/index.go`가 같은 `pkg/app`을 불러 같은 엔진을 만들므로, 로컬에서 확인한 앱과 배포된 앱이 조립 코드를 공유한다.
두 진입점의 차이는 {ch-vercel}에서 다시 본다.

== 낯선 파일을 여는 순서

이 저장소의 Go 파일은 대체로 같은 차례로 쓰여 있어서, 위에서부터 읽으면 목적에서 세부로 내려가게 된다.

맨 위는 패키지 주석이다.
`package` 선언 바로 앞의 주석은 Go에서 그 패키지 전체의 문서로 취급되고, 이 저장소는 그 자리에 "이 패키지가 무엇을 아는가"를 적는다(방금 본 `pgstore`와 `litestore`의 첫 줄).
이 몇 줄만 읽어도 계속 읽을지 정할 수 있다.

그다음이 임포트 목록이다.
`internal/model`만 있으면 데이터베이스를 모르는 코드이고, `pgx`가 보이면 PostgreSQL 전용 코드다.

그다음은 상수와 타입 선언, 생성자, 메서드 순이다.
함수는 이름의 첫 글자부터 본다.
대문자로 시작하면 패키지 밖에 공개된 약속이고, 소문자면 내부 사정이다({ch-go-hello}).
공개된 것만 먼저 읽으면 그 패키지가 바깥과 맺은 계약이 손에 잡힌다.

== 에이전트 활용 아이디어

* 프로젝트 지침 파일(`AGENTS.md`)에 이 장의 규약을 적어 둔다. "`api/` 아래 파일은 `internal/` 패키지를 직접 임포트하지 않는다", "화면과 핸들러는 저장소 구현을 직접 임포트하지 않는다", "`pgstore`와 `litestore`는 같은 파일·같은 이름으로 대칭을 유지한다"가 후보다. 적어 두지 않으면 에이전트가 로컬 빌드 통과만 확인하고 끝내거나 한쪽 저장소만 고친다.
* 새 코드를 어디에 둘지는 지시하는 대신 묻는다. "새 패키지로 뺄지 기존 패키지에 둘지, 임포트 방향과 함께 근거를 들어 제안해 달라"고 하면 파일이 생기기 전에 경계부터 정리된다.
* 낯선 패키지는 "이 패키지가 임포트하는 것과 이 패키지를 임포트하는 곳을 목록으로 만들어 달라"고 해 관계부터 본다. 파일 요약보다 구조를 익히는 데 빠르다.

== 정리

첫째, Flashcard는 모듈 하나에 패키지 {n-packages-no-cmd-ko}이고 바깥 의존성은 {n-direct-deps-ko-attr} 꾸러미뿐이다.
`go.mod`의 모듈 이름이 임포트 주소의 접두어가 된다.

둘째, `cmd/`는 진입점, `internal/`은 앱의 본체, `pkg/app`은 Vercel 제약 때문에 밖으로 나온 조립 코드다.
`pkg/app`이 그 자리에 있어야 하는 이유는 코드에 흔적이 없어 문서로만 남는다.

셋째, 모두가 `internal/model`을 알고 `model`은 아무도 모르며, 저장소 구현 둘은 같은 파일 이름으로 대칭을 이룬다.

넷째, 환경 변수 `DATABASE_URL`의 유무가 저장소와 인증 방식을 함께 정하고, 어긋난 설정으로는 서버가 아예 뜨지 않는다.

다섯째, 로컬 서버와 Vercel 함수 모두 설정을 읽고 저장소를 열어 `pkg/app`에 조립을 맡긴다.

다음 {ch-database-design}에서는 앱에서 수명이 가장 긴 데이터의 자리부터 걷는다.
{ch-requirements}의 요구사항이 테이블과 인덱스로 구체화되는 과정을 `internal/litestore`의 SQLite 스키마로 따라간다.
