= 앱을 통째로 띄우는 테스트: 화면과 API를 한 번에 검증하기

3부에서는 테이블({ch-database-design})에서 라우터({ch-gin})를 지나 화면({ch-html-css~htmx})까지 한 층씩 올라왔다.
그런데 층이 각각 옳다는 것과 이어 붙였을 때 옳다는 것은 다른 이야기다.

라우트 등록을 한 줄 빼먹어도 핸들러 코드는 멀쩡하다.
템플릿에서 `{{.Meaning}}`을 `{{.Meaninng}}`으로 잘못 적어도 Go 컴파일러는 아무 말을 하지 않는다.
폼의 `name` 속성과 서버가 읽는 이름이 어긋나도 양쪽 파일은 각각 문법에 맞다.
부품을 따로 놓고 보는 {ch-unit-tests}의 단위 테스트는 이런 어긋남을 잡지 못한다.

이 장에서는 브라우저 없이 앱을 통째로 띄워 진짜 HTTP 요청을 보내는 테스트(`pkg/app`의 테스트 함수 {n-app-test-count}개)를 읽는다.
하네스와 요청 헬퍼, 학습 한 판을 끝까지 돌리는 테스트, 실패 주입을 차례로 보고, 이 그물에 걸리는 것과 걸리지 않는 것을 정리한다.

== 왜 핸들러를 하나씩 부르지 않는가

핸들러는 `*gin.Context` 하나를 받는 함수라 직접 부를 수도 있지만, `gin.Context`를 손으로 만들고 경로 파라미터와 사용자 ID까지 심는 밑준비가 길어진다.
더 중요한 것은 그래도 잡히지 않는 오류가 남는다는 점이다.
라우터를 거치지 않으니 핸들러가 어느 주소에 등록됐는지 확인할 수 없고, 미들웨어를 거치지 않으니 사용자 ID를 심는 장치가 빠졌는지도 알 수 없다.
{ch-unit-tests}의 커버리지 표에서 `handlers`가 3.2%에 머문 것은 이 계층을 그런 방식으로 검사하지 않기로 했다는 뜻이다.

그래서 앱을 통째로 띄우고, 바깥에서 주소로 요청을 보낸다.

.[용어 풀이] 통합 테스트(Integration Test)
[NOTE]
====
여러 부품을 실제로 이어 붙인 상태에서 그 조합이 옳은지 확인하는 테스트로, 단위 테스트와 브라우저까지 띄우는 E2E 테스트 사이에 있다.
부품 사이의 배선(어느 주소에 무엇이 등록됐는지, 어떤 값이 다음 부품으로 넘어가는지)에서 생기는 오류를 잡는다.
쓰는 사람마다 범위가 다른 이름이라, 이 책에서는 브라우저만 빼고 앱 전체를 이어 붙인 것을 가리킨다.
실패했을 때 원인을 단위 테스트만큼 좁혀 주지 않는 것이 대가다.
====

세 종류를 이 앱에 대입하면 다음과 같다.

|===
| 종류 | 무엇을 이어 붙이나 | 걸리는 시간 | 이 앱에서

| 단위 테스트
| 함수 하나(srs, smartrules, cardcsv)
| 0.01초 미만
| {ch-unit-tests}에서 다룸

| 통합 테스트
| 라우터·미들웨어·템플릿·저장소
| 1초 안쪽
| 이 장에서 다룸

| E2E 테스트
| 위의 전부에 브라우저와 자바스크립트
| 수십 초에서 몇 분
| 두지 않음({ch-whats-next})
|===

통합 테스트는 비용에 비해 얻는 것이 많다.
브라우저를 띄우지 않으므로 `pkg/app` 전체가 1초 안쪽(이 글을 쓸 때 0.7초)에 끝나고, `go test ./...` 한 번에 단위 테스트와 나란히 돈다.
{ch-quality-gates}에서 볼 커밋 전 `./check.sh`에도, CI가 부르는 명령에도 이 테스트가 이미 들어 있다(파일을 고칠 때마다 도는 검사는 gofmt와 `go vet`만 맡는다).

따로 준비할 것이 없는 것은, 환경 변수도 계정도 없이 파일 하나짜리 데이터베이스로 도는 로컬 모드({ch-first-run})를 테스트가 그대로 빌려 쓰기 때문이다(원리는 {ch-local-dev}).

.[용어 풀이] 테스트 하네스(Test Harness)
[NOTE]
====
테스트를 돌리기 위한 밑준비와 뒷정리를 대신 맡는 코드로, 검증 대상을 감싸 실행 환경을 만들어 주는 마구(harness)라는 뜻이다.
{ch-unit-tests}의 픽스처 헬퍼가 데이터 한 벌을 준비했다면, 하네스는 앱 자체를 준비한다.
잘 만든 하네스는 테스트 본문에 무엇을 확인하려는지만 남긴다.

== 렌더링된 화면에서 상태 꺼내기

실제 사용은 화면을 보고 그 화면의 버튼을 누르는 왕복이고, {ch-htmx}의 학습 화면은 진행 상태를 hidden 필드에 실어 오간다.
테스트도 같은 왕복을 한다.

[source,go]

include::../../flashcard-advanced/pkg/app/apptest_test.go[tag=hidden-fields]

돌려받은 값이 곧 "사용자가 버튼을 누르기 직전의 화면 상태"이고, 테스트는 거기에 `correct` 같은 값 하나만 더해 되돌려 보낸다.

이 함수는 정규식으로 HTML을 읽는다.
정규식(regular expression)은 찾고 싶은 글자의 모양을 규칙으로 적어 두고, 긴 문자열에서 그 모양에 맞는 부분을 골라내는 표기법이다.
HTML 파서가 아니라 문자열 패턴이므로, 템플릿에서 속성 순서를 바꾸면 값을 찾지 못한다.
그때 조용히 빈 값을 넘기는 대신 곧바로 실패하게 한 것이 `len(values) == 0` 검사다.
hidden 필드는 서버가 같은 템플릿 한 곳에서 그리므로 패턴 하나로 충분하다고 보았고, 어긋나면 테스트가 실패로 알려 주므로 틀린 채 통과할 위험은 없다.

== 여기서 잡히는 것과 잡히지 않는 것

잡히는 것은 대개 "각 파일은 문법에 맞는데 이어 붙인 결과가 어긋난" 부류다.
등록을 빼먹은 라우트, 순서가 잘못된 미들웨어, 템플릿의 필드 이름 오타, 폼의 `name`과 서버가 읽는 이름의 불일치, PRG 리다이렉트의 목적지, htmx 헤더의 이름, 남의 덱이나 없는 덱을 404로 막는 권한 경계가 그렇다.

보안 쪽 검사도 여기에 들어간다.
학습을 그만둘 때 돌아갈 주소는 폼에서 오므로, 공격자가 남이 만든 링크로 자기 사이트 주소를 심으면 사용자가 가짜 화면으로 넘어갈 수 있다.
앱이 자기 주소로 시작하지 않는 값을 따라가지 않는지 테스트가 확인한다.
개인 화면에 `Cache-Control: no-store`가 붙는지, 내용 해시(주소 끝 `?v=`에 붙이는 버전 값)가 없는 정적 자원 주소가 영구 캐시로 선언되지 않는지도 검사한다({ch-caching}).

데이터가 왕복하는 흐름도 잘 맞는 대상이다.
CSV로 내보낸 파일을 다른 덱으로 그대로 가져올 수 있는지, 같은 파일을 두 번 가져오면 중복이 걸러지는지를 한 테스트에서 확인한다.

시간대처럼 환경에 따라 답이 달라지는 것도 확인하기 좋다.
공유 갤러리의 날짜는 방문자의 하루를 따라야 하는데, 저장소는 시각을 UTC로 읽어 온다.
UTC는 세계가 공통으로 쓰는 기준 시각(한국은 UTC+9)이고, 화면에 그릴 때 방문자의 시간대로 옮기므로 같은 순간이라도 날짜가 하루 달라질 수 있다.

마지막 `len(seen) < 2` 검사는 두 시간대가 같은 날짜를 냈다면 검증이 헛돌았다고 알려, 통과가 의미 있는지도 함께 검사한다.

잡히지 않는 것은 넷이다.
첫째, 브라우저가 실제로 그린 결과다(HTML에 옳은 값이 있어도 CSS가 그 요소를 가렸을 수 있다).
둘째, `app.js`와 htmx의 실제 동작이다(서버가 옳은 조각을 돌려주는지는 확인해도, htmx가 그것을 옳은 자리에 끼웠는지는 확인하지 않는다).
셋째, {ch-supabase-auth}의 실제 OAuth 로그인이다.
넷째, SQLite로 도는 테스트라 PostgreSQL 전용 SQL의 오류는 잡지 못한다.
이 넷을 덮는 E2E 테스트를 두지 않은 이유는 {ch-whats-next}에서 짚는다.
그래도 손으로 눌러 확인할 범위는 크게 줄었다.
`pkg/app`의 커버리지는 78.9%(이 글을 쓸 때 `go test -cover ./pkg/app` 결과)이고, 자기 패키지의 조립 코드만 센 수치라 실제로 지나간 코드는 그보다 넓다.

== 에이전트 활용 아이디어

에이전트는 코드를 고친 뒤 스스로 검증할 신호가 있어야 하고({ch-instructing}), 화면과 API를 한 번에 통과하는 이 테스트가 그 신호가 된다.

첫째, 새 화면이나 API를 만들 때 테스트를 함께 요구한다.
"덱 이름 변경 화면을 추가하고, `pkg/app`의 기존 테스트처럼 폼 제출과 검증 실패 경로를 확인하는 테스트를 더해 달라"처럼 지시하고, `postForm`·`mustRedirect` 같은 헬퍼 이름을 적어 주면 새 헬퍼를 또 만들지 않는다.

둘째, 버그를 고칠 때는 "먼저 이 증상을 재연하는 테스트를 추가해 실패하는 것을 보이고, 그다음 고쳐 달라"고 한다.
고쳤다는 주장이 아니라 통과한 테스트가 근거로 남는다.

셋째, 실패 경로를 늘리는 일을 맡긴다.
`brokenStore`에 플래그와 메서드 하나를 더하는 작업은 형태가 정해져 있어, 확인할 것을 문장으로 적어 주면 된다.

주의할 것도 있다.
테스트가 실패하면 에이전트가 `mustContain`의 문구를 지우거나 기댓값을 실제 출력에 맞추는 식으로 검증을 느슨하게 고쳐 통과시킬 수 있다.
무엇을 검증하지 않게 되었는지는 통과한 테스트 목록에 드러나지 않으므로, 테스트가 바뀐 커밋은 사람이 직접 읽는다.

== 정리

* 핸들러를 하나씩 부르는 대신 앱을 통째로 띄워 `engine.ServeHTTP`로 요청을 통과시킨다. 포트를 열지 않고도 라우팅·미들웨어·템플릿·저장소가 전부 지나가고, 1초 안쪽에 끝난다.
* 환경 변수 없이 SQLite로 도는 로컬 모드와, 로컬 서버·Vercel 함수가 쓰는 `New`를 그대로 빌려 쓴다.
* 브라우저가 하는 일은 헤더와 본문 모양의 차이로 흉내 내고, 밑준비도 웹 폼으로 만들어 준비 자체가 검증이 되게 했다.
* 렌더링된 화면에서 hidden 필드를 꺼내 다음 요청에 실어 학습 한 판을 끝까지 돌리고, 화면으로 확인할 수 없는 1차 정답률은 저장소를 읽어 검증한다.
* `model.Store`를 묻은 구조체로 메서드 하나만 깨뜨려 오류 화면, JSON 오류 응답, 원문 노출 여부를 검사한다.
* 브라우저가 그린 결과, `app.js`와 htmx의 실제 동작, 실제 OAuth 로그인, PostgreSQL 전용 SQL은 이 그물 밖에 있다.

다음 {ch-local-dev}에서는 이 장의 테스트가 빌려 쓴 로컬 모드가 어떻게 설정 없이 돌 수 있었는지 해부하고, 코드를 고치는 사람 쪽 개발 환경까지 갖춰 3부를 마무리한다.
