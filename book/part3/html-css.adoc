= 화면의 구조: 템플릿 삼층과 스타일 시스템

{ch-html-hello}과 {ch-css-hello}에서 HTML과 CSS의 문법을 파일 하나짜리 예제로 익혔다.
이 장에서는 그 눈으로 Flashcard의 실제 화면을 읽는데, 문법을 다시 설명하지는 않는다.
연습용 예제와 실제 앱의 차이는 문법이 아니라 규모와 조직이기 때문이다.

화면이 열두어 장이 되면 질문이 달라진다.
같은 상단 바와 하단 탭을 화면마다 한 벌씩 적을 것인가, 색을 바꾸려면 몇 군데를 고쳐야 하는가, 새 화면을 하나 더할 때 무엇을 복사하고 무엇을 물려받을 것인가.
스타일시트가 1,000줄이 되면 여기에 하나가 더 붙는다.
템플릿에서 태그를 하나 바꿨을 때 스타일이 조용히 풀리는 일을 어떻게 막을 것인가.

이 장은 그 답들을 읽는다.
화면 한 장이 세 층의 파일로 조립되는 구조를 먼저 보고, 겉틀과 페이지가 각각 무엇을 맡는지, 사용자 입력을 브라우저 기본 기능으로 어디까지 처리했는지를 확인한다.
그다음 스타일시트 한 파일을 조직하는 네 가지 규칙을 보고, 마지막으로 이 앱의 간판 장면인 카드 뒤집기가 자바스크립트 한 줄 없이 도는 원리를 뜯어본다.

화면 이야기는 이 장 뒤로도 이어진다.
{ch-html-template}에서는 Go 서버가 이 템플릿에 데이터를 채워 넣는 방법을, {ch-htmx}에서는 화면 일부만 갈아 끼우는 방법을 다룬다.

== 화면 한 장은 세 층으로 조립된다

브라우저가 화면에 그리는 것은 전부 HTML 문서다.
뉴스 기사도, 쇼핑몰 장바구니도, Flashcard의 학습 화면도 브라우저 입장에서는 태그가 달린 긴 텍스트 문서 하나다.
Flashcard에서 이 문서는 Go 서버가 만든다.
{ch-app-assembly}의 조립부가 `web.New(cfg, s)`로 등록하던 화면 라우트가 응답하는 실물이 바로 이 문서다.
브라우저가 주소를 요청하면 서버가 `internal/web/templates/` 아래의 파일들을 조립해 완성된 문서 하나를 응답으로 보낸다.

그 디렉터리는 세 층으로 나뉜다.

[source,text]
----
internal/web/templates/
├── layout.html      # 겉틀: 모든 화면이 공유하는 문서 뼈대
├── pages/           # 화면 하나에 파일 하나 (home, decks, deck, card_form, stats, …)
└── partials/        # 여러 화면이 나눠 쓰거나 일부만 갈아 끼우는 조각
----

조립 규칙은 단순하다.
겉틀은 문서의 머리와 상단 바, 하단 탭처럼 어느 화면에나 똑같이 있는 것을 갖고, 가운데에 구멍을 하나 남겨 둔다.
페이지 파일은 그 구멍에 들어갈 내용만 적는다.
여러 화면이 함께 쓰거나 화면 일부만 다시 그려야 하는 덩어리는 조각으로 뺀다.

이 배치의 값어치는 화면을 하나 더할 때 드러난다.
새 화면을 만들려면 `pages/`에 파일 하나를 쓰면 되고, 상단 바나 하단 탭은 한 줄도 적지 않는다.
반대로 하단 탭에 항목을 하나 더하려면 `layout.html` 한 곳만 고치면 열두 화면에 함께 반영된다.

세 층을 실제로 이어 붙이는 것은 Go의 html/template이고, 그 문법과 조립 코드는 {ch-html-template}의 주제다.
이 장에서는 각 층에 무엇이 들어 있는지를 읽는다.

== 겉틀이 맡는 것

`layout.html`의 앞부분은 문서의 머리다.

[source,html]
----
{{define "layout"}}<!doctype html>
<html lang="ko">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <meta name="theme-color" content="#2563eb">
  <meta name="description" content="단어·문장·숙어·개념을 카드로 뒤집으며 외우는 학습 앱">
  <title>{{.Title}}</title>
  <link rel="manifest" href="/manifest.webmanifest">
  <!-- ... 아이콘 링크 생략 ... -->
  <link rel="stylesheet" href="{{asset "/static/app.css"}}">
  <script src="{{asset "/static/htmx.min.js"}}" defer></script>
  <script src="{{asset "/static/app.js"}}" defer></script>
</head>
<body>
<!-- ... 본문은 다음 절에서 ... -->
</body>
</html>{{end}}
----

중괄호 두 겹으로 감싼 부분은 서버가 값을 채워 넣는 자리다.
`{{.Title}}`은 화면마다 다른 제목이 들어갈 구멍이고, `{{asset "..."}}`은 파일 주소 뒤에 내용 해시를 붙이는 함수다.
문법은 {ch-html-template}에서 다루므로 여기서는 "서버가 채우는 자리"로만 읽으면 된다.

이 열 줄 남짓한 머리에 이 앱의 결정 네 가지가 들어 있다.

첫째, 모바일을 기본으로 삼는다.
`viewport` 한 줄이 "화면 폭에 맞춰 그리고 임의로 축소하지 말라"고 브라우저에 알린다.
이 줄이 없으면 스마트폰에서 페이지가 데스크톱 크기로 그려진 뒤 축소되어 글자가 깨알만 해진다.

둘째, 스타일시트는 하나다.
`app.css` 한 파일만 불러오고, 화면별 스타일시트를 따로 두지 않는다.

셋째, 자바스크립트는 두 파일뿐이다.
하나는 부분 갱신을 맡는 htmx 라이브러리({ch-htmx})이고, 다른 하나는 이 앱이 직접 쓴 유일한 스크립트다.
둘 다 `defer`가 붙어 있어 문서를 다 읽은 뒤에 실행되므로 화면 그리기를 막지 않는다.

넷째, 설치되는 앱을 겨냥한다.
`manifest`와 `theme-color`가 그 준비물인데, {ch-pwa}에서 다룬다.

`asset` 함수가 붙는 이유도 짚어 두자.
브라우저는 한 번 받은 CSS나 자바스크립트를 주소가 같으면 다시 받지 않고 저장해 둔 사본을 쓴다.
해시(hash)는 파일 내용을 짧은 글자 묶음으로 요약한 값으로, 내용이 한 글자만 달라져도 전혀 다른 값이 된다.
이 앱의 정적 파일 이름에는 해시가 들어 있지 않아서, 파일을 고쳐도 브라우저가 예전에 받아 둔 것을 계속 쓸 수 있다.
그래서 템플릿에서 반드시 이 함수를 거쳐 주소 뒤에 내용 해시를 붙인다.
내용이 바뀌면 주소가 바뀌므로 브라우저가 새로 받아 간다.
이 규칙을 빠뜨린 자리는 사용자 기기에 배포 전의 옛 화면이 남는 사고로 이어지는데, 자세한 사연은 {ch-caching}에 있다.

=== 태그 이름이 곧 화면의 뼈대다

`<body>` 안으로 들어가 보자.
모든 화면에 공통인 틀을 만드는 부분이다.

[source,html]
----
  <div class="frame">
    <header class="topbar">
      {{if .LoggedIn}}<a class="brand" href="/">{{template "logo"}} Flashcard</a>
      {{else}}<a class="brand" href="/shared">{{template "logo"}} Flashcard</a>{{end}}
      <!-- ... 로그인 상태 표시 생략 ... -->
    </header>
    <!-- ... 오프라인 안내 배너 생략 ... -->
    <main{{if .LoggedIn}} class="with-nav"{{end}}>
      {{template "content" .}}
    </main>
    {{if .LoggedIn}}
    <nav class="bottomnav">
      <div class="bottomnav-inner">
        <a class="navlink{{if eq .Path "/"}} active{{end}}" href="/">{{icon "home"}}홈</a>
        <a class="navlink{{if hasPrefix .Path "/decks"}} active{{end}}" href="/decks">{{icon "layers"}}덱</a>
        <!-- ... 통계·설정 탭 생략 ... -->
      </div>
    </nav>
    {{end}}
  </div>
----

`{{template "content" .}}`가 앞 절에서 말한 구멍이다.
페이지 파일이 채울 자리가 이 한 줄이고, 그 위아래는 어느 화면에서나 같다.

태그 이름도 눈여겨보자.
상단 바는 `<header>`, 본문은 `<main>`, 하단 탭은 `<nav>`다.
셋 다 `<div>`로 만들어도 화면은 똑같이 나오지만, 이름 있는 태그를 쓰면 화면 낭독기가 `<nav>`를 만나 "여기는 이동 메뉴"라고 알려 줄 수 있다.
검색 엔진도 `<main>` 안을 본문으로 대접한다.
{ch-html-hello}에서 본 시맨틱 마크업의 값어치가 이 파일에서는 하나 더 있다.
겉틀 하나가 열두 화면의 구조를 정하므로, 여기서 태그를 제대로 골라 두면 그 이득이 앱 전체에 한 번에 적용된다.

하단 탭의 `active` 클래스는 서버가 붙인다.
`{{if eq .Path "/"}} active{{end}}`는 지금 보고 있는 주소가 홈이면 그 탭에만 `active`를 덧붙이라는 뜻이다.
화면이 지금 기억하고 있어야 하는 값을 상태(state)라고 부르는데, 여기서는 "지금 어느 화면을 보고 있는가"가 그 값이다.
이 상태를 브라우저의 자바스크립트가 아니라 서버가 알고 있고, 그 판단이 클래스 이름 하나로 화면에 실려 온다.
상태를 누가 드는가는 이 장의 마지막 절에서 본격적으로 다룬다.
이 장 끝에서 볼 카드 뒤집기와 함께, 상태를 어디에 둘 것인가라는 질문에 이 앱이 내놓은 두 가지 답이다.

== 페이지가 채우는 자리

페이지 파일은 겉틀이 남긴 구멍에 들어갈 내용만 적는다.
홈 화면인 `pages/home.html`에서 "내 덱" 목록 부분을 보자.

[source,html]
----
<section class="stack">
  <div class="row-between">
    <h2>내 덱</h2>
    <a class="link" href="/decks">전체 보기</a>
  </div>
  {{range .Data.Decks}}
  <a class="tile row-between" href="/decks/{{.Slug}}">
    <span class="medium">{{.Name}}</span>
    <span class="small muted">{{.CardCount}}장</span>
  </a>
  {{else}}
  <a class="tile-dashed" href="/decks">{{icon "plus"}} 첫 덱 만들기</a>
  {{end}}
</section>
----

덱이 있으면 타일을 줄줄이 그리고, 없으면 "첫 덱 만들기" 안내를 대신 보여 준다.
목록이 비었을 때 무엇을 보여 줄지가 템플릿 안에 함께 적혀 있다는 점이 눈에 띈다.
빈 화면을 따로 만들거나 조건문을 서버 코드에 두지 않아도 되는 것이 서버 렌더링의 소소한 이점이다.

덱 타일이 `<a>` 링크라는 것도 짚어 둘 만하다.
Flashcard에서 화면 사이의 이동은 이 링크가 거의 전부다.
브라우저가 새 주소를 요청하고 서버가 새 문서를 보내 주는, 웹에 처음부터 있던 이동 방식이다.
자바스크립트로 화면 전환을 직접 구현하는 방식과의 비교는 {ch-tech-choices}에서 다뤘고, 이 방식이 어색해지는 장면(카드를 채점할 때마다 화면 전체가 새로 뜨는 일)도 있는데, 그 틈을 메우는 htmx는 {ch-htmx}에서 다룬다.

한 가지 더, 이 파일에는 색이나 크기를 적은 곳이 한 군데도 없다.
`class="tile row-between"`처럼 이름표만 달아 두고 생김새는 전부 스타일시트에 맡긴다.
템플릿에 인라인 `style` 속성을 두지 않는 것이 이 저장소의 규약인데, 서버가 계산한 값을 넣는 경우(진행 막대의 너비 같은)만 예외로 둔다.

== 폼: 브라우저 기본 기능으로 끝낸 자리들

지금까지는 서버가 브라우저로 보내는 방향이었다.
반대 방향, 즉 사용자가 입력한 것을 서버로 보내는 도구가 폼이다.
Flashcard의 폼에서 볼 것은 폼 문법이 아니라, 자바스크립트를 쓰지 않고 어디까지 갔는지다.

새 덱 만들기 폼부터 보자.

[source,html]
----
{{/* 새 덱 폼: summary를 누르면 열린다. 자바스크립트 없이 details만으로. */}}
<details class="reveal">
  <summary class="tile-dashed">{{icon "plus"}} 새 덱 만들기</summary>
  <form method="post" action="/decks" class="row reveal-form">
    <input name="name" placeholder="덱 이름 (예: 토익 필수 단어)" autofocus required>
    <button class="btn btn-primary no-shrink">만들기</button>
  </form>
</details>
----

폼 자체는 `action`(어디로)과 `method`(어떻게) 두 속성으로 끝난다.
버튼을 누르면 브라우저가 입력값을 모아 `POST /decks` 요청을 보내고, 서버가 덱을 만든 뒤 새 화면으로 안내한다.

주목할 것은 폼을 감싼 `<details>`와 `<summary>`다.
평소에는 "새 덱 만들기"라는 줄만 보이다가 그것을 누르면 폼이 펼쳐지고 다시 누르면 접힌다.
예전에는 자바스크립트로 짜는 것이 당연했던 여닫기 상호작용을 태그 두 개가 공짜로 제공한다.
비어 있을 때 흐리게 보이는 안내 문구(`placeholder`), 비워 두면 제출을 막는 검사(`required`), 화면이 열리면 커서를 두는 지시(`autofocus`)도 마찬가지로 브라우저가 처리한다.

카드 입력 화면에는 카드 종류를 고르는 라디오 버튼이 있다.

[source,html]
----
  <div class="type-pills">
    <label><input class="pill-radio" type="radio" name="card_type" value="word" {{if eq $f.CardType "word"}}checked{{end}}><span class="pill-label">단어</span></label>
    <label><input class="pill-radio" type="radio" name="card_type" value="sentence" {{if eq $f.CardType "sentence"}}checked{{end}}><span class="pill-label">문장</span></label>
    <!-- ... 숙어·개념 선택지 생략 ... -->
  </div>
----

`name`이 같은 라디오 버튼들은 한 묶음이 되어 그중 하나만 선택된다.
그런데 실제 화면에는 동그란 라디오 버튼이 보이지 않고 알약 모양의 선택 버튼만 있다.
라디오 버튼은 CSS로 숨기고 함께 묶인 `<span>`을 알약처럼 꾸민 것인데, 그 방법은 이 장의 마지막 절에서 본다.
지금 짚어 둘 것은 "무엇이 선택됐는가"라는 상태를 여전히 라디오 버튼이 들고 있다는 사실이다.
겉모습만 바꿨을 뿐 선택 상태를 자바스크립트 변수로 옮기지 않았으므로, 폼을 제출하면 서버는 평범한 라디오 버튼 값으로 받는다.

파일을 보내는 폼도 있다.
덱 상세 화면의 CSV 가져오기다.

[source,html]
----
{{/* CSV 업로드: details/summary로 자바스크립트 없이 여닫는다. */}}
<details class="reveal">
  <summary class="tile-dashed">{{icon "upload"}} CSV 파일 선택해서 가져오기</summary>
  <form method="post" action="/decks/{{$deck.Slug}}/import" enctype="multipart/form-data"
        class="row reveal-form">
    <input type="file" name="file" accept=".csv,text/csv" required>
    <button class="btn btn-primary no-shrink">가져오기</button>
  </form>
  <!-- ... CSV 형식 안내 문구 생략 ... -->
</details>
----

`type="file"`이 파일 선택 창을 띄우고 `accept`가 고를 수 있는 파일 종류를 좁힌다.
폼에 붙은 `enctype="multipart/form-data"`는 파일이 실려 있으니 여러 부분으로 나눠 포장해 보내라는 지시다.
서버 쪽에서 이 파일을 카드로 바꾸는 코드는 {ch-core-logic}에서 읽은 `internal/cardcsv`다.

여기까지가 이 앱의 입력이다.
여닫기, 필수 입력 검사, 하나만 고르기, 파일 선택까지 전부 브라우저에 내장된 동작이고, 이를 위해 직접 쓴 자바스크립트는 없다.
{ch-tech-choices}에서 "배울 것을 줄인다"고 한 결정이 화면에서 어떻게 지켜지는지가 이 절에 있다.

== 스타일시트 한 파일을 조직하는 규칙

Flashcard의 스타일은 `internal/web/static/app.css` 한 파일, 1,000줄 남짓이 전부다.
전처리기도 프레임워크도 없고, 사람이 쓴 원본을 브라우저가 읽을 형태로 한 번 변환해 두는 준비 과정(빌드 단계)도 없다.
파일을 고치고 화면을 새로 고치면 그것이 곧 결과다.
그 대신 파일 하나가 커져도 읽고 고칠 수 있도록 규칙 네 가지를 지킨다.

=== 하나, 색과 치수에 이름을 붙여 맨 앞에 모은다

파일의 맨 앞은 값의 목록이다.

[source,css]
----
/* Flashcard 스타일시트. 빌드 도구 없이 이 파일 하나로 끝난다.
   색·둥근 정도 같은 디자인 토큰은 CSS 변수로 두고, 다크 모드는
   prefers-color-scheme에서 변수만 바꾼다. */

:root {
  --bg: #fafafa;
  --fg: #171717;
  --surface: #ffffff;
  --border: #e5e5e5;
  --muted: #737373;
  --faint: #a3a3a3;
  --primary: #2563eb;
  --primary-fg: #ffffff;
  /* ... 강조색(호박색·초록·빨강) 변수 생략 ... */
  --radius: 0.75rem;
  --radius-lg: 1rem;
}
----

이렇게 이름 붙여 둔 색과 치수를 디자인 토큰(design token)이라고 부른다.
아래의 1,000줄은 색을 직접 적는 대신 `var(--bg)`처럼 이 이름을 꺼내 쓴다.
주 색상을 바꿀 때 `--primary` 한 줄만 고치면 버튼과 링크와 진행 막대가 한꺼번에 바뀌고, 잠시 뒤에 볼 다크 모드도 이 목록 덕분에 거저 얻는다.

이름을 짓는 기준은 쓰임이지 색깔이 아니다.
`--blue`가 아니라 `--primary`, `--gray`가 아니라 `--muted`인 것은 다크 모드에서 같은 이름이 다른 색을 담아야 하기 때문이다.
색 이름으로 지어 두면 어두운 테마에서 `--blue`가 하늘색이 되는 이상한 상황이 생긴다.

=== 둘, 요소마다 이름표를 달고 평평하게 고른다

두 번째 규칙은 이 저장소가 특히 신경 쓰는 항목이다.

CSS에서 요소를 고르는 방법은 여럿인데, 그중 자손 선택자는 편한 만큼 위험하다.
하단 탭의 링크를 `.bottomnav a`("하단 탭 안의 모든 `<a>`")로 고르면 이름을 새로 지을 필요가 없어 편하다.
그런데 나중에 템플릿에서 그 `<a>`를 `<button>`으로 바꾸거나 감싸는 태그를 하나 더 두는 순간 스타일이 풀린다.
컴파일 오류도 테스트 실패도 나지 않고 화면만 어긋나므로 알아채기 어렵다.

그래서 이 앱은 요소마다 이름표를 직접 달고 평평하게 고른다.
하단 탭의 링크에는 `navlink`라는 클래스가 붙어 있고, CSS는 `.navlink`로 고른다.
현재 화면의 탭만 파랗게 칠하는 것은 `.navlink.active`, 즉 "그중 `active` 클래스가 함께 붙은 것"이다.
이름을 하나 더 짓는 비용을 치르고, 태그를 바꿔도 스타일이 따라오는 안정성을 얻는 맞바꿈이다.

예외는 상태 선택자다.
`:checked ~`(카드 뒤집기), `:checked +`(알약 라디오), `details.reveal[open] > summary`처럼 상태를 자식이나 형제에게 전달하는 선택자는 자바스크립트 없이 상태를 다루는 메커니즘 그 자체라 클래스로 대체할 수 없다.
이런 선택자를 새로 둘 때는 왜 평탄화하지 않는지 주석에 남기는 것이 이 저장소의 규약이다.

캐스케이드도 이 규칙 위에서 단순해진다.
한 요소에 여러 규칙이 겹치면 더 구체적인 선택자가 이기고, 구체성이 같으면 나중에 적힌 규칙이 이긴다.
`.navlink`(클래스 하나)보다 `.navlink.active`(클래스 둘)가 구체적이므로 활성 탭이 파랗게 된다.
우선순위 계산을 다 외울 필요는 없고, "넓은 규칙을 앞에, 좁은 예외를 뒤에"라는 감각이면 이 파일을 읽는 데 충분하다.

=== 셋, 배치는 이름 붙인 부품으로 재사용한다

배치도 같은 원리다.
자주 쓰는 배치에 이름을 붙여 부품으로 만들어 두고, 화면에서는 그 이름을 조합한다.

가장 많이 쓰는 부품은 가로 줄 세우기 `.row`다.

[source,css]
----
.row {
  display: flex;
  align-items: center;
  gap: 0.5rem;
}
----

세 줄이 전부지만 앞서 본 덱 타일, 폼, 상단 바가 전부 이 부품을 쓴다.
격자가 필요한 곳에는 그리드를 쓴 부품을 따로 둔다.
채점 버튼 두 개를 반반으로 놓는 `.grade-grid`나 학습 완료 화면의 통계 세 칸을 그리는 `.stat-3`이 그것이다.
한 줄로 흘러가는 배치에는 플렉스박스가, 행과 열이 있는 표 모양 배치에는 그리드가 편하다는 {ch-css-hello}의 기준이 그대로 적용됐다.

화면 전체의 틀도 부품 하나다.

[source,css]
----
.frame {
  max-width: 32rem;
  margin: 0 auto;
  min-height: 100dvh;
  display: flex;
  flex-direction: column;
}
----

`max-width: 32rem`이 폭을 512픽셀 언저리로 묶고 `margin: 0 auto`가 남는 좌우 공간을 나눠 가운데 정렬한다.
큰 모니터에서 옆으로 퍼지는 대신 가운데 좁은 기둥으로 서는 이유가 이 두 줄이다.
`flex-direction: column`이 상단 바와 본문과 하단 탭을 위에서 아래로 쌓고, `min-height: 100dvh`가 카드가 몇 장뿐인 화면에서도 본문 영역을 아래까지 늘린다.

작은 화면을 기본으로 두고 큰 화면을 예외로 다루는 이 접근을 모바일 우선(mobile first)이라고 부른다.
이동 중에 한 손으로 카드를 넘기는 이 앱의 쓰임에는, 화면 폭에 따라 컬럼 수를 늘리는 정교한 반응형보다 한 컬럼 고정이 맞는 옷이었다.

파일의 맨 앞에는 부품들보다 먼저 오는 규칙이 하나 있다.

[source,css]
----
* {
  box-sizing: border-box;
}
----

모든 요소의 너비를 잴 때 테두리와 안쪽 여백까지 포함하라는 뜻으로, 기본값대로라면 여백만큼 상자가 부모 밖으로 삐져나온다.
현대 CSS가 거의 관습처럼 첫머리에 두는 규칙이다.

=== 넷, 테마는 변수 값만 바꾼다

마지막 규칙은 첫 번째 규칙이 회수되는 자리다.

[source,css]
----
@media (prefers-color-scheme: dark) {
  :root {
    --bg: #0a0a0a;
    --fg: #f5f5f5;
    --surface: #171717;
    --border: #262626;
    --muted: #a3a3a3;
    --faint: #737373;
    /* ... 강조색·정답 카드 배경 변수 생략 ... */
  }
}
----

사용자가 운영체제에서 어두운 테마를 고르면 이 블록 안의 값들이 앞의 목록을 덮어쓴다.
바뀌는 것은 변수 값 열댓 개뿐이고, `background: var(--bg)`라고 적어 둔 1,000줄의 규칙들은 한 줄도 손대지 않는다.

변수 없이 다크 모드를 만들려면 색을 쓰는 규칙마다 어두운 버전을 한 벌씩 더 써야 하고, 색 하나를 빠뜨리면 어두운 배경에 검은 글자 같은 사고가 난다.
디자인 토큰을 앞에 모아 둔 보상이 여기서 돌아온다.
새 색을 더할 때 두 팔레트에 모두 정의해야 한다는 규칙이 따라붙는데, 이것이 이 앱에서 CSS를 고칠 때 가장 자주 어기게 되는 규약이기도 하다.

== 상태는 HTML이 들고 겉모습은 CSS가 따라간다

이 앱의 화면에서 가장 특이한 부분을 볼 차례다.
자바스크립트로 짜는 것이 일반적인 두 장면을 이 앱은 다른 방법으로 만들었고, 둘의 원리가 같다.

.[용어 풀이] 상태(state)
[NOTE]
====
화면이나 프로그램이 지금 기억하고 있는 값이다.
전등이 켜져 있는지 꺼져 있는지, 라디오 버튼 넷 중 어느 것이 선택됐는지, 카드의 정답을 이미 봤는지가 모두 상태다.
소프트웨어 설계의 큰 질문은 언제나 "이 상태를 누가 들고 있는가"이며, 브라우저의 자바스크립트 변수인지 HTML 요소 자신인지 서버인지 데이터베이스인지에 따라 코드의 모양이 달라진다.
Flashcard의 화면은 될 수 있으면 상태를 HTML 요소에 들려 두고 CSS가 그것을 읽어 겉모습만 바꾼다.
====

=== 알약 버튼: 선택 상태를 라디오 버튼이 든다

앞서 미뤄 둔 알약 라디오부터 보자.

[source,css]
----
.pill-radio {
  position: absolute;
  opacity: 0;
  width: 0;
}

.pill-label {
  display: inline-block;
  border-radius: 9999px;
  padding: 0.375rem 1rem;
  /* ... 글자 크기·바탕색 속성 생략 ... */
  cursor: pointer;
}

.pill-radio:checked + .pill-label {
  background: var(--primary);
  color: var(--primary-fg);
}
----

`.pill-radio:checked + .pill-label`을 우리말로 풀면 "선택된 라디오 버튼의 바로 다음 형제인 알약 라벨"이다.
라디오 버튼은 투명해도 여전히 동작하므로, 사용자가 알약을 누르면 뒤에 숨은 라디오 버튼이 선택되고 그 순간 이 규칙이 발동해 알약이 파랗게 변한다.

이 장면의 상태는 "네 종류 중 어느 것이 선택됐는가" 하나다.
그 상태를 HTML 요소가 들고 있으므로 자바스크립트가 기억할 것이 없고, 폼을 제출하면 서버가 그대로 받는다.

=== 카드 뒤집기: 정답을 봤는지를 체크박스가 든다

같은 원리로 만든 것이 이 앱의 간판 장면이다.
학습 화면에서 카드를 탭하면 카드가 옆으로 회전하며 뒷면의 정답이 드러나고, 그제야 아래에 채점 버튼 두 개가 나타난다.
전형적인 자바스크립트의 일처럼 보이지만 여기에도 자바스크립트가 한 줄도 없다.

이 장면의 상태도 단 하나, "정답을 봤는가"다.
알약 라디오가 선택 상태를 라디오 버튼에 들렸듯, 여기서는 체크박스 하나가 그 상태를 든다.

[source,html]
----
      {{/* 뒤집기 상태는 이 체크박스 하나. CSS 형제 선택자가 카드 회전과
           채점 버튼 표시를 모두 처리한다 — 자바스크립트가 필요 없다. */}}
      <input type="checkbox" id="reveal" class="reveal-toggle">

      <label for="reveal" class="flip-scene">
        <div class="flip-inner">
          <div class="flip-face">
            <!-- ... 앞면: 카드 종류 표시와 문제 텍스트 생략 ... -->
            <p class="tiny faint center hint">탭해서 정답 보기</p>
          </div>
          <div class="flip-face flip-back">
            <!-- ... 뒷면: 정답·발음·예문 생략 ... -->
          </div>
        </div>
      </label>

      <label for="reveal" class="btn btn-primary btn-big reveal-btn">정답 보기</label>

      <form class="grade-grid" hx-post="/study/grade" hx-target="#study-body">
        {{template "study_state_fields" $}}
        <button class="btn btn-red btn-big" name="correct" value="false">{{icon "x"}} 틀렸어요</button>
        <button class="btn btn-green btn-big" name="correct" value="true">{{icon "check"}} 맞았어요</button>
      </form>
----

구조는 넷이다.
숨긴 체크박스 하나, 그것을 대신 눌러 주는 라벨 둘(카드 자체와 "정답 보기" 버튼), 그리고 채점 폼이다.
`<label for="reveal">`은 라벨과 입력 칸을 `for` 속성으로 잇는 방식이라, 카드를 탭하든 버튼을 누르든 `id="reveal"`인 체크박스가 켜진다.
채점 폼에 붙은 `hx-`로 시작하는 속성들과 이 폼이 실어 나르는 것의 정체는 {ch-htmx}에서 다루니 지금은 접어 두자.

이제 CSS가 이 상태 변화를 받아 세 가지 일을 벌인다.
첫째, 카드를 3차원으로 회전시킨다.

[source,css]
----
.flip-scene {
  display: block;
  perspective: 1200px;
  min-height: 18rem;
  cursor: pointer;
  /* ... 탭 강조·글자 선택 방지 속성 생략 ... */
}

.flip-inner {
  position: relative;
  width: 100%;
  min-height: 18rem;
  transform-style: preserve-3d;
  transition: transform 0.45s cubic-bezier(0.4, 0, 0.2, 1);
}

.reveal-toggle:checked ~ .flip-scene .flip-inner {
  transform: rotateY(180deg);
}
----

핵심 선택자는 `.reveal-toggle:checked ~ .flip-scene .flip-inner`, 우리말로 "체크박스가 켜져 있으면, 그 뒤 형제인 카드 무대 안의 회전판"이다.
알약 라디오에서 본 `+`(바로 다음 형제) 대신 `~`(뒤에 오는 형제 아무나)를 썼는데, 체크박스와 카드 사이에 다른 요소가 끼어도 되게 하기 위함이다.

회전 자체는 `transform: rotateY(180deg)`, 세로축 기준 반 바퀴다.
`perspective`는 관찰자와의 거리를 정해 원근감을 주고, `transform-style: preserve-3d`는 앞뒤 두 면을 같은 3차원 공간에 두라는 지시이며, `transition`은 그 변화를 0.45초에 걸쳐 부드럽게 진행하라는 선언이다.

둘째, 앞면과 뒷면을 겹쳐 두고 뒤통수를 숨긴다.

[source,css]
----
.flip-face {
  position: absolute;
  inset: 0;
  display: flex;
  flex-direction: column;
  backface-visibility: hidden;
  -webkit-backface-visibility: hidden;
  /* ... 테두리·바탕색·그림자 속성 생략 ... */
}

.flip-back {
  transform: rotateY(180deg);
  border-color: var(--answer-border);
  background: var(--answer-bg);
}
----

두 면은 같은 자리에 포개져 있고 뒷면은 처음부터 180도 돌려 둔다.
그래서 회전판이 돌면 앞면이 뒤로 가고 뒷면이 정면을 향한다.
`backface-visibility: hidden`은 뒤집힌 면을 보이지 않게 하라는 속성으로, 이것이 없으면 앞면의 글자가 거울상으로 비쳐 보인다.

셋째, 채점 버튼과 "정답 보기" 버튼을 맞바꾼다.

[source,css]
----
.reveal-toggle:checked ~ .grade-grid {
  display: grid;
}

.reveal-btn {
  display: block;
}

.reveal-toggle:checked ~ .reveal-btn {
  display: none;
}
----

`.grade-grid`는 평소 `display: none`으로 숨겨져 있다가 체크박스가 켜지면 그리드로 살아나고, 반대로 "정답 보기" 버튼은 숨는다.
정답을 보기 전에 채점부터 하는 실수를 배치가 구조적으로 막는다.

정리하면 상태는 체크박스가 들고, 상태 전환은 라벨이 맡고, 상태에 따른 화면 변화는 `:checked ~` 선택자가 맡는다.
같은 일을 자바스크립트로 짜는 것이 더 일반적이고, 상태가 여러 개로 늘거나 뒤집힐 때 소리를 내는 등 화면 밖의 동작이 필요하면 자바스크립트 없이는 안 된다.
하지만 "표시 상태 하나에 겉모습이 따라오는" 정도라면 브라우저 내장 동작만으로 충분하고, 코드가 줄어드는 만큼 깨질 곳도 준다.

그래도 이 앱의 자바스크립트가 0줄은 아니다.
발음 읽어주기나 클립보드 복사처럼 브라우저만 가진 기능은 자바스크립트로만 접근할 수 있어서, 그런 기능을 감싸는 `static/app.js` 한 파일이 있다.
100줄 남짓이고 화면의 상태를 다루는 코드는 거기 없다.

카드를 뒤집은 다음 단계, 즉 채점 결과를 서버에 보내고 다음 카드를 받아 오는 일은 CSS만으로는 안 되므로 {ch-htmx}의 htmx가 이어받는다.

== 에이전트 활용 아이디어

화면의 구조와 스타일을 에이전트와 함께 다룰 때의 요령이다.

`CLAUDE.md`에는 이 장에서 본 규약을 적어 둔다.
"CSS는 `app.css` 한 파일, 프레임워크와 전처리기 금지", "색과 간격은 파일 상단의 변수로만 추가하고 두 팔레트에 모두 정의한다", "자손 선택자 대신 클래스 이름표를 쓰되 상태 선택자는 예외로 두고 이유를 주석에 남긴다", "템플릿에 인라인 `style` 속성을 두지 않는다"가 그 후보다.
그냥 두면 에이전트는 인라인 스타일이나 유틸리티 클래스 흉내로 지름길을 낸다.
특히 자손 선택자는 이름을 새로 짓지 않아도 되니 에이전트가 가장 먼저 손을 뻗는 방식이라, 적어 두지 않으면 파일 전체가 자손 선택자 방식으로 서서히 되돌아간다.

새 화면을 만들 때는 어느 층에 무엇을 둘지 먼저 정하게 한다.
"이 화면에서 겉틀이 이미 제공하는 것, `pages/`에 새로 쓸 것, `partials/`로 뺄 것을 나눠 제안해 달라"고 하면, 상단 바를 통째로 복사해 붙이는 결과를 피할 수 있다.

화면 작업에는 컴파일러 같은 자동 검증이 없다.
그래서 "바꾼 뒤 어느 화면의 어느 요소를 확인해야 하는지"를 에이전트가 보고하게 하고, 사람이 브라우저로 그 목록을 눌러 보는 흐름이 현실적이다.
{ch-claude-code}의 검토 기준으로 보면 화면 마크업은 오류 발견이 쉬운 영역이라, 빠르게 훑고 눈으로 확인하는 쪽에 힘을 싣는다.

접근성 점검은 에이전트가 잘하는 반복 작업이다.
"템플릿 전체에서 img의 alt 누락, 라벨 없는 입력, 대비가 약한 색 조합을 찾아 표로 보고해 달라"처럼 훑기형 검사를 맡기면 사람이 놓치는 구석을 값싸게 커버한다.

== 정리

첫째, 화면 한 장은 세 층으로 조립된다.
겉틀(`layout.html`)이 문서의 머리와 상단 바와 하단 탭을 갖고 가운데에 구멍을 남기면, 페이지 파일이 그 구멍을 채우고, 여러 화면이 나눠 쓰는 덩어리는 조각으로 빠진다.
새 화면을 더할 때 쓰는 것은 페이지 파일 하나뿐이다.

둘째, 사용자 입력은 브라우저 기본 기능으로 끝냈다.
여닫기(`details`)와 필수 검사와 하나만 고르기와 파일 선택까지, 이를 위해 직접 쓴 자바스크립트가 없다.

셋째, 스타일시트 한 파일은 규칙 네 가지로 조직된다.
색과 치수에 이름을 붙여 맨 앞에 모으고, 요소마다 이름표를 달아 평평하게 고르고, 자주 쓰는 배치를 부품으로 만들어 재사용하고, 테마는 변수 값만 갈아 끼운다.
자손 선택자를 아끼는 두 번째 규칙은 템플릿의 태그를 바꿔도 스타일이 따라오게 하려는 것으로, 이름 짓는 비용과 안정성을 맞바꾼 결정이다.

넷째, 이 앱의 화면은 상태를 HTML 요소에 들려 두고 CSS가 그것을 읽어 겉모습만 바꾼다.
알약 버튼의 선택 상태는 라디오 버튼이, 카드 뒤집기의 "정답을 봤는가"는 체크박스가 든다.
상태가 하나뿐이고 그에 따라 겉모습만 달라지는 장면이라면 이 분업으로 충분하다.

다만 이 장에서 읽은 템플릿에는 아직 설명하지 않은 구멍이 있다.
`{{.Title}}`, `{{range .Data.Decks}}` 같은 중괄호 자리들이다.
다음 {ch-html-template}에서는 Go의 html/template이 이 자리에 데이터를 채워 완성된 문서를 만드는 과정을 살펴보겠다.
