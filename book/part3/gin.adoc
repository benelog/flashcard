= Gin 깊이 보기: 완성본의 라우팅·바인딩·미들웨어

이번 장에서는 HTTP API를 실제로 만드는 웹 프레임워크(web framework) Gin을 다룬다.
Gin을 고른 이유는 {ch-tech-choices}에서 정리했으므로, 여기서는 요청 하나가 Gin을 통과하는 길을 실제 코드로 좇는다.

브라우저가 API 주소로 요청을 보내면 Gin이 그 주소에 맞는 담당 함수를 찾고(라우팅), 요청은 그 함수에 닿기 전 인증 같은 공통 검사를 거친다(미들웨어).
담당 함수(핸들러)는 요청 본문을 읽고 데이터베이스를 다녀와 응답을 만든다.
핸들러 뒤의 저장소 계층과 앱 전체의 조립은 다음 {ch-app-assembly}에서 본다.

.[용어 풀이] HTTP 요청과 응답(메서드·상태 코드)
[NOTE]
====
브라우저와 서버가 주고받는, 형식이 정해진 편지다.
브라우저가 "이 주소의 것을 달라(GET)", "이것을 새로 만들어 달라(POST)"처럼 메서드로 요청을 보내면, 서버는 결과를 세 자리 상태 코드(성공은 200, 잘못된 요청은 400, 없는 자원은 404 등)로 답한다.
요청과 응답은 각각 부가 정보를 적는 헤더(header)와 실제 내용이 담기는 본문(body)으로 나뉜다.
봉투 겉면의 발신인이나 취급 주의 표시가 헤더이고, 그 안에 든 편지지가 본문이다.
====

== 라우팅과 핸들러

=== 라우트 그룹으로 인증 경계를 선언한다

다음은 `pkg/app/app.go`에서 미들웨어 선택부와 라우트 등록부를 발췌한 것이다.
어떤 주소가 어떤 핸들러로 연결되는지가 여기 모여 있다.

[source,go]
----
required := auth.Middleware(cfg.JWKSURL, cfg.JWTSecret)
optional := auth.OptionalMiddleware(cfg.JWKSURL, cfg.JWTSecret)
if cfg.AuthMode == "local" {
	required = auth.LocalMiddleware()
	optional = auth.LocalMiddleware()
}

r.GET("/api/healthz", h.Healthz)

pub := r.Group("/api", optional, func(c *gin.Context) {
	c.Header("Cache-Control", "no-store")
})
{
	pub.GET("/shared-decks", h.ListSharedDecks)
	pub.GET("/shared-decks/:slug", h.GetSharedDeck)
}

api := r.Group("/api", required, h.EnsureProfile())
{
	// ... 프로필 라우트 생략
	api.GET("/decks", h.ListDecks)
	api.POST("/decks", h.CreateDeck)
	// 덱은 UUID가 아니라 짧은 Base36 슬러그로 가리킨다.
	api.GET("/decks/:slug", h.GetDeck)
	api.PATCH("/decks/:slug", h.UpdateDeck)
	api.DELETE("/decks/:slug", h.DeleteDeck)
	api.GET("/decks/:slug/cards", h.ListDeckCards)
	// ...
	api.POST("/sessions", h.CreateSession)
	api.POST("/sessions/:id/reviews", h.RecordReview)
	// ...
}
----

라우팅이 세 구역으로 나뉜다.
서버가 살아 있는지 묻는 헬스 체크(health check)는 미들웨어 없이 루트에 직접 등록한다.
비로그인 사용자도 볼 수 있어야 하는 공유 덱 열람은, 토큰이 있으면 확인하되 없어도 거절하지 않는 `optional`이 붙은 `pub` 그룹에 둔다.
나머지 전부는 유효한 토큰을 요구하는 `required`가 붙은 `api` 그룹이다.

.[용어 풀이] 라우터와 라우팅
[NOTE]
====
들어온 요청의 주소(예: `/api/decks`)와 메서드를 보고 어느 처리 함수로 보낼지 정하는 교환대가 라우터다.
그 주소와 함수를 짝지어 주는 일을 라우팅이라 한다.
우편물의 주소를 보고 담당 부서로 보내는 우체국 분류대에 해당한다.
====

맨 위의 분기는 인증 방식을 설정으로 갈아 끼우는 스위치다.
기본값은 Supabase 토큰을 검증하는 미들웨어이고, 로컬 모드에서는 두 자리 모두 검증 없이 고정 사용자를 실어 주는 `auth.LocalMiddleware`로 바뀐다.
라우트 등록부는 어느 모드에서든 한 글자도 달라지지 않는다.

Gin의 그룹은 "접두사 + 미들웨어 묶음"일 뿐이라, 두 그룹처럼 같은 `/api` 접두사를 써도 최종 경로만 겹치지 않으면 엔드포인트마다 다른 인증 정책을 줄 수 있다.

.[용어 풀이] 엔드포인트
[NOTE]
====
요청을 받는 하나의 주소와 메서드 조합이다.
`GET /api/decks`(덱 목록)와 `POST /api/decks`(덱 생성)는 주소가 같아도 메서드가 달라 서로 다른 엔드포인트다.
====

`r.Group`의 두 번째 인자부터는 미들웨어를 필요한 개수만큼 받고, `pub` 그룹의 세 번째 인자처럼 그 자리에서 만든 익명 함수(anonymous function)를 끼워 넣을 수도 있다.
브라우저와 서버 사이에는 응답을 보관했다가 같은 주소의 다음 요청에 대신 돌려주는 공유 캐시(shared cache)가 놓일 수 있다.
공유 덱 목록은 로그인 여부에 따라 응답이 달라지므로, 로그인 사용자에게 "내 덱" 표시를 붙여 나간 목록을 공유 캐시가 다른 방문자에게 돌려주지 않도록 `Cache-Control: no-store`를 그룹 전체에 붙였다.
중괄호 블록 `{ ... }`는 문법적 의미가 없고, 그룹에 속한 라우트를 눈으로 구분하기 쉽게 하는 관례다.

=== gin.Context: 요청과 응답을 다루는 단일 창구

Gin 핸들러의 시그니처는 `func(c *gin.Context)` 하나다.
`gin.Context`는 요청 읽기(파라미터, 본문, 헤더)와 응답 쓰기(상태 코드, JSON), 미들웨어 간 데이터 전달까지 맡는다.

.[용어 풀이] 핸들러(Handler)
[NOTE]
====
특정 엔드포인트로 온 요청을 실제로 처리해 응답을 만들어 내는 함수다.
라우터가 배달한 요청을 넘겨받아 일을 끝내는 담당 직원에 해당한다.
====

가장 단순한 핸들러는 서버가 살아 있는지 묻는 요청에 "정상이다"라고만 답하는 `internal/handlers/handlers.go`의 헬스 체크다.

`c.JSON`은 인자를 JSON으로 직렬화하고 Content-Type 헤더(본문이 어떤 형식인지 알리는 헤더)와 상태 코드를 설정한다.
`gin.H`는 맵 `map[string]any`({ch-go-types})의 짧은 별명이라, 일회성 응답을 만들 때 구조체를 따로 선언하지 않아도 된다.

.[용어 풀이] 바인딩(Binding)
[NOTE]
====
{ch-gin-hello}에서 `c.JSON`으로 처음 본 JSON이 여기서는 서버와 브라우저가 데이터를 주고받는 형식으로 쓰인다.
바인딩은 그렇게 들어온 JSON 텍스트를 프로그램이 다루는 구조체의 각 칸에 채워 넣는 일이다.
택배 송장의 항목을 창고 대장의 정해진 칸에 옮겨 적는 것과 같고, 칸에 맞지 않는 값은 그 자리에서 걸러 낼 수 있다.
====

요청은 본문뿐 아니라 주소에도 값을 실어 온다.

.[용어 풀이] 경로 파라미터와 쿼리 파라미터
[NOTE]
====
둘 다 요청 주소에 값을 실어 보내는 방법이지만 값이 앉는 자리가 다르다.
경로 파라미터(path parameter)는 주소의 한 칸 자체가 값인 경우로, `/api/decks/ab3f`에서 덱마다 달라지는 `ab3f` 자리가 그것이다.
쿼리 파라미터(query parameter)는 주소 뒤에 물음표를 붙여 덧대는 부가 조건으로, `?dueBefore=2026-07-12T09:00:00Z`처럼 `이름=값` 형태로 적고 여러 개면 `&`로 잇는다.
무엇을 가리키는지는 경로에, 결과를 어떻게 걸러 볼지는 쿼리에 적는 것이 보통이다.
====

경로 파라미터는 `c.Param`으로 읽는다.
`internal/handlers/decks.go`의 덱 단건 조회다.

[source,go]
----

라우트의 `:slug` 자리에 매칭된 값을 `c.Param("slug")`로 꺼낸다.
`c.Request.Context()`로 꺼내 스토어에 넘기는 표준 `context.Context`는 이름만 닮았을 뿐 `gin.Context`와 다른 물건으로, "이 일은 그만해도 된다"는 취소 소식을 함수에서 함수로 실어 나르는 값이다.
클라이언트가 요청을 중단하면 이 컨텍스트가 취소되어 진행 중인 DB 쿼리도 함께 멈춘다.

쿼리 파라미터는 `c.Query`로 읽는다.
`internal/handlers/sessions.go`의 복습 대기 카드 수 조회 `DueCount`의 일부다.

[source,go]
----
// 기본 만기 창은 방문자(?tz=) 시간대의 오늘 끝. 홈 화면 배지와 같은 수가
// 나오게 하기 위해서다.
_, loc := clientLocation(c)
dueBefore := study.EndOfDay(time.Now(), loc)
if raw := c.Query("dueBefore"); raw != "" {
	t, err := time.Parse(time.RFC3339, raw)
	if err != nil {
		badRequest(c, "dueBefore must be RFC3339")
		return
	}
	dueBefore = t
}
// ... 스토어 조회 후 c.JSON으로 {"count": n} 응답
----

파라미터가 없으면 방문자의 시간대에서 오늘이 끝나는 시각을 기본값으로 쓰고, 있으면 RFC3339(`2026-07-12T09:00:00Z` 같은 국제 표준 표기)로 파싱해 실패 시 400으로 응답한다.
"없으면 기본값, 있으면 검증"이 선택적 쿼리 파라미터를 다루는 전형적인 패턴이다.

JSON이 아닌 응답도 가능하다.
`internal/handlers/cards.go`의 CSV 내보내기 핸들러 `ExportDeck`은 `gin.Context`가 감싼 응답 스트림 `c.Writer`를 `internal/cardcsv`에 그대로 넘기고, 받은 쪽은 표준 라이브러리의 `csv.Writer`로 카드를 한 줄씩 흘려보낸다.
CSV 전체를 메모리에 쌓아 둘 필요가 없고, `c.Writer`가 Go 표준의 응답 쓰기 규격(`http.ResponseWriter`)을 따르므로 표준 라이브러리의 부품을 곧바로 끼울 수 있다.

== 요청 바인딩과 검증

=== ShouldBindJSON과 익명 구조체

요청 본문을 받는 기본 패턴을 `internal/handlers/decks.go`의 덱 생성에서 보자.
덱 이름과 설명을 JSON으로 받아 검증한 뒤 새 덱을 만들어 응답하는 핸들러다.

[source,go]
----
include::../../flashcard-advanced/internal/handlers/decks.go[tag=create-deck]
----

요청 본문 타입은 핸들러 안의 익명 구조체(anonymous struct)로 선언했다.
`var body struct { ... }` 한 줄이 타입 선언과 변수 선언을 겸하고, 이 필드 조합은 다른 곳에서 쓸 일이 없다.

Gin의 `BindJSON`은 파싱 실패 시 스스로 400 응답을 쓰지만, `ShouldBindJSON`은 에러만 반환하므로 Flashcard는 에러 메시지 형식을 직접 통제하려고 이쪽만 쓴다.

검증도 `strings.TrimSpace(body.Name) == ""` 같은 코드로 직접 한다.
Gin에는 `binding:"required"` 같은 구조체 태그로 규칙을 적는 기능도 있지만, 공백만 있는 이름 거부처럼 태그로 표현하기 애매한 규칙이 있고 에러 메시지를 직접 쓰고 싶었다.
태그 하나로 적히는 규칙이 대부분이고 기본 에러 문구로 충분하다면 태그 방식이 코드를 줄여 준다.

부분 수정(PATCH)에서는 포인터 필드가 쓰인다.
같은 파일에서 요청에 담겨 온 필드만 골라 고치는 덱 수정 핸들러다.

[source,go]
----
func (h *Handlers) UpdateDeck(c *gin.Context) {
	// ...
	var body struct {
		Name        *string `json:"name"`
		Description *string `json:"description"`
	}
	// ... ShouldBindJSON 생략
	if body.Name != nil && strings.TrimSpace(*body.Name) == "" {
		badRequest(c, "name cannot be empty")
		return
	}
	// ...
}
----

필드를 `*string`으로 선언하면 "JSON에 키가 없었다(nil)"와 "빈 문자열이 왔다"를 구분할 수 있다.
그래서 `name`을 보내지 않으면 이름을 그대로 두고, 보냈는데 공백이면 거부할 수 있다.

`toInput`은 HTTP 입력 타입 `cardBody`를 검증하면서 스토어 계층의 입력 타입 `model.CardInput`으로 바꾸고, 두 번째 반환값으로 검증 실패 사유를 돌려준다(빈 문자열이면 통과).

어긋난 값의 처리는 입구마다 달라서, 프로그램이 보내는 API 요청은 오타를 400으로 알리고, 사람이 채우는 폼과 CSV는 `model.NormalizeCardType`으로 기본 종류를 채워 등록을 살린다.

일괄 등록 핸들러 `BulkCreateCards`도 같은 함수를 행 단위로 쓰지만, 불량 행을 만나도 400을 내지 않는다.
CSV에서 파싱한 최대 2,000행(`model.MaxBulkCards`) 가운데 불량 행만 건너뛰고 나머지를 저장한 뒤, 건너뛴 개수를 `invalid`로 응답에 담는다.

`badRequest`는 요청을 보낸 쪽의 잘못(400)을 알리고, `fail`은 스토어가 돌려준 에러가 `model.ErrNotFound`면 404를, 그 밖이면 상세를 로그에만 남긴 채 "internal error" 메시지로 500을 준다.
남은 401은 인증 미들웨어가 맡으므로, 이 앱의 JSON API가 내는 오류 상태 코드는 이 넷이 전부다.
테이블 이름이나 SQL 조각이 담긴 DB 에러 문장을 화면에 그대로 보여 주면 공격자에게 내부 구조를 알려 주게 된다.

Gin 핸들러는 에러를 반환하지 않으므로({ch-tech-choices}), 도우미 호출 뒤 `return`하는 패턴이 모든 핸들러에 반복된다.
Echo였다면 `return err` 한 줄로 중앙 에러 핸들러에 위임했을 대목이지만, 어디서 어떤 상태 코드가 나가는지 핸들러 안에서 다 보인다는 이점도 있다.

== 미들웨어

=== 미들웨어는 등록 순서대로 실행되는 체인이다

Gin에서 미들웨어(middleware)와 핸들러는 같은 타입 `gin.HandlerFunc`이고, 한 요청에 매칭된 함수들이 등록 순서대로 배열을 이뤄 실행된다.
미들웨어 안에서 `c.Next()`를 호출하면 체인의 다음 함수로 진행하고, `c.Abort()`를 호출하면 남은 체인을 건너뛴다.

.[용어 풀이] 미들웨어(Middleware)
[NOTE]
====
요청이 최종 처리 함수(핸들러)에 닿기 전에 반드시 거치는 중간 관문이다.
신분증을 확인하는 검문소처럼, 로그인 검사같이 여러 요청에 공통으로 필요한 처리를 핸들러 앞에서 대신 맡는다.
여러 관문을 순서대로 세워 두고, 한 곳에서 막히면 뒤는 건너뛴다.
====

Flashcard에서 인증이 필요한 요청 하나가 지나는 체인은 다음과 같다.

. `gin.Recovery()`: 패닉(코드의 전제가 깨져 프로그램이 그 자리에서 실행을 중단하는 오류)을 잡아 500으로 변환한다(전역).
. `auth.Middleware`: JWT 검증, 사용자 ID를 컨텍스트에 저장(그룹).
. `h.EnsureProfile()`: 프로필 행이 아직 없으면 이때 만든다(그룹).
. 최종 핸들러.

=== JWT 인증 미들웨어: 컨텍스트에 사용자 ID를 싣는다

인증 미들웨어는 토큰을 검증하고, 통과하면 사용자 ID를 요청 컨텍스트에 실어 준다.
`internal/auth/jwt.go`의 핵심부다.

[source,go]
----
const userIDKey = "auth.userID"

// Middleware는 Supabase 액세스 토큰을 검증하고 사용자 ID를 컨텍스트에 싣는다.
func Middleware(jwksURL, secret string) gin.HandlerFunc {
	return func(c *gin.Context) {
		raw := bearerToken(c)
		if raw == "" {
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "missing bearer token"})
			return
		}
		kf, err := keyfuncFor(jwksURL, secret)
		// ... 검증 키 준비 실패 시 500 응답 (생략)
		userID, err := parseUserID(raw, kf)
		if err != nil {
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "invalid token"})
			return
		}
		c.Set(userIDKey, userID)
		c.Next()
	}
}

func UserID(c *gin.Context) uuid.UUID {
	return c.MustGet(userIDKey).(uuid.UUID)
}
----

`Middleware`는 설정값을 받아 `gin.HandlerFunc`를 반환하는 팩토리 함수(factory function)이고, 반환된 함수는 `jwksURL`과 `secret`을 기억한 채 도는 클로저(closure)다.
미들웨어에 인자를 넘기고 싶을 때 쓰는 Gin의 표준 관용구다.

.[용어 풀이] 팩토리 함수(Factory Function)와 클로저(Closure)
[NOTE]
====
팩토리 함수는 값이 아니라 함수를 만들어 돌려주는 함수다.
클로저는 그렇게 만들어진 함수가 자기가 태어난 자리의 변수들을 기억한 채 살아 있는 것을 말한다.
Gin의 미들웨어처럼 "인자를 하나만 받는 함수"라는 규격을 지켜야 하는 자리에 설정값을 딸려 보내고 싶을 때 이 조합을 쓴다.
====

먼저 Authorization 헤더에서 Bearer 토큰을 꺼내고, 없으면 `c.AbortWithStatusJSON`으로 401을 응답하며 체인을 끊는다.
토큰은 Supabase가 발급한 JWT(JSON Web Token), 곧 위조를 막는 서명이 붙은 디지털 출입증이다.
`parseUserID`는 서명, 유효 기간, 수신자(audience)를 검증한 뒤 토큰의 subject 항목(클레임)에서 사용자 UUID를 얻는다.
검증의 원리는 {ch-token-verification}에서, Supabase 인증 체계는 {ch-supabase-auth}에서 다룬다.
이 장에서 중요한 것은 검증에 성공하면 `c.Set(userIDKey, userID)`로 사용자 ID를 요청 컨텍스트에 저장하고 `c.Next()`로 진행하는 마지막 두 줄이다.

이후의 모든 핸들러는 `auth.UserID(c)` 한 줄로 지금 요청한 사용자를 얻는다.
앞의 핸들러들에서 `h.Store.ListDecks(ctx, auth.UserID(c))`처럼 스토어 호출마다 첫 인자로 들어가던 값이고, 모든 쿼리에 조건으로 들어간다.
그래서 누군가 남의 덱 주소를 알아내 요청해도 쿼리 결과가 비어 404가 된다.

`UserID`가 값이 없으면 패닉을 일으키는 `c.MustGet`을 쓰는 것은, 인증 미들웨어 뒤에서 값이 없다면 라우팅 구성 버그라서 크게 실패해야 빨리 드러나기 때문이다.

공개 엔드포인트용 `OptionalMiddleware`는 토큰이 유효하면 사용자 ID를 실어 주고 없거나 무효면 거절 없이 통과시킨다.
핸들러는 `auth.OptionalUserID(c)`로 "로그인했으면 UUID, 아니면 uuid.Nil"을 받아 공유 덱 목록의 "내 덱" 표시에 쓴다.

로컬 모드의 `auth.LocalMiddleware`(`internal/auth/local.go`)는 검증 없이 모든 요청에 미리 정해 둔 사용자 ID를 싣지만, `c.Set(userIDKey, ...)`라는 계약은 그대로 지키므로 핸들러는 두 모드를 구분할 필요가 없다.
검증 없는 인증이 왜 로컬에서만 허용되는지는 {ch-token-verification}에서 다룬다.

=== 도메인 로직도 미들웨어가 될 수 있다

미들웨어가 인증·로깅처럼 모든 요청에 걸치는 일 전용은 아니다.
`internal/auth/profile.go`의 `EnsureProfile`은 요청한 사용자의 프로필 행이 DB에 없으면 만들어 두고, 한 번 확인한 사용자는 다시 조회하지 않는다.

덱과 카드 테이블은 profiles 테이블을 외래 키로 참조하므로 첫 쓰기 전에 프로필 행이 있어야 한다.
이를 핸들러마다 챙기는 대신 인증 그룹 전체에 미들웨어로 걸어 "인증된 사용자는 반드시 프로필이 있다"는 불변식(invariant, 언제나 참이라고 보장되는 조건)을 만들었다.
클로저 안의 `sync.Map`이 이미 확인한 사용자를 적어 두므로, 서버가 살아 있는 동안 사용자 한 명당 DB를 한 번만 확인한다.

이 미들웨어는 JSON API와 웹 화면이 함께 쓰는데(화면 쪽은 {ch-supabase-auth}), 실패를 JSON으로 알릴지 오류 페이지로 알릴지는 `fail` 인자로 받는다.
라우트 등록부의 `h.EnsureProfile()`은 여기에 JSON 오류 응답을 끼운 얇은 메서드다.

저장소는 `model.Store` 전체가 아니라 이 미들웨어가 부르는 메서드 하나만 담은 `profileStore` 인터페이스로 받는다.
Go에서는 인터페이스를 쓰는 쪽에서 필요한 만큼만 정의하는 것이 관용구이고, 그러면 시그니처가 "저장소의 무엇을 건드리는가"를 알려 주며 테스트도 메서드 하나만 채운 스텁으로 충분하다.

== 에이전트 활용 아이디어

새 엔드포인트는 기존 코드를 본보기로 지목하며 시키는 것이 가장 정확하다.
"태그 목록 API를 추가해 달라. 요청 검증과 에러 응답은 덱 목록 핸들러의 방식을 따르라"처럼 저장소 안의 관례를 참조점으로 준다.

"`pkg/app`의 라우트 등록을 읽어 메서드·경로·핸들러 표로 정리해 달라"는 지시는 자주 쓰는 지시문으로 저장해 두고 API가 늘 때마다 불러 쓸 만하다.

== 정리

net/http·chi·Echo 같은 대안과의 비교는 {ch-alternatives}에 있다.

라우트 그룹이 인증 경계를 정하고, 핸들러는 `gin.Context` 하나로 파라미터를 읽고 `c.JSON`으로 응답한다.
요청 본문은 `ShouldBindJSON`으로 받고 검증은 코드로 직접 하며, 에러 응답은 `badRequest`와 `fail`로 통일한다.
미들웨어 체인은 Recovery, JWT 인증(로컬 모드에서는 고정 사용자), 프로필 보장 순으로 흐르고, 인증 미들웨어가 실어 준 사용자 ID를 모든 핸들러가 `auth.UserID(c)`로 꺼내 쓴다.

다음 {ch-app-assembly}에서는 이 조각들이 한 벌의 앱으로 조립되어 내 컴퓨터의 서버와 Vercel 함수가 같은 엔진을 나눠 쓰는 구조를 본다.
