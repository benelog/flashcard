= 데이터베이스 설계: 요구사항에서 테이블로

애플리케이션에서는 코드보다 데이터의 수명이 길다.
프레임워크는 갈아탈 수 있어도 쌓인 학습 기록은 버릴 수 없으므로, 데이터베이스 설계는 앱 전체에서 가장 신중해야 할 결정이다.
관계형 데이터베이스와 SQLite·PostgreSQL을 고른 이유는 {ch-tech-choices}에서, 테이블과 키·SQL·인덱스의 기초는 {ch-database-basics}에서 다뤘다.
이 장에서는 {ch-requirements}의 요구사항에서 엔티티를 뽑고, 관계와 제약을 걸고, 조회 패턴에서 인덱스를 역산하는 과정을 로컬 모드의 SQLite 스키마로 따라가 보겠다.
이 앱에만 있는 설계(간격 반복 상태, 덱 주소)는 {ch-domain-model}에서, 운영 PostgreSQL의 전용 타입과 장치는 {ch-supabase-db}에서 다룬다.

== 요구사항에서 테이블을 도출하다

{ch-requirements}의 기능 요구사항은 양방향 카드와 덱·태그, 학습 세션(맞음/틀림 자가 판정, 재도전 라운드), 간격 반복, 통계, 스마트 덱, 덱 공유가 핵심이다.
요구사항 문장에서 '사용자', '덱', '카드'처럼 데이터로 남겨야 할 실체를 골라내면 그 하나하나가 테이블 하나가 된다.
이렇게 골라낸 실체를 엔티티(entity)라 부른다.

.[용어 풀이] 엔티티(Entity)
[NOTE]
====
앱이 데이터로 남겨 두어야 할 실체 하나하나를 가리키는 말이다.
사용자·덱·카드처럼 여럿 존재하면서 각각을 구별해 저장해야 하는 대상이 엔티티이고, 엔티티 하나가 보통 테이블 하나가 된다.
'학습한다' 같은 행위는 엔티티가 아니지만, 그 기록(학습 세션, 복습 기록)을 남겨야 한다면 기록이 엔티티가 된다.
====

* *사용자*: 로컬 모드에서는 나 하나뿐이지만 표시 이름과 설정을 담을 자리가 필요하다 → `profiles`.
* 카드의 묶음인 *덱*과 학습 단위인 *카드*(태그는 카드의 속성으로 본다) → `decks`, `cards`.
* 카드마다 붙는 *간격 반복 상태*(다음 복습 시각, 그 카드가 얼마나 쉽게 외워지는지 나타내는 용이도 등, {ch-domain-model}) → `card_srs`.
* 학습의 단위인 *세션*과, 세션 안에서 카드 한 장에 매긴 판정 하나하나인 *복습 기록* → `study_sessions`, `review_logs`.
* "오답률 높은 카드"처럼 조건으로 정의되는 가상의 덱인 *스마트 덱* → `smart_decks`.

이렇게 도출된 {n-tables-ko-attr} 개 테이블이 `internal/litestore/schema.sql` 한 파일에 담겨 있다.
서버가 시작할 때 이 파일을 통째로 실행하는데, 모든 문장이 `if not exists`라서 몇 번을 다시 시작해도 안전하다.

=== 사용자, 덱, 카드

`internal/litestore/schema.sql`의 앞부분으로, `profiles`(사용자)·`decks`(덱)·`cards`(카드) 세 테이블을 만드는 코드다.

[source,sql]
----
create table if not exists profiles (
  id text primary key,
  display_name text,
  settings text not null default '{}',
  created_at text not null
);

create table if not exists decks (
  id text primary key,
  user_id text not null references profiles(id) on delete cascade,
  name text not null,
  description text,
  story text,
  share_slug text,
  shared_at text,
  seq integer not null unique,
  created_at text not null,
  updated_at text not null
);

create table if not exists cards (
  id text primary key,
  user_id text not null references profiles(id) on delete cascade,
  deck_id text not null references decks(id) on delete cascade,
  text text not null,
  meaning text not null,
  card_type text not null default 'word'
    check (card_type in ('word', 'sentence', 'idiom', 'concept')),
  tags text not null default '[]',
  phonetic text,
  example text,
  notes text,
  created_at text not null,
  updated_at text not null
);
----

`profiles.id`에는 `default`가 없다.
로그인한 사용자의 식별자를 그대로 받아 쓰기 때문이다(로컬 모드는 고정 UUID인 `internal/auth/local.go`의 `LocalUserID`, 운영은 Supabase Auth가 발급한 UUID).
인증 시스템과 앱 데이터의 식별자가 같으므로 인증된 사용자 ID로 바로 조회할 수 있다({ch-supabase-auth}).

태그는 별도 테이블이 아니라 카드의 열 하나로, `["toeic", "동사"]` 같은 JSON 배열 텍스트를 담는다.
정석적인 정규화라면 `tags` 테이블과 `card_tags` 연결 테이블을 두겠지만, 이 앱의 태그에는 이름 변경이나 태그별 설명 같은 요구 없이 "이 태그가 붙은 카드 찾기"만 있어 테이블 수와 조인을 줄였다.
태그 자체가 관리 대상이 되면 연결 테이블로 옮기는 것이 맞다.
사용자 설정 `profiles.settings`와 스마트 덱 규칙도 같은 JSON 텍스트다(운영 PostgreSQL에는 배열 타입 `text[]`과 JSON 전용 타입 jsonb가 있다).

`cards`에 `deck_id`뿐 아니라 `user_id`도 둔 것은 실용적 비정규화(denormalization, {ch-database-basics})다.
"오늘 복습" 목록(이 책이 앞으로 due 큐라고 부르는 것)과 스마트 덱처럼 덱을 거치지 않고 "이 사용자의 모든 카드"를 자주 조회하므로, 조인을 한 단계 줄였다.

`card_type`의 `check` 제약은 뒤의 제약 절에서, `decks`의 `share_slug`·`shared_at`·`seq`가 받치는 덱 공유와 URL 슬러그는 {ch-domain-model}에서 다룬다.

=== 카드와 SRS 상태의 분리

카드의 간격 반복 상태, 곧 SRS(Spaced Repetition System) 상태만 따로 담는 `card_srs` 테이블을 만드는 코드다.

[source,sql]
----
create table if not exists card_srs (
  card_id text primary key references cards(id) on delete cascade,
  user_id text not null references profiles(id) on delete cascade,
  ease_factor real not null default 2.5,
  interval_days real not null default 0,
  repetitions integer not null default 0,
  lapses integer not null default 0,
  due_at text not null,
  last_reviewed_at text,
  correct_count integer not null default 0,
  incorrect_count integer not null default 0
);
----

SRS 상태를 `cards`의 칼럼으로 넣지 않고 1:1 테이블로 분리했다.
`card_id`가 외래 키이면서 기본 키라서 "카드당 상태는 정확히 하나"가 스키마 수준에서 보장된다.

분리한 이유는 바뀌는 때가 다르기 때문이다.
카드 내용은 사용자가 편집할 때만 바뀌지만 SRS 상태는 복습할 때마다 갱신된다.
둘이 한 행에 있으면 복습을 기록할 때마다 카드 본문 행에 잠금(lock)이 걸리고, 분리하면 여러 요청이 동시에 도는 운영 DB에서 잠금 경합의 범위가 좁아진다.

.[용어 풀이] 잠금(Lock)
[NOTE]
====
DB가 어떤 행을 고치는 동안 그 행에 걸어 두는 표시로, 잠금이 풀릴 때까지 같은 행을 고치려는 다른 작업은 기다린다.
두 갱신이 서로의 결과를 덮어쓰는 사고를 막는 대신, 여러 요청이 같은 행에 몰릴수록 줄을 서서 기다리는 시간(잠금 경합)이 길어진다.
그래서 자주 갱신되는 데이터를 어느 행에 둘 것인가가 설계 문제가 된다.
====

숫자 칼럼들의 기본값 덕분에 행을 만들 때는 `card_id`, `user_id`, `due_at`만 넣으면 "지금 바로 복습 대상인 새 카드" 상태로 시작한다.
`due_at`에 현재 시각 기본값이 없는 것은 SQLite의 `current_timestamp` 형식(`2026-07-11 09:30:00`)이 이 앱의 표기(`2026-07-11T09:30:00.000Z`)와 달라서다.
이 스키마의 시각은 전부 Go가 만들어 넣는다(뒤의 시각 절).

=== 학습 세션과 리뷰 로그

학습 세션과 판정 하나하나를 남기는 복습 기록, 두 테이블을 만드는 코드다.

[source,sql]
----
create table if not exists study_sessions (
  id text primary key,
  user_id text not null references profiles(id) on delete cascade,
  mode text not null check (mode in ('deck', 'due', 'smart')),
  direction text not null default 'text_to_meaning'
    check (direction in ('text_to_meaning', 'meaning_to_text')),
  deck_id text references decks(id) on delete set null,
  smart_rule text,
  total_cards integer not null default 0,
  started_at text not null,
  ended_at text,
  completed integer not null default 0
);

create table if not exists review_logs (
  id integer primary key autoincrement,
  user_id text not null references profiles(id) on delete cascade,
  card_id text not null references cards(id) on delete cascade,
  session_id text references study_sessions(id) on delete set null,
  result integer not null,
  is_retry integer not null default 0,
  reviewed_at text not null
);
----

`study_sessions.mode`는 학습 방식(덱 전체, due 큐, 스마트 덱)을 구분하고, 허용 값은 `check` 제약으로 지킨다.
`direction`은 학습 방향이다(`text_to_meaning`은 단어나 문장을 보고 뜻을 떠올리고, `meaning_to_text`는 그 반대다).
양방향 학습이라는 요구를 카드 두 장이 아니라 세션의 열 하나로 소화했다(방향을 학습 세션의 속성으로 본 판단이다).
스마트 덱으로 시작한 세션은 그 시점의 규칙을 `smart_rule`에 JSON 텍스트 스냅샷으로 남기므로, 규칙이 나중에 수정되거나 삭제돼도 "그때 무엇을 학습했는지"가 보존된다.

`review_logs`는 판정 한 번이 행 하나인 순수 추가(append) 테이블로, `result`는 맞음/틀림, `is_retry`는 재도전 라운드 여부다.
재도전 라운드의 판정은 기록만 남기고 SRS에는 반영하지 않으므로({ch-requirements}), 정답률을 세는 통계 쿼리는 `is_retry = 0` 조건으로 첫 판정만 골라낸다.
`completed`·`result`·`is_retry`가 integer인 것은 SQLite에 boolean 전용 타입이 없어 참/거짓을 0과 1로 담기 때문이다(운영 PostgreSQL에는 boolean 타입이 있다).

=== 스마트 덱과 통계 뷰

조건으로 정의되는 스마트 덱 테이블과, 카드와 SRS 상태를 합쳐 보여 주는 통계용 뷰를 만드는 코드다.

[source,sql]
----
create table if not exists smart_decks (
  id text primary key,
  user_id text not null references profiles(id) on delete cascade,
  name text not null,
  rule text not null,
  created_at text not null
);

create view if not exists cards_with_stats as
select
  c.id, c.user_id, c.deck_id, c.text, c.meaning, c.card_type,
  c.tags, c.phonetic, c.example, c.notes, c.created_at,
  s.ease_factor, s.interval_days, s.repetitions, s.lapses, s.due_at,
  s.last_reviewed_at, s.correct_count, s.incorrect_count,
  (s.correct_count + s.incorrect_count) as attempts,
  case when s.correct_count + s.incorrect_count = 0 then 0.0
       else cast(s.incorrect_count as real) / (s.correct_count + s.incorrect_count)
  end as error_rate
from cards c
join card_srs s on s.card_id = c.id;
----

스마트 덱은 카드 ID 목록이 아니라 규칙(JSON 텍스트)만 저장하고, 학습을 시작하는 순간 규칙을 쿼리로 바꿔 실행하므로 고르는 카드는 항상 최신 상태다.
그 쿼리가 조회하는 `cards_with_stats` 뷰(view)는 카드 내용과 SRS 상태를 조인하고 시도 횟수(`attempts`)와 오답률(`error_rate`)을 파생 칼럼으로 계산해 둔다.
"오답률 0.4 이상" 같은 규칙 조건과 store 계층(DB를 읽고 쓰는 Go 코드, {ch-core-logic}·{ch-app-assembly})의 카드 조회가 모두 이 뷰를 보므로, 오답률 계산식이 한 곳에만 있다.

.[용어 풀이] 뷰(View)
[NOTE]
====
자주 쓰는 select 문에 이름을 붙여 스키마에 저장해 두고, 테이블처럼 조회할 수 있게 만든 것이다.
데이터를 복사해 두지 않고 조회할 때마다 저장된 select 문이 실행되므로, 뷰가 보여 주는 값은 언제나 원본 테이블의 최신 상태다.
여러 코드가 같은 계산식을 베껴 쓰는 일을 막아 주지만, DB가 뷰의 정의를 펼쳐 실행하므로 원본 테이블을 직접 조회할 때와 실행 계획이 달라질 수 있다.
====

규칙을 쿼리로 바꾸는 함수는 `internal/litestore/rules.go`의 `ruleQuery`다.
규칙의 값은 SQL 문자열에 이어 붙이지 않고, 문장에는 자리표시자 `?`만 적은 뒤 값을 따로 전달한다(바인딩, {ch-database-basics}의 SQL 인젝션 방지 원칙).
태그 규칙은 JSON 배열의 원소를 행처럼 펼쳐 주는 SQLite 함수 `json_each`로 "카드의 태그 가운데 찾는 태그와 일치하는 것이 있는가"를 묻는다.
운영 PostgreSQL에서는 배열 타입의 겹침(overlap) 연산자가 같은 질문을 처리한다.

== 스키마 설계 요소

위 스키마의 열 타입은 text, integer, real 세 가지뿐이다.
SQLite에는 uuid도, 타임스탬프도, 배열도, enum도 전용 타입이 없다.
그래서 이 스키마의 상당 부분은 "전용 타입이 없는 자리에 설계 의도를 어떻게 담는가"의 답이다.

=== 기본 키 전략: UUID를 text에 담는다

사용자에게 노출될 수 있는 여섯 테이블(`profiles`, `decks`, `cards`, `card_srs`, `study_sessions`, `smart_decks`)의 기본 키는 UUID를 담은 `text primary key`이고, 내부 로그 테이블인 `review_logs`만 `integer primary key autoincrement`라는 순번이다.

UUID를 기본으로 삼은 이유는 셋이다.
첫째, 순번 키는 값 자체가 정보를 누설한다.
`/cards/42` 같은 URL에서는 전체 카드 수가 드러나고 이웃 ID도 추측할 수 있지만, UUID는 추측할 수 없다.
둘째, 값이 전역에서 유일하므로 로컬 SQLite 파일의 데이터를 운영 DB로 옮겨도 ID를 다시 매길 필요가 없다.
셋째, 운영의 인증 시스템(Supabase Auth)이 사용자를 UUID로 식별하므로 `profiles.id`와 자연스럽게 이어진다.

SQLite에는 uuid 타입도, UUID를 만드는 함수도 없으므로 ID는 text 열에 담고 값은 Go가 만든다.
`internal/litestore/cards.go`에서 발췌한, 카드 한 장과 그 SRS 행을 만들어 넣는 함수다.
새 UUID와 시각을 Go에서 만들어 insert에 바인딩한다.

[source,go]
----
// insertCard는 tx 안에서 카드와 그 SRS 행을 넣는다. internal/pgstore에 같은
// 이름의 짝이 있다: 그쪽은 열 기본값(gen_random_uuid(), now())이 id와 시각을
// 만들고, SQLite에는 그런 기본값이 없어 여기서 만든다.
func insertCard(ctx context.Context, tx *sql.Tx, userID uuid.UUID, in model.CardInput, now string) (uuid.UUID, error) {
	cardID := uuid.New()
	_, err := tx.ExecContext(ctx,
		`insert into cards (id, user_id, deck_id, text, meaning, card_type, tags,
		                    phonetic, example, notes, created_at, updated_at)
		 values (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)`,
		cardID.String(), userID.String(), in.DeckID.String(), in.Text, in.Meaning,
		in.CardType, tagsJSON(in.Tags), in.Phonetic, in.Example, in.Notes, now, now)
	if err != nil {
		return uuid.Nil, err
	}
	_, err = tx.ExecContext(ctx,
		`insert into card_srs (card_id, user_id, due_at) values (?, ?, ?)`,
		cardID.String(), userID.String(), now)
	return cardID, err
}
----

첫 인자 `ctx`는 요청 하나의 수명을 담아 함수에서 함수로 전달되는 컨텍스트(context)로, 요청이 끊기면 진행 중인 질의도 멈추라는 신호를 나른다({ch-gin}, {ch-template-hello}의 템플릿 "컨텍스트"와는 이름만 같다).
`tx`는 여러 SQL 문장을 전부 되거나 전부 안 되게 하나로 합치는 트랜잭션의 값이다({ch-domain-model}).

UUID에도 비용이 있다.
SQLite에서는 36자 텍스트로 저장돼 자리를 더 차지하고(PostgreSQL의 uuid 타입은 16바이트), 값이 무작위라 새 행이 인덱스의 정렬 순서상 매번 다른 위치에 꽂힌다.
인덱스는 값을 정렬해 보관하는 구조({ch-database-basics}의 B-tree)라, 서류철 맨 뒤에 붙이는 대신 매번 중간을 벌려 끼워 넣는 셈이다.
그래서 빠르게 대량으로 쌓이고 외부에 노출되지 않는 `review_logs`에는 순번을 썼다.
운영 스키마도 "노출되는 것은 UUID, 내부 대량 로그는 순번"이라는 같은 전략을 쓴다.

=== 외래 키와 ON DELETE 정책

모든 관계에는 외래 키가 걸려 있고, 삭제 정책은 두 가지로 나뉜다.
일곱 테이블과 그 사이의 외래 키를 그림 14에 모았다.

![profiles, decks, cards, card_srs, study_sessions, review_logs, smart_decks 일곱 테이블 상자를 실선과 점선의 외래 키 화살표로 이은 그림](/screenshots/er-diagram.png)

</div>

<p class="fc-caption">그림 14 일곱 테이블의 관계. 실선은 <code>on delete cascade</code>인 소유 관계, 점선은 <code>on delete set null</code>인 참조 관계다. 모든 테이블에 있는 <code>user_id</code>에서 <code>profiles</code>로 가는 선은 생략했다.</p>
++++

소유 관계는 `on delete cascade`다.
사용자를 지우면 덱·카드·SRS 상태·세션·로그가 연쇄 삭제되고, 덱을 지우면 카드가, 카드를 지우면 SRS 상태와 리뷰 로그가 따라 지워진다.
"부모 없이 존재할 수 없는 데이터"의 삭제를 DB에 맡긴 덕분에 store 계층의 `DeleteDeck`은 `delete from decks where user_id = ? and id = ?` 한 문장으로 끝난다.

참조 관계는 `on delete set null`이다.
`study_sessions.deck_id`와 `review_logs.session_id`가 그렇다.
덱을 지웠다고 그 덱으로 학습한 세션 기록까지 지우면 통계 요구사항에 어긋나므로, 기록은 남기고 참조만 끊는다.
그래서 두 열은 NULL을 허용한다.

cascade는 편리한 만큼 파괴력도 크다.
연쇄 삭제가 무섭다면 `on delete restrict`로 막고 애플리케이션에서 명시적으로 지우는 대안도 있지만, 이 앱은 소유 관계가 `profiles`→`decks`→`cards`→`card_srs`·`review_logs`의 세 단계뿐이라 cascade를 택했다.

SQLite는 옛 버전과의 호환 때문에 외래 키 강제를 꺼 둔 채 출발하므로, 접속할 때마다 `foreign_keys` 프래그마(pragma, 접속 단위 설정)로 켜야 한다.
이 앱은 DB 파일을 여는 접속 문자열에 이 설정을 붙여 둔다(`internal/litestore/store.go`의 `Open`).
잊으면 cascade와 참조 검사가 전부 조용히 무시된다.

=== NOT NULL, check, UNIQUE: 제약을 DB에 맡긴다

필수 값은 모두 `not null`이고, 일부에는 `default`가 함께 붙어 있다.
`not null default`는 "값이 없으면 안 되지만 호출자가 매번 챙길 필요는 없다"는 뜻이라 insert 문이 짧아진다.

값의 범위 제한은 text 열에 `check` 제약을 붙여 해결했다(`card_type`, `mode`, `direction`).
허용 값 목록이 스키마 자체에 문서로 남고, 목록에 없는 값은 insert 시점에 거부된다.
운영 PostgreSQL은 값 목록을 아예 타입으로 만드는 enum으로 같은 제한을 건다.
enum은 값을 더할 때는 `alter type ... add value` 한 줄이면 되지만, 값을 빼는 문장은 없어 타입을 새로 만들어 갈아 끼워야 한다(카드 종류에 `concept`를 더한 마이그레이션은 {ch-migrations}에서 본다).

UNIQUE 제약 중에는 테이블 전체가 아니라 조건에 맞는 행만 골라 중복을 검사하는 부분 유니크 인덱스(partial unique index)가 있다.
다음 절 인덱스 목록의 `decks_share_slug_idx`가 그것으로, `where share_slug is not null` 조건 덕분에 공유되지 않은 다수의 덱(NULL)은 인덱스에 들어가지 않고 공유된 덱들 사이에서만 슬러그가 겹치지 않게 막는다.

=== 인덱스는 조회 패턴에서 나온다

`internal/litestore/schema.sql` 마지막의 인덱스 목록이다.

[source,sql]
----
create index if not exists decks_user_idx on decks (user_id);
create unique index if not exists decks_share_slug_idx on decks (share_slug)
  where share_slug is not null;
create index if not exists cards_user_idx on cards (user_id);
create index if not exists cards_deck_idx on cards (deck_id);
create index if not exists card_srs_user_due_idx on card_srs (user_id, due_at);
create index if not exists review_logs_user_time_idx on review_logs (user_id, reviewed_at);
create index if not exists review_logs_card_idx on review_logs (card_id);
create index if not exists study_sessions_user_idx on study_sessions (user_id, started_at);
create index if not exists smart_decks_user_idx on smart_decks (user_id);
----

인덱스는 "일단 다 걸어 두는" 것이 아니라 실제 조회 패턴에서 역산한다.

첫째, `card_srs_user_due_idx (user_id, due_at)`은 핵심 쿼리인 "오늘 복습" 큐를 위한 복합 인덱스다.
"이 사용자의 것"(`user_id` 등치 조건) 가운데 "복습 시각이 지금 이전인 것"(`due_at` 범위 조건)을 고르므로 {ch-database-basics}의 (등치, 범위) 순서 원칙에 들어맞고, `order by due_at` 정렬도 인덱스 순서로 해결된다.
다만 이 인덱스로 두 조건을 한꺼번에 처리하는 쪽은 `card_srs`를 직접 세는 `DueCount`다.
카드 목록을 돌려주는 `DueCards`는 `cards_with_stats` 뷰를 조회하는데, 뷰를 펼치면 `user_id`는 `cards`에서, `due_at`은 `card_srs`에서 와 조인이 한 단계 더 붙는다(둘 다 `internal/litestore/cards.go`).

둘째, `review_logs_user_time_idx (user_id, reviewed_at)`은 통계 화면의 잔디(최근 1년)와 막대 차트(최근 30일)용 복습 기록 조회(`internal/litestore/stats.go`의 `DailyStats`)를 받친다.
`study_sessions_user_idx (user_id, started_at)`도 같은 (등치, 범위) 무늬다.

셋째, 외래 키 열의 단일 열 인덱스 다섯(`decks_user_idx`, `cards_user_idx`, `cards_deck_idx`, `review_logs_card_idx`, `smart_decks_user_idx`)은 자식 조회와 cascade 삭제 때 자식 찾기를 빠르게 한다.
SQLite도 PostgreSQL도 외래 키에 인덱스를 자동으로 만들지 않는다.

여기 없는 인덱스도 의도다.
인덱스는 쓰기마다 유지 비용을 내므로, 카드 본문 검색 기능이 없는 `cards.text`에는 걸지 않았다.
태그 검색 인덱스도 없다.
`json_each` 검색은 그 사용자의 카드마다 태그 배열을 펼쳐 보므로 읽는 양이 카드 수에 비례하지만, 카드 5,000장을 넣은 임시 SQLite 파일에서 태그 하나로 카드 20장을 고르는 데 이 글을 쓰는 컴퓨터에서 3ms 안팎이 걸렸다.
한 사람의 카드가 수백~수천 장인 규모에서는 인덱스 없이 둬도 된다(운영 PostgreSQL은 배열 열 전용의 GIN 인덱스를 건다).

=== 고정 폭 UTC 텍스트: 문자열 비교가 곧 시간 순서다

SQLite에는 날짜·시각 전용 타입도 없다.
이 앱은 모든 시각 칼럼을 text로 두되, 표기를 하나의 고정 폭 형식으로 통일했다.
`internal/litestore/store.go`에서 발췌한, 그 형식을 정의하는 상수다.

[source,go]
----
// timeLayout은 모든 timestamp 열에 쓰는 고정 폭 UTC 형식이다. 값의 폭이 모두
// 같아 사전순이 곧 시간순이 되므로 due_at 비교가 SQL의 단순 문자열 비교로
// 성립한다. SQL에는 now()를 쓰지 않고, 부르는 쪽이 time.Now().UTC()를 이
// 형식으로 만들어 바인딩한다.
const timeLayout = "2006-01-02T15:04:05.000Z"
----

Go는 `YYYY-MM-DD` 같은 기호 대신 약속된 기준 시각(2006년 1월 2일 15시 4분 5초)을 원하는 모양 그대로 적어 형식을 지정한다.
이 형식의 요점은 두 가지다.
첫째, 모든 값이 UTC 기준이라 서울에서 쓰던 DB 파일을 뉴욕에서 열어도 값의 의미가 달라지지 않는다.
둘째, 모든 값이 같은 폭이다.
연·월·일·시·분·초·밀리초가 큰 단위부터 항상 같은 자릿수로 적히므로, `'2026-07-11T09:30:00.000Z' < '2026-07-12T08:00:00.000Z'`처럼 문자열의 사전순 비교가 곧 시간 순서 비교가 된다.

"오늘 복습" 큐의 `due_at <= ?` 조건도, `(user_id, due_at)` 인덱스의 정렬도 DB 입장에서는 전부 문자열 비교라, 이 성질이 핵심 쿼리의 전제다.
형식이 하나라도 어긋나면(밀리초를 뺀 값이 섞이거나 시간대 표기가 붙으면) 이 보장은 소리 없이 깨진다.
그래서 SQL에는 현재 시각 함수가 등장하지 않고, 모든 시각은 Go가 `time.Now().UTC()`를 이 레이아웃으로 포맷해 바인딩한다.

시간대가 필요한 곳은 해석 단계다.
일별 통계와 연속 학습일(streak)은 "그 사용자의 하루" 단위로 집계해야 하는데, 서울의 자정과 뉴욕의 자정은 다른 절대 시각이다.
SQLite에는 시간대 변환 기능이 없으므로 `DailyStats`는 UTC 텍스트로 쌓인 복습 시각을 읽어 와 Go에서 사용자의 IANA 시간대(전 세계 시간대에 붙인 표준 이름, 예: `Asia/Seoul`)의 날짜별로 집계한다.
데이터가 한 사람 분량이라 가능한 방식이고, 운영 PostgreSQL은 시간대를 품은 timestamptz 타입으로 DB 안에서 처리한다.

== 에이전트 활용 아이디어

* 프로젝트 지침 파일(`AGENTS.md`)에 설계 규약을 적어 둔다. "마이그레이션 파일은 수정하지 말고 새 번호로 추가한다", "모든 테이블에 외래 키와 제약을 선언한다", "SQLite와 PostgreSQL 스키마 두 벌을 함께 고친다"가 후보이고, 특히 마지막은 지시가 없으면 에이전트가 한쪽만 고치기 쉽다.
* 새 테이블이 필요하면 칼럼 목록을 불러 주는 대신 요구사항을 주고 계획부터 받는다. "덱에 즐겨찾기 기능을 붙이려 한다. 테이블을 새로 만들지 기존 테이블에 칼럼을 더할지, 인덱스와 제약까지 포함한 설계안을 코드를 고치기 전에 먼저 제안해 달라"는 식이다. 설계안을 사이에 둔 왕복이 요구사항의 빈틈을 드러낸다({ch-instructing}).

== 정리

첫째, 요구사항에서 일곱 엔티티를 도출했고, 정합성은 외래 키·cascade·not null·check·유니크 제약으로 DB에 맡겼다.
기본 키는 노출되는 엔티티에 UUID, 내부 로그에 순번을 썼고, 인덱스는 due 큐의 `(user_id, due_at)` 복합 인덱스처럼 조회 패턴에서 역산했다.

둘째, 전용 타입이 없는 SQLite에는 설계 의도를 표현 방식으로 담았다.
UUID는 Go가 만들어 text에, 시각은 고정 폭 UTC 텍스트로, 태그·설정·규칙은 JSON 텍스트로, 종류 값은 check 제약으로 지켰다.
운영 PostgreSQL의 전용 타입(uuid, timestamptz, jsonb, 배열, enum)과 이 장에서 미뤄 둔 차이들(enum의 비용, GIN 인덱스, 시간대 집계)은 {ch-supabase-db}에서 다룬다.

다음 {ch-domain-model}에서는 이 앱에만 있는 두 가지 설계를 본다.
간격 반복 알고리즘의 상태를 어떤 칼럼으로 붙잡아 두는가, 그리고 덱의 주소를 어떻게 짧고 예측하기 어렵게 만드는가다.
