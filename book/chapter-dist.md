# 장별 분량 비교

`book/` 원고의 장별 분량을 재고, 그 편차를 줄인 기록이다.
측정은 `scripts/chapter-stats.mjs`가 하고, 아래 "측정 결과" 절은 그 스크립트가 덮어쓴다.
진단과 이력은 손으로 쓴 글이라 스크립트를 다시 돌려도 남는다.
아래 "재편 이력" 이하의 장 번호와 `doc/` 경로는 그 기록을 쓸 당시의 것이다(저장소 재편으로 `doc/`은 `book/`이 됐다).

```
cd book
node scripts/chapter-stats.mjs --out chapter-dist.md      # 이 파일의 측정 결과 절을 갱신
node scripts/chapter-stats.mjs --sections part3/gin.adoc  # 한 장을 절 단위로 쪼개 보기
node scripts/chapter-stats.mjs --json                     # 다른 도구에 넘길 형태
```

장 목록은 `book.config.mjs`의 `toc`에서 읽는다. 장을 늘리거나 빼도 스크립트는 손댈 일이 없다.

**재는 방법.** 파일 크기(바이트)로는 실제 분량을 알 수 없다.
이 책은 코드를 베끼지 않고 `include::`로 인용하므로, 원고 한 줄이 지면에서는 코드 수십 줄이 되기 때문이다.
예를 들어 20장은 원고 파일이 28KB인데 인용을 펼치면 코드만 355줄이다.
그래서 스크립트가 인용을 모두 펼친 뒤 본문 글자와 코드 줄을 따로 센다.

## 재편 이력 (2026-07-25)

아래 장 번호는 **그때의 번호**다. 같은 날 뒤이은 재배치로 1부 앞에 장이 하나 더 들어와 2부부터는 번호가 하나씩 밀렸다(다음 절 참조).

측정에서 드러난 편차는 5.6배였다(32개 장, 평균 15.5쪽, 최소 5.0 ~ 최대 27.8쪽, 표준편차 6.7쪽).
아래 넷을 적용해 35개 장, 평균 14.2쪽, 최소 6.5 ~ 최대 22.9쪽, 표준편차 4.6쪽으로 줄였다.
최대·최소 비는 **5.6배에서 3.5배**가 됐다.

### 1부: 설치 장을 흡수해 마지막으로 옮겼다

기존 2장(개발 도구 설치, 6.3쪽)과 5장(완성된 앱 띄워 보기, 5.0쪽)을 하나로 합쳐 1부의 마지막 장(4장, 11.2쪽)으로 두었다.
그 결과 1부는 5장에서 4장이 되고, 앞의 세 장은 아무것도 설치하지 않고 읽기만 하는 구간이 됐다.

이 배치는 크기 균형보다 독자 경험이 목적이다.
1~3장은 기술 선택과 에이전트 협업을 다루는데, 원래도 독자가 실행할 것이 거의 없으면서 "설치했으니 따라 해 보자"는 문장만 군데군데 있었다.
그 문장들을 걷어 내고 각 장 도입부에 "여기까지는 읽고 이해하기만 한다"고 명시했다.
설치라는 진입 장벽을 세 장 뒤로 미루면, 도구를 깔기 전에 이 책이 무엇을 하려는지 먼저 판단할 수 있다.

`setup.adoc`은 삭제하고 `first-run.adoc`이 그 내용을 흡수했다.
`{ch-setup}` 토큰 14곳은 `{ch-first-run}`으로 옮겼다(반대 방향이었으면 27곳을 고쳐야 했다).

**옮기려다 만 것이 셋 있다.** 원고를 열어 보니 절 제목이 시사한 것과 내용이 달랐다.

32장이 작은 것은 감수했다.

20쪽을 넘는 장은 다섯이다.
27장 Supabase 인증(22.9), 20장 앱 테스트(21.8), 14장 Go 테스트(21.2), 1장 기술 선택(20.7), 13장 Go 코드 읽기(20.6).

- **27장만 남은 숙제다.** "서버 사이드 인증" 절 하나가 12.4쪽으로 장의 절반이 넘는다. 나눈다면 그 절의 소절 여섯을 경계로 삼는 것이 자연스럽다.

10쪽에 못 미치는 장은 여섯이다.
32장 PWA(6.5), 35장 다음 단계(6.6), 31장 환경 변수(7.1), 28장 토큰 검증(8.0), 34장 무료 티어(9.3), 3장 지시하기(9.1).

부 단위로는 3부가 12장 199.3쪽으로 여전히 가장 두껍다.
11~15장(데이터와 로직)과 17~21장(화면과 배선) 사이에 경계가 있어 나눌 수는 있지만, 부 번호가 뒤로 밀리는 큰 변경이라 3부가 더 늘어날 때 꺼낼 카드로 남겨 둔다.

## 도입·서문 재배치와 대안 분리 (2026-07-25, 앞 재편에 이어)

### 요구사항 장을 1부의 1장으로 올렸다

번호 없는 "도입"으로 떠 있던 `requirements.adoc`을 `part1/requirements.adoc`으로 옮겨 1장으로 삼았다.

그 뒤 모든 장의 번호가 하나씩 밀렸다(2부 6~10, 3부 11~22, 4부 23~31, 5부 32~36).

번호가 밀린 값은 `{ch-} 토큰`이 알아서 따라오지만, **코드 블록 안 주석의 장 번호 네 곳은 빌드가 치환하지 않아** 손으로 고쳤다.
본문에 흩어져 있던 "도입에서 정리했듯" 류의 참조 15곳도 `{ch-requirements}` 토큰으로 바꿨다.

### "이 책을 읽는 법"을 서문에 합쳤다

2.9쪽과 3.4쪽으로 둘 다 가장 짧은 축이었고, 저자가 독자에게 직접 건네는 안내라는 성격도 같았다.
합쳐서 6.5쪽 한 편이 됐고, 앞머리에 짧은 글이 둘 놓이던 구성이 하나로 정리됐다.
문체는 서문 쪽에 맞춰 '~습니다'체로 통일했다(맨 끝 "저자 소개"만 '~다'체 그대로).

### 대안 기술 서술을 부록 A로 뺐다

기술 선택 장(옛 1장, 20.7쪽)이 컸던 이유의 절반은 고르지 않은 기술의 설명이었다.
"대안 검토: 문서형 NoSQL", "대안 검토: Node.js·Python·JVM", "net/http만으로도 서버는 만들 수 있다", "대안 비교: net/http·chi·Echo", "SPA가 더 나은 경우", Alpine.js·Stimulus 비교가 그것이다.
개발이 처음인 독자에게는 아직 고른 기술의 이름도 낯선데 고르지 않은 기술의 이름이 그 곱절로 나오는 셈이었다.

이것들을 `appendix/alternatives.adoc`으로 모으고, 본문에는 각 계층마다 "저울에 무엇이 함께 올라갔고 상세는 부록 A에 있다"는 한두 문장만 남겼다.
2장은 20.7 → 15.8쪽이 되고 부록 A가 7.2쪽으로 섰다.
`http.ServeMux` 예제 코드와 htmx 채점 폼 코드도 이때 본문에서 빠졌다(전자는 부록으로, 후자는 18·20장에 같은 코드가 이미 있어 말로만 남겼다).

트레이드오프를 반드시 다룬다는 이 책의 원칙은 지켰다.
2장 정리의 요약 표에는 '검토한 대안' 칸이 그대로 있고, 부록 A는 계층별 표로 "대안이 더 나은 조건"을 한자리에 모아 준다.

## 3부에서 2부의 재탕을 걷어냈다 (2026-07-25)

**진단.** 2부에서 문법을 익히고 3부에서 앱 코드를 읽는 순서를 정해 두었는데, 3부의 세 장이 절 제목까지 2부를 되풀이하고 있었다.

| 장 | 그때의 절 제목 | 2부의 짝 |
|---|---|---|
| 13장 | 변수와 기본 타입 / 함수와 다중 반환값 / 제어문(if·for·switch) / 상수 | 8장의 같은 절들 |
| 14장 | 포인터 / 슬라이스와 맵 / 문자열 처리 / 제네릭 | 9장의 같은 절들 |
| 18장 | 시맨틱 마크업 / 폼 / 선택자 / 박스 모델 / 배치 / 다크 모드 | 6·7장의 같은 절들 |

예제만 앱 코드로 바꾼 문법 강의여서, 2부를 읽고 온 독자에게는 같은 이야기를 두 번 듣는 구간이 됐다.
14장에는 아예 저장소에 없는 연습용 제네릭 예제(`firstString`/`sum`)까지 있었는데, 이는 "연습용 예제는 2부에만 둔다"는 이 책의 규칙과도 어긋났다.

**고친 방향.** 세 장을 문법 항목이 아니라 **앱의 구조와 앱이 푸는 문제**로 다시 나눴다.

| 장 | 새 제목 | 절 구성 |
|---|---|---|
| 13장 | 코드는 어디에 있는가: 패키지 지도와 앱의 시작점 | 모듈과 패키지 열넷 / 저장소 두 구현의 대칭 / internal이 막고 Vercel이 밀어낸 pkg / 의존은 한 방향으로 / 앱이 켜질 때 정해지는 것 / 낯선 파일을 여는 순서 |
| 14장 | 핵심 로직 읽기: 간격 반복 알고리즘과 도메인 코드 | 오늘 이 카드를 다시 보여 줄 것인가 / 조건을 규칙 값으로 / 에러가 계층을 건너는 방법 / 값이 없다는 사실을 표현하기 / 여덟 곳의 반복을 하나로 / 카드가 드나드는 길 |
| 18장 | 화면의 구조: 템플릿 삼층과 스타일 시스템 | 화면 한 장은 세 층으로 / 겉틀이 맡는 것 / 페이지가 채우는 자리 / 브라우저 기본 기능으로 끝낸 폼 / 스타일시트를 조직하는 네 규칙 / 상태는 HTML이 들고 겉모습은 CSS가 |

13장에는 전에 없던 내용이 들어왔다.
저장소 구현 둘(`pgstore`·`litestore`)이 같은 파일 이름으로 대칭을 이룬다는 사실, `internal/model`을 향해 의존이 한 방향으로만 흐른다는 규약, `DATABASE_URL` 하나가 저장소와 인증 방식을 함께 정한다는 것이다.
전부 `doc/CLAUDE.md`와 저장소 `CLAUDE.md`에는 적혀 있었지만 책 어디에도 없던 설명이다.

18장도 마찬가지로 "자손 선택자 대신 클래스를 쓴다", "새 색은 두 팔레트에 모두 정의한다", "템플릿에 인라인 `style`을 두지 않는다" 같은 이 저장소의 CSS 규약을 본문으로 끌어올렸다.

**옮긴 것과 뺀 것.**

- 제네릭 문법 소개(연습용 예제 포함)를 14장에서 9장 끝으로 옮겼다. 9장 10.7 → 13.2쪽.
- 13장에 있던 상수 절(`deckslug.go` 인용)은 지웠다. 같은 코드를 12장이 이미 인용하고 있었다.
- `internal/model/store.go`의 `Store` 인터페이스 선언에 `store-head` 인용 태그를 새로 달아, 17장이 손으로 베껴 두었던 발췌를 `include::`로 바꿨다.
- `pgstore`·`litestore`의 패키지 주석에도 태그를 달아 13장이 나란히 인용한다. 두 구현의 대칭을 주장이 아니라 코드로 보이기 위해서다.

**결과.** 13장 12.6 → 10.8쪽, 14장 20.6 → 17.3쪽, 18장 19.0 → 17.1쪽.
표준편차는 4.4에서 4.3으로 줄었고, 20쪽을 넘는 장이 다섯에서 셋이 됐다.
