= 완성된 앱 띄워 보기: 클론에서 실행까지

{ch-instructing}에서는 에이전트에게 지시해 앱의 골격을 만들고, 내 컴퓨터에서 첫 실행까지 해 봤다.
이 장에서는 골격이 아니라 완성본을 손에 넣는다.
이 책이 처음부터 끝까지 소재로 삼는 Flashcard의 완성된 저장소를 클론해, 전체 앱을 내 컴퓨터에서 띄우고 브라우저로 만져 본다.
덱을 만들고 카드를 뒤집는 화면 뒤에서 데이터가 파일 하나에 쌓이는 것도 직접 확인한다.
이렇게 손에 쥔 앱이 이 책의 나머지를 받치는 실물이다.
2부에서는 이 앱을 이루는 세 언어의 문법을 첫걸음부터 익히고, 3부에서는 같은 앱을 코드로 해부한다.

== 클론에서 실행까지, 명령 하나

준비물은 Go 툴체인(toolchain, 컴파일러와 그에 딸린 도구가 함께 설치되는 묶음) 하나다.
아직 없다면 {ch-setup}의 안내를 따라 설치하고, `go version`이 버전을 출력하면 준비가 끝난 것이다(이 책의 코드는 Go 1.26에서 확인했다).

저장소를 아직 받지 않았다면 클론(clone) 명령 한 줄로 내려받는다.
Git 자체는 {ch-git}에서 제대로 다루므로, 여기서는 이 명령 하나만 쓰고 지나간다.

.[용어 풀이] 클론(Clone)
[NOTE]
====
GitHub 같은 서비스에 올라가 있는 프로젝트를 내 컴퓨터로 통째로 복사해 오는 일이다.
지금의 파일들만 내려받는 것이 아니라 그 프로젝트가 지금까지 거쳐 온 변경 이력까지 함께 받아 오므로, 복사가 끝난 뒤에는 인터넷이 끊겨도 과거의 기록을 열어 볼 수 있다.
받아 온 사본은 내 것이라 마음껏 고치고 실험해도 원본에는 아무 영향이 없고, 망가뜨렸다면 폴더를 지우고 다시 클론하면 처음 상태로 돌아온다.
복사해 오는 그 꾸러미가 정확히 무엇이고 고친 결과를 어떻게 원본으로 돌려보내는지는 {ch-git}에서 다룬다.
====

[source,bash]
----
git clone https://github.com/benelog/flashcard.git
cd flashcard
----

이제 서버를 띄운다.

[source,bash]
----
go run ./cmd/server
----

처음 한 번은 의존성 다운로드와 컴파일 때문에 시간이 조금 걸리고, 기동에 성공하면 로그 한 줄이 나온다.

----
2026/07/11 06:15:20 flashcard api listening on :8080 (local mode, sqlite: local-db/flashcard.db)
----

`local mode`라는 표시를 눈여겨보자.
아무 설정도 주지 않았으므로 서버가 로컬 모드로 떴고, 데이터는 `local-db/flashcard.db`라는 SQLite 파일에 저장된다는 뜻이다.
이것으로 실행은 끝이다.
이 Go 서버 하나가 HTML 화면과 JSON API를 모두 서빙하므로, 프로세스를 하나 더 띄울 일이 없다(이 구조는 {ch-gin}에서 다룬다).
저장소 루트의 `run_local.sh`는 같은 명령을 스크립트로 감싼 것이라 어느 쪽을 써도 결과가 같다.

[source,bash]
----
#!/usr/bin/env bash
# 로컬 모드 실행: Go 서버 하나(:8080)가 HTML 페이지와 API를 모두 서빙한다.
# 환경 변수 불필요, SQLite 파일(local-db/flashcard.db) 사용, 로그인 없음.
set -euo pipefail
cd "$(dirname "$0")"

exec go run ./cmd/server
----

브라우저로 `http://localhost:8080`을 열면 로그인 화면 없이 곧바로 홈 화면이 나오고, 배포된 앱이라면 계정 이메일이 있을 상단 바 오른쪽 자리에는 "로컬 모드"라고 적혀 있다.

.[용어 풀이] localhost와 포트(Port)
[NOTE]
====
localhost는 "내 컴퓨터 자신"을 가리키는 주소다.
이 주소로 보낸 요청은 인터넷으로 나가지 않고 방금 내가 켠 서버로 되돌아오므로, 아직 아무에게도 공개하지 않은 앱을 내 브라우저로 열어 볼 수 있다.
뒤에 붙는 8080은 포트로, 한 컴퓨터 안에서 여러 프로그램이 각자 다른 창구 번호를 나눠 갖는 것과 같다.
다른 프로그램이 8080번 창구를 이미 쓰고 있어 서버가 뜨지 않으면, {ch-local-dev}에서 볼 `PORT=9090`으로 창구 번호를 바꿔 주면 된다.
====

"기본 영단어"라는 덱을 만들고 resilient와 deliberate 두 카드를 추가해 학습을 시작하면, 도입 장에서 화면 캡처로만 봤던 그 흐름이 내 컴퓨터에서 돈다.
맞음과 틀림을 고를 때마다 복습 기록이 테이블에 쌓이고, SRS 함수가 다음 복습 시각을 계산하며, 서버가 그 결과를 화면으로 그려 보낸다.
이 장치들은 3부에서 하나씩 코드로 해부한다(테이블 설계는 {ch-database}, SRS 함수는 {ch-go}, 화면 템플릿과 htmx는 {ch-go-templates}과 {ch-htmx}).

여기서 지킨 규약은 하나다.
*환경 변수가 하나도 없으면 로컬 모드다.*
서버는 `DATABASE_URL`이 없으면 로컬 모드로 동작하고, 클론 직후의 저장소에는 그 값이 없다.
설정 없이 실행되는 이 구조가 어떤 원리로 성립하는지는 {ch-local-dev}에서 파고든다.


== 내 데이터는 파일 하나에 있다

앱을 조금 만져 봤다면 저장소에 `local-db/` 폴더가 생기고 그 안에 `flashcard.db`가 만들어졌을 것이다(쓰는 도중에는 `-wal`·`-shm`이 붙은 작업 파일 두 개도 함께 보인다).
이 파일이 데이터베이스 전부다.
{ch-tech-choices}에서 SQLite를 "파일 하나로 동작하는 관계형 데이터베이스"라고 소개했는데, 그 파일이 바로 이것이다.
`local-db/` 폴더는 Git이 아예 추적하지 않을 목록(`.gitignore`)에 통째로 올라 있어서, 내 학습 데이터가 저장소에 딸려 들어갈 일은 없다.
그 목록이 무엇이고 코드의 이력을 어떻게 남기는지는 {ch-git}에서 다룬다.

그런데 테이블을 만드는 명령을 한 번도 실행하지 않았는데도 이 앱의 테이블들이 전부 준비되어 있다.
서버가 시작할 때 스키마(테이블의 구조 정의)를 통째로 적용하기 때문인데, 그 일을 하는 코드가 `internal/litestore/store.go`에 있다.
이 코드는 SQLite 파일과 그것이 담길 폴더를 없으면 만들어 가며 열고, 소스에 함께 임베드된 스키마를 곧바로 적용한다.

[source,go]
----
//go:embed schema.sql
var schemaSQL string

// ...
func Open(path string) (*Store, error) {
	if dir := filepath.Dir(path); dir != "." {
		if err := os.MkdirAll(dir, 0o755); err != nil {
			return nil, fmt.Errorf("create sqlite dir: %w", err)
		}
	}
	db, err := sql.Open("sqlite",
		path+"?_pragma=foreign_keys(1)&_pragma=busy_timeout(5000)&_pragma=journal_mode(wal)")
	// ...
	if _, err := db.Exec(schemaSQL); err != nil {
		db.Close()
		return nil, fmt.Errorf("apply schema: %w", err)
	}
	return &Store{db: db}, nil
}
----

`internal/litestore/schema.sql`이 그 스키마 파일이고, {ch-database}에서 이 파일을 발췌해 읽는다.
모든 문장이 `if not exists` 꼴이라 몇 번을 다시 실행해도 이미 있는 테이블과 인덱스는 건드리지 않으므로, 별도의 명령 없이 서버를 켜기만 하면 스키마가 준비된다.

이 파일을 직접 열어 보자.
sqlite3 명령줄 도구는 macOS에 기본으로 들어 있고, 다른 OS의 설치 방법은 {ch-setup}에 있다.
서버를 잠시 멈춘 뒤(Ctrl+C) 저장소 루트에서 `sqlite3 local-db/flashcard.db`를 실행한다.

그러면 화면에 `sqlite>`가 뜨는데, 이것은 내가 타이핑하는 글자가 아니라 도구가 "명령을 기다린다"고 찍어 주는 입력 대기 표시다.
아래 블록에서도 `sqlite>` 뒤에 이어지는 부분만 입력한 것이고, 나머지 줄은 도구가 출력한 결과다.
`.tables`처럼 점으로 시작하는 명령은 SQL이 아니라 sqlite3 도구 자체에 내리는 지시이며, 빠져나올 때는 `.quit`을 입력한다.

----
sqlite> .tables
card_srs          cards_with_stats  profiles          smart_decks
cards             decks             review_logs       study_sessions
sqlite> select name from decks;
기본 영단어
sqlite> select text, meaning from cards;
resilient|회복력 있는
deliberate|의도적인; 심사숙고하다
----

브라우저에서 만든 덱과 카드가 표 형태로 그대로 들어 있다.
방금 입력한 `select`가 데이터베이스에 묻는 언어인 SQL이고, {ch-database-basics}에서 바로 이 파일을 상대로 SQL을 익힌다.
`.tables` 목록의 `cards_with_stats`는 테이블이 아니라 통계 조회용 뷰(view)인데, 뷰가 무엇인지는 {ch-database}에서 다룬다.
`profiles`에는 사용자가 단 한 명 있는데, 로그인 없는 로컬 모드에서 모든 데이터의 주인이 되는 고정 사용자다(이 사용자를 만드는 코드는 {ch-local-dev}에서 본다).
무엇을 조회하든 내 데이터라 결과를 눈으로 검증할 수 있고, 실수로 망가뜨려도 파일을 지우고 서버를 다시 켜면 빈 상태에서 새로 시작한다.
그래서 SQL을 실험할 놀이터로 이 파일만 한 것이 없다.

백업도 단순해서, 서버를 멈춘 상태에서 파일을 복사하면 끝이다.
sqlite3로 한 번 열었다 닫으면 작업 파일의 내용이 본 파일로 합쳐지므로 `local-db/flashcard.db` 하나만 복사해도 된다.
데이터베이스 백업이라는 말의 무게에 비하면 싱거울 정도인데, 운영 데이터베이스에서는 파일 복사가 통하지 않으므로 백업은 {ch-free-tier}에서 전용 도구와 복원 기한을 따지는 주제로 다룬다.


== 정리

이 장에서는 완성본 저장소를 클론해 내 컴퓨터에서 전체 앱을 띄웠다.

준비물은 Go 하나였고, `go run ./cmd/server` 한 줄로 서버가 로컬 모드로 떠서 로그인 없이 홈 화면까지 열렸다.
데이터는 `local-db/flashcard.db`라는 SQLite 파일 하나에 쌓이고, sqlite3로 그 파일을 직접 열어 방금 만든 덱과 카드를 눈으로 확인했다.
환경 변수가 하나도 없으면 로컬 모드라는 규약 덕분에 설정 없이 실행이 끝났는데, 그 원리는 {ch-local-dev}에서 파고든다.

이제 읽을 수 있는 요구사항과 만질 수 있는 앱이 모두 손에 있다.
다음 {ch-html-hello}부터는 방금 만진 화면이 무엇으로 만들어졌는지부터 배운다.
브라우저가 표시하는 문서의 언어인 HTML을, 저장소가 아니라 파일 하나짜리 연습 예제로 첫걸음부터 익힌다.
