= 토큰 검증의 원리: JWT와 JWKS

{ch-supabase-auth}에서 로그인 여정을 완성했다.
로그인 버튼을 누른 브라우저가 OAuth 왕복을 마치고 나면, HttpOnly 쿠키에는 서명된 토큰이 담겨 돌아온다.
이 장은 서버가 그 토큰을 어떻게 진짜라고 판별하는지, 그 원리를 해부한다.
앱을 따라 만드는 데에는 {ch-supabase-auth}까지로 충분하므로, 이 장은 원리가 궁금할 때 읽으면 된다.
먼저 JWT라는 토큰의 구조를 열어 보고, JWKS 공개키로 서명을 확인하는 절차와 공유 시크릿 방식과의 차이를 짚는다.
이어서 서명 너머의 클레임 검증을 살펴보고, 페이지와 API라는 두 인증 경로가 같은 검증 코드로 수렴하는 구조로 마무리한다.

== Go에서의 JWT 검증

이제 {ch-supabase-auth}에서 쿠키에 담아 온 토큰을 검증하는 코드를 파헤쳐 보자.
JWT(JSON Web Token)를 일상어로 옮기면, 소지자가 누구이고 언제까지 유효한지를 적고 위조를 막는 서명을 붙인 디지털 출입증이다.
기술적으로는 헤더·페이로드·서명 세 부분을 점으로 이은 문자열이고, 페이로드에는 사용자 ID(`sub`), 만료 시각(`exp`) 같은 클레임(claim)이 들어 있다.
검증의 핵심은 "이 토큰을 정말 Supabase가 발급했는가"를 서명으로 확인하는 것이다.

.[용어 풀이] JWT(JSON Web Token)
[NOTE]
====
로그인에 성공했다는 사실을 서버가 서명해서 발급하는 긴 문자열이다.
놀이공원에서 입장 확인 후 손목에 채워 주는 밴드처럼, 한 번 받으면 매 요청마다 신분증을 다시 보이지 않아도 된다.
위조하면 서명이 깨지므로 서버는 밴드가 진짜인지 검사만 하면 된다.
====

.[용어 풀이] 클레임(Claim)
[NOTE]
====
토큰 안에 적힌 주장 하나하나를 클레임이라 한다.
"이 토큰의 주인은 이 사용자다"(`sub`), "이 시각에 만료된다"(`exp`), "이 토큰은 로그인한 사용자용이다"(`aud`)처럼, 발급자가 서명으로 보증하는 항목들이다.
신분증에 적힌 이름·생년월일·유효기간 한 줄 한 줄에 해당한다.
검증하는 쪽은 이 항목들을 읽어 요청의 주인을 판별하므로, 어떤 클레임을 어디까지 믿을지 정하는 일이 곧 인증 규칙이 된다.
====

=== JWKS: 공개키를 내려받아 서명을 확인한다

Supabase는 비대칭 키(asymmetric key)로 토큰에 서명하고, 그중 확인용 열쇠인 공개키(public key) 목록을 JWKS(JSON Web Key Set)라는 표준 형식으로 공개한다.
주소는 `https://<project-ref>.supabase.co/auth/v1/.well-known/jwks.json`이다.

.[용어 풀이] 대칭 키와 비대칭 키(Symmetric/Asymmetric Key)
[NOTE]
====
서명과 검증에 같은 열쇠 하나를 쓰는 방식이 대칭 키이고, 서명하는 개인키(private key)와 확인하는 공개키(public key)가 짝으로 나뉘는 방식이 비대칭 키다.
대칭 키에서는 확인만 하려는 사람도 서명까지 할 수 있는 열쇠를 가져야 하지만, 비대칭 키에서는 확인만 할 수 있는 열쇠를 따로 나눠 줄 수 있다.
JWT의 서명 방식 이름에서 HS256은 대칭 키(HMAC)를, RS256과 ES256은 비대칭 키를 뜻한다.
====

.[용어 풀이] JWKS와 서명 검증
[NOTE]
====
발급자가 개인키로 토큰에 찍은 서명이 진짜인지 확인하도록, 대조에 쓸 공개키를 묶어 공개한 목록이 JWKS(JSON Web Key Set)다.
인감과 인감증명서에 빗댈 수 있다.
인감은 주인만 찍을 수 있지만, 인감증명서(공개키)를 가진 사람은 누구나 그 도장이 진짜인지 대조할 수 있다.
즉 토큰은 발급자만 만들 수 있고, 진위 확인은 공개키만 있으면 누구나 할 수 있다.
====

`internal/auth/jwt.go`에서 검증 키를 준비하는 부분을 보자.
토큰의 서명을 대조할 때 쓸 열쇠를 어디서 가져올지 정하는 함수다.

[source,go]
----
func keyfuncFor(jwksURL, secret string) (jwt.Keyfunc, error) {
	if secret != "" {
		return func(t *jwt.Token) (any, error) {
			if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
				return nil, jwt.ErrTokenSignatureInvalid
			}
			return []byte(secret), nil
		}, nil
	}
	jwksOnce.Do(func() {
		jwks, jwksErr = keyfunc.NewDefaultCtx(context.Background(), []string{jwksURL})
	})
	if jwksErr != nil {
		return nil, jwksErr
	}
	return jwks.Keyfunc, nil
}
----

기본 경로는 아래쪽 JWKS 분기다.
`github.com/MicahParks/keyfunc/v3` 라이브러리가 JWKS 문서를 내려받아 캐시하고 주기적으로 갱신하며, 토큰 헤더의 키 ID(`kid`)에 맞는 공개키를 골라 준다.
패키지 전역 변수 `jwks`를 `sync.Once`로 한 번만 초기화하는 것은 {ch-vercel}에서 본 서버리스 함수의 생명주기 때문이다.
웜 인스턴스는 여러 요청을 처리하므로, JWKS 클라이언트를 재사용하면 첫 요청 이후에는 네트워크 조회 없이 검증할 수 있다.

위쪽 분기는 공유 시크릿(HS256) 폴백(fallback)이다.
이 분기는 옛 Supabase 프로젝트를 위한 예비 경로라, 처음 읽을 때는 건너뛰어도 된다.
JWKS 엔드포인트가 없는 구형 Supabase 프로젝트는 대칭 키(HS256)로 서명하므로, 그런 환경에서는 환경 변수 `SUPABASE_JWT_SECRET`을 설정해 이 분기를 탄다.
이때 서명 방식이 HMAC인지 명시적으로 확인하는 부분이 중요하다.
공격자가 공개키를 HMAC 시크릿인 척 쓰도록 헤더의 `alg`를 바꿔치기하는 알고리즘 혼동(algorithm confusion) 공격을 차단하는 코드다.

=== 왜 공유 시크릿이 아닌가

결론부터 일상어로 말해 보겠다.
공유 시크릿 방식은 열쇠를 하나 만들어 발급자와 검증자가 나눠 갖는 것이라, 우리 서버 쪽에서 그 열쇠가 새면 남이 얼마든지 토큰을 위조할 수 있다.
JWKS 방식에서는 앞 상자의 비유대로 도장을 Supabase만 갖고 우리는 대조용 인감증명서만 받으므로, 우리 쪽에서 무엇이 새어 나가도 위조는 불가능하다.
같은 이야기를 기술 용어로 다시 짚어 보겠다.

검증자가 발급자 하나뿐이면 시크릿을 나눠 가질 일이 없어 HS256으로 충분하지만, Flashcard처럼 발급은 Supabase가 하고 검증은 Go 함수가 하는 구조에서는 JWKS가 낫다.

HS256은 서명과 검증에 같은 시크릿을 쓴다.
검증하는 쪽도 시크릿을 가져야 하므로, Go 함수에 시크릿을 환경 변수로 배포해야 하고, 그 시크릿이 유출되면 누구든 유효한 토큰을 위조할 수 있다.
시크릿을 교체(회전)하려면 발급자와 모든 검증자를 동시에 업데이트해야 한다.

JWKS 기반 비대칭 서명은 이 문제를 구조적으로 없앤다.
첫째, 개인키는 Supabase만 보유하고 검증자는 공개키만 쓰므로, 검증자 쪽에서 무엇이 유출되어도 토큰을 위조할 수 없다.
둘째, 배포할 비밀 자체가 없다.
JWKS URL은 공개 정보라서 환경 변수로 관리할 비밀이 하나 줄어든다.
셋째, 키 회전(key rotation)이 매끄럽다.
JWKS 문서에 새 키를 추가하고 옛 키를 제거하는 것만으로 회전이 끝나고, 검증자는 캐시를 갱신하며 자동으로 따라간다.

물론 발급자와 검증자가 같은 프로세스이거나 외부 네트워크 조회를 피해야 하는 폐쇄 환경이라면, 내려받을 키 목록 없이 시크릿 하나로 검증이 끝나는 대칭 키가 낫다.
Flashcard처럼 발급자(Supabase)와 검증자(Go 서버)가 서로 다른 조직의 인프라에 있는 구성에서는 JWKS가 명백히 유리하다.

옵션 세 개가 각각 한 가지 공격 경로를 막는다.
`WithValidMethods`는 허용 알고리즘을 화이트리스트로 고정해 `alg: none` 같은 우회를 차단한다.
`WithAudience("authenticated")`는 Supabase가 로그인 사용자에게 발급한 토큰만 받는다는 뜻으로, 익명 토큰이나 다른 용도의 토큰을 거른다.
`WithExpirationRequired`는 `exp` 클레임이 아예 없는, 영원히 유효한 토큰을 거부한다.

검증을 통과하면 `sub` 클레임이 사용자 식별자다.
이 값은 Supabase `auth.users` 테이블의 UUID이고, {ch-database}에서 설계한 `profiles.id`가 이 값을 그대로 쓴다.
인증 시스템의 사용자와 우리 스키마의 사용자가 같은 키로 이어지는 접점이다.

이 함수를 부르는 곳은 둘이다.
{ch-gin}에서 본 JSON API용 `parseUserID`는 `sub`만 꺼내 사용자 ID를 돌려주고, 웹 계층용 `ParseUser`는 화면에 표시할 이메일 클레임까지 함께 돌려준다.
{ch-supabase-auth}에서 `withUser`가 쿠키에서 꺼낸 토큰을 건네던 것이 뒤쪽이다.

검증 옵션을 두 함수에 한 벌씩 적어 두는 방법도 있었지만, 그렇게 두면 나중에 한쪽에만 검사를 더하고 다른 쪽을 잊기 쉽다.
옵션이 `parseClaims` 한 곳에만 있으므로 두 입구의 기준이 어긋날 자리가 없다.

=== 필수 인증과 선택 인증

이 파일은 JSON API용 미들웨어도 두 가지 내보낸다.
`Middleware`는 `Authorization: Bearer` 헤더의 토큰이 없거나 무효하면 401로 요청을 끊고, `OptionalMiddleware`는 유효한 토큰이 있을 때만 사용자 ID를 붙이되 없어도 통과시킨다.
둘 다 방금 본 검증 경로를 그대로 거치며, 차이는 검증에 실패한 요청을 어떻게 처리하느냐뿐이다.
두 미들웨어가 라우터 조립에서 나뉘어 붙는 곳과 그 이유(공유 덱의 "익명 허용 + 로그인 시 개인화" 요구, 그리고 `Cache-Control: no-store`가 한 세트인 사연)는 {ch-gin}에서 다뤘다.


== 두 인증 경로의 공존

여기까지 읽고 나면 이 앱에 인증 경로가 둘 있다는 사실이 보인다.
HTML 페이지는 쿠키로, `/api/*`의 JSON API는 Bearer 헤더로 신원을 밝힌다.
JSON API는 {ch-gin}에서 만든 그대로이고, PWA의 서비스 워커나 외부 스크립트처럼 화면 없이 API만 부르는 호출자를 위해 남아 있다.

둘은 같은 Gin 엔진에 등록되고 같은 검증 코드를 쓴다.
`internal/web/routes.go`의 라우트 등록부에서 페이지 쪽 구성을 발췌한다.
공개 페이지와 로그인 필수 페이지가 미들웨어 사슬로 나뉘는 곳이다.

[source,go]
----
// 공개 페이지: 공유 덱 구경과 로그인 흐름.
pub := r.Group("/", w.withUser())
{
	pub.GET("/login", w.loginPage)
	pub.GET("/auth/login/:provider", w.startOAuth)
	pub.GET("/auth/callback", w.oauthCallback)
	pub.POST("/logout", w.logout)
	// ...
}

// 로그인해야 보는 페이지와 그 폼·htmx 끝점.
app := r.Group("/", w.withUser(), w.requireUser(), auth.EnsureProfile(w.store, w.failPage))
{
	app.GET("/", w.homePage)
	// ...
}
----

공개 그룹은 `withUser`만 지나서 익명도 통과하고, 로그인 그룹은 `requireUser`가 문을 지킨다.
로그인 그룹 끝의 `EnsureProfile`은 첫 요청에서 사용자의 프로필 행을 만들어 주는 미들웨어로, {ch-gin}의 JSON API와 이 웹 페이지 그룹이 함께 쓴다.
같은 미들웨어라도 실패의 모양은 달라야 하므로, API는 JSON 오류 응답을, 화면은 오류 화면(`failPage`)을 끼워 만든다.

이 공유가 성립하는 열쇠가 `internal/auth/jwt.go`의 작은 함수 하나다.

[source,go]
----
// SetUserID는 인증된 사용자 ID를 요청 컨텍스트에 싣는다. API 미들웨어와 같은
// 키를 쓰므로, 쿠키로 인증한 웹 요청에서도 핸들러와 EnsureProfile이 똑같이
// 동작한다.
func SetUserID(c *gin.Context, id uuid.UUID) {
	c.Set(userIDKey, id)
}
----

쿠키에서 신원을 확인한 `withUser`도, 헤더에서 확인한 API 미들웨어도 사용자 ID를 컨텍스트의 같은 키에 넣는다.
그래서 그 아래의 모든 코드(핸들러, `EnsureProfile`, store 계층)는 요청이 어느 문으로 들어왔는지 모른 채 `auth.UserID(c)` 하나로 동작한다.
인증 방식이 둘이어도 인증 이후의 세계는 하나다.


== 정리

첫째, JWT 검증의 핵심은 서명 확인이다.
Supabase가 개인키로 서명한 토큰을 우리 서버는 JWKS로 공개된 공개키를 내려받아 대조하고, `sync.Once`로 초기화한 JWKS 클라이언트를 웜 인스턴스가 재사용하므로 첫 요청 이후에는 네트워크 조회 없이 검증이 끝난다.

둘째, 공유 시크릿(HS256)과의 차이는 유출의 결과에 있다.
시크릿을 나눠 가지는 방식에서는 검증자 쪽이 새어도 토큰을 위조할 수 있지만, JWKS 방식에서는 검증자에게 위조 능력 자체가 없고, 배포할 비밀도 없으며, 키 회전도 발급자 혼자 끝낸다.

셋째, 서명이 유효해도 클레임 검증을 건너뛰지 않는다.
허용 알고리즘 고정, `aud` 확인, 만료 필수라는 옵션 세 개가 `parseClaims` 한 곳에 모여 있어, 어느 입구로 들어온 토큰이든 같은 검사를 통과한다.
검증을 통과한 `sub` 클레임이 `profiles.id`로 이어져, 인증의 사용자와 앱 데이터의 사용자가 같은 키로 묶인다.

넷째, 인증 경로는 둘이지만 그 이후는 하나다.
페이지는 쿠키로, JSON API는 Bearer 헤더로 신원을 밝혀도 같은 검증 코드를 거쳐 같은 컨텍스트 키에 사용자 ID를 남기므로, 핸들러부터 아래의 세계는 요청이 어느 문으로 들어왔는지 구분하지 않는다.

다음 {ch-supabase-db}에서는 같은 Supabase의 다른 얼굴, 즉 데이터베이스를 다룬다.
함수 인스턴스가 여럿 뜨는 서버리스 환경에서 커넥션이 폭증하는 문제를 트랜잭션 풀러로 푸는 방법과 그 대가로 pgx에 붙여야 하는 설정이 그 내용이다.
