= 로컬 개발 환경: 무설정 실행의 원리와 개발 도구

{ch-first-run}에서 우리는 저장소를 클론해 명령 하나로 이 앱을 띄웠다.
데이터베이스 설치도, 계정 가입도, 설정 파일 작성도 없었다.
그때는 결과만 확인하고 지나갔지만, 3부에서 테이블부터 화면까지 코드를 층층이 읽고 그 코드를 검증하는 테스트까지 본 지금은 그 무설정 실행의 원리를 해부할 수 있다.
{ch-app-tests}의 테스트가 계정도 설정도 없이 앱을 띄울 수 있었던 것도 이 절에서 볼 분기 덕분이다.
이번 장에서는 먼저 그 실행을 성립시키는 코드의 분기들을 따라가고, 이어서 에디터 설정으로 사람 쪽 개발 환경을 갖춘 뒤, 환경 변수로 동작을 바꾸는 길까지 정리해 3부를 마무리하겠다.

== 무설정 실행은 어떻게 가능한가

배포된 Flashcard는 PostgreSQL과 Supabase 인증 위에서 도는데, {ch-first-run}에서 띄운 로컬 서버는 둘 다 없이 돌았다.
공짜 마법이 아니라 코드 곳곳에 준비된 분기 덕분이므로 그 분기를 따라가 보겠다.

출발점은 {ch-go-basics}에서 읽었던 `internal/config/config.go`다.
이 코드는 `DATABASE_URL`이 있으면 운영과 같은 PostgreSQL 구성을, 없으면 SQLite 파일과 로컬 인증이라는 기본값을 채운다.

[source,go]
----
	if cfg.DatabaseURL != "" {
		cfg.Driver = "postgres"
		cfg.AuthMode = "supabase"
		if cfg.SupabaseURL == "" || cfg.SupabaseAnonKey == "" {
			return nil, fmt.Errorf("SUPABASE_URL and SUPABASE_ANON_KEY are required")
		}
		// ...
		return cfg, nil
	}

	// DATABASE_URL이 없으면 SQLite 파일로 1인 로컬 모드를 돈다. Vercel에서는
	// 함수의 일회용 파일시스템에 조용히 쓰게 되므로, 거기서 DATABASE_URL이
	// 없는 것은 언제나 설정 실수다.
	if os.Getenv("VERCEL") != "" {
		return nil, fmt.Errorf("DATABASE_URL is required on Vercel")
	}
	cfg.Driver = "sqlite"
	cfg.AuthMode = "local"
	cfg.SQLitePath = os.Getenv("SQLITE_PATH")
	if cfg.SQLitePath == "" {
		cfg.SQLitePath = "local-db/flashcard.db"
	}
	return cfg, nil
----

로컬 모드의 기본값 두 가지가 여기서 정해진다.
데이터베이스 드라이버는 SQLite(파일은 `local-db/flashcard.db`), 인증 모드는 로컬이다.
거꾸로 `DATABASE_URL`이 있는 운영 구성에서는 로그인에 필요한 `SUPABASE_URL`과 `SUPABASE_ANON_KEY`까지 요구해서, 값이 빠진 채 어중간하게 뜨는 일을 막는다.
이 값들이 무엇인지는 {ch-supabase-auth}에서 다룬다.

중간의 `VERCEL` 검사는 로컬 기본값이 사고로 번지는 것을 막는 가드다.
배포 환경에서 `DATABASE_URL`을 깜빡 빠뜨리면 서버리스 함수의 일회용 파일 시스템에 조용히 SQLite 파일을 만들었다가 데이터를 통째로 잃게 되므로, Vercel 위에서는 로컬 모드로 넘어가는 대신 기동을 거부한다.

인증 쪽 분기는 `internal/auth/local.go`에 있다.
이 코드는 토큰을 검사하는 대신 모든 요청을 고정된 한 명의 사용자로 로그인시킨다.

[source,go]
----
// LocalUserID는 로컬 모드의 모든 요청이 쓰는 고정 사용자다.
var LocalUserID = uuid.MustParse("00000000-0000-0000-0000-000000000001")

// ...
func LocalMiddleware() gin.HandlerFunc {
	return func(c *gin.Context) {
		c.Set(userIDKey, LocalUserID)
		c.Next()
	}
}
----

{ch-gin}에서 본 라우터 조립부(`pkg/app/app.go`)는 인증 모드가 로컬이면 JWT 검증 미들웨어 자리에 이 함수를 대신 끼운다.
라우터도, 핸들러도, 그 아래 store 계층도 전부 그대로이고 바뀌는 것은 문 앞의 문지기 하나뿐이다.
로컬 모드라고 다른 앱이 도는 것이 아니라, 배포 환경과 같은 코드가 다른 문지기를 세우고 도는 것이다.

화면 쪽에도 같은 분기가 하나 있다.
HTML 페이지의 방문자 식별을 맡는 `internal/web/cookies.go`의 `withUser` 미들웨어는, 인증 모드가 로컬이면 쿠키를 살피는 대신 모든 방문자를 고정 사용자로 세운다.

[source,go]
----
func (w *Web) withUser() gin.HandlerFunc {
	if w.cfg.AuthMode == "local" {
		return func(c *gin.Context) {
			auth.SetUserID(c, auth.LocalUserID)
			c.Next()
		}
	}
	// ... 쿠키 세션 검증과 갱신 (25장에서 다룬다)
}
----

로그인 화면이 아예 안 나온 이유가 이 분기다.
로그인 페이지로 보내는 문지기는 "방문자가 식별되지 않았을 때"만 작동하는데, 로컬 모드에서는 모든 방문자가 이미 식별된 상태로 들어오므로 그 문이 열릴 일이 없다.
상단 바에 "로컬 모드"라고 표시되는 근거도 같은 설정값이다.


== .vscode: 에디터가 프로젝트의 규칙을 실어 나른다

앱이 돌았으니 이제 코드를 고치는 사람의 환경을 갖출 차례다.
여기서는 코드 편집기로 VS Code(Visual Studio Code)를 쓰고, 그 위에 확장(extension) 두 개를 얹는다.
설치는 {ch-setup}의 안내를 따르면 된다.
다른 편집기를 쓰는 독자라면 이 절을 "프로젝트의 규칙을 어떻게 저장소에 실어 보내는가"라는 관점으로만 읽어도 좋다.

.[용어 풀이] 코드 편집기(Code Editor)와 확장(Extension)
[NOTE]
====
코드 편집기는 코드를 쓰고 고치는 일에 특화된 프로그램이고, VS Code는 마이크로소프트가 무료로 배포하는 코드 편집기다.
확장은 그 편집기에 기능을 하나씩 얹어 주는 부가 프로그램이다.
편집기 본체는 파일을 열고 글자를 고치는 기본 기능만 갖추고, 언어마다 다른 자동 완성이나 디버깅 같은 기능은 확장이 채운다.
스마트폰을 사 놓고 필요한 앱을 골라 까는 것과 같아서, 같은 편집기라도 어떤 확장을 깔았느냐에 따라 다른 도구가 된다.
====

에디터 설정은 보통 개인의 영역이라, 글꼴 크기나 색 테마를 저장소에 강요할 이유는 없다.
그러나 "이 프로젝트의 Go 파일은 저장할 때 gofmt를 돌린다", "검증은 이 명령들로 한다" 같은 규칙은 취향이 아니라 프로젝트의 성질이다.
이런 규칙이 각자의 머릿속에만 있으면 새로 합류한 사람도, AI 에이전트도 알 길이 없다.

VS Code는 작업 폴더의 `.vscode/` 디렉터리를 읽어 개인 설정 위에 덮어쓴다.
프로젝트에 종속된 규칙만 골라 이 디렉터리에 담아 커밋하면, 클론한 사람은 별도 안내 없이 같은 환경을 얻는다.
Flashcard의 `.vscode/`에는 파일 네 개(`extensions.json`, `settings.json`, `tasks.json`, `launch.json`)가 들어 있다.

=== extensions.json: 필요한 확장을 저장소가 알려 준다

파일의 내용은 추천 확장 두 개의 목록이 전부다.

[source,json]
----
{
  "recommendations": ["golang.go", "anthropic.claude-code"]
}
----

VS Code는 이 목록을 읽고 "이 저장소가 권장하는 확장이 있습니다"라고 안내한다(강제 설치가 아니라 추천이다).
`golang.go`는 Go 공식 확장으로 뒤에서 볼 포맷·검사·디버깅이 모두 여기에 얹히고, `anthropic.claude-code`는 {ch-claude-code}의 Claude Code를 에디터 안에서 띄우는 확장이다.

목록이 두 개뿐인 것은 의도한 결과다.
이 저장소의 코드는 Go 하나로 수렴하고(화면도 서버가 렌더링하는 템플릿과 순수 CSS, 100줄의 JS라 별도 툴체인이 없다), 포맷은 설정 옵션이 없는 gofmt가 독점하므로 포매터나 린터(코드의 흠을 찾아 주는 정적 분석 도구) 확장을 따로 들일 이유가 없었다.

=== settings.json: 저장하는 순간 규칙이 적용된다

다음은 `settings.json`의 주요 부분으로, 파일을 저장할 때 적용되는 규칙과 테스트 실행 방식을 정한다.

[source,json]
----
{
  "editor.formatOnSave": true,

  "[go]": {
    "editor.defaultFormatter": "golang.go",
    "editor.codeActionsOnSave": {
      "source.organizeImports": "explicit"
    }
  },
  "go.useLanguageServer": true,
  "go.formatTool": "gofmt",
  "go.vetOnSave": "package",
  "go.testFlags": ["-count=1"],
  // ...
  "files.trimTrailingWhitespace": true
}
----

`editor.formatOnSave`가 켜져 있고 `[go]` 블록이 포매터를 Go 확장으로 지정하므로, Go 파일을 저장하는 순간 gofmt가 돌아 {ch-go-testing}에서 본 세로 정렬이 자동으로 맞춰진다.
`source.organizeImports`는 저장할 때 쓰지 않는 import를 지우고 남은 것을 표준 순서로 정렬한다.
Go는 쓰지 않는 import를 컴파일 에러로 처리하므로, 이 한 줄이 "빌드는 되는데 import만 어긋난" 상태를 아예 만들지 않는다.
`go.vetOnSave`를 `package`로 두면 저장할 때마다 그 파일이 속한 패키지에 `go vet`이 돌아, {ch-go-testing}에서 본 정적 분석이 편집 중에 밑줄로 나타난다.

.[용어 풀이] 언어 서버(Language Server)
[NOTE]
====
에디터와 따로 떨어져 돌면서 코드를 읽고 이해해 주는 배후 프로그램이다.
자동 완성, 정의로 이동, 오류 표시 같은 기능을 에디터가 직접 구현하는 대신 이 서버에 물어보는 구조라, 언어 하나에 서버 하나만 만들어 두면 여러 에디터가 함께 쓸 수 있다.
Go의 언어 서버는 gopls이고, `go.useLanguageServer`가 이를 켜는 설정이다.
====

`go.testFlags`의 `-count=1`은 테스트를 돌릴 때 캐시된 지난 결과를 재사용하지 않게 하는 플래그다.
에디터에서 실행 버튼으로 돌리는 테스트가 "방금 정말 실행된 결과"라는 것을 보장한다.

=== tasks.json: 검증 명령에 이름을 붙인다

{ch-go-testing}의 `go build`·`go vet`·`go test`는 모두 터미널에서 치면 되는 명령이다.
그래도 태스크(task, 자주 쓰는 명령에 이름을 붙여 VS Code 메뉴에서 실행하게 하는 기능)로 등록하면 명령을 외우지 않아도 되고, VS Code가 출력에서 파일과 줄 번호를 뽑아 문제 목록으로 만들어 준다.

[source,json]
----
{
  "version": "2.0.0",
  "tasks": [
    { "label": "go: build", "type": "shell", "command": "go build ./...",
      "group": "build", "problemMatcher": ["$go"] },
    { "label": "go: test", "type": "shell", "command": "go test ./...",
      "group": "test", "problemMatcher": ["$go"] },
    { "label": "go: vet", "type": "shell", "command": "go vet ./...",
      "problemMatcher": ["$go"] },
    {
      "label": "전체 검증",
      "dependsOn": ["go: build", "go: vet", "go: test"],
      "dependsOrder": "sequence",
      "group": { "kind": "test", "isDefault": true },
      "problemMatcher": []
    }
  ]
}
----

`problemMatcher`의 `$go`는 VS Code에 내장된 출력 해석 규칙이다.
`go vet`이 `internal/model/deckslug.go:42:5: ...` 같은 줄을 뱉으면, 이 규칙이 파일 경로와 위치를 알아채 문제 목록에 클릭 가능한 항목으로 올린다.

마지막 `전체 검증` 태스크는 앞의 셋을 순서대로 묶고, `dependsOrder`가 `sequence`이므로 하나라도 실패하면 거기서 멈춘다.
커밋 전에 이 태스크 하나만 돌리면 기계적 검증이 한 번에 끝난다.

=== launch.json: F5 한 번으로 디버거를 붙인다

다음은 `launch.json` 전문으로, 서버 실행과 테스트 실행이라는 두 가지 디버깅 구성이 담겨 있다.

.[용어 풀이] 디버거(Debugger)와 중단점(Breakpoint)
[NOTE]
====
프로그램을 내가 지정한 줄에서 잠시 멈춰 세우고, 그 순간의 변수 값을 하나씩 들여다보게 해 주는 도구가 디버거다.
영상을 특정 장면에서 멈춰 놓고 화면 구석구석을 뜯어보는 것과 같아서, 코드가 어떤 값으로 도는지를 짐작이 아니라 눈으로 확인할 수 있다.
어디서 멈출지 미리 지정해 두는 표식이 중단점이고, 에디터에서 줄 번호 왼쪽을 클릭해 찍는다.
Go의 디버거는 델브(Delve)이고, 실행 파일 이름은 `dlv`다.
====

[source,json]
----
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "서버 (cmd/server)",
      "type": "go",
      "request": "launch",
      "mode": "debug",
      "program": "${workspaceFolder}/cmd/server"
    },
    {
      "name": "Go: 현재 파일의 패키지 테스트",
      "type": "go",
      "request": "launch",
      "mode": "test",
      "program": "${fileDirname}"
    }
  ]
}
----

첫 구성에 환경 변수 항목이 없다는 것부터 짚어 두자.
로컬 모드 덕분에 디버거로 띄우는 서버도 아무 값 없이 그냥 뜨므로, 클론 직후의 저장소에서 F5(VS Code에서 디버깅 실행을 시작하는 단축키) 한 번으로 중단점까지 걸 수 있다.
{ch-go}에서 읽은 `srs.Grade`에 중단점을 걸고 카드 하나를 "맞음"으로 넘겨 보면, 글로만 따라가던 간격 계산이 값을 바꿔 가며 눈앞에서 진행된다.

두 번째 구성은 지금 열어 둔 파일이 속한 패키지의 테스트를 디버거 아래에서 돌린다.
{ch-go-testing}에서 본 테이블 주도 테스트가 실패할 때, 실패한 케이스의 입력값을 중단점에서 직접 들여다보는 용도다.

델브는 따로 준비해 둘 필요가 없다.
`dlv` 실행 파일이 없으면 Go 확장이 설치하겠느냐고 먼저 물어 준다.

에디터의 저장 시 검사와 에이전트의 훅이 같은 규칙을 지키는 두 입구라는 이야기는 {ch-quality-gates}에서 잇는다.


== 환경 변수로 동작 바꾸기

이 장에서 "환경 변수가 없으면"이라는 말을 여러 번 썼으니 개념을 정리하고 가자.
환경 변수(Environment Variable)는 프로그램이 실행될 때 운영체제에서 건네받는 이름표 붙은 값으로, 코드를 고치지 않고 프로그램의 동작을 바깥에서 바꾸는 수단이다.
로컬 모드는 이 관점에서 다시 읽을 수 있는데, "환경 변수를 하나도 채우지 않았을 때의 기본 동작"을 신중하게 설계해 둔 결과다.

몇 개는 지금 당장 돌려 볼 수 있다.
셸에서는 명령 앞에 `이름=값`을 붙여 한 줄로 적을 수 있는데, 이는 그 값을 환경 변수로 얹은 채 뒤의 명령을 실행하라는 뜻이다(두 개의 명령이 아니라 한 줄짜리 명령 하나다).
`SQLITE_PATH=~/cards/my.db go run ./cmd/server`로 실행하면 데이터 파일의 위치가 바뀌고, `PORT=9090 go run ./cmd/server`로 실행하면 접속 주소가 `http://localhost:9090`으로 바뀐다.
화면과 API가 한 서버에서 나가므로 포트를 바꿔도 다른 곳에 알릴 일이 없다.

그리고 동작을 가장 크게 바꾸는 환경 변수가 남아 있다.
`DATABASE_URL`을 채우는 순간 서버는 SQLite를 접고 진짜 PostgreSQL에 연결하며, 함께 채우는 `SUPABASE_URL`과 `SUPABASE_ANON_KEY`가 화면에 로그인을 만든다.
그 값들을 어디서 얻고, 매번 타이핑하지 않도록 어디에 적어 두는지는 {ch-env-secrets}에서 다룬다.

== 이 구성이 내주는 것

무설정 실행과 커밋된 에디터 설정에도 대가가 있다.

첫째, 로컬 모드는 운영과 다른 데이터베이스 엔진 위에서 돈다.
`internal/litestore`는 `internal/pgstore`와 같은 인터페이스를 SQLite 방언으로 다시 구현한 것이라 같은 기능을 두 벌 유지하는 비용이 들고, PostgreSQL에만 있는 기능({ch-supabase-db}에서 다룰 RLS와 태그 검색용 GIN 인덱스)은 로컬 모드에 없으므로 로컬에서 통과했다고 운영에서도 똑같이 동작한다는 보장은 없다.
그 대가로 계정도 네트워크도 없는 실행을 얻었고, 남는 간극은 {ch-supabase-db}에서 개발용 PostgreSQL을 연결해 메운다.

둘째, `.vscode/`는 VS Code에 맞춘 설정이라 다른 에디터를 쓰는 사람에게는 도움이 되지 않는다.
Neovim이나 JetBrains GoLand를 쓰는 사람은 같은 규칙을 자기 환경에 손으로 옮겨야 한다.
이 문제를 줄이는 방법은 규칙의 원본을 에디터 바깥에 두는 것이다.
Flashcard에서 포맷의 원본은 `gofmt`이고 검증의 원본은 `go vet`과 `go test`이며, `.vscode/`는 그 명령들을 편하게 부르는 껍데기라 에디터를 바꿔도 따라오지 못할 규칙이 없다.

셋째, `settings.json`에 개인 취향을 섞기 시작하면 금세 다툼거리가 된다.
글꼴, 색 테마, 탭 표시 폭처럼 커밋되는 파일의 내용을 바꾸지 않는 항목은 개인 설정에 두고, 저장소에는 파일 내용을 바꾸는 규칙만 남기는 것이 경계선이다.
`files.trimTrailingWhitespace`가 저장소에 들어간 이유도 그것이 취향이 아니라 커밋 내용을 바꾸는 규칙이기 때문이다.

== 에이전트 활용 아이디어

개발 환경 자체도 에이전트와 함께 다듬을 수 있다.

`CLAUDE.md`에는 "로컬 서버는 go run ./cmd/server, 환경 변수 없이 로컬 모드로 뜬다"와 "local-db/ 폴더는 지워도 되는 개발 데이터다"를 적어 둘 만하다.
전자는 에이전트가 검증용 서버를 띄울 때, 후자는 실험 뒤 정리할 때 판단 근거가 된다.

"서버를 띄우고 홈 화면과 /api/healthz 응답을 확인한 뒤 종료해 달라"는 스모크 테스트 지시를 스킬로 저장해 두면, 변경이 앱을 실제로 깨뜨렸는지 명령 하나로 확인할 수 있다.
`tasks.json`에 적어 둔 검증 명령과 같은 것을 에이전트도 쓰게 하면, 사람과 에이전트의 게이트가 어긋나지 않는다.

== 정리

이번 장에서는 {ch-first-run}의 무설정 실행이 코드로 어떻게 가능한지 해부했다.
`config.go`가 `DATABASE_URL`이 없는 것을 보고 SQLite 드라이버와 로컬 인증을 채우고, API 쪽은 `LocalMiddleware`가, 화면 쪽은 `withUser`의 로컬 분기가 고정 사용자를 세워 로그인 화면 자체가 뜨지 않는다.
바뀌는 것은 문지기와 저장소이고, 라우터·핸들러·화면은 배포 환경과 같은 코드다.
`.vscode/` 네 파일은 포맷과 검증 명령, 디버깅 구성을 저장소가 실어 나르게 하고, 환경 변수는 코드를 고치지 않고 동작을 바꾸는 통로로 남는다.

이 장으로 3부의 앱 코드 해부가 끝났다.
{ch-database}에서 요구사항을 테이블로 옮겼고, {ch-go-basics}부터 {ch-go-testing}까지 그 테이블을 다루는 Go 코드와 테스트를 읽었다.
{ch-gin}에서 Gin이 요청을 핸들러로 잇는 길을 봤고, {ch-html-css}부터 {ch-htmx}까지 HTML·CSS와 html/template, htmx로 화면이 만들어지는 과정을 따라갔다.
그리고 이 장에서 그 전부가 설정 없이 도는 원리를 확인하고, 코드를 고치는 사람의 작업 환경까지 갖췄다.
여기까지가 내 컴퓨터 안의 이야기다.

그런데 이 앱은 아직 내 컴퓨터에만 있어서, 주소를 아는 사람도, 접속할 방법도 없다.
4부에서는 이 앱을 세상에 공개하는 길을 걷는다.
그 첫걸음은 배포 버튼이 아니라 코드의 이력을 관리하는 규율, 곧 {ch-git}의 Git이다.
