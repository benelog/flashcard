= 환경 변수와 시크릿: 값이 두 벌이 된다

{ch-supabase-db}에서 개발용과 운영용 Supabase 프로젝트를 분리하면서 연결 문자열과 키도 두 벌이 됐다.
값이 두 벌이 되는 순간부터는 값 자체보다 값을 다루는 방식이 문제가 된다.
이 값들을 로컬에서 어떻게 읽어 오고, 어디에 보관하며, 무엇을 비밀로 다루는가.
이번 장에서는 그 세 질문에 이 저장소가 내린 답을 살펴보겠다.
먼저 로컬 서버를 개발 DB에 붙이는 실행 스크립트 `run_dev.sh`를 읽고, 값의 단일 출처인 `.env.dev`와 그 값을 셸에 올리는 일을 누가 맡을지 따져 본 뒤, 시크릿이 새지 않게 지키는 습관으로 마무리한다.

== 로컬에서 개발 DB에 붙는다: run_dev.sh

로컬에서도 데이터베이스는 둘이다.
평소에는 SQLite 파일 하나면 충분하지만(`./run_local.sh`), 풀러와 RLS, JWKS 검증과 OAuth 로그인처럼 Supabase에 붙어야만 확인되는 것들을 시험할 때는 내 컴퓨터의 서버를 개발 DB에 붙여야 한다.
그 두 번째 실행 방법이 저장소 루트의 `run_dev.sh`다.
개발 프로젝트의 값을 담아 둔 `.env.dev` 파일을 읽어 셸에 올리고 서버를 띄우는 스크립트로, 전체가 열 줄 남짓이다.

[source,bash]
----
env_file="${ENV_FILE:-.env.dev}"
if [[ ! -f "$env_file" ]]; then
  echo "$env_file 이 없습니다. .env.dev.example 를 복사해 개발용 Supabase 값을 채우세요." >&2
  exit 1
fi

set -a
source "$env_file"
set +a
# ... (DATABASE_URL·SUPABASE_URL·SUPABASE_ANON_KEY 가 채워져 있는지 검사)

exec go run ./cmd/server
----

`set -a`는 그 뒤로 대입되는 변수를 모두 export 대상으로 만드는 셸 설정이라, `source`로 읽어 들인 파일의 값들이 그대로 자식 프로세스의 환경 변수가 된다.
{ch-supabase-db}에서 본 대로 `DATABASE_URL`이 채워져 있으면 앱은 PostgreSQL과 Supabase 인증 모드로 뜨므로, 코드는 그대로 두고 실행 스크립트만 바꿔 로컬 SQLite와 개발 DB를 오간다.
로그인까지 왕복하려면 개발 Supabase 프로젝트의 Redirect URL 목록에 `http://localhost:8080/auth/callback`이 등록되어 있어야 한다({ch-supabase-auth}).

스키마를 개발 DB에 미리 적용해 보는 `migrate_dev.sh`도 짝으로 둔다.
같은 `.env.dev`에서 마이그레이션용 연결 문자열만 꺼내 {ch-migrations}의 마이그레이션 실행기를 돌리는 스크립트다.

[source,bash]
----
# 마이그레이션은 advisory lock 을 잡으므로 transaction pooler(6543)가 아니라
# Session pooler / direct connection(5432)이어야 한다.
: "${MIGRATE_DATABASE_URL:?$env_file 에 MIGRATE_DATABASE_URL(5432)이 필요합니다}"
export MIGRATE_DATABASE_URL

echo "==> dev DB 마이그레이션 적용"
exec go run ./cmd/migrate
----

이 스크립트가 읽는 파일이 개발 프로젝트의 `.env.dev` 하나뿐이라는 점이 설계의 절반이다.
운영 연결 문자열을 건네받을 통로가 아예 없으므로, 손이 미끄러져 운영 DB에 마이그레이션을 거는 사고가 구조적으로 불가능하다.


== 환경 변수 구성

3부까지의 로컬 모드에는 환경 변수가 하나도 없었지만, Supabase에 붙는 순간 연결 문자열과 키가 생기고, {ch-supabase-db}에서 프로젝트를 개발·운영으로 나눴으니 그 값도 두 벌이다.
저장소 루트의 `.env.dev.example`이 변수의 전체 목록이다.
아래 블록의 두 연결 문자열은 {ch-supabase-db}과 {ch-migrations}에서 본 형식 그대로다.
그 두 장에서 계속 나온 6543과 5432가 끝에서 두 번째 자리의 포트 번호이고, 이 앱에서 두 문자열이 서로 다른 곳은 그 숫자뿐이다.

[source,bash]
----
# 로컬 모드(SQLite)는 이 파일이 필요 없다. ./run_local.sh 는 환경 변수 없이 뜬다.
# Vercel 대시보드에는 같은 이름으로 등록하되 스코프를 나눈다:
# Preview = 개발 프로젝트 값, Production = 운영 프로젝트 값.

# 서버용: Supabase → Connect → Transaction pooler (port 6543)
DATABASE_URL=postgresql://postgres.<dev-project-ref>:<password>@aws-0-us-east-1.pooler.supabase.com:6543/postgres

# 마이그레이션용: Session pooler (port 5432).
# advisory lock 이 세션에 묶이므로 6543 은 쓸 수 없고,
# direct 연결(db.<ref>.supabase.co)은 IPv6 전용이라 IPv4 환경에서는 붙지 않는다.
MIGRATE_DATABASE_URL=postgresql://postgres.<dev-project-ref>:<password>@aws-0-us-east-1.pooler.supabase.com:5432/postgres

# 웹 로그인(OAuth)과 토큰 검증. Supabase → Settings → API
SUPABASE_URL=https://<dev-project-ref>.supabase.co
SUPABASE_ANON_KEY=<anon key 또는 publishable key>
# JWKS URL 은 SUPABASE_URL 에서 자동 유도된다. 직접 지정하려면:
# SUPABASE_JWKS_URL=https://<dev-project-ref>.supabase.co/auth/v1/.well-known/jwks.json
----

파일 이름이 `.env.local`이 아니라 `.env.dev`인 데는 이유가 있다.
`.env.local`은 Create React App에서 시작해 Next.js와 Vite로 퍼진 자바스크립트 빌드 도구의 관례인데, 거기서 `.local`은 "로컬 환경"이 아니라 "이 컴퓨터에만 있고 커밋하지 않는 덮어쓰기 파일"을 뜻한다.
이 책의 환경 이름은 로컬·개발·운영이고 그중 로컬 모드는 환경 변수가 하나도 필요 없으므로, 같은 이름을 쓰면 파일 이름이 가리키는 환경과 파일이 담은 값이 어긋난다.
그래서 이 저장소는 파일 이름을 환경 이름에 맞춰 `.env.dev`로 부른다.

첫 줄의 주석 그대로 이 파일이 필요해지는 것은 Supabase에 연결할 때부터고, 로컬에서 값을 채울 때는 개발 프로젝트의 것을 쓴다.
같은 목록을 개발 프로젝트 값으로 채워 `.env.dev`라는 이름으로 저장해 두면 앞 절의 `run_dev.sh`와 `migrate_dev.sh`가 그 파일을 읽는다.
자리표시자만 담긴 `.env.dev.example`은 저장소에 함께 있다.

=== anon key는 왜 비밀이 아닌가

목록의 세 값 중 성격이 다른 하나가 `SUPABASE_ANON_KEY`다.
{ch-supabase-auth}에서 봤듯 anon key는 요청이 어느 프로젝트 것인지 구분하는 공개 전제의 식별자이고, {ch-supabase-db}의 RLS 전략 덕분에 이 키로는 어차피 데이터에 접근할 수 없다.
이 앱에서는 인증까지 Go 서버가 대신 처리하므로, 공개돼도 되는 값조차 브라우저로 내려갈 일이 없다.

=== 서버는 파일이 아니라 셸에서 읽는다

Go 쪽은 `.env` 파일을 읽지 않고, {ch-supabase-db}에서 본 `internal/config/config.go`가 `os.Getenv`로 셸의 환경 변수를 그대로 가져올 뿐이다.
godotenv 같은 라이브러리를 넣지 않은 것은 의도적인 선택이다.
배포 환경인 Vercel은 대시보드에 등록한 값을 프로세스 환경 변수로 주입하므로 파일을 읽는 코드는 로컬에만 필요한 군더더기가 되고, 로컬과 배포가 같은 경로로 설정을 받는 편이 "로컬에서는 되는데 배포하면 안 되는" 부류의 사고를 줄인다.
필수 값이 빠졌으면 서버가 뜨는 시점에 즉시 실패해, 설정 오류를 첫 요청의 알 수 없는 500 오류가 아니라 명확한 메시지로 드러낸다.
JWKS URL은 따로 받지 않아도 `Load`가 `SUPABASE_URL` 뒤에 정해진 경로를 붙여 만들어 내고, `SUPABASE_JWKS_URL`이나 `SUPABASE_JWT_SECRET`(구형 프로젝트의 HS256 폴백, {ch-token-verification})을 직접 지정하면 그쪽이 우선한다.

각 변수의 성격을 구분해 두자.
`DATABASE_URL`은 DB 비밀번호가 포함된 진짜 비밀로, 유출되면 데이터 전체가 넘어간다.
브라우저로 내려가는 일 없이 서버 측(Vercel 함수 환경 변수)에만 존재해야 한다.
`SUPABASE_URL`은 프로젝트 주소이고 `SUPABASE_ANON_KEY`는 앞 절에서 본 공개 전제의 식별자라 비밀은 아니지만, 프로젝트마다 달라서 설정으로 뺐다.

=== 값을 셸에 올리는 일은 누가 맡는가

Go API가 셸의 환경 변수만 본다는 것은, 개발 DB에 붙여 돌리려면 셸에 값이 올라와 있어야 한다는 뜻이다.
`DATABASE_URL='...' go run ./cmd/server`처럼 명령 앞에 붙이는 방식은 한 번은 견딜 만하지만, 서버를 껐다 켤 때마다, 마이그레이션을 돌릴 때마다, 새 터미널 탭을 열 때마다 반복해야 한다.
누군가는 이 반복을 대신해야 하고, 맡길 만한 후보는 셋이다.

첫째는 앱이 직접 파일을 읽는 것이다.
godotenv 같은 라이브러리를 넣으면 서버가 뜨면서 `.env` 파일을 찾아 자기 환경 변수로 채운다.
앞 절에서 본 대로 로컬과 배포가 설정을 받는 경로가 달라지는 방식이라 이 저장소는 택하지 않았다.
Go에 `.env` 파일을 읽는 관례가 없다는 점도 여기에 더해진다.
표준 라이브러리가 제공하는 것은 `os.Getenv`뿐이다.

둘째는 셸 계층의 도구에 맡기는 것이고, direnv가 대표적이다.
디렉터리에 `.envrc` 파일을 두면, 셸이 그 디렉터리로 들어가는 순간 파일에 적힌 변수를 자동으로 export하고 벗어나면 되돌린다.
설정을 환경 변수로 받는 12요소 앱(Twelve-Factor App)의 원칙을 앱 코드에서 지키면서 로컬의 편의는 앱 바깥에서 해결하는, 언어와 무관한 해법이다.
대신 저장소를 클론한 사람마다 도구를 설치하고 셸 설정 파일에 훅을 걸어야 하고, 값이 셸에 상주하는 데서 오는 함정이 하나 따라온다(잠시 뒤에 본다).

셋째는 개발 DB에 붙는 실행 경로 자체를 스크립트로 못 박는 것이고, 이 저장소의 선택이다.
개발 DB로 가는 길은 이 장 첫머리에서 본 `run_dev.sh`와 `migrate_dev.sh` 둘뿐이고, 두 스크립트가 `.env.dev`를 직접 읽어 자기가 띄우는 자식 프로세스에만 넘긴다.
설치할 도구가 없으니 저장소를 클론한 사람이 곧바로 실행할 수 있고, 값이 셸에 남지 않으니 개발 DB의 연결 문자열이 다른 명령에 조용히 딸려 들어갈 일도 없다.
앱이 파일을 읽지 않기로 했다면 그 일을 앱 바깥의 누군가가 맡아야 한다는 조건은 그대로 지키되, 그 자리를 상주하는 도구 대신 실행 스크립트가 채운 것이다.

그러면 스크립트로 만들 것까지는 없는 일회성 명령은 어떻게 하는가.
`psql`로 테이블을 들여다보거나 `go run ./cmd/migrate`를 그대로 실행하고 싶을 때는, 그 터미널에서 같은 파일을 한 번 읽어 오면 된다.

[source,bash]
----
set -a
source .env.dev
set +a

psql "$MIGRATE_DATABASE_URL"
----

`set -a`는 `run_dev.sh`가 쓰는 것과 같은 설정으로, 그 뒤로 대입되는 변수를 모두 export 대상으로 만든다.
지금 열려 있는 터미널 창에서만 유효하고 창을 닫으면 사라지므로, 도구를 하나도 설치하지 않고 direnv가 주는 편의의 대부분을 얻는다.
이런 일회성 명령이 하루에도 몇 번씩 필요할 만큼 잦아진다면 그때 direnv를 얹는 것이 낫고, 도구를 하나 늘릴 만한지는 각자의 작업 방식이 정할 문제다.

값이 셸에 올라와 있을 때의 함정은 어느 방식을 택하든 알아 둘 필요가 있다.
`DATABASE_URL`이 셸에 남아 있으면, 로컬 모드로 띄웠다고 생각한 서버가 실은 개발 DB에 붙는다.
{ch-supabase-db}에서 본 대로 `DATABASE_URL`의 유무가 모드를 정하기 때문이다.
그래서 `run_local.sh`는 이 변수를 지운 채로 서버를 띄운다.

[source,bash]
----
exec env -u DATABASE_URL go run ./cmd/server
----

`env -u`는 지정한 환경 변수를 지운 채로 명령을 실행하는 옵션이다.
로컬 모드는 언제나 SQLite로 뜨고 개발 DB에 붙는 것은 `run_dev.sh`로만 한다는 규칙을, 문서가 아니라 스크립트가 강제하게 만든 것이다.
셸에 환경 변수를 올려 두는 방식을 쓸 때는, 그 변수가 의미를 갖는 다른 실행 경로가 없는지 함께 살펴야 한다.

운영 프로젝트의 값은 어느 방식으로도 셸에 올리지 않는다.
운영 값이 늘 셸에 올라와 있으면 개발 DB에 돌릴 마이그레이션을 운영에 돌리는 사고가 명령 한 줄 거리로 가까워지기 때문이다.
{ch-migrations}에서 본 대로 스키마 적용을 워크플로에 맡기고 나면 이 원칙을 끝까지 밀고 갈 수 있다.
로컬에서 운영 연결 문자열이 필요했던 유일한 작업이 마이그레이션이었는데 그것을 이제 저장소가 대신 실행하므로, 운영 값은 GitHub 저장소 시크릿 한 곳에만 있으면 되고 개발자의 노트북에는 아예 없어도 된다.
값이 없는 곳에서는 그 값으로 저지르는 사고도 일어나지 않는다.

=== 시크릿 관리 주의점

시크릿이 저장소에 새는 사고를 막는 첫 방어선은 `.gitignore`다.

[source,txt]
----
# env files (실제 값은 커밋하지 않는다. 예제 파일만 예외)
.env*
!.env.dev.example
----

`.env`로 시작하는 모든 파일을 무시하되 자리표시자만 담긴 예제 파일만 예외로 커밋한다.
예제 파일에는 `<password>`처럼 형태만 보여 주는 값을 두고, 실제 값은 로컬의 `.env.dev`와 Vercel 대시보드의 환경 변수, 그리고 GitHub 저장소 시크릿에만 존재하게 한다.

몇 가지 습관을 덧붙인다.
첫째, 새 변수를 추가할 때 예제 파일에도 반영해 두면 예제 파일이 곧 설정 문서가 된다.
둘째, 유출이 의심되면 즉시 회전한다.
Supabase 대시보드에서 DB 비밀번호를 재설정하면 기존 연결 문자열은 무효가 된다.
실수로 비밀 값을 커밋해 push까지 했다면 그 값은 유출된 것으로 간주한다.
커밋을 지워도 원격 저장소의 이력과 이미 퍼진 사본에는 남을 수 있으므로, 대처는 이력을 고치는 것이 아니라 값을 재발급해 옛 값을 쓸모없게 만드는 것이다.
지금은 나만 보는 비공개 저장소라도 마찬가지다.
저장소는 클론될 때마다 이력째 복사되고, 언젠가 공개로 바꾸거나 협업자를 초대하는 순간 과거 이력까지 함께 열린다.
셋째, 값이 사는 곳을 환경마다 하나로 정해 둔다.
로컬은 `.env.dev` 하나, 프리뷰와 프로덕션은 Vercel의 스코프별 환경 변수, 마이그레이션 워크플로는 GitHub 저장소 시크릿이 그곳이다.
운영 프로젝트의 값이 사는 곳은 그중 뒤의 둘뿐이고, 값을 바꿀 때는 그 두 곳을 함께 고친다.


== 정리

첫째, 개발·운영 프로젝트를 분리하면 연결 문자열과 키가 두 벌이 된다.
개발 값의 단일 출처는 `.env.dev` 하나이고, 이 파일을 읽는 곳은 `run_dev.sh`와 `migrate_dev.sh` 둘뿐이다.
값이 셸에 상주하지 않으므로 로컬 모드로 띄운 서버가 개발 DB에 붙는 사고도, 개발 DB의 연결 문자열이 다른 명령에 딸려 들어가는 사고도 막힌다.

둘째, 운영 값은 로컬에 두지 않는다.
운영 값이 사는 곳은 Vercel의 Production 스코프와 GitHub 저장소 시크릿 두 곳뿐이고, 값이 없는 곳에서는 그 값으로 저지르는 사고도 일어나지 않는다.

셋째, 시크릿의 첫 방어선은 `.gitignore`이고, 유출이 의심되면 이력을 고치는 대신 값을 재발급해 옛 값을 쓸모없게 만든다.
자리표시자만 담긴 예제 파일을 최신으로 유지하면 그 파일이 곧 설정 문서가 된다.

값 관리까지 갖췄으니 앱을 오래 굴릴 기초는 놓였다.
다음 {ch-pwa}에서는 배포된 웹 앱을 홈 화면에 설치되는 앱으로 만드는 PWA를 다룬다.
