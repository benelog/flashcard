# 원고 장 파일 교정

## 전체 흐름

1. **1차 기준을 확인한다.** `doc/CLAUDE.md`의 "문체 가이드", "금지·주의 표현", "AsciiDoc 표기 규약"이
   이 책의 교정 기준이다. 컨텍스트에 없으면 먼저 Read로 읽는다.
2. **대상 파일을 Read 도구로 처음부터 끝까지 읽는다.** 긴 파일은 나눠서라도 전체를 읽는다.
   일부만 보고 고치면 같은 파일 안의 표기 혼용을 놓친다. `cat`은 쓰지 않는다(주석·마커가 걸러져 보인다).
3. **문제를 먼저 목록으로 수집하고, 수정은 그 후에 한다.**
   표기 통일 방향은 파일 전체와 책 전체 용례를 본 뒤에야 정할 수 있기 때문이다.
4. **표기 일관성을 grep으로 대조한다.** (아래 절 참고)
5. **제목을 고칠 때는 참조를 먼저 확인한다.**
   장 제목(첫 줄 `=`)을 고치면 `doc/book.config.mjs`의 toc 제목도 함께 고친다
   (사이드바·PDF 차례·`{ch-…}` 라벨이 전부 toc에서 파생된다).
   절 제목은 다른 원고가 참조하는 곳이 있는지 grep으로 확인한다.
6. **Edit로 수정한다.** 서로 다른 부분은 한 응답에 여러 Edit를 묶어 보낸다.
   문장을 나누면 줄도 함께 나눈다(소스 수준에서 한 문장마다 줄바꿈, 문단 구분은 빈 줄).
7. **검증한다.** (아래 절 참고)
8. **유형별로 보고한다.** (아래 절 참고)

## 점검 기준

1차 기준은 `doc/CLAUDE.md`다. 특히 아래를 그대로 적용한다.

* **문체 가이드**: '~다'체(유일한 예외는 `preface.adoc`의 저자 서문), 한 문장 한 줄,
  기술 용어 첫 등장 시 한글(영문) 병기, 정도 부사 대신 근거·수치.
* **금지·주의 표현**: 줄표(—), "사실상", "지점", "무너진다", "맞물린다", "가른다/갈린다",
  "축", "가볍다/무겁다", "겹", "손잡이", "~인 셈이다", 번역투, 조사와 문장 호응, 띄어쓰기·표기.
  각 항목의 허용 예외와 대체 요령이 `doc/CLAUDE.md`에 상세히 있으므로 그 전문을 따른다.
* **AsciiDoc 표기 규약**(downdoc 부분집합): 굵게는 `*한 겹*`, 중첩 목록 금지, 맨몸 URL 금지
  (`https://주소[표시 문구]` 매크로), `[source,언어]` + `----`, 백틱 든 인라인 코드는 이중 백틱,
  패스스루 `+…+`·문서 속성 정의 금지.
* **장 번호는 본문에 직접 쓰지 않는다.** 다른 장 참조는 `{ch-파일명}` 토큰이다.
  본문에서 날 숫자 장 참조("15장에서")를 발견하면 토큰으로 바꾼다.
  예외 셋(코드 블록 안 생략 주석, "N부" 참조, 카드 수 세기 "카드 8장")은 그대로 둔다.
* **용어 상자 소유권**: 한 용어의 상자는 책 전체에서 한 장만 갖는다(`doc/CLAUDE.md`의 배정표).
  다른 장에 중복 상자가 보이면 고치지 말고 보고한다. 상자 제목은 `[용어 풀이] 이름(영문)` 형식이다.
* **비개발자 독자**: 전문용어로만 굴러가는 문장은 일상어 풀이가 먼저 오는지,
  코드 블록 앞에 "이 코드가 하는 일" 한두 문장이 있는지 본다.

지침에 더해, 아래는 이런 원고에서 실제로 자주 나온 문제 패턴이다.
`doc/CLAUDE.md`와 어긋나는 항목이 있으면 `doc/CLAUDE.md`가 우선한다.

### 오타와 조사

* 한글 오타: 프럼프트→프롬프트처럼 자주 치는 글자. 의심되면 국어사전 기준으로 본다.
* 백틱·따옴표 뒤의 조사는 **발음 기준**으로 검사한다. 영어 단어와 숫자는 한국어 발음으로 받침 유무를 판단한다.
    - `study_sessions`(세션스, 받침 없음) → "가", "를", "와"
    - `2026-07-28`(이십팔, ㄹ 받침) → "과", "은"
    - 'record not found'(파운드, 받침 없음) → "라는"
    - `htmx`(에이치티엠엑스, 받침 없음) → "가" / `sw.js`(제이에스, 받침 없음) → "가"
* "알람"은 거의 항상 "알림"의 오용이다.

### 어색한 문장

* 과거완료 남용: "확인했었다", "소개했었다" → 단절된 과거를 강조할 이유가 없으면 "확인했다", "소개했다".
* 중복 표현: "매번 ~마다", "'A', 'B'의 두 개의", 한 문장 안에 같은 단어가 세 번 나오는 문장.
  중복이 심하면 두 문장으로 나눈다(한 문장에는 한 가지 내용). 나눌 때는 줄도 나눈다.
* 주어-서술어 호응: "모듈은 ~ 제어할 수 있다"(모듈이 제어하는 게 아님) → "모듈을 추가하면 ~ 제어할 수 있다".
  연결어미 뒤에서 주어가 바뀌면 문장을 나눈다(`doc/CLAUDE.md` "조사와 문장 호응" 참고).
* 띄어쓰기: "업그레이드 할"→"업그레이드할", "10여개"→"10여 개", "복제구성"→"복제 구성", "덮어 쓰다"→"덮어쓰다".

### 표기 규칙 위반

* 클래스·함수·필드·테이블·파일 이름이 마크업 없이 노출된 곳 → 백틱으로 감싼다.
  조사가 붙어 백틱이 깨지면 이중 백틱(``` ``JobRepository``는 ```)으로 쓴다.
* UI 라벨·문자열 인용의 대소문자가 원본과 다른 곳(예: 대시보드 실제 라벨과 대조).
* 같은 개념의 영문 표기 대소문자, 백틱/따옴표 선택이 책 전체 용례와 다른 곳.

### 사실·코드 정확성

* 본문에서 인용한 문자열을 같은 파일의 로그·코드 블록과 대조한다.
* `include::`로 인용한 코드는 빌드가 대조해 주지만, **본문의 인라인 코드 언급(함수·필드·경로 이름)은
  빌드가 검사하지 않는다.** 실제 저장소 코드와 grep으로 대조한다.
* **문법 입문 장(part2의 HTML·CSS·Go 장)의 예제는 저장소에 없는 직접 작성 코드다.**
  이 코드를 고치는 수정은 실제로 컴파일·실행해 확인해야 하고, 출력 예시 블록도 실행 결과와 맞춘다.
* 클래스·함수가 실제로 하는 일과 서술이 맞는지 본다.
* **기술적 사실을 바꾸는 수정은 보고에서 별도로 표시한다.** 저자가 실측으로 검증한 내용
  (예: 응답 시간·용량 수치)은 문장만 다듬고 내용은 건드리지 않는다.

## 고치지 않는 것

* `include::`로 인용되는 코드(원본이 저장소 코드라 원고에 없다). 인용 경로·태그 이름도 건드리지 않는다.
* 원고에 직접 쓴 `[source]` 블록 중 로그, 에러 메시지, 설정 파일, 프롬프트 예시의 원문.
  블록 안 문구가 표기 지침과 어긋나도 인용은 원문 그대로 둔다(블록 앞 설명 문장과 캡션은 교정 대상).
* `++++` 패스스루 블록의 HTML 구조(화면 캡처 배치). `fc-caption`의 문구는 교정 대상.
* 외부 링크의 URL. 표시 문구는 명백한 오타만 고친다.
* `{ch-…}` 토큰을 날 숫자로 풀지 않는다.
* 문단 순서 재배치처럼 편집 주관이 큰 재구성. 명백히 어색할 때만 최소한으로 고치고 보고한다.

## 표기 일관성 grep 대조

두 표기가 섞여 있을 때 임의로 고르지 말고 용례를 센다. 원고 전체는 아래 경로다.

```bash
cd doc
grep -c "표기A" intro.adoc preface.adoc part*/*.adoc appendix/*.adoc   # 파일별 건수
grep -rn "표기A\|표기B" intro.adoc preface.adoc part*/*.adoc appendix/*.adoc | head -20
```

* 책 전체가 한쪽으로 기울어 있으면 그 표기를 따른다.
* 책 전체가 혼용이면 `doc/CLAUDE.md` 지침·국어 규범에 맞는 쪽으로 **해당 파일 안에서만** 통일하고,
  다른 장에도 혼용이 남아 있다는 사실을 보고한다.
  (`doc/CLAUDE.md`에 정해진 예: "포맷터"가 아니라 "포매터", "도구 사슬"이 아니라 "툴체인".)

## 검증

1. 고친 패턴이 남아 있지 않은지 재확인한다.

    ```bash
    grep -n "프럼프트\|했었다\|알람" doc/대상파일.adoc   # 이번에 고친 패턴들로 구성
    ```

2. 책 빌드를 돌린다. 깨진 링크, `{ch-…}` 토큰 오류, AsciiDoc 부분집합 위반을 여기서 잡는다.

    ```bash
    cd doc && npm run build
    ```

3. 장 제목이나 차례가 바뀌었으면 `npm run pdf`도 돌린다.
4. 커밋은 사용자가 요청할 때만 한다.

## 보고 형식

수정 요약을 유형별로 정리한다. 항목마다 건수와 대표 예 한두 개를 든다.

* **저자 확인 필요** (맨 앞에): 기술적 사실을 바꾼 수정, 문법 입문 장 예제의 실행 재확인 필요 여부,
  용어 상자 소유권 위반, 책 전체에 남은 혼용 표기
* 오타·조사 교정
* 표기 통일 (무엇을 기준으로 통일했는지)
* 문장 다듬기 (중복 제거, 호응, 번역투, 금지 표현 제거)
* 검증 결과 (`npm run build` 통과 여부)
